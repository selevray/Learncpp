25.7 — Fonctions virtuelles pures, classes de base abstraites et classes interfaces

Fonctions virtuelles pures (abstraites) et classes de base abstraites

Jusqu'à présent, toutes les fonctions virtuelles que nous avons écrites possédaient un corps (une définition). Cependant, le C++ vous permet de créer un type particulier de fonction virtuelle appelée fonction virtuelle pure (ou fonction abstraite), qui n'a aucun corps ! Une fonction virtuelle pure sert simplement de substitut, destiné à être redéfini par les classes dérivées.

Pour créer une fonction virtuelle pure, au lieu de définir un corps pour la fonction, il suffit de lui affecter la valeur 0.

#include <string_view>

class Base
{
public:
    std::string_view sayHi() const { return "Hi"; } // a normal non-virtual function

    virtual std::string_view getName() const { return "Base"; } // a normal virtual function

    virtual int getValue() const = 0; // a pure virtual function

    int doSomething() = 0; // Compile error: can not set non-virtual functions to 0
};

Lorsque nous ajoutons une fonction virtuelle pure à notre classe, nous indiquons en fait : « c'est aux classes dérivées d'implémenter cette fonction ».

L'utilisation d'une fonction virtuelle pure a deux conséquences principales. Premièrement, toute classe possédant une ou plusieurs fonctions virtuelles pures devient une classe de base abstraite, ce qui signifie qu'elle ne peut pas être instanciée ! Examinons ce qui se passerait si nous pouvions créer une instance de Base :

int main()
{
    Base base {}; // We can't instantiate an abstract base class, but for the sake of example, pretend this was allowed
    base.getValue(); // what would this do?

    return 0;
}

Comme il n'existe aucune définition de getValue(), vers quoi base.getValue() se résoudrait-il ?

Deuxièmement, toute classe dérivée doit définir un corps pour cette fonction, sans quoi cette classe dérivée sera elle aussi considérée comme une classe de base abstraite.

Un exemple de fonction virtuelle pure

Examinons un exemple de fonction virtuelle pure en action. Dans une leçon précédente, nous avons écrit une classe de base simple Animal et dérivé les classes Cat et Dog à partir de celle-ci. Voici le code tel que nous l'avons laissé :

#include <string>
#include <string_view>

class Animal
{
protected:
    std::string m_name {};

    // We're making this constructor protected because
    // we don't want people creating Animal objects directly,
    // but we still want derived classes to be able to use it.
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

public:
    const std::string& getName() const { return m_name; }
    virtual std::string_view speak() const { return "???"; }

    virtual ~Animal() = default;
};

class Cat: public Animal
{
public:
    Cat(std::string_view name)
        : Animal{ name }
    {
    }

    std::string_view speak() const override { return "Meow"; }
};

class Dog: public Animal
{
public:
    Dog(std::string_view name)
        : Animal{ name }
    {
    }

    std::string_view speak() const override { return "Woof"; }
};

Nous avons empêché la création d'objets de type Animal en rendant le constructeur protégé. Il reste cependant possible de créer des classes dérivées qui ne redéfinissent pas la fonction speak().

Par exemple :

#include <iostream>
#include <string>
#include <string_view>

class Animal
{
protected:
    std::string m_name {};

    // We're making this constructor protected because
    // we don't want people creating Animal objects directly,
    // but we still want derived classes to be able to use it.
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

public:
    const std::string& getName() const { return m_name; }
    virtual std::string_view speak() const { return "???"; }

    virtual ~Animal() = default;
};

class Cow : public Animal
{
public:
    Cow(std::string_view name)
        : Animal{ name }
    {
    }

    // We forgot to redefine speak
};

int main()
{
    Cow cow{"Betsy"};
    std::cout << cow.getName() << " says " << cow.speak() << '\n';

    return 0;
}

Ce programme affiche :


Betsy says ???

Que s'est-il passé ? Nous avons oublié de redéfinir la fonction speak(), donc cow.speak() se résout vers Animal::speak(), ce qui n'est pas ce que nous voulions.

Une meilleure solution à ce problème consiste à utiliser une fonction virtuelle pure :

#include <string>
#include <string_view>

class Animal // This Animal is an abstract base class
{
protected:
    std::string m_name {};

public:
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

    const std::string& getName() const { return m_name; }
    virtual std::string_view speak() const = 0; // note that speak is now a pure virtual function

    virtual ~Animal() = default;
};

Il y a plusieurs points à noter ici. Premièrement, speak() est désormais une fonction virtuelle pure. Cela signifie qu'Animal est maintenant une classe de base abstraite et ne peut pas être instanciée. Par conséquent, nous n'avons plus besoin de rendre le constructeur protégé (même si cela ne fait pas de mal). Deuxièmement, comme notre classe Cow dérive d'Animal mais que nous n'avons pas défini Cow::speak(), Cow est également une classe de base abstraite. Si nous essayons maintenant de compiler ce code :

#include <iostream>
#include <string>
#include <string_view>

class Animal // This Animal is an abstract base class
{
protected:
    std::string m_name {};

public:
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

    const std::string& getName() const { return m_name; }
    virtual std::string_view speak() const = 0; // note that speak is now a pure virtual function

    virtual ~Animal() = default;
};

class Cow: public Animal
{
public:
    Cow(std::string_view name)
        : Animal{ name }
    {
    }

    // We forgot to redefine speak
};

int main()
{
    Cow cow{ "Betsy" };
    std::cout << cow.getName() << " says " << cow.speak() << '\n';

    return 0;
}

Le compilateur produira une erreur, car Cow est une classe de base abstraite et nous ne pouvons pas créer d'instances de classes de base abstraites :


prog.cc:35:9: error: variable type 'Cow' is an abstract class
   35 |     Cow cow{ "Betsy" };
      |         ^
prog.cc:17:30: note: unimplemented pure virtual method 'speak' in 'Cow'
   17 |     virtual std::string_view speak() const = 0; // note that speak is now a pure virtual function
      |                              ^

Cela nous indique que nous ne pourrons instancier Cow que si Cow fournit un corps pour speak().

Faisons-le :

#include <iostream>
#include <string>
#include <string_view>

class Animal // This Animal is an abstract base class
{
protected:
    std::string m_name {};

public:
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

    const std::string& getName() const { return m_name; }
    virtual std::string_view speak() const = 0; // note that speak is now a pure virtual function

    virtual ~Animal() = default;
};

class Cow: public Animal
{
public:
    Cow(std::string_view name)
        : Animal(name)
    {
    }

    std::string_view speak() const override { return "Moo"; }
};

int main()
{
    Cow cow{ "Betsy" };
    std::cout << cow.getName() << " says " << cow.speak() << '\n';

    return 0;
}

Ce programme se compile maintenant et affiche :


Betsy says Moo

Une fonction virtuelle pure est utile lorsque nous voulons placer une fonction dans la classe de base, mais que seules les classes dérivées savent ce qu'elle doit retourner. Une fonction virtuelle pure fait qu'il est impossible d'instancier la classe de base, et oblige les classes dérivées à définir ces fonctions avant de pouvoir être instanciées. Cela permet de s'assurer que les classes dérivées n'oublient pas de redéfinir les fonctions que la classe de base attendait d'elles.

Tout comme pour les fonctions virtuelles normales, les fonctions virtuelles pures peuvent être appelées à l'aide d'une référence (ou d'un pointeur) vers une classe de base :

int main()
{
    Cow cow{ "Betsy" };
    Animal& a{ cow };

    std::cout << a.speak(); // resolves to Cow::speak(), prints "Moo"

    return 0;
}

Dans l'exemple ci-dessus, a.speak() se résout vers Cow::speak() grâce à la résolution dynamique des fonctions virtuelles.

Rappel

Toute classe possédant des fonctions virtuelles pures devrait également posséder un destructeur virtuel.

Fonctions virtuelles pures avec définitions

Il s'avère que nous pouvons créer des fonctions virtuelles pures qui possèdent une définition :

#include <string>
#include <string_view>

class Animal // This Animal is an abstract base class
{
protected:
    std::string m_name {};

public:
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

    const std::string& getName() { return m_name; }
    virtual std::string_view speak() const = 0; // The = 0 means this function is pure virtual

    virtual ~Animal() = default;
};

std::string_view Animal::speak() const  // even though it has a definition
{
    return "buzz";
}

Dans ce cas, speak() est toujours considérée comme une fonction virtuelle pure à cause du « = 0 » (bien qu'elle possède une définition), et Animal reste une classe de base abstraite (et ne peut donc pas être instanciée). Toute classe qui hérite d'Animal doit fournir sa propre définition de speak(), sans quoi elle sera également considérée comme une classe de base abstraite.

Lorsqu'on fournit une définition pour une fonction virtuelle pure, cette définition doit être fournie séparément (et non en ligne).

Pour les utilisateurs de Visual Studio

Visual Studio autorise les déclarations de fonctions virtuelles pures à être des définitions, par exemple :

virtual std::string_view speak() const = 0
{
  return "buzz";
}

Ceci n'est pas conforme à la norme C++, et ne peut pas être désactivé.

Ce paradigme peut être utile lorsque vous voulez que votre classe de base fournisse une implémentation par défaut d'une fonction, tout en obligeant les classes dérivées à fournir leur propre implémentation. Cependant, si la classe dérivée se contente de l'implémentation par défaut fournie par la classe de base, elle peut simplement appeler directement l'implémentation de la classe de base. Par exemple :

#include <iostream>
#include <string>
#include <string_view>

class Animal // This Animal is an abstract base class
{
protected:
    std::string m_name {};

public:
    Animal(std::string_view name)
        : m_name(name)
    {
    }

    const std::string& getName() const { return m_name; }
    virtual std::string_view speak() const = 0; // note that speak is a pure virtual function

    virtual ~Animal() = default;
};

std::string_view Animal::speak() const
{
    return "buzz"; // some default implementation
}

class Dragonfly: public Animal
{

public:
    Dragonfly(std::string_view name)
        : Animal{name}
    {
    }

    std::string_view speak() const override// this class is no longer abstract because we defined this function
    {
        return Animal::speak(); // use Animal's default implementation
    }
};

int main()
{
    Dragonfly dfly{"Sally"};
    std::cout << dfly.getName() << " says " << dfly.speak() << '\n';

    return 0;
}

Le code ci-dessus affiche :


Sally says buzz

Cette possibilité n'est pas très couramment utilisée.

Un destructeur peut être rendu virtuel pur, mais il doit alors recevoir une définition afin de pouvoir être appelé lors de la destruction d'un objet dérivé.

Classes interfaces

Une classe interface (interface class) est une classe qui ne possède aucune variable membre et dont toutes les fonctions sont virtuelles pures ! Les interfaces sont utiles lorsque vous voulez définir les fonctionnalités que les classes dérivées doivent implémenter, tout en laissant entièrement à la classe dérivée le soin de décider comment elle implémente ces fonctionnalités.

Les noms des classes interfaces commencent souvent par un I. Voici un exemple de classe interface :

#include <string_view>

class IErrorLog
{
public:
    virtual bool openLog(std::string_view filename) = 0;
    virtual bool closeLog() = 0;

    virtual bool writeError(std::string_view errorMessage) = 0;

    virtual ~IErrorLog() {} // make a virtual destructor in case we delete an IErrorLog pointer, so the proper derived destructor is called
};

Toute classe héritant d'IErrorLog doit fournir des implémentations pour les trois fonctions afin de pouvoir être instanciée. Vous pourriez dériver une classe nommée FileErrorLog, où openLog() ouvre un fichier sur le disque, closeLog() ferme le fichier et writeError() écrit le message dans ce fichier. Vous pourriez dériver une autre classe nommée ScreenErrorLog, où openLog() et closeLog() ne font rien, et writeError() affiche le message dans une fenêtre contextuelle à l'écran.

Supposons maintenant que vous ayez besoin d'écrire du code qui utilise un journal d'erreurs. Si vous écrivez votre code en incluant directement FileErrorLog ou ScreenErrorLog, vous êtes en pratique contraint d'utiliser ce type de journal d'erreurs (du moins sans recoder votre programme). Par exemple, la fonction suivante oblige en fait les appelants de mySqrt() à utiliser un FileErrorLog, ce qui ne correspond peut-être pas à ce qu'ils souhaitent.

#include <cmath> // for sqrt()

double mySqrt(double value, FileErrorLog& log)
{
    if (value < 0.0)
    {
        log.writeError("Tried to take square root of value less than 0");
        return 0.0;
    }

    return std::sqrt(value);
}

Une bien meilleure façon d'implémenter cette fonction consiste à utiliser IErrorLog à la place :

#include <cmath> // for sqrt()
double mySqrt(double value, IErrorLog& log)
{
    if (value < 0.0)
    {
        log.writeError("Tried to take square root of value less than 0");
        return 0.0;
    }

    return std::sqrt(value);
}

Désormais, l'appelant peut passer n'importe quelle classe conforme à l'interface IErrorLog. S'il souhaite que l'erreur soit écrite dans un fichier, il peut passer une instance de FileErrorLog. S'il souhaite un affichage à l'écran, il peut passer une instance de ScreenErrorLog. Ou s'il souhaite faire quelque chose que vous n'avez même pas envisagé, comme envoyer un e-mail à quelqu'un en cas d'erreur, il peut dériver une nouvelle classe d'IErrorLog (par exemple EmailErrorLog) et utiliser une instance de celle-ci ! En utilisant IErrorLog, votre fonction devient plus indépendante et plus souple.

N'oubliez pas d'inclure un destructeur virtuel dans vos classes interfaces, afin que le destructeur dérivé approprié soit appelé si un pointeur vers l'interface est supprimé.

Les classes interfaces sont devenues extrêmement populaires, car elles sont faciles à utiliser, à étendre et à maintenir. En fait, certains langages modernes, comme Java et C#, ont ajouté un mot-clé « interface » qui permet aux programmeurs de définir directement une classe interface sans avoir à marquer explicitement toutes les fonctions membres comme abstraites. De plus, bien que Java et C# n'autorisent pas l'héritage multiple pour les classes normales, ils permettent d'hériter de plusieurs interfaces à la fois. Comme les interfaces n'ont ni données ni corps de fonctions, elles évitent bon nombre des problèmes traditionnels de l'héritage multiple tout en offrant une grande partie de sa souplesse.

Fonctions virtuelles pures et table virtuelle

Par cohérence, les classes abstraites possèdent tout de même des tables virtuelles. Un constructeur ou un destructeur d'une classe abstraite peut appeler une fonction virtuelle, et celle-ci doit se résoudre vers la fonction appropriée (dans la même classe, puisque les classes dérivées n'ont soit pas encore été construites, soit déjà été détruites).

L'entrée de la table virtuelle d'une classe possédant une fonction virtuelle pure contient généralement soit un pointeur nul, soit un pointeur vers une fonction générique qui affiche une erreur (cette fonction porte parfois le nom de __purecall).
