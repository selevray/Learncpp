25.2 — Fonctions virtuelles et polymorphisme

Dans la leçon précédente sur les pointeurs et références vers la classe de base d'objets dérivés, nous avons examiné plusieurs exemples où l'utilisation de pointeurs ou de références vers une classe de base pouvait simplifier le code. Cependant, dans chaque cas, nous nous heurtions au même problème : le pointeur ou la référence de base ne pouvait appeler que la version de base d'une fonction, et non une version dérivée.

Voici un exemple simple de ce comportement :

#include <iostream>
#include <string_view>

class Base
{
public:
    std::string_view getName() const { return "Base"; }
};

class Derived: public Base
{
public:
    std::string_view getName() const { return "Derived"; }
};

int main()
{
    Derived derived {};
    Base& rBase{ derived };
    std::cout << "rBase is a " << rBase.getName() << '\n';

    return 0;
}

Ce programme affiche :


rBase is a Base

Comme rBase est une référence de type Base, il appelle Base::getName(), même s'il référence en réalité la partie Base d'un objet Derived.

Dans cette leçon, nous allons montrer comment résoudre ce problème à l'aide des fonctions virtuelles.

Fonctions virtuelles

Une fonction virtuelle (virtual function) est un type particulier de fonction membre qui, lorsqu'elle est appelée, se résout en la version la plus dérivée de la fonction, pour le type réel de l'objet référencé ou pointé.

Une fonction dérivée est considérée comme correspondante si elle a la même signature (nom, types des paramètres et caractère const) et le même type de retour que la version de base de la fonction. De telles fonctions sont appelées redéfinitions (overrides).

Pour rendre une fonction virtuelle, il suffit de placer le mot-clé virtual devant sa déclaration.

Voici l'exemple précédent avec une fonction virtuelle :

#include <iostream>
#include <string_view>

class Base
{
public:
    virtual std::string_view getName() const { return "Base"; } // note : ajout du mot-clé virtual
};

class Derived: public Base
{
public:
    virtual std::string_view getName() const { return "Derived"; }
};

int main()
{
    Derived derived {};
    Base& rBase{ derived };
    std::cout << "rBase is a " << rBase.getName() << '\n';

    return 0;
}

Ce programme affiche :


rBase is a Derived

Astuce

Certains compilateurs modernes peuvent signaler une erreur concernant la présence de fonctions virtuelles et d'un destructeur non virtuel accessible. Si c'est le cas, ajoutez un destructeur virtuel à la classe de base. Dans le programme ci-dessus, ajoutez ceci à la définition de Base :

    virtual ~Base() = default;

Nous aborderons les destructeurs virtuels dans la leçon 25.4 -- Destructeurs virtuels, affectation virtuelle et neutralisation de la virtualisation.

Comme rBase est une référence à la partie Base d'un objet Derived, lorsque rBase.getName() est évalué, il se résoudrait normalement en Base::getName(). Cependant, Base::getName() est virtuelle, ce qui demande au programme de rechercher s'il existe une version plus dérivée de la fonction pour un objet Derived. Dans ce cas, l'appel se résout en Derived::getName() !

Examinons un exemple légèrement plus complexe :

#include <iostream>
#include <string_view>

class A
{
public:
    virtual std::string_view getName() const { return "A"; }
};

class B: public A
{
public:
    virtual std::string_view getName() const { return "B"; }
};

class C: public B
{
public:
    virtual std::string_view getName() const { return "C"; }
};

class D: public C
{
public:
    virtual std::string_view getName() const { return "D"; }
};

int main()
{
    C c {};
    A& rBase{ c };
    std::cout << "rBase is a " << rBase.getName() << '\n';

    return 0;
}

Que pensez-vous que ce programme affiche ?

Analysons son fonctionnement. Tout d'abord, nous instancions un objet de classe C. rBase est une référence de type A, que nous initialisons pour qu'elle référence la partie A de l'objet C. Enfin, nous appelons rBase.getName(). rBase.getName() se résoudrait en A::getName(). Cependant, A::getName() est virtuelle, donc le compilateur appelle la version la plus dérivée correspondant entre A et C. Dans ce cas, il s'agit de C::getName(). Notez qu'il n'appellera pas D::getName(), car notre objet d'origine était un C et non un D : seules les fonctions situées entre A et C sont prises en compte.

Par conséquent, notre programme affiche :


rBase is a C

Notez que la résolution des fonctions virtuelles ne fonctionne que lorsqu'une fonction membre virtuelle est appelée à travers un pointeur ou une référence vers un objet de type classe. Cela fonctionne parce que le compilateur peut distinguer le type du pointeur ou de la référence du type de l'objet pointé ou référencé, comme dans l'exemple ci-dessus.

Appeler directement une fonction membre virtuelle sur un objet (et non à travers un pointeur ou une référence) invoquera toujours la fonction membre appartenant au type de cet objet. Par exemple :

C c{};
std::cout << c.getName(); // appelle toujours C::getName

A a { c }; // copie la partie A de c dans a (à ne pas faire)
std::cout << a.getName(); // appelle toujours A::getName

Point clé

La résolution des fonctions virtuelles ne fonctionne que lorsqu'une fonction membre est appelée à travers un pointeur ou une référence vers un objet de type classe.

Polymorphisme

En programmation, le polymorphisme (polymorphism) désigne la capacité d'une entité à prendre plusieurs formes (le terme « polymorphisme » signifie littéralement « plusieurs formes »). Par exemple, considérons les deux déclarations de fonctions suivantes :

int add(int, int);
double add(double, double);

L'identifiant add possède deux formes : add(int, int) et add(double, double).

Le polymorphisme à la compilation (compile-time polymorphism) désigne les formes de polymorphisme résolues par le compilateur. Elles incluent la résolution de surcharge des fonctions, ainsi que la résolution des modèles (templates).

Le polymorphisme à l'exécution (runtime polymorphism) désigne les formes de polymorphisme résolues à l'exécution. Il inclut la résolution des fonctions virtuelles.

Un exemple plus complexe

Reprenons l'exemple de la classe Animal que nous avons utilisé dans la leçon précédente. Voici la classe d'origine, accompagnée d'un code de test :

#include <iostream>
#include <string>
#include <string_view>

class Animal
{
protected:
    std::string m_name {};

    // Nous rendons ce constructeur protégé car
    // nous ne voulons pas que l'on crée directement des objets Animal,
    // mais nous voulons tout de même que les classes dérivées puissent l'utiliser.
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

public:
    const std::string& getName() const { return m_name; }
    std::string_view speak() const { return "???"; }
};

class Cat: public Animal
{
public:
    Cat(std::string_view name)
        : Animal{ name }
    {
    }

    std::string_view speak() const { return "Meow"; }
};

class Dog: public Animal
{
public:
    Dog(std::string_view name)
        : Animal{ name }
    {
    }

    std::string_view speak() const { return "Woof"; }
};

void report(const Animal& animal)
{
    std::cout << animal.getName() << " says " << animal.speak() << '\n';
}

int main()
{
    Cat cat{ "Fred" };
    Dog dog{ "Garbo" };

    report(cat);
    report(dog);

    return 0;
}

Ce programme affiche :


Fred says ???
Garbo says ???

Voici la classe équivalente dans laquelle la fonction speak() est devenue virtuelle :

#include <iostream>
#include <string>
#include <string_view>

class Animal
{
protected:
    std::string m_name {};

    // Nous rendons ce constructeur protégé car
    // nous ne voulons pas que l'on crée directement des objets Animal,
    // mais nous voulons tout de même que les classes dérivées puissent l'utiliser.
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

public:
    const std::string& getName() const { return m_name; }
    virtual std::string_view speak() const { return "???"; }
};

class Cat: public Animal
{
public:
    Cat(std::string_view name)
        : Animal{ name }
    {
    }

    virtual std::string_view speak() const { return "Meow"; }
};

class Dog: public Animal
{
public:
    Dog(std::string_view name)
        : Animal{ name }
    {
    }

    virtual std::string_view speak() const { return "Woof"; }
};

void report(const Animal& animal)
{
    std::cout << animal.getName() << " says " << animal.speak() << '\n';
}

int main()
{
    Cat cat{ "Fred" };
    Dog dog{ "Garbo" };

    report(cat);
    report(dog);

    return 0;
}

Ce programme produit le résultat suivant :


Fred says Meow
Garbo says Woof

Ça fonctionne !

Lorsque animal.speak() est évaluée, le programme constate que Animal::speak() est une fonction virtuelle. Dans le cas où animal référence la partie Animal d'un objet Cat, le programme examine toutes les classes situées entre Animal et Cat pour voir s'il peut trouver une fonction plus dérivée. Ici, il trouve Cat::speak(). Dans le cas où animal référence la partie Animal d'un objet Dog, le programme résout l'appel en Dog::speak().

Notez que nous n'avons pas rendu Animal::getName() virtuelle. En effet, getName() n'est redéfinie dans aucune des classes dérivées : il n'y a donc pas lieu de le faire.

De même, l'exemple suivant utilisant un tableau fonctionne désormais comme prévu :

Cat fred{ "Fred" };
Cat misty{ "Misty" };
Cat zeke{ "Zeke" };

Dog garbo{ "Garbo" };
Dog pooky{ "Pooky" };
Dog truffle{ "Truffle" };

// Crée un tableau de pointeurs vers des animaux, et initialise ces pointeurs avec nos objets Cat et Dog
Animal* animals[]{ &fred, &garbo, &misty, &pooky, &truffle, &zeke };

for (const auto* animal : animals)
    std::cout << animal->getName() << " says " << animal->speak() << '\n';

Ce qui produit le résultat :


Fred says Meow
Garbo says Woof
Misty says Meow
Pooky says Woof
Truffle says Woof
Zeke says Meow

Bien que ces deux exemples n'utilisent que Cat et Dog, toute autre classe que nous dériverons de Animal fonctionnerait également avec notre fonction report() et notre tableau d'animaux, sans modification supplémentaire ! C'est sans doute le plus grand avantage des fonctions virtuelles : la possibilité de structurer votre code de manière à ce que les nouvelles classes dérivées fonctionnent automatiquement avec l'ancien code, sans modification !

Une mise en garde : la signature de la fonction de la classe dérivée doit exactement correspondre à celle de la fonction virtuelle de la classe de base pour être utilisée. Si la fonction dérivée a des types de paramètres différents, le programme se compilera probablement sans problème, mais la fonction virtuelle ne se résoudra pas comme prévu. Dans la prochaine leçon, nous verrons comment s'en prémunir.

Notez que si une fonction est marquée comme virtuelle, toutes les redéfinitions correspondantes dans les classes dérivées sont également considérées implicitement comme virtuelles, même si elles ne sont pas explicitement marquées comme telles.

Règle

Si une fonction est virtuelle, toutes les redéfinitions correspondantes dans les classes dérivées sont implicitement virtuelles.

Ce n'est pas vrai dans l'autre sens : une redéfinition virtuelle dans une classe dérivée ne rend pas implicitement virtuelle la fonction de la classe de base.

Types de retour des fonctions virtuelles

Dans les circonstances normales, le type de retour d'une fonction virtuelle et celui de sa redéfinition doivent correspondre. Considérez l'exemple suivant :

class Base
{
public:
    virtual int getValue() const { return 5; }
};

class Derived: public Base
{
public:
    virtual double getValue() const { return 6.78; }
};

Dans ce cas, Derived::getValue() n'est pas considérée comme une redéfinition correspondante de Base::getValue() et la compilation échouera.

Ne pas appeler de fonctions virtuelles depuis les constructeurs ou les destructeurs

Voici un autre piège qui attend souvent les programmeurs débutants. Vous ne devez pas appeler de fonctions virtuelles depuis les constructeurs ou les destructeurs. Pourquoi ?

Rappelez-vous que lorsqu'un objet de classe dérivée est créé, la partie Base est construite en premier. Si vous appeliez une fonction virtuelle depuis le constructeur de Base, alors que la partie Derived de la classe n'a pas encore été créée, il serait impossible d'appeler la version Derived de la fonction, car il n'existe pas encore d'objet Derived sur lequel elle pourrait travailler. En C++, c'est la version de Base qui sera appelée.

Un problème similaire existe pour les destructeurs. Si vous appelez une fonction virtuelle dans le destructeur de la classe de base, elle se résoudra toujours en la version de la classe de base, puisque la partie Derived de la classe aura déjà été détruite.

Bonne pratique

N'appelez jamais de fonctions virtuelles depuis les constructeurs ou les destructeurs.

L'inconvénient des fonctions virtuelles

Puisque la plupart du temps vous voudrez que vos fonctions soient virtuelles, pourquoi ne pas rendre toutes les fonctions virtuelles ? La réponse est que cela est inefficace : la résolution d'un appel de fonction virtuelle prend plus de temps que celle d'un appel de fonction ordinaire.

De plus, pour que les fonctions virtuelles fonctionnent, le compilateur doit allouer un pointeur supplémentaire pour chaque objet d'une classe possédant des fonctions virtuelles. Cela ajoute une surcharge importante aux objets qui, sans cela, seraient de petite taille. Nous reviendrons sur ce point dans les prochaines leçons de ce chapitre.
