9.4 — Détection et gestion des erreurs

Dans la leçon 9.3 -- Erreurs sémantiques courantes en C++, nous avons passé en revue plusieurs types d'erreurs sémantiques que rencontrent les programmeurs débutants en C++. Lorsqu'une erreur résulte d'une mauvaise utilisation d'une fonctionnalité du langage ou d'une erreur de logique, il suffit de la corriger.

Mais la plupart des erreurs d'un programme ne proviennent pas d'une mauvaise utilisation involontaire des fonctionnalités du langage. Elles proviennent plutôt d'hypothèses erronées faites par le programmeur, et/ou d'un manque de détection et de gestion appropriées des erreurs.

Par exemple, dans une fonction conçue pour rechercher la note d'un élève, vous pourriez avoir supposé que :

  • L'élève recherché existe.
  • Tous les noms d'élèves sont uniques.
  • La classe utilise une notation par lettres (et non une notation par réussite/échec).

Que se passe-t-il si l'une de ces hypothèses est fausse ? Si le programmeur n'a pas anticipé ces cas, le programme risque de mal fonctionner ou de planter lorsque ces cas se présentent (généralement à un moment ultérieur, bien après l'écriture de la fonction).

Les erreurs d'hypothèses surviennent typiquement à trois endroits clés :

  • Lorsqu'une fonction renvoie une valeur, le programmeur peut avoir supposé que la fonction appelée avait réussi, alors qu'elle ne l'avait pas fait.
  • Lorsqu'un programme reçoit des données (de l'utilisateur ou d'un fichier), le programmeur peut avoir supposé que ces données étaient au bon format et sémantiquement valides, alors qu'elles ne l'étaient pas.
  • Lorsqu'une fonction est appelée, le programmeur peut avoir supposé que les arguments seraient sémantiquement valides, alors qu'ils ne l'étaient pas.

Beaucoup de programmeurs débutants écrivent du code et ne testent que le chemin heureux (happy path) : les cas où tout se passe bien. Mais vous devriez aussi prévoir et tester vos chemins malheureux (sad paths), c'est-à-dire les situations où les choses peuvent mal tourner, et tourneront mal. Dans la leçon 3.10 -- Repérer les problèmes avant qu'ils ne deviennent des difficultés, nous avons défini la programmation défensive comme la pratique consistant à anticiper toutes les façons dont un logiciel peut être mal utilisé, que ce soit par les utilisateurs finaux ou par les développeurs (le programmeur lui-même ou d'autres). Une fois qu'un mauvais usage a été anticipé (ou découvert), il reste à le gérer.

Dans cette leçon, nous verrons des stratégies de gestion des erreurs (que faire lorsque les choses tournent mal) à l'intérieur d'une fonction. Dans les leçons suivantes, nous aborderons la validation des saisies utilisateur, puis nous présenterons un outil utile pour documenter et valider les hypothèses.

Gérer les erreurs dans les fonctions

Une fonction peut échouer pour de nombreuses raisons : l'appelant peut avoir transmis un argument de valeur invalide, ou quelque chose peut échouer dans le corps de la fonction. Par exemple, une fonction qui ouvre un fichier en lecture peut échouer si le fichier est introuvable.

Dans ce cas, vous disposez de plusieurs options. Il n'existe pas de meilleure façon de gérer une erreur : tout dépend de la nature du problème et de la possibilité ou non de le corriger.

Quatre stratégies générales peuvent être utilisées :

  • Gérer l'erreur à l'intérieur de la fonction
  • Renvoyer l'erreur à l'appelant pour qu'il s'en occupe
  • Arrêter le programme
  • Lever une exception

Gérer l'erreur à l'intérieur de la fonction

Si c'est possible, la meilleure stratégie consiste à se rétablir de l'erreur dans la fonction même où elle s'est produite, afin que l'erreur soit contenue et corrigée sans affecter le code situé en dehors de la fonction. Deux options s'offrent alors : réessayer jusqu'au succès, ou annuler l'opération en cours.

Si l'erreur est due à un événement hors du contrôle du programme, celui-ci peut réessayer jusqu'à réussir. Par exemple, si le programme a besoin d'une connexion Internet et que l'utilisateur l'a perdue, le programme peut afficher un avertissement, puis utiliser une boucle pour vérifier périodiquement la connectivité. De même, si l'utilisateur a saisi une valeur invalide, le programme peut lui demander de réessayer, et boucler jusqu'à ce qu'il saisisse une valeur valide. Nous présenterons des exemples de gestion des saisies invalides et de réessai par boucle dans la prochaine leçon (9.5 -- std::cin et gestion des saisies invalides).

Une autre stratégie consiste simplement à ignorer l'erreur et/ou à annuler l'opération. Par exemple :

// Échec silencieux si y=0
void printIntDivision(int x, int y)
{
    if (y != 0)
        std::cout << x / y;
}

Dans l'exemple ci-dessus, si l'utilisateur a transmis une valeur invalide pour y, nous ignorons simplement la demande d'affichage du résultat de la division. Le principal inconvénient de cette approche est que l'appelant ou l'utilisateur n'ont aucun moyen de savoir que quelque chose s'est mal passé. Dans ce cas, afficher un message d'erreur peut être utile :

void printIntDivision(int x, int y)
{
    if (y != 0)
        std::cout << x / y;
    else
        std::cout << "Error: Could not divide by zero\n";
}

Cependant, si la fonction appelante attend de la fonction appelée une valeur de retour ou un effet de bord utile, ignorer simplement l'erreur n'est peut-être pas une option.

Renvoyer les erreurs à l'appelant

Dans de nombreux cas, l'erreur ne peut pas raisonnablement être gérée dans la fonction qui la détecte. Par exemple, considérons la fonction suivante :

int doIntDivision(int x, int y)
{
    return x / y;
}

Si y vaut 0, que faire ? On ne peut pas simplement sauter la logique du programme, car la fonction doit renvoyer une valeur. On ne doit pas non plus demander à l'utilisateur de saisir une nouvelle valeur pour y, car il s'agit d'une fonction de calcul, et y introduire des routines de saisie peut ou non être approprié selon le programme qui appelle cette fonction.

Dans ces cas, la meilleure option peut être de renvoyer l'erreur à l'appelant, en espérant qu'il saura la traiter.

Comment faire ?

Si la fonction a un type de retour void, on peut la modifier pour qu'elle renvoie un bool indiquant le succès ou l'échec. Par exemple, au lieu de :

void printIntDivision(int x, int y)
{
    if (y != 0)
        std::cout << x / y;
    else
        std::cout << "Error: Could not divide by zero\n";
}

On peut écrire :

bool printIntDivision(int x, int y)
{
    if (y == 0)
    {
        std::cout << "Error: could not divide by zero\n";
        return false;
    }

    std::cout << x / y;

    return true;
}

Ainsi, l'appelant peut vérifier la valeur de retour pour savoir si la fonction a échoué pour une raison quelconque.

Si la fonction renvoie une valeur normale, les choses se compliquent un peu. Dans certains cas, toute la plage des valeurs de retour n'est pas utilisée. On peut alors utiliser une valeur de retour qui ne pourrait normalement pas se produire pour signaler une erreur. Par exemple, considérons la fonction suivante :

// L'inverse de x vaut 1/x
double reciprocal(double x)
{
    return 1.0 / x;
}

L'inverse d'un nombre x est défini comme 1/x, et un nombre multiplié par son inverse vaut 1.

Mais que se passe-t-il si l'utilisateur appelle cette fonction avec reciprocal(0.0) ? On obtient une erreur de division par zéro et un plantage du programme. Il est donc clair qu'il faut se protéger contre ce cas. Or cette fonction doit renvoyer un double, alors quelle valeur renvoyer ? Il se trouve que cette fonction ne produira jamais 0.0 comme résultat légitime : on peut donc renvoyer 0.0 pour indiquer un cas d'erreur.

// L'inverse de x vaut 1/x, renvoie 0.0 si x=0
constexpr double error_no_reciprocal { 0.0 }; // peut aussi être placé dans un espace de noms

double reciprocal(double x)
{
    if (x == 0.0)
       return error_no_reciprocal;

    return 1.0 / x;
}

Une valeur sentinelle (sentinel value) est une valeur ayant une signification particulière dans le contexte d'une fonction ou d'un algorithme. Dans notre fonction reciprocal() ci-dessus, 0.0 est une valeur sentinelle indiquant l'échec de la fonction. L'appelant peut tester la valeur de retour pour voir si elle correspond à la valeur sentinelle : si c'est le cas, il sait que la fonction a échoué. Bien que les fonctions renvoient souvent directement la valeur sentinelle, renvoyer une constante qui décrit cette valeur sentinelle améliore la lisibilité.

En revanche, si la fonction peut produire toute la plage des valeurs de retour, utiliser une valeur sentinelle pour signaler une erreur pose problème, car l'appelant ne peut pas distinguer une valeur valide d'une valeur d'erreur.

Contenu associé

Dans un tel cas, renvoyer un std::optional (ou un std::expected) serait un meilleur choix. Nous présentons std::optional dans la leçon 12.15 -- std::optional.

Erreurs fatales

Si l'erreur est si grave que le programme ne peut pas continuer à fonctionner correctement, on parle d'erreur non récupérable (aussi appelée erreur fatale). Dans ce cas, le mieux est de terminer le programme. Si votre code se trouve dans main() ou dans une fonction appelée directement depuis main(), il suffit de faire en sorte que main() renvoie un code d'état non nul. En revanche, si vous êtes profondément imbriqué dans une sous-fonction, il peut être malaisé, voire impossible, de remonter l'erreur jusqu'à main(). Dans ce cas, on peut utiliser une instruction d'arrêt (halt statement), comme std::exit().

Par exemple :

double doIntDivision(int x, int y)
{
    if (y == 0)
    {
        std::cout << "Error: Could not divide by zero\n";
        std::exit(1);
    }
    return x / y;
}

Exceptions

Renvoyer une erreur depuis une fonction vers l'appelant est compliqué, et les nombreuses façons de le faire mènent à des incohérences, et les incohérences mènent aux erreurs. C++ propose donc un moyen entièrement distinct de transmettre les erreurs à l'appelant : les exceptions.

L'idée de base est la suivante : lorsqu'une erreur survient, une exception est « levée » (thrown). Si la fonction courante ne « capture » (catch) pas l'erreur, l'appelant de la fonction a la possibilité de la capturer. Si l'appelant ne la capture pas non plus, l'appelant de l'appelant a à son tour sa chance, et ainsi de suite. L'erreur remonte progressivement la pile d'appels, jusqu'à être capturée et gérée (l'exécution reprend alors normalement), ou jusqu'à ce que main() ne parvienne pas à la gérer, auquel cas le programme se termine avec une erreur d'exception.

Nous traiterons la gestion des exceptions dans le chapitre 27 de cette série de tutoriels.

Quand utiliser std::cout, std::cerr ou la journalisation

Dans la leçon 3.4 -- Techniques de base de débogage, nous avons présenté std::cerr. Vous vous demandez peut-être quand (ou si) utiliser std::cerr, std::cout ou l'écriture dans un fichier journal.

Par défaut, std::cout et std::cerr affichent tous deux du texte dans la console. Cependant, les systèmes d'exploitation modernes permettent de rediriger les flux de sortie vers des fichiers, afin que la sortie puisse être conservée pour être examinée ou traitée automatiquement plus tard.

Pour cette discussion, il est utile de distinguer deux types d'applications :

  • Les applications interactives sont celles avec lesquelles l'utilisateur interagit après leur lancement. La plupart des applications autonomes, comme les jeux et les lecteurs de musique, entrent dans cette catégorie.
  • Les applications non interactives sont des applications qui n'ont pas besoin d'une interaction avec l'utilisateur pour fonctionner. La sortie de ces programmes peut servir d'entrée à une autre application.

Parmi les applications non interactives, il existe deux types :

  • Les outils (tools) sont des applications non interactives généralement lancées pour produire un résultat immédiat, puis qui se terminent après l'avoir produit. Un exemple est la commande grep d'Unix, un utilitaire qui recherche dans un texte les lignes correspondant à un motif donné.
  • Les services (services) sont des applications non interactives qui fonctionnent généralement en silence en arrière-plan pour assurer une fonction continue. Un exemple serait un antivirus.

Voici quelques règles empiriques :

  • Utilisez std::cout pour tout texte classique destiné à l'utilisateur.
  • Pour un programme interactif, utilisez std::cout pour les messages d'erreur ordinaires destinés à l'utilisateur (par exemple « Votre saisie est invalide »). Utilisez std::cerr ou un fichier journal pour les informations d'état et de diagnostic qui peuvent aider à identifier un problème mais qui ne sont probablement pas intéressantes pour l'utilisateur normal. Cela peut inclure les avertissements et erreurs techniques (par exemple une mauvaise entrée pour la fonction x), les mises à jour d'état (par exemple « fichier x ouvert avec succès », « échec de la connexion au service internet x »), le pourcentage d'avancement de tâches longues (par exemple « encodage terminé à 50 % »), etc.
  • Pour une application non interactive (outil ou service), utilisez std::cerr uniquement pour les messages d'erreur (par exemple « impossible d'ouvrir le fichier x »). Cela permet d'afficher ou d'analyser les erreurs séparément de la sortie normale.
  • Pour tout type d'application de nature transactionnelle (par exemple une application qui traite des événements précis, comme un navigateur web interactif ou un serveur web non interactif), utilisez un fichier journal pour produire un historique transactionnel des événements, consultable ultérieurement. Il peut contenir le nom du fichier en cours de traitement, les mises à jour du pourcentage d'avancement, l'horodatage du début de certaines étapes de calcul, les messages d'avertissement et d'erreur, etc.
