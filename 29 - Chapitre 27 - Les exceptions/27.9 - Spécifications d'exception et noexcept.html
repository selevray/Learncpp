27.9 — Spécifications d'exception et noexcept

(Remerciements à Koe, qui a fourni la première version de cette leçon !)

En regardant la déclaration typique d'une fonction, il n'est pas possible de savoir si elle peut lever une exception :

int doSomething(); // cette fonction peut-elle lever une exception ?

Dans l'exemple ci-dessus, doSomething() peut-elle lever une exception ? Ce n'est pas clair. Pourtant, la réponse est importante dans certains contextes. Dans la leçon 27.8 -- Dangers et inconvénients des exceptions, nous avons expliqué qu'une exception qui sort d'un destructeur pendant le déroulement de la pile (stack unwinding) provoque l'arrêt du programme. Si doSomething() peut lever une exception, l'appeler depuis un destructeur (ou depuis tout autre endroit où une exception levée n'est pas souhaitable) est risqué. Nous pourrions bien sûr faire en sorte que le destructeur gère les exceptions levées par doSomething() (afin que ces exceptions ne se propagent pas hors du destructeur), mais il faudrait penser à le faire, et s'assurer de couvrir tous les types d'exceptions susceptibles d'être levées.

Les commentaires peuvent aider à indiquer si une fonction lève des exceptions (et, le cas échéant, lesquelles), mais la documentation peut devenir obsolète, et le compilateur ne vérifie pas les commentaires.

Les spécifications d'exception (exception specifications) sont un mécanisme du langage conçu à l'origine pour documenter le type d'exceptions qu'une fonction peut lever, dans le cadre de sa spécification. Bien que la plupart de ces spécifications soient aujourd'hui obsolètes (deprecated) ou supprimées, une spécification d'exception utile a été ajoutée pour les remplacer ; c'est elle que nous allons étudier dans cette leçon.

Le spécificateur noexcept

En C++, toutes les fonctions sont classées soit comme non lanceuses (non-throwing), soit comme potentiellement lanceuses (potentially throwing). Une fonction non lanceuse est une fonction qui promet de ne pas lever d'exceptions visibles par l'appelant. Une fonction potentiellement lanceuse peut lever des exceptions visibles par l'appelant.

Pour déclarer qu'une fonction est non lanceuse, nous pouvons utiliser le spécificateur noexcept (noexcept specifier). Pour cela, on place mot-clé noexcept dans la déclaration de la fonction, à droite de la liste des paramètres :

void doSomething() noexcept; // cette fonction est spécifiée comme non lanceuse

Notez que noexcept n'empêche pas réellement la fonction de lever des exceptions, ni d'appeler d'autres fonctions potentiellement lanceuses. C'est autorisé, à condition que la fonction noexcept intercepte et gère ces exceptions en interne, et que ces exceptions ne sortent pas de la fonction noexcept.

Si une exception non gérée sortait d'une fonction noexcept, std::terminate serait appelée (même s'il existe un gestionnaire d'exceptions qui aurait pu la traiter plus haut dans la pile). Et si std::terminate est appelée depuis l'intérieur d'une fonction noexcept, le déroulement de la pile peut ou non avoir lieu (selon l'implémentation et les optimisations), ce qui signifie que vos objets peuvent ou non être correctement détruits avant la fin du programme.

Point clé

La promesse qu'une fonction noexcept fait de ne pas lever d'exceptions visibles par l'appelant est une promesse contractuelle, et non une garantie imposée par le compilateur. Ainsi, bien qu'appeler une fonction noexcept doive être sûr, tout bogue de gestion des exceptions dans la fonction noexcept qui rompt ce contrat provoquera l'arrêt du programme ! Cela ne devrait pas arriver, mais les bogues ne devraient pas non plus arriver.

Pour cette raison, il est préférable que les fonctions noexcept ne manipulent pas du tout les exceptions, ni n'appellent de fonctions potentiellement lanceuses susceptibles de lever une exception. Une fonction noexcept ne peut pas comporter de bogue de gestion des exceptions si aucune exception ne peut être levée !

De même que des fonctions ne différant que par leur valeur de retour ne peuvent pas être surchargées, des fonctions ne différant que par leur spécification d'exception ne peuvent pas être surchargées.

Illustration du comportement des fonctions noexcept et des exceptions

Le programme suivant illustre le comportement des fonctions noexcept et des exceptions dans différents cas :

// Remerciements à yellowEmu pour la première version de ce programme
#include <iostream>

class Doomed
{
public:
    ~Doomed()
    {
        std::cout << "Doomed destructed\n";
    }
};

void thrower()
{
    std::cout << "Throwing exception\n";
    throw 1;
}

void pt()
{
    std::cout << "pt (potentally throwing) called\n";
    // Cet objet sera détruit pendant le déroulement de la pile (s'il a lieu)
    Doomed doomed{};
    thrower();
    std::cout << "This never prints\n";
}

void nt() noexcept
{
    std::cout << "nt (noexcept) called\n";
    // Cet objet sera détruit pendant le déroulement de la pile (s'il a lieu)
    Doomed doomed{};
    thrower();
    std::cout << "this never prints\n";
}

void tester(int c) noexcept
{
    std::cout << "tester (noexcept) case " << c << " called\n";
    try
    {
        (c == 1) ? pt() : nt();
    }
    catch (...)
    {
        std::cout << "tester caught exception\n";
    }
}

int main()
{
    std::cout << std::unitbuf; // vide le tampon après chaque insertion
    std::cout << std::boolalpha; // affiche les booléens sous forme true/false
    tester(1);
    std::cout << "Test successful\n\n";
    tester(2);
    std::cout << "Test successful\n";

    return 0;
}

Sur la machine de l'auteur, ce programme a affiché :


tester (noexcept) case 1 called
pt (potentially throwing) called
Throwing exception
Doomed destructed
tester caught exception
Test successful

tester (noexcept) case 2 called
nt (noexcept) called
throwing exception
terminate called after throwing an instance of 'int'

puis le programme a été interrompu.

Examinons plus en détail ce qui se passe ici. Notez que tester est une fonction noexcept et qu'elle promet donc de ne exposer aucune exception à l'appelant (main).

Le premier cas montre que les fonctions noexcept peuvent appeler des fonctions potentiellement lanceuses, et même gérer les exceptions que ces fonctions lèvent. Tout d'abord, tester(1) est appelée ; elle appelle la fonction potentiellement lanceuse pt, qui appelle thrower, qui lève une exception. Le premier gestionnaire de cette exception se trouve dans tester. L'exception déroule donc la pile (en détruisant au passage la variable locale doomed), puis elle est interceptée et gérée à l'intérieur de tester. Comme tester n'expose pas cette exception à l'appelant (main), il n'y a aucune violation de noexcept ici, et le contrôle revient à main.

Le second cas montre ce qui se passe lorsqu'une fonction noexcept tente de renvoyer une exception à son appelant. Tout d'abord, tester(2) est appelée ; elle appelle la fonction non lanceuse nt, qui appelle thrower, qui lève une exception. Le premier gestionnaire de cette exception se trouve dans tester. Cependant, nt est noexcept, et pour atteindre le gestionnaire dans tester, l'exception devrait se propager jusqu'à l'appelant de nt. C'est une violation du noexcept de nt : std::terminate est donc appelée, et notre programme est interrompu immédiatement. Sur la machine de l'auteur, la pile n'a pas été déroulée (comme le montre le fait que doomed n'a pas été détruit).

Le spécificateur noexcept avec un paramètre booléen

Le spécificateur noexcept accepte un paramètre booléen optionnel. noexcept(true) est équivalent à noexcept : la fonction est non lanceuse. noexcept(false) signifie que la fonction est potentiellement lanceuse. Ces paramètres ne sont généralement utilisés que dans les fonctions modèles (template functions), afin qu'une fonction modèle puisse être créée dynamiquement comme non lanceuse ou potentiellement lanceuse, selon une valeur paramétrée.

Quelles fonctions sont non lanceuses et potentiellement lanceuses

Fonctions implicitement non lanceuses :

  • Destructeurs

Fonctions non lanceuses par défaut, pour les fonctions déclarées implicitement ou défaites (defaulted) :

  • Constructeurs : par défaut, de copie, de déplacement
  • Opérateurs d'affectation : de copie, de déplacement
  • Opérateurs de comparaison (à partir de C++20)

Toutefois, si l'une de ces fonctions appelle (explicitement ou implicitement) une autre fonction potentiellement lanceuse, la fonction concernée sera elle aussi considérée comme potentiellement lanceuse. Par exemple, si une classe possède un membre de donnée dont le constructeur est potentiellement lanceur, les constructeurs de cette classe seront également considérés comme potentiellement lanceurs. Autre exemple : si un opérateur d'affectation de copie appelle un opérateur d'affectation potentiellement lanceur, l'affectation de copie sera elle aussi potentiellement lanceuse.

Fonctions potentiellement lanceuses (si elles ne sont pas déclarées implicitement ou défaites) :

  • Fonctions ordinaires
  • Constructeurs définis par l'utilisateur
  • Opérateurs définis par l'utilisateur

L'opérateur noexcept

L'opérateur noexcept peut aussi être utilisé à l'intérieur d'expressions. Il prend une expression en argument et renvoie true ou false selon que le compilateur estime qu'elle peut lever une exception ou non. L'opérateur noexcept est évalué statiquement à la compilation, et n'évalue pas réellement l'expression passée en argument.

void foo() {throw -1;}
void boo() {};
void goo() noexcept {};
struct S{};

constexpr bool b1{ noexcept(5 + 3) }; // true ; les int sont non lanceurs
constexpr bool b2{ noexcept(foo()) }; // false ; foo() lève une exception
constexpr bool b3{ noexcept(boo()) }; // false ; boo() est implicitement noexcept(false)
constexpr bool b4{ noexcept(goo()) }; // true ; goo() est explicitement noexcept(true)
constexpr bool b5{ noexcept(S{}) };   // true ; le constructeur par défaut d'une struct est noexcept par défaut

L'opérateur noexcept peut servir à exécuter du code de manière conditionnelle, selon que l'expression est potentiellement lanceuse ou non. Cela est nécessaire pour satisfaire certaines garanties de sécurité face aux exceptions (exception safety guarantees), que nous verrons dans la section suivante.

Garanties de sécurité face aux exceptions

Une garantie de sécurité face aux exceptions est une directive contractuelle décrivant le comportement des fonctions ou des classes lorsqu'une exception survient. Il existe quatre niveaux de garanties :

  • Aucune garantie -- Il n'y a aucune garantie quant à ce qui se passe lorsqu'une exception est levée (par exemple, une classe peut être laissée dans un état inutilisable).
  • Garantie de base -- Si une exception est levée, aucune mémoire n'est perdue et l'objet reste utilisable, mais le programme peut rester dans un état modifié.
  • Garantie forte -- Si une exception est levée, aucune mémoire n'est perdue et l'état du programme n'est pas modifié. Cela signifie que la fonction doit soit réussir entièrement, soit ne produire aucun effet de bord en cas d'échec. C'est facile si l'échec survient avant toute modification, mais cela peut aussi être obtenu en annulant les modifications déjà effectuées, afin de ramener le programme à l'état précédant l'échec.
  • Garantie de non-lancement / garantie de non-échec (No throw / No fail) -- La fonction réussit toujours (no-fail) ou échoue sans lever d'exception visible par l'appelant (no-throw). Des exceptions peuvent être levées en interne si elles ne sont pas exposées. Le spécificateur noexcept correspond à ce niveau de garantie.

Examinons plus en détail les garanties no-throw et no-fail :

La garantie no-throw : si une fonction échoue, elle ne lève pas d'exception. Elle renvoie à la place un code d'erreur ou ignore le problème. Les garanties no-throw sont requises pendant le déroulement de la pile, lorsqu'une exception est déjà en cours de traitement ; par exemple, tous les destructeurs doivent offrir une garantie no-throw (de même que toutes les fonctions appelées par ces destructeurs). Exemples de code qui devrait être no-throw :

  • destructeurs et fonctions de libération ou de nettoyage de la mémoire
  • fonctions dont les fonctions no-throw de plus haut niveau ont besoin

La garantie no-fail : une fonction réussit toujours dans ce qu'elle tente de faire (elle n'a donc jamais besoin de lever une exception ; no-fail est donc une forme légèrement plus forte de no-throw). Exemples de code qui devrait être no-fail :

  • constructeurs de déplacement et affectation par déplacement (sémantique de déplacement, traitée au chapitre 22)
  • fonctions d'échange (swap)
  • fonctions clear, erase et reset des conteneurs
  • opérations sur std::unique_ptr (également traitées au chapitre 22)
  • fonctions dont les fonctions no-fail de plus haut niveau ont besoin

Quand utiliser noexcept

Ce n'est pas parce que votre code ne lève explicitement aucune exception que vous devez parsemer votre code de noexcept. Par défaut, la plupart des fonctions sont potentiellement lanceuses : si votre fonction appelle d'autres fonctions, il est probable qu'elle appelle une fonction potentiellement lanceuse, et qu'elle soit donc elle aussi potentiellement lanceuse.

Il existe toutefois quelques bonnes raisons de déclarer des fonctions non lanceuses :

  • Les fonctions non lanceuses peuvent être appelées en toute sécurité depuis des fonctions qui ne sont pas sûres face aux exceptions, comme les destructeurs.
  • Les fonctions noexcept peuvent permettre au compilateur d'effectuer certaines optimisations qui ne seraient pas possibles autrement. Comme une fonction noexcept ne peut pas lever d'exception en dehors d'elle-même, le compilateur n'a pas à veiller à ce que la pile d'exécution reste dans un état permettant le déroulement, ce qui peut lui permettre de produire un code plus rapide.
  • Il existe des cas importants où connaître qu'une fonction est noexcept permet de produire des implémentations plus efficaces dans notre propre code : les conteneurs de la bibliothèque standard (comme std::vector) tiennent compte de noexcept et utilisent l'opérateur noexcept pour déterminer s'il faut recourir à la sémantique de déplacement (plus rapide) ou à la sémantique de copie (plus lente) à certains endroits. Nous abordons la sémantique de déplacement au chapitre 22, et cette optimisation dans la leçon 27.10 -- std::move_if_noexcept.

La politique de la bibliothèque standard consiste à n'utiliser noexcept que pour les fonctions qui ne doivent pas lever d'exception ni échouer. Les fonctions potentiellement lanceuses qui, en raison de leur implémentation, ne lèvent pas réellement d'exception ne sont généralement pas marquées noexcept.

Pour votre propre code, marquez systématiquement les éléments suivants comme noexcept :

  • Constructeurs de déplacement
  • Opérateurs d'affectation par déplacement
  • Fonctions d'échange (swap)

Pour votre code, envisagez de marquer les éléments suivants comme noexcept :

  • Fonctions pour lesquelles vous souhaitez exprimer une garantie no-throw ou no-fail (par exemple pour indiquer qu'elles peuvent être appelées en toute sécurité depuis des destructeurs ou d'autres fonctions noexcept)
  • Constructeurs de copie et opérateurs d'affectation de copie qui sont no-throw (pour profiter des optimisations).
  • Destructeurs. Les destructeurs sont implicitement noexcept tant que tous les membres ont des destructeurs noexcept.

Bonne pratique

Rendez toujours noexcept les constructeurs de déplacement, les opérateurs d'affectation par déplacement et les fonctions d'échange.

Rendez noexcept les constructeurs de copie et les opérateurs d'affectation de copie chaque fois que c'est possible.

Utilisez noexcept sur les autres fonctions pour exprimer une garantie no-fail ou no-throw.

Bonne pratique

Si vous n'êtes pas certain qu'une fonction doive offrir une garantie no-fail/no-throw, faites preuve de prudence et ne la marquez pas noexcept. Revenir sur une décision d'utiliser noexcept revient à rompre un engagement d'interface envers l'utilisateur concernant le comportement de la fonction, et peut casser du code existant. En revanche, renforcer une garantie en ajoutant ultérieurement noexcept à une fonction qui ne l'était pas à l'origine est considéré comme sûr.

Spécifications d'exception dynamiques

Lecture facultative

Avant C++11, et jusqu'à C++17, les spécifications d'exception dynamiques (dynamic exception specifications) étaient utilisées à la place de noexcept. La syntaxe des spécifications d'exception dynamiques utilise le mot-clé throw pour énumérer les types d'exceptions qu'une fonction peut lever, directement ou indirectement :

int doSomething() throw(); // ne lève pas d'exception
int doSomething() throw(std::out_of_range, int*); // peut lever std::out_of_range ou un pointeur vers un entier
int doSomething() throw(...); // peut lever n'importe quoi

En raison de facteurs tels que des implémentations incomplètes des compilateurs, une certaine incompatibilité avec les fonctions modèles, des idées reçues sur leur fonctionnement, et le fait que la bibliothèque standard ne les utilisait pratiquement pas, les spécifications d'exception dynamiques ont été rendues obsolètes en C++11, puis supprimées du langage en C++17 et C++20. Voir cet article pour plus de contexte.
