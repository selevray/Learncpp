14.7 — Fonctions membres renvoyant des références vers des membres de données

Dans la leçon 12.12 -- Return by reference and return by address, nous avons abordé le renvoi par référence. En particulier, nous avons noté : « L'objet renvoyé par référence doit exister après que la fonction a retourné sa valeur ». Cela signifie que nous ne devons pas renvoyer par référence des variables locales, car la référence resterait pendante (dangling) après la destruction de la variable locale. En revanche, il est généralement acceptable de renvoyer par référence soit des paramètres de fonction passés par référence, soit des variables à durée de stockage statique (variables locales statiques ou variables globales), car elles ne sont généralement pas détruites à la fin de la fonction.

Par exemple :

// Prend deux objets std::string et renvoie celui qui vient en premier par ordre alphabétique
const std::string& firstAlphabetical(const std::string& a, const std::string& b)
{
    return (a < b) ? a : b; // On peut utiliser operator< sur std::string pour déterminer lequel vient en premier
}

int main()
{
    std::string hello { "Hello" };
    std::string world { "World" };

    std::cout << firstAlphabetical(hello, world); // soit hello, soit world, est renvoyé par référence

    return 0;
}

Les fonctions membres peuvent elles aussi renvoyer par référence, et elles suivent les mêmes règles que les fonctions non membres pour savoir quand il est sûr de renvoyer par référence. Cependant, les fonctions membres ont un cas supplémentaire que nous devons examiner : les fonctions membres qui renvoient par référence des membres de données.

Cela se rencontre le plus souvent avec les fonctions d'accès en lecture (getters), nous illustrerons donc ce sujet à l'aide de ces fonctions. Notez toutefois que ce sujet s'applique à toute fonction membre renvoyant une référence vers un membre de données.

Renvoyer des membres de données par valeur peut être coûteux

Considérons l'exemple suivant :

#include <iostream>
#include <string>

class Employee
{
    std::string m_name{};

public:
    void setName(std::string_view name) { m_name = name; }
    std::string getName() const { return m_name; } //  le getter renvoie par valeur
};

int main()
{
    Employee joe{};
    joe.setName("Joe");
    std::cout << joe.getName();

    return 0;
}

Dans cet exemple, la fonction d'accès getName() renvoie std::string m_name par valeur.

Bien que ce soit la solution la plus sûre, cela signifie qu'une copie coûteuse de m_name est effectuée à chaque appel de getName(). Comme les fonctions d'accès sont appelées très souvent, ce n'est généralement pas le meilleur choix.

Renvoyer des membres de données par référence lvalue

Les fonctions membres peuvent également renvoyer des membres de données par référence lvalue (const ou non).

Les membres de données ont la même durée de vie que l'objet qui les contient. Comme les fonctions membres sont toujours appelées sur un objet, et que cet objet doit exister dans la portée de l'appelant, il est généralement sûr pour une fonction membre de renvoyer un membre de données par référence lvalue (const ou non), puisque le membre renvoyé par référence existera toujours dans la portée de l'appelant lorsque la fonction retourne.

Mettons à jour l'exemple ci-dessus pour que getName() renvoie m_name par référence lvalue const :

#include <iostream>
#include <string>

class Employee
{
    std::string m_name{};

public:
    void setName(std::string_view name) { m_name = name; }
    const std::string& getName() const { return m_name; } //  le getter renvoie par référence const
};

int main()
{
    Employee joe{}; // joe existe jusqu'à la fin de la fonction
    joe.setName("Joe");

    std::cout << joe.getName(); // renvoie joe.m_name par référence

    return 0;
}

Désormais, lorsque joe.getName() est invoquée, joe.m_name est renvoyé par référence à l'appelant, ce qui évite de faire une copie. L'appelant utilise ensuite cette référence pour afficher joe.m_name sur la console.

Comme joe existe dans la portée de l'appelant jusqu'à la fin de la fonction main(), la référence vers joe.m_name reste valide pendant toute cette durée.

Point clé

Il est acceptable de renvoyer une référence lvalue (const ou non) vers un membre de données. L'objet implicite (qui contient le membre de données) existe toujours dans la portée de l'appelant après le retour de la fonction, donc les références renvoyées restent valides.

Le type de retour d'une fonction membre renvoyant une référence vers un membre de données doit correspondre au type de ce membre

En général, le type de retour d'une fonction membre renvoyant par référence doit correspondre au type du membre de données renvoyé. Dans l'exemple ci-dessus, m_name est de type std::string, donc getName() renvoie const std::string&.

Renvoyer un std::string_view obligerait à créer et renvoyer un std::string_view temporaire à chaque appel de la fonction. C'est inutilement inefficace. Si l'appelant souhaite un std::string_view, il peut effectuer la conversion lui-même.

Bonne pratique

Une fonction membre renvoyant une référence doit renvoyer une référence du même type que le membre de données renvoyé, afin d'éviter des conversions inutiles.

Pour les getters, utiliser auto pour laisser le compilateur déduire le type de retour à partir du membre renvoyé est un moyen utile de garantir qu'aucune conversion n'a lieu :

#include <iostream>
#include <string>

class Employee
{
    std::string m_name{};

public:
    void setName(std::string_view name) { m_name = name; }
    const auto& getName() const { return m_name; } // utilise `auto` pour déduire le type de retour à partir de m_name
};

int main()
{
    Employee joe{}; // joe existe jusqu'à la fin de la fonction
    joe.setName("Joe");

    std::cout << joe.getName(); // renvoie joe.m_name par référence

    return 0;
}

Contenu associé

Nous abordons les types de retour auto dans la leçon 10.9 -- Type deduction for functions.

Cependant, utiliser un type de retour auto masque le type de retour du getter du point de vue de la documentation. Par exemple :

    const auto& getName() const { return m_name; } // utilise `auto` pour déduire le type de retour à partir de m_name

On ne sait pas vraiment quel type de chaîne cette fonction renvoie (cela pourrait être un std::string, un std::string_view, une chaîne de style C, ou autre chose encore !).

Pour cette raison, nous privilégierons généralement les types de retour explicites.

Objets implicites rvalue et renvoi par référence

Il existe un cas auquel il faut être un peu attentif. Dans l'exemple ci-dessus, joe est un objet lvalue qui existe jusqu'à la fin de la fonction. Par conséquent, la référence renvoyée par joe.getName() reste également valide jusqu'à la fin de la fonction.

Mais que se passe-t-il si l'objet implicite est une rvalue (comme la valeur de retour d'une fonction qui renvoie par valeur) ? Les objets rvalue sont détruits à la fin de l'expression complète dans laquelle ils sont créés. Lorsqu'un objet rvalue est détruit, toute référence vers un de ses membres est invalidée et devient pendante, et son utilisation produit un comportement indéfini.

Une référence vers un membre d'un objet rvalue ne peut donc être utilisée en toute sécurité que dans l'expression complète où cet objet rvalue est créé.

Astuce

Nous avons expliqué ce qu'est une expression complète dans la leçon 1.10 -- Introduction to expressions.

Avertissement

Un objet rvalue est détruit à la fin de l'expression complète dans laquelle il est créé. Toute référence vers ses membres est alors pendante.

Une référence vers un membre d'un objet rvalue ne peut être utilisée en toute sécurité que dans l'expression complète où cet objet rvalue est créé.

Examinons quelques cas liés à cela :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
    std::string m_name{};

public:
    void setName(std::string_view name) { m_name = name; }
    const std::string& getName() const { return m_name; } //  le getter renvoie par référence const
};

// createEmployee() renvoie un Employee par valeur (ce qui signifie que la valeur retournée est une rvalue)
Employee createEmployee(std::string_view name)
{
    Employee e;
    e.setName(name);
    return e;
}

int main()
{
    // Cas 1 : correct : utilisation immédiate de la référence vers le membre de l'objet rvalue dans la même expression
    std::cout << createEmployee("Frank").getName();

    // Cas 2 : incorrect : conservation de la référence vers le membre d'un objet rvalue pour une utilisation ultérieure
    const std::string& ref { createEmployee("Garbo").getName() }; // la référence devient pendante lorsque la valeur retournée par createEmployee() est détruite
    std::cout << ref; // comportement indéfini

    // Cas 3 : correct : copie de la valeur référencée dans une variable locale pour une utilisation ultérieure
    std::string val { createEmployee("Hans").getName() }; // fait une copie du membre référencé
    std::cout << val; // correct : val est indépendant du membre référencé

    return 0;
}

Lorsque createEmployee() est appelée, elle renvoie un objet Employee par valeur. Cet objet Employee renvoyé est une rvalue qui existe jusqu'à la fin de l'expression complète contenant l'appel à createEmployee(). Lorsque cet objet rvalue est détruit, toute référence vers ses membres devient pendante.

Dans le cas 1, nous appelons createEmployee("Frank"), qui renvoie un objet Employee rvalue. Nous appelons ensuite getName() sur cet objet rvalue, ce qui renvoie une référence vers m_name. Cette référence est alors utilisée immédiatement pour afficher le nom sur la console. À ce stade, l'expression complète contenant l'appel à createEmployee("Frank") se termine, et l'objet rvalue ainsi que ses membres sont détruits. Comme ni l'objet rvalue ni ses membres ne sont utilisés au-delà de ce point, ce cas est correct.

Dans le cas 2, nous rencontrons des problèmes. D'abord, createEmployee("Garbo") renvoie un objet rvalue. Nous appelons ensuite getName() pour obtenir une référence vers le membre m_name de cet objet rvalue. Ce membre m_name sert alors à initialiser ref. À ce stade, l'expression complète contenant l'appel à createEmployee("Garbo") se termine, et l'objet rvalue ainsi que ses membres sont détruits. Cela rend ref pendante. Ainsi, lorsque nous utilisons ref dans l'instruction suivante, nous accédons à une référence pendante, et il en résulte un comportement indéfini.

Point clé

L'évaluation d'une expression complète se termine après toute utilisation de cette expression comme initialiseur. Cela permet d'initialiser un objet avec une rvalue du même type (puisque la rvalue n'est pas détruite avant la fin de l'initialisation).

Mais que faire si nous voulons conserver une valeur issue d'une fonction qui renvoie un membre par référence, pour une utilisation ultérieure ? Plutôt que d'utiliser la référence renvoyée pour initialiser une variable locale de type référence, nous pouvons utiliser cette référence pour initialiser une variable locale qui n'est pas une référence.

Dans le cas 3, nous utilisons la référence renvoyée pour initialiser la variable locale non référence val. Cela entraîne la copie du membre référencé dans val. Après l'initialisation, val existe indépendamment de la référence. Ainsi, lorsque l'objet rvalue est ensuite détruit, val n'en est pas affecté. val peut donc être affiché dans les instructions suivantes sans problème.

Utiliser en toute sécurité des fonctions membres qui renvoient par référence

Malgré le danger potentiel lié aux objets implicites rvalue, il est d'usage que les getters renvoient par référence const les types coûteux à copier, plutôt que par valeur.

Partant de là, voyons comment utiliser en toute sécurité les valeurs de retour de ces fonctions. Les trois cas de l'exemple ci-dessus illustrent les trois points essentiels :

  • Préférez utiliser immédiatement la valeur de retour d'une fonction membre qui renvoie par référence (illustré par le cas 1). Comme cela fonctionne aussi bien avec des objets lvalue que rvalue, si vous le faites systématiquement, vous éviterez les problèmes.
  • Ne « conservez » pas une référence renvoyée pour une utilisation ultérieure (illustré par le cas 2), sauf si vous êtes certain que l'objet implicite est une lvalue. Si vous le faites avec un objet implicite rvalue, un comportement indéfini résultera de l'utilisation de la référence devenue pendante.
  • Si vous devez vraiment conserver une référence renvoyée pour une utilisation ultérieure, et que vous n'êtes pas certain que l'objet implicite soit une lvalue, utilisez la référence renvoyée comme initialiseur d'une variable locale qui n'est pas une référence. Cela copiera le membre référencé dans la variable locale (illustré par le cas 3).

Bonne pratique

Préférez utiliser immédiatement la valeur de retour d'une fonction membre qui renvoie par référence, afin d'éviter les problèmes de références pendantes lorsque l'objet implicite est une rvalue.

Ne renvoyez pas de références non const vers des membres de données privés

Comme une référence se comporte exactement comme l'objet référencé, une fonction membre qui renvoie une référence non const donne un accès direct à ce membre (même s'il est privé).

Par exemple :

#include <iostream>

class Foo
{
private:
    int m_value{ 4 }; // membre privé

public:
    int& value() { return m_value; } // renvoie une référence non const (à éviter)
};

int main()
{
    Foo f{};                // f.m_value est initialisé à la valeur par défaut 4
    f.value() = 5;          // L'équivalent de m_value = 5
    std::cout << f.value(); // affiche 5

    return 0;
}

Comme value() renvoie une référence non const vers m_value, l'appelant peut utiliser cette référence pour accéder directement à m_value (et modifier sa valeur).

Cela permet à l'appelant de contourner le système de contrôle d'accès.

Les fonctions membres const ne peuvent pas renvoyer de références non const vers des membres de données

Une fonction membre const n'est pas autorisée à renvoyer une référence non const vers des membres. C'est logique : une fonction membre const n'a pas le droit de modifier l'état de l'objet, ni d'appeler des fonctions qui le modifieraient. Elle ne doit rien faire qui puisse conduire à la modification de l'objet.

Si une fonction membre const était autorisée à renvoyer une référence non const vers un membre, elle donnerait à l'appelant un moyen de modifier directement ce membre. Cela violerait l'intention même d'une fonction membre const.
