14.12 — Constructeurs délégants

Chaque fois que c'est possible, nous voulons réduire le code redondant (en suivant le principe DRY : Don't Repeat Yourself, « ne vous répétez pas »).

Considérons les fonctions suivantes :

void A()
{
    // instructions qui accomplissent la tâche A
}

void B()
{
    // instructions qui accomplissent la tâche A
    // instructions qui accomplissent la tâche B
}

Les deux fonctions contiennent un ensemble d'instructions qui font exactement la même chose (la tâche A). Dans ce cas, nous pouvons refactoriser ainsi :

void A()
{
    // instructions qui accomplissent la tâche A
}

void B()
{
    A();
    // instructions qui accomplissent la tâche B
}

De cette manière, nous avons supprimé le code redondant présent dans les fonctions A() et B(). Cela rend notre code plus facile à maintenir, car les modifications ne doivent être faites qu'à un seul endroit.

Lorsqu'une classe contient plusieurs constructeurs, il est très courant que le code de chacun d'eux soit similaire, voire identique, avec beaucoup de répétitions. Nous aimerions de la même façon supprimer la redondance entre constructeurs, lorsque c'est possible.

Considérons l'exemple suivant :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    std::string m_name { "???" };
    int m_id { 0 };
    bool m_isManager { false };

public:
    Employee(std::string_view name, int id) // Un employé doit avoir un nom et un id
        : m_name{ name }, m_id { id }
    {
        std::cout << "Employee " << m_name << " created\n";
    }

    Employee(std::string_view name, int id, bool isManager) // Il peut éventuellement être manager
        : m_name{ name }, m_id{ id }, m_isManager { isManager }
    {
        std::cout << "Employee " << m_name << " created\n";
    }
};

int main()
{
    Employee e1{ "James", 7 };
    Employee e2{ "Dave", 42, true };
}

Le corps de chaque constructeur contient exactement la même instruction d'affichage.

Note de l'auteur

Il n'est généralement pas une bonne idée qu'un constructeur affiche quelque chose (sauf à des fins de débogage), car cela signifie que vous ne pouvez pas créer un objet avec ce constructeur dans les cas où vous ne souhaitez rien afficher. Nous le faisons dans cet exemple pour illustrer ce qui se passe.

Les constructeurs sont autorisés à appeler d'autres fonctions, y compris d'autres fonctions membres de la classe. Nous pourrions donc refactoriser ainsi :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    std::string m_name { "???" };
    int m_id{ 0 };
    bool m_isManager { false };

    void printCreated() const // notre nouvelle fonction d'aide
    {
        std::cout << "Employee " << m_name << " created\n";
    }

public:
    Employee(std::string_view name, int id)
        : m_name{ name }, m_id { id }
    {
        printCreated(); // nous l'appelons ici
    }

    Employee(std::string_view name, int id, bool isManager)
        : m_name{ name }, m_id{ id }, m_isManager { isManager }
    {
        printCreated(); // et ici
    }
};

int main()
{
    Employee e1{ "James", 7 };
    Employee e2{ "Dave", 42, true };
}

Bien que ce soit mieux que la version précédente (l'instruction redondante a été remplacée par un appel de fonction redondant), cela nécessite l'introduction d'une nouvelle fonction. De plus, nos deux constructeurs initialisent tous deux m_name et m_id. Idéalement, nous voudrions supprimer aussi cette redondance.

Peut-on faire mieux ? Oui. Mais c'est ici que de nombreux programmeurs débutants rencontrent des difficultés.

Appeler un constructeur dans le corps d'une fonction crée un objet temporaire

De la même façon que la fonction B() appelait la fonction A() dans l'exemple précédent, la solution évidente semble être d'appeler le constructeur Employee(std::string_view, int) depuis le corps de Employee(std::string_view, int, bool), afin d'initialiser m_name, m_id et d'afficher le message. Voici ce que cela donne :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    std::string m_name { "???" };
    int m_id { 0 };
    bool m_isManager { false };

public:
    Employee(std::string_view name, int id)
        : m_name{ name }, m_id { id } // ce constructeur initialise name et id
    {
        std::cout << "Employee " << m_name << " created\n"; // notre instruction d'affichage est de retour ici
    }

    Employee(std::string_view name, int id, bool isManager)
        : m_isManager { isManager } // ce constructeur initialise m_isManager
    {
        // Appeler Employee(std::string_view, int) pour initialiser m_name et m_id
        Employee(name, id); // cela ne fonctionne pas comme prévu !
    }

    const std::string& getName() const { return m_name; }
};

int main()
{
    Employee e2{ "Dave", 42, true };
    std::cout << "e2 has name: " << e2.getName() << "\n"; // affiche e2.m_name
}

Mais cela ne fonctionne pas correctement : le programme affiche ceci :

Employee Dave created
e2 has name: ???

Bien que Employee Dave created ait été affiché, une fois la construction de e2 terminée, e2.m_name semble toujours avoir sa valeur initiale "???". Comment est-ce possible ?

Nous pensions que Employee(name, id) allait appeler le constructeur pour poursuivre l'initialisation de l'objet implicite courant (e2). Mais l'initialisation d'un objet de classe est terminée une fois que la liste d'initialisation des membres a fini de s'exécuter. Au moment où le corps du constructeur commence à s'exécuter, il est trop tard pour effectuer une initialisation supplémentaire.

Lorsqu'il est appelé depuis le corps d'une fonction, ce qui ressemble à un appel de constructeur crée généralement un objet temporaire en l'initialisant directement (dans un autre cas, vous obtiendrez une erreur de compilation). Dans notre exemple ci-dessus, Employee(name, id); crée un objet Employee temporaire (sans nom). C'est cet objet temporaire dont m_name est défini à Dave, et c'est lui qui affiche Employee Dave created. Ensuite, le temporaire est détruit. e2 ne voit jamais ses m_name ou m_id modifiés : ils gardent leurs valeurs par défaut.

Bonne pratique

Les constructeurs ne doivent pas être appelés directement depuis le corps d'une autre fonction. Cela entraînera soit une erreur de compilation, soit l'initialisation directe d'un objet temporaire.
Si vous souhaitez réellement un objet temporaire, privilégiez l'initialisation par liste (qui indique clairement que vous voulez créer un objet).

Donc, si nous ne pouvons pas appeler un constructeur depuis le corps d'un autre constructeur, comment résoudre ce problème ?

Constructeurs délégants

Les constructeurs peuvent déléguer (transférer la responsabilité de) l'initialisation à un autre constructeur du même type de classe. Ce procédé est parfois appelé chaînage de constructeurs (constructor chaining), et de tels constructeurs sont appelés constructeurs délégants (delegating constructors).

Pour qu'un constructeur délègue l'initialisation à un autre constructeur, il suffit d'appeler ce constructeur dans la liste d'initialisation des membres :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    std::string m_name { "???" };
    int m_id { 0 };

public:
    Employee(std::string_view name)
        : Employee{ name, 0 } // délègue l'initialisation au constructeur Employee(std::string_view, int)
    {
    }

    Employee(std::string_view name, int id)
        : m_name{ name }, m_id { id } // initialise réellement les membres
    {
        std::cout << "Employee " << m_name << " created\n";
    }

};

int main()
{
    Employee e1{ "James" };
    Employee e2{ "Dave", 42 };
}

Lorsque e1 { "James" } est initialisé, le constructeur correspondant Employee(std::string_view) est appelé avec le paramètre name valant "James". La liste d'initialisation des membres de ce constructeur délègue l'initialisation à un autre constructeur, donc Employee(std::string_view, int) est alors appelé. La valeur de name ("James") est passée comme premier argument, et le littéral 0 comme second argument. La liste d'initialisation des membres du constructeur délégué initialise ensuite les membres. Le corps du constructeur délégué s'exécute alors. Ensuite, le contrôle revient au constructeur initial, dont le corps (vide) s'exécute. Enfin, le contrôle revient à l'appelant.

L'inconvénient de cette méthode est qu'elle nécessite parfois de dupliquer des valeurs d'initialisation. Dans la délégation au constructeur Employee(std::string_view, int), nous avons besoin d'une valeur d'initialisation pour le paramètre int. Nous avons dû coder en dur le littéral 0, car il n'existe pas de moyen de référencer l'initialisation par défaut du membre.

Quelques remarques supplémentaires sur les constructeurs délégants. Premièrement, un constructeur qui délègue à un autre constructeur n'a pas le droit d'initialiser lui-même des membres. Vos constructeurs peuvent donc soit déléguer, soit initialiser, mais pas les deux.

En passant…

Notez que nous avons fait déléguer Employee(std::string_view) (le constructeur avec le moins de paramètres) à Employee(std::string_view name, int id) (le constructeur avec plus de paramètres). Il est courant que le constructeur ayant moins de paramètres délègue au constructeur ayant plus de paramètres.

Si nous avions choisi plutôt de faire déléguer Employee(std::string_view name, int id) à Employee(std::string_view), nous n'aurions pas pu initialiser m_id avec id, car un constructeur ne peut que déléguer ou initialiser, pas les deux.

Deuxièmement, il est possible qu'un constructeur délègue à un autre constructeur, lequel délègue à son tour au premier. Cela forme une boucle infinie, et provoquera l'épuisement de la pile et le plantage de votre programme. Vous pouvez éviter cela en vous assurant que tous vos constructeurs aboutissent à un constructeur non délégant.

Bonne pratique

Si vous disposez de plusieurs constructeurs, vérifiez si vous pouvez utiliser des constructeurs délégants pour réduire le code dupliqué.

Réduire le nombre de constructeurs grâce aux arguments par défaut

Les valeurs par défaut peuvent aussi parfois servir à réduire plusieurs constructeurs en un nombre plus restreint. Par exemple, en donnant une valeur par défaut à notre paramètre id, nous pouvons créer un unique constructeur Employee qui exige un argument de nom, mais accepte optionnellement un argument d'identifiant :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    std::string m_name{};
    int m_id{ 0 }; // initialisation par défaut du membre

public:

    Employee(std::string_view name, int id = 0) // argument par défaut pour id
        : m_name{ name }, m_id{ id }
    {
        std::cout << "Employee " << m_name << " created\n";
    }
};

int main()
{
    Employee e1{ "James" };
    Employee e2{ "Dave", 42 };
}

Comme les valeurs par défaut doivent être attachées aux paramètres les plus à droite lors d'un appel de fonction, une bonne pratique lors de la définition d'une classe consiste à définir d'abord les membres pour lesquels l'utilisateur doit fournir une valeur d'initialisation (et à en faire les paramètres les plus à gauche du constructeur). Les membres pour lesquels l'utilisateur peut fournir une valeur facultativement (parce que les valeurs par défaut sont acceptables) doivent être définis ensuite (et devenir les paramètres les plus à droite du constructeur).

Bonne pratique

Les membres pour lesquels l'utilisateur doit fournir des valeurs d'initialisation doivent être définis en premier (et être les paramètres les plus à gauche du constructeur). Les membres pour lesquels l'utilisateur peut fournir facultativement des valeurs d'initialisation (parce que les valeurs par défaut sont acceptables) doivent être définis ensuite (et être les paramètres les plus à droite du constructeur).

Notez que cette méthode nécessite également de dupliquer la valeur d'initialisation par défaut de m_id (« 0 ») : une fois comme initialisation par défaut du membre, et une fois comme argument par défaut.

Un dilemme : constructeurs redondants contre valeurs par défaut redondantes

Dans les exemples précédents, nous avons utilisé des constructeurs délégants, puis des arguments par défaut, pour réduire la redondance entre constructeurs. Mais ces deux méthodes nous ont obligés à dupliquer les valeurs d'initialisation de nos membres à plusieurs endroits. Malheureusement, il n'existe actuellement aucun moyen d'indiquer qu'un constructeur délégant ou un argument par défaut doit utiliser la valeur d'initialisation par défaut du membre.

Les avis divergent sur la question de savoir s'il vaut mieux avoir moins de constructeurs (avec duplication des valeurs d'initialisation) ou plus de constructeurs (sans duplication). Notre avis est qu'il est généralement plus simple d'avoir moins de constructeurs, même si cela entraîne une duplication des valeurs d'initialisation.

Pour les lecteurs avancés

Lorsqu'une valeur d'initialisation est utilisée à plusieurs endroits (par exemple comme initialisation par défaut d'un membre et comme argument par défaut d'un paramètre de constructeur), nous pouvons définir une constante nommée et l'utiliser partout où la valeur d'initialisation est nécessaire. Cela permet de définir la valeur d'initialisation à un seul endroit.

Bien que vous puissiez utiliser une variable globale constexpr pour cela, une meilleure option consiste à utiliser un membre static constexpr à l'intérieur de la classe :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    static constexpr int default_id { 0 }; // définit une constante nommée avec la valeur d'initialisation souhaitée

    std::string m_name {};
    int m_id { default_id }; // on peut l'utiliser ici

public:

    Employee(std::string_view name, int id = default_id) // et on peut l'utiliser ici
        : m_name { name }, m_id { id }
    {
        std::cout << "Employee " << m_name << " created\n";
    }
};

int main()
{
    Employee e1 { "James" };
    Employee e2 { "Dave", 42 };
}

L'utilisation du mot-clé static dans ce contexte nous permet d'avoir un unique membre default_id partagé par tous les objets Employee. Sans static, chaque objet Employee aurait son propre membre default_id indépendant (ce qui fonctionnerait, mais gaspillerait de la mémoire).

L'inconvénient de cette approche est que chaque constante nommée supplémentaire ajoute un nom de plus à comprendre, ce qui rend votre classe un peu plus encombrée et complexe. Le fait que cela en vaille la peine dépend du nombre de ces constantes nécessaires et du nombre d'endroits où les valeurs d'initialisation sont requises.

Nous abordons les membres de données statiques dans la leçon 15.6 -- Variables membres statiques.

Temps du quiz

Question n° 1

Écrivez une classe nommée Ball. Ball doit posséder deux variables membres privées : l'une pour stocker une couleur (valeur par défaut : black), et l'autre pour stocker un rayon (valeur par défaut : 10.0). Ajoutez 4 constructeurs, chacun traitant un des cas ci-dessous :

int main()
{
    Ball def{};
    Ball blue{ "blue" };
    Ball twenty{ 20.0 };
    Ball blueTwenty{ "blue", 20.0 };

    return 0;
}

Le programme doit produire le résultat suivant :


Ball(black, 10)
Ball(blue, 10)
Ball(black, 20)
Ball(blue, 20)
Solution 
#include <iostream>
#include <string>
#include <string_view>

class Ball
{
private:
    std::string m_color{ "black" };
    double m_radius{ 10.0 };

public:
    // Constructeur par défaut (la couleur et le rayon utilisent leur valeur par défaut)
    Ball()
    {
            print();
    }

    // Constructeur avec seulement le paramètre rayon (la couleur utilise sa valeur par défaut)
    Ball(double radius)
        : m_radius{ radius }
    {
            print();
    }

    // Constructeur avec seulement le paramètre couleur (le rayon utilise sa valeur par défaut)
    Ball(std::string_view color)
        : m_color{ color }
    {
            print();
    }

    // Constructeur avec les paramètres couleur et rayon
    Ball(std::string_view color, double radius)
        : m_color{ color }
        , m_radius{ radius }
    {
            print();
    }

    void print() const
    {
        std::cout << "Ball(" << m_color << ", " << m_radius << ")\n";
    }
};

int main()
{
    Ball def{};
    Ball blue{ "blue" };
    Ball twenty{ 20.0 };
    Ball blueTwenty{ "blue", 20.0 };

    return 0;
}

Question n° 2

Réduisez le nombre de constructeurs du programme ci-dessus en utilisant des arguments par défaut et des constructeurs délégants.

Solution 
#include <iostream>
#include <string>
#include <string_view>

class Ball
{
private:
    std::string m_color{ "black" };
    double m_radius{ 10.0 };

public:
    // Gère Ball(radius)
    Ball(double radius)
        : Ball{ "black", radius } // délègue à l'autre constructeur
    {
        // Pas besoin d'appeler print() ici, car il sera appelé par
        // le constructeur auquel on délègue
    }

    // Gère Ball(color, radius), Ball(color) et Ball()
    Ball(std::string_view color="black", double radius=10.0)
        : m_color{ color }
        , m_radius{ radius }
    {
        print();
    }

    void print() const
    {
        std::cout << "Ball(" << m_color << ", " << m_radius << ")\n";
    }
};

int main()
{
    Ball def{};
    Ball blue{ "blue" };
    Ball twenty{ 20.0 };
    Ball blueTwenty{ "blue", 20.0 };

    return 0;
}
