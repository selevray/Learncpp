12.12 — Retour par référence et retour par adresse

Dans les leçons précédentes, nous avons vu que, lors d'un passage par valeur, une copie de l'argument est créée dans le paramètre de la fonction. Pour les types fondamentaux, qui sont peu coûteux à copier, cela ne pose pas de problème. Mais la copie est généralement coûteuse pour les types classe (comme std::string). Nous pouvons éviter cette copie coûteuse en utilisant un passage par référence (constante) ou par adresse.

Nous rencontrons une situation similaire lors d'un retour par valeur : une copie de la valeur de retour est renvoyée à l'appelant. Si le type de retour de la fonction est un type classe, cela peut être coûteux.

std::string returnByValue(); // renvoie une copie d'une std::string (coûteux)

Retour par référence

Lorsque nous renvoyons un objet de type classe à l'appelant, nous pouvons vouloir (ou non) le renvoyer par référence. Le retour par référence renvoie une référence liée à l'objet retourné, ce qui évite de copier la valeur de retour. Pour retourner par référence, il suffit de définir le type de retour de la fonction comme un type référence :

std::string&       returnByReference(); // renvoie une référence à une std::string existante (peu coûteux)
const std::string& returnByReferenceToConst(); // renvoie une référence constante à une std::string existante (peu coûteux)

Voici un programme académique qui illustre le mécanisme du retour par référence :

#include <iostream>
#include <string>

const std::string& getProgramName() // renvoie une référence constante
{
    static const std::string s_programName { "Calculator" }; // a une durée de stockage statique, détruit à la fin du programme

    return s_programName;
}

int main()
{
    std::cout << "This program is named " << getProgramName();

    return 0;
}

Ce programme affiche :


This program is named Calculator

Comme getProgramName() renvoie une référence constante, lorsque la ligne return s_programName est exécutée, getProgramName() renvoie une référence constante vers s_programName (évitant ainsi une copie). Cette référence constante peut ensuite être utilisée par l'appelant pour accéder à la valeur de s_programName, qui est affichée.

L'objet renvoyé par référence doit exister après le retour de la fonction

Le retour par référence présente un inconvénient majeur : le programmeur doit s'assurer que l'objet référencé survit à la fonction qui renvoie la référence. Sinon, la référence renvoyée devient pendante (elle référence un objet détruit), et son utilisation entraîne un comportement indéfini.

Dans le programme ci-dessus, comme s_programName a une durée de stockage statique, il existe jusqu'à la fin du programme. Lorsque main() accède à la référence renvoyée, il accède en réalité à s_programName, ce qui est correct, car s_programName n'est détruit qu'à la fin.

Modifions maintenant ce programme pour montrer ce qui se passe lorsque la fonction renvoie une référence pendante :

#include <iostream>
#include <string>

const std::string& getProgramName()
{
    const std::string programName { "Calculator" }; // désormais une variable locale non statique, détruite à la fin de la fonction

    return programName;
}

int main()
{
    std::cout << "This program is named " << getProgramName(); // comportement indéfini

    return 0;
}

Le résultat de ce programme est indéfini. Au retour de getProgramName(), une référence liée à la variable locale programName est renvoyée. Or, programName est une variable locale à durée automatique, donc elle est détruite à la fin de la fonction. La référence renvoyée devient alors pendante, et l'utilisation de programName dans la fonction main() entraîne un comportement indéfini.

Les compilateurs modernes produisent un avertissement ou une erreur si vous essayez de renvoyer par référence une variable locale (le programme ci-dessus pourrait donc ne même pas compiler), mais ils ont parfois du mal à détecter des cas plus complexes.

Avertissement

Les objets renvoyés par référence doivent survivre à la portée de la fonction qui renvoie la référence, sinon une référence pendante en résulte. Ne renvoyez jamais par référence une variable locale (non statique) ou un temporaire.

L'extension de durée de vie ne fonctionne pas au-delà des frontières de fonction

Examinons un exemple où nous renvoyons un temporaire par référence :

#include <iostream>

const int& returnByConstReference()
{
    return 5; // renvoie une référence constante vers un objet temporaire
}

int main()
{
    const int& ref { returnByConstReference() };

    std::cout << ref; // comportement indéfini

    return 0;
}

Dans le programme ci-dessus, returnByConstReference() renvoie un littéral entier, mais le type de retour de la fonction est const int&. Il en résulte la création et le renvoi d'une référence temporaire liée à un objet temporaire contenant la valeur 5. Cette référence renvoyée est copiée dans une référence temporaire dans la portée de l'appelant. L'objet temporaire sort ensuite de sa portée, laissant pendante la référence temporaire dans la portée de l'appelant.

Au moment où la référence temporaire de la portée de l'appelant est liée à la variable de référence constante ref (dans main()), il est trop tard pour prolonger la durée de vie de l'objet temporaire, qui a déjà été détruit. ref est donc une référence pendante, et l'utilisation de sa valeur entraîne un comportement indéfini.

Voici un exemple moins évident qui ne fonctionne pas de la même façon :

#include <iostream>

const int& returnByConstReference(const int& ref)
{
    return ref;
}

int main()
{
    // cas 1 : liaison directe
    const int& ref1 { 5 }; // prolonge la durée de vie
    std::cout << ref1 << '\n'; // correct

    // cas 2 : liaison indirecte
    const int& ref2 { returnByConstReference(5) }; // se lie à une référence pendante
    std::cout << ref2 << '\n'; // comportement indéfini

    return 0;
}

Dans le cas 2, un objet temporaire contenant la valeur 5 est créé, auquel le paramètre de fonction ref se lie. La fonction renvoie simplement cette référence à l'appelant, qui l'utilise pour initialiser ref2. Comme il ne s'agit pas d'une liaison directe à l'objet temporaire (la référence ayant transité par une fonction), l'extension de durée de vie ne s'applique pas. ref2 reste donc pendante, et son utilisation ultérieure est un comportement indéfini.

Avertissement

L'extension de durée de vie d'une référence ne fonctionne pas au-delà des frontières de fonction.

Ne renvoyez pas par référence des variables locales statiques non constantes

Dans l'exemple original ci-dessus, nous avons renvoyé par référence une variable locale statique constante pour illustrer simplement le mécanisme du retour par référence. Cependant, renvoyer par référence des variables locales statiques non constantes n'est pas idiomatique et doit généralement être évité. Voici un exemple simplifié qui illustre l'un des problèmes qui peuvent survenir :

#include <iostream>
#include <string>

const int& getNextId()
{
    static int s_x{ 0 }; // remarque : la variable n'est pas constante
    ++s_x; // génère le prochain identifiant
    return s_x; // et renvoie une référence vers celui-ci
}

int main()
{
    const int& id1 { getNextId() }; // id1 est une référence
    const int& id2 { getNextId() }; // id2 est une référence

    std::cout << id1 << id2 << '\n';

    return 0;
}

Ce programme affiche :


22

Cela se produit parce que id1 et id2 référencent le même objet (la variable statique s_x). Ainsi, lorsque quelque chose (par exemple getNextId()) modifie cette valeur, toutes les références accèdent à la valeur modifiée.

L'exemple ci-dessus peut être corrigé en faisant de id1 et id2 des variables normales (et non des références), afin qu'elles conservent une copie de la valeur de retour plutôt qu'une référence vers s_x.

Pour les lecteurs avancés

Voici un autre exemple, moins évident, du même problème :

#include <iostream>
#include <string>
#include <string_view>

std::string& getName()
{
    static std::string s_name{};
    std::cout << "Enter a name: ";
    std::cin >> s_name;
    return s_name;
}

void printFirstAlphabetical(const std::string& s1, const std::string& s2)
{
    if (s1 < s2)
        std::cout << s1 << " comes before " << s2 << '\n';
    else
        std::cout << s2 << " comes before " << s1 << '\n';
}

int main()
{
    printFirstAlphabetical(getName(), getName());

    return 0;
}

Voici le résultat d'une exécution de ce programme :


Enter a name: Dave
Enter a name: Stan
Stan comes before Stan

Dans cet exemple, getName() renvoie une référence vers la variable locale statique s_name. Initialiser un const std::string& avec une référence à s_name fait que cette std::string& se lie à s_name (sans en faire une copie).

Ainsi, s1 et s2 désignent toutes deux s_name (qui a reçu le dernier nom saisi).

Notez que si nous utilisons plutôt des paramètres std::string_view, le premier paramètre std::string_view sera invalidé lorsque la std::string sous-jacente sera modifiée.

Un autre problème fréquent avec les programmes qui renvoient par référence une variable statique locale non constante est qu'il n'existe pas de moyen standardisé de remettre s_x dans son état par défaut. Ces programmes doivent donc soit utiliser une solution non conventionnelle (par exemple un paramètre de fonction de réinitialisation), soit ne peuvent être réinitialisés qu'en quittant et en relançant le programme.

Bonne pratique

Évitez de renvoyer des références vers des variables locales statiques non constantes.

Renvoyer une référence constante vers une variable locale statique constante est parfois fait lorsque la variable est coûteuse à créer et/ou à initialiser (afin de ne pas la recréer à chaque appel de fonction). Mais c'est rare.

Renvoyer une référence constante vers une variable globale constante est également parfois fait comme moyen d'encapsuler l'accès à une variable globale. Nous en discutons dans la leçon 7.8 -- Pourquoi les variables globales (non constantes) sont néfastes. Utilisé à dessein et avec précaution, cela est également acceptable.

Initialiser ou affecter une variable normale avec une référence renvoyée crée une copie

Si une fonction renvoie une référence, et que cette référence sert à initialiser ou à affecter une variable qui n'est pas une référence, la valeur de retour sera copiée (comme si elle avait été renvoyée par valeur).

#include <iostream>
#include <string>

const int& getNextId()
{
    static int s_x{ 0 };
    ++s_x;
    return s_x;
}

int main()
{
    const int id1 { getNextId() }; // id1 est désormais une variable normale et reçoit une copie de la valeur renvoyée par référence par getNextId()
    const int id2 { getNextId() }; // id2 est désormais une variable normale et reçoit une copie de la valeur renvoyée par référence par getNextId()

    std::cout << id1 << id2 << '\n';

    return 0;
}

Dans l'exemple ci-dessus, getNextId() renvoie une référence, mais id1 et id2 sont des variables qui ne sont pas des références. Dans ce cas, la valeur de la référence renvoyée est copiée dans la variable normale. Ce programme affiche donc :


12

Notez également que si un programme renvoie une référence pendante, celle-ci reste pendante avant que la copie ne soit faite, ce qui conduit à un comportement indéfini :

#include <iostream>
#include <string>

const std::string& getProgramName() // renverra une référence constante
{
    const std::string programName{ "Calculator" };

    return programName;
}

int main()
{
    std::string name { getProgramName() }; // fait une copie d'une référence pendante
    std::cout << "This program is named " << name << '\n'; // comportement indéfini

    return 0;
}

Il est correct de renvoyer par référence des paramètres passés par référence

De nombreux cas justifient de renvoyer des objets par référence, et nous en rencontrerons beaucoup dans les leçons à venir. Cependant, en voici un exemple utile que nous pouvons montrer dès maintenant.

Si un paramètre est passé à une fonction par référence, il est sûr de renvoyer ce paramètre par référence. Cela a du sens : pour passer un argument à une fonction, l'argument doit exister dans la portée de l'appelant. Lorsque la fonction appelée retourne, cet objet doit toujours exister dans la portée de l'appelant.

Voici un exemple simple d'une telle fonction :

#include <iostream>
#include <string>

// Prend deux objets std::string, renvoie celui qui vient en premier dans l'ordre alphabétique
const std::string& firstAlphabetical(const std::string& a, const std::string& b)
{
    return (a < b) ? a : b; // On peut utiliser operator< sur std::string pour déterminer lequel vient en premier alphabétiquement
}

int main()
{
    std::string hello { "Hello" };
    std::string world { "World" };

    std::cout << firstAlphabetical(hello, world) << '\n';

    return 0;
}

Ce programme affiche :


Hello

Dans la fonction ci-dessus, l'appelant transmet deux objets std::string par référence constante, et la chaîne qui vient en premier alphabétiquement est renvoyée par référence constante. Si nous avions utilisé un passage par valeur et un retour par valeur, nous aurions créé jusqu'à 3 copies de std::string (une pour chaque paramètre, une pour la valeur de retour). En utilisant le passage par référence et le retour par référence, nous évitons ces copies.

Il est correct de renvoyer par référence constante un rvalue passé par référence constante

Lorsqu'un argument passé à un paramètre de référence constante est une rvalue, il reste correct de renvoyer ce paramètre par référence constante.

En effet, les rvalues ne sont détruites qu'à la fin de l'expression complète dans laquelle elles sont créées.

Examinons d'abord cet exemple :

#include <iostream>
#include <string>

std::string getHello()
{
    return "Hello"; // conversion implicite en std::string
}

int main()
{
    const std::string s{ getHello() };

    std::cout << s;

    return 0;
}

Dans ce cas, getHello() renvoie une std::string par valeur, qui est une rvalue. Cette rvalue sert ensuite à initialiser s. Une fois l'initialisation de s terminée, l'expression dans laquelle la rvalue a été créée est évaluée entièrement, et la rvalue est détruite.

Examinons maintenant cet exemple similaire :

#include <iostream>
#include <string>

const std::string& foo(const std::string& s)
{
    return s;
}

std::string getHello()
{
    return "Hello"; // conversion implicite en std::string
}

int main()
{
    const std::string s{ foo(getHello()) };

    std::cout << s;

    return 0;
}

La seule différence dans ce cas est que la rvalue est passée par référence constante à foo(), puis renvoyée par référence constante à l'appelant avant d'être utilisée pour initialiser s. Tout le reste fonctionne de manière identique.

Nous examinons un cas similaire dans la leçon 14.6 -- Fonctions d'accès.

L'appelant peut modifier des valeurs via la référence

Lorsqu'un argument est passé à une fonction par référence non constante, la fonction peut utiliser cette référence pour modifier la valeur de l'argument.

De même, lorsqu'une référence non constante est renvoyée par une fonction, l'appelant peut utiliser cette référence pour modifier la valeur renvoyée.

Voici un exemple illustratif :

#include <iostream>

// prend deux entiers par référence non constante, et renvoie le plus grand par référence
int& max(int& x, int& y)
{
    return (x > y) ? x : y;
}

int main()
{
    int a{ 5 };
    int b{ 6 };

    max(a, b) = 7; // affecte 7 au plus grand de a ou b

    std::cout << a << b << '\n';

    return 0;
}

Dans le programme ci-dessus, max(a, b) appelle la fonction max() avec a et b comme arguments. Le paramètre de référence x se lie à l'argument a, et le paramètre de référence y se lie à l'argument b. La fonction détermine ensuite lequel de x (5) et y (6) est le plus grand. Ici, c'est y, donc la fonction renvoie y (toujours lié à b) à l'appelant. L'appelant affecte alors la valeur 7 à cette référence renvoyée.

L'expression max(a, b) = 7 se résout donc effectivement en b = 7.

Ce programme affiche :


57

Retour par adresse

Le retour par adresse fonctionne presque de la même manière que le retour par référence, à ceci près qu'un pointeur vers un objet est renvoyé à la place d'une référence vers un objet. Le retour par adresse a la même mise en garde principale que le retour par référence : l'objet renvoyé par adresse doit survivre à la portée de la fonction qui renvoie l'adresse, sinon l'appelant reçoit un pointeur pendant.

L'avantage majeur du retour par adresse par rapport au retour par référence est que la fonction peut renvoyer nullptr s'il n'existe aucun objet valide à renvoyer. Par exemple, supposons que nous disposions d'une liste d'étudiants dans laquelle nous voulons effectuer une recherche. Si nous trouvons l'étudiant recherché dans la liste, nous pouvons renvoyer un pointeur vers l'objet qui représente cet étudiant. Si aucun étudiant ne correspond, nous pouvons renvoyer nullptr pour indiquer qu'aucun objet étudiant correspondant n'a été trouvé.

L'inconvénient majeur du retour par adresse est que l'appelant doit penser à vérifier que le pointeur n'est pas nullptr avant de le déréférencer, sinon un déréférencement de pointeur nul peut survenir et entraîner un comportement indéfini. À cause de ce danger, le retour par référence doit être préféré au retour par adresse, sauf si la possibilité de renvoyer « aucun objet » est nécessaire.

Bonne pratique

Préférez le retour par référence au retour par adresse, sauf si la possibilité de renvoyer « aucun objet » (à l'aide de nullptr) est importante.

Contenu associé
