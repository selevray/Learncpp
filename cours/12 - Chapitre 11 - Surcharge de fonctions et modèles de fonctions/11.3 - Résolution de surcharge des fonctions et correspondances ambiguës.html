11.3 — Résolution de surcharge des fonctions et correspondances ambiguës

Dans la leçon précédente (11.2 -- Différenciation des fonctions surchargées), nous avons vu quels attributs d'une fonction permettent de différencier les fonctions surchargées les unes des autres. Si une fonction surchargée n'est pas correctement différenciée des autres surcharges portant le même nom, le compilateur produira une erreur de compilation.

Cependant, disposer d'un ensemble de fonctions surchargées correctement différenciées ne représente que la moitié du tableau. Lors de chaque appel de fonction, le compilateur doit aussi s'assurer qu'une déclaration de fonction correspondante peut être trouvée.

Avec les fonctions non surchargées (fonctions dont le nom est unique), une seule fonction peut potentiellement correspondre à un appel. Cette fonction correspond soit directement, soit après application de conversions de types, soit pas du tout (et une erreur de compilation en résulte). Avec les fonctions surchargées, plusieurs fonctions peuvent potentiellement correspondre à un appel. Comme un appel ne peut se rattacher qu'à une seule d'entre elles, le compilateur doit déterminer la surcharge qui correspond le mieux. Le processus qui consiste à associer un appel de fonction à une surcharge précise s'appelle résolution de surcharge (overload resolution).

Dans les cas simples où le type des arguments et le type des paramètres correspondent exactement, cette résolution est (en général) directe :

#include <iostream>

void print(int x)
{
     std::cout << x << '\n';
}

void print(double d)
{
     std::cout << d << '\n';
}

int main()
{
     print(5); // 5 est un int, donc cela correspond à print(int)
     print(6.7); // 6.7 est un double, donc cela correspond à print(double)

     return 0;
}

Mais que se passe-t-il lorsque les types des arguments de l'appel ne correspondent exactement aux types des paramètres d'aucune surcharge ? Par exemple :

#include <iostream>

void print(int x)
{
     std::cout << x << '\n';
}

void print(double d)
{
     std::cout << d << '\n';
}

int main()
{
     print('a'); // char ne correspond ni à int ni à double, que se passe-t-il ?
     print(5L); // long ne correspond ni à int ni à double, que se passe-t-il ?

     return 0;
}

Il n'y a pas de correspondance exacte ici, mais cela ne signifie pas qu'aucune correspondance ne peut être trouvée : après tout, un char ou un long peut être converti implicitement en int ou en double. Mais quelle est la meilleure conversion à effectuer dans chaque cas ?

Dans cette leçon, nous allons voir comment le compilateur associe un appel de fonction donné à une fonction surchargée précise.

Résolution des appels de fonctions surchargées

Lorsqu'un appel est effectué vers une fonction surchargée, le compilateur parcourt une suite de règles pour déterminer laquelle des fonctions surchargées (le cas échéant) correspond le mieux (nous détaillerons ces étapes dans la section suivante).

À chaque étape, le compilateur applique différentes conversions de types aux arguments de l'appel. Pour chaque conversion appliquée, il vérifie si l'une des fonctions surchargées correspond désormais. Une fois toutes les conversions de l'étape appliquées et vérifiées, l'étape est terminée. Le résultat peut prendre l'une de trois formes :

  • Aucune fonction correspondante n'a été trouvée. Le compilateur passe à l'étape suivante de la séquence.
  • Une seule fonction correspondante a été trouvée. Cette fonction est considérée comme la meilleure correspondance. Le processus de recherche est alors terminé, et les étapes suivantes ne sont pas exécutées.
  • Plusieurs fonctions correspondantes ont été trouvées. Le compilateur émet une erreur de compilation de correspondance ambiguë. Nous reviendrons plus loin sur ce cas.

Si le compilateur atteint la fin de toute la séquence sans trouver de correspondance, il génère une erreur de compilation indiquant qu'aucune fonction surchargée correspondant à l'appel n'a pu être trouvée.

La séquence de correspondance des arguments

Étape 1) Le compilateur cherche d'abord une correspondance exacte. Cette étape se déroule en deux phases. Dans la première, le compilateur vérifie s'il existe une surcharge pour laquelle le type des arguments de l'appel correspond exactement au type des paramètres :

void foo(int)
{
}

void foo(double)
{
}

int main()
{
    foo(0);   // correspondance exacte avec foo(int)
    foo(3.4); // correspondance exacte avec foo(double)

    return 0;
}

Comme le 0 de l'appel foo(0) est un int, le compilateur vérifie si une surcharge foo(int) a été déclarée. C'est le cas, donc le compilateur considère que foo(int) est une correspondance exacte.

Dans la seconde phase, le compilateur applique un certain nombre de conversions triviales aux arguments de l'appel. Les conversions triviales (trivial conversions) forment un ensemble de règles de conversion particulières qui modifient le type (sans modifier la valeur) afin de trouver une correspondance. Elles comprennent :

  • les conversions lvalue vers rvalue ;
  • les conversions de qualification (par exemple non-const vers const) ;
  • les conversions non-référence vers référence.

Par exemple :

void foo(const int)
{
}

void foo(const double&) // double& est une référence vers un double
{
}

int main()
{
    int x { 1 };
    foo(x); // x est converti trivialement de int en const int

    double d { 2.3 };
    foo(d); // d est converti trivialement de double en const double& (conversion non-référence vers référence)

    return 0;
}

Dans l'exemple ci-dessus, nous appelons foo(x), où x est un int. Le compilateur convertit trivialement x d'un int en const int, ce qui correspond alors à foo(const int). Nous appelons aussi foo(d), où d est un double. Le compilateur convertit trivialement d d'un double en const double&, ce qui correspond alors à foo(const double&).

Contenu connexe

Nous abordons les références dans la leçon 12.3 -- Références lvalue.

Les correspondances obtenues par ces conversions triviales sont considérées comme des correspondances exactes. Cela signifie que le programme suivant produit une correspondance ambiguë :

void foo(int)
{
}

void foo(const int&) // int& est une référence vers un int
{
}

int main()
{
    int x { 1 };
    foo(x); // correspondance ambiguë avec foo(int) et foo(const int&)

    return 0;
}

Étape 2) Si aucune correspondance exacte n'est trouvée, le compilateur tente une correspondance en appliquant la promotion numérique aux arguments. Dans la leçon (10.1 -- Conversion implicite de type), nous avons vu que certains types entiers et flottants étroits peuvent être automatiquement promus vers des types plus larges, tels que int ou double. Si, après promotion numérique, une correspondance est trouvée, l'appel est résolu.

Par exemple :

void foo(int)
{
}

void foo(double)
{
}

int main()
{
    foo('a');  // promu pour correspondre à foo(int)
    foo(true); // promu pour correspondre à foo(int)
    foo(4.5f); // promu pour correspondre à foo(double)

    return 0;
}

Pour foo('a'), comme aucune correspondance exacte avec foo(char) n'a pu être trouvée à l'étape précédente, le compilateur promeut le char 'a' en int et recherche une correspondance. Elle correspond à foo(int), donc l'appel se résout vers foo(int).

Étape 3) Si aucune correspondance n'est trouvée par promotion numérique, le compilateur tente une correspondance en appliquant aux arguments des conversions numériques (10.3 -- Conversions numériques).

Par exemple :

#include <string> // pour std::string

void foo(double)
{
}

void foo(std::string)
{
}

int main()
{
    foo('a'); // 'a' converti pour correspondre à foo(double)

    return 0;
}

Ici, comme il n'existe ni foo(char) (correspondance exacte) ni foo(int) (correspondance par promotion), le 'a' est converti numériquement en double et associé à foo(double).

Point clé

Les correspondances obtenues par promotions numériques l'emportent sur celles obtenues par conversions numériques.

Étape 4) Si aucune correspondance n'est trouvée par conversion numérique, le compilateur tente une correspondance par conversions définies par l'utilisateur. Bien que nous n'ayons pas encore abordé ces conversions, certains types (par exemple les classes) peuvent définir des conversions vers d'autres types qui peuvent être invoquées implicitement. Voici un exemple, uniquement pour illustrer le propos :

// Nous n'avons pas encore vu les classes, donc ne vous inquiétez pas si cela ne vous semble pas clair
class X // ceci définit un nouveau type appelé X
{
public:
    operator int() { return 0; } // Voici une conversion définie par l'utilisateur de X vers int
};

void foo(int)
{
}

void foo(double)
{
}

int main()
{
    X x; // Ici, nous créons un objet de type X (nommé x)
    foo(x); // x est converti en int grâce à la conversion définie par l'utilisateur de X vers int

    return 0;
}

Dans cet exemple, le compilateur vérifie d'abord s'il existe une correspondance exacte avec foo(X). Nous n'en avons pas défini. Ensuite, il vérifie si x peut être promu numériquement, ce qui n'est pas le cas. Il vérifie alors si x peut subir une conversion numérique, ce qui n'est pas non plus le cas. Enfin, il recherche les conversions définies par l'utilisateur. Comme nous avons défini une conversion de X vers int, le compilateur convertit X en int pour correspondre à foo(int).

Après application d'une conversion définie par l'utilisateur, le compilateur peut appliquer des promotions ou conversions supplémentaires pour trouver une correspondance. Ainsi, si notre conversion définie par l'utilisateur avait produit un char au lieu d'un int, le compilateur aurait utilisé cette conversion vers char, puis promu le résultat en int pour trouver la correspondance.

Contenu connexe

Le constructeur d'une classe agit aussi comme une conversion définie par l'utilisateur, depuis d'autres types vers ce type classe, et peut être utilisé à cette étape pour trouver des fonctions correspondantes.

Étape 5) Si aucune correspondance n'est trouvée par conversion définie par l'utilisateur, le compilateur recherche une fonction correspondante qui utilise des points de suspension (ellipsis).

Contenu connexe

Étape 6) Si aucune correspondance n'a été trouvée à ce stade, le compilateur abandonne et émet une erreur de compilation indiquant qu'il n'a pas pu trouver de fonction correspondante.

Correspondances ambiguës

Avec les fonctions non surchargées, chaque appel se résout soit vers une fonction, soit, si aucune correspondance n'est trouvée, vers une erreur de compilation :

void foo()
{
}

int main()
{
     foo(); // correct : correspondance trouvée
     goo(); // erreur de compilation : aucune correspondance trouvée

     return 0;
}

Avec les fonctions surchargées, il existe un troisième résultat possible : une correspondance ambiguë (ambiguous match). Une correspondance ambiguë (ambiguous match) se produit lorsque le compilateur trouve deux fonctions ou plus pouvant correspondre à l'appel au ccours de la même étape. Dans ce cas, le compilateur arrête la recherche et émet une erreur de compilation signalant un appel de fonction ambigu.

Comme chaque fonction surchargée doit être différenciée pour que le programme compile, vous pouvez vous demander comment un appel de fonction peut correspondre à plus d'une fonction. Examinons un exemple qui l'illustre :

void foo(int)
{
}

void foo(double)
{
}

int main()
{
    foo(5L); // 5L est de type long

    return 0;
}

Comme le littéral 5L est de type long, le compilateur cherche d'abord une correspondance exacte avec foo(long), sans en trouver. Ensuite, il tente une promotion numérique, mais les valeurs de type long ne peuvent pas être promues, donc il n'y a pas non plus de correspondance à cette étape.

Il tente alors une correspondance en appliquant des conversions numériques à l'argument long. En parcourant toutes les règles de conversion numérique, le compilateur trouve deux correspondances possibles. Si l'argument long est converti en int, l'appel correspond à foo(int). Si l'argument long est converti en double, il correspond alors à foo(double). Comme deux correspondances possibles par conversion numérique ont été trouvées, l'appel est considéré comme ambigu.

Avec Visual Studio 2019, cela produit le message d'erreur suivant :


error C2668: 'foo': ambiguous call to overloaded function
message : could be 'void foo(double)'
message : or       'void foo(int)'
message : while trying to match the argument list '(long)'

Point clé

Si le compilateur trouve plusieurs correspondances au cours d'une même étape, l'appel de fonction est ambigu. Cela signifie qu'aucune correspondance de cette étape n'est considérée comme meilleure qu'une autre correspondance de la même étape.

Voici un autre exemple produisant des correspondances ambiguës :

void foo(unsigned int)
{
}

void foo(float)
{
}

int main()
{ 
    foo(0);       // un int peut être converti numériquement en unsigned int ou en float
    foo(3.14159); // un double peut être converti numériquement en unsigned int ou en float

    return 0;
}

Bien que l'on puisse s'attendre à ce que 0 se résolve vers foo(unsigned int) et 3.14159 vers foo(float), ces deux appels produisent une correspondance ambiguë. La valeur int 0 peut être convertie numériquement en unsigned int ou en float, donc les deux surcharges correspondent aussi bien l'une que l'autre, et l'appel est ambigu.

Il en va de même pour la conversion d'un double en float ou en unsigned int. Ce sont deux conversions numériques, donc les deux surcharges correspondent aussi bien l'une que l'autre, et le résultat est à nouveau ambigu.

Pour les lecteurs avancés

Les arguments par défaut peuvent également provoquer des correspondances ambiguës. Nous traitons ces cas dans la leçon 11.5 -- Arguments par défaut.

Résoudre les correspondances ambiguës

Les correspondances ambiguës étant une erreur de compilation, elles doivent être levées avant que votre programme puisse compiler. Il existe plusieurs façons de les résoudre :

  1. Souvent, la meilleure solution consiste simplement à définir une nouvelle fonction surchargée qui prend des paramètres exactement du type avec lequel vous appelez la fonction. C++ pourra alors trouver une correspondance exacte pour l'appel.
  2. Vous pouvez aussi convertir explicitement les arguments ambigus pour qu'ils correspondent au type de la fonction que vous voulez appeler. Par exemple, pour que foo(0) corresponde à foo(unsigned int) dans l'exemple ci-dessus, vous écririez :
int x{ 0 };
foo(static_cast<unsigned int>(x)); // appellera foo(unsigned int)
  1. Si votre argument est un littéral, vous pouvez utiliser le suffixe du littéral pour vous assurer qu'il est interprété avec le bon type :
foo(0u); // appellera foo(unsigned int) car le suffixe 'u' désigne un unsigned int, c'est donc désormais une correspondance exacte

La liste des suffixes les plus utilisés se trouve dans la leçon 5.2 -- Littéraux.

Correspondance pour les fonctions à plusieurs arguments

S'il y a plusieurs arguments, le compilateur applique les règles de correspondance à chaque argument tour à tour. La fonction choisie est celle pour laquelle chaque argument correspond au moins aussi bien que dans toutes les autres fonctions candidates, et pour laquelle au moins un argument correspond mieux que dans toutes les autres fonctions. En d'autres termes, la fonction choisie doit offrir une meilleure correspondance que toutes les autres fonctions candidates pour au moins un paramètre, et une correspondance non moins bonne pour tous les autres paramètres.

Si une telle fonction est trouvée, elle constitue clairement et sans ambiguïté le meilleur choix. Si aucune fonction de ce type ne peut être trouvée, l'appel est considéré comme ambigu (ou comme n'ayant aucune correspondance).

Par exemple :

#include <iostream>

void print(char, int)
{
    std::cout << 'a' << '\n';
}

void print(char, double)
{
    std::cout << 'b' << '\n';
}

void print(char, float)
{
    std::cout << 'c' << '\n';
}

int main()
{
    print('x', 'a');

    return 0;
}

Dans le programme ci-dessus, toutes les fonctions correspondent exactement au premier argument. En revanche, la fonction du haut correspond au second paramètre par promotion, alors que les autres nécessitent une conversion. Par conséquent, print(char, int) est sans ambiguïté la meilleure correspondance.
