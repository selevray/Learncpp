20.2 — La pile (stack) et le tas (heap)

La mémoire utilisée par un programme est généralement divisée en plusieurs zones, appelées segments :

  • Le segment de code (aussi appelé segment de texte), où se trouve le programme compilé en mémoire. Ce segment est généralement en lecture seule.
  • Le segment bss (aussi appelé segment de données non initialisées), où sont stockées les variables globales et statiques initialisées à zéro.
  • Le segment de données (aussi appelé segment de données initialisées), où sont stockées les variables globales et statiques initialisées explicitement.
  • Le tas (heap), à partir duquel sont alloués les objets créés dynamiquement.
  • La pile d'appels (call stack), où sont stockés les paramètres des fonctions, les variables locales et les autres informations liées aux fonctions.

Dans cette leçon, nous nous concentrerons principalement sur le tas et la pile, car c'est là que se passe l'essentiel des choses intéressantes.

Le segment de tas

Le segment de tas (aussi appelé « magasin libre », free store) garde la trace de la mémoire utilisée pour l'allocation dynamique. Nous avons déjà abordé le tas brièvement dans la leçon 19.1 -- Allocation dynamique de mémoire avec new et delete, voici donc un bref rappel.

En C++, lorsque vous utilisez l'opérateur new pour allouer de la mémoire, cette mémoire est allouée dans le segment de tas de l'application.

En supposant qu'un int occupe 4 octets :

int* ptr { new int }; // new int alloue 4 octets dans le tas
int* array { new int[10] }; // new int[10] alloue 40 octets dans le tas

L'adresse de cette mémoire est renvoyée par l'opérateur new et peut ensuite être stockée dans un pointeur. Vous n'avez pas à vous soucier du mécanisme qui permet de trouver de la mémoire libre et de la mettre à disposition de l'utilisateur. Il est toutefois bon de savoir que des allocations successives ne donnent pas forcément des adresses mémoire successives !

int* ptr1 { new int };
int* ptr2 { new int };
// ptr1 et ptr2 n'ont pas forcément des adresses consécutives

Lorsqu'une variable allouée dynamiquement est supprimée, la mémoire est « rendue » au tas et peut être réattribuée pour les demandes d'allocation futures. Rappelez-vous que supprimer un pointeur ne supprime pas la variable : cela renvoie simplement au système d'exploitation la mémoire située à l'adresse associée.

Le tas présente des avantages et des inconvénients :

  • L'allocation de mémoire sur le tas est relativement lente.
  • La mémoire allouée reste allouée jusqu'à sa libération explicite (attention aux fuites de mémoire) ou jusqu'à la fin de l'application (le système d'exploitation doit alors la récupérer).
  • La mémoire allouée dynamiquement doit être accédée à travers un pointeur. Déréférencer un pointeur est plus lent que d'accéder directement à une variable.
  • Comme le tas est un grand réservoir de mémoire, de grands tableaux, structures ou classes peuvent y être alloués.

La pile d'appels

La pile d'appels (généralement appelée « la pile », call stack en anglais) joue un rôle beaucoup plus intéressant. Elle garde la trace de toutes les fonctions actives (celles qui ont été appelées et ne se sont pas encore terminées), depuis le début du programme jusqu'au point d'exécution courant, et gère l'allocation de tous les paramètres de fonctions et de toutes les variables locales.

La pile d'appels est implémentée sous la forme d'une structure de données de type pile. Avant de voir comment fonctionne la pile d'appels, il faut donc comprendre ce qu'est une pile.

La structure de données pile

Une structure de données (data structure) est un mécanisme de programmation permettant d'organiser les données de façon à pouvoir les utiliser efficacement. Vous avez déjà rencontré plusieurs structures de données, comme les tableaux et les structures (struct). Ces deux structures fournissent des mécanismes pour stocker des données et y accéder de manière efficace. Il existe de nombreuses autres structures de données couramment utilisées en programmation, dont beaucoup sont implémentées dans la bibliothèque standard, et la pile en fait partie.

Pensez à une pile d'assiettes dans une cafétéria. Comme chaque assiette est lourde et qu'elles sont empilées, vous ne pouvez faire que l'une de ces trois choses :

  1. Regarder la surface de l'assiette du dessus
  2. Retirer l'assiette du dessus de la pile (ce qui découvre celle située dessous, si elle existe)
  3. Poser une nouvelle assiette sur le dessus de la pile (ce qui cache celle située dessous, si elle existe)

En programmation, une pile est une structure conteneur qui contient plusieurs variables (un peu comme un tableau). Cependant, alors qu'un tableau permet d'accéder et de modifier les éléments dans l'ordre que l'on souhaite (c'est ce qu'on appelle l'accès aléatoire, random access), une pile est plus restrictive. Les opérations possibles sur une pile correspondent aux trois actions mentionnées ci-dessus :

  1. Regarder l'élément du dessus de la pile (généralement via une fonction nommée top(), parfois appelée peek())
  2. Retirer l'élément du dessus de la pile (via une fonction nommée pop())
  3. Placer un nouvel élément au sommet de la pile (via une fonction nommée push())

Une pile est une structure de type dernier entré, premier sorti (LIFO, last-in, first-out). Le dernier élément empilé sera le premier à être dépilé. Si vous posez une nouvelle assiette sur la pile, la première assiette retirée sera celle que vous venez de poser. Dernier entré, premier sorti. Au fur et à mesure que des éléments sont empilés, la pile grossit ; à mesure qu'ils sont dépilés, elle rétrécit.

Par exemple, voici une courte séquence montrant le fonctionnement des opérations d'empilement et de dépilement :

L'analogie des assiettes est assez bonne pour comprendre le fonctionnement de la pile d'appels, mais nous pouvons en proposer une meilleure. Imaginez une série de boîtes aux lettres empilées les unes sur les autres. Chaque boîte ne peut contenir qu'un seul objet, et toutes les boîtes sont vides au départ. De plus, chaque boîte est clouée à celle qui se trouve en dessous, si bien que leur nombre ne peut pas changer. Si l'on ne peut pas modifier le nombre de boîtes, comment obtenir un comportement de pile ?

Tout d'abord, nous utilisons un marqueur (comme un post-it) pour repérer la boîte vide la plus basse. Au départ, il s'agit de la boîte la plus basse (au fond de la pile). Lorsque nous empilons un élément, nous le plaçons dans la boîte marquée (c'est-à-dire la première boîte vide) et nous remontons le marqueur d'une boîte. Lorsque nous dépilons un élément, nous descendons le marqueur d'une boîte (il pointe alors sur la boîte non vide la plus haute) et nous retirons l'élément de cette boîte. Tout ce qui se trouve sous le marqueur est considéré comme « sur la pile ». Tout ce qui se trouve au niveau du marqueur ou au-dessus n'est pas sur la pile.

Le segment de la pile d'appels

Le segment de la pile d'appels contient la mémoire utilisée par la pile d'appels. Au démarrage de l'application, le système d'exploitation empile la fonction main(). Le programme commence alors son exécution.

Lorsqu'un appel de fonction est rencontré, la fonction est empilée. Lorsque la fonction courante se termine, elle est dépilée (ce processus est parfois appelé dérouler la pile, unwinding the stack). Ainsi, en examinant les fonctions actuellement présentes sur la pile d'appels, on peut voir toutes les fonctions qui ont été appelées pour arriver au point d'exécution courant.

Notre analogie des boîtes aux lettres correspond assez bien au fonctionnement de la pile d'appels. La pile elle-même est un bloc d'adresses mémoire de taille fixe. Les boîtes aux lettres représentent les adresses mémoire, et les « éléments » que nous empilons et dépilons sont appelés cadres de pile (stack frames). Un cadre de pile contient toutes les données associées à un appel de fonction donné. Nous reparlerons des cadres de pile dans un instant. Le « marqueur » est un registre (une petite zone de mémoire située dans le processeur) appelé pointeur de pile (stack pointer, souvent abrégé « SP »). Le pointeur de pile indique où se trouve actuellement le sommet de la pile d'appels.

Nous pouvons faire une optimisation supplémentaire : lorsque nous dépilons un élément, il suffit de descendre le pointeur de pile. Nous n'avons pas besoin de nettoyer ni de mettre à zéro la mémoire utilisée par le cadre de pile dépilé (l'équivalent de vider la boîte aux lettres). Cette mémoire n'est plus considérée comme « sur la pile » (le pointeur de pile est à cette adresse ou en dessous), donc elle ne sera plus accédée. Si nous empilons plus tard un nouveau cadre à cet endroit, il écrasera l'ancienne valeur que nous n'avons jamais nettoyée.

La pile d'appels en action

Examinons plus en détail le fonctionnement de la pile d'appels. Voici la suite d'étapes qui se produit lorsqu'une fonction est appelée :

  1. Le programme rencontre un appel de fonction.
  2. Un cadre de pile est construit et empilé. Le cadre de pile contient :
  • L'adresse de l'instruction qui suit l'appel de fonction (appelée adresse de retour, return address). C'est ce qui permet au processeur de se souvenir où reprendre l'exécution une fois la fonction appelée terminée.
  • Tous les arguments de la fonction.
  • L'espace mémoire des variables locales.
  • Les copies sauvegardées des registres modifiés par la fonction, qui doivent être restaurées au retour de celle-ci.
  1. Le processeur saute au point d'entrée de la fonction.
  2. Les instructions de la fonction commencent à s'exécuter.

Lorsque la fonction se termine, les étapes suivantes ont lieu :

  1. Les registres sont restaurés depuis la pile d'appels.
  2. Le cadre de pile est dépilé. Cela libère la mémoire de toutes les variables locales et de tous les arguments.
  3. La valeur de retour est traitée.
  4. Le processeur reprend l'exécution à l'adresse de retour.

La valeur de retour peut être traitée de différentes manières, selon l'architecture de l'ordinateur. Certaines architectures incluent la valeur de retour dans le cadre de pile, d'autres utilisent des registres du processeur.

En général, il n'est pas indispensable de connaître tous les détails du fonctionnement de la pile d'appels. Toutefois, comprendre que les fonctions sont empilées lorsqu'elles sont appelées et dépilées (déroulées) lorsqu'elles retournent vous donne les bases nécessaires pour comprendre la récursivité, ainsi que d'autres concepts utiles lors du débogage.

Une remarque technique : sur certaines architectures, la pile d'appels croît en s'éloignant de l'adresse mémoire 0. Sur d'autres, elle croît en direction de l'adresse 0. Par conséquent, les nouveaux cadres de pile peuvent avoir une adresse mémoire supérieure ou inférieure à celle des précédents.

Un exemple rapide de pile d'appels

Considérez l'application simple suivante :

int foo(int x)
{
    // b
    return x;
} // foo est dépilée de la pile d'appels ici

int main()
{
    // a
    foo(5); // foo est empilée sur la pile d'appels ici
    // c

    return 0;
}

La pile d'appels se présente ainsi aux points repérés :

a :


main()

b :


foo() (avec le paramètre x)
main()

c :


main()

Dépassement de pile (stack overflow)

La pile a une taille limitée et ne peut donc contenir qu'une quantité limitée d'informations. Sous Visual Studio pour Windows, la taille par défaut de la pile est de 1 Mo. Avec g++/Clang sur les variantes d'Unix, elle peut atteindre 8 Mo. Si le programme tente de placer trop d'informations sur la pile, un dépassement de pile (stack overflow) se produit. Il survient lorsque toute la mémoire de la pile a été allouée : les allocations suivantes débordent alors dans d'autres zones de la mémoire.

Un dépassement de pile résulte généralement d'une allocation de trop nombreuses variables sur la pile, et/ou d'un trop grand nombre d'appels de fonctions imbriqués (où la fonction A appelle B, qui appelle C, qui appelle D, etc.). Sur les systèmes d'exploitation modernes, un dépassement de pile provoque généralement une violation d'accès signalée par le système, qui termine le programme.

Voici un exemple de programme qui provoquera probablement un dépassement de pile. Vous pouvez l'exécuter sur votre système et observer le plantage :

#include <iostream>

int main()
{
    int stack[10000000];
    std::cout << "hi" << stack[0]; // nous utilisons stack[0] ici afin que le compilateur n'optimise pas le tableau

    return 0;
}

Ce programme tente d'allouer sur la pile un tableau énorme (probablement 40 Mo). Comme la pile n'est pas assez grande pour contenir ce tableau, l'allocation déborde dans des zones de la mémoire que le programme n'a pas le droit d'utiliser.

Sous Windows (Visual Studio), ce programme produit le résultat suivant :


HelloWorld.exe (process 15916) exited with code -1073741571.

-1073741571 correspond à c0000005 en hexadécimal, qui est le code Windows d'une violation d'accès. Notez que « hi » n'est jamais affiché, car le programme est terminé avant ce point.

Voici un autre programme qui provoquera un dépassement de pile pour une raison différente :

// Merci au lecteur yellowEmu pour l'idée d'ajouter un compteur
#include <iostream>

int g_counter{ 0 };

void eatStack()
{
    std::cout << ++g_counter << ' ';

    // Nous utilisons une condition ici pour éviter les avertissements du compilateur concernant la récursion infinie
    if (g_counter > 0)
        eatStack(); // notez que eatStack() s'appelle elle-même

    // Nécessaire pour empêcher le compilateur d'effectuer une optimisation d'appel terminal (tail-call optimization)
    std::cout << "hi";
}

int main()
{
    eatStack();

    return 0;
}

Dans le programme ci-dessus, un cadre de pile est empilé à chaque appel de la fonction eatStack(). Comme eatStack() s'appelle elle-même (et ne retourne jamais à l'appelant), la pile finit par manquer de mémoire et provoque un dépassement.

Note de l'auteur

Exécuté sur la machine Windows 10 de l'auteur (depuis l'IDE Visual Studio Community), eatStack() a planté après 4848 appels en mode debug, et après 128 679 appels en mode release.

Contenu associé

Nous reparlerons des fonctions qui s'appellent elles-mêmes dans la prochaine leçon 20.3 -- La récursivité.

La pile présente des avantages et des inconvénients :

  • L'allocation de mémoire sur la pile est relativement rapide.
  • La mémoire allouée sur la pile reste dans sa portée tant qu'elle est sur la pile. Elle est détruite lorsqu'elle est dépilée.
  • Toute la mémoire allouée sur la pile est connue à la compilation. Par conséquent, elle peut être accédée directement à travers une variable.
  • Comme la pile est relativement petite, il est généralement déconseillé de faire quoi que ce soit qui consomme beaucoup d'espace de pile. Cela inclut l'allocation ou la copie de grands tableaux, ou d'autres structures gourmandes en mémoire.
