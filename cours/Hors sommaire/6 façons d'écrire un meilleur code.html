6 façons d'écrire un meilleur code

Un article repris sur Digg il y a quelques jours, intitulé « 6 ways to write better code », donnait de bons conseils (pour la plupart). J'ai donc pensé le relayer ici.

http://www.ibm.com/developerworks/linux/library/l-clear-code/index.html?ca=drs-

Voici les recommandations de l'auteur, accompagnées de mes propres commentaires :
1) Commentez comme une personne intelligente.

Je ne saurais trop insister là-dessus. Un code qui semble évident sur le moment se lit parfois comme une langue étrangère au bout de quelques mois. Commentez tout, et ne vous contentez pas d'énoncer l'évident. Essayez de rédiger chaque commentaire comme si vous le destiniez à quelqu'un qui ignore tout de ce que vous faites. Car dans trois ou six mois, cette personne, ce sera vous.

2) Utilisez beaucoup de #define. Non, BEAUCOUP.

Bonne intention, mauvaise mise en œuvre. Comme l'article le dit, c'est une très mauvaise idée que de coder des nombres en dur dans votre programme. Inévitablement, vous voudrez modifier quelque chose plus tard, et ce sera très difficile si des nombres sont dispersés partout. Utiliser #define aide à documenter ce que vous faites et facilite la modification de ces nombres par la suite.

Mais #define est tellement… du C. L'usage de #define pose quelques problèmes. D'abord, comme #define est une directive du préprocesseur, celui-ci remplace tous vos noms définis par leurs valeurs correspondantes. Cela signifie que ces noms ne sont pas disponibles pendant le débogage, ce qui rend le débogage plus difficile. Supposons qu'un appel de fonction reçoive une valeur définie par #define appelée EXP_PER_KILL. Même si le code que vous déboguez affiche AddExp(EXP_PER_KILL), vous ne saurez pas à quoi EXP_PER_KILL correspond, à moins de retrouver sa définition.

Ensuite, les variables définies par #define sont toujours déclarées dans la portée globale, quel que soit l'endroit où elles sont définies.

En C++, nous pouvons faire mieux. Un choix préférable consiste à utiliser une variable const. Les variables const sont de véritables objets : vous pouvez facilement consulter leurs valeurs dans le débogueur, et elles suivent les règles de portée habituelles. L'autre bon choix consiste à utiliser une énumération (enum), qui offre les mêmes avantages.

3) N'utilisez pas de noms de variables qui vous joueront des tours.

Peu de choses à dire là-dessus : donner à vos variables des noms qui indiquent clairement leur rôle est un aspect important de la documentation de votre code.

4) Vérifiez les erreurs. Vous commettez des erreurs. Oui, vous.

Ce point est à la fois plus simple et plus difficile qu'il n'y paraît. Vous utiliserez inévitablement de façon incorrecte une fonction que vous avez écrite, en lui passant un paramètre invalide, ou quelque chose se passera mal et un pointeur finira à NULL alors que vous attendiez une valeur, ou l'inverse. Vérifier ces situations est une bonne chose, et cela peut empêcher votre programme de planter. Cependant, si vous détectez une erreur sans rien faire d'intelligent de cette information, votre programme pourrait tout aussi bien planter immédiatement.

Détecter une erreur n'est pas le seul problème : il faut aussi savoir y répondre intelligemment. Si vous écrivez une fonction réutilisable, la bonne réponse consiste généralement à signaler à l'appelant qu'un problème est survenu, en lui laissant le soin de le traiter. Si vous êtes l'appelant, ou si vous écrivez une fonction essentielle à votre programme, déterminer comment gérer les erreurs peut s'avérer délicat. Faut-il afficher une boîte de message d'avertissement ? Demander de nouvelles données à l'utilisateur ? Sauvegarder les données de l'utilisateur puis terminer le programme ? Cela dépend vraiment du contexte, et il n'existe pas de solution simple.

Mais avant de pouvoir faire quoi que ce soit de tout cela, il faut d'abord détecter qu'une erreur s'est produite. C'est pourquoi je suis d'accord avec l'auteur : ce point est important.

5) « L'optimisation prématurée est la racine de tous les maux. » - Donald Knuth

L'un des plus gros problèmes rencontrés par les programmeurs débutants ou trop zélés consiste à vouloir écrire un code aussi rapide que possible, au détriment de choses comme la lisibilité. C'est presque toujours une mauvaise idée. Il EST bon de choisir un algorithme adapté au problème à résoudre : par exemple, si vous effectuez de nombreuses insertions et suppressions d'éléments, une liste chaînée sera probablement un meilleur choix qu'un tableau. Mais cela ne signifie pas qu'il faille concevoir un algorithme qui tire jusqu'à la dernière goutte de performance de cette liste chaînée. L'efficacité se paie généralement en lisibilité et, à quelques exceptions près, la lisibilité est plus importante, car à un moment donné, vous devrez corriger un bogue ou étendre votre code, et un code astucieusement optimisé ne facilitera ni l'un ni l'autre.

Une fois votre code écrit, vous pouvez toujours le profiler pour découvrir où se trouvent les VÉRITABLES goulots d'étranglement, plutôt que d'agir prématurément sur ceux que vous pensez deviner. Avec un code correctement implémenté, qui met en œuvre des concepts comme l'encapsulation, remplacer un algorithme par un meilleur, lorsque c'est nécessaire, ne pose souvent aucun problème.

6) Ne soyez pas trop malin.

Ce point va dans le même sens que le n° 5. Il est presque toujours préférable d'écrire un code propre, simple et lisible, plutôt qu'un code aussi efficace que possible. Comme je l'ai écrit dans la section sur les commentaires, si vous avez besoin d'un commentaire pour expliquer ce que fait votre ligne de code, c'est probablement cette ligne qu'il faut réécrire, plutôt que la commenter.

Beaucoup d'entre vous connaissent l'acronyme KISS : « Keep It Simple, Stupid » (« Restez simple, idiot »). Cela s'applique aussi au code.
