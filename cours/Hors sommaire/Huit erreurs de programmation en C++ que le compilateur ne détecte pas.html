Huit erreurs de programmation en C++ que le compilateur ne détecte pas

Le C++ est un langage complexe, plein de pièges subtils pour qui n'y prend pas garde. Il existe un nombre presque infini de façons de tout gâcher. Heureusement, les compilateurs modernes sont assez doués pour détecter un grand nombre de ces cas et signaler le problème par des erreurs de compilation ou des avertissements. En définitive, toute erreur détectable à la compilation cesse d'être un problème si elle est correctement prise en charge, car elle sera repérée et corrigée avant que le programme ne quitte la phase de développement. Au pire, une erreur détectable à la compilation coûte du temps, le temps que le programmeur passe à chercher une solution ou un contournement.

Les erreurs dangereuses sont celles que les compilateurs sont incapables de détecter. Elles ont beaucoup moins de chances d'être remarquées et peuvent avoir de graves conséquences : résultats incorrects, données corrompues, plantages du programme. À mesure que la taille d'un projet augmente, la complexité de la logique et le grand nombre de chemins d'exécution peuvent masquer ces bogues, qui n'apparaissent alors que de façon intermittente, ce qui les rend particulièrement difficiles à traquer et à déboguer. Bien que cette liste ne soit sans doute qu'un rappel pour les programmeurs expérimentés, les conséquences de ces erreurs sont aussi amplifiées par l'échelle et la nature commerciale des projets sur lesquels ces programmeurs travaillent généralement.

Ces exemples ont tous été testés avec Visual Studio 2005 Express, au niveau d'avertissement par défaut. Vos résultats peuvent différer avec d'autres compilateurs. Je vous recommande vivement d'utiliser le niveau d'avertissement le plus élevé possible ! Certains points qui ne sont pas signalés comme problèmes potentiels au niveau par défaut peuvent être détectés au niveau le plus élevé !

1) Variables non initialisées

Les variables non initialisées sont l'une des erreurs les plus insidieuses qui se commettent en C++. La mémoire allouée à une variable en C++ n'est ni effacée ni mise à zéro lors de l'allocation. Par conséquent, une variable non initialisée possède une valeur quelconque, mais il est impossible de prévoir cette valeur. De plus, la valeur de la variable peut changer à chaque exécution du programme. Cela peut provoquer des problèmes intermittents, particulièrement difficiles à localiser. Considérez l'extrait suivant :


if (bValue)
    // fait A
else
    // fait B

Si bValue n'est pas initialisée, elle peut valoir true ou false, et l'une ou l'autre branche peut être exécutée.

Dans quelques cas simples, le compilateur peut vous signaler une variable non initialisée. Le code suivant provoque un avertissement du compilateur avec la plupart des compilateurs :


int foo()
{
int nX;
return nX;
}

En revanche, d'autres cas simples ne produisent généralement aucun avertissement :


void increment(int &nValue)
{
    ++nValue;
}

int foo()
{
int nX;
increment(nX);
return nX;
}

Le ci-dessus peut ne pas produire d'avertissement, car le compilateur ne vérifie généralement pas si increment() affecte une valeur à nValue.

Les variables non initialisées sont encore plus fréquentes dans les classes, où la déclaration des membres est généralement séparée de l'implémentation du constructeur :


class Foo
{
private:
    int m_nValue;

public:
    Foo();
    int GetValue() { return m_nValue; }
};

Foo::Foo()
{
    // Oups, on a oublié d'initialiser m_nValue
}

int main()
{
    Foo cFoo;
    if (cFoo.GetValue() > 0)
        // fait quelque chose
    else
        // fait autre chose
}

Notez que m_nValue n'est jamais initialisée. Par conséquent, GetValue() renvoie une valeur quelconque, et l'une ou l'autre branche peut être exécutée.

Les nouveaux programmeurs commettent souvent l'erreur suivante lorsqu'ils déclarent plusieurs variables :


int nValue1, nValue2 = 5;

On suppose ici que 5 est affecté à nValue1 et à nValue2, alors qu'en réalité la valeur 5 n'est affectée qu'à nValue2, et nValue1 reste non initialisée.

Comme les variables non initialisées peuvent prendre n'importe quelle valeur, ce qui peut faire que le programme se comporte différemment à chaque exécution, les problèmes qu'elles causent sont particulièrement difficiles à trouver. Une fois, le programme fonctionne correctement. La fois suivante, il plante. La fois d'après, il produit un résultat faux.

Pour compliquer encore la recherche de variables non initialisées, les variables déclarées lors de l'exécution du programme dans un débogueur sont généralement mises à zéro. Cela signifie que votre programme peut fonctionner correctement à chaque fois dans un débogueur, mais planter de façon intermittente en mode release ! Dans ce cas, une variable non initialisée est souvent à l'origine du problème.

2) Division entière

La plupart des opérateurs binaires en C++ exigent que leurs deux opérandes soient du même type. Si les opérandes sont de types différents, l'un d'eux est promu pour correspondre au type de l'autre.

En C++, l'opérateur de division peut être considéré comme deux opérateurs différents : l'un qui travaille sur des opérandes entiers, et l'autre sur des opérandes à virgule flottante. Si les opérandes sont de type à virgule flottante, l'opérateur de division renvoie une valeur à virgule flottante :


float fX = 7;
float fY = 2;
float fValue = fX / fY; // fValue = 3.5

Si les opérandes sont de type entier, l'opérateur de division supprime la partie fractionnaire et renvoie une valeur entière :


int nX = 7;
int nY = 2;
int nValue = nX / nY; // nValue = 3

Si l'un des opérandes est un entier et l'autre une valeur à virgule flottante, l'entier est promu vers un type à virgule flottante :


float fX = 7.0;
int nY = 2;
float fValue = fX / nY;

// nY est promu en float, une division à virgule flottante est utilisée
// fValue = 3.5

Beaucoup de nouveaux programmeurs essaient de faire ceci :


int nX = 7;
int nY = 2;
float fValue = nX / nY;  // fValue = 3 (et non 3.5 !)

L'hypothèse sous-jacente ici est que nX / nY effectuera une division à virgule flottante puisque le résultat est affecté à une variable à virgule flottante. Ce n'est pas le cas. nX / nY est évalué en premier, produisant une valeur entière, qui est ensuite promue en float et affectée à fValue. Mais, à ce stade, la partie fractionnaire est déjà perdue.

Pour forcer une division à virgule flottante entre deux entiers, l'un des deux doit être converti explicitement en valeur à virgule flottante :


int nX = 7;
int nY = 2;
float fValue = static_cast<float>(nX) / nY; // fValue = 3.5

Comme nX est explicitement converti en float, nY sera implicitement promu en float, ce qui fera effectuer une division à virgule flottante à l'opérateur de division, donnant la valeur 3.5.

Il est souvent difficile de voir d'un coup d'œil si une opération de division est entière ou à virgule flottante :


z = x / y; // s'agit-il d'une division entière ou à virgule flottante ?

Cependant, l'utilisation de la notation hongroise peut lever l'ambiguïté et aider à prévenir les erreurs :


int nZ = nX / nY; // division entière
double dZ = dX / dY; // division à virgule flottante

Autre point intéressant concernant la division entière : le C++ ne définit pas comment tronquer le résultat lorsqu'un opérande est négatif. Par conséquent, le compilateur est libre de tronquer vers le haut ou vers le bas ! Par exemple, -5 / 2 peut valoir -3 ou -2, selon que le compilateur arrondit vers le bas ou vers 0. La plupart des compilateurs modernes arrondissent vers 0.

3) = contre ==

Celle-ci est un classique. De nombreux débutants en C++ confondent l'opérateur d'affectation (=) avec l'opérateur d'égalité (==). Mais même les programmeurs qui connaissent la différence peuvent faire une faute de frappe aux conséquences inattendues :


// si nValue vaut 0, renvoie 1, sinon renvoie nValue
int foo(int nValue)
{
    if (nValue = 0) // FAUTE DE FRAPPE !
        return 1;
    else
        return nValue;
}

int main()
{
    std::cout << foo(0) << std::endl;
    std::cout << foo(1) << std::endl;
    std::cout << foo(2) << std::endl;

    return 0;
}

La fonction foo() est censée renvoyer 1 si nValue vaut 0, sinon renvoyer nValue. Mais, en utilisant par inadvertance l'opérateur d'affectation au lieu de l'opérateur d'égalité, le programme produit un résultat inattendu :


0
0
0

Lorsque l'instruction if de foo() est évaluée, nValue reçoit la valeur 0. if (nValue = 0) s'évalue de la même façon que nValue = 0; if (nValue). Par conséquent, la condition du if est fausse, ce qui fait exécuter le else qui renvoie nValue, qui vient d'être affectée à 0 !

Ainsi, cette fonction renvoie toujours 0.

Si vous compilez avec un compilateur moderne au niveau d'avertissement le plus élevé, celui-ci émettra un avertissement lorsqu'une affectation est utilisée dans une instruction conditionnelle, ou une note indiquant que l'instruction ne fait rien lorsqu'un test d'égalité est utilisé à la place d'une affectation en dehors d'une condition. C'est l'un des rares problèmes qui sont essentiellement évitables, à condition d'utiliser les niveaux d'avertissement élevés.

4) Mélange de valeurs signées et non signées

Comme indiqué dans la section sur la division entière, la plupart des opérateurs binaires en C++ exigent que leurs deux opérandes soient du même type. Si les opérandes sont de types différents, l'un d'eux est promu pour correspondre au type de l'autre.

Cela peut conduire à des résultats très inattendus lorsqu'on mélange des valeurs signées et non signées ! Considérez le cas suivant :


cout << 10 - 15u; // 15u est non signé

On s'attendrait à obtenir -5. Cependant, comme 10 est un entier signé et 15 un entier non signé, les règles de promotion de type entrent en jeu. La hiérarchie utilisée pour la promotion de type en C++ est la suivante :

long double (le plus élevé)
double
float
unsigned long int
long int
unsigned int
int (le plus bas)

Comme l'opérande int est considéré comme inférieur à l'opérande unsigned int, l'int est promu en unsigned int. Heureusement, 10 est déjà un nombre positif, donc la promotion ne change pas la façon dont notre nombre est interprété.

Nous avons donc, en pratique :


cout << 10u - 15u

C'est ici que la partie délicate intervient. Comme les deux opérandes sont des entiers non signés, le résultat de l'opération est aussi un entier non signé ! 10u - 15u vaut -5u. Mais une variable non signée ne peut pas contenir de nombre négatif, et donc le -5 est interprété comme 4 294 967 291 (en supposant des entiers sur 32 bits).

Par conséquent, le programme suivant :


cout << 10 - 15u; // 15u est non signé

affiche 4 294 967 291, et non -5.

Cette situation peut se présenter sous des formes plus obscures :


int nX;
unsigned int nY;

if (nX - nY < 0)
    // fait quelque chose

En raison de la conversion de type, cette instruction if sera toujours évaluée à faux, ce qui n'est évidemment pas ce que le programmeur veut !

5) delete contre delete[]

De nombreux programmeurs C++ oublient qu'il existe en réalité deux formes des opérateurs new et delete : une version scalaire et une version tableau.

L'opérateur new sert à allouer sur le tas des données scalaires (non tableau). Si l'objet alloué est de type classe, le constructeur de l'objet est appelé.


Foo *pScalar = new Foo;

L'opérateur delete sert à détruire un objet scalaire alloué avec l'opérateur new. Si l'objet détruit est de type classe, le destructeur de l'objet est appelé.


delete pScalar;

Considérez maintenant l'extrait suivant :


Foo *pArray = new Foo[10];

Cet extrait alloue un tableau de 10 Foo. Comme l'indice [10] est placé après le spécificateur de type, de nombreux programmeurs C++ ne réalisent pas que c'est operator new[] qui est appelé pour l'allocation du tableau, et non operator new. operator new[] garantit que le constructeur est appelé pour chaque objet construit.

Inversement, pour libérer un tableau, il faut utiliser l'opérateur delete[] :


delete[] pArray;

Cela garantit que le destructeur de chaque objet du tableau est appelé.

Si l'opérateur delete est utilisé sur un tableau, seul le premier objet sera détruit, et une corruption du tas peut en résulter !

6) Effets de bord dans les expressions composées ou les appels de fonctions

Un effet de bord est un résultat d'un opérateur, d'une expression, d'une instruction ou d'une fonction qui persiste même après que l'opérateur, l'expression, l'instruction ou la fonction a fini d'être évalué.

Les effets de bord peuvent être utiles :


x = 5;

L'opérateur d'affectation a pour effet de bord de modifier définitivement la valeur de x. Les autres opérateurs C++ aux effets de bord utiles incluent *=, /=, %=, +=, -=, <<=, >>=, &=, |=, ^=, ainsi que les fameux opérateurs ++ et --.

Cependant, il existe plusieurs endroits en C++ où l'ordre des opérations n'est pas défini, ce qui peut entraîner un comportement incohérent. Par exemple :


int multiply(int x, int y)
{
    return x * y;
}

int main()
{
    int x = 5;
    std::cout << multiply(x, ++x);
}

Comme l'ordre d'évaluation des paramètres de multiply() n'est pas défini, ce programme peut afficher 30 ou 36, selon que x ou ++x est évalué en premier.

Un exemple un peu plus étrange, impliquant des opérateurs :


int foo(int x)
{
return x;
}

int main()
{
    int x = 5;
    std::cout << foo(x) * foo(++x);
}

Comme l'ordre d'évaluation des opérandes des opérateurs C++ n'est pas défini (pour la plupart des opérateurs, il existe quelques exceptions), ce programme peut lui aussi afficher 30 ou 36, selon que l'opérande de gauche ou celui de droite est évalué en premier.

Considérez aussi l'expression composée suivante :


if (x == 1 && ++y == 2)
    // fait quelque chose

L'intention du programmeur est probablement de dire « si x vaut 1 et si la valeur de y après incrémentation vaut 2, alors fais quelque chose ». Cependant, si x ne vaut pas 1, le C++ utilise l'évaluation court-circuitée, ce qui signifie que ++y n'est jamais évalué ! Ainsi, y n'est incrémenté que si x vaut 1, ce qui n'est probablement pas ce que le programmeur voulait !

Une bonne règle empirique consiste à placer tout opérateur produisant un effet de bord dans sa propre instruction.

7) Instructions switch sans break

Une autre erreur classique que font les nouveaux programmeurs est d'oublier d'utiliser break pour terminer un bloc switch :


switch (nValue)
{
    case 1: eColor = Color::BLUE;
    case 2: eColor = Color::PURPLE;
    case 3: eColor = Color::GREEN;
    default: eColor = Color::RED;
}

Lorsque l'expression du switch vaut la même valeur que l'expression d'une étiquette case, l'exécution commence à l'instruction case correspondante. L'exécution se poursuit ensuite jusqu'à ce que la fin du bloc switch soit atteinte, ou qu'une instruction return, goto ou break soit exécutée. Les autres étiquettes sont ignorées !

Voyons ce qui se passe si nValue vaut 1 dans le programme ci-dessus. Le case 1 correspond, donc eColor reçoit Color::BLUE. L'évaluation passe à l'instruction suivante, qui affecte Color::PURPLE à eColor. L'instruction suivante l'affecte à Color::GREEN. Et finalement, elle reçoit Color::RED.

En fait, cet extrait finit par affecter Color::RED à eColor quelle que soit la valeur de nValue !

La bonne façon d'écrire le programme ci-dessus est :


switch (nValue)
{
    case 1: eColor = Color::BLUE;  break;
    case 2: eColor = Color::PURPLE;  break;
    case 3: eColor = Color::GREEN;  break;
    default: eColor = Color::RED;  break;
}

Le break met fin à l'instruction case, ce qui permet à eColor de conserver la valeur voulue par le programmeur.

Bien que ce soit une logique switch/case très basique, il est très facile d'oublier un break et de se retrouver avec un passage involontaire d'un cas à l'autre (fall-through).

8) Appeler des fonctions virtuelles dans les constructeurs

Considérez le programme suivant :


class Base
{
private:
    int m_nID;
public:
    Base()
    {
        m_nID = ClassID();
    }

    // ClassID renvoie un numéro d'identifiant propre à la classe
    virtual int ClassID() { return 1; }

    int GetID() { return m_nID; }
};

class Derived: public Base
{
public:
    Derived()
    {
    }

    virtual int ClassID() { return 2; }
};

int main()
{
    Derived cDerived;
    cout << cDerived.GetID(); // affiche 1, et non 2 !
    return 0;
}

Dans ce programme, le programmeur a appelé une fonction virtuelle dans le constructeur d'une classe de base, en s'attendant à ce qu'elle se résolve vers Derived::ClassID(). Ce n'est pas le cas : le programme affiche 1 au lieu de 2.

Lorsqu'une classe dérivée d'une classe de base est instanciée, l'objet de la classe de base est construit avant l'objet de la classe dérivée. Cela se fait parce que les membres de la classe dérivée peuvent dépendre de membres de la classe de base déjà initialisés. Par conséquent, lorsque le constructeur de l'objet de base est exécuté, il n'existe pas encore d'objet dérivé ! Il n'a pas encore été créé. Ainsi, tout appel à une fonction virtuelle ne peut se résoudre qu'au niveau de la classe de base, et non de la classe dérivée.

Dans cet exemple, lorsque la partie Base de cDerived est en cours de construction, la partie Derived n'existe pas encore. Ainsi, l'appel à ClassID() se résout en Base::ClassID() (et non en Derived::ClassID()), ce qui affecte 1 à m_nID.

Une fois la partie Derived de cDerived construite, tout appel à ClassID() sur cet objet se résoudra en Derived::ClassID(), comme prévu.

Notez que certains autres langages (comme C# et Java) résolvent les appels de fonctions virtuelles vers la classe la plus dérivée, même si la classe dérivée n'a pas encore été initialisée ! Le C++ diffère sur ce point, et il le fait pour la sécurité du programmeur. Cela ne signifie pas qu'une approche soit nécessairement meilleure que l'autre, mais seulement que différents langages peuvent avoir des comportements différents.

Conclusion

Comme il s'agit du premier article de cette série, j'ai jugé approprié de commencer par certains problèmes plus élémentaires que rencontreront les nouveaux programmeurs. Les articles suivants de cette série aborderont des erreurs de programmation de nature de plus en plus complexe.

Quel que soit le niveau d'expérience d'un programmeur, les erreurs arrivent, qu'elles viennent d'un manque de connaissances, d'une faute de frappe ou d'une simple inattention. Être conscient des problèmes qui sont les plus susceptibles de causer des ennuis peut aider à réduire la probabilité qu'ils en causent effectivement. Il n'existe pas de substitut à l'expérience et aux connaissances, mais de bons tests unitaires peuvent aider à en attraper beaucoup avant qu'ils ne soient enfouis sous des couches d'autre code !
