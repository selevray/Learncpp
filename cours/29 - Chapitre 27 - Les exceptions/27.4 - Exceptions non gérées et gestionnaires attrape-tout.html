27.4 — Exceptions non gérées et gestionnaires attrape-tout

À ce stade, vous devriez avoir une idée raisonnable du fonctionnement des exceptions. Dans cette leçon, nous verrons quelques cas particuliers intéressants.

Exceptions non gérées

Lorsqu'une fonction lève une exception qu'elle ne gère pas elle-même, elle suppose qu'une fonction située plus bas dans la pile d'appels la gérera. Dans l'exemple suivant, mySqrt() suppose que quelqu'un traitera l'exception qu'elle lève. Mais que se passe-t-il si personne ne le fait ?

Voici à nouveau notre programme de calcul de racine carrée, sans le bloc try dans main() :

#include <iostream>
#include <cmath> // pour la fonction sqrt()

// Une fonction de calcul de racine carrée modulaire
double mySqrt(double x)
{
    // Si l'utilisateur a saisi un nombre négatif, il s'agit d'une condition d'erreur
    if (x < 0.0)
        throw "Can not take sqrt of negative number"; // lève une exception de type const char*

    return std::sqrt(x);
}

int main()
{
    std::cout << "Enter a number: ";
    double x;
    std::cin >> x;

    // Regardez, pas de gestionnaire d'exception !
    std::cout << "The sqrt of " << x << " is " << mySqrt(x) << '\n';

    return 0;
}

Supposons maintenant que l'utilisateur saisisse -4 : mySqrt(-4) lève alors une exception. La fonction mySqrt() ne la gère pas, le programme cherche donc si une fonction située plus bas dans la pile d'appels la gérera. main() n'a pas non plus de gestionnaire pour cette exception, aucun gestionnaire ne peut donc être trouvé.

Lorsqu'aucun gestionnaire d'exception ne peut être trouvé pour une fonction, std::terminate() est appelée et l'application se termine. Dans ce cas, la pile d'appels peut ou non être déroulée ! Si la pile n'est pas déroulée, les variables locales ne sont pas détruites, et le nettoyage normalement effectué lors de leur destruction n'a pas lieu !

Attention

La pile d'appels peut ou non être déroulée si une exception n'est pas gérée.

Si la pile n'est pas déroulée, les variables locales ne sont pas détruites, ce qui peut poser problème si ces variables ont des destructeurs non triviaux.

En passant…

Bien qu'il puisse sembler étrange de ne pas dérouler la pile dans ce cas, il existe une bonne raison de ne pas le faire. Une exception non gérée est en général quelque chose qu'on veut éviter à tout prix. Si la pile était déroulée, toutes les informations de débogage sur l'état de la pile ayant conduit au lancement de l'exception non gérée seraient perdues ! En ne déroulant pas la pile, nous conservons ces informations, ce qui facilite la compréhension de la manière dont l'exception non gérée a été levée, et sa correction.

Lorsqu'une exception n'est pas gérée, le système d'exploitation vous signale généralement qu'une erreur d'exception non gérée s'est produite. La manière dont il le fait dépend du système d'exploitation : il peut afficher un message d'erreur, ouvrir une boîte de dialogue, ou simplement planter. Certains systèmes sont moins élégants que d'autres. En général, c'est une situation qu'il faut absolument éviter !

Gestionnaires attrape-tout

Nous nous retrouvons maintenant face à un dilemme :

  • Les fonctions peuvent potentiellement lever des exceptions de n'importe quel type (y compris des types définis par le programme), ce qui signifie qu'il existe un nombre infini de types d'exceptions possibles à attraper.
  • Si une exception n'est pas attrapée, votre programme se termine immédiatement (et la pile peut ne pas être déroulée, si bien que votre programme ne nettoie peut-être même pas correctement ce qu'il a fait).
  • Ajouter un gestionnaire explicite pour chaque type possible est fastidieux, en particulier pour ceux qui ne devraient être atteints que dans des cas exceptionnels !

Heureusement, C++ nous fournit aussi un mécanisme pour attraper tous les types d'exceptions. Il s'agit du gestionnaire attrape-tout (catch-all handler). Un gestionnaire attrape-tout fonctionne comme un bloc catch ordinaire, sauf qu'au lieu d'utiliser un type précis, il utilise l'opérateur d'ellipse (…) comme type à attraper. C'est pourquoi le gestionnaire attrape-tout est parfois aussi appelé « gestionnaire à ellipse ».

Si vous vous rappelez la leçon 20.5 -- Ellipsis (and why to avoid them), les ellipses servaient auparavant à passer à une fonction des arguments de n'importe quel type. Dans ce contexte, elles représentent des exceptions de n'importe quel type de données. Voici un exemple simple :

#include <iostream>

int main()
{
    try
    {
        throw 5; // lève une exception de type int
    }
    catch (double x)
    {
        std::cout << "We caught an exception of type double: " << x << '\n';
    }
    catch (...) // gestionnaire attrape-tout
    {
        std::cout << "We caught an exception of an undetermined type\n";
    }
}

Comme il n'existe pas de gestionnaire spécifique pour le type int, c'est le gestionnaire attrape-tout qui intercepte cette exception. Cet exemple produit le résultat suivant :


We caught an exception of an undetermined type

Le gestionnaire attrape-tout doit être placé en dernier dans la chaîne de blocs catch. Cela garantit que les exceptions peuvent être interceptées par les gestionnaires spécifiques à certains types de données, si ces gestionnaires existent.

Souvent, le bloc du gestionnaire attrape-tout est laissé vide :

catch(...) {} // ignore toute exception imprévue

Cela intercepte toute exception imprévue, garantit que le déroulement de la pile a lieu jusqu'à ce point et empêche le programme de se terminer, mais ne effectue aucun traitement d'erreur particulier.

Utiliser le gestionnaire attrape-tout pour englober main()

Une utilisation possible du gestionnaire attrape-tout consiste à englober le contenu de main() :

#include <iostream>

struct GameSession
{
    // Données de la session de jeu ici
};

void runGame(GameSession&)
{
    throw 1;
}

void saveGame(GameSession&)
{
    // Sauvegarde la partie de l'utilisateur ici
}

int main()
{
    GameSession session{};

    try
    {
        runGame(session);
    }
    catch(...)
    {
        std::cerr << "Abnormal termination\n";
    }

    saveGame(session); // sauvegarde la partie de l'utilisateur (même si le gestionnaire attrape-tout a été atteint)

    return 0;
}

Dans ce cas, si runGame() ou l'une des fonctions qu'elle appelle lève une exception non gérée, celle-ci sera interceptée par ce gestionnaire attrape-tout. La pile sera déroulée de manière ordonnée (ce qui garantit la destruction des variables locales). Cela empêche aussi le programme de se terminer immédiatement, ce qui nous laisse la possibilité d'afficher un message d'erreur de notre choix et de sauvegarder l'état de l'utilisateur avant de quitter.

Astuce

Si votre programme utilise des exceptions, envisagez d'utiliser un gestionnaire attrape-tout dans main, afin de garantir un comportement ordonné en cas d'exception non gérée.

Si une exception est interceptée par le gestionnaire attrape-tout, considérez que le programme se trouve désormais dans un état indéterminé, effectuez immédiatement un nettoyage, puis terminez le programme.

Déboguer les exceptions non gérées

Les exceptions non gérées indiquent que quelque chose d'inattendu s'est produit, et nous voulons probablement comprendre pourquoi une exception non gérée a été levée en premier lieu. De nombreux débogueurs s'arrêtent (ou peuvent être configurés pour s'arrêter) sur les exceptions non gérées, ce qui nous permet d'examiner la pile au point où l'exception non gérée a été levée. Cependant, si nous disposons d'un gestionnaire attrape-tout, alors toutes les exceptions sont gérées et, comme la pile est déroulée, nous perdons des informations de diagnostic utiles.

Par conséquent, dans les versions de débogage, il peut être utile de désactiver le gestionnaire attrape-tout. Nous pouvons le faire à l'aide de directives de compilation conditionnelle.

Voici une façon de procéder :

#include <iostream>

struct GameSession
{
    // Données de la session de jeu ici
};

void runGame(GameSession&)
{
    throw 1;
}

void saveGame(GameSession&)
{
    // Sauvegarde la partie de l'utilisateur ici
}

class DummyException // une classe factice qui ne peut pas être instanciée
{
    DummyException() = delete;
}; 

int main()
{
    GameSession session {}; 

    try
    {
        runGame(session);
    }
#ifndef NDEBUG // si nous sommes en mode release
    catch(...) // on compile le gestionnaire attrape-tout
    {
        std::cerr << "Abnormal termination\n";
    }
#else // en mode débogage, on compile un catch qui ne sera jamais atteint (pour des raisons syntaxiques)
    catch(DummyException)
    {
    }
#endif

    saveGame(session); // sauvegarde la partie de l'utilisateur (même si le gestionnaire attrape-tout a été atteint)

    return 0;
}

Sur le plan syntaxique, un bloc try exige au moins un bloc catch associé. Ainsi, si le gestionnaire attrape-tout est exclu par compilation conditionnelle, nous devons soit exclure aussi le bloc try par compilation conditionnelle, soit inclure un autre bloc catch. Il est plus propre de choisir la seconde solution.

Dans ce but, nous créons la classe DummyException, qui ne peut pas être instanciée car elle possède un constructeur par défaut supprimé (deleted) et aucun autre constructeur. Lorsque NDEBUG est défini, nous compilons un gestionnaire capable d'intercepter une exception de type DummyException. Comme il est impossible de créer un objet DummyException, ce gestionnaire ne interceptera jamais rien. Par conséquent, les exceptions qui atteignent ce point ne seront pas gérées.
