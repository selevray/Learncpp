27.8 — Dangers et inconvénients des exceptions

Comme presque tout ce qui présente des avantages, les exceptions ont aussi des inconvénients potentiels. Cet article ne se veut pas exhaustif. Il signale simplement les principaux problèmes à prendre en compte lorsque l'on utilise les exceptions, ou que l'on hésite à les utiliser.

Libérer les ressources

L'un des plus gros problèmes rencontrés par les programmeurs débutants avec les exceptions concerne la libération des ressources lorsqu'une exception survient. Considérez l'exemple suivant :

#include <iostream>

try
{
    openFile(filename);
    writeFile(filename, data);
    closeFile(filename);
}
catch (const FileException& exception)
{
    std::cerr << "Failed to write to file: " << exception.what() << '\n';
}

Que se passe-t-il si WriteFile() échoue et lève une FileException ? À ce stade, nous avons déjà ouvert le fichier, et le flux d'exécution saute maintenant au gestionnaire de FileException, qui affiche une erreur et quitte. Notez que le fichier n'a jamais été fermé ! Cet exemple devrait être réécrit ainsi :

#include <iostream>

try
{
    openFile(filename);
    writeFile(filename, data);
}
catch (const FileException& exception)
{
    std::cerr << "Failed to write to file: " << exception.what() << '\n';
}

// Make sure file is closed
closeFile(filename);

Ce type d'erreur apparaît souvent sous une autre forme lorsque l'on manipule de la mémoire allouée dynamiquement :

#include <iostream>

try
{
    auto* john { new Person{ "John", 18, PERSON_MALE } };
    processPerson(john);
    delete john;
}
catch (const PersonException& exception)
{
    std::cerr << "Failed to process person: " << exception.what() << '\n';
}

Si processPerson() lève une exception, le flux d'exécution saute au gestionnaire catch. En conséquence, john n'est jamais désalloué ! Cet exemple est un peu plus délicat que le précédent : comme john est local au bloc try, il sort de portée lorsque ce bloc se termine. Le gestionnaire d'exception ne peut donc pas accéder à john du tout (il a déjà été détruit), et il n'a aucun moyen de désallouer la mémoire.

Il existe cependant deux façons relativement simples de corriger cela. La première consiste à déclarer john en dehors du bloc try, afin qu'il ne sorte pas de portée à la fin de ce bloc :

#include <iostream>

Person* john{ nullptr };

try
{
    john = new Person("John", 18, PERSON_MALE);
    processPerson(john);
}
catch (const PersonException& exception)
{
    std::cerr << "Failed to process person: " << exception.what() << '\n';
}

delete john;

Comme john est déclaré en dehors du bloc try, il est accessible à la fois dans le bloc try et dans les gestionnaires catch. Le gestionnaire peut donc effectuer correctement le nettoyage.

La seconde façon consiste à utiliser une variable locale d'une classe capable de se nettoyer elle-même lorsqu'elle sort de portée (souvent appelée « pointeur intelligent » (smart pointer)). La bibliothèque standard fournit une classe appelée std::unique_ptr qui peut servir à cet usage. std::unique_ptr est une classe modèle (template) qui contient un pointeur et le désalloue lorsqu'il sort de portée.

#include <iostream>
#include <memory> // for std::unique_ptr

try
{
    auto* john { new Person("John", 18, PERSON_MALE) };
    std::unique_ptr<Person> upJohn { john }; // upJohn now owns john

    ProcessPerson(john);

    // when upJohn goes out of scope, it will delete john
}
catch (const PersonException& exception)
{
    std::cerr << "Failed to process person: " << exception.what() << '\n';
}

La meilleure option (chaque fois que c'est possible) est de privilégier les objets alloués sur la pile qui implémentent le RAII (allocation automatique des ressources à la construction, libération de la ressource à la destruction). Ainsi, lorsque l'objet qui gère la ressource sort de portée, quelle qu'en soit la raison, il libère automatiquement la ressource comme il convient, et nous n'avons pas à nous soucier de ces questions !

Exceptions et destructeurs

Contrairement aux constructeurs, pour lesquels lever une exception peut être un moyen utile d'indiquer que la création de l'objet a échoué, les exceptions ne doivent jamais être levées dans les destructeurs.

Le problème survient lorsqu'une exception est levée hors d'un destructeur pendant le processus de déroulement de la pile (stack unwinding). Dans ce cas, le compilateur se retrouve dans une situation où il ne sait pas s'il doit poursuivre le déroulement de la pile ou traiter la nouvelle exception. Le résultat final est que votre programme se termine immédiatement.

Par conséquent, la meilleure solution consiste simplement à s'abstenir d'utiliser les exceptions dans les destructeurs. Écrivez plutôt un message dans un fichier journal.

Règle

Si une exception est levée hors d'un destructeur pendant le déroulement de la pile, le programme est arrêté.

Problèmes de performance

Les exceptions ont un petit coût en performance. Elles augmentent la taille de votre exécutable et peuvent aussi le rendre plus lent, à cause des vérifications supplémentaires à effectuer. Cependant, la principale pénalité de performance liée aux exceptions survient lorsqu'une exception est effectivement levée. Dans ce cas, la pile doit être déroulée et un gestionnaire d'exception approprié doit être trouvé, ce qui est une opération relativement coûteuse.

Notons que certaines architectures d'ordinateurs modernes prennent en charge un modèle d'exceptions appelé exceptions à coût nul (zero-cost exceptions). Lorsqu'elles sont prises en charge, les exceptions à coût nul n'ajoutent aucun coût à l'exécution dans le cas sans erreur (le cas qui nous intéresse le plus pour les performances). En revanche, elles entraînent une pénalité encore plus importante lorsqu'une exception est effectivement traitée.

Alors, quand dois-je utiliser les exceptions ?

La gestion des exceptions est particulièrement adaptée lorsque toutes les conditions suivantes sont réunies :

  • L'erreur à traiter n'est susceptible de survenir que rarement.
  • L'erreur est grave, et l'exécution ne pourrait pas se poursuivre autrement.
  • L'erreur ne peut pas être traitée à l'endroit où elle se produit.
  • Il n'existe pas de bonne alternative pour renvoyer un code d'erreur à l'appelant.

Prenons comme exemple le cas où vous avez écrit une fonction qui attend de l'utilisateur qu'il lui transmette le nom d'un fichier sur le disque. Votre fonction ouvre ce fichier, lit des données, ferme le fichier et renvoie un résultat à l'appelant. Supposons maintenant que l'utilisateur transmette le nom d'un fichier qui n'existe pas, ou une chaîne nulle. Est-ce un bon candidat pour une exception ?

Dans ce cas, les deux premières conditions ci-dessus sont trivialement remplies : cela ne va pas arriver souvent, et votre fonction ne peut pas calculer de résultat sans données à traiter. La fonction ne peut pas non plus gérer l'erreur : ce n'est pas à elle de demander à nouveau à l'utilisateur un nouveau nom de fichier, et cela pourrait même ne pas être approprié selon la conception de votre programme. La quatrième condition est la clé : existe-t-il une bonne alternative pour renvoyer un code d'erreur à l'appelant ? Cela dépend des détails de votre programme. Si c'est le cas (par exemple, vous pouvez renvoyer un pointeur nul ou un code d'état indiquant l'échec), c'est probablement le meilleur choix. Sinon, une exception serait raisonnable.
