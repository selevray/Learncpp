27.10 — std::move_if_noexcept

(Remerciements au lecteur Koe, qui a fourni la première ébauche de cette leçon !)

Dans la leçon 22.4 -- std::move, nous avons étudié std::move, qui convertit son argument lvalue en rvalue afin de pouvoir invoquer la sémantique de déplacement. Dans la leçon 27.9 -- Spécifications d'exception et noexcept, nous avons étudié le spécificateur d'exception noexcept et l'opérateur noexcept. Cette leçon s'appuie sur ces deux notions.

Nous avons également vu la garantie forte d'exception (strong exception guarantee), qui assure que, si une fonction est interrompue par une exception, aucune mémoire n'est perdue et l'état du programme n'est pas modifié. En particulier, tous les constructeurs doivent respecter cette garantie, afin que le reste du programme ne soit pas laissé dans un état altéré si la construction d'un objet échoue.

Le problème des constructeurs de déplacement face aux exceptions

Considérons le cas où l'on copie un objet et où la copie échoue pour une raison quelconque (par exemple, si la machine manque de mémoire). Dans ce cas, l'objet copié n'est en rien endommagé, car l'objet source n'a pas besoin d'être modifié pour créer une copie. On peut écarter la copie échouée et poursuivre. La garantie forte d'exception est respectée.

Considérons maintenant le cas où l'on déplace un objet à la place. Une opération de déplacement transfère la propriété d'une ressource donnée de l'objet source vers l'objet destination. Si l'opération de déplacement est interrompue par une exception après le transfert de propriété, l'objet source reste dans un état modifié. Ce n'est pas un problème si l'objet source est un objet temporaire, destiné de toute façon à être détruit après le déplacement. Mais pour un objet non temporaire, nous avons alors endommagé l'objet source. Pour respecter la garantie forte d'exception, il faudrait restituer la ressource à l'objet source, mais si le déplacement a échoué une première fois, rien ne garantit que ce déplacement inverse réussira.

Comment garantir la garantie forte d'exception pour les constructeurs de déplacement ? Il est assez simple d'éviter de lever une exception dans le corps d'un constructeur de déplacement, mais un constructeur de déplacement peut invoquer d'autres constructeurs potentiellement lanceurs d'exceptions (potentially throwing). Prenons par exemple le constructeur de déplacement de std::pair, qui doit tenter de déplacer chaque sous-objet de la paire source dans le nouvel objet paire.

// Exemple de définition du constructeur de déplacement de std::pair
// Prend une paire « old » et construit par déplacement les sous-objets « first » et « second » de la nouvelle paire à partir de ceux de « old »
template <typename T1, typename T2>
pair<T1,T2>::pair(pair&& old)
  : first(std::move(old.first)),
    second(std::move(old.second))
{}

Utilisons maintenant deux classes, MoveClass et CopyClass, que nous allons associer dans une pair pour illustrer le problème de la garantie forte d'exception avec les constructeurs de déplacement :

#include <iostream>
#include <utility> // Pour std::pair, std::make_pair, std::move, std::move_if_noexcept
#include <stdexcept> // std::runtime_error

class MoveClass
{
private:
  int* m_resource{};

public:
  MoveClass() = default;

  MoveClass(int resource)
    : m_resource{ new int{ resource } }
  {}

  // Constructeur de copie
  MoveClass(const MoveClass& that)
  {
    // copie profonde
    if (that.m_resource != nullptr)
    {
      m_resource = new int{ *that.m_resource };
    }
  }

  // Constructeur de déplacement
  MoveClass(MoveClass&& that) noexcept
    : m_resource{ that.m_resource }
  {
    that.m_resource = nullptr;
  }

  ~MoveClass()
  {
    std::cout << "destroying " << *this << '\n';

    delete m_resource;
  }

  friend std::ostream& operator<<(std::ostream& out, const MoveClass& moveClass)
  {
    out << "MoveClass(";

    if (moveClass.m_resource == nullptr)
    {
      out << "empty";
    }
    else
    {
      out << *moveClass.m_resource;
    }

    out << ')';

    return out;
  }
};


class CopyClass
{
public:
  bool m_throw{};

  CopyClass() = default;

  // Le constructeur de copie lève une exception lorsqu'il copie
  // un objet CopyClass dont m_throw vaut « true »
  CopyClass(const CopyClass& that)
    : m_throw{ that.m_throw }
  {
    if (m_throw)
    {
      throw std::runtime_error{ "abort!" };
    }
  }
};

int main()
{
  // On peut créer une std::pair sans aucun problème :
  std::pair my_pair{ MoveClass{ 13 }, CopyClass{} };

  std::cout << "my_pair.first: " << my_pair.first << '\n';

  // Mais le problème survient lorsque nous essayons de déplacer cette paire dans une autre paire.
  try
  {
    my_pair.second.m_throw = true; // Pour déclencher l'exception du constructeur de copie

    // La ligne suivante lève une exception
    std::pair moved_pair{ std::move(my_pair) }; // Nous commenterons cette ligne plus loin
    // std::pair moved_pair{ std::move_if_noexcept(my_pair) }; // Nous la décommenterons plus tard

    std::cout << "moved pair exists\n"; // Ne s'affiche jamais
  }
  catch (const std::exception& ex)
  {
      std::cerr << "Error found: " << ex.what() << '\n';
  }

  std::cout << "my_pair.first: " << my_pair.first << '\n';

  return 0;
}

Le programme ci-dessus affiche :


destroying MoveClass(empty)
my_pair.first: MoveClass(13)
destroying MoveClass(13)
Error found: abort!
my_pair.first: MoveClass(empty)
destroying MoveClass(empty)

Analysons ce qui s'est passé. La première ligne affichée montre que l'objet temporaire MoveClass utilisé pour initialiser my_pair est détruit dès que l'instruction de création de my_pair a été exécutée. Il est empty car le sous-objet MoveClass de my_pair a été construit par déplacement à partir de lui, comme le montre la ligne suivante, qui indique que my_pair.first contient l'objet MoveClass de valeur 13.

La troisième ligne est plus intéressante. Nous avons créé moved_pair en construisant par copie son sous-objet CopyClass (qui n'a pas de constructeur de déplacement), mais cette construction par copie a levé une exception, puisque nous avions modifié le drapeau booléen. La construction de moved_pair a été interrompue par l'exception, et ses membres déjà construits ont été détruits. Dans ce cas, le membre MoveClass a été détruit, ce qui affiche destroying MoveClass(13) variable. Ensuite, nous voyons le message Error found: abort! affiché par main().

Lorsque nous essayons d'afficher de nouveau my_pair.first, le membre MoveClass apparaît vide. Comme moved_pair a été initialisé avec std::move, le membre MoveClass (qui possède un constructeur de déplacement) a été construit par déplacement, et my_pair.first a été vidé.

Enfin, my_pair est détruit à la fin de main().

Pour résumer ces résultats : le constructeur de déplacement de std::pair a utilisé le constructeur de copie potentiellement lanceur de CopyClass. Ce constructeur de copie a levé une exception, ce qui a interrompu la création de moved_pair, et a endommagé de façon permanente my_pair.first. La garantie forte d'exception n'a pas été respectée.

std::move_if_noexcept à la rescousse

Notons que le problème ci-dessus aurait pu être évité si std::pair avait tenté une copie au lieu d'un déplacement. Dans ce cas, la construction de moved_pair aurait échoué, mais my_pair n'aurait pas été altéré.

Mais copier au lieu de déplacer a un coût en performance que nous ne voulons pas payer pour tous les objets. Idéalement, nous voulons effectuer un déplacement lorsque c'est possible sans risque, et une copie dans le cas contraire.

Heureusement, C++ propose deux mécanismes qui, combinés, permettent précisément cela. Premièrement, comme les fonctions noexcept ne lèvent pas d'exception et ne échouent pas, elles respectent implicitement les critères de la garantie forte d'exception. Ainsi, un constructeur de déplacement noexcept est garanti de réussir.

Deuxièmement, nous pouvons utiliser la fonction de la bibliothèque standard std::move_if_noexcept() pour déterminer s'il faut effectuer un déplacement ou une copie. std::move_if_noexcept est l'équivalent de std::move et s'utilise de la même manière.

Si le compilateur peut déterminer qu'un objet passé en argument à std::move_if_noexcept ne lèvera pas d'exception lors de sa construction par déplacement (ou si l'objet n'est déplaçable que et ne possède pas de constructeur de copie), alors std::move_if_noexcept se comportera exactement comme std::move() (et renverra l'objet converti en rvalue). Sinon, std::move_if_noexcept renverra une référence lvalue ordinaire vers l'objet.

Point clé

std::move_if_noexcept renvoie une rvalue déplaçable si l'objet possède un constructeur de déplacement noexcept, sinon il renvoie une lvalue copiable. Nous pouvons utiliser le spécificateur noexcept conjointement avec std::move_if_noexcept pour n'utiliser la sémantique de déplacement que lorsqu'une garantie forte d'exception existe (et utiliser la sémantique de copie dans le cas contraire).

Modifions le code de l'exemple précédent comme suit :

//std::pair moved_pair{std::move(my_pair)}; // on commente cette ligne maintenant
std::pair moved_pair{std::move_if_noexcept(my_pair)}; // et on décommente celle-ci

Exécutons de nouveau le programme ; il affiche :


destroying MoveClass(empty)
my_pair.first: MoveClass(13)
destroying MoveClass(13)
Error found: abort!
my_pair.first: MoveClass(13)
destroying MoveClass(13)

Comme vous pouvez le constater, après le lancement de l'exception, le sous-objet my_pair.first contient toujours la valeur 13.

Le constructeur de déplacement de std::pair n'est pas noexcept (jusqu'à C++20), donc std::move_if_noexcept renvoie my_pair sous forme de référence lvalue. Cela fait que moved_pair est créée via le constructeur de copie (et non via le constructeur de déplacement). Le constructeur de copie peut lever une exception sans danger, car il ne modifie pas l'objet source.

La bibliothèque standard utilise souvent std::move_if_noexcept pour optimiser les fonctions noexcept. Par exemple, std::vector::resize utilisera la sémantique de déplacement si le type des éléments possède un constructeur de déplacement noexcept, et la sémantique de copie dans le cas contraire. Cela signifie que std::vector fonctionnera généralement plus rapidement avec des objets dotés d'un constructeur de déplacement noexcept.

Attention

Si un type possède à la fois une sémantique de déplacement potentiellement lanceuse d'exceptions et une sémantique de copie supprimée (le constructeur de copie et l'opérateur d'affectation par copie sont indisponibles), alors std::move_if_noexcept renonce à la garantie forte et invoque la sémantique de déplacement. Cette renonciation conditionnelle à la garantie forte est omniprésente dans les classes conteneurs de la bibliothèque standard, puisqu'elles utilisent fréquemment std::move_if_noexcept.
