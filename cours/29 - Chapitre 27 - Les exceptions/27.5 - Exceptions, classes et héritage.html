27.5 — Exceptions, classes et héritage

Exceptions et fonctions membres

Jusqu'à présent dans ce tutoriel, vous n'avez vu les exceptions utilisées que dans des fonctions non membres. Elles sont pourtant tout aussi utiles dans les fonctions membres, et encore davantage dans les surcharges d'opérateurs. Considérons la surcharge de l'opérateur [] suivante, faisant partie d'une classe de tableau d'entiers simple :

int& IntArray::operator[](const int index)
{
    return m_data[index];
}

Cette fonction fonctionne très bien tant que index est un indice valide du tableau, mais elle manque cruellement de vérifications d'erreurs. Nous pourrions ajouter une instruction assert pour nous assurer que l'indice est valide :

int& IntArray::operator[](const int index)
{
    assert (index >= 0 && index < getLength());
    return m_data[index];
}

Désormais, si l'utilisateur passe un indice invalide, le programme provoque une erreur d'assertion. Malheureusement, comme les surcharges d'opérateurs ont des exigences précises quant au nombre et au type de leurs paramètres et de leur valeur de retour, il n'y a aucune souplesse pour renvoyer à l'appelant un code d'erreur ou une valeur booléenne qu'il pourrait traiter. En revanche, comme les exceptions ne modifient pas la signature d'une fonction, elles peuvent être très utiles ici. Voici un exemple :

int& IntArray::operator[](const int index)
{
    if (index < 0 || index >= getLength())
        throw index;

    return m_data[index];
}

Désormais, si l'utilisateur passe un indice invalide, operator[] lance une exception de type int.

Lorsque les constructeurs échouent

Les constructeurs sont un autre domaine des classes où les exceptions peuvent être très utiles. Si un constructeur doit échouer pour une raison quelconque (par exemple, si l'utilisateur a passé une entrée invalide), il suffit de lancer une exception pour indiquer que l'objet n'a pas pu être créé. Dans ce cas, la construction de l'objet est interrompue, et tous les membres de la classe (qui ont déjà été créés et initialisés avant l'exécution du corps du constructeur) sont détruits comme d'habitude.

En revanche, le destructeur de la classe n'est jamais appelé (puisque la construction de l'objet n'a jamais été achevée). Comme le destructeur ne s'exécute jamais, vous ne pouvez pas compter sur lui pour libérer les ressources qui ont déjà été allouées.

Cela soulève la question de ce que nous devons faire si nous avons alloué des ressources dans notre constructeur, puis qu'une exception survient avant la fin de ce constructeur. Comment garantir que les ressources déjà allouées soient correctement libérées ? Une solution consiste à placer le code susceptible d'échouer dans un bloc try, à capturer l'exception dans un bloc catch correspondant pour effectuer le nettoyage nécessaire, puis à relancer l'exception (un sujet que nous aborderons dans la leçon 27.6 -- Relancer des exceptions). Cependant, cela alourdit beaucoup le code, et il est facile de se tromper, en particulier si votre classe alloue plusieurs ressources.

Heureusement, il existe une meilleure méthode. En tirant parti du fait que les membres d'une classe sont détruits même si le constructeur échoue, si vous effectuez les allocations de ressources à l'intérieur des membres de la classe (plutôt que dans le constructeur lui-même), alors ces membres peuvent se nettoyer eux-mêmes lorsqu'ils sont détruits.

Voici un exemple :

#include <iostream>

class Member
{
public:
    Member()
    {
        std::cerr << "Member allocated some resources\n";
    }

    ~Member()
    {
        std::cerr << "Member cleaned up\n";
    }
};

class A
{
private:
    int m_x {};
    Member m_member;

public:
    A(int x) : m_x{x}
    {
        if (x <= 0)
            throw 1;
    }

    ~A()
    {
        std::cerr << "~A\n"; // should not be called
    }
};


int main()
{
    try
    {
        A a{0};
    }
    catch (int)
    {
        std::cerr << "Oops\n";
    }

    return 0;
}

Ce programme affiche :


Member allocated some resources
Member cleaned up
Oops

Dans le programme ci-dessus, lorsque la classe A lance une exception, tous les membres de A sont détruits. Le destructeur de m_member est appelé, ce qui offre l'occasion de libérer les ressources qu'il a allouées.

C'est en partie pour cette raison que la technique RAII (présentée dans la leçon 19.3 -- Destructeurs) est tant recommandée : même dans des circonstances exceptionnelles, les classes qui implémentent RAII sont capables de se nettoyer elles-mêmes.

Cependant, créer une classe personnalisée comme Member pour gérer une allocation de ressource n'est pas efficace. Heureusement, la bibliothèque standard C++ fournit des classes conformes à RAII pour gérer les types de ressources courants, comme les fichiers (std::fstream, présenté dans la leçon 28.6 -- Entrées/sorties de fichiers de base) et la mémoire dynamique (std::unique_ptr et les autres pointeurs intelligents, présentés dans 22.1 -- Introduction aux pointeurs intelligents et à la sémantique de déplacement).

Par exemple, au lieu de ceci :

class Foo
private:
    int* ptr; // Foo will handle allocation/deallocation

Écrivez ceci :

class Foo
private:
    std::unique_ptr<int> ptr; // std::unique_ptr will handle allocation/deallocation

Dans le premier cas, si le constructeur de Foo échoue après que ptr a alloué sa mémoire dynamique, Foo est responsable du nettoyage, ce qui peut s'avérer délicat. Dans le second cas, si le constructeur de Foo échoue après que ptr a alloué sa mémoire dynamique, le destructeur de ptr s'exécute et rend cette mémoire au système. Foo n'a aucun nettoyage explicite à effectuer lorsque la gestion des ressources est déléguée à des membres conformes à RAII !

Classes d'exception

L'un des principaux problèmes de l'utilisation de types de base (comme int) comme types d'exception est qu'ils sont intrinsèquement vagues. Un problème encore plus grave est de déterminer ce que signifie une exception lorsque plusieurs instructions ou appels de fonctions se trouvent dans un bloc try.

// Using the IntArray overloaded operator[] above

try
{
    int* value{ new int{ array[index1] + array[index2]} };
}
catch (int value)
{
    // What are we catching here?
}

Dans cet exemple, si nous capturons une exception de type int, qu'est-ce que cela nous apprend réellement ? L'un des indices de tableau était-il hors limites ? operator+ a-t-il provoqué un dépassement de capacité entière ? operator new a-t-il échoué faute de mémoire ? Dans ce cas, il n'existe tout simplement aucun moyen facile de lever l'ambiguïté. Bien que nous puissions lancer des exceptions de type const char* pour identifier CE qui a mal tourné, cela ne nous permet toujours pas de traiter différemment les exceptions provenant de sources diverses.

Une façon de résoudre ce problème consiste à utiliser des classes d'exception. Une classe d'exception (exception class) est simplement une classe ordinaire, conçue spécifiquement pour être lancée comme exception. Créons une classe d'exception simple à utiliser avec notre classe IntArray :

#include <string>
#include <string_view>

class ArrayException
{
private:
    std::string m_error;

public:
    ArrayException(std::string_view error)
        : m_error{ error }
    {
    }

    const std::string& getError() const { return m_error; }
};

Voici un programme complet utilisant cette classe :

#include <iostream>
#include <string>
#include <string_view>

class ArrayException
{
private:
    std::string m_error;

public:
    ArrayException(std::string_view error)
        : m_error{ error }
    {
    }

    const std::string& getError() const { return m_error; }
};

class IntArray
{
private:
    int m_data[3]{}; // assume array is length 3 for simplicity

public:
    IntArray() {}

    int getLength() const { return 3; }

    int& operator[](const int index)
    {
        if (index < 0 || index >= getLength())
            throw ArrayException{ "Invalid index" };

        return m_data[index];
    }

};

int main()
{
    IntArray array;

    try
    {
        int value{ array[5] }; // out of range subscript
    }
    catch (const ArrayException& exception)
    {
        std::cerr << "An array exception occurred (" << exception.getError() << ")\n";
    }
}

Grâce à une telle classe, l'exception peut renvoyer une description du problème survenu, ce qui donne du contexte sur l'origine de l'erreur. Et comme ArrayException est un type unique, nous pouvons capturer spécifiquement les exceptions lancées par la classe de tableau et les traiter différemment des autres exceptions si nous le souhaitons.

Notez que les gestionnaires d'exceptions doivent capturer les objets d'exception de classe par référence plutôt que par valeur. Cela empêche le compilateur de créer une copie de l'exception au moment où elle est capturée, ce qui peut être coûteux lorsque l'exception est un objet de classe, et évite le phénomène de découpage (object slicing) lorsqu'on traite des classes d'exception dérivées (dont nous parlerons dans un instant). Capturer des exceptions par pointeur doit en général être évité, sauf si vous avez une raison particulière de le faire.

Bonne pratique

Les exceptions d'un type fondamental peuvent être capturées par valeur, car leur copie est peu coûteuse.
Les exceptions d'un type classe doivent être capturées par référence (constante) afin d'éviter une copie coûteuse et le découpage.

Exceptions et héritage

Puisqu'il est possible de lancer des classes comme exceptions, et que les classes peuvent être dérivées d'autres classes, nous devons examiner ce qui se passe lorsque des classes héritées servent d'exceptions. Il s'avère que les gestionnaires d'exceptions ne correspondent pas seulement aux classes d'un type donné, mais aussi aux classes dérivées de ce type ! Considérons l'exemple suivant :

#include <iostream>

class Base
{
public:
    Base() {}
};

class Derived: public Base
{
public:
    Derived() {}
};

int main()
{
    try
    {
        throw Derived();
    }
    catch (const Base& base)
    {
        std::cerr << "caught Base";
    }
    catch (const Derived& derived)
    {
        std::cerr << "caught Derived";
    }

    return 0;
}

Dans l'exemple ci-dessus, nous lançons une exception de type Derived. Pourtant, la sortie de ce programme est :


caught Base

Que s'est-il passé ?

Premièrement, comme indiqué plus haut, les classes dérivées seront capturées par les gestionnaires du type de base. Comme Derived dérive de Base, Derived est un Base (elles entretiennent une relation « est-un »). Deuxièmement, lorsque C++ cherche un gestionnaire pour une exception levée, il le fait séquentiellement. Par conséquent, la première chose que fait C++ est de vérifier si le gestionnaire pour Base correspond à l'exception Derived. Comme Derived est un Base, la réponse est oui, et le bloc catch pour le type Base est exécuté ! Le bloc catch pour Derived n'est même jamais testé dans ce cas.

Pour que cet exemple fonctionne comme prévu, nous devons inverser l'ordre des blocs catch :

#include <iostream>

class Base
{
public:
    Base() {}
};

class Derived: public Base
{
public:
    Derived() {}
};

int main()
{
    try
    {
        throw Derived();
    }
    catch (const Derived& derived)
    {
        std::cerr << "caught Derived";
    }
    catch (const Base& base)
    {
        std::cerr << "caught Base";
    }

    return 0;
}

Ainsi, le gestionnaire de Derived aura la première chance de capturer les objets de type Derived (avant que le gestionnaire de Base ne le puisse). Les objets de type Base ne correspondront pas au gestionnaire de Derived (Derived est un Base, mais Base n'est pas un Derived) et « passeront à travers » le gestionnaire de Base.

Règle

Les gestionnaires des classes d'exception dérivées doivent être placés avant ceux des classes de base.

La possibilité d'utiliser un gestionnaire de classe de base pour capturer les exceptions de types dérivés s'avère extrêmement utile.

std::exception

De nombreuses classes et opérateurs de la bibliothèque standard lancent des classes d'exception en cas d'échec. Par exemple, operator new peut lancer std::bad_alloc s'il ne parvient pas à allouer assez de mémoire. Un dynamic_cast échoué lance std::bad_cast. Et ainsi de suite. À partir de C++20, il existe 28 classes d'exception différentes pouvant être lancées, et d'autres sont ajoutées à chaque nouvelle norme du langage.

La bonne nouvelle est que toutes ces classes d'exception dérivent d'une seule classe appelée std::exception (définie dans l'en-tête <exception>). std::exception est une petite classe d'interface conçue pour servir de classe de base à toute exception lancée par la bibliothèque standard C++.

La plupart du temps, lorsqu'une exception est lancée par la bibliothèque standard, peu nous importe qu'il s'agisse d'une allocation échouée, d'un cast échoué ou d'autre chose. Nous voulons seulement savoir qu'un problème grave est survenu et que notre programme est en train de s'effondrer. Grâce à std::exception, nous pouvons mettre en place un gestionnaire d'exceptions qui capture les exceptions de type std::exception, ce qui nous permet de capturer std::exception et toutes les exceptions dérivées ensemble, à un seul endroit. Simple !

#include <cstddef> // for std::size_t
#include <exception> // for std::exception
#include <iostream>
#include <limits>
#include <string> // for this example

int main()
{
    try
    {
        // Your code using standard library goes here
        // We'll trigger one of these exceptions intentionally for the sake of the example
        std::string s;
        s.resize(std::numeric_limits<std::size_t>::max()); // will trigger a std::length_error or allocation exception
    }
    // This handler will catch std::exception and all the derived exceptions too
    catch (const std::exception& exception)
    {
        std::cerr << "Standard exception: " << exception.what() << '\n';
    }

    return 0;
}

Sur la machine de l'auteur, le programme ci-dessus affiche :


Standard exception: string too long

L'exemple ci-dessus devrait être assez simple. Un seul point mérite d'être relevé : std::exception possède une fonction membre virtuelle nommée what() qui renvoie une description de l'exception sous forme de chaîne de caractères de style C. La plupart des classes dérivées redéfinissent la fonction what() pour modifier le message. Notez que cette chaîne est destinée uniquement à un texte descriptif : ne l'utilisez pas pour des comparaisons, car elle n'est pas garantie d'être identique d'un compilateur à l'autre.

Il arrive que nous souhaitions traiter différemment un type d'exception particulier. Dans ce cas, nous pouvons ajouter un gestionnaire pour ce type précis, et laisser toutes les autres exceptions « passer à travers » vers le gestionnaire de base. Considérons :

try
{
     // code using standard library goes here
}
// This handler will catch std::length_error (and any exceptions derived from it) here
catch (const std::length_error& exception)
{
    std::cerr << "You ran out of memory!" << '\n';
}
// This handler will catch std::exception (and any exception derived from it) that fall
// through here
catch (const std::exception& exception)
{
    std::cerr << "Standard exception: " << exception.what() << '\n';
}

Dans cet exemple, les exceptions de type std::length_error seront capturées et traitées par le premier gestionnaire. Les exceptions de type std::exception et toutes les autres classes dérivées seront capturées par le second gestionnaire.

De telles hiérarchies d'héritage nous permettent d'utiliser des gestionnaires spécifiques pour cibler des classes d'exception dérivées précises, ou d'utiliser des gestionnaires de classe de base pour capturer toute une hiérarchie d'exceptions. Nous disposons ainsi d'un contrôle fin sur les exceptions que nous souhaitons traiter, tout en évitant d'avoir à fournir trop d'efforts pour capturer « tout le reste » au sein d'une hiérarchie.

Utiliser directement les exceptions standard

Rien ne lance directement un std::exception, et vous non plus ne devriez pas le faire. En revanche, n'hésitez pas à lancer les autres classes d'exception standard de la bibliothèque si elles répondent adéquatement à vos besoins. Vous pouvez trouver la liste de toutes les exceptions standard sur cppreference.

std::runtime_error (inclus dans l'en-tête stdexcept) est un choix populaire, car il possède un nom générique et son constructeur accepte un message personnalisable :

#include <exception> // for std::exception
#include <iostream>
#include <stdexcept> // for std::runtime_error

int main()
{
    try
    {
        throw std::runtime_error("Bad things happened");
    }
    // This handler will catch std::exception and all the derived exceptions too
    catch (const std::exception& exception)
    {
        std::cerr << "Standard exception: " << exception.what() << '\n';
    }

    return 0;
}

Ce programme affiche :


Standard exception: Bad things happened

Dériver vos propres classes de std::exception ou std::runtime_error

Vous pouvez bien sûr dériver vos propres classes de std::exception et redéfinir la fonction membre virtuelle what() const. Voici le même programme que précédemment, avec ArrayException dérivée de std::exception :

#include <exception> // for std::exception
#include <iostream>
#include <string>
#include <string_view>

class ArrayException : public std::exception
{
private:
    std::string m_error{}; // handle our own string

public:
    ArrayException(std::string_view error)
        : m_error{error}
    {
    }

    // std::exception::what() returns a const char*, so we must as well
    const char* what() const noexcept override { return m_error.c_str(); }
};

class IntArray
{
private:
    int m_data[3] {}; // assume array is length 3 for simplicity

public:
    IntArray() {}

    int getLength() const { return 3; }

    int& operator[](const int index)
    {
        if (index < 0 || index >= getLength())
            throw ArrayException("Invalid index");

        return m_data[index];
    }

};

int main()
{
    IntArray array;

    try
    {
        int value{ array[5] };
    }
    catch (const ArrayException& exception) // derived catch blocks go first
    {
        std::cerr << "An array exception occurred (" << exception.what() << ")\n";
    }
    catch (const std::exception& exception)
    {
        std::cerr << "Some other std::exception occurred (" << exception.what() << ")\n";
    }
}

Notez que la fonction virtuelle what() porte le spécificateur noexcept (ce qui signifie que la fonction promet de ne pas lancer elle-même d'exceptions). Par conséquent, notre redéfinition doit également porter le spécificateur noexcept.

Comme std::runtime_error possède déjà des fonctionnalités de gestion de chaînes de caractères, il constitue aussi une classe de base populaire pour les classes d'exception dérivées. std::runtime_error peut accepter en paramètre une chaîne de style C ou une const std::string&.

Voici le même exemple, dérivé cette fois de std::runtime_error :

#include <exception> // for std::exception
#include <iostream>
#include <stdexcept> // for std::runtime_error
#include <string>

class ArrayException : public std::runtime_error
{
public:
    // std::runtime_error takes either a null-terminated const char* or a const std::string&.
    // We will follow their lead and take a const std::string&
    ArrayException(const std::string& error)
        : std::runtime_error{ error } // std::runtime_error will handle the string
    {
    }


        // no need to override what() since we can just use std::runtime_error::what()
};

class IntArray
{
private:
    int m_data[3]{}; // assume array is length 3 for simplicity

public:
    IntArray() {}

    int getLength() const { return 3; }

    int& operator[](const int index)
    {
        if (index < 0 || index >= getLength())
            throw ArrayException("Invalid index");

        return m_data[index];
    }

};

int main()
{
    IntArray array;

    try
    {
        int value{ array[5] };
    }
    catch (const ArrayException& exception) // derived catch blocks go first
    {
        std::cerr << "An array exception occurred (" << exception.what() << ")\n";
    }
    catch (const std::exception& exception)
    {
        std::cerr << "Some other std::exception occurred (" << exception.what() << ")\n";
    }
}

Vous êtes libre de choisir entre créer vos propres classes d'exception autonomes, utiliser les classes d'exception standard, ou dériver vos propres classes d'exception de std::exception ou std::runtime_error. Toutes ces approches sont valides selon vos objectifs.

La durée de vie des exceptions

Lorsqu'une exception est lancée, l'objet lancé est généralement un temporaire ou une variable locale allouée sur la pile. Cependant, le traitement de l'exception peut dérouler la pile d'appels de la fonction, ce qui entraîne la destruction de toutes les variables locales de la fonction. Comment l'objet d'exception lancé survit-il alors au déroulement de la pile ?

Lorsqu'une exception est lancée, le compilateur crée une copie de l'objet d'exception dans une zone mémoire non précisée (située en dehors de la pile d'appels) réservée au traitement des exceptions. Ainsi, l'objet d'exception persiste quel que soit le déroulement de la pile, et quel que soit le nombre de fois où elle est déroulée. L'exception est garantie d'exister jusqu'à ce qu'elle ait été traitée.

Cela signifie que les objets lancés doivent en général être copiables (même si la pile n'est pas réellement déroulée). Des compilateurs performants peuvent parfois effectuer un déplacement à la place, ou même supprimer complètement la copie dans certaines circonstances précises.

Remarque

Les objets d'exception doivent être copiables.

Voici un exemple montrant ce qui se passe lorsque nous essayons de lancer un objet Derived qui n'est pas copiable :

#include <iostream>

class Base
{
public:
    Base() {}
};

class Derived : public Base
{
public:
    Derived() {}

    Derived(const Derived&) = delete; // not copyable
};

int main()
{
    Derived d{};

    try
    {
        throw d; // compile error: Derived copy constructor was deleted
    }
    catch (const Derived& derived)
    {
        std::cerr << "caught Derived";
    }
    catch (const Base& base)
    {
        std::cerr << "caught Base";
    }

    return 0;
}

Lorsque ce programme est compilé, le compilateur signale que le constructeur de copie de Derived n'est pas disponible, et interrompt la compilation.

Les objets d'exception ne doivent pas conserver de pointeurs ou de références vers des objets alloués sur la pile. Si une exception lancée entraîne le déroulement de la pile (et donc la destruction des objets alloués sur la pile), ces pointeurs ou références peuvent devenir des pointeurs pendants (dangling).
