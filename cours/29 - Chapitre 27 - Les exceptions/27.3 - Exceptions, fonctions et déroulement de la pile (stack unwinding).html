27.3 — Exceptions, fonctions et déroulement de la pile (stack unwinding)

Dans la leçon précédente, 27.2 -- Gestion de base des exceptions, nous avons expliqué comment throw, try et catch fonctionnent ensemble pour permettre la gestion des exceptions. Dans cette leçon, nous allons voir comment la gestion des exceptions interagit avec les fonctions.

Lancer des exceptions depuis une fonction appelée

Dans la leçon précédente, nous avons indiqué : « un bloc try détecte toutes les exceptions lancées par les instructions situées à l'intérieur de ce bloc try ». Dans les exemples correspondants, nos instructions throw étaient placées dans un bloc try et capturées par un bloc catch associé, le tout dans la même fonction. Devoir à la fois lancer et capturer une exception au sein d'une même fonction n'a qu'une utilité limitée.

Ce qui est plus intéressant, c'est ce qui se passe si une instruction à l'intérieur d'un bloc try est un appel de fonction, et que la fonction appelée lance une exception. Le bloc try détectera-t-il une exception lancée par une fonction appelée depuis ce bloc try ?

La réponse, heureusement, est oui !

L'une des propriétés les plus utiles de la gestion des exceptions est que les instructions throw n'ont PAS besoin d'être placées directement à l'intérieur d'un bloc try. Les exceptions peuvent être lancées depuis n'importe quel endroit d'une fonction, et être capturées par le bloc try de l'appelant (ou de l'appelant de l'appelant, etc.). Lorsqu'une exception est capturée de cette manière, l'exécution saute du point où l'exception est lancée vers le bloc catch qui la traite.

Point clé

Les blocs try capturent les exceptions non seulement des instructions situées à l'intérieur du bloc try, mais aussi des fonctions appelées à l'intérieur de ce bloc try.

Cela nous permet d'utiliser la gestion des exceptions de manière beaucoup plus modulaire. Nous allons le démontrer en réécrivant le programme de racine carrée de la leçon précédente afin d'utiliser une fonction modulaire.

#include <cmath> // pour la fonction sqrt()
#include <iostream>

// Une fonction racine carrée modulaire
double mySqrt(double x)
{
    // Si l'utilisateur a saisi un nombre négatif, c'est une condition d'erreur
    if (x < 0.0)
        throw "Can not take sqrt of negative number"; // lance une exception de type const char*

    return std::sqrt(x);
}

int main()
{
    std::cout << "Enter a number: ";
    double x {};
    std::cin >> x;

    try // Recherche les exceptions survenant dans le bloc try et les envoie au(x) bloc(s) catch associé(s)
    {
        double d = mySqrt(x);
        std::cout << "The sqrt of " << x << " is " << d << '\n';
    }
    catch (const char* exception) // capture les exceptions de type const char*
    {
        std::cerr << "Error: " << exception << std::endl;
    }

    return 0;
}

Dans ce programme, nous avons pris le code qui vérifie l'exception et calcule la racine carrée, et nous l'avons placé dans une fonction modulaire appelée mySqrt(). Nous avons ensuite appelé cette fonction mySqrt() depuis un bloc try. Vérifions qu'elle fonctionne toujours comme prévu :


Enter a number: -4
Error: Can not take sqrt of negative number

C'est bien le cas ! Lorsque l'exception est lancée dans mySqrt(), il n'existe aucun gestionnaire dans mySqrt() pour la traiter. Cependant, l'appel à mySqrt() (dans main()) se trouve dans un bloc try doté d'un gestionnaire d'exception correspondant. L'exécution saute donc de l'instruction throw dans mySqrt() jusqu'au début du bloc catch dans main(), puis reprend.

La partie la plus intéressante de ce programme est que la fonction mySqrt() peut lancer une exception sans la traiter elle-même ! Cela signifie en substance que mySqrt() est prête à dire « Hé, il y a un problème ! », mais ne veut pas le résoudre elle-même. Elle délègue, en somme, la responsabilité du traitement de l'exception à son appelant (un peu comme l'utilisation d'un code de retour transmet à l'appelant la responsabilité de traiter une erreur).

À ce stade, certains d'entre vous se demandent probablement pourquoi il est judicieux de renvoyer les erreurs à l'appelant. Pourquoi ne pas simplement faire en sorte que mySqrt() gère sa propre erreur ? Le problème est que différentes applications peuvent vouloir traiter les erreurs de différentes façons. Une application console peut vouloir afficher un message texte. Une application fenêtrée peut vouloir afficher une boîte de dialogue d'erreur. Dans une application, il peut s'agir d'une erreur fatale, et dans une autre non. En faisant remonter l'erreur hors de la fonction, chaque application peut traiter une erreur venant de mySqrt() de la manière la plus adaptée à son contexte ! Au final, cela maintient mySqrt() aussi modulaire que possible, et la gestion des erreurs peut être placée dans les parties moins modulaires du code.

Gestion des exceptions et déroulement de la pile (stack unwinding)

Dans cette section, nous allons examiner comment la gestion des exceptions fonctionne réellement lorsque plusieurs fonctions sont impliquées.

Contenu associé

Avant de continuer, consultez la leçon 20.2 -- La pile et le tas si vous avez besoin de revoir les piles d'appels (call stacks) et le déroulement de la pile.

Lorsqu'une exception est lancée, le programme regarde d'abord si l'exception peut être traitée immédiatement à l'intérieur de la fonction courante (c'est-à-dire si l'exception a été lancée dans un bloc try situé dans la fonction courante, et qu'un bloc catch correspondant lui est associé). Si la fonction courante peut traiter l'exception, elle le fait.

Sinon, le programme vérifie ensuite si l'appelant de la fonction (la fonction immédiatement au-dessus dans la pile d'appels) peut traiter l'exception. Pour que l'appelant puisse la traiter, l'appel à la fonction courante doit se trouver dans un bloc try, et un bloc catch correspondant doit lui être associé. Si aucune correspondance n'est trouvée, on vérifie l'appelant de l'appelant (deux fonctions plus haut dans la pile d'appels). De la même façon, pour que l'appelant de l'appelant traite l'exception, l'appel à l'appelant doit se trouver dans un bloc try, et un bloc catch correspondant doit lui être associé.

Le processus consistant à vérifier chaque fonction de la pile d'appels se poursuit jusqu'à ce qu'un gestionnaire soit trouvé, ou jusqu'à ce que toutes les fonctions de la pile d'appels aient été vérifiées sans qu'aucun gestionnaire ne soit trouvé.

Si un gestionnaire d'exception correspondant est trouvé, l'exécution saute du point où l'exception est lancée jusqu'au début du bloc catch correspondant. Cela nécessite de dérouler la pile (retirer la fonction courante de la pile d'appels) autant de fois que nécessaire pour que la fonction qui traite l'exception devienne la fonction au sommet de la pile d'appels.

Si aucun gestionnaire d'exception correspondant n'est trouvé, la pile peut ou non être déroulée. Nous reviendrons sur ce cas dans la prochaine leçon (27.4 -- Exceptions non capturées et gestionnaires universels).

Lorsque la fonction courante est retirée de la pile d'appels, toutes ses variables locales sont détruites comme d'habitude, mais aucune valeur n'est renvoyée.

Point clé

Le déroulement de la pile détruit les variables locales des fonctions dont la pile est déroulée (ce qui est une bonne chose, car cela garantit l'exécution de leurs destructeurs).

Un autre exemple de déroulement de la pile

Pour illustrer ce qui précède, examinons un exemple plus complexe, utilisant une pile plus grande. Bien que ce programme soit long, il est assez simple : main() appelle A(), A() appelle B(), B() appelle C(), C() appelle D(), et D() lance une exception.

#include <iostream>

void D() // appelée par C()
{
    std::cout << "Start D\n";
    std::cout << "D throwing int exception\n";

    throw - 1;

    std::cout << "End D\n"; // ignorée
}

void C() // appelée par B()
{
    std::cout << "Start C\n";
    D();
    std::cout << "End C\n";
}

void B() // appelée par A()
{
    std::cout << "Start B\n";

    try
    {
        C();
    }
    catch (double) // non capturée : le type de l'exception ne correspond pas
    {
        std::cerr << "B caught double exception\n";
    }

    try
    {
    }
    catch (int) // non capturée : l'exception n'a pas été lancée dans le bloc try
    {
        std::cerr << "B caught int exception\n";
    }

    std::cout << "End B\n";
}

void A() // appelée par main()
{
    std::cout << "Start A\n";

    try
    {
        B();
    }
    catch (int) // exception capturée ici et traitée
    {
        std::cerr << "A caught int exception\n";
    }
    catch (double) // non appelée car l'exception a été traitée par le bloc catch précédent
    {
        std::cerr << "A caught double exception\n";
    }

    // l'exécution reprend ici une fois l'exception traitée
    std::cout << "End A\n";
}

int main()
{
    std::cout << "Start main\n";

    try
    {
        A();
    }
    catch (int) // non appelée car l'exception a été traitée par A
    {
        std::cerr << "main caught int exception\n";
    }
    std::cout << "End main\n";

    return 0;
}

Examinez ce programme en détail, et essayez de déterminer ce qui sera affiché et ce qui ne le sera pas lors de son exécution. La réponse suit :


Start main
Start A
Start B
Start C
Start D
D throwing int exception
A caught int exception
End A
End main

Examinons ce qui se passe dans ce cas. L'affichage de toutes les instructions « Start » est simple et ne nécessite pas d'explication supplémentaire. La fonction D() affiche « D throwing int exception », puis lance une exception de type int. C'est là que les choses deviennent intéressantes.

Comme D() ne traite pas l'exception elle-même, ses appelants (les fonctions situées plus haut dans la pile d'appels) sont vérifiés pour voir si l'un d'eux peut la traiter. La fonction C() ne traite aucune exception, donc aucune correspondance n'est trouvée à cet endroit.

La fonction B() possède deux blocs try distincts. Le bloc try contenant l'appel à C() dispose d'un gestionnaire pour les exceptions de type double, qui ne correspond pas à notre exception de type int (et les exceptions n'effectuent pas de conversion de type), donc aucune correspondance n'est trouvée. Le bloc try vide dispose bien d'un gestionnaire d'exception de type int, mais ce bloc catch n'est pas considéré comme correspondant, car l'appel à C() ne se trouve pas dans le bloc try associé.

A() possède également un bloc try, et l'appel à B() s'y trouve, donc le programme vérifie s'il existe un gestionnaire catch pour les exceptions de type int. Il en existe un ! En conséquence, A() traite l'exception et affiche « A caught int exception ».

L'exception ayant maintenant été traitée, le contrôle se poursuit normalement après les blocs catch de A(). A() affiche donc « End A », puis se termine normalement.

Le contrôle revient à main(). Bien que main() possède un gestionnaire d'exception de type int, notre exception a déjà été traitée par A(), donc le bloc catch de main() n'est pas exécuté. main() affiche simplement « End main » puis se termine normalement.

Ce programme illustre plusieurs principes intéressants :

Premièrement, la fonction appelante immédiate d'une fonction qui lance une exception n'est pas obligée de traiter cette exception si elle ne le souhaite pas. Dans ce cas, C() n'a pas traité l'exception lancée par D(). Elle a délégué cette responsabilité à l'un de ses appelants situés plus haut dans la pile.

Deuxièmement, si un bloc try ne possède pas de gestionnaire catch pour le type d'exception lancée, le déroulement de la pile se produit exactement comme s'il n'y avait pas du tout de bloc try. Dans ce cas, B() n'a pas non plus traité l'exception, car elle ne disposait pas du bon type de bloc catch.

Troisièmement, si une fonction possède un bloc catch correspondant mais que l'appel à la fonction courante ne s'est pas produit dans le bloc try associé, ce bloc catch n'est pas utilisé. Nous avons également vu ce cas avec B().

Enfin, une fois qu'un bloc catch correspondant est exécuté, le flux de contrôle se poursuit normalement, à partir de la première instruction suivant le dernier bloc catch. C'est ce que montre A() : elle traite l'erreur, poursuit avec « End A », puis retourne à son appelant. Lorsque le programme revient à main(), l'exception a déjà été lancée et traitée : main() ne sait même pas qu'il y a eu une exception !

Comme vous pouvez le voir, le déroulement de la pile nous offre un comportement très utile : si une fonction ne souhaite pas traiter une exception, elle n'y est pas obligée. L'exception remontera dans la pile jusqu'à trouver quelqu'un qui la traitera ! Cela nous permet de décider à quel endroit de la pile d'appels il est le plus approprié de traiter les erreurs qui peuvent survenir.

Dans la prochaine leçon, nous verrons ce qui se passe lorsqu'une exception n'est pas capturée, ainsi qu'une méthode pour éviter que cela ne se produise.
