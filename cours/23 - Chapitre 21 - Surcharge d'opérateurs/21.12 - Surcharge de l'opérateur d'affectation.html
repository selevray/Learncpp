21.12 — Surcharge de l'opérateur d'affectation

L'opérateur d'affectation par copie (operator=) sert à copier les valeurs d'un objet vers un autre objet déjà existant.

Contenu associé

Depuis C++11, C++ prend aussi en charge l'« affectation par déplacement » (move assignment). Nous traitons cette notion dans la leçon 22.3 -- Constructeurs de déplacement et affectation par déplacement.

Affectation par copie et constructeur de copie

Le constructeur de copie et l'opérateur d'affectation par copie ont des rôles presque équivalents : tous deux copient un objet vers un autre. Cependant, le constructeur de copie initialise de nouveaux objets, tandis que l'opérateur d'affectation remplace le contenu d'objets existants.

La différence entre le constructeur de copie et l'opérateur d'affectation par copie embrouille beaucoup de programmeurs débutants, mais elle n'est pas vraiment difficile à saisir. En résumé :

  • Si un nouvel objet doit être créé avant que la copie puisse avoir lieu, c'est le constructeur de copie qui est utilisé (remarque : cela inclut le passage ou le renvoi d'objets par valeur).- Si aucun nouvel objet n'a besoin d'être créé avant la copie, c'est l'opérateur d'affectation qui est utilisé.

Surcharge de l'opérateur d'affectation

La surcharge de l'opérateur d'affectation par copie (operator=) est assez simple, avec une précaution particulière que nous verrons. L'opérateur d'affectation par copie doit être surchargé en tant que fonction membre.

#include <cassert>
#include <iostream>

class Fraction
{
private:
    int m_numerator { 0 };
    int m_denominator { 1 };

public:
    // Constructeur par défaut
    Fraction(int numerator = 0, int denominator = 1 )
        : m_numerator { numerator }, m_denominator { denominator }
    {
        assert(denominator != 0);
    }

    // Constructeur de copie
    Fraction(const Fraction& copy)
        : m_numerator { copy.m_numerator }, m_denominator { copy.m_denominator }
    {
        // inutile de vérifier ici que le dénominateur n'est pas nul, car copy doit déjà être une Fraction valide
        std::cout << "Copy constructor called\n"; // juste pour prouver que cela fonctionne
    }

    // Affectation surchargée
    Fraction& operator= (const Fraction& fraction);

    friend std::ostream& operator<<(std::ostream& out, const Fraction& f1);

};

std::ostream& operator<<(std::ostream& out, const Fraction& f1)
{
    out << f1.m_numerator << '/' << f1.m_denominator;
    return out;
}

// Une implémentation simpliste de operator= (voir une meilleure implémentation plus bas)
Fraction& Fraction::operator= (const Fraction& fraction)
{
    // effectuer la copie
    m_numerator = fraction.m_numerator;
    m_denominator = fraction.m_denominator;

    // renvoyer l'objet courant afin de pouvoir enchaîner cet opérateur
    return *this;
}

int main()
{
    Fraction fiveThirds { 5, 3 };
    Fraction f;
    f = fiveThirds; // appelle l'affectation surchargée
    std::cout << f;

    return 0;
}

Ce programme affiche :


5/3

Tout cela doit maintenant vous paraître assez clair. Notre operator= surchargé renvoie *this, ce qui permet d'enchaîner plusieurs affectations :

int main()
{
    Fraction f1 { 5, 3 };
    Fraction f2 { 7, 2 };
    Fraction f3 { 9, 5 };

    f1 = f2 = f3; // affectation enchaînée

    return 0;
}

Problèmes liés à l'auto-affectation

Les choses deviennent un peu plus intéressantes ici. C++ autorise l'auto-affectation :

int main()
{
    Fraction f1 { 5, 3 };
    f1 = f1; // auto-affectation

    return 0;
}

Cela appelle f1.operator=(f1) et, avec l'implémentation simpliste ci-dessus, chacun des membres est affecté à lui-même. Dans cet exemple particulier, l'auto-affectation consiste à affecter chaque membre à lui-même, ce qui n'a aucun effet global, si ce n'est de perdre du temps. Dans la plupart des cas, une auto-affectation n'a même pas besoin de faire quoi que ce soit !

Cependant, lorsqu'un opérateur d'affectation doit allouer dynamiquement de la mémoire, l'auto-affectation peut effectivement être dangereuse :

#include <algorithm> // pour std::max et std::copy_n
#include <iostream>

class MyString
{
private:
    char* m_data {};
    int m_length {};

public:
    MyString(const char* data = nullptr, int length = 0 )
        : m_length { std::max(length, 0) }
    {
        if (length)
        {
            m_data = new char[static_cast<std::size_t>(length)];
            std::copy_n(data, length, m_data); // copie length éléments de data dans m_data
        }
    }
    ~MyString()
    {
        delete[] m_data;
    }

    MyString(const MyString&) = default; // certains compilateurs (gcc) émettent un avertissement si vous avez des membres pointeurs mais pas de constructeur de copie déclaré

    // Affectation surchargée
    MyString& operator= (const MyString& str);

    friend std::ostream& operator<<(std::ostream& out, const MyString& s);
};

std::ostream& operator<<(std::ostream& out, const MyString& s)
{
    out << s.m_data;
    return out;
}

// Une implémentation simpliste de operator= (à ne pas utiliser)
MyString& MyString::operator= (const MyString& str)
{
    // si des données existent dans la chaîne courante, les supprimer
    if (m_data) delete[] m_data;

    m_length = str.m_length;
    m_data = nullptr;

    // allouer un nouveau tableau de la longueur appropriée
    if (m_length)
        m_data = new char[static_cast<std::size_t>(str.m_length)];

    std::copy_n(str.m_data, m_length, m_data); // copie m_length éléments de str.m_data dans m_data

    // renvoyer l'objet courant afin de pouvoir enchaîner cet opérateur
    return *this;
}

int main()
{
    MyString alex("Alex", 5); // Voici Alex
    MyString employee;
    employee = alex; // Alex est notre nouvel employé
    std::cout << employee; // Dites votre nom, employé

    return 0;
}

Commencez par exécuter le programme tel quel. Vous verrez qu'il affiche « Alex », comme prévu.

Exécutez maintenant le programme suivant :

int main()
{
    MyString alex { "Alex", 5 }; // Voici Alex
    alex = alex; // Alex est lui-même
    std::cout << alex; // Dites votre nom, Alex

    return 0;
}

Vous obtiendrez probablement une sortie incohérente. Que s'est-il passé ?

Examinons ce qui se produit dans l'operator= surchargé lorsque l'objet implicite ET le paramètre passé (str) sont tous deux la variable alex. Dans ce cas, m_data est identique à str.m_data. La première chose qui se produit est que la fonction vérifie si l'objet implicite contient déjà une chaîne. Si c'est le cas, elle doit la supprimer, afin d'éviter une fuite mémoire. Ici, m_data est alloué, donc la fonction supprime m_data. Mais comme str est le même objet que *this, la chaîne que nous voulions copier a été supprimée, et m_data (ainsi que str.m_data) est maintenant un pointeur pendant (dangling).

Ensuite, nous allouons une nouvelle mémoire pour m_data (et donc pour str.m_data). Ainsi, lorsque nous copions ensuite les données de str.m_data dans m_data, nous copions des données incohérentes, car str.m_data n'a jamais été initialisé.

Détecter et gérer l'auto-affectation

Heureusement, nous pouvons détecter quand une auto-affectation se produit. Voici une version mise à jour de notre operator= surchargé pour la classe MyString :

MyString& MyString::operator= (const MyString& str)
{
    // vérification de l'auto-affectation
    if (this == &str)
        return *this;

    // si des données existent dans la chaîne courante, les supprimer
    if (m_data) delete[] m_data;

    m_length = str.m_length;
    m_data = nullptr;

    // allouer un nouveau tableau de la longueur appropriée
    if (m_length)
        m_data = new char[static_cast<std::size_t>(str.m_length)];

    std::copy_n(str.m_data, m_length, m_data); // copie m_length éléments de str.m_data dans m_data

    // renvoyer l'objet courant afin de pouvoir enchaîner cet opérateur
    return *this;
}

En vérifiant si l'adresse de notre objet implicite est la même que l'adresse de l'objet passé en paramètre, nous pouvons faire en sorte que l'opérateur d'affectation renvoie immédiatement, sans effectuer aucun autre travail.

Comme il s'agit simplement d'une comparaison de pointeurs, l'opération est rapide et ne nécessite pas de surcharger operator==.

Quand ne pas gérer l'auto-affectation

En général, la vérification d'auto-affectation est omise dans les constructeurs de copie. Comme l'objet copié est nouvellement créé, le seul cas où l'objet nouvellement créé peut être égal à l'objet copié est celui où vous tentez d'initialiser un objet nouvellement défini avec lui-même :

someClass c { c };

Dans de tels cas, votre compilateur devrait vous avertir que c est une variable non initialisée.

Ensuite, la vérification d'auto-affectation peut être omise dans les classes qui gèrent naturellement l'auto-affectation. Considérons cet opérateur d'affectation de la classe Fraction, qui comporte une garde d'auto-affectation :

// Une meilleure implémentation de operator=
Fraction& Fraction::operator= (const Fraction& fraction)
{
    // garde d'auto-affectation
    if (this == &fraction)
        return *this;

    // effectuer la copie
    m_numerator = fraction.m_numerator; // gère l'auto-affectation
    m_denominator = fraction.m_denominator; // gère l'auto-affectation

    // renvoyer l'objet courant afin de pouvoir enchaîner cet opérateur
    return *this;
}

Si la garde d'auto-affectation n'existait pas, cette fonction fonctionnerait tout de même correctement lors d'une auto-affectation (car toutes les opérations effectuées par la fonction gèrent correctement l'auto-affectation).

Comme l'auto-affectation est un événement rare, certains gourous éminents du C++ recommandent d'omettre la garde d'auto-affectation, même dans les classes qui en bénéficieraient. Nous ne recommandons pas cette approche, car nous pensons qu'il est préférable de coder de manière défensive, puis d'optimiser sélectivement par la suite.

L'idiome copie et échange

Une meilleure façon de gérer les problèmes d'auto-affectation passe par ce qu'on appelle l'idiome copie et échange (copy and swap). Vous trouverez une excellente présentation du fonctionnement de cet idiome sur Stack Overflow.

L'opérateur d'affectation par copie implicite

Contrairement aux autres opérateurs, le compilateur fournit un opérateur d'affectation par copie implicite et public pour votre classe si vous n'en fournissez pas de version définie par l'utilisateur. Cet opérateur d'affectation effectue une affectation membre à membre (ce qui revient essentiellement à l'initialisation membre à membre effectuée par les constructeurs de copie par défaut).

Comme pour les autres constructeurs et opérateurs, vous pouvez interdire les affectations en rendant votre opérateur d'affectation par copie privé, ou en utilisant le mot-clé delete :

#include <cassert>
#include <iostream>

class Fraction
{
private:
    int m_numerator { 0 };
    int m_denominator { 1 };

public:
    // Constructeur par défaut
    Fraction(int numerator = 0, int denominator = 1)
        : m_numerator { numerator }, m_denominator { denominator }
    {
        assert(denominator != 0);
    }

    // Constructeur de copie
    Fraction(const Fraction &copy) = delete;

    // Affectation surchargée
    Fraction& operator= (const Fraction& fraction) = delete; // pas de copies par affectation !

    friend std::ostream& operator<<(std::ostream& out, const Fraction& f1);

};

std::ostream& operator<<(std::ostream& out, const Fraction& f1)
{
    out << f1.m_numerator << '/' << f1.m_denominator;
    return out;
}

int main()
{
    Fraction fiveThirds { 5, 3 };
    Fraction f;
    f = fiveThirds; // erreur de compilation, operator= a été supprimé
    std::cout << f;

    return 0;
}

Notez que si votre classe possède des membres const, le compilateur définit à la place l'operator= implicite comme supprimé. En effet, les membres const ne peuvent pas être affectés, donc le compilateur considère que votre classe ne devrait pas être affectable.

Si vous souhaitez qu'une classe ayant des membres const soit affectable (pour tous les membres qui ne sont pas const), vous devrez surcharger explicitement operator= et affecter manuellement chaque membre non const.
