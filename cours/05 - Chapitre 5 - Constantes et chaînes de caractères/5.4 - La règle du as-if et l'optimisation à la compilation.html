5.4 — La règle du as-if et l'optimisation à la compilation

Introduction à l'optimisation

En programmation, l'optimisation consiste à modifier un logiciel pour qu'il fonctionne plus efficacement (par exemple pour s'exécuter plus vite ou consommer moins de ressources). L'optimisation peut avoir un impact considérable sur les performances globales d'une application.

Certains types d'optimisation sont généralement réalisés à la main. Un programme appelé profileur (profiler) permet de voir combien de temps prend l'exécution de chaque partie d'un programme, et quelles parties nuisent le plus aux performances globales. Le programmeur peut alors chercher des moyens de résoudre ces problèmes de performance. Comme l'optimisation manuelle est lente, les programmeurs se concentrent en général sur des améliorations de haut niveau ayant un fort impact (comme le choix d'algorithmes plus performants, l'optimisation du stockage et de l'accès aux données, la réduction de l'utilisation des ressources, la parallélisation des tâches, etc.).

D'autres formes d'optimisation peuvent être réalisées automatiquement. Un programme qui optimise un autre programme est appelé optimiseur (optimizer). Les optimiseurs travaillent généralement à bas niveau, en cherchant à améliorer des instructions ou des expressions en les réécrivant, en les réordonnant ou en les supprimant. Par exemple, lorsque vous écrivez i = i * 2;, l'optimiseur peut la réécrire en i *= 2;, i += i; ou i <<= 1;. Pour des valeurs entières, toutes ces formes produisent le même résultat, mais l'une d'elles peut être plus rapide que les autres sur une architecture donnée. Un programmeur ne saurait probablement pas quel est le choix le plus performant (et la réponse peut varier selon l'architecture), alors qu'un optimiseur pour un système donné le saurait. Chaque optimisation de bas niveau ne procure peut-être qu'un petit gain de performance, mais leur effet cumulé peut aboutir à une amélioration significative.

Les compilateurs C++ modernes sont des compilateurs optimisants, c'est-à-dire qu'ils sont capables d'optimiser automatiquement vos programmes au cours du processus de compilation. Comme le préprocesseur, ces optimisations ne modifient pas vos fichiers source : elles sont appliquées de manière transparente pendant la compilation.

Point clé

Les compilateurs optimisants permettent aux programmeurs de se concentrer sur l'écriture d'un code lisible et facile à maintenir, sans sacrifier les performances.

Comme l'optimisation implique certains compromis (nous en parlerons en fin de leçon), les compilateurs proposent généralement plusieurs niveaux d'optimisation, qui déterminent s'ils optimisent, à quel degré de agressivité, et quel type d'optimisation ils privilégient (par exemple la vitesse ou la taille).

La plupart des compilateurs n'optimisent pas par défaut. Si vous utilisez un compilateur en ligne de commande, vous devrez donc activer l'optimisation vous-même. Si vous utilisez un IDE, celui-ci configurera probablement automatiquement les builds de version (release) avec optimisation activée, et les builds de débogage (debug) sans optimisation.

Pour les utilisateurs de gcc et Clang

Consultez 0.9 -- Configurer votre compilateur : configurations de build pour savoir comment activer l'optimisation.

La règle du as-if

En C++, les compilateurs disposent d'une grande latitude pour optimiser les programmes. La règle du as-if (as-if rule) indique que le compilateur peut modifier un programme comme il l'entend afin de produire un code plus optimisé, tant que ces modifications n'affectent pas le « comportement observable » du programme.

Pour les lecteurs avancés

La règle du as-if connaît une exception notable : les appels inutiles au constructeur de copie (ou de déplacement) peuvent être supprimés (omis), même si ces constructeurs ont un comportement observable. Nous traitons ce sujet dans la leçon 14.15 -- Initialisation de classe et élision de copie.

Les compilateurs modernes emploient diverses techniques pour optimiser efficacement un programme. Les techniques applicables dépendent du programme ainsi que de la qualité du compilateur et de l'optimiseur.

Une opportunité d'optimisation

Considérons le programme court suivant :

#include <iostream>

int main()
{
    int x { 3 + 4 };
    std::cout << x << '\n';

    return 0;
}

La sortie est directe :


7

Pourtant, une possibilité d'optimisation intéressante se cache derrière.

Si ce programme était compilé exactement tel qu'il est écrit (sans optimisation), le compilateur générerait un exécutable qui calcule le résultat de 3 + 4 à l'exécution (lorsque le programme tourne). Si le programme était exécuté un million de fois, 3 + 4 serait évalué un million de fois, et la valeur 7 produite un million de fois.

Comme le résultat de 3 + 4 ne change jamais (il vaut toujours 7), recalculer ce résultat à chaque exécution du programme est un gaspillage.

Évaluation à la compilation

Les compilateurs C++ modernes sont capables d'évaluer entièrement ou partiellement certaines expressions à la compilation (plutôt qu'à l'exécution). Lorsque le compilateur évalue entièrement ou partiellement une expression à la compilation, on parle d'évaluation à la compilation (compile-time evaluation).

Point clé

L'évaluation à la compilation permet au compilateur de réaliser à la compilation un travail qui serait autrement effectué à l'exécution. Comme ces expressions n'ont plus besoin d'être évaluées à l'exécution, les exécutables obtenus sont plus rapides et plus petits (au prix d'une compilation légèrement plus lente).

À titre illustratif, nous allons voir dans cette leçon quelques techniques d'optimisation simples qui exploitent l'évaluation à la compilation. Nous poursuivrons ensuite la discussion sur l'évaluation à la compilation dans les leçons suivantes.

Pliage de constantes

L'une des premières formes d'évaluation à la compilation s'appelle « pliage de constantes » (constant folding). Le pliage de constantes (constant folding) est une technique d'optimisation dans laquelle le compilateur remplace les expressions dont les opérandes sont des littéraux par le résultat de l'expression. Grâce au pliage de constantes, le compilateur reconnaît que l'expression 3 + 4 n'a que des opérandes constants, puis la remplace par le résultat 7.

Le résultat serait équivalent au programme suivant :

#include <iostream>

int main()
{
    int x { 7 };
    std::cout << x << '\n';

    return 0;
}

Ce programme produit la même sortie (7) que la version précédente, mais l'exécutable obtenu n'a plus besoin de consommer des cycles de processeur pour calculer 3 + 4 à l'exécution !

Le pliage de constantes peut aussi s'appliquer à des sous-expressions, même lorsque l'expression complète doit être exécutée à l'exécution.

#include <iostream>

int main()
{
    std::cout << 3 + 4 << '\n';

    return 0;
}

Dans l'exemple ci-dessus, 3 + 4 est une sous-expression de l'expression complète std::cout << 3 + 4 << '\n';. Le compilateur peut optimiser cela en std::cout << 7 << '\n';.

Propagation de constantes

Le programme suivant contient une autre opportunité d'optimisation :

#include <iostream>

int main()
{
    int x { 7 };
    std::cout << x << '\n';

    return 0;
}

Lors de l'initialisation de x, la valeur 7 est stockée dans la mémoire allouée pour x. Puis, à la ligne suivante, le programme retourne en mémoire pour lire à nouveau la valeur 7 afin de l'afficher. Cela nécessite deux opérations d'accès mémoire (une pour écrire la valeur, une pour la lire).

La propagation de constantes (constant propagation) est une technique d'optimisation dans laquelle le compilateur remplace les variables dont il sait qu'elles ont une valeur constante par cette valeur. Grâce à la propagation de constantes, le compilateur comprend que x a toujours la valeur constante 7, et remplace toute utilisation de la variable x par la valeur 7.

Le résultat serait équivalent au programme suivant :

#include <iostream>

int main()
{
    int x { 7 };
    std::cout << 7 << '\n';

    return 0;
}

Le programme n'a ainsi plus besoin d'aller en mémoire pour lire la valeur de x.

La propagation de constantes peut produire un résultat qui pourra ensuite être optimisé par pliage de constantes :

#include <iostream>

int main()
{
    int x { 7 };
    int y { 3 };
    std::cout << x + y << '\n';

    return 0;
}

Dans cet exemple, la propagation de constantes transforme x + y en 7 + 3, qui peut ensuite être plié en la valeur 10.

Élimination du code mort

L'élimination du code mort (dead code elimination) est une technique d'optimisation dans laquelle le compilateur supprime du code qui peut être exécuté mais qui n'a aucun effet sur le comportement du programme.

Revenons à un exemple précédent :

#include <iostream>

int main()
{
    int x { 7 };
    std::cout << 7 << '\n';

    return 0;
}

Dans ce programme, la variable x est définie et initialisée, mais elle n'est jamais utilisée, elle n'a donc aucun effet sur le comportement du programme. L'élimination du code mort supprimerait la définition de x.

Le résultat serait équivalent au programme suivant :

#include <iostream>

int main()
{
    std::cout << 7 << '\n';

    return 0;
}

Lorsqu'une variable est retirée du programme parce qu'elle n'est plus nécessaire, on dit que la variable a été optimisée (optimized out) ou éliminée (optimized away).

Par rapport à la version originale, cette version optimisée ne nécessite plus le calcul à l'exécution de l'expression 3 + 4, ni deux opérations d'accès mémoire (une pour initialiser la variable x et une pour lire sa valeur). Le programme est donc à la fois plus petit et plus rapide.

Les variables const sont plus faciles à optimiser

Dans certains cas, il existe des moyens simples d'aider le compilateur à mieux optimiser.

La propagation de constantes peut être difficile pour le compilateur. Dans la section sur la propagation de constantes, nous avons donné cet exemple :

#include <iostream>

int main()
{
    int x { 7 };
    std::cout << x << '\n';

    return 0;
}

Comme x est définie comme une variable non-const, pour appliquer cette optimisation, le compilateur doit comprendre que la valeur de x ne change pas réellement (alors qu'elle pourrait changer). Sa capacité à le faire dépend de la complexité du programme et de la sophistication des routines d'optimisation du compilateur.

Nous pouvons aider le compilateur à mieux optimiser en utilisant des variables constantes chaque fois que c'est possible. Par exemple :

#include <iostream>

int main()
{
    const int x { 7 }; // x est maintenant const
    std::cout << x << '\n';

    return 0;
}

Comme x est maintenant const, le compilateur a la garantie que x ne peut pas être modifiée après son initialisation. Il est ainsi plus probable que le compilateur applique la propagation de constantes, puis élimine entièrement la variable.

Point clé

L'utilisation de variables const peut aider le compilateur à mieux optimiser.

L'optimisation peut rendre les programmes plus difficiles à déboguer

Si l'optimisation rend nos programmes plus rapides, pourquoi n'est-elle pas activée par défaut ?

Lorsque le compilateur optimise un programme, il peut réordonner, modifier, remplacer ou supprimer entièrement des variables, des expressions, des instructions et des appels de fonctions. De tels changements peuvent rendre le débogage difficile.

À l'exécution, il peut être difficile de déboguer un code compilé qui ne correspond plus très bien au code source d'origine. Par exemple, si vous tentez de surveiller une variable qui a été éliminée par l'optimisation, le débogueur ne pourra pas la localiser. Si vous tentez d'entrer dans une fonction qui a été supprimée par l'optimisation, le débogueur la survolera simplement. Ainsi, si vous déboguez votre code et que le débogueur se comporte de façon étrange, c'est la cause la plus probable.

À la compilation, nous disposons de peu de visibilité et d'outils pour comprendre ce que fait réellement le compilateur. Si une variable ou une expression est remplacée par une valeur, et que cette valeur est fausse, comment déboguer le problème ? C'est un défi toujours d'actualité.

Pour limiter ce genre de problèmes, les builds de débogage laissent généralement les optimisations désactivées, afin que le code compilé corresponde plus fidèlement au code source.

Note de l'auteur

Le débogage à la compilation est un domaine peu développé. À partir de C++23, plusieurs propositions sont à l'étude pour les futures normes du langage (comme celle-ci) qui, si elles sont approuvées, ajouteront des capacités utiles dans ce domaine.

Terminologie : constantes à la compilation et constantes à l'exécution

Les constantes en C++ sont parfois réparties en deux catégories informelles.

Une constante de compilation (compile-time constant) est une constante dont la valeur est connue à la compilation. Par exemple :

  • Les littéraux.
  • Les objets constants dont les initialisateurs sont des constantes de compilation.

Une constante d'exécution (runtime constant) est une constante dont la valeur est déterminée dans un contexte d'exécution. Par exemple :

  • Les paramètres de fonction constants.
  • Les objets constants dont les initialisateurs sont des non-constantes ou des constantes d'exécution.

Par exemple :

#include <iostream>

int five()
{
    return 5;
}

int pass(const int x) // x est une constante d'exécution
{
    return x;
}

int main()
{
    // Les éléments suivants sont des non-constantes :
    [[maybe_unused]] int a { 5 };

    // Les éléments suivants sont des constantes de compilation :
    [[maybe_unused]] const int b { 5 };
    [[maybe_unused]] const double c { 1.2 };
    [[maybe_unused]] const int d { b };       // b est une constante de compilation

    // Les éléments suivants sont des constantes d'exécution :
    [[maybe_unused]] const int e { a };       // a n'est pas const
    [[maybe_unused]] const int f { e };       // e est une constante d'exécution
    [[maybe_unused]] const int g { five() };  // la valeur de retour n'est connue qu'à l'exécution
    [[maybe_unused]] const int h { pass(5) }; // la valeur de retour n'est connue qu'à l'exécution

    return 0;
}

Bien que vous rencontriez ces termes dans la nature, en C++ ces définitions ne sont pas très utiles :

  • Certaines constantes d'exécution (et même certaines non-constantes) peuvent être évaluées à la compilation à des fins d'optimisation (en vertu de la règle du as-if).
  • Certaines constantes de compilation (par exemple const double d { 1.2 };) ne peuvent pas être utilisées dans les fonctionnalités de compilation définies par la norme du langage. Nous en reparlerons dans la leçon 5.5 -- Expressions constantes.

Pour cette raison, nous vous recommandons d'éviter ces termes. Nous verrons la terminologie à utiliser à la place dans la prochaine leçon.
