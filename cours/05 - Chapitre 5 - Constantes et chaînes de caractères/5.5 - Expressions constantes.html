5.5 — Expressions constantes

Dans la leçon 1.10 -- Introduction aux expressions, nous avons présenté les expressions. Par défaut, les expressions sont évaluées à l'exécution. Dans certains cas, elles doivent l'être :

std::cin >> x;
std::cout << 5 << '\n';

Comme les entrées et sorties ne peuvent pas être réalisées à la compilation, les expressions ci-dessus doivent obligatoirement être évaluées à l'exécution.

Dans la leçon précédente 5.4 -- La règle du as-if et l'optimisation à la compilation, nous avons abordé la règle du as-if et la manière dont le compilateur peut optimiser un programme en déplaçant du travail de l'exécution vers la compilation. En vertu de cette règle, le compilateur peut choisir d'évaluer certaines expressions à l'exécution ou à la compilation :

const double x { 1.2 };
const double y { 3.4 };
const double z { x + y }; // x + y peut être évaluée à l'exécution ou à la compilation

L'expression x + y serait normalement évaluée à l'exécution. Mais comme les valeurs de x et y sont connues à la compilation, le compilateur peut choisir de l'évaluer à la compilation et d'initialiser z avec la valeur calculée à la compilation, 4.6.

Dans quelques autres cas, le langage C++ exige une expression évaluable à la compilation. Par exemple, une variable constexpr exige un initialisateur évaluable à la compilation :

int main()
{
    constexpr int x { expr }; // Comme la variable x est constexpr, expr doit être évaluable à la compilation
}

Lorsqu'une expression constante est requise mais qu'aucune n'est fournie, le compilateur signale une erreur et interrompt la compilation.

Nous étudierons les variables constexpr dans la leçon suivante (5.6 -- Variables constexpr).

Pour les lecteurs avancés

Quelques cas courants où une expression évaluable à la compilation est requise :

  • L'initialisateur d'une variable constexpr (5.6 -- Variables constexpr).
  • Un argument de paramètre template non typé (11.9 -- Paramètres template non typés).
  • La taille déclarée d'un std::array (17.1 -- Introduction à std::array) ou d'un tableau de style C (17.7 -- Introduction aux tableaux de style C).

Dans cette leçon, nous allons explorer davantage les capacités de C++ en matière d'évaluation à la compilation, et voir comment C++ distingue ce dernier cas des deux précédents.

Les avantages de la programmation à la compilation

Si la règle du as-if est excellente pour améliorer les performances, elle nous laisse dépendants de la sophistication du compilateur pour déterminer ce qui peut être évalué à la compilation. Ainsi, si une portion de code doit impérativement s'exécuter à la compilation, ce n'est pas garanti. Ce même code, compilé sur une autre plateforme, avec un autre compilateur, avec d'autres options de compilation, ou légèrement modifié, peut produire un résultat différent. Comme la règle du as-if s'applique de manière invisible, le compilateur ne nous indique pas quelles parties du code il a décidé d'évaluer à la compilation, ni pourquoi. Un code que nous souhaitons évaluer à la compilation peut même ne pas en être éligible (à cause d'une coquille ou d'un malentendu), sans que nous le sachions jamais.

Pour améliorer cette situation, le langage C++ nous permet d'indiquer explicitement les parties de code que nous voulons exécuter à la compilation. L'utilisation de fonctionnalités du langage qui entraînent une évaluation à la compilation s'appelle programmation à la compilation (compile-time programming).

Ces fonctionnalités peuvent améliorer les logiciels dans plusieurs domaines :

  • Performance : l'évaluation à la compilation rend nos programmes plus petits et plus rapides. Plus nous pouvons garantir qu'un code est évaluable à la compilation, plus le gain de performance est important.
  • Polyvalence : nous pouvons toujours utiliser un tel code aux endroits qui exigent une valeur de compilation. Un code qui repose sur la règle du as-if pour être évalué à la compilation ne peut pas être utilisé à ces endroits (même si le compilateur choisit de l'évaluer à la compilation). Cette décision a été prise pour que le code qui compile aujourd'hui ne cesse pas de compiler demain, lorsque le compilateur décidera d'optimiser différemment.
  • Prévisibilité : nous pouvons demander au compilateur d'interrompre la compilation s'il juge qu'un code ne peut pas être exécuté à la compilation (au lieu d'opter silencieusement pour une évaluation à l'exécution). Cela nous permet de nous assurer qu'une portion de code que nous voulons vraiment exécuter à la compilation le sera.
  • Qualité : nous pouvons demander au compilateur de détecter de manière fiable certains types d'erreurs de programmation à la compilation, et d'interrompre la construction s'il en rencontre. C'est bien plus efficace que de tenter de détecter et de gérer proprement ces mêmes erreurs à l'exécution.
  • Qualité : et c'est peut-être le plus important, le comportement indéfini n'est pas autorisé à la compilation. Si nous faisons quelque chose qui provoque un comportement indéfini à la compilation, le compilateur doit interrompre la construction et nous demander de corriger le problème. Notez que c'est un problème difficile pour les compilateurs, qui peuvent ne pas détecter tous les cas.

En résumé, l'évaluation à la compilation nous permet d'écrire des programmes à la fois plus performants et de meilleure qualité (plus sûrs et comportant moins de bogues) ! Ainsi, même si l'évaluation à la compilation ajoute un peu de complexité au langage, ses bénéfices peuvent être substantiels.

Les fonctionnalités de C++ suivantes sont les plus fondamentales pour la programmation à la compilation :

  • Les variables constexpr (abordées dans la prochaine leçon, 5.6 -- Variables constexpr).
  • Les fonctions constexpr (abordées dans la leçon F.1 -- Fonctions constexpr).
  • Les templates (présentés dans la leçon 11.6 -- Templates de fonctions).
  • static_assert (abordé dans la leçon 9.6 -- Assert et static_assert).

Toutes ces fonctionnalités ont un point commun : elles utilisent des expressions constantes.

Les expressions constantes

Il est peut-être surprenant que la norme C++ mentionne à peine la « compilation ». Elle définit plutôt une « expression constante », c'est-à-dire une expression qui doit pouvoir être évaluée à la compilation, ainsi que des règles déterminant comment le compilateur doit traiter ces expressions. Les expressions constantes forment l'ossature de l'évaluation à la compilation en C++.

Dans la leçon 1.10 -- Introduction aux expressions, nous avons défini une expression comme « une séquence non vide de littéraux, de variables, d'opérateurs et d'appels de fonctions ». Une expression constante (constant expression) est une séquence non vide de littéraux, de variables constantes, d'opérateurs et d'appels de fonctions, dont chaque élément doit pouvoir être évalué à la compilation. La différence essentielle est que, dans une expression constante, chaque partie de l'expression doit être évaluable à la compilation.

Point clé

Dans une expression constante, chaque partie de l'expression doit être évaluable à la compilation.

Une expression qui n'est pas une expression constante est souvent appelée expression non constante, et peut être informellement nommée expression d'exécution (runtime expression), car ces expressions sont généralement évaluées à l'exécution.

Lecture facultative

La norme C++20 (à la section [expr.const]) indique que « les expressions constantes peuvent être évaluées pendant la traduction ». Comme nous l'avons vu dans la leçon 2.10 -- Introduction au préprocesseur, la traduction désigne l'ensemble du processus de construction d'un programme (qui comprend le prétraitement, la compilation et l'édition de liens). Ainsi, dans un programme compilé, les expressions constantes peuvent être évaluées dans le cadre du processus de compilation. Dans un programme interprété, la traduction a lieu à l'exécution.

Comme les programmes C++ sont généralement compilés, nous partirons du principe que les expressions constantes peuvent être évaluées à la compilation.

Que peut contenir une expression constante ?

Note de l'auteur

Sur le plan technique, les expressions constantes sont assez complexes. Dans cette section, nous allons approfondir un peu ce qu'elles peuvent et ne peuvent pas contenir. Vous n'avez pas besoin de retenir la plupart de ces détails. Si une expression constante est requise à un endroit et que vous n'en fournissez pas, le compilateur vous signalera volontiers votre erreur, et vous pourrez la corriger à ce moment-là.

Le plus souvent, les expressions constantes contiennent les éléments suivants :

  • Des littéraux (par exemple '5', 1.2)
  • La plupart des opérateurs dont les opérandes sont des expressions constantes (par exemple 3 + 4, 2 * sizeof(int)).
  • Des variables constantes de type entier avec un initialisateur qui est une expression constante (par exemple const int x { 5 };). C'est une exception historique : en C++ moderne, on préfère les variables constexpr.
  • Des variables constexpr (abordées dans la prochaine leçon, 5.6 -- Variables constexpr).
  • Des appels de fonctions constexpr dont les arguments sont des expressions constantes (voir F.1 -- Fonctions constexpr).

Pour les lecteurs avancés

Les expressions constantes peuvent aussi contenir :

  • Des paramètres template non typés (voir 11.9 -- Paramètres template non typés).
  • Des énumérateurs (voir 13.2 -- Énumérations non délimitées).
  • Des traits de type (voir la page cppreference sur les traits de type).
  • Des expressions lambda constexpr (voir 20.6 -- Introduction aux lambdas (fonctions anonymes)).

Astuce

Notamment, les éléments suivants ne peuvent pas être utilisés dans une expression constante :

  • Les variables non constantes.
  • Les variables constantes non entières, même lorsqu'elles ont un initialisateur qui est une expression constante (par exemple const double d { 1.2 };). Pour utiliser de telles variables dans une expression constante, définissez-les plutôt comme des variables constexpr (voir la leçon 5.6 -- Variables constexpr).
  • Les valeurs de retour des fonctions non constexpr (même lorsque l'expression de retour est une expression constante).
  • Les paramètres de fonction (même lorsque la fonction est constexpr).
  • Les opérateurs dont les opérandes ne sont pas des expressions constantes (par exemple x + y lorsque x ou y n'est pas une expression constante, ou std::cout << "hello\n" car std::cout n'est pas une expression constante).
  • Les opérateurs new, delete, throw, typeid et operator, (virgule).

Une expression contenant l'un des éléments ci-dessus est une expression d'exécution.

Pour aller plus loin

Pour la définition précise d'une expression constante, consultez la page cppreference sur les expressions constantes. Notez qu'une expression constante est définie par ce qu'elle n'est pas. Il nous faut donc deviner ce qu'elle est. Bonne chance !

Terminologie

Lorsqu'on parle d'expressions constantes, on utilise couramment l'une de ces deux formulations :

  • « X est utilisable dans une expression constante » est souvent employé pour insister sur ce qu'est X. Par exemple, « 5 est utilisable dans une expression constante » souligne que le littéral 5 peut figurer dans une expression constante.
  • « X est une expression constante » est parfois employé pour insister sur le fait que l'expression complète (constituée de X) est une expression constante. Par exemple, « 5 est une expression constante » souligne que l'expression 5 est une expression constante.

La seconde formulation peut sembler maladroite lorsqu'on dit « les littéraux sont des expressions constantes » (car ce sont en réalité des valeurs). Mais cela signifie simplement qu'une expression constituée d'un littéral est une expression constante.

En passant…

Lorsque les expressions constantes ont été définies, les types entiers const ont été admis par tolérance, car le langage les traitait déjà comme des expressions constantes.

Le comité a discuté de la question de savoir si les types const non entiers, avec un initialisateur qui est une expression constante, devaient également être traités comme des expressions constantes (par cohérence avec le cas des types entiers const). Finalement, il a décidé que non, afin de favoriser un usage plus cohérent de constexpr.

Exemples d'expressions constantes et non constantes

Dans le programme suivant, nous examinons quelques instructions d'expression et indiquons si chaque expression est une expression constante ou une expression d'exécution :

#include <iostream>

int getNumber()
{
    std::cout << "Enter a number: ";
    int y{};
    std::cin >> y; // ne peut s'exécuter qu'à l'exécution

    return y;      // cette expression de retour est une expression d'exécution
}

// La valeur de retour d'une fonction non constexpr est une expression d'exécution
// même lorsque l'expression de retour est une expression constante
int five()
{
    return 5;      // cette expression de retour est une expression constante
}

int main()
{
    // Les littéraux peuvent être utilisés dans les expressions constantes
    5;                           // expression constante
    1.2;                         // expression constante
    "Hello world!";              // expression constante

    // La plupart des opérateurs dont les opérandes sont des expressions constantes peuvent être utilisés dans les expressions constantes
    5 + 6;                       // expression constante
    1.2 * 3.4;                   // expression constante
    8 - 5.6;                     // expression constante (même si les opérandes ont des types différents)
    sizeof(int) + 1;             // expression constante (sizeof peut être déterminé à la compilation)

    // Les valeurs de retour des fonctions non constexpr ne peuvent être utilisées que dans des expressions d'exécution
    getNumber();                 // expression d'exécution
    five();                      // expression d'exécution (même si l'expression de retour est une expression constante)

    // Les opérateurs dont les opérandes ne sont pas des expressions constantes ne peuvent être utilisés que dans des expressions d'exécution
    std::cout << 5;              // expression d'exécution (std::cout n'est pas un opérande d'expression constante)

    return 0;
}

Dans l'extrait suivant, nous définissons plusieurs variables et indiquons si elles peuvent être utilisées dans des expressions constantes :

    // Les variables constantes de type entier avec un initialisateur qui est une expression constante peuvent être utilisées dans les expressions constantes :
    const int a { 5 };           // a est utilisable dans les expressions constantes
    const int b { a };           // b est utilisable dans les expressions constantes (a est une expression constante, d'après l'instruction précédente)
    const long c { a + 2 };      // c est utilisable dans les expressions constantes (operator+ a des opérandes qui sont des expressions constantes)

    // Les autres variables ne peuvent pas être utilisées dans les expressions constantes (même lorsqu'elles ont un initialisateur qui est une expression constante) :
    int d { 5 };                 // d n'est pas utilisable dans les expressions constantes (d n'est pas const)
    const int e { d };           // e n'est pas utilisable dans les expressions constantes (l'initialisateur n'est pas une expression constante)
    const double f { 1.2 };      // f n'est pas utilisable dans les expressions constantes (ce n'est pas une variable constante de type entier)

Quand les expressions constantes sont-elles évaluées à la compilation ?

Comme les expressions constantes peuvent toujours être évaluées à la compilation, on pourrait supposer qu'elles le seront toujours. Contre toute intuition, ce n'est pas le cas.

Le compilateur n'est tenu d'évaluer les expressions constantes à la compilation que dans les contextes qui exigent une expression constante.

Terminologie

Le terme technique désignant une expression qui doit être évaluée à la compilation est expression évaluée manifestement à la compilation (manifestly constant-evaluated expression). Vous ne rencontrerez probablement ce terme que dans la documentation technique.

Dans les contextes qui n'exigent pas d'expression constante, le compilateur peut choisir d'évaluer une expression constante à la compilation ou à l'exécution.

const int x { 3 + 4 }; // l'expression constante 3 + 4 doit être évaluée à la compilation
int y { 3 + 4 };       // l'expression constante 3 + 4 peut être évaluée à la compilation ou à l'exécution

La variable x est de type const int et possède un initialisateur qui est une expression constante : x est donc utilisable dans une expression constante. Son initialisateur doit être évalué à la compilation (sinon la valeur de x ne serait pas connue à la compilation, et x ne serait pas utilisable dans une expression constante). En revanche, la variable y n'est pas constante, donc elle n'est pas utilisable dans une expression constante. Même si son initialisateur est une expression constante, le compilateur peut décider de l'évaluer à la compilation ou à l'exécution.

Même lorsqu'il n'y est pas tenu, un compilateur moderne évaluera généralement une expression constante à la compilation lorsque les optimisations sont activées.

Point clé

Le compilateur n'est tenu d'évaluer les expressions constantes à la compilation que dans les contextes qui exigent une expression constante. Dans les autres cas, il peut le faire ou non.

Astuce

La probabilité qu'une expression soit entièrement évaluée à la compilation peut être classée comme suit :

  • Jamais : une expression non constante dont le compilateur ne peut pas déterminer toutes les valeurs à la compilation.
  • Éventuellement : une expression non constante dont le compilateur peut déterminer toutes les valeurs à la compilation (optimisée selon la règle du as-if).
  • Probablement : une expression constante utilisée dans un contexte qui n'exige pas d'expression constante.
  • Toujours : une expression constante utilisée dans un contexte qui exige une expression constante.

Pour les lecteurs avancés

Pourquoi C++ n'exige-t-il pas que toutes les expressions constantes soient évaluées à la compilation ? Il existe au moins deux bonnes raisons :

  1. L'évaluation à la compilation rend le débogage plus difficile. Si notre code contient un calcul bogué évalué à la compilation, nous disposons de peu d'outils pour diagnostiquer le problème. Autoriser l'évaluation à l'exécution des expressions constantes qui n'y sont pas tenues (généralement lorsque les optimisations sont désactivées) permet de déboguer notre code à l'exécution. Pouvoir parcourir pas à pas et inspecter l'état de nos programmes pendant leur exécution peut rendre la recherche de bogues plus simple.
  2. Donner au compilateur la liberté d'optimiser comme il l'entend (ou selon les options du compilateur). Par exemple, un compilateur pourrait proposer une option qui reporte à l'exécution toute évaluation d'expression constante non exigée, afin de réduire les temps de compilation pour les développeurs.

Pourquoi les expressions de compilation doivent-elles être constantes (Facultatif)

Vous vous demandez peut-être pourquoi les expressions de compilation ne peuvent contenir que des objets constants (ainsi que des opérateurs et des fonctions qui peuvent être évalués à la compilation en constantes).

Considérons le programme suivant :

#include <iostream>

int main()
{
    int x { 5 };
    // x est connu du compilateur à ce stade

    std::cin >> x; // lit la valeur de x saisie par l'utilisateur
    // x n'est plus connu du compilateur

    return 0;
}

Au départ, x est initialisé avec la valeur 5. La valeur de x est connue du compilateur à ce stade. Mais ensuite, x reçoit une valeur saisie par l'utilisateur. Le compilateur ne peut pas savoir, à la compilation, quelle valeur l'utilisateur fournira. Au-delà de ce point, la valeur de x n'est donc plus connue du compilateur. L'expression x n'est donc pas toujours évaluable à la compilation, ce qui viole l'exigence selon laquelle une telle expression doit toujours pouvoir être évaluée à la compilation.

Comme les constantes ne peuvent pas voir leur valeur modifiée, une variable constante dont l'initialisateur est évaluable à la compilation aura toujours une valeur connue à la compilation. Cela simplifie les choses.

Les concepteurs du langage auraient pu définir une expression de compilation comme une expression dont toutes les valeurs sont connues actuellement à la compilation (plutôt que comme une expression qui doit toujours pouvoir être évaluée à la compilation). Mais cela aurait considérablement complexifié le compilateur, qui aurait alors dû déterminer à chaque instant quelles variables pourraient prendre une valeur inconnue à la compilation. Ajouter une seule ligne de code (comme std::cin >> x) pourrait casser le programme ailleurs (si x était utilisée dans un contexte exigeant une valeur connue à la compilation).

Quiz

Question n° 1

Pour chaque instruction, indiquez :

  • si l'initialisateur est une expression constante ou non constante ;
  • si la variable est une expression constante ou non constante.

a)

    char a { 'q' };
Solution

'q' est une expression constante, car c'est un littéral.
a est une expression non constante, car elle n'est pas définie comme const.

b)

    const int b { 0 };
Solution

0 est une expression constante, car c'est un littéral.
b est une expression constante, car c'est un type entier const avec un initialisateur qui est une expression constante.

c)

    const double c { 5.0 };
Solution

5.0 est une expression constante, car c'est un littéral.
c est une expression non constante, car elle est définie comme const mais n'est pas de type entier.

Selon la définition d'une constante de compilation, seules les variables const de type entier avec un initialisateur qui est une expression constante sont des constantes de compilation. c est un double, qui n'est pas un type entier : elle ne répond donc pas à cette définition.

d)

    const int d { a * 2 }; // a définie comme char a { 'q' };
Solution

a n'est pas une expression constante, donc a * 2 est une expression non constante.
d est une expression non constante, car son initialisateur n'est pas une expression constante.

e)

    int e { c + 1.0 }; // c définie comme const double c { 5.0 };
Solution

c est une expression non constante, donc c + 1.0 est une expression non constante.
e est une expression non constante, car elle n'est pas définie comme const et n'a pas d'initialisateur qui est une expression constante.

f)

    const int f { d * 2 }; // d définie comme const int d { 0 };
Solution

d et 2 sont des expressions constantes, donc d * 2 est une expression constante.
f est une expression constante, car c'est un type entier const avec un initialisateur qui est une expression constante.

g)

    const int g { getNumber() }; // getNumber renvoie un int par valeur
Solution

getNumber() renvoie une valeur non constante, c'est donc une expression non constante.
g est une expression non constante, car son initialisateur est une expression non constante.

h)
Bonus :

    const int h{};
Solution

{} déclenche l'initialisation par valeur. Il n'y a pas d'initialisateur explicite ici.
h est une expression constante, car c'est un type entier const avec un initialisateur qui est une expression constante (l'initialisation par valeur donne à h la valeur 0, qui est une expression constante).
