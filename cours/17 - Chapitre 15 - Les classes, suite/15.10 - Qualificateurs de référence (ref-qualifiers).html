15.10 — Qualificateurs de référence (ref-qualifiers)

Note de l'auteur

Cette leçon est facultative. Nous vous recommandons de la parcourir rapidement pour vous familiariser avec le sujet, mais une compréhension complète n'est pas nécessaire pour suivre les prochaines leçons.

Dans la leçon 14.7 -- Fonctions membres renvoyant des références vers des membres de données, nous avons vu que l'appel de fonctions d'accès renvoyant des références vers des membres de données peut être dangereux lorsque l'objet implicite est une rvalue. Voici un bref rappel :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    std::string m_name{};

public:
    Employee(std::string_view name): m_name { name } {}
    const std::string& getName() const { return m_name; } //  le getter renvoie une référence constante
};

// createEmployee() renvoie un Employee par valeur (la valeur renvoyée est donc une rvalue)
Employee createEmployee(std::string_view name)
{
    Employee e { name };
    return e;
}

int main()
{
    // Cas 1 : correct : utilisation de la référence renvoyée vers un membre d'un objet rvalue dans la même expression
    std::cout << createEmployee("Frank").getName() << '\n';

    // Cas 2 : incorrect : conservation de la référence renvoyée vers un membre d'un objet rvalue pour une utilisation ultérieure
    const std::string& ref { createEmployee("Garbo").getName() }; // la référence devient pendante lorsque la valeur renvoyée par createEmployee() est détruite
    std::cout << ref << '\n'; // comportement indéfini

    return 0;
}

Dans le cas 2, l'objet rvalue renvoyé par createEmployee("Garbo") est détruit après l'initialisation de ref, ce qui laisse ref référencer un membre de données qui vient d'être détruit. Toute utilisation ultérieure de ref entraîne un comportement indéfini.

Cela pose un véritable dilemme.

  • Si notre fonction getName() renvoie par valeur, c'est sûr lorsque l'objet implicite est une rvalue, mais cela entraîne une copie coûteuse et inutile lorsque l'objet implicite est une lvalue (ce qui est le cas le plus courant).
  • Si notre fonction getName() renvoie par référence constante, c'est efficace (aucune copie de std::string n'est réalisée), mais elle peut être mal utilisée lorsque l'objet implicite est une rvalue (ce qui entraîne un comportement indéfini).

Les fonctions membres étant généralement appelées sur des objets implicites lvalues, le choix conventionnel consiste à renvoyer une référence constante, et simplement à éviter de mal utiliser la référence renvoyée lorsque l'objet implicite est une rvalue.

Qualificateurs de référence (ref-qualifiers)

La racine du problème illustré ci-dessus est que nous voulons qu'une seule fonction serve deux cas différents (celui où l'objet implicite est une lvalue, et celui où il est une rvalue). Ce qui est optimal pour un cas ne l'est pas pour l'autre.

Pour résoudre ce genre de situation, le C++11 a introduit une fonctionnalité peu connue, appelée qualificateur de référence (ref-qualifier), qui permet de surcharger une fonction membre selon que l'appel porte sur un objet implicite lvalue ou rvalue. Grâce à cette fonctionnalité, nous pouvons créer deux versions de getName() : l'une pour le cas où l'objet implicite est une lvalue, et l'autre pour le cas où il est une rvalue.

Commençons par notre version de getName() sans qualificateur de référence :

const std::string& getName() const { return m_name; } // appelable avec des objets implicites lvalue et rvalue

Pour qualifier cette fonction par référence, nous ajoutons le qualificateur & à la surcharge qui ne correspondra qu'aux objets implicites lvalue, et le qualificateur && à la surcharge qui ne correspondra qu'aux objets implicites rvalue :

const std::string& getName() const &  { return m_name; } //  le qualificateur & limite la fonction aux objets implicites lvalue, renvoie par référence
std::string        getName() const && { return m_name; } // le qualificateur && limite la fonction aux objets implicites rvalue, renvoie par valeur

Ces fonctions étant des surcharges distinctes, elles peuvent avoir des types de retour différents ! La surcharge qualifiée par lvalue renvoie une référence constante, tandis que la surcharge qualifiée par rvalue renvoie une valeur.

Voici un exemple complet :

#include <iostream>
#include <string>
#include <string_view>

class Employee
{
private:
    std::string m_name{};

public:
    Employee(std::string_view name): m_name { name } {}

    const std::string& getName() const &  { return m_name; } //  le qualificateur & limite la fonction aux objets implicites lvalue
    std::string        getName() const && { return m_name; } // le qualificateur && limite la fonction aux objets implicites rvalue
};

// createEmployee() renvoie un Employee par valeur (la valeur renvoyée est donc une rvalue)
Employee createEmployee(std::string_view name)
{
    Employee e { name };
    return e;
}

int main()
{
    Employee joe { "Joe" };
    std::cout << joe.getName() << '\n'; // joe est une lvalue, donc cet appel invoque std::string& getName() & (renvoie une référence)

    std::cout << createEmployee("Frank").getName() << '\n'; // Frank est une rvalue, donc cet appel invoque std::string getName() && (produit une copie)

    return 0;
}

Cela nous permet de faire la chose performante lorsque l'objet implicite est une lvalue, et la chose sûre lorsqu'il est une rvalue.

Pour les lecteurs avancés

La surcharge rvalue de getName() ci-dessus peut être sous-optimale en termes de performance lorsque l'objet implicite est un temporaire non constant. Dans ce cas, l'objet implicite va de toute façon être détruit à la fin de l'expression. Plutôt que de faire renvoyer au getter rvalue une copie (potentiellement coûteuse) du membre, nous pouvons lui faire essayer de déplacer le membre (à l'aide de std::move).

Cela se fait en ajoutant la surcharge suivante du getter pour les rvalues non constantes :

        // Si l'objet implicite est une rvalue non constante, utiliser std::move pour tenter de déplacer m_name
    std::string getName() && { return std::move(m_name); }

Cette version peut coexister avec le getter rvalue constant, ou vous pouvez simplement la remplacer par celle-ci (les rvalues constantes étant assez rares).

Nous abordons std::move dans la leçon 22.4 -- std::move.

Quelques remarques sur les fonctions membres qualifiées par référence

Tout d'abord, pour une fonction donnée, les surcharges non qualifiées par référence et les surcharges qualifiées par référence ne peuvent pas coexister. Utilisez l'une ou l'autre.

Ensuite, à l'image de la façon dont une référence constante sur lvalue peut se lier à une rvalue, si seule une fonction qualifiée par lvalue constante existe, elle acceptera aussi bien les objets implicites lvalue que rvalue.

Enfin, l'une ou l'autre des surcharges qualifiées peut être explicitement supprimée (à l'aide de = delete), ce qui interdit d'appeler cette fonction. Par exemple, supprimer la version qualifiée par rvalue empêche d'utiliser la fonction avec des objets implicites rvalue.

Pourquoi ne recommandons-nous pas d'utiliser les qualificateurs de référence ?

Si les qualificateurs de référence sont intéressants, leur utilisation de cette manière présente quelques inconvénients.

  • Ajouter une surcharge rvalue à chaque getter renvoyant une référence encombre la classe, pour se prémunir contre un cas peu fréquent et facilement évitable avec de bonnes habitudes.
  • Une surcharge rvalue qui renvoie par valeur nous oblige à payer le coût d'une copie (ou d'un déplacement) même dans les cas où nous aurions pu utiliser une référence en toute sécurité (par exemple dans le cas 1 de l'exemple du début de la leçon).

De plus :

  • La plupart des développeurs C++ ne connaissent pas cette fonctionnalité (ce qui peut entraîner des erreurs ou des inefficacités à l'utilisation).
  • La bibliothèque standard n'utilise généralement pas cette fonctionnalité.

Pour toutes ces raisons, nous ne recommandons pas l'utilisation des qualificateurs de référence comme bonne pratique. Nous recommandons plutôt de toujours utiliser immédiatement le résultat d'une fonction d'accès, sans conserver les références renvoyées pour une utilisation ultérieure.
