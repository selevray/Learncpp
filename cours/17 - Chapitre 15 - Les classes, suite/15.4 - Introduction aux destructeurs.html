15.4 — Introduction aux destructeurs

Le problème du nettoyage

Imaginons que vous écriviez un programme qui doit envoyer des données sur un réseau. Cependant, établir une connexion avec le serveur coûte cher, donc vous voulez collecter un ensemble de données puis les envoyer toutes d'un coup. Une telle classe pourrait être structurée ainsi :

// Cet exemple ne compilera pas car il est (volontairement) incomplet
class NetworkData
{
private:
    std::string m_serverName{};
    DataStore m_dataQueue{};

public:
    NetworkData(std::string_view serverName)
        : m_serverName { serverName }
    {
    }

    void addData(std::string_view data)
    {
        m_dataQueue.add(data);
    }

    void sendData()
    {
        // se connecter au serveur
        // envoyer toutes les données
        // vider les données
    }
};

int main()
{
    NetworkData n("someipAddress");

    n.addData("somedata1");
    n.addData("somedata2");

    n.sendData();

    return 0;
}

Cependant, cette classe NetworkData présente un problème potentiel. Elle repose sur le fait que sendData() soit explicitement appelée avant l'arrêt du programme. Si l'utilisateur de NetworkData oublie de le faire, les données ne seront pas envoyées au serveur et seront perdues à la fin du programme. Vous pourriez dire : « Ce n'est pas difficile de penser à le faire ! », et dans cet exemple précis, vous auriez raison. Mais considérons un exemple un peu plus complexe, comme cette fonction :

bool someFunction()
{
    NetworkData n("someipAddress");

    n.addData("somedata1");
    n.addData("somedata2");

    if (someCondition)
        return false;

    n.sendData();
    return true;
}

Dans ce cas, si someCondition vaut true, la fonction retourne prématurément et sendData() n'est pas appelée. Cette erreur est plus facile à commettre, car l'appel à sendData() est bien présent : simplement, le programme n'y accède pas dans tous les cas.

Pour généraliser ce problème, les classes qui utilisent une ressource (le plus souvent de la mémoire, mais parfois des fichiers, des bases de données, des connexions réseau, etc.) doivent souvent être explicitement envoyées ou fermées avant la destruction de l'objet qui les utilise. Dans d'autres cas, nous pouvons vouloir effectuer une tenue de registres avant la destruction de l'objet, comme écrire des informations dans un fichier journal ou envoyer une donnée de télémétrie à un serveur. Le terme « nettoyage » désigne souvent l'ensemble des tâches qu'une classe doit accomplir avant la destruction d'un objet de cette classe pour se comporter comme attendu. Si nous devons compter sur l'utilisateur d'une telle classe pour s'assurer que la fonction de nettoyage est appelée avant la destruction de l'objet, nous risquons de rencontrer des erreurs tôt ou tard.

Mais pourquoi exiger cela de l'utilisateur ? Si l'objet est détruit, nous savons qu'un nettoyage doit être effectué à ce moment-là. Ce nettoyage ne devrait-il pas se faire automatiquement ?

Les destructeurs à la rescousse

Dans la leçon 14.9 -- Introduction aux constructeurs, nous avons étudié les constructeurs, des fonctions membres spéciales appelées lors de la création d'un objet d'un type de classe non agrégat. Les constructeurs servent à initialiser les membres et à effectuer toute autre tâche de préparation nécessaire pour que les objets de la classe soient prêts à l'emploi.

De manière analogue, les classes possèdent un autre type de fonction membre spéciale, appelée automatiquement lorsqu'un objet d'un type de classe non agrégat est détruit. Cette fonction s'appelle un destructeur (destructor). Les destructeurs permettent à une classe d'effectuer tout nettoyage nécessaire avant la destruction d'un objet de cette classe.

Nommage des destructeurs

Comme les constructeurs, les destructeurs obéissent à des règles de nommage précises :

  1. Le destructeur doit porter le même nom que la classe, précédé d'un tilde (~).
  2. Le destructeur ne peut pas prendre d'arguments.
  3. Le destructeur n'a pas de type de retour.

Une classe ne peut avoir qu'un seul destructeur.

En général, vous ne devriez pas appeler un destructeur explicitement (il sera appelé automatiquement lorsque l'objet sera détruit), car il est rare que vous ayez besoin de nettoyer un objet plus d'une fois.

Les destructeurs peuvent appeler sans risque d'autres fonctions membres, puisque l'objet n'est détruit qu'après l'exécution du destructeur.

Un exemple de destructeur

#include <iostream>

class Simple
{
private:
    int m_id {};

public:
    Simple(int id)
        : m_id { id }
    {
        std::cout << "Constructing Simple " << m_id << '\n';
    }

    ~Simple() // voici notre destructeur
    {
        std::cout << "Destructing Simple " << m_id << '\n';
    }

    int getID() const { return m_id; }
};

int main()
{
    // Alloue un Simple
    Simple simple1{ 1 };
    {
        Simple simple2{ 2 };
    } // simple2 est détruit ici

    return 0;
} // simple1 est détruit ici

Ce programme produit le résultat suivant :


Constructing Simple 1
Constructing Simple 2
Destructing Simple 2
Destructing Simple 1

Notez que, lorsque chaque objet Simple est détruit, le destructeur est appelé, ce qui affiche un message. « Destructing Simple 1 » est affiché après « Destructing Simple 2 » parce que simple2 a été détruit avant la fin de la fonction, alors que simple1 ne l'a été qu'à la fin de main().

Rappelez-vous que les variables statiques (y compris les variables globales et les variables locales statiques) sont construites au démarrage du programme et détruites à son arrêt.

Amélioration du programme NetworkData

Revenons à notre exemple du début de la leçon : nous pouvons supprimer la nécessité pour l'utilisateur d'appeler explicitement sendData() en faisant appeler cette fonction par un destructeur :

class NetworkData
{
private:
    std::string m_serverName{};
    DataStore m_dataQueue{};

public:
    NetworkData(std::string_view serverName)
        : m_serverName { serverName }
    {
    }

    ~NetworkData()
    {
        sendData(); // s'assurer que toutes les données sont envoyées avant la destruction de l'objet
    }

    void addData(std::string_view data)
    {
        m_dataQueue.add(data);
    }

    void sendData()
    {
        // se connecter au serveur
        // envoyer toutes les données
        // vider les données
    }
};

int main()
{
    NetworkData n("someipAddress");

    n.addData("somedata1");
    n.addData("somedata2");

    return 0;
}

Avec un tel destructeur, notre objet NetworkData enverra toujours les données qu'il contient avant d'être détruit ! Le nettoyage se fait automatiquement, ce qui réduit les risques d'erreurs et le nombre de choses à penser.

Un destructeur implicite

Si un objet d'un type de classe non agrégat ne possède pas de destructeur déclaré par l'utilisateur, le compilateur en génère un dont le corps est vide. Ce destructeur est appelé destructeur implicite (implicit destructor) ; il ne sert en pratique que de marque-place.

Si votre classe n'a pas besoin d'effectuer de nettoyage à sa destruction, vous pouvez ne pas définir de destructeur et laisser le compilateur générer un destructeur implicite pour votre classe.

Mise en garde concernant la fonction std::exit()

Dans la leçon 8.12 -- Arrêts (quitter votre programme prématurément), nous avons vu que la fonction std::exit() peut être utilisée pour terminer immédiatement votre programme. Lorsque le programme se termine immédiatement, il s'arrête simplement. Les variables locales ne sont pas détruites au préalable et, pour cette raison, aucun destructeur n'est appelé. Soyez prudent si vous comptez sur vos destructeurs pour effectuer un travail de nettoyage nécessaire dans un tel cas.

Pour les lecteurs avancés

Les exceptions non gérées provoquent également la fin du programme et peuvent ne pas dérouler la pile avant de le faire. Si le déroulement de la pile (stack unwinding) n'a pas lieu, les destructeurs ne seront pas appelés avant la terminaison du programme.
