15.2 — Classes et fichiers d'en-tête

Toutes les classes que nous avons écrites jusqu'à présent étaient suffisamment simples pour que nous ayons pu implémenter leurs fonctions membres directement dans la définition de la classe. Par exemple, voici une classe Date simple dont toutes les fonctions membres sont définies à l'intérieur de la définition de la classe Date :

#include <iostream>

class Date
{
private:
    int m_year{};
    int m_month{};
    int m_day{};

public:
    Date(int year, int month, int day)
        : m_year { year }
        , m_month { month }
        , m_day { day}
    {
    }

    void print() const { std::cout << "Date(" << m_year << ", " << m_month << ", " << m_day << ")\n"; }

    int getYear() const { return m_year; }
    int getMonth() const { return m_month; }
    int getDay() const { return m_day; }
};

int main()
{
    Date d { 2015, 10, 14 };
    d.print();

    return 0;
}

Cependant, à mesure que les classes deviennent plus longues et plus complexes, le fait de placer toutes les définitions des fonctions membres à l'intérieur de la classe peut la rendre plus difficile à gérer et à utiliser. Pour utiliser une classe déjà écrite, il suffit de comprendre son interface publique (les fonctions membres publiques), et non le fonctionnement interne de la classe. Les implémentations des fonctions membres encombrent l'interface publique avec des détails qui ne sont pas pertinents pour l'utilisation de la classe.

Pour remédier à cela, C++ nous permet de séparer la partie « déclaration » de la classe de la partie « implémentation » en définissant les fonctions membres en dehors de la définition de la classe.

Voici la même classe Date que ci-dessus, avec le constructeur et la fonction membre print() définis en dehors de la définition de la classe. Notez que les prototypes de ces fonctions membres restent présents dans la définition de la classe (car ces fonctions doivent être déclarées dans la définition du type de la classe), mais que l'implémentation a été déplacée à l'extérieur :

#include <iostream>

class Date
{
private:
    int m_year{};
    int m_month{};
    int m_day{};

public:
    Date(int year, int month, int day); // déclaration du constructeur

    void print() const; // déclaration de la fonction print

    int getYear() const { return m_year; }
    int getMonth() const { return m_month; }
    int getDay() const  { return m_day; }
};

Date::Date(int year, int month, int day) // définition du constructeur
    : m_year{ year }
    , m_month{ month }
    , m_day{ day }
{
}

void Date::print() const // définition de la fonction print
{
    std::cout << "Date(" << m_year << ", " << m_month << ", " << m_day << ")\n";
};

int main()
{
    const Date d{ 2015, 10, 14 };
    d.print();

    return 0;
}

Les fonctions membres peuvent être définies en dehors de la définition de la classe, exactement comme les fonctions non membres. La seule différence est que nous devons faire précéder le nom de la fonction membre du nom du type de la classe (ici, Date::) afin que le compilateur sache que nous définissons un membre de ce type de classe et non une fonction non membre.

Notez que nous avons laissé les fonctions d'accès définies à l'intérieur de la définition de la classe. Comme les fonctions d'accès ne comportent généralement qu'une seule ligne, les définir à l'intérieur de la classe n'encombre que très peu le code, alors que les déplacer à l'extérieur ajouterait de nombreuses lignes supplémentaires. Pour cette raison, les définitions des fonctions d'accès (et des autres fonctions triviales d'une seule ligne) sont souvent laissées à l'intérieur de la définition de la classe.

Placer les définitions de classes dans un fichier d'en-tête

Si vous définissez une classe dans un fichier source (.cpp), cette classe n'est utilisable que dans ce fichier source particulier. Dans les programmes plus importants, il est courant de vouloir utiliser les classes que nous écrivons dans plusieurs fichiers source.

Dans la leçon 2.11 -- Fichiers d'en-tête, vous avez appris que vous pouvez placer des déclarations de fonctions dans des fichiers d'en-tête, puis #inclure ces déclarations de fonctions dans plusieurs fichiers de code (voire plusieurs projets). Les classes ne font pas exception. Les définitions de classes peuvent être placées dans des fichiers d'en-tête, puis #incluses dans tous les autres fichiers qui souhaitent utiliser le type de la classe.

Contrairement aux fonctions, qui n'ont besoin que d'une déclaration anticipée pour être utilisées, le compilateur doit généralement voir la définition complète d'une classe (ou de tout type défini par le programme) pour pouvoir utiliser ce type. En effet, le compilateur doit connaître la manière dont les membres sont déclarés afin de s'assurer qu'ils sont utilisés correctement, et il doit pouvoir calculer la taille des objets de ce type pour les instancier. C'est pourquoi nos fichiers d'en-tête contiennent généralement la définition complète d'une classe plutôt qu'une simple déclaration anticipée.

Nommer les fichiers d'en-tête et de code de vos classes

Le plus souvent, les classes sont définies dans des fichiers d'en-tête portant le même nom que la classe, et les fonctions membres définies en dehors de la classe sont placées dans un fichier .cpp portant également le même nom que la classe.

Voici à nouveau notre classe Date, répartie entre un fichier .cpp et un fichier .h :

Date.h :

#ifndef DATE_H
#define DATE_H

class Date
{
private:
    int m_year{};
    int m_month{};
    int m_day{};

public:
    Date(int year, int month, int day);

    void print() const;

    int getYear() const { return m_year; }
    int getMonth() const { return m_month; }
    int getDay() const { return m_day; }
};

#endif

Date.cpp :

#include "Date.h"

Date::Date(int year, int month, int day) // définition du constructeur
    : m_year{ year }
    , m_month{ month }
    , m_day{ day }
{
}

void Date::print() const // définition de la fonction print
{
    std::cout << "Date(" << m_year << ", " << m_month << ", " << m_day << ")\n";
};

Désormais, tout autre fichier d'en-tête ou de code qui souhaite utiliser la classe Date peut simplement faire #include "Date.h". Notez que Date.cpp doit aussi être compilé dans tout projet qui utilise Date.h, afin que l'éditeur de liens (linker) puisse relier les appels aux fonctions membres à leurs définitions.

Bonne pratique

Privilégiez la placement des définitions de vos classes dans un fichier d'en-tête portant le même nom que la classe. Les fonctions membres triviales (comme les fonctions d'accès, les constructeurs au corps vide, etc.) peuvent être définies à l'intérieur de la définition de la classe.

Privilégiez la définition des fonctions membres non triviales dans un fichier source portant le même nom que la classe.

Définir une classe dans un fichier d'en-tête ne viole-t-il pas la règle de définition unique si l'en-tête est #inclus plus d'une fois ?

Les types sont exemptés de la partie de la règle de définition unique (ODR, One-Definition Rule) qui stipule qu'il ne peut y avoir qu'une seule définition par programme. Il n'y a donc aucun problème à #inclure des définitions de classes dans plusieurs unités de traduction. Si cela posait problème, les classes ne seraient pas d'une grande utilité.

Inclure la définition d'une classe plus d'une fois dans une même unité de traduction reste en revanche une violation de l'ODR. Cependant, les gardes d'inclusion (ou #pragma once) empêchent que cela se produise.

Fonctions membres en ligne (inline)

Les fonctions membres ne sont pas exemptées de l'ODR. Vous vous demandez donc peut-être comment nous évitons les violations de l'ODR lorsque des fonctions membres sont définies dans un fichier d'en-tête (qui peut ensuite être inclus dans plusieurs unités de traduction).

Les fonctions membres définies à l'intérieur de la définition de la classe sont implicitement en ligne (inline). Les fonctions en ligne sont exemptées de la partie de la règle de définition unique selon laquelle il ne peut y avoir qu'une seule définition par programme.

Les fonctions membres définies en dehors de la définition de la classe ne sont pas implicitement en ligne (et sont donc soumises à la partie de la règle de définition unique selon laquelle il ne peut y avoir qu'une seule définition par programme). C'est pourquoi ces fonctions sont généralement définies dans un fichier de code (où elles n'auront qu'une seule définition dans l'ensemble du programme).

Autrement, les fonctions membres définies en dehors de la définition de la classe peuvent rester dans le fichier d'en-tête si elles sont rendues en ligne (à l'aide du mot-clé inline). Voici à nouveau notre en-tête Date.h, avec les fonctions membres définies en dehors de la classe marquées comme inline :

Date.h :

#ifndef DATE_H
#define DATE_H

#include <iostream>

class Date
{
private:
    int m_year{};
    int m_month{};
    int m_day{};

public:
    Date(int year, int month, int day);

    void print() const;

    int getYear() const { return m_year; }
    int getMonth() const { return m_month; }
    int getDay() const { return m_day; }
};

inline Date::Date(int year, int month, int day) // désormais en ligne
    : m_year{ year }
    , m_month{ month }
    , m_day{ day }
{
}

inline void Date::print() const // désormais en ligne
{
    std::cout << "Date(" << m_year << ", " << m_month << ", " << m_day << ")\n";
};

#endif

Ce Date.h peut être inclus dans plusieurs unités de traduction sans poser de problème.

Point clé

Les fonctions définies à l'intérieur de la définition de la classe sont implicitement en ligne, ce qui leur permet d'être #incluses dans plusieurs fichiers de code sans violer l'ODR.

Les fonctions définies en dehors de la définition de la classe ne sont pas implicitement en ligne. Elles peuvent le devenir à l'aide du mot-clé inline.

Expansion en ligne des fonctions membres

Le compilateur doit pouvoir voir la définition complète d'une fonction pour effectuer l'expansion en ligne. Le plus souvent, ces fonctions (par exemple les fonctions d'accès) sont définies à l'intérieur de la définition de la classe. Cependant, si vous souhaitez définir une fonction membre en dehors de la définition de la classe tout en la rendant éligible à l'expansion en ligne, vous pouvez la définir comme une fonction en ligne juste sous la définition de la classe (dans le même fichier d'en-tête). Ainsi, la définition de la fonction est accessible à quiconque #inclut l'en-tête.

Alors pourquoi ne pas tout mettre dans un fichier d'en-tête ?

Vous pourriez être tenté de placer toutes vos définitions de fonctions membres dans le fichier d'en-tête, soit à l'intérieur de la définition de la classe, soit sous forme de fonctions en ligne juste après la définition de la classe. Bien que cela compile, cette approche présente quelques inconvénients.

Premièrement, comme mentionné plus haut, définir les membres à l'intérieur de la définition de la classe encombre celle-ci.

Deuxièmement, si vous modifiez le code de l'en-tête, vous devrez recompiler tous les fichiers qui incluent cet en-tête. Cela peut avoir un effet en cascade, où une modification mineure oblige à recompiler l'ensemble du programme. Le coût de la recompilation peut varier considérablement : un petit projet ne prendra peut-être qu'une minute ou moins pour se construire, alors qu'un grand projet commercial peut prendre plusieurs heures.

À l'inverse, si vous modifiez le code d'un fichier .cpp, seul ce fichier .cpp doit être recompilé. Par conséquent, lorsque c'est possible, il est généralement préférable de placer le code non trivial dans un fichier .cpp.

Il existe quelques cas où il peut être judicieux de déroger à la bonne pratique consistant à placer la définition de la classe dans un en-tête et les fonctions membres non triviales dans un fichier de code.

Premièrement, pour une petite classe utilisée dans un seul fichier de code et non destinée à une réutilisation générale, vous pouvez préférer définir la classe (et toutes ses fonctions membres) directement dans le seul fichier .cpp où elle est utilisée. Cela permet de montrer clairement que la classe n'est utilisée que dans ce fichier et qu'elle n'est pas destinée à un usage plus large. Vous pourrez toujours déplacer la classe dans des fichiers d'en-tête et de code séparés plus tard, si vous souhaitez l'utiliser dans plusieurs fichiers, ou si les définitions de la classe et de ses fonctions membres encombrent votre fichier source.

Deuxièmement, si une classe ne possède qu'un petit nombre de fonctions membres non triviales peu susceptibles de changer, créer un fichier .cpp ne contenant qu'une ou deux définitions peut ne pas valoir la peine (car cela encombre le projet). Dans ce cas, il peut être préférable de rendre les fonctions membres inline et de les placer sous la définition de la classe dans l'en-tête.

Troisièmement, en C++ moderne, les classes ou bibliothèques sont de plus en plus souvent distribuées « en tout-en-un dans un en-tête » (header-only), ce qui signifie que tout le code de la classe ou de la bibliothèque est placé dans un fichier d'en-tête. Cela vise principalement à faciliter la distribution et l'utilisation de ces fichiers : un en-tête doit simplement être #inclus, alors qu'un fichier de code doit être explicitement ajouté à chaque projet qui l'utilise, afin d'être compilé. Si vous créez intentionnellement une classe ou une bibliothèque tout-en-un dans un en-tête pour la distribuer, toutes les fonctions membres non triviales peuvent être rendues inline et placées dans le fichier d'en-tête sous la définition de la classe.

Enfin, pour les classes templates, les fonctions membres template définies en dehors de la classe sont presque toujours définies dans le fichier d'en-tête, sous la définition de la classe. Comme pour les fonctions template non membres, le compilateur doit voir la définition complète du template pour l'instancier. Nous aborderons les fonctions membres template dans la leçon 15.5 -- Classes template avec fonctions membres.

Note de l'auteur

Dans les prochaines leçons, la plupart de nos classes seront définies dans un seul fichier .cpp, avec toutes les fonctions implémentées directement dans la définition de la classe. Ceci permet de garder les exemples concis et faciles à compiler soi-même. Dans les projets réels, il est beaucoup plus courant de placer les classes dans leurs propres fichiers de code et d'en-tête, et vous devriez vous habituer à procéder ainsi.

Arguments par défaut des fonctions membres

Dans la leçon 11.5 -- Arguments par défaut, nous avons présenté la bonne pratique concernant les arguments par défaut des fonctions non membres : « Si la fonction possède une déclaration anticipée (en particulier dans un fichier d'en-tête), placez l'argument par défaut à cet endroit. Sinon, placez-le dans la définition de la fonction. »

Les fonctions membres étant toujours déclarées (ou définies) dans la définition de la classe, la bonne pratique pour les fonctions membres est en réalité plus simple : placez toujours l'argument par défaut à l'intérieur de la définition de la classe.

Bonne pratique

Placez les arguments par défaut des fonctions membres à l'intérieur de la définition de la classe.

Bibliothèques

Tout au long de vos programmes, vous avez utilisé des classes faisant partie de la bibliothèque standard, comme std::string. Pour utiliser ces classes, il vous suffit d'#inclure l'en-tête correspondant (par exemple #include <string>). Notez que vous n'avez pas eu besoin d'ajouter de fichiers de code (comme string.cpp ou iostream.cpp) à vos projets.

Les fichiers d'en-tête fournissent les déclarations dont le compilateur a besoin pour vérifier que les programmes que vous écrivez sont syntaxiquement corrects. En revanche, les implémentations des classes appartenant à la bibliothèque standard C++ se trouvent dans un fichier précompilé, lié automatiquement lors de l'étape d'édition de liens. Vous ne voyez jamais ce code.

De nombreux paquets logiciels open source fournissent à la fois des fichiers .h et .cpp que vous compilez dans votre programme. En revanche, la plupart des bibliothèques commerciales ne fournissent que des fichiers .h et un fichier de bibliothèque précompilé. Plusieurs raisons à cela : 1) il est plus rapide de lier une bibliothèque précompilée que de la recompiler à chaque besoin, 2) une seule copie d'une bibliothèque précompilée peut être partagée par de nombreuses applications, alors que le code compilé est intégré dans chaque exécutable qui l'utilise (ce qui gonfle la taille des fichiers), et 3) pour des raisons de propriété intellectuelle (on ne souhaite pas que l'on vole son code).

Nous verrons comment inclure des bibliothèques précompilées tierces dans vos projets dans l'annexe.

Bien que vous ne créerez probablement pas et ne distribuerez pas vos propres bibliothèques avant un certain temps, séparer vos classes en fichiers d'en-tête et fichiers source est non seulement une bonne pratique, mais facilite aussi la création de vos propres bibliothèques personnalisées. La création de bibliothèques dépasse le cadre de ces tutoriels, mais séparer déclaration et implémentation en est un prérequis si vous voulez distribuer des binaires précompilés.
