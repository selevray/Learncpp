9.6 — Assert et static_assert

Dans une fonction qui prend des paramètres, l'appelant peut passer des arguments syntaxiquement valides mais dénués de sens sur le plan sémantique. Par exemple, dans la leçon précédente (9.4 -- Détecter et gérer les erreurs), nous avons présenté la fonction suivante :

void printDivision(int x, int y)
{
    if (y != 0)
        std::cout << static_cast<double>(x) / y;
    else
        std::cerr << "Error: Could not divide by zero\n";
}

Cette fonction vérifie explicitement si y vaut 0, puisque la division par zéro est une erreur sémantique qui fera planter le programme si elle est exécutée.

Dans la leçon précédente, nous avons évoqué plusieurs façons de traiter ce type de problème, notamment arrêter le programme ou ignorer les instructions fautives.

Ces deux options posent cependant problème. Si un programme ignore des instructions à cause d'une erreur, il échoue en silence. Pendant l'écriture et le débogage des programmes, les échecs silencieux sont particulièrement néfastes, car ils masquent les vrais problèmes. Même si nous affichons un message d'erreur, celui-ci peut se perdre parmi les autres sorties du programme, et il peut être difficile de savoir d'où il provient ou comment les conditions qui l'ont déclenché sont apparues. Certaines fonctions sont appelées des dizaines, voire des centaines de fois, et si un seul de ces appels pose problème, il peut être difficile de déterminer lequel.

Si le programme se termine (via std::exit), nous perdons la pile d'appels et toutes les informations de débogage qui pourraient nous aider à isoler le problème. std::abort est une meilleure option dans ces cas, car le développeur peut généralement démarrer le débogage à l'endroit où le programme a été interrompu.

Préconditions, invariants et postconditions

En programmation, une précondition (precondition) est une condition qui doit être vraie avant l'exécution d'une section de code (généralement le corps d'une fonction). Dans l'exemple précédent, notre vérification y != 0 est une précondition qui garantit que y a une valeur non nulle avant la division par y.

Les préconditions d'une fonction sont idéalement placées en début de fonction, avec un retour anticipé (early return) pour revenir à l'appelant si la précondition n'est pas satisfaite. Par exemple :

void printDivision(int x, int y)
{
    if (y == 0) // gère le cas
    {
        std::cerr << "Error: Could not divide by zero\n";
        return; // renvoie l'utilisateur à l'appelant
    }

    // Nous savons maintenant que y != 0
    std::cout << static_cast<double>(x) / y;
}

Lecture facultative

Ceci est parfois appelé le « motif du videur » (« bouncer pattern »), car on est immédiatement éjecté de la fonction dès qu'une erreur est détectée.

Ce motif présente deux avantages majeurs :

  1. Tous vos cas de test sont regroupés en début de fonction, et le test et le code qui gère l'erreur sont ensemble.
  2. Vous obtenez moins d'imbrication.

Voici à quoi ressemble la version sans ce motif :

void printDivision(int x, int y)
{
    if (y != 0)
    {
        std::cout << static_cast<double>(x) / y;
    }
    else
    {
        std::cerr << "Error: Could not divide by zero\n";
        return; // renvoie l'utilisateur à l'appelant
    }
}

Cette version est strictement moins bonne, car le test et le code qui gère l'erreur sont plus éloignés et il y a davantage d'imbrication.

Un invariant (invariant) est une condition qui doit être vraie pendant l'exécution d'une section de code. Cette notion sert souvent pour les boucles, où le corps de la boucle ne s'exécute que tant que l'invariant reste vrai.

Pour les lecteurs avancés

Nous parlons d'un type courant d'invariant, l'« invariant de classe », dans la leçon 14.2 -- Introduction aux classes.

De même, une postcondition (postcondition) est une condition qui doit être vraie après l'exécution d'une section de code. Notre fonction n'a aucune postcondition.

Assertions

Utiliser une instruction conditionnelle pour détecter un paramètre invalide (ou pour valider une autre hypothèse), afficher un message d'erreur et terminer le programme est une méthode si courante de détection de problèmes que C++ fournit un raccourci pour le faire.

Une assertion (assertion) est une expression qui doit être vraie, sauf en cas de bogue dans le programme. Si l'expression vaut true, l'instruction d'assertion ne fait rien. Si l'expression conditionnelle vaut false, un message d'erreur est affiché et le programme est terminé (via std::abort). Ce message contient généralement le texte de l'expression qui a échoué, ainsi que le nom du fichier de code et le numéro de ligne de l'assertion. Il est ainsi très facile de savoir non seulement quel était le problème, mais aussi où il s'est produit dans le code. Cela facilite énormément le débogage.

Point clé

Les assertions servent à détecter les erreurs pendant le développement et le débogage.

Lorsqu'une assertion vaut false, votre programme est immédiatement arrêté. Vous pouvez alors utiliser des outils de débogage pour examiner l'état du programme et déterminer pourquoi l'assertion a échoué. En remontant le fil, vous pouvez ensuite trouver et corriger le problème rapidement.

Sans assertion pour détecter l'erreur et échouer, une telle erreur provoquerait probablement un dysfonctionnement plus tard. Dans ce cas, il peut être très difficile de déterminer où les choses tournent mal, ou quelle est la véritable cause du problème.

En C++, les assertions à l'exécution sont implémentées par la macro du préprocesseur assert, définie dans l'en-tête <cassert>.

#include <cassert> // pour assert()
#include <cmath> // pour std::sqrt
#include <iostream>

double calculateTimeUntilObjectHitsGround(double initialHeight, double gravity)
{
  assert(gravity > 0.0); // L'objet n'atteindra pas le sol sans gravité positive.

  if (initialHeight <= 0.0)
  {
    // L'objet est déjà au sol. Ou enterré.
    return 0.0;
  }

  return std::sqrt((2.0 * initialHeight) / gravity);
}

int main()
{
  std::cout << "Took " << calculateTimeUntilObjectHitsGround(100.0, -9.8) << " second(s)\n";

  return 0;
}

Lorsque le programme appelle calculateTimeUntilObjectHitsGround(100.0, -9.8), assert(gravity > 0.0) vaut false, ce qui déclenche l'assertion. Cela affiche un message semblable à celui-ci :


dropsimulator: src/main.cpp:6: double calculateTimeUntilObjectHitsGround(double, double): Assertion 'gravity > 0.0' failed.

Le message exact varie selon le compilateur utilisé.

Bien que les assertions servent le plus souvent à valider les paramètres de fonction, elles peuvent être utilisées partout où vous voulez vérifier qu'une condition est vraie.

Nous vous avons déjà recommandé d'éviter les macros du préprocesseur, mais assert fait partie des rares macros considérées comme acceptables. Nous vous encourageons à utiliser les instructions assert généreusement dans votre code.

Point clé

Les assertions valent mieux que les commentaires, car elles documentent une condition tout en la faisant respecter. Un commentaire peut devenir obsolète lorsque le code change et que le commentaire n'est pas mis à jour. Une assertion devenue obsolète provoque une erreur de correction du code, si bien que les développeurs sont moins enclins à la laisser traîner.

Rendre vos instructions assert plus descriptives

Il arrive que les expressions d'assertion ne soient pas très descriptives. Considérons l'instruction suivante :

assert(found);

Si cette assertion se déclenche, elle affichera :


Assertion failed: found, file C:\\VCProjects\\Test.cpp, line 34

Qu'est-ce que cela signifie réellement ? Il est clair que found valait false (puisque l'assertion s'est déclenchée), mais qu'est-ce qui n'a pas été trouvé ? Il faudrait aller regarder le code pour le savoir.

Heureusement, une petite astuce permet de rendre vos assertions plus descriptives. Il suffit d'ajouter une chaîne littérale reliée par un ET logique :

assert(found && "Car could not be found in database");

Voici pourquoi cela fonctionne : une chaîne littérale s'évalue toujours à true en tant que booléen. Ainsi, si found vaut false, false && true vaut false. Si found vaut true, true && true vaut true. Le ET logique avec une chaîne littérale n'affecte donc pas l'évaluation de l'assertion.

En revanche, lorsque l'assertion se déclenche, la chaîne littérale est incluse dans le message :


Assertion failed: found && "Car could not be found in database", file C:\\VCProjects\\Test.cpp, line 34

Cela vous donne un contexte supplémentaire sur ce qui a mal tourné.

Utiliser les assertions pour les fonctionnalités non implémentées

Les assertions servent aussi parfois à documenter des cas non implémentés, parce qu'ils n'étaient pas nécessaires au moment où le programmeur a écrit le code :

assert(moved && "Need to handle case where student was just moved to another classroom");

Ainsi, si un développeur rencontre une situation où ce cas est nécessaire, le code échouera avec un message d'erreur utile, et le programmeur pourra alors déterminer comment implémenter ce cas.

NDEBUG

La macro assert entraîne un petit coût en performance à chaque vérification de sa condition. De plus, les assertions ne devraient (idéalement) jamais être rencontrées dans le code de production, car votre code doit déjà avoir été testé en profondeur. C'est pourquoi la plupart des développeurs préfèrent que les assertions ne soient actives que dans les versions de débogage. C++ fournit un moyen intégré de désactiver les assertions dans le code de production : si la macro du préprocesseur NDEBUG est définie, la macro assert est désactivée.

La plupart des IDE définissent NDEBUG par défaut, dans les paramètres du projet, pour les configurations de version (release). Par exemple, dans Visual Studio, les définitions de préprocesseur suivantes sont données au niveau du projet : WIN32;NDEBUG;_CONSOLE. Si vous utilisez Visual Studio et souhaitez que vos assertions se déclenchent dans les versions de release, vous devrez retirer NDEBUG de ce paramètre.

Si vous utilisez un IDE ou un système de build qui ne définit pas automatiquement NDEBUG dans la configuration de release, vous devrez l'ajouter manuellement dans les paramètres du projet ou de compilation.

Astuce

À des fins de test, vous pouvez activer ou désactiver les assertions dans une unité de traduction donnée. Pour cela, placez l'une des lignes suivantes seule sur sa ligne, avant tout #include : #define NDEBUG (pour désactiver les assertions) ou #undef NDEBUG (pour les activer). Veillez à ne pas terminer la ligne par un point-virgule.

Par exemple :

#define NDEBUG // désactive les assertions (doit être placé avant tout #include)
#include <cassert>
#include <iostream>

int main()
{
    assert(false); // ne se déclenchera pas, car les assertions sont désactivées dans cette unité de traduction
    std::cout << "Hello, world!\n";

    return 0;
}

static_assert

C++ possède aussi un autre type d'assertion, appelé static_assert. Une static_assert (static_assert) est une assertion vérifiée à la compilation plutôt qu'à l'exécution ; une static_assert en échec provoque une erreur de compilation. Contrairement à assert, déclarée dans l'en-tête <cassert>, static_assert est un mot-clé : aucun en-tête n'a besoin d'être inclus pour l'utiliser.

Une static_assert prend la forme suivante :


static_assert(condition, diagnostic_message)

Si la condition n'est pas vraie, le message de diagnostic est affiché. Voici un exemple d'utilisation de static_assert pour vérifier la taille de types :

static_assert(sizeof(long) == 8, "long must be 8 bytes");
static_assert(sizeof(int) >= 4, "int must be at least 4 bytes");

int main()
{
    return 0;
}

Sur la machine de l'auteur, la compilation produit l'erreur suivante :


1>c:\consoleapplication1\main.cpp(19): error C2338: long must be 8 bytes

Quelques remarques utiles sur static_assert :

  • Comme static_assert est évaluée par le compilateur, la condition doit être une expression constante.
  • static_assert peut être placée n'importe où dans le fichier de code (même dans l'espace de noms global).
  • static_assert n'est pas désactivée dans les versions de release (contrairement à assert normal).
  • Comme c'est le compilateur qui effectue l'évaluation, une static_assert n'a aucun coût à l'exécution.

Avant C++17, le message de diagnostic doit être fourni comme second paramètre. Depuis C++17, fournir un message de diagnostic est facultatif.

Bonne pratique

Privilégiez static_assert à assert() chaque fois que possible.

Assertions et gestion des erreurs

Les assertions et la gestion des erreurs se ressemblent suffisamment pour que leurs rôles puissent être confondus ; clarifions donc.

Les assertions servent à détecter les erreurs de programmation pendant le développement, en documentant des hypothèses sur des événements qui ne devraient jamais se produire. Et s'ils se produisent, c'est la faute du programmeur. Les assertions ne permettent pas de récupérer d'une erreur (après tout, si quelque chose ne devrait jamais arriver, il n'y a pas besoin de s'en remettre). Comme les asserts sont généralement retirées à la compilation dans les versions de release, vous pouvez en placer beaucoup sans vous soucier des performances ; il y a donc peu de raisons de ne pas les utiliser généreusement.

La gestion des erreurs sert à traiter avec élégance les cas qui peuvent se produire (même rarement) dans une version de release. Il peut s'agir de problèmes récupérables (où le programme peut continuer à fonctionner) ou non récupérables (où le programme doit s'arrêter, mais où nous pouvons au moins afficher un message d'erreur soigné et nous assurer que tout est correctement nettoyé). La détection et la gestion des erreurs ont un coût à l'exécution comme un coût de développement.

Dans certains cas, ce qu'il faut faire est moins clair. Considérons une fonction comme celle-ci :

double getInverse(double x)
{
    return 1.0 / x;
}

Si x vaut 0.0, cette fonction se comportera mal, et nous devons nous en prémunir. Faut-il utiliser une assertion ou une gestion des erreurs ? La meilleure réponse est peut-être « les deux ».

Pendant le débogage, si cette fonction est appelée avec x égal à 0.0, cela indique un bogue quelque part dans notre code, et nous voulons le savoir immédiatement. Une assertion est donc tout à fait appropriée.

Cependant, cela pourrait aussi raisonnablement se produire dans une version de release (par exemple sur un chemin obscur que nous n'avons pas testé). Si l'assertion est retirée à la compilation et que nous n'avons pas de gestion d'erreur, cette fonction renverra une valeur inattendue et se comportera mal. Dans ce cas, il vaut probablement mieux détecter la situation et la traiter.

Notre fonction finale pourrait ressembler à ceci :

double getInverse(double x)
{
    assert(x != 0.0);
    if (x == 0.0)
       // gérer l'erreur d'une manière ou d'une autre (par exemple en lançant une exception)

    return 1.0 / x;
}

Astuce

Compte tenu de cela, nous vous suggérons ce qui suit :

  • Utilisez les assertions pour détecter les erreurs de programmation, les hypothèses incorrectes ou les conditions qui ne devraient jamais survenir dans un code correct. Il revient au programmeur de les corriger, donc nous voulons les repérer au plus tôt.
  • Utilisez la gestion des erreurs pour les problèmes que nous prévoyons de rencontrer pendant le fonctionnement normal de votre programme.
  • Utilisez les deux lorsqu'un événement ne devrait pas se produire, mais que nous voulons échouer proprement s'il se produit.

Quelques limites et mises en garde sur les assertions

Les assertions présentent quelques pièges et limites. Premièrement, l'assertion elle-même peut être mal écrite. Dans ce cas, elle signalera une erreur là où il n'y en a aucune, ou ne signalera pas un bogue qui existe bel et bien.

Deuxièmement, les expressions de vos assert() ne doivent pas avoir d'effets de bord, car l'expression d'assertion n'est pas évaluée lorsque NDEBUG est définie (et l'effet de bord n'est donc pas appliqué). Sinon, ce que vous testez dans une configuration de débogage ne sera pas identique à ce qui s'exécute dans une configuration de release (en supposant que vous livrez avec NDEBUG).

Notez également que la fonction abort() termine le programme immédiatement, sans possibilité d'effectuer un nettoyage supplémentaire (par exemple fermer un fichier ou une base de données). Pour cette raison, les assertions ne doivent être utilisées que dans les cas où une corruption est peu probable si le programme se termine de façon inattendue.
