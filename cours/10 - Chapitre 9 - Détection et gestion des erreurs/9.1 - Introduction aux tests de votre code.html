9.1 — Introduction aux tests de votre code

Vous avez écrit un programme, il compile, et il semble même fonctionner ! Et maintenant ?

Cela dépend. Si vous avez écrit votre programme pour qu'il ne soit exécuté qu'une seule fois puis jeté, alors vous avez terminé. Dans ce cas, peu importe qu'il ne fonctionne pas dans tous les cas : s'il fonctionne pour le seul cas dont vous aviez besoin, et que vous ne comptez l'exécuter qu'une fois, c'est fini.

Si votre programme est entièrement linéaire (il ne contient aucune condition, comme des instructions if ou des instructions switch), ne prend aucune entrée et produit la bonne réponse, alors vous avez probablement terminé. Dans ce cas, vous avez déjà testé le programme entier en l'exécutant et en validant sa sortie. Vous voudrez peut-être compiler et exécuter le programme sur plusieurs systèmes différents pour vérifier qu'il se comporte de manière cohérente (si ce n'est pas le cas, vous avez probablement fait quelque chose qui produit un comportement indéfini et qui, par hasard, fonctionne quand même sur votre système initial).

Mais il est plus probable que vous ayez écrit un programme que vous comptez exécuter de nombreuses fois, qui utilise des boucles et une logique conditionnelle, et qui accepte une forme de saisie utilisateur. Vous avez peut-être écrit des fonctions réutilisables dans de futurs programmes. Vous avez peut-être connu un peu de dérive du périmètre (scope creep), c'est-à-dire l'ajout de nouvelles fonctionnalités qui n'étaient pas prévues à l'origine. Vous envisagez peut-être même de distribuer ce programme à d'autres personnes, qui sont susceptibles d'essayer des choses auxquelles vous n'avez pas pensé. Dans ce cas, vous devriez vraiment vérifier que votre programme fonctionne comme vous le pensez dans un large éventail de conditions, et cela demande des tests proactifs.

Le fait que votre programme ait fonctionné pour un jeu de données ne signifie pas qu'il fonctionnera correctement dans tous les cas.

Le test logiciel (aussi appelé validation logicielle, ou software testing en anglais) est le processus qui consiste à déterminer si le logiciel fonctionne réellement comme prévu.

Le défi des tests

Avant de parler de manières pratiques de tester votre code, voyons pourquoi il est difficile de tester votre programme de façon exhaustive.

Considérons ce programme simple :

#include <iostream>

void compare(int x, int y)
{
    if (x > y)
        std::cout << x << " is greater than " << y << '\n'; // case 1
    else if (x < y)
        std::cout << x << " is less than " << y << '\n'; // case 2
    else
        std::cout << x << " is equal to " << y << '\n'; // case 3
}

int main()
{
    std::cout << "Enter a number: ";
    int x{};
    std::cin >> x;

    std::cout << "Enter another number: ";
    int y{};
    std::cin >> y;

    compare(x, y);

    return 0;
}

En supposant un entier de 4 octets, tester explicitement ce programme avec chaque combinaison possible d'entrées nécessiterait de l'exécuter 18 446 744 073 709 551 616 fois (environ 18 quintillions). Ce n'est évidemment pas une tâche réalisable !

Chaque fois que nous demandons une saisie utilisateur, ou que nous avons une condition dans notre code, nous multiplions le nombre de chemins d'exécution possibles de notre programme par un certain facteur. Pour tous sauf les programmes les plus simples, tester explicitement chaque combinaison d'entrées devient impossible presque immédiatement.

Votre intuition devrait vous dire qu'il n'est pas nécessaire d'exécuter le programme ci-dessus 18 quintillions de fois pour s'assurer qu'il fonctionne. Vous pouvez raisonnablement conclure que si le cas 1 fonctionne pour une paire de valeurs x et y où x > y, il devrait fonctionner pour toute paire où x > y. Dans ces conditions, il apparaît que nous n'avons besoin d'exécuter ce programme qu'environ trois fois (une fois pour chacun des trois cas de la fonction compare()) pour avoir une grande confiance dans son bon fonctionnement. Il existe d'autres astuces similaires qui permettent de réduire considérablement le nombre de fois où nous devons tester quelque chose, afin de rendre les tests gérables.

On pourrait écrire beaucoup de choses sur les méthodologies de test ; on pourrait même y consacrer un chapitre entier. Mais comme il ne s'agit pas d'un sujet propre au C++, nous nous en tiendrons à une introduction brève et informelle, du point de vue de vous, en tant que développeur, qui testez votre propre code. Dans les sous-sections suivantes, nous parlerons de quelques éléments pratiques auxquels vous devriez penser en testant votre code.

Testez vos programmes par petites parties

Imaginez un constructeur automobile qui conçoit une voiture-concept personnalisée. Lequel des deux scénarios suivants pensez-vous qu'il mette en œuvre ? a) Construire (ou acheter) et tester chaque composant individuellement avant de l'installer. Une fois qu'un composant a fait ses preuves, l'intégrer à la voiture et le retester pour s'assurer que l'intégration s'est bien passée. À la fin, tester la voiture complète, comme validation finale que tout semble correct. b) Assembler une voiture avec tous les composants d'un seul coup, puis tester l'ensemble pour la première fois à la toute fin.

Il semble évident que l'option a) est le meilleur choix. Et pourtant, de nombreux programmeurs débutants écrivent du code selon le modèle b) !

Dans le cas b), si l'une des pièces de la voiture ne fonctionne pas comme prévu, le mécanicien doit diagnostiquer l'ensemble de la voiture pour déterminer ce qui ne va pas, et le problème peut se trouver n'importe où. Un symptôme peut avoir de nombreuses causes : la voiture ne démarre pas à cause d'une bougie défectueuse, d'une batterie, d'une pompe à essence ou d'autre chose ? Cela fait perdre beaucoup de temps à identifier précisément où se trouvent les problèmes et à décider quoi faire. Et si un problème est découvert, les conséquences peuvent être désastreuses : un changement dans un domaine peut provoquer des « effets de ricochet » (des modifications) à plusieurs autres endroits. Par exemple, une pompe à essence trop petite peut conduire à repenser le moteur, ce qui conduit à repenser le châssis. Dans le pire des cas, vous pourriez finir par redessiner une grande partie de la voiture simplement pour accommoder ce qui, au départ, n'était qu'un petit problème !

Dans le cas a), l'entreprise teste au fur et à mesure. Si un composant est défectueux dès sa sortie d'emballage, elle le saura immédiatement et pourra le réparer ou le remplacer. Rien n'est intégré à la voiture tant qu'il n'a pas fait ses preuves seul, et cette pièce est à nouveau testée dès qu'elle est intégrée à la voiture. Ainsi, les problèmes inattendus sont découverts le plus tôt possible, alors qu'ils sont encore petits et faciles à corriger.

Au moment où l'on assemble enfin la voiture complète, on devrait avoir une confiance raisonnable dans son bon fonctionnement : après tout, toutes les pièces ont été testées isolément, puis lors de leur première intégration. Il reste possible que des problèmes inattendus apparaissent à ce stade, mais ce risque est minimisé grâce à tous les tests effectués auparavant.

L'analogie ci-dessus s'applique aussi aux programmes, même si, pour une raison ou une autre, les programmeurs débutants ne s'en rendent souvent pas compte. Vous avez tout intérêt à écrire de petites fonctions (ou de petites classes), puis à les compiler et à les tester immédiatement. Ainsi, si vous faites une erreur, vous saurez qu'elle se trouve forcément dans la petite quantité de code que vous avez modifiée depuis la dernière compilation et le dernier test. Il y a alors moins d'endroits où chercher, et beaucoup moins de temps passé au débogage.

Tester une petite partie de votre code isolément pour s'assurer que cette « unité » de code est correcte s'appelle le test unitaire (unit testing). Chaque test unitaire (unit test) est conçu pour vérifier qu'un comportement particulier de l'unité est correct.

Bonne pratique

Écrivez votre programme en petites unités bien définies (fonctions ou classes), compilez souvent et testez votre code au fur et à mesure.

Si le programme est court et accepte une saisie utilisateur, essayer diverses saisies peut suffire. Mais à mesure que les programmes s'allongent, cela devient de moins en moins suffisant, et il est plus utile de tester individuellement les fonctions ou les classes avant de les intégrer au reste du programme.

Alors, comment tester notre code par unités ?

Test informel

Une façon de tester du code consiste à effectuer des tests informels pendant que vous écrivez le programme. Après avoir écrit une unité de code (une fonction, une classe, ou un autre « paquet » de code distinct), vous pouvez écrire du code pour tester l'unité qui vient d'être ajoutée, puis supprimer ce test une fois qu'il réussit. Par exemple, pour la fonction isLowerVowel() suivante, vous pourriez écrire le code suivant :

#include <iostream>

// We want to test the following function
// For simplicity, we'll ignore that 'y' is sometimes counted as a vowel
bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

int main()
{
    // So here's our temporary tests to validate it works
    std::cout << isLowerVowel('a') << '\n'; // temporary test code, should produce 1
    std::cout << isLowerVowel('q') << '\n'; // temporary test code, should produce 0

    return 0;
}

Si les résultats sont 1 et 0, alors tout est bon. Vous savez que votre fonction fonctionne pour quelques cas de base, et vous pouvez raisonnablement en déduire, en regardant le code, qu'elle fonctionnera pour les cas que vous n'avez pas testés (‘e’, ‘i’, ‘o’ et ‘u’). Vous pouvez donc supprimer ce code de test temporaire et poursuivre la programmation.

Conserver vos tests

Même si l'écriture de tests temporaires est un moyen rapide et simple de tester du code, elle ne tient pas compte du fait qu'à un moment donné, vous voudrez peut-être tester à nouveau ce même code. Vous avez peut-être modifié une fonction pour lui ajouter une nouvelle capacité, et voulez vous assurer que vous n'avez rien cassé de ce qui fonctionnait déjà. Pour cette raison, il peut être plus judicieux de conserver vos tests afin qu'ils puissent être relancés plus tard. Par exemple, au lieu de supprimer votre code de test temporaire, vous pouvez le déplacer dans une fonction testVowel() :

#include <iostream>

bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

// Not called from anywhere right now
// But here if you want to retest things later
void testVowel()
{
    std::cout << isLowerVowel('a') << '\n'; // temporary test code, should produce 1
    std::cout << isLowerVowel('q') << '\n'; // temporary test code, should produce 0
}

int main()
{
    return 0;
}

Au fur et à mesure que vous créez de nouveaux tests, vous pouvez simplement les ajouter à la fonction testVowel().

Automatiser vos fonctions de test

Un problème de la fonction de test ci-dessus est qu'elle vous oblige à vérifier manuellement les résultats lorsque vous l'exécutez. Au pire, cela vous oblige à vous souvenir de la réponse attendue (en supposant que vous ne l'ayez pas documentée), et à comparer manuellement les résultats obtenus avec les résultats attendus.

Nous pouvons faire mieux en écrivant une fonction de test qui contient à la fois les tests ET les réponses attendues, et qui les compare à notre place.

#include <iostream>

bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

// returns the number of the test that failed, or 0 if all tests passed
int testVowel()
{
    if (!isLowerVowel('a')) return 1;
    if (isLowerVowel('q')) return 2;

    return 0;
}

int main()
{
    int result { testVowel() };
    if (result != 0)
        std::cout << "testVowel() test " << result << " failed.\n";
    else
        std::cout << "testVowel() tests passed.\n";

    return 0;
}

Désormais, vous pouvez appeler testVowel() à tout moment pour prouver à nouveau que vous n'avez rien cassé, et la routine de test fera tout le travail à votre place, en renvoyant soit un signal « tout est bon » (valeur de retour 0), soit le numéro du test qui n'a pas réussi, afin que vous puissiez examiner pourquoi il ne fonctionne plus. C'est particulièrement utile lorsque vous revenez modifier du code ancien, pour vous assurer que vous n'avez pas accidentellement cassé quoi que ce soit !

Pour les lecteurs avancés

Une meilleure méthode consiste à utiliser assert, qui interrompt le programme avec un message d'erreur si un test échoue. Nous n'avons alors pas besoin de créer et de gérer des numéros de cas de test.

#include <cassert> // for assert
#include <cstdlib> // for std::abort
#include <iostream>

bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

// Program will halt on any failed test case
int testVowel()
{
#ifdef NDEBUG
    // If NDEBUG is defined, asserts are compiled out.
    // Since this function requires asserts to not be compiled out, we'll terminate the program if this function is called when NDEBUG is defined.
    std::cerr << "Tests run with NDEBUG defined (asserts compiled out)";
    std::abort();
#endif

    assert(isLowerVowel('a'));
    assert(isLowerVowel('e'));
    assert(isLowerVowel('i'));
    assert(isLowerVowel('o'));
    assert(isLowerVowel('u'));
    assert(!isLowerVowel('b'));
    assert(!isLowerVowel('q'));
    assert(!isLowerVowel('y'));
    assert(!isLowerVowel('z'));

    return 0;
}

int main()
{
    testVowel();

    // If we reached here, all tests must have passed
    std::cout << "All tests succeeded\n";

    return 0;
}

Nous traitons assert dans la leçon 9.6 -- Assert et static_assert.

Frameworks de tests unitaires

Comme écrire des fonctions qui exercent d'autres fonctions est si courant et si utile, il existe des frameworks entiers (appelés frameworks de tests unitaires, ou unit testing frameworks) conçus pour simplifier l'écriture, la maintenance et l'exécution des tests unitaires. Comme ils font appel à des logiciels tiers, nous ne les aborderons pas ici, mais vous devez savoir qu'ils existent.

Tests d'intégration

Une fois chacune de vos unités testée isolément, elles peuvent être intégrées à votre programme et retestées pour s'assurer qu'elles ont été intégrées correctement. C'est ce qu'on appelle un test d'intégration (integration test). Les tests d'intégration tendent à être plus compliqués : pour l'instant, exécuter votre programme quelques fois et vérifier par sondage le comportement de l'unité intégrée suffira.
