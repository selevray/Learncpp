22.1 — Introduction aux pointeurs intelligents et à la sémantique de déplacement

Considérons une fonction dans laquelle nous allouons dynamiquement une valeur :

void someFunction()
{
    Resource* ptr = new Resource(); // Resource est une struct ou une classe

    // faire quelque chose avec ptr ici

    delete ptr;
}

Bien que ce code paraisse assez simple, il est facile d'oublier de désallouer ptr. Même si vous pensez à supprimer ptr à la fin de la fonction, il existe de nombreuses façons pour que ptr ne soit pas supprimé si la fonction se termine prématurément. Cela peut se produire avec un retour anticipé :

#include <iostream>

void someFunction()
{
    Resource* ptr = new Resource();

    int x;
    std::cout << "Enter an integer: ";
    std::cin >> x;

    if (x == 0)
        return; // la fonction se termine prématurément, et ptr ne sera pas supprimé !

    // faire quelque chose avec ptr ici

    delete ptr;
}

ou via une exception levée :

#include <iostream>

void someFunction()
{
    Resource* ptr = new Resource();

    int x;
    std::cout << "Enter an integer: ";
    std::cin >> x;

    if (x == 0)
        throw 0; // la fonction se termine prématurément, et ptr ne sera pas supprimé !

    // faire quelque chose avec ptr ici

    delete ptr;
}

Dans les deux programmes ci-dessus, l'instruction de retour anticipé ou de levée d'exception s'exécute, ce qui fait terminer la fonction sans que la variable ptr ne soit supprimée. En conséquence, la mémoire allouée pour la variable ptr est maintenant perdue (fuite mémoire), et cette fuite se reproduira chaque fois que cette fonction sera appelée et se terminera prématurément.

Au fond, ce type de problème survient parce que les variables pointeurs n'ont pas de mécanisme intrinsèque pour se nettoyer elles-mêmes.

Les classes de pointeurs intelligents à la rescousse ?

L'un des grands avantages des classes est qu'elles contiennent des destructeurs, exécutés automatiquement lorsqu'un objet de la classe sort de sa portée. Ainsi, si vous allouez (ou acquérez) de la mémoire dans votre constructeur, vous pouvez la désallouer dans votre destructeur, et être certain que la mémoire sera libérée lorsque l'objet de la classe sera détruit (qu'il sorte de sa portée, qu'il soit explicitement supprimé, etc.). C'est au cœur du paradigme de programmation RAII dont nous avons parlé dans la leçon 19.3 -- Destructeurs.

Peut-on donc utiliser une classe pour nous aider à gérer et nettoyer nos pointeurs ? Oui !

Considérons une classe dont le seul rôle serait de contenir et de « posséder » un pointeur qui lui est transmis, puis de désallouer ce pointeur lorsque l'objet de la classe sort de sa portée. Tant que les objets de cette classe ne sont créés que comme variables locales, nous pouvons garantir que la classe sortira bien de sa portée (quels que soient le moment et la manière dont nos fonctions se terminent), et que le pointeur qu'elle possède sera détruit.

Voici une première ébauche de cette idée :

#include <iostream>

template <typename T>
class Auto_ptr1
{
    T* m_ptr {};
public:
    // Transmettre un pointeur à « posséder » via le constructeur
    Auto_ptr1(T* ptr=nullptr)
        :m_ptr(ptr)
    {
    }

    // Le destructeur s'assurera que la mémoire est désallouée
    ~Auto_ptr1()
    {
        delete m_ptr;
    }

    // Surcharger l'opérateur de déréférencement et operator-> pour pouvoir utiliser Auto_ptr1 comme m_ptr.
    T& operator*() const { return *m_ptr; }
    T* operator->() const { return m_ptr; }
};

// Une classe d'exemple pour prouver que ce qui précède fonctionne
class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    Auto_ptr1<Resource> res(new Resource()); // Notez l'allocation de mémoire ici

        // ... mais aucun delete explicite n'est nécessaire

    // Notez également que nous utilisons <Resource>, et non <Resource*>
        // C'est parce que nous avons défini m_ptr avec le type T* (et non T)

    return 0;
} // res sort de sa portée ici, et détruit pour nous la Resource allouée

Ce programme affiche :


Resource acquired
Resource destroyed

Examinons le fonctionnement de ce programme et de cette classe. Tout d'abord, nous créons dynamiquement une Resource, et nous la passons en paramètre à notre classe Auto_ptr1 templatisée. À partir de ce moment, notre variable Auto_ptr1 res possède cet objet Resource (Auto_ptr1 entretient une relation de composition avec m_ptr). Comme res est déclarée comme variable locale et a une portée de bloc, elle sortira de sa portée à la fin du bloc et sera détruite (pas de risque d'oublier de la désallouer). Et comme il s'agit d'une classe, lors de sa destruction, le destructeur d'Auto_ptr1 sera appelé. Ce destructeur veillera à supprimer le pointeur Resource qu'il détient !

Tant qu'Auto_ptr1 est définie comme variable locale (à durée de stockage automatique, d'où la partie « Auto » du nom de la classe), la Resource sera garantie d'être détruite à la fin du bloc dans lequel elle est déclarée, quelle que soit la façon dont la fonction se termine (même en cas de terminaison anticipée).

Une telle classe est appelée un pointeur intelligent (smart pointer). Un pointeur intelligent est une classe de composition conçue pour gérer la mémoire allouée dynamiquement et garantir que cette mémoire sera libérée lorsque l'objet pointeur intelligent sort de sa portée. (Par analogie, les pointeurs natifs sont parfois appelés « pointeurs bêtes » (dumb pointers) car ils ne peuvent pas se nettoyer eux-mêmes.)

Revenons maintenant à notre exemple someFunction() ci-dessus, et montrons comment une classe de pointeur intelligent peut résoudre notre problème :

#include <iostream>

template <typename T>
class Auto_ptr1
{
    T* m_ptr {};
public:
    // Transmettre un pointeur à « posséder » via le constructeur
    Auto_ptr1(T* ptr=nullptr)
        :m_ptr(ptr)
    {
    }

    // Le destructeur s'assurera que la mémoire est désallouée
    ~Auto_ptr1()
    {
        delete m_ptr;
    }

    // Surcharger l'opérateur de déréférencement et operator-> pour pouvoir utiliser Auto_ptr1 comme m_ptr.
    T& operator*() const { return *m_ptr; }
    T* operator->() const { return m_ptr; }
};

// Une classe d'exemple pour prouver que ce qui précède fonctionne
class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
    void sayHi() { std::cout << "Hi!\n"; }
};

void someFunction()
{
    Auto_ptr1<Resource> ptr(new Resource()); // ptr possède maintenant la Resource

    int x;
    std::cout << "Enter an integer: ";
    std::cin >> x;

    if (x == 0)
        return; // la fonction se termine prématurément

    // faire quelque chose avec ptr ici
    ptr->sayHi();
}

int main()
{
    someFunction();

    return 0;
}

Si l'utilisateur saisit un entier non nul, le programme ci-dessus affiche :


Resource acquired
Hi!
Resource destroyed

Si l'utilisateur saisit zéro, le programme ci-dessus se termine prématurément en affichant :


Resource acquired
Resource destroyed

Notez que, même dans le cas où l'utilisateur saisit zéro et où la fonction se termine prématurément, la Resource est tout de même correctement désallouée.

Comme la variable ptr est une variable locale, ptr sera détruite lorsque la fonction se terminera (quelle que soit la façon dont elle se termine). Et comme le destructeur d'Auto_ptr1 nettoie la Resource, nous avons l'assurance qu'elle sera correctement libérée.

Un défaut critique

La classe Auto_ptr1 comporte un défaut critique, caché derrière du code généré automatiquement. Avant de poursuivre la lecture, essayez de l'identifier. Nous attendons…

(Indice : pensez aux parties d'une classe qui sont générées automatiquement si vous ne les fournissez pas.)

(Musique de Jeopardy)

Le temps est écoulé.

Plutôt que de vous le dire, nous allons vous le montrer. Considérez le programme suivant :

#include <iostream>

// Identique à ci-dessus
template <typename T>
class Auto_ptr1
{
    T* m_ptr {};
public:
    Auto_ptr1(T* ptr=nullptr)
        :m_ptr(ptr)
    {
    }

    ~Auto_ptr1()
    {
        delete m_ptr;
    }

    T& operator*() const { return *m_ptr; }
    T* operator->() const { return m_ptr; }
};

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    Auto_ptr1<Resource> res1(new Resource());
    Auto_ptr1<Resource> res2(res1); // Alternativement, n'initialisez pas res2 puis affectez res2 = res1;

    return 0;
} // res1 et res2 sortent de leur portée ici

Ce programme affiche :


Resource acquired
Resource destroyed
Resource destroyed

Très probablement (mais pas nécessairement), votre programme plantera à ce stade. Voyez-vous le problème ? Comme nous n'avons fourni ni constructeur de copie ni opérateur d'affectation, C++ en fournit un à notre place. Et les fonctions qu'il fournit effectuent des copies superficielles (shallow copies). Ainsi, lorsque nous initialisons res2 avec res1, les deux variables Auto_ptr1 pointent vers la même Resource. Quand res2 sort de sa portée, elle supprime la ressource, laissant res1 avec un pointeur pendouillant (dangling pointer). Lorsque res1 tente de supprimer sa Resource (déjà supprimée), il en résulte un comportement indéfini (probablement un plantage) !

Vous rencontreriez un problème similaire avec une fonction comme celle-ci :

void passByValue(Auto_ptr1<Resource> res)
{
}

int main()
{
    Auto_ptr1<Resource> res1(new Resource());
    passByValue(res1);

    return 0;
}

Dans ce programme, res1 est copiée par valeur dans le paramètre res, de sorte que res1.m_ptr et res.m_ptr contiennent la même adresse.

Lorsque res est détruite à la fin de la fonction, res1.m_ptr reste pendouillant. Lorsque res1.m_ptr sera supprimé plus tard, il en résultera un comportement indéfini.

Ce n'est clairement pas acceptable. Comment remédier à cela ?

Une solution consisterait à définir et supprimer explicitement le constructeur de copie et l'opérateur d'affectation, ce qui empêcherait toute copie. Cela résoudrait le cas du passage par valeur (ce qui est une bonne chose, nous ne devrions de toute façon probablement pas passer ces objets par valeur).

Mais comment alors renvoyer un Auto_ptr1 depuis une fonction vers l'appelant ?

??? generateResource()
{
     Resource* r{ new Resource() };
     return Auto_ptr1(r);
}

Nous ne pouvons pas renvoyer notre Auto_ptr1 par référence, car l'Auto_ptr1 locale sera détruite à la fin de la fonction, et l'appelant se retrouverait avec une référence pendouillante. Nous pourrions renvoyer le pointeur r sous la forme d'un Resource*, mais nous risquerions alors d'oublier de supprimer r plus tard, ce qui est précisément la raison même d'utiliser des pointeurs intelligents. Cette option est donc à écarter. Renvoyer l'Auto_ptr1 par valeur est la seule option sensée, mais on aboutit alors à des copies superficielles, des pointeurs dupliqués et des plantages.

Une autre option consisterait à surcharger le constructeur de copie et l'opérateur d'affectation pour effectuer des copies profondes (deep copies). De cette façon, nous éviterions au moins d'avoir des pointeurs multiples vers le même objet. Mais la copie peut être coûteuse (et peut ne pas être souhaitable, voire même possible), et nous ne voulons pas créer de copies inutiles d'objets simplement pour renvoyer un Auto_ptr1 depuis une fonction. De plus, l'initialisation ou l'affectation d'un pointeur natif ne copie pas l'objet pointé, alors pourquoi attendrions-nous un comportement différent des pointeurs intelligents ?

Que faire alors ?

La sémantique de déplacement

Et si, au lieu de faire en sorte que notre constructeur de copie et notre opérateur d'affectation copient le pointeur (« sémantique de copie »), nous transférions plutôt la propriété du pointeur de l'objet source vers l'objet destination ? C'est l'idée centrale de la sémantique de déplacement (move semantics). La sémantique de déplacement signifie que la classe transfère la propriété de l'objet plutôt que d'en créer une copie.

Mettons à jour notre classe Auto_ptr1 pour montrer comment cela peut se faire :

#include <iostream>

template <typename T>
class Auto_ptr2
{
    T* m_ptr {};
public:
    Auto_ptr2(T* ptr=nullptr)
        :m_ptr(ptr)
    {
    }

    ~Auto_ptr2()
    {
        delete m_ptr;
    }

    // Un constructeur de copie qui implémente la sémantique de déplacement
    Auto_ptr2(Auto_ptr2& a) // remarque : non const
    {
        // Nous n'avons pas besoin de supprimer m_ptr ici. Ce constructeur n'est appelé que lors de la création d'un nouvel objet, et m_ptr ne peut pas avoir été défini auparavant.
        m_ptr = a.m_ptr; // transférer notre pointeur natif de la source vers notre objet local
        a.m_ptr = nullptr; // s'assurer que la source ne possède plus le pointeur
    }

    // Un opérateur d'affectation qui implémente la sémantique de déplacement
    Auto_ptr2& operator=(Auto_ptr2& a) // remarque : non const
    {
        if (&a == this)
            return *this;

        delete m_ptr; // s'assurer d'abord de désallouer tout pointeur que la destination détient déjà
        m_ptr = a.m_ptr; // puis transférer notre pointeur natif de la source vers l'objet local
        a.m_ptr = nullptr; // s'assurer que la source ne possède plus le pointeur
        return *this;
    }

    T& operator*() const { return *m_ptr; }
    T* operator->() const { return m_ptr; }
    bool isNull() const { return m_ptr == nullptr; }
};

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    Auto_ptr2<Resource> res1(new Resource());
    Auto_ptr2<Resource> res2; // Démarre à nullptr

    std::cout << "res1 is " << (res1.isNull() ? "null\n" : "not null\n");
    std::cout << "res2 is " << (res2.isNull() ? "null\n" : "not null\n");

    res2 = res1; // res2 prend la propriété, res1 est mis à null

    std::cout << "Ownership transferred\n";

    std::cout << "res1 is " << (res1.isNull() ? "null\n" : "not null\n");
    std::cout << "res2 is " << (res2.isNull() ? "null\n" : "not null\n");

    return 0;
}

Ce programme affiche :


Resource acquired
res1 is not null
res2 is null
Ownership transferred
res1 is null
res2 is not null
Resource destroyed

Notez que notre opérateur= surchargé a transféré la propriété de m_ptr de res1 vers res2 ! Par conséquent, nous n'obtenons pas de copies dupliquées du pointeur, et tout est proprement nettoyé.

Rappel

Supprimer un nullptr ne pose aucun problème, car cela ne fait rien.

std::auto_ptr, et pourquoi c'était une mauvaise idée

Le moment est opportun pour parler de std::auto_ptr. std::auto_ptr, introduit en C++98 et supprimé en C++17, a été la première tentative de C++ d'offrir un pointeur intelligent standardisé. std::auto_ptr a choisi d'implémenter la sémantique de déplacement exactement comme la classe Auto_ptr2 le fait.

Cependant, std::auto_ptr (et notre classe Auto_ptr2) présente plusieurs problèmes qui rendent son utilisation dangereuse.

Premièrement, comme std::auto_ptr implémente la sémantique de déplacement via le constructeur de copie et l'opérateur d'affectation, le passage d'un std::auto_ptr par valeur à une fonction fera transférer votre ressource vers le paramètre de la fonction (et elle sera détruite à la fin de la fonction, lorsque les paramètres de celle-ci sortiront de leur portée). Puis, lorsque vous accéderez à votre argument auto_ptr depuis l'appelant (sans vous rendre compte qu'il a été transféré et supprimé), vous déréférencerez soudainement un pointeur nul. Plantage !

Deuxièmement, std::auto_ptr supprime toujours son contenu à l'aide d'un delete non tableau. Cela signifie que auto_ptr ne fonctionne pas correctement avec les tableaux alloués dynamiquement, car il utilise le mauvais type de désallocation. Pire encore, il ne vous empêchera pas de lui passer un tableau dynamique, qu'il gérera alors incorrectement, provoquant des fuites mémoire.

Enfin, auto_ptr ne s'entend pas bien avec beaucoup d'autres classes de la bibliothèque standard, dont la plupart des conteneurs et des algorithmes. Cela vient du fait que ces classes de la bibliothèque standard supposent que, lorsqu'elles copient un élément, il s'agit réellement d'une copie et non d'un déplacement.

En raison des inconvénients mentionnés ci-dessus, std::auto_ptr a été déprécié en C++11 et supprimé en C++17.

Aller de l'avant

Le problème fondamental de la conception de std::auto_ptr est qu'avant C++11, le langage C++ ne disposait tout simplement d'aucun mécanisme permettant de distinguer la « sémantique de copie » de la « sémantique de déplacement ». Redéfinir la sémantique de copie pour implémenter la sémantique de déplacement conduit à des cas limites étranges et à des bugs involontaires. Par exemple, vous pouvez écrire res1 = res2 sans savoir du tout si res2 sera modifié ou non !

C'est pourquoi, en C++11, la notion de « déplacement » a été formellement définie, et la « sémantique de déplacement » a été ajoutée au langage pour bien distinguer la copie du déplacement. Maintenant que nous avons posé le contexte expliquant pourquoi la sémantique de déplacement peut être utile, nous explorerons ce sujet tout au long du reste de ce chapitre. Nous corrigerons également notre classe Auto_ptr2 en utilisant la sémantique de déplacement.

En C++11, std::auto_ptr a été remplacé par plusieurs autres types de pointeurs intelligents « compatibles avec le déplacement » : std::unique_ptr, std::weak_ptr et std::shared_ptr. Nous explorerons également les deux plus populaires d'entre eux : unique_ptr (qui est un remplacement direct de auto_ptr) et shared_ptr.
