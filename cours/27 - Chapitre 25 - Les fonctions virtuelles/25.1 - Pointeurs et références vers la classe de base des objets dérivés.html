25.1 — Pointeurs et références vers la classe de base des objets dérivés

Dans le chapitre précédent, vous avez appris à utiliser l'héritage pour dériver de nouvelles classes à partir de classes existantes. Dans ce chapitre, nous allons nous concentrer sur l'un des aspects les plus importants et les plus puissants de l'héritage : les fonctions virtuelles.

Mais avant de discuter de ce que sont les fonctions virtuelles, commençons par poser le contexte et expliquer pourquoi nous en avons besoin.

Dans le chapitre sur la construction des classes dérivées, vous avez appris que lorsque vous créez une classe dérivée, elle est composée de plusieurs parties : une partie pour chaque classe dont elle hérite, et une partie pour elle-même.

Par exemple, voici un cas simple :

#include <string_view>

class Base
{
protected:
    int m_value {};

public:
    Base(int value)
        : m_value{ value }
    {
    }

    std::string_view getName() const { return "Base"; }
    int getValue() const { return m_value; }
};

class Derived: public Base
{
public:
    Derived(int value)
        : Base{ value }
    {
    }

    std::string_view getName() const { return "Derived"; }
    int getValueDoubled() const { return m_value * 2; }
};

Lorsque nous créons un objet Derived, il contient une partie Base (construite en premier) et une partie Derived (construite en second). Rappelez-vous que l'héritage implique une relation est-un (is-a) entre deux classes. Comme un Derived est un Base, il est logique que Derived contienne une partie Base.

Pointeurs, références et classes dérivées

Il devrait être assez intuitif de pouvoir définir des pointeurs et des références de type Derived vers des objets Derived :

#include <iostream>

int main()
{
    Derived derived{ 5 };
    std::cout << "derived is a " << derived.getName() << " and has value " << derived.getValue() << '\n';

    Derived& rDerived{ derived };
    std::cout << "rDerived is a " << rDerived.getName() << " and has value " << rDerived.getValue() << '\n';

    Derived* pDerived{ &derived };
    std::cout << "pDerived is a " << pDerived->getName() << " and has value " << pDerived->getValue() << '\n';

    return 0;
}

Ce programme produit la sortie suivante :


derived is a Derived and has value 5
rDerived is a Derived and has value 5
pDerived is a Derived and has value 5

Cependant, comme Derived possède une partie Base, une question plus intéressante est de savoir si C++ nous autorise à définir un pointeur ou une référence de type Base vers un objet Derived. La réponse est oui !

#include <iostream>

int main()
{
    Derived derived{ 5 };

    // Ces deux lignes sont légales !
    Base& rBase{ derived }; // rBase est une référence lvalue (et non une référence rvalue)
    Base* pBase{ &derived };

    std::cout << "derived is a " << derived.getName() << " and has value " << derived.getValue() << '\n';
    std::cout << "rBase is a " << rBase.getName() << " and has value " << rBase.getValue() << '\n';
    std::cout << "pBase is a " << pBase->getName() << " and has value " << pBase->getValue() << '\n';

    return 0;
}

Ce programme produit le résultat suivant :


derived is a Derived and has value 5
rBase is a Base and has value 5
pBase is a Base and has value 5

Ce résultat n'est peut-être pas tout à fait celui que vous attendiez au premier abord !

En effet, comme rBase et pBase sont une référence et un pointeur de type Base, ils ne peuvent voir que les membres de Base (ou ceux des classes dont Base hérite). Ainsi, même si Derived::getName() masque (cache) Base::getName() pour les objets Derived, la référence et le pointeur de type Base ne peuvent pas voir Derived::getName(). Par conséquent, ils appellent Base::getName(), ce qui explique pourquoi rBase et pBase indiquent qu'ils sont un Base et non un Derived.

Notez que cela signifie également qu'il est impossible d'appeler Derived::getValueDoubled() à l'aide de rBase ou pBase. Ils ne peuvent rien voir de ce qui est défini dans Derived.

Voici un autre exemple, un peu plus complexe, sur lequel nous nous appuierons dans la prochaine leçon :

#include <iostream>
#include <string_view>
#include <string>

class Animal
{
protected:
    std::string m_name;

    // Ce constructeur est protégé car
    // nous ne voulons pas que l'on crée directement des objets Animal,
    // mais nous voulons quand même que les classes dérivées puissent l'utiliser.
    Animal(std::string_view name)
        : m_name{ name }
    {
    }

    // Pour empêcher le découpage (slicing, abordé plus tard)
    Animal(const Animal&) = delete;
    Animal& operator=(const Animal&) = delete;

public:
    std::string_view getName() const { return m_name; }
    std::string_view speak() const { return "???"; }
};

class Cat: public Animal
{
public:
    Cat(std::string_view name)
        : Animal{ name }
    {
    }

    std::string_view speak() const { return "Meow"; }
};

class Dog: public Animal
{
public:
    Dog(std::string_view name)
        : Animal{ name }
    {
    }

    std::string_view speak() const { return "Woof"; }
};

int main()
{
    const Cat cat{ "Fred" };
    std::cout << "cat is named " << cat.getName() << ", and it says " << cat.speak() << '\n';

    const Dog dog{ "Garbo" };
    std::cout << "dog is named " << dog.getName() << ", and it says " << dog.speak() << '\n';

    const Animal* pAnimal{ &cat };
    std::cout << "pAnimal is named " << pAnimal->getName() << ", and it says " << pAnimal->speak() << '\n';

    pAnimal = &dog;
    std::cout << "pAnimal is named " << pAnimal->getName() << ", and it says " << pAnimal->speak() << '\n';

    return 0;
}

Ce programme produit le résultat suivant :


cat is named Fred, and it says Meow
dog is named Garbo, and it says Woof
pAnimal is named Fred, and it says ???
pAnimal is named Garbo, and it says ???

On retrouve ici le même problème. Comme pAnimal est un pointeur vers Animal, il ne peut voir que la partie Animal de la classe. Par conséquent, pAnimal->speak() appelle Animal::speak() au lieu de Dog::speak() ou Cat::speak().

Utilisation des pointeurs et des références vers des classes de base

Vous pourriez maintenant dire : « Ces exemples semblent assez absurdes. Pourquoi définir un pointeur ou une référence vers la classe de base d'un objet dérivé alors que je peux simplement utiliser l'objet dérivé ? » Il existe en fait plusieurs bonnes raisons.

Tout d'abord, supposons que vous vouliez écrire une fonction qui affiche le nom et le cri d'un animal. Sans utiliser de pointeur vers une classe de base, vous devriez l'écrire à l'aide de fonctions surchargées, comme ceci :

void report(const Cat& cat)
{
    std::cout << cat.getName() << " says " << cat.speak() << '\n';
}

void report(const Dog& dog)
{
    std::cout << dog.getName() << " says " << dog.speak() << '\n';
}

Ce n'est pas très difficile, mais imaginez ce qui se passerait si nous avions 30 types d'animaux au lieu de 2. Il faudrait écrire 30 fonctions presque identiques ! De plus, si vous ajoutiez un nouveau type d'animal, il faudrait écrire une nouvelle fonction pour celui-ci également. C'est une énorme perte de temps, d'autant que la seule véritable différence est le type du paramètre.

En revanche, comme Cat et Dog dérivent de Animal, Cat et Dog possèdent une partie Animal. Il est donc logique de pouvoir écrire quelque chose comme ceci :

void report(const Animal& rAnimal)
{
    std::cout << rAnimal.getName() << " says " << rAnimal.speak() << '\n';
}

Cela nous permettrait de passer en argument n'importe quelle classe dérivée de Animal, même celles que nous aurions créées après avoir écrit la fonction ! Au lieu d'une fonction par classe dérivée, nous obtenons une seule fonction qui fonctionne avec toutes les classes dérivées de Animal !

Le problème est, bien sûr, que comme rAnimal est une référence vers Animal, rAnimal.speak() appellera Animal::speak() au lieu de la version dérivée de speak().

En passant…

Nous pourrions aussi utiliser une fonction modèle (template) pour réduire le nombre de fonctions surchargées à écrire :

template <typename T>
void report(const T& rAnimal)
{
    std::cout << rAnimal.getName() << " says " << rAnimal.speak() << '\n';
}

Et bien que cela fonctionne, cette approche pose ses propres problèmes :

  1. Il n'est pas clair de savoir quel type T est censé représenter, puisque nous avons perdu la documentation indiquant que T est destiné à être un Animal.
  2. Cette fonction ne garantit pas que T est un Animal. Elle acceptera en fait un objet de n'importe quel type contenant des fonctions membres getName() et speak(), que cela ait un sens ou non.

Deuxièmement, supposons que vous ayez 3 chats et 3 chiens que vous voulez conserver dans un tableau pour y accéder facilement. Comme un tableau ne peut contenir que des objets d'un seul type, sans pointeur ni référence vers une classe de base, vous devriez créer un tableau différent pour chaque type dérivé, comme ceci :

#include <array>
#include <iostream>

// Cat et Dog de l'exemple ci-dessus

int main()
{
    const auto& cats{ std::to_array<Cat>({{ "Fred" }, { "Misty" }, { "Zeke" }}) };
    const auto& dogs{ std::to_array<Dog>({{ "Garbo" }, { "Pooky" }, { "Truffle" }}) };

    // Avant C++20
    // const std::array<Cat, 3> cats{{ { "Fred" }, { "Misty" }, { "Zeke" } }};
    // const std::array<Dog, 3> dogs{{ { "Garbo" }, { "Pooky" }, { "Truffle" } }};

    for (const auto& cat : cats)
    {
        std::cout << cat.getName() << " says " << cat.speak() << '\n';
    }

    for (const auto& dog : dogs)
    {
        std::cout << dog.getName() << " says " << dog.speak() << '\n';
    }

    return 0;
}

Imaginez maintenant ce qui se passerait avec 30 types d'animaux différents. Il vous faudrait 30 tableaux, un pour chaque type d'animal !

En revanche, comme Cat et Dog dérivent tous deux de Animal, il est logique de pouvoir écrire quelque chose comme ceci :

#include <array>
#include <iostream>

// Cat et Dog de l'exemple ci-dessus

int main()
{
    const Cat fred{ "Fred" };
    const Cat misty{ "Misty" };
    const Cat zeke{ "Zeke" };

    const Dog garbo{ "Garbo" };
    const Dog pooky{ "Pooky" };
    const Dog truffle{ "Truffle" };

    // Création d'un tableau de pointeurs vers des animaux, initialisés avec nos objets Cat et Dog
    const auto animals{ std::to_array<const Animal*>({&fred, &garbo, &misty, &pooky, &truffle, &zeke }) };

    // Avant C++20, avec la taille du tableau spécifiée explicitement
    // const std::array<const Animal*, 6> animals{ &fred, &garbo, &misty, &pooky, &truffle, &zeke };

    for (const auto animal : animals)
    {
        std::cout << animal->getName() << " says " << animal->speak() << '\n';
    }

    return 0;
}

Bien que ce code compile et s'exécute, le fait que chaque élément du tableau « animals » soit un pointeur vers un Animal signifie malheureusement que animal->speak() appellera Animal::speak() au lieu de la version de speak() de la classe dérivée que nous souhaitons. La sortie est :


Fred says ???
Garbo says ???
Misty says ???
Pooky says ???
Truffle says ???
Zeke says ???

Bien que ces deux techniques puissent nous faire gagner beaucoup de temps et d'énergie, elles présentent le même problème : le pointeur ou la référence vers la classe de base appelle la version de base de la fonction au lieu de la version dérivée. Si seulement il existait un moyen de faire en sorte que ces pointeurs de base appellent la version dérivée d'une fonction au lieu de la version de base…

Devinez à quoi servent les fonctions virtuelles ? :)

#include <array>
#include <string>
#include <string_view>
#include <iostream>

class Animal
{
protected:
    std::string m_name;
    std::string m_speak;

    // Ce constructeur est protégé car
    // nous ne voulons pas que l'on crée directement des objets Animal,
    // mais nous voulons quand même que les classes dérivées puissent l'utiliser.
    Animal(std::string_view name, std::string_view speak)
        : m_name{ name }, m_speak{ speak }
    {
    }

    // Pour empêcher le découpage (slicing, abordé plus tard)
    Animal(const Animal&) = delete;
    Animal& operator=(const Animal&) = delete;

public:
    std::string_view getName() const { return m_name; }
    std::string_view speak() const { return m_speak; }
};

class Cat: public Animal
{
public:
    Cat(std::string_view name)
        : Animal{ name, "Meow" }
    {
    }
};

class Dog: public Animal
{
public:
    Dog(std::string_view name)
        : Animal{ name, "Woof" }
    {
    }
};

int main()
{
    const Cat fred{ "Fred" };
    const Cat misty{ "Misty" };
    const Cat zeke{ "Zeke" };

    const Dog garbo{ "Garbo" };
    const Dog pooky{ "Pooky" };
    const Dog truffle{ "Truffle" };

    // Création d'un tableau de pointeurs vers des animaux, initialisés avec nos objets Cat et Dog
    const auto animals{ std::to_array<const Animal*>({ &fred, &garbo, &misty, &pooky, &truffle, &zeke }) };

    // Avant C++20, avec la taille du tableau spécifiée explicitement
    // const std::array<const Animal*, 6> animals{ &fred, &garbo, &misty, &pooky, &truffle, &zeke };

    // animal n'est pas une référence, car nous parcourons des pointeurs
    for (const auto animal : animals)
    {
        std::cout << animal->getName() << " says " << animal->speak() << '\n';
    }

    return 0;
}
  1. Pourquoi la solution ci-dessus n'est-elle pas optimale ?

Indice : pensez à l'évolution future de Cat et Dog, lorsque nous voudrons les différencier selon davantage de critères. Indice : pensez aux limites imposées par le fait qu'un membre doive être initialisé à la construction.

Solution

La solution actuelle n'est pas optimale, pour plusieurs raisons.

Premièrement, il faut ajouter un membre à Animal pour chaque façon dont nous voulons différencier Cat et Dog. Avec le temps, la classe Animal pourrait devenir très volumineuse en mémoire et compliquée !

Deuxièmement, cette solution ne fonctionne que si la valeur du membre de la classe de base peut être déterminée au moment de l'initialisation. Par exemple, si speak() renvoyait un résultat aléatoire pour chaque Animal (par exemple, appeler Dog::speak() pourrait renvoyer « ouaf », « arf » ou « yip »), cette solution deviendrait vite maladroite et ne tiendrait plus.

Troisièmement, comme speak() est un membre de Animal, speak() aura le même comportement pour les Cat et les Dog (c'est-à-dire qu'elle renverra toujours m_speak). Si nous voulions que speak() ait un comportement différent pour les Cat et les Dog (par exemple, que les Dog renvoient un cri aléatoire), il faudrait placer toute cette logique supplémentaire dans Animal, ce qui rendrait Animal encore plus complexe.
