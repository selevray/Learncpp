25.3 — Les spécificateurs override et final, et les types de retour covariants

Pour résoudre certaines difficultés courantes liées à l'héritage, C++ dispose de deux identifiants liés à l'héritage : override et final. Notez que ce ne sont pas des mots-clés : ce sont des mots ordinaires qui n'ont une signification particulière que dans certains contextes. La norme C++ les appelle « identifiants à signification spéciale (identifiers with special meaning) », mais on les désigne souvent sous le nom de « spécificateurs (specifiers) ».

Bien que final ne soit pas très utilisé, override est un ajout formidable que vous devriez employer régulièrement. Dans cette leçon, nous examinerons les deux, ainsi qu'une exception à la règle selon laquelle les types de retour d'une fonction virtuelle redéfinie doivent correspondre.

Le spécificateur override

Comme nous l'avons mentionné dans la leçon précédente, une fonction virtuelle de classe dérivée n'est considérée comme une redéfinition que si sa signature et ses types de retour correspondent exactement. Cela peut causer des problèmes involontaires : une fonction destinée à redéfinir une fonction de la classe de base ne la redéfinit en fait pas.

Considérez l'exemple suivant :

#include <iostream>
#include <string_view>

class A
{
public:
    virtual std::string_view getName1(int x) { return "A"; }
    virtual std::string_view getName2(int x) { return "A"; }
};

class B : public A
{
public:
    virtual std::string_view getName1(short x) { return "B"; } // remarque : le paramètre est un short
    virtual std::string_view getName2(int x) const { return "B"; } // remarque : la fonction est const
};

int main()
{
    B b{};
    A& rBase{ b };
    std::cout << rBase.getName1(1) << '\n';
    std::cout << rBase.getName2(2) << '\n';

    return 0;
}

Comme rBase est une référence de type A vers un objet B, l'intention est d'utiliser les fonctions virtuelles pour accéder à B::getName1() et B::getName2(). Cependant, comme B::getName1() prend un paramètre différent (un short au lieu d'un int), elle n'est pas considérée comme une redéfinition de A::getName1(). Plus insidieusement, comme B::getName2() est const alors que A::getName2() ne l'est pas, B::getName2() n'est pas non plus considérée comme une redéfinition de A::getName2().

Par conséquent, ce programme affiche :


A
A

Dans ce cas précis, comme A et B se contentent d'afficher leur nom, il est assez facile de voir que nous avons raté nos redéfinitions et que c'est la mauvaise fonction virtuelle qui est appelée. En revanche, dans un programme plus complexe, où les fonctions ont des comportements ou des valeurs de retour qui ne sont pas affichés, de tels problèmes peuvent être très difficiles à déboguer.

Pour résoudre le problème des fonctions qui sont censées être des redéfinitions mais ne le sont pas, le spécificateur override peut être appliqué à n'importe quelle fonction virtuelle afin d'indiquer au compilateur de vérifier que la fonction est bien une redéfinition. Le spécificateur override se place à la fin de la déclaration d'une fonction membre (à l'endroit où l'on place un const de fonction). Si une fonction membre est à la fois const et une redéfinition, le const doit précéder override.

Si une fonction marquée override ne redéfinit aucune fonction de la classe de base (ou si elle est appliquée à une fonction non virtuelle), le compilateur signalera une erreur.

#include <string_view>

class A
{
public:
    virtual std::string_view getName1(int x) { return "A"; }
    virtual std::string_view getName2(int x) { return "A"; }
    virtual std::string_view getName3(int x) { return "A"; }
};

class B : public A
{
public:
    std::string_view getName1(short int x) override { return "B"; } // erreur de compilation, la fonction n'est pas une redéfinition
    std::string_view getName2(int x) const override { return "B"; } // erreur de compilation, la fonction n'est pas une redéfinition
    std::string_view getName3(int x) override { return "B"; } // correct, la fonction redéfinit A::getName3(int)

};

int main()
{
    return 0;
}

Le programme ci-dessus produit deux erreurs de compilation : une pour B::getName1() et une pour B::getName2(), car aucune des deux ne redéfinit une fonction existante. B::getName3() redéfinit bien A::getName3(), donc aucune erreur n'est produite pour cette ligne.

Comme l'utilisation du spécificateur override n'a aucun coût en performance et aide à s'assurer que vous redéfinissez réellement la fonction que vous pensez redéfinir, toutes les fonctions virtuelles redéfinies devraient être marquées avec le spécificateur override. De plus, comme override implique virtual, il n'est pas nécessaire d'utiliser le mot-clé virtual sur les fonctions marquées override.

Bonne pratique

Utilisez le mot-clé virtual sur les fonctions virtuelles d'une classe de base.

Utilisez le spécificateur override (mais pas le mot-clé virtual) sur les fonctions redéfinies dans les classes dérivées. Cela inclut les destructeurs virtuels.

Règle

Si une fonction membre est à la fois const et override, le const doit être écrit en premier. const override est correct, override const ne l'est pas.

Le spécificateur final

Il peut arriver que vous ne souhaitiez pas qu'une fonction virtuelle puisse être redéfinie, ou qu'une classe puisse être dérivée. Le spécificateur final permet d'indiquer au compilateur de faire respecter cette contrainte. Si un utilisateur tente de redéfinir une fonction ou d'hériter d'une classe marquée final, le compilateur produira une erreur de compilation.

Lorsque l'on souhaite interdire la redéfinition d'une fonction, le spécificateur final s'utilise à la même place que le spécificateur override, comme suit :

#include <string_view>

class A
{
public:
    virtual std::string_view getName() const { return "A"; }
};

class B : public A
{
public:
    // notez l'utilisation du spécificateur final sur la ligne suivante : cela empêche la redéfinition de cette fonction dans les classes dérivées
    std::string_view getName() const override final { return "B"; } // correct, redéfinit A::getName()
};

class C : public B
{
public:
    std::string_view getName() const override { return "C"; } // erreur de compilation : redéfinit B::getName(), qui est final
};

Dans le code ci-dessus, B::getName() redéfinit A::getName(), ce qui est correct. Mais B::getName() porte le spécificateur final, ce qui signifie que toute redéfinition ultérieure de cette fonction doit être considérée comme une erreur. C'est bien ce qui se passe : C::getName() tente de redéfinir B::getName() (le spécificateur override n'est pas pertinent ici, il est simplement présent par bonne pratique), donc le compilateur produit une erreur de compilation.

Lorsque l'on souhaite empêcher l'héritage d'une classe, le spécificateur final s'applique après le nom de la classe :

#include <string_view>

class A
{
public:
    virtual std::string_view getName() const { return "A"; }
};

class B final : public A // notez l'utilisation du spécificateur final ici
{
public:
    std::string_view getName() const override { return "B"; }
};

class C : public B // erreur de compilation : impossible d'hériter d'une classe final
{
public:
    std::string_view getName() const override { return "C"; }
};

Dans l'exemple ci-dessus, la classe B est déclarée final. Ainsi, lorsque C tente d'hériter de B, le compilateur produit une erreur de compilation.

Les types de retour covariants

Il existe un cas particulier dans lequel une fonction virtuelle redéfinie dans une classe dérivée peut avoir un type de retour différent de celui de la classe de base, tout en restant considérée comme une redéfinition valide. Si le type de retour d'une fonction virtuelle est un pointeur ou une référence vers une classe, les fonctions redéfinies peuvent renvoyer un pointeur ou une référence vers une classe dérivée. On parle alors de types de retour covariants (covariant return types). Voici un exemple :

#include <iostream>
#include <string_view>

class Base
{
public:
    // Cette version de getThis() renvoie un pointeur vers une classe Base
    virtual Base* getThis() { std::cout << "appel de Base::getThis()\n"; return this; }
    void printType() { std::cout << "a renvoyé une Base\n"; }
};

class Derived : public Base
{
public:
    // En principe, les fonctions redéfinies doivent renvoyer des objets du même type que la fonction de base
    // Cependant, comme Derived dérive de Base, il est permis de renvoyer Derived* au lieu de Base*
    Derived* getThis() override { std::cout << "appel de Derived::getThis()\n";  return this; }
    void printType() { std::cout << "a renvoyé une Derived\n"; }
};

int main()
{
    Derived d{};
    Base* b{ &d };
    d.getThis()->printType(); // appelle Derived::getThis(), renvoie un Derived*, appelle Derived::printType
    b->getThis()->printType(); // appelle Derived::getThis(), renvoie un Base*, appelle Base::printType

    return 0;
}

Ce programme affiche :


appel de Derived::getThis()
a renvoyé une Derived
appel de Derived::getThis()
a renvoyé une Base

Une remarque intéressante au sujet des types de retour covariants : C++ ne peut pas sélectionner de types dynamiquement, vous obtiendrez donc toujours le type correspondant à la version réellement appelée de la fonction.

Dans l'exemple ci-dessus, nous appelons d'abord d.getThis(). Comme d est un Derived, cela appelle Derived::getThis(), qui renvoie un Derived*. Ce Derived* est ensuite utilisé pour appeler la fonction non virtuelle Derived::printType().

Passons au cas intéressant. Nous appelons ensuite b->getThis(). La variable b est un pointeur de type Base pointant vers un objet Derived. Base::getThis() est une fonction virtuelle, donc cela appelle Derived::getThis(). Bien que Derived::getThis() renvoie un Derived*, comme la version de la fonction de la classe Base renvoie un Base*, le Derived* renvoyé est converti implicitement en Base* (conversion ascendante). Comme Base::printType() n'est pas virtuelle, c'est Base::printType() qui est appelée.

En d'autres termes, dans l'exemple ci-dessus, vous n'obtenez un Derived* que si vous appelez getThis() sur un objet dont le type déclaré est déjà Derived.

Notez que si printType() était virtuelle au lieu d'être non virtuelle, le résultat de b->getThis() (un objet de type Base*) subirait la résolution des fonctions virtuelles, et Derived::printType() serait appelée.

Les types de retour covariants sont souvent utilisés lorsqu'une fonction membre virtuelle renvoie un pointeur ou une référence vers la classe qui contient la fonction membre (par exemple, Base::getThis() renvoie un Base*, et Derived::getThis() renvoie un Derived*). Toutefois, cela n'est pas strictement nécessaire. Les types de retour covariants peuvent être utilisés dans tout cas où le type de retour de la fonction membre redéfinie dérive du type de retour de la fonction membre virtuelle de base.

Quiz

Question n° 1

Que affiche le programme suivant ?

#include <iostream>

class A
{
public:
    void print()
    {
        std::cout << "A";
    }
    virtual void vprint()
    {
        std::cout << "A";
    }
};
class B : public A
{
public:
    void print()
    {
        std::cout << "B";
    }
    void vprint() override
    {
        std::cout << "B";
    }
};


class C
{
private:
    A m_a{};

public:
    virtual A& get()
    {
        return m_a;
    }
};

class D : public C
{
private:
    B m_b{};

public:
    B& get() override // type de retour covariant
    {
        return m_b;
    }
};

int main()
{
    // cas 1
    D d {};
    d.get().print();
    d.get().vprint();
    std::cout << '\n';

    // cas 2
    C c {};
    c.get().print();
    c.get().vprint();
    std::cout << '\n';

    // cas 3
    C& ref{ d };
    ref.get().print();
    ref.get().vprint();
    std::cout << '\n';

    return 0;
}
Solution 

BB
AA
AB

Dans tous les cas, comme get() a un type de retour covariant, le type de retour de get() est celui de la fonction membre get() de l'objet implicite.

Le cas 1 est direct. Dans les deux instructions, d.get() appelle D::get(), qui renvoie m_b. Comme get() est appelée sur d, de type D, c'est le type de retour de D::get() qui est utilisé, soit le type B&. Les appels à print() et vprint() correspondent respectivement à B::print() et B::vprint().

Le cas 2 est également direct. Dans les deux instructions, c.get() appelle C::get(), qui renvoie m_a. Comme get() est appelée sur c, de type C, c'est le type de retour de C::get() qui est utilisé, soit le type A&. Les appels à print() et vprint() correspondent respectivement à A::print() et A::vprint().

Le cas 3 est le plus intéressant. ref est un C& qui référence un D. ref.get() est une fonction virtuelle, donc ref.get() se résout virtuellement en D::get(), qui renvoie m_b. Cependant, get() a un type de retour covariant, donc le type de retour de get() est déterminé par le type de l'objet implicite sur lequel get() est appelée. Comme ref est un C&, c'est le type de retour de C::get() qui est utilisé, ce qui signifie que ref.get() renvoie un A& (référence à l'objet m_b, qui est un B).

Comme le type de retour de ref.get() est un A&, l'appel de fonction non virtuelle ref.get().print() se résout en A::print().

Lorsque la fonction virtuelle ref.get().vprint() est appelée, la résolution des fonctions virtuelles intervient. Bien que le type de retour de ref.get() soit un A&, l'objet référencé est en réalité un B. Par conséquent, c'est B::vprint() qui est appelée.

Question n° 2

Quand utiliser la surcharge de fonctions plutôt que la redéfinition de fonctions ?

Solution

La surcharge de fonctions s'utilise lorsque nous avons besoin qu'une fonction membre ou non membre se comporte différemment selon le type des paramètres qu'on lui transmet.

La redéfinition de fonctions s'utilise lorsque nous avons besoin qu'une fonction membre se comporte différemment selon que l'objet implicite est un objet de classe dérivée.
