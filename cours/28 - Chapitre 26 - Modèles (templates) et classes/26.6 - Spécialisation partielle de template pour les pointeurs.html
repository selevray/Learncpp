26.6 — Spécialisation partielle de template pour les pointeurs

Dans la leçon précédente 26.4 -- Spécialisation de classe template, nous avons examiné une classe template simple Storage, ainsi qu'une spécialisation pour le type double :

#include <iostream>

template <typename T>
class Storage
{
private:
    T m_value {};
public:
    Storage(T value)
      : m_value { value }
    {
    }

    void print()
    {
        std::cout << m_value << '\n';
    }
};

template<>
void Storage<double>::print() // spécialisation complète pour le type double
{
    std::cout << std::scientific << m_value << '\n';
}

int main()
{
    // Définissons quelques unités de stockage
    Storage i { 5 };
    Storage d { 6.7 }; // va entraîner l'instanciation implicite de Storage<double>

    // Affichons quelques valeurs
    i.print(); // appelle Storage<int>::print (instanciée depuis Storage<T>)
    d.print(); // appelle Storage<double>::print (appelée depuis la spécialisation explicite de Storage<double>::print())
}

Cependant, aussi simple que soit cette classe, elle possède un défaut caché : elle se compile mais fonctionne mal lorsque T est un type pointeur. Par exemple :

int main()
{
    double d { 1.2 };
    double *ptr { &d };

    Storage s { ptr };
    s.print();

    return 0;
}

Sur la machine de l'auteur, ce programme a produit le résultat suivant :


0x7ffe164e0f50

Que s'est-il passé ? Comme ptr est un double*, s a le type Storage<double*>, ce qui signifie que m_value a le type double*. Lors de l'appel du constructeur, m_value reçoit une copie de l'adresse contenue dans ptr, et c'est cette adresse qui est affichée lorsque la fonction membre print() est appelée.

Alors, comment corriger cela ?

Une option consiste à ajouter une spécialisation complète pour le type double* :

#include <iostream>

template <typename T>
class Storage
{
private:
    T m_value {};
public:
    Storage(T value)
      : m_value { value }
    {
    }

    void print()
    {
        std::cout << m_value << '\n';
    }
};

template<>
void Storage<double*>::print() // spécialisation complète pour le type double*
{
    if (m_value)
        std::cout << std::scientific << *m_value << '\n';
}

template<>
void Storage<double>::print() // spécialisation complète pour le type double (pour comparaison, non utilisée)
{
    std::cout << std::scientific << m_value << '\n';
}

int main()
{
    double d { 1.2 };
    double *ptr { &d };

    Storage s { ptr };
    s.print(); // appelle Storage<double*>::print()

    return 0;
}

Ce programme affiche maintenant le bon résultat :


1.200000e+00

Mais cela ne résout le problème que lorsque T est de type double*. Qu'en est-il lorsque T est int*, char*, ou tout autre type pointeur ?

Nous ne voulons vraiment pas avoir à créer une spécialisation complète pour chaque type pointeur. Et en fait, ce n'est même pas possible, car l'utilisateur peut toujours passer un pointeur vers un type défini par le programme.

Spécialisation partielle de template pour les pointeurs

Vous pourriez penser essayer de créer une fonction template surchargée sur le type T* :

// ne fonctionne pas
template<typename T>
void Storage<T*>::print()
{
    if (m_value)
        std::cout << std::scientific << *m_value << '\n';
}

Une telle fonction est une fonction template partiellement spécialisée, car elle restreint le type T (à un type pointeur), mais T reste un paramètre template de type.

Malheureusement, cela ne fonctionne pas pour une raison simple : à la date de rédaction (C++23), les fonctions ne peuvent pas être partiellement spécialisées. Comme nous l'avons indiqué dans la leçon 26.5 -- Spécialisation partielle de template, seules les classes peuvent être partiellement spécialisées.

Spécialisons donc plutôt partiellement la classe Storage :

#include <iostream>

template <typename T>
class Storage // Ceci est la classe template primaire (identique à précédemment)
{
private:
    T m_value {};
public:
    Storage(T value)
      : m_value { value }
    {
    }

    void print()
    {
        std::cout << m_value << '\n';
    }
};

template <typename T> // nous avons toujours un paramètre template de type
class Storage<T*> // Ceci est partiellement spécialisé pour T*
{
private:
    T* m_value {};
public:
    Storage(T* value)
      : m_value { value }
    {
    }

    void print();
};

template <typename T>
void Storage<T*>::print() // Ceci est une fonction non spécialisée de la classe partiellement spécialisée Storage<T*>
{
    if (m_value)
        std::cout << std::scientific << *m_value << '\n';
}

int main()
{
    double d { 1.2 };
    double *ptr { &d };

    Storage s { ptr }; // instancie Storage<double*> à partir de la classe partiellement spécialisée
    s.print(); // appelle Storage<double*>::print()

    return 0;
}

Nous avons défini Storage<T*>::print() en dehors de la classe simplement pour montrer comment procéder, et pour montrer que cette définition est identique à la fonction Storage<T*>::print() partiellement spécialisée qui ne fonctionnait pas plus haut. Cependant, maintenant que Storage<T*> est une classe partiellement spécialisée, Storage<T*>::print() n'est plus partiellement spécialisée : c'est une fonction non spécialisée, c'est pourquoi elle est autorisée.

Il est intéressant de noter que notre paramètre template de type est défini comme T, et non T*. Cela signifie que T sera déduit comme le type non pointeur, nous devons donc utiliser T* partout où nous voulons un pointeur vers T. Il faut également rappeler que la spécialisation partielle Storage<T*> doit être définie après la classe template primaire Storage<T>.

Problèmes de propriété et de durée de vie

La classe partiellement spécialisée Storage<T*> ci-dessus présente un autre problème potentiel. Comme m_value est un T*, il s'agit d'un pointeur vers l'objet qui est passé en paramètre. Si cet objet est ensuite détruit, notre Storage<T*> se retrouvera avec un pointeur pendouillant (dangling).

Le problème fondamental est que notre implémentation de Storage<T> a une sémantique de copie (c'est-à-dire qu'elle fait une copie de son initialiseur), alors que Storage<T*> a une sémantique de référence (c'est-à-dire qu'elle est une référence vers son initialiseur). Cette incohérence est une source de bugs.

Il existe plusieurs façons de traiter ce type de problème (par ordre de complexité croissante) :

  1. Indiquer très clairement que Storage<T*> est une classe de vue (avec sémantique de référence), donc qu'il incombe à l'appelant de s'assurer que l'objet pointé reste valide tant que Storage<T*> existe. Malheureusement, comme cette classe partiellement spécialisée doit porter le même nom que la classe template primaire, nous ne pouvons pas lui donner un nom comme StorageView. Nous sommes donc limités à utiliser des commentaires ou d'autres moyens faciles à manquer. Ce n'est pas une excellente option.
  2. Empêcher totalement l'utilisation de Storage<T*>. Nous n'avons probablement pas besoin que Storage<T*> existe, car l'appelant peut toujours déréférencer le pointeur au moment de l'instanciation pour utiliser Storage<T> et faire une copie de la valeur (ce qui est sémantiquement approprié pour une classe de stockage).

Cependant, alors que vous pouvez supprimer une fonction surchargée, le C++ (jusqu'à C++23) ne permet pas de supprimer une classe. La solution évidente serait de spécialiser partiellement Storage<T*> puis de faire en sorte qu'elle ne compile pas (par exemple avec static_assert) lorsque le template est instancié. Cette approche a cependant un inconvénient majeur : std::nullptr_t n'est pas un type pointeur, donc Storage<std::nullptr_t> ne correspond pas à Storage<T*> !

Une meilleure solution consiste à éviter complètement la spécialisation partielle, et à utiliser un static_assert dans notre template primaire pour nous assurer que T est un type acceptable. Voici un exemple de cette approche :

#include <iostream>
#include <type_traits> // pour std::is_pointer_v et std::is_null_pointer_v

template <typename T>
class Storage
{
    // Vérifions que T n'est ni un pointeur ni un std::nullptr_t
    static_assert(!std::is_pointer_v<T> && !std::is_null_pointer_v<T>, "Storage<T*> and Storage<nullptr> disallowed");

private:
    T m_value {};

public:
    Storage(T value)
      : m_value { value }
    {
    }

    void print()
    {
        std::cout << m_value << '\n';
    }
};

int main()
{
    double d { 1.2 };

    Storage s1 { d }; // ok
    s1.print();

    Storage s2 { &d }; // static_assert car T est un pointeur
    s2.print();

    Storage s3 { nullptr }; // static_assert car T est un nullptr
    s3.print();

    return 0;
}
  1. Faire en sorte que Storage<T*> fasse une copie de l'objet sur le tas. Si vous gérez vous-même toute la gestion de la mémoire du tas, cela nécessite de surcharger le constructeur, le constructeur de copie, l'opérateur d'affectation par copie et le destructeur. Une alternative plus simple consiste simplement à utiliser std::unique_ptr (que nous présentons dans la leçon 22.5 -- std::unique_ptr) :
#include <iostream>
#include <type_traits> // pour std::is_pointer_v et std::is_null_pointer_v
#include <memory>

template <typename T>
class Storage
{
    // Vérifions que T n'est ni un pointeur ni un std::nullptr_t
    static_assert(!std::is_pointer_v<T> && !std::is_null_pointer_v<T>, "Storage<T*> and Storage<nullptr> disallowed");

private:
    T m_value {};

public:
    Storage(T value)
      : m_value { value }
    {
    }

    void print()
    {
        std::cout << m_value << '\n';
    }
};

template <typename T>
class Storage<T*>
{
private:
    std::unique_ptr<T> m_value {}; // utilise std::unique_ptr pour désallouer automatiquement lorsque Storage est détruit

public:
    Storage(T* value)
      : m_value { std::make_unique<T>(value ? *value : 0) } // ou lever une exception lorsque !value
    {
    }

    void print()
    {
        if (m_value)
            std::cout << *m_value << '\n';
    }
};

int main()
{
    double d { 1.2 };

    Storage s1 { d }; // ok
    s1.print();

    Storage s2 { &d }; // ok, copie d sur le tas
    s2.print();

    return 0;
}

Utiliser la spécialisation partielle de classe template pour créer des implémentations distinctes pour les pointeurs et les non-pointeurs d'une classe est extrêmement utile lorsque vous voulez qu'une classe traite ces cas différemment, tout en restant totalement transparente pour l'utilisateur final.
