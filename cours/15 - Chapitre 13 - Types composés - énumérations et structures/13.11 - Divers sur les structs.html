13.11 — Divers sur les structs

Structs dont les membres sont des types définis par le programme

En C++, les structs (et les classes) peuvent avoir pour membres d'autres types définis par le programme. Il existe deux façons de procéder.

Premièrement, nous pouvons définir un type défini par le programme (dans la portée globale), puis l'utiliser comme membre d'un autre type défini par le programme :

#include <iostream>

struct Employee
{
    int id {};
    int age {};
    double wage {};
};

struct Company
{
    int numberOfEmployees {};
    Employee CEO {}; // Employee is a struct within the Company struct
};

int main()
{
    Company myCompany{ 7, { 1, 32, 55000.0 } }; // Nested initialization list to initialize Employee
    std::cout << myCompany.CEO.wage << '\n'; // print the CEO's wage

    return 0;
}

Dans le cas ci-dessus, nous avons défini une struct Employee, puis l'avons utilisée comme membre de la struct Company. Lorsque nous initialisons Company, nous pouvons aussi initialiser Employee à l'aide d'une liste d'initialisation imbriquée. Et si nous voulons connaître le salaire du PDG, il suffit d'utiliser deux fois l'opérateur de sélection de membre : myCompany.CEO.wage;

Deuxièmement, des types peuvent aussi être imbriqués à l'intérieur d'autres types. Ainsi, si un Employee n'existe qu'en tant que partie d'une Company, le type Employee peut être imbriqué dans la struct Company :

#include <iostream>

struct Company
{
    struct Employee // accessed via Company::Employee
    {
        int id{};
        int age{};
        double wage{};
    };

    int numberOfEmployees{};
    Employee CEO{}; // Employee is a struct within the Company struct
};

int main()
{
    Company myCompany{ 7, { 1, 32, 55000.0 } }; // Nested initialization list to initialize Employee
    std::cout << myCompany.CEO.wage << '\n'; // print the CEO's wage

    return 0;
}

Cette approche est plus souvent utilisée avec les classes, nous en reparlerons donc dans une future leçon (15.3 -- Types imbriqués (types membres)).

Les structs qui sont propriétaires doivent avoir des membres de données propriétaires

Dans la leçon 5.9 -- std::string_view (partie 2), nous avons présenté les deux notions complémentaires de propriétaire et de observateur. Les propriétaires gèrent leurs propres données et contrôlent le moment de leur destruction. Les observateurs regardent les données de quelqu'un d'autre, et ne contrôlent ni le moment de leur modification ni celui de leur destruction.

Dans la plupart des cas, nous voulons que nos structs (et classes) soient propriétaires des données qu'elles contiennent. Cela apporte plusieurs avantages :

  • Les membres de données resteront valides aussi longtemps que la struct (ou la classe) existera.
  • La valeur de ces membres de données ne changera pas de façon inattendue.

Le moyen le plus simple de faire d'une struct (ou d'une classe) un propriétaire consiste à donner à chaque membre de données un type qui est un propriétaire (c'est-à-dire ni un observateur, ni un pointeur, ni une référence). Si une struct ou une classe a uniquement des membres de données qui sont des propriétaires, alors la struct ou la classe elle-même est automatiquement un propriétaire.

Si une struct (ou une classe) possède un membre de données qui est un observateur, il est possible que l'objet observé par ce membre soit détruit avant le membre de données qui l'observe. Si cela se produit, la struct se retrouve avec un membre pendouillant (dangling), et y accéder conduit à un comportement indéfini.

Bonne pratique

Dans la plupart des cas, nous voulons que nos structs (et classes) soient propriétaires. Le moyen le plus simple d'y parvenir est de s'assurer que chaque membre de données a un type propriétaire (c'est-à-dire ni un observateur, ni un pointeur, ni une référence).

Note de l'auteur

Pratiquez des structs sûres. Ne laissez pas vos membres pendouiller.

C'est pourquoi les membres de données de type chaîne sont presque toujours de type std::string (qui est un propriétaire), et non de type std::string_view (qui est un observateur). L'exemple suivant illustre un cas où cela a de l'importance :

#include <iostream>
#include <string>
#include <string_view>

struct Owner
{
    std::string name{}; // std::string is an owner
};

struct Viewer
{
    std::string_view name {}; // std::string_view is a viewer
};

// getName() returns the user-entered string as a temporary std::string
// This temporary std::string will be destroyed at the end of the full expression
// containing the function call.
std::string getName()
{
    std::cout << "Enter a name: ";
    std::string name{};
    std::cin >> name;
    return name;
}

int main()
{
    Owner o { getName() };  // The return value of getName() is destroyed just after initialization
    std::cout << "The owners name is " << o.name << '\n';  // ok

    Viewer v { getName() }; // The return value of getName() is destroyed just after initialization
    std::cout << "The viewers name is " << v.name << '\n'; // undefined behavior

    return 0;
}

La fonction getName() renvoie le nom saisi par l'utilisateur sous la forme d'un std::string temporaire. Cette valeur de retour temporaire est détruite à la fin de l'expression complète dans laquelle la fonction est appelée.

Dans le cas de o, ce std::string temporaire sert à initialiser o.name. Comme o.name est un std::string, o.name effectue une copie du std::string temporaire. Le std::string temporaire disparaît ensuite, mais o.name n'est pas affecté puisqu'il s'agit d'une copie. Lorsque nous affichons o.name dans l'instruction suivante, cela fonctionne comme attendu.

Dans le cas de v, ce std::string temporaire sert à initialiser v.name. Comme v.name est un std::string_view, v.name n'est qu'une vue sur le std::string temporaire, et non une copie. Le std::string temporaire disparaît ensuite, laissant v.name pendouiller. Lorsque nous affichons v.name dans l'instruction suivante, nous obtenons un comportement indéfini.

Taille des structs et alignement des structures de données

En général, la taille d'une struct est la somme des tailles de tous ses membres, mais pas toujours !

Considérons le programme suivant :

#include <iostream>

struct Foo
{
    short a {};
    int b {};
    double c {};
};

int main()
{
    std::cout << "The size of short is " << sizeof(short) << " bytes\n";
    std::cout << "The size of int is " << sizeof(int) << " bytes\n";
    std::cout << "The size of double is " << sizeof(double) << " bytes\n";

    std::cout << "The size of Foo is " << sizeof(Foo) << " bytes\n";

    return 0;
}

Sur la machine de l'auteur, ce programme a affiché :

The size of short is 2 bytes
The size of int is 4 bytes
The size of double is 8 bytes
The size of Foo is 16 bytes

Remarquez que la somme des tailles de short, int et double vaut 14 octets, mais que la taille de Foo vaut 16 octets !

En fait, nous pouvons seulement dire que la taille d'une struct sera au moins égale à la somme des tailles de toutes les variables qu'elle contient. Mais elle peut être plus grande ! Pour des raisons de performance, le compilateur ajoute parfois des espaces vides dans les structures (on parle de bourrage, ou padding).

Dans la struct Foo ci-dessus, le compilateur ajoute invisiblement 2 octets de bourrage après le membre a, ce qui porte la taille de la structure à 16 octets au lieu de 14.

Pour les lecteurs avancés

Les raisons pour lesquelles les compilateurs peuvent ajouter du bourrage dépassent le cadre de ce tutoriel, mais les lecteurs qui souhaitent en savoir plus peuvent consulter la page sur l'alignement des structures de données sur Wikipédia. Cette lecture est facultative et n'est pas nécessaire pour comprendre les structures ou le C++ !

Cela peut avoir un impact assez important sur la taille de la struct, comme le montre le programme suivant :

#include <iostream>

struct Foo1
{
    short a{}; // will have 2 bytes of padding after a
    int b{};
    short c{}; // will have 2 bytes of padding after c
};

struct Foo2
{
    int b{};
    short a{};
    short c{};
};

int main()
{
    std::cout << sizeof(Foo1) << '\n'; // prints 12
    std::cout << sizeof(Foo2) << '\n'; // prints 8

    return 0;
}

Ce programme affiche :


12
8

Remarquez que Foo1 et Foo2 ont exactement les mêmes membres, seul l'ordre de déclaration diffère. Pourtant, Foo1 est 50 % plus grande à cause du bourrage supplémentaire.

Astuce

Vous pouvez réduire le bourrage en déclarant vos membres par ordre de taille décroissante.

Le compilateur C++ n'a pas le droit de réordonner les membres : cela doit être fait manuellement.
