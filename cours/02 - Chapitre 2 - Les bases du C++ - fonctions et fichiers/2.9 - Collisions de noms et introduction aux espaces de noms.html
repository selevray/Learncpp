2.9 — Collisions de noms et introduction aux espaces de noms

Imaginez que vous conduisiez chez un ami pour la première fois, et que l'adresse qu'il vous a donnée soit le 245 Front Street, à Mill City. En arrivant à Mill City, vous sortez votre plan, pour découvrir que la ville compte en fait deux Front Street, situées à l'opposé l'une de l'autre ! Laquelle devez-vous rejoindre ? À moins d'un indice supplémentaire qui vous aide à trancher (par exemple, si vous vous souvenez que la maison de votre ami est près de la rivière), vous devrez appeler votre ami pour obtenir davantage d'informations. Cela serait source de confusion et d'inefficacité (en particulier pour le facteur), c'est pourquoi, dans la plupart des pays, les noms de rues et les numéros d'habitation doivent être uniques au sein d'une même ville.

De la même manière, C++ exige que tous les identifiants soient non ambigus. Si deux identifiants identiques sont introduits dans un même programme de façon que le compilateur ou l'éditeur de liens ne puisse pas les distinguer, le compilateur ou l'éditeur de liens produira une erreur. Cette erreur est généralement appelée collision de noms (ou conflit de noms, en anglais naming collision ou naming conflict).

Si les identifiants en collision sont introduits dans le même fichier, il en résulte une erreur de compilation. Si les identifiants en collision sont introduits dans des fichiers distincts appartenant au même programme, il en résulte une erreur de l'éditeur de liens.

Un exemple de collision de noms

a.cpp :

#include <iostream>

void myFcn(int x)
{
    std::cout << x;
}

main.cpp :

#include <iostream>

void myFcn(int x)
{
    std::cout << 2 * x;
}

int main()
{
    return 0;
}

Lorsque le compilateur compile ce programme, il compile a.cpp et main.cpp indépendamment, et chaque fichier se compile sans problème.

En revanche, lorsque l'éditeur de liens s'exécute, il lie ensemble toutes les définitions de a.cpp et de main.cpp, et découvre des définitions contradictoires pour la fonction myFcn(). L'éditeur de liens interrompt alors la liaison avec une erreur. Notez que cette erreur se produit même si myFcn() n'est jamais appelée !

La plupart des collisions de noms surviennent dans deux cas :

  1. Deux fonctions (ou variables globales) portant le même nom sont introduites dans des fichiers distincts appartenant au même programme. Cela produit une erreur de l'éditeur de liens, comme montré ci-dessus.
  2. Deux fonctions (ou variables globales) portant le même nom sont introduites dans le même fichier. Cela produit une erreur de compilation.

Plus un programme est grand et utilise d'identifiants, plus les risques de collision de noms augmentent sensiblement. La bonne nouvelle est que C++ fournit de nombreux mécanismes pour éviter les collisions de noms. La portée locale, qui empêche les variables locales définies à l'intérieur des fonctions d'entrer en conflit entre elles, en fait partie. Mais la portée locale ne fonctionne pas pour les noms de fonctions. Comment, dès lors, empêcher les noms de fonctions d'entrer en conflit entre eux ?

Régions de portée

Revenons un instant à notre analogie avec les adresses : le fait d'avoir deux Front Street ne posait problème que parce que ces rues existaient dans la même ville. En revanche, si vous deviez livrer du courrier à deux adresses, l'une au 245 Front Street à Mill City et l'autre au 245 Front Street à Jonesville, il n'y aurait aucune confusion quant à la destination. Autrement dit, les villes constituent des regroupements qui permettent de désambiguïser des adresses susceptibles d'entrer en conflit.

Une région de portée (scope region) est une zone du code source dans laquelle tous les identifiants déclarés sont considérés comme distincts des noms déclarés dans d'autres portées (un peu comme les villes de notre analogie). Deux identifiants de même nom peuvent être déclarés dans des régions de portée séparées sans provoquer de collision. En revanche, à l'intérieur d'une région de portée donnée, tous les identifiants doivent être uniques, faute de quoi une collision de noms se produit.

Le corps d'une fonction est un exemple de région de portée. Deux identifiants portant le même nom peuvent être définis dans des fonctions distinctes sans problème, car chaque fonction constitue une région de portée séparée et il n'y a donc aucune collision. En revanche, si vous essayez de définir deux identifiants de même nom à l'intérieur d'une même fonction, une collision de noms se produit et le compilateur se plaint.

Espaces de noms

Un espace de noms (namespace) constitue un autre type de région de portée (appelée portée d'espace de noms, namespace scope) qui permet de déclarer ou de définir des noms à l'intérieur de celui-ci, dans un but de désambiguïsation. Les noms déclarés dans un espace de noms sont isolés des noms déclarés dans d'autres portées, ce qui permet à ces noms d'exister sans conflit.

Point clé

Un nom déclaré dans une région de portée (comme un espace de noms) est distinct de tout nom identique déclaré dans une autre portée.

Par exemple, deux fonctions aux déclarations identiques peuvent être définies dans des espaces de noms différents, sans qu'aucune collision de noms ni aucune ambiguïté ne se produise.

Un espace de noms ne peut contenir que des déclarations et des définitions (par exemple des variables et des fonctions). Les instructions exécutables ne sont pas autorisées, sauf lorsqu'elles font partie d'une définition (par exemple à l'intérieur d'une fonction).

Point clé

Un espace de noms ne peut contenir que des déclarations et des définitions. Les instructions exécutables ne sont autorisées que dans le cadre d'une définition (par exemple, d'une fonction).

Les espaces de noms servent souvent à regrouper des identifiants apparentés dans un grand projet, afin de limiter le risque qu'ils entrent accidentellement en collision avec d'autres identifiants. Par exemple, si vous placez toutes vos fonctions mathématiques dans un espace de noms nommé math, alors vos fonctions mathématiques n'entreront pas en collision avec des fonctions de même nom situées en dehors de l'espace de noms math.

Nous verrons comment créer vos propres espaces de noms dans une leçon ultérieure.

L'espace de noms global

En C++, tout nom qui n'est pas défini à l'intérieur d'une classe, d'une fonction ou d'un espace de noms fait partie d'un espace de noms implicite appelé espace de noms global (parfois aussi appelé portée globale, global scope).

Dans l'exemple présenté au début de la leçon, la fonction main() et les deux versions de myFcn() sont définies dans l'espace de noms global. La collision de noms rencontrée dans cet exemple provient du fait que les deux versions de myFcn() se retrouvent dans l'espace de noms global, ce qui viole la règle selon laquelle tous les noms d'une région de portée doivent être uniques.

Nous étudions l'espace de noms global plus en détail dans la leçon 7.4 -- Introduction aux variables globales.

Pour l'instant, retenez deux points :

  • Les identifiants déclarés dans la portée globale sont visibles depuis le point de leur déclaration jusqu'à la fin du fichier.
  • Bien que des variables puissent être définies dans l'espace de noms global, cela doit généralement être évité (nous expliquons pourquoi dans la leçon 7.8 -- Pourquoi les variables globales (non constantes) sont néfastes).

Par exemple :

#include <iostream> // importe la déclaration de std::cout dans la portée globale

// Toutes les instructions suivantes font partie de l'espace de noms global

void foo();    // correct : déclaration anticipée de fonction
int x;         // compile mais fortement déconseillé : définition de variable globale non constante (sans initialisation)
int y { 5 };   // compile mais fortement déconseillé : définition de variable globale non constante (avec initialisation)
x = 5;         // erreur de compilation : les instructions exécutables ne sont pas autorisées dans les espaces de noms

int main()     // correct : définition de fonction
{
    return 0;
}

void goo();    // correct : déclaration anticipée de fonction

L'espace de noms std

Lorsque C++ a été conçu à l'origine, tous les identifiants de la bibliothèque standard C++ (y compris std::cin et std::cout) pouvaient être utilisés sans le préfixe std:: (ils faisaient partie de l'espace de noms global). Cependant, cela signifiait que n'importe quel identifiant de la bibliothèque standard pouvait entrer en conflit avec n'importe quel nom que vous choisissiez pour vos propres identifiants (eux aussi définis dans l'espace de noms global). Du code qui fonctionnait auparavant pouvait soudainement présenter un conflit de noms lorsque vous incluiez une autre partie de la bibliothèque standard. Pire encore, du code compilant avec une version de C++ pouvait ne plus compiler avec la version suivante, car de nouveaux identifiants introduits dans la bibliothèque standard pouvaient entrer en conflit avec du code déjà écrit. C++ a donc regroupé toutes les fonctionnalités de la bibliothèque standard dans un espace de noms nommé std (abréviation de « standard »).

Il s'avère que le nom de std::cout n'est pas vraiment std::cout. Il s'agit simplement de cout, et std est le nom de l'espace de noms auquel appartient l'identifiant cout. Parce que cout est défini dans l'espace de noms std, le nom cout n'entre en conflit avec aucun objet ou fonction nommé cout que nous créons en dehors de l'espace de noms std (par exemple dans l'espace de noms global).

Point clé

Lorsque vous utilisez un identifiant défini dans un espace de noms autre que l'espace de noms global (par exemple l'espace de noms std), vous devez indiquer au compilateur que cet identifiant se trouve dans cet espace de noms.

Il existe plusieurs façons de procéder.

Qualificateur d'espace de noms explicite std::

La manière la plus directe d'indiquer au compilateur que nous voulons utiliser cout de l'espace de noms std consiste à utiliser explicitement le préfixe std::. Par exemple :

#include <iostream>

int main()
{
    std::cout << "Hello world!"; // quand nous écrivons cout, nous désignons le cout défini dans l'espace de noms std
    return 0;
}

Le symbole :: est un opérateur appelé opérateur de résolution de portée (scope resolution operator). L'identifiant situé à gauche du symbole :: désigne l'espace de noms dans lequel se trouve le nom situé à droite de ce symbole. Si aucun identifiant n'est fourni à gauche du symbole ::, l'espace de noms global est sous-entendu.

Ainsi, lorsque nous écrivons std::cout, nous disons « le cout déclaré dans l'espace de noms std ».

C'est la manière la plus sûre d'utiliser cout, car il n'y a aucune ambiguïté quant au cout auquel nous faisons référence (celui de l'espace de noms std).

Bonne pratique

Utilisez des préfixes d'espace de noms explicites pour accéder aux identifiants définis dans un espace de noms.

Lorsqu'un identifiant est accompagné d'un préfixe d'espace de noms, on parle de nom qualifié (qualified name).

Utiliser using namespace std (et pourquoi l'éviter)

Une autre façon d'accéder aux identifiants d'un espace de noms consiste à utiliser une instruction de directive using. Voici notre programme « Hello world » initial avec une directive using :

#include <iostream>

using namespace std; // il s'agit d'une directive using qui permet d'accéder aux noms de l'espace de noms std sans préfixe

int main()
{
    cout << "Hello world!";
    return 0;
}

Une directive using (using directive) permet d'accéder aux noms d'un espace de noms sans utiliser de préfixe d'espace de noms. Ainsi, dans l'exemple ci-dessus, lorsque le compilateur cherche à déterminer quel identifiant correspond à cout, il retient std::cout qui, grâce à la directive using, est accessible simplement sous le nom cout.

De nombreux ouvrages, tutoriels, et même certains environnements de développement recommandent ou utilisent une directive using en début de programme. Pourtant, utilisée de cette manière, il s'agit d'une mauvaise pratique, fortement déconseillée.

Considérez le programme suivant :

#include <iostream> // importe la déclaration de std::cout dans la portée globale

using namespace std; // rend std::cout accessible sous le nom « cout »

int cout() // définit notre propre fonction « cout » dans l'espace de noms global
{
    return 5;
}

int main()
{
    cout << "Hello, world!"; // Erreur de compilation ! Quel cout voulons-nous ici ? Celui de l'espace de noms std ou celui que nous avons défini ci-dessus ?

    return 0;
}

Le programme ci-dessus ne compile pas, car le compilateur ne peut plus déterminer si nous voulons la fonction cout que nous avons définie, ou std::cout.

Lorsqu'on utilise une directive using de cette manière, n'importe quel identifiant que nous définissons peut entrer en conflit avec n'importe quel identifiant de même nom dans l'espace de noms std. Pire encore, si un nom ne pose pas de problème aujourd'hui, il peut entrer en conflit avec de nouveaux identifiants ajoutés à l'espace de noms std lors de révisions futures du langage. C'est précisément le but de l'organisation de tous les identifiants de la bibliothèque standard dans l'espace de noms std.

Attention

Évitez les directives using (comme using namespace std;) en début de programme ou dans les fichiers d'en-tête. Elles vont à l'encontre de la raison même pour laquelle les espaces de noms ont été introduits.

Accolades et code indenté

En C++, les accolades servent souvent à délimiter une région de portée imbriquée dans une autre région de portée (les accolades ont aussi d'autres usages, non liés à la portée, comme l'initialisation par liste). Par exemple, une fonction définie dans la région de portée globale utilise des accolades pour séparer la région de portée de la fonction de la portée globale.

Dans certains cas, des identifiants définis en dehors des accolades peuvent néanmoins faire partie de la portée délimitée par ces accolades plutôt que de la portée environnante : les paramètres de fonction en sont un bon exemple.

Par exemple :

#include <iostream> // importe la déclaration de std::cout dans la portée globale

void foo(int x) // foo est défini dans la portée globale, x est défini dans la portée de foo()
{ // accolades délimitant la région de portée imbriquée de la fonction foo()
    std::cout << x << '\n';
} // x sort de portée ici

int main()
{ // accolades délimitant la région de portée imbriquée de la fonction main()
    foo(5);

    int x { 6 }; // x est défini dans la portée de main()
    std::cout << x << '\n';

    return 0;
} // x sort de portée ici
// foo et main (ainsi que std::cout) sortent de portée ici (la fin du fichier)

Le code situé à l'intérieur d'une région de portée imbriquée est, par convention, indenté d'un niveau, à la fois pour la lisibilité et pour indiquer qu'il se trouve dans une région de portée distincte.

Les #include et les définitions des fonctions foo() et main() se trouvent dans la région de portée globale ; ils ne sont donc pas indentés. Les instructions à l'intérieur de chaque fonction se trouvent dans la région de portée imbriquée de la fonction ; elles sont donc indentées d'un niveau.
