8.13 — Introduction à la génération de nombres aléatoires

La capacité de générer des nombres aléatoires est utile dans certains types de programmes, notamment les jeux, les programmes de modélisation statistique et les applications cryptographiques qui doivent chiffrer et déchiffrer des données. Prenons l'exemple des jeux : sans événements aléatoires, les monstres vous attaqueraient toujours de la même façon, vous trouveriez toujours le même trésor, la disposition du donjon ne changerait jamais, etc. Cela ne donnerait pas un très bon jeu.

Dans la vie réelle, nous produisons souvent de l'aléatoire en lançant une pièce de monnaie, en lançant un dé ou en battant un jeu de cartes. Ces événements ne sont pas vraiment aléatoires, mais ils dépendent de tant de variables physiques (gravité, frottement, résistance de l'air, quantité de mouvement, etc.) qu'ils deviennent presque impossibles à prévoir ou à contrôler. Sauf si vous êtes magicien, ils produisent des résultats qui sont, à toutes fins utiles, aléatoires.

Cependant, les ordinateurs ne sont pas conçus pour tirer parti de variables physiques : votre ordinateur ne peut pas lancer une pièce, lancer un dé ou battre de vraies cartes. Les ordinateurs modernes évoluent dans un monde électrique contrôlé où tout est binaire (0 ou 1), sans aucun entre-deux. Par nature, ils sont conçus pour produire des résultats aussi prévisibles que possible. Quand vous demandez à l'ordinateur de calculer 2 + 2, vous voulez toujours obtenir 4, et non 3 ou 5 de temps en temps.

Par conséquent, les ordinateurs sont généralement incapables de générer de véritables nombres aléatoires (du moins par logiciel). Les programmes modernes simulent donc généralement le hasard à l'aide d'un algorithme.

Dans cette leçon, nous allons aborder une grande partie de la théorie qui explique comment les nombres aléatoires sont générés dans les programmes, et introduire une terminologie que nous utiliserons dans les leçons suivantes.

Algorithmes et état

Commençons d'abord par un détour par les notions d'algorithme et d'état.

Un algorithme est une suite finie d'instructions qui peut être suivie pour résoudre un problème ou produire un résultat utile.

Par exemple, supposons que votre responsable vous remette un petit fichier texte contenant une liste de noms non triés (un par ligne) et vous demande de trier cette liste. Comme la liste est petite et que vous ne comptez pas le faire souvent, vous décidez de la trier à la main. Il existe plusieurs façons de trier une liste, mais vous pourriez procéder ainsi :

  • Créer une nouvelle liste vide pour accueillir les résultats triés
  • Parcourir la liste des noms non triés pour trouver le nom qui vient en premier dans l'ordre alphabétique
  • Couper ce nom de la liste non triée et le coller en bas de la liste triée
  • Répéter les deux étapes précédentes jusqu'à ce qu'il ne reste plus aucun nom dans la liste non triée

L'ensemble d'étapes ci-dessus décrit un algorithme de tri (exprimé en langage naturel). Par nature, les algorithmes sont réutilisables : si votre responsable vous demande de trier une autre liste demain, vous pouvez appliquer le même algorithme à la nouvelle liste.

Comme les ordinateurs peuvent exécuter des instructions et manipuler des données beaucoup plus vite que nous, les algorithmes sont souvent écrits dans des langages de programmation, ce qui nous permet d'automatiser des tâches. En C++, les algorithmes sont généralement implémentés sous forme de fonctions réutilisables.

Voici un algorithme simple qui génère une suite de nombres dont chaque nombre successif est augmenté de 1 :

#include <iostream>

int plusOne()
{
    static int s_state { 3 }; // n'est initialisée que la première fois que cette fonction est appelée

    // Générer le nombre suivant

    ++s_state;      // d'abord, nous modifions l'état
    return s_state; // puis nous utilisons le nouvel état pour générer le nombre suivant de la suite
}

int main()
{
    std::cout << plusOne() << '\n';
    std::cout << plusOne() << '\n';
    std::cout << plusOne() << '\n';

    return 0;
}

Ce programme affiche :


4
5
6

Cet algorithme est assez simple. La première fois que nous appelons plusOne(), s_state est initialisée à la valeur 3. Ensuite, le nombre suivant de la suite de sortie est généré et renvoyé.

Un algorithme est dit avec état (stateful) s'il conserve certaines informations d'un appel à l'autre. Inversement, un algorithme sans état (stateless) ne stocke aucune information (et doit recevoir, à chaque appel, toutes les informations dont il a besoin). Notre fonction plusOne() est avec état, car elle utilise la variable statique s_state pour stocker le dernier nombre généré. Appliqué aux algorithmes, le terme état désigne les valeurs courantes des variables avec état (celles qui sont conservées d'un appel à l'autre).

Pour générer le nombre suivant de la suite, notre algorithme procède en deux étapes :

  • D'abord, l'état courant (initialisé à partir de la valeur de départ, ou conservé depuis l'appel précédent) est modifié pour produire un nouvel état.
  • Ensuite, le nombre suivant de la suite est généré à partir du nouvel état.

Notre algorithme est dit déterministe, ce qui signifie que, pour une entrée donnée (la valeur fournie pour start), il produira toujours la même suite de sorties.

Générateurs de nombres pseudo-aléatoires (PRNG)

Pour simuler le hasard, les programmes utilisent généralement un générateur de nombres pseudo-aléatoires. Un générateur de nombres pseudo-aléatoires (PRNG, pseudo-random number generator) est un algorithme qui génère une suite de nombres dont les propriétés simulent une suite de nombres aléatoires.

Il est facile d'écrire un PRNG basique. Voici un court exemple de PRNG qui génère 100 nombres pseudo-aléatoires de 16 bits :

#include <iostream>

// Uniquement à des fins d'illustration, ne l'utilisez pas
unsigned int LCG16() // notre PRNG
{
    static unsigned int s_state{ 0 }; // n'est initialisée que la première fois que cette fonction est appelée

    // Générer le nombre suivant

    // Nous modifions l'état à l'aide de grandes constantes et d'un dépassement de capacité volontaire, afin qu'il soit
    // difficile pour quelqu'un de deviner facilement le prochain nombre de la suite.

    s_state = 8253729 * s_state + 2396403; // d'abord, nous modifions l'état
    return s_state % 32768; // puis nous utilisons le nouvel état pour générer le nombre suivant de la suite
}

int main()
{
    // Afficher 100 nombres aléatoires
    for (int count{ 1 }; count <= 100; ++count)
    {
        std::cout << LCG16() << '\t';

        // Si nous avons affiché 10 nombres, commencer une nouvelle ligne
        if (count % 10 == 0)
            std::cout << '\n';
    }

    return 0;
}

Remarquez à quel point LCG16() ressemble à notre exemple plusOne() ci-dessus ! L'état est initialisé à la valeur 0. Ensuite, pour produire le nombre suivant de la suite de sortie, l'état courant est modifié (par application d'opérations mathématiques) pour produire un nouvel état, et le nombre suivant de la suite est généré à partir de ce nouvel état.

En réalité, cet algorithme particulier n'est pas très bon comme générateur de nombres aléatoires (remarquez que chaque résultat alterne entre pair et impair, ce qui n'est pas très aléatoire !). Mais la plupart des PRNG fonctionnent de façon similaire à LCG16() : ils utilisent simplement davantage de variables d'état et des opérations mathématiques plus complexes afin de produire de meilleurs résultats.

Initialisation (seeding) d'un PRNG

La suite de « nombres aléatoires » générée par un PRNG n'a rien d'aléatoire. Tout comme notre fonction plusOne(), LCG16() est déterministe. Pour une valeur d'état initiale donnée (par exemple 0), un PRNG générera toujours la même suite de nombres. Si vous exécutez le programme ci-dessus 3 fois, vous verrez qu'il génère chaque fois la même suite de valeurs.

Pour obtenir des suites de sortie différentes, l'état initial d'un PRNG doit donc varier. La valeur (ou l'ensemble de valeurs) utilisée pour fixer l'état initial d'un PRNG s'appelle une graine aléatoire (random seed, ou simplement seed). Lorsque l'état initial d'un PRNG a été fixé à l'aide d'une graine, on dit qu'il a été initialisé (seeded).

Point clé

Comme l'état initial du PRNG est fixé à partir de la ou des valeurs de la graine, toutes les valeurs que produit un PRNG sont calculées de façon déterministe à partir de cette ou ces valeurs.

La valeur de la graine est généralement fournie par le programme qui utilise le PRNG. Voici un exemple de programme qui demande à l'utilisateur une valeur de graine, puis génère 10 nombres aléatoires à partir de cette valeur (en utilisant notre fonction LCG16()).

#include <iostream>

unsigned int g_state{ 0 };

void seedPRNG(unsigned int seed)
{
    g_state = seed;
}

// Uniquement à des fins d'illustration, ne l'utilisez pas
unsigned int LCG16() // notre PRNG
{
    // Nous modifions l'état à l'aide de grandes constantes et d'un dépassement de capacité volontaire, afin qu'il soit
    // difficile pour quelqu'un de deviner facilement le prochain nombre de la suite.

    g_state = 8253729 * g_state + 2396403; // d'abord, nous modifions l'état
    return g_state % 32768; // puis nous utilisons le nouvel état pour générer le nombre suivant de la suite
}

void print10()
{
    // Afficher 10 nombres aléatoires
    for (int count{ 1 }; count <= 10; ++count)
    {
        std::cout << LCG16() << '\t';
    }   

    std::cout << '\n';
}

int main()
{
    unsigned int x {};
    std::cout << "Entrez une valeur de graine : ";
    std::cin >> x;

    seedPRNG(x); // initialiser notre PRNG
    print10();   // générer 10 valeurs aléatoires

    return 0;
}

Qualité de la graine et sous-initialisation

Si nous voulons que le programme produise des nombres aléatoires différents à chaque exécution, il faut un moyen de faire varier la graine à chaque lancement. Demander à l'utilisateur de fournir une valeur de graine n'est pas idéal, car il peut simplement entrer chaque fois la même valeur. Le programme a réellement besoin d'un moyen de générer une valeur de graine aléatoire à chaque exécution. Malheureusement, nous ne pouvons pas utiliser un PRNG pour générer une graine aléatoire, car nous avons besoin d'une graine aléatoire pour générer des nombres aléatoires. Nous utiliserons donc généralement un algorithme de génération de graines, conçu pour produire des valeurs de graine. Nous étudierons (et implémenterons) de tels algorithmes dans la prochaine leçon.

Le nombre maximal théorique de suites uniques qu'un PRNG peut générer est déterminé par le nombre de bits de l'état du PRNG. Par exemple, un PRNG dont l'état fait 128 bits peut théoriquement générer jusqu'à 2^128 (340 282 366 920 938 463 463 374 607 431 768 211 456) suites de sortie uniques. C'est énorme !

Cependant, la suite de sortie qui est effectivement générée dépend de l'état initial du PRNG, lui-même déterminé par la graine. Par conséquent, en pratique, le nombre de suites de sortie uniques qu'un PRNG peut réellement générer est limité par le nombre de valeurs de graine uniques que le programme utilisant le PRNG peut fournir. Par exemple, si un algorithme de génération de graines ne peut produire que 4 valeurs de graine différentes, le PRNG ne pourra générer au plus que 4 suites de sortie différentes.

Si un PRNG ne reçoit pas assez de bits de données de graine de qualité, on dit qu'il est sous-initialisé (underseeded). Un PRNG sous-initialisé peut commencer à produire des résultats aléatoires dont la qualité est altérée d'une façon ou d'une autre, et plus la sous-initialisation est sévère, plus la qualité des résultats se dégrade.

Par exemple, un PRNG sous-initialisé peut présenter l'un des problèmes suivants :

  • Les suites aléatoires produites par des exécutions successives peuvent être fortement corrélées entre elles.
  • Lors de la génération du N-ième nombre aléatoire, certaines valeurs ne pourront jamais être générées. Par exemple, un Mersenne Twister sous-initialisé d'une certaine façon ne produira jamais les valeurs 7 ou 13 comme première sortie.
  • Quelqu'un peut être capable de deviner la graine à partir de la valeur aléatoire initiale produite (ou des quelques premières valeurs). Il peut alors générer tous les nombres aléatoires futurs produits par le générateur, ce qui peut lui permettre de tricher ou de manipuler le système.

Pour les lecteurs avancés

Une graine idéale devrait présenter les caractéristiques suivantes :

  • La graine devrait contenir au moins autant de bits que l'état du PRNG, afin que chaque bit de l'état du PRNG puisse être initialisé par un bit indépendant de la graine.
  • Chaque bit de la graine devrait être randomisé de façon indépendante.
  • La graine devrait contenir un bon mélange de 0 et de 1, répartis sur l'ensemble des bits.
  • Aucun bit de la graine ne devrait être toujours à 0 ou toujours à 1. Ces « bits bloqués » n'apportent aucune valeur.
  • La graine devrait avoir une faible corrélation avec les graines générées précédemment.

En pratique, il arrive que nous devions faire des concessions sur certaines de ces caractéristiques. Certains PRNG ont des états énormes (par exemple, l'état d'un Mersenne Twister compte 19937 bits), et générer des graines de qualité d'une telle taille peut être difficile. Par conséquent, les PRNG à grands états sont souvent conçus pour résister à une initialisation avec moins de bits. Les bits bloqués sont aussi courants. Par exemple, si nous utilisons l'horloge système dans notre graine, nous obtiendrons un certain nombre de bits bloqués, car les bits qui représentent de grandes unités de temps (par exemple les années) restent en pratique fixes.

Les développeurs qui ne connaissent pas les bonnes pratiques d'initialisation essaient souvent d'initialiser un PRNG avec une seule valeur de 32 ou 64 bits (malheureusement, la conception de la bibliothèque standard Random de C++ encourage involontairement cette pratique). Cela donne généralement un PRNG fortement sous-initialisé.

Initialiser un PRNG avec 64 octets de données de graine de qualité (moins si l'état du PRNG est plus petit) suffit généralement pour générer des valeurs aléatoires de 8 octets pour des usages non sensibles (par exemple, pas pour des simulations statistiques ou de la cryptographie).

Qu'est-ce qu'un bon PRNG ? (lecture facultative)

Pour être un bon PRNG, un générateur doit présenter un certain nombre de propriétés :

  • Le PRNG devrait générer chaque nombre avec à peu près la même probabilité.

C'est ce qu'on appelle l'uniformité de la distribution. Si certains nombres sont générés plus souvent que d'autres, le résultat du programme qui utilise le PRNG sera biaisé ! Pour vérifier l'uniformité de la distribution, nous pouvons utiliser un histogramme. Un histogramme est un graphique qui compte combien de fois chaque nombre a été généré. Comme nos histogrammes sont textuels, nous utiliserons le symbole * pour représenter chaque fois qu'un nombre donné a été généré.

Considérons un PRNG qui génère des nombres entre 1 et 6. Si nous générons 36 nombres, un PRNG à distribution uniforme devrait produire un histogramme qui ressemble à ceci :


1|******
2|******
3|******
4|******
5|******
6|******

Un PRNG biaisé d'une façon ou d'une autre produira un histogramme irrégulier, comme ceci :

2|******
3|******
4|******
5|******
6|*********

ou bien ceci :


1|****
2|********
3|******
4|********
5|******
6|****

ou même ceci :


1|*******
2|********
3|*******
4|********
5|
6|******

Supposons que vous écriviez un générateur aléatoire d'objets pour un jeu. Quand un monstre est tué, votre code génère un nombre aléatoire entre 1 et 6 ; si le résultat est 6, le monstre laisse tomber un objet rare au lieu d'un objet commun. Vous vous attendez à une chance sur 6 que cela se produise. Mais si le PRNG sous-jacent n'est pas uniforme et génère beaucoup plus de 6 qu'il ne le devrait (comme dans le second histogramme ci-dessus), vos joueurs obtiendront plus d'objets rares que prévu, ce qui pourrait trivialiser la difficulté de votre jeu ou perturber son économie interne.

Trouver des algorithmes de PRNG qui produisent des résultats uniformes est difficile.

  • La méthode par laquelle le nombre suivant de la suite est généré ne devrait pas être prévisible.

Par exemple, considérons l'algorithme de PRNG suivant : return ++num. Ce PRNG est parfaitement uniforme, mais il est aussi complètement prévisible, et peu utile comme suite de nombres aléatoires !

Même des suites de nombres qui semblent aléatoires à l'œil (comme la sortie de LCG16() ci-dessus) peuvent être trivialement prévisibles par quelqu'un de déterminé. En examinant seulement quelques nombres générés par la fonction LCG16() ci-dessus, il est possible de déterminer les constantes utilisées (8253729 et 2396403) pour modifier l'état. Une fois cela connu, il devient trivial de calculer tous les nombres futurs que ce PRNG produira.

Imaginez maintenant que vous exploitiez un site de paris en ligne où les utilisateurs peuvent miser 100 $. Votre site génère ensuite un nombre aléatoire entre 0 et 32767. Si ce nombre est supérieur à 20000, le client gagne et vous lui rendez le double de sa mise. Sinon, il perd et vous gardez la mise. Comme le client ne gagne que 12767/32767 (39 %) du temps, votre site devrait gagner énormément d'argent, non ? Pourtant, si les clients sont capables de déterminer quels nombres seront générés ensuite, ils peuvent placer leurs paris de façon stratégique et gagner à coup sûr, ou presque. Félicitations, vous allez pouvoir déposer le bilan !

  • Le PRNG devrait avoir une bonne distribution dimensionnelle des nombres.

Cela signifie que le PRNG devrait renvoyer des nombres de façon aléatoire sur toute la plage des résultats possibles. Par exemple, le PRNG devrait générer des nombres petits, moyens et grands, pairs et impairs, d'une manière qui paraisse aléatoire.

Un PRNG qui renverrait d'abord uniquement des petits nombres, puis uniquement des grands nombres, pourrait être uniforme et non prévisible, mais il conduirait tout de même à des résultats biaisés, en particulier si le nombre de nombres aléatoires réellement utilisés est petit.

  • Le PRNG devrait avoir une période élevée pour toutes les graines.

Tous les PRNG sont périodiques, ce qui signifie qu'à un moment donné la suite de nombres générés commence à se répéter. La longueur de la suite avant que le PRNG ne commence à se répéter s'appelle la période.

Vous remarquerez qu'il a généré 9 comme 2e nombre, à nouveau comme 16e nombre, puis tous les 14 nombres ensuite. Ce PRNG est coincé à générer en boucle la suite suivante : 9-130-97-64-31-152-119-86-53-20-141-108-75-42-(répétition).

Cela se produit parce que les PRNG sont déterministes. Dès que l'état d'un PRNG redevient identique à un état antérieur, le PRNG recommence à produire la même suite de sorties qu'auparavant, ce qui forme une boucle.

Un bon PRNG devrait avoir une longue période pour toutes les graines. Concevoir un algorithme qui satisfait cette propriété peut être extrêmement difficile : de nombreux PRNG n'ont une longue période que pour certaines graines et pas pour d'autres. Si l'utilisateur choisit par hasard une graine qui conduit à un état de courte période, le PRNG ne fera pas du bon travail si beaucoup de nombres aléatoires sont nécessaires.

  • Le PRNG devrait être efficace.

La plupart des PRNG ont un état de moins de 4096 octets, de sorte que la consommation totale de mémoire n'est généralement pas un problème. Cependant, plus l'état interne est grand, plus le PRNG risque d'être sous-initialisé, et plus l'initialisation initiale sera lente (puisqu'il y a davantage d'état à initialiser).

Ensuite, pour générer le nombre suivant de la suite, un PRNG doit mélanger son état interne en appliquant diverses opérations mathématiques. Le temps que cela prend peut varier de façon significative selon le PRNG et selon l'architecture (certains PRNG sont plus performants sur certaines architectures que sur d'autres). Cela n'a pas d'importance si vous ne générez des nombres aléatoires que de temps en temps, mais cela peut avoir un impact énorme si vous avez besoin de beaucoup d'aléatoire.

Il existe de nombreux types d'algorithmes PRNG

Au fil des années, de nombreux types d'algorithmes PRNG ont été développés (Wikipédia propose une bonne liste ici). Chaque algorithme de PRNG a ses forces et ses faiblesses, qui peuvent le rendre plus ou moins adapté à une application donnée. Choisir le bon algorithme pour votre application est donc important.

De nombreux PRNG sont aujourd'hui considérés comme médiocres selon les standards modernes, et il n'y a aucune raison d'utiliser un PRNG peu performant alors qu'il est tout aussi facile d'en utiliser un qui fonctionne bien.

Un test appelé PracRand est souvent utilisé pour évaluer les performances et la qualité des PRNG (afin de déterminer s'ils présentent différents types de biais). Vous pouvez aussi rencontrer les mentions de SmallCrush, Crush ou BigCrush : ce sont d'autres tests parfois utilisés dans le même but.

Donc on devrait utiliser Mersenne Twister, non ?

Probablement. Pour la plupart des applications, Mersenne Twister convient, tant du point de vue des performances que de la qualité.

Il faut toutefois noter que, selon les standards modernes des PRNG, Mersenne Twister est un peu dépassé. Le principal problème de Mersenne Twister est que ses résultats peuvent être prédits après l'observation de 624 nombres générés, ce qui le rend inadapté à toute application exigeant de la non-prévisibilité.

Si vous développez une application qui requiert les résultats aléatoires de la plus haute qualité (par exemple une simulation statistique), les résultats les plus rapides, ou une application où la non-prévisibilité est importante (par exemple la cryptographie), vous devrez utiliser une bibliothèque tierce.

Choix populaires au moment de la rédaction :

  • La famille Xoshiro et Wyrand pour les PRNG non cryptographiques.
  • La famille ChaCha pour les PRNG cryptographiques (non prévisibles).
