7.10 — Partager des constantes globales entre plusieurs fichiers (à l'aide de variables inline)

Dans certaines applications, certaines constantes symboliques peuvent devoir être utilisées partout dans votre code (et pas seulement à un seul endroit). Il peut s'agir de constantes physiques ou mathématiques qui ne changent pas (par exemple pi ou le nombre d'Avogadro), ou de valeurs de « réglage » propres à l'application (par exemple des coefficients de frottement ou de gravité). Plutôt que de redéfinir ces constantes dans chaque fichier qui en a besoin (ce qui viole la règle « Ne vous répétez pas » (Don't Repeat Yourself)), il est préférable de les déclarer une seule fois dans un emplacement central et de les utiliser partout où c'est nécessaire. Ainsi, si vous devez les modifier, il suffit de le faire à un seul endroit, et ces changements se propagent ensuite dans tout le programme.

Cette leçon présente les façons les plus courantes d'y parvenir.

Constantes globales sous forme de variables internes

Avant C++17, la solution suivante est la plus simple et la plus courante :

  1. Créer un fichier d'en-tête qui contiendra ces constantes
  2. Dans ce fichier d'en-tête, définir un espace de noms (abordé dans la leçon 7.2 -- Espaces de noms définis par l'utilisateur et opérateur de résolution de portée)
  3. Placer toutes vos constantes dans cet espace de noms (assurez-vous qu'elles sont constexpr)
  4. Utiliser #include pour inclure cet en-tête partout où vous en avez besoin

Par exemple :

constants.h :

#ifndef CONSTANTS_H
#define CONSTANTS_H

// Définir votre propre espace de noms pour contenir les constantes
namespace constants
{
    // Les constantes globales ont par défaut un lien interne
    constexpr double pi { 3.14159 };
    constexpr double avogadro { 6.0221413e23 };
    constexpr double myGravity { 9.2 }; // m/s^2 -- la gravité est faible sur cette planète
    // ... autres constantes liées
}
#endif

Ensuite, pour accéder à vos constantes dans les fichiers .cpp, utilisez l'opérateur de résolution de portée (::) avec le nom de l'espace de noms à gauche et le nom de la variable à droite :

main.cpp :

#include "constants.h" // inclut une copie de chaque constante dans ce fichier

#include <iostream>

int main()
{
    std::cout << "Enter a radius: ";
    double radius{};
    std::cin >> radius;

    std::cout << "The circumference is: " << 2 * radius * constants::pi << '\n';

    return 0;
}

Lorsque cet en-tête est inclus dans un fichier .cpp, chacune des variables qu'il définit est copiée dans ce fichier de code à l'endroit de l'inclusion. Comme ces variables sont situées en dehors de toute fonction, elles sont traitées comme des variables globales dans le fichier où elles sont incluses, ce qui explique que vous puissiez les utiliser n'importe où dans ce fichier.

Comme les globales const ont un lien interne, chaque fichier .cpp obtient une version indépendante de la variable globale, que l'éditeur de liens (linker) ne voit pas. Dans la plupart des cas, comme il s'agit de constexpr, le compilateur se contente d'éliminer ces variables lors de l'optimisation.

Bien que cette méthode soit simple (et convienne pour les petits programmes), chaque fois que constants.h est inclus dans un fichier de code différent, chacune de ces variables est copiée dans le fichier qui l'inclut. Ainsi, si constants.h est inclus dans 20 fichiers de code différents, chacune de ces variables est dupliquée 20 fois. Les gardes d'inclusion n'empêchent pas ce phénomène : elles évitent seulement qu'un en-tête soit inclus plusieurs fois dans un même fichier, et non qu'il soit inclus une fois dans plusieurs fichiers de code différents. Cela pose deux problèmes :

  1. Modifier la valeur d'une seule constante obligerait à recompiler chaque fichier qui inclut l'en-tête des constantes, ce qui peut entraîner des temps de reconstruction longs pour les projets plus importants.
  2. Si les constantes sont volumineuses et ne peuvent pas être éliminées à l'optimisation, cela peut consommer beaucoup de mémoire.

Avantages :

  • Fonctionne avant C++17.
  • Peut être utilisée dans des expressions constantes dans n'importe quelle unité de traduction qui les inclut.

Inconvénients :

  • Toute modification du fichier d'en-tête oblige à recompiler les fichiers qui l'incluent.
  • Chaque unité de traduction qui inclut l'en-tête possède sa propre copie de la variable.

Constantes globales sous forme de variables externes

Si vous modifiez souvent les valeurs ou ajoutez régulièrement de nouvelles constantes, la solution précédente peut poser problème, du moins jusqu'à ce que les choses se stabilisent.

Une façon d'éviter ces problèmes consiste à transformer ces constantes en variables externes, puisqu'on peut alors disposer d'une seule variable (initialisée une fois) partagée par tous les fichiers. Dans cette méthode, on définit les constantes dans un fichier .cpp (pour que les définitions n'existent qu'à un seul endroit) et on place des déclarations anticipées (forward declarations) dans l'en-tête (qui sera inclus par les autres fichiers).

constants.cpp :

#include "constants.h"

namespace constants
{
    // On utilise extern pour garantir que ces variables ont un lien externe
    extern constexpr double pi { 3.14159 };
    extern constexpr double avogadro { 6.0221413e23 };
    extern constexpr double myGravity { 9.2 }; // m/s^2 -- la gravité est faible sur cette planète
}

constants.h :

#ifndef CONSTANTS_H
#define CONSTANTS_H

namespace constants
{
    // Comme les variables réelles se trouvent dans un espace de noms, les déclarations anticipées doivent aussi être dans cet espace de noms
    // On ne peut pas déclarer à l'avance des variables constexpr, mais on peut les déclarer comme const (à l'exécution)
    extern const double pi;
    extern const double avogadro;
    extern const double myGravity;
}

#endif

L'utilisation dans le fichier de code reste la même :

main.cpp :

#include "constants.h" // inclut toutes les déclarations anticipées

#include <iostream>

int main()
{
    std::cout << "Enter a radius: ";
    double radius{};
    std::cin >> radius;

    std::cout << "The circumference is: " << 2 * radius * constants::pi << '\n';

    return 0;
}

Désormais, les constantes symboliques ne sont instanciées qu'une seule fois (dans constants.cpp) au lieu de l'être dans chaque fichier de code où constants.h est inclus, et toutes les utilisations de ces constantes sont liées à la version instanciée dans constants.cpp. Toute modification de constants.cpp nécessite seulement de recompiler constants.cpp.

Cette méthode présente toutefois quelques inconvénients. D'abord, comme seules les définitions de variables sont constexpr (les déclarations anticipées ne le sont pas, et ne peuvent pas l'être), ces constantes ne sont des expressions constantes que dans le fichier où elles sont réellement définies (constants.cpp). Dans les autres fichiers, le compilateur ne voit que la déclaration anticipée, qui ne définit pas de valeur constexpr (et doit être résolue par l'éditeur de liens). Cela signifie qu'en dehors du fichier de définition, ces variables ne peuvent pas être utilisées dans une expression constante. Ensuite, comme les expressions constantes peuvent généralement être davantage optimisées que les expressions évaluées à l'exécution, le compilateur risque de ne pas pouvoir les optimiser autant.

Point clé

Pour qu'une variable puisse être utilisée dans un contexte de compilation, comme la taille d'un tableau, le compilateur doit voir la définition de la variable (et pas seulement une déclaration anticipée).

Comme le compilateur compile chaque fichier source individuellement, il ne peut voir que les définitions de variables qui apparaissent dans le fichier source compilé (y compris les en-têtes inclus). Par exemple, les définitions de variables de constants.cpp ne sont pas visibles lorsque le compilateur compile main.cpp. Pour cette raison, les variables constexpr ne peuvent pas être séparées entre un en-tête et un fichier source : elles doivent être définies dans le fichier d'en-tête.

Compte tenu des inconvénients ci-dessus, privilégiez la définition de vos constantes dans un fichier d'en-tête (selon la section précédente ou la suivante). Si vous constatez que les valeurs de vos constantes changent souvent (par exemple parce que vous ajustez le programme) et que cela allonge fortement les temps de compilation, vous pouvez temporairement déplacer uniquement les constantes concernées dans un fichier .cpp (avec cette méthode), au besoin.

Avantages :

  • Fonctionne avant C++17.
  • Une seule copie de chaque variable est nécessaire.
  • Seule la recompilation d'un fichier est nécessaire si la valeur d'une constante change.

Inconvénients :

  • Les déclarations anticipées et les définitions de variables se trouvent dans des fichiers séparés, et doivent être tenues synchronisées.
  • Les variables ne peuvent pas être utilisées dans des expressions constantes en dehors du fichier où elles sont définies.

Constantes globales sous forme de variables inline (C++17)

Dans la leçon 7.9 -- Fonctions et variables inline, nous avons abordé les variables inline, c'est-à-dire des variables pouvant posséder plusieurs définitions, à condition que ces définitions soient identiques. En rendant nos variables constexpr inline, nous pouvons les définir dans un fichier d'en-tête, puis inclure celui-ci dans n'importe quel fichier .cpp qui en a besoin. Cela évite à la fois les violations de la règle de définition unique (ODR) et l'inconvénient des variables dupliquées.

Rappel

Les fonctions constexpr sont implicitement inline, mais les variables constexpr ne le sont pas implicitement. Si vous voulez une variable constexpr inline, vous devez explicitement la marquer avec inline.

Point clé

Les variables inline ont par défaut un lien externe, afin d'être visibles par l'éditeur de liens. C'est nécessaire pour que l'éditeur de liens puisse fusionner les définitions en double.

Les variables constexpr non inline ont un lien interne. Si elles sont incluses dans plusieurs unités de traduction, chaque unité de traduction obtient sa propre copie de la variable. Ce n'est pas une violation de la règle ODR, car elles ne sont pas exposées à l'éditeur de liens.

constants.h :

#ifndef CONSTANTS_H
#define CONSTANTS_H

// Définir votre propre espace de noms pour contenir les constantes
namespace constants
{
    inline constexpr double pi { 3.14159 }; // note : désormais inline constexpr
    inline constexpr double avogadro { 6.0221413e23 };
    inline constexpr double myGravity { 9.2 }; // m/s^2 -- la gravité est faible sur cette planète
    // ... autres constantes liées
}
#endif

main.cpp :

#include "constants.h"

#include <iostream>

int main()
{
    std::cout << "Enter a radius: ";
    double radius{};
    std::cin >> radius;

    std::cout << "The circumference is: " << 2 * radius * constants::pi << '\n';

    return 0;
}

Nous pouvons inclure constants.h dans autant de fichiers de code que nous le souhaitons : ces variables ne seront instanciées qu'une seule fois et partagées par tous les fichiers de code.

Cette méthode conserve néanmoins l'inconvénient de devoir recompiler chaque fichier qui inclut l'en-tête des constantes si la valeur d'une constante est modifiée.

Avantages :

  • Peut être utilisée dans des expressions constantes dans n'importe quelle unité de traduction qui les inclut.
  • Une seule copie de chaque variable est nécessaire.

Inconvénients :

  • Fonctionne uniquement à partir de C++17.
  • Toute modification du fichier d'en-tête oblige à recompiler les fichiers qui l'incluent.

Bonne pratique

Si vous avez besoin de constantes globales et que votre compilateur prend en charge C++17, privilégiez la définition de variables globales inline constexpr dans un fichier d'en-tête.
