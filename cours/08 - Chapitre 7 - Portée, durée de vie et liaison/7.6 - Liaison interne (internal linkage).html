7.6 — Liaison interne (internal linkage)

Dans la leçon 7.3 -- Variables locales, nous avons dit : « Le lien (linkage) d'un identifiant détermine si d'autres déclarations de ce nom font référence au même objet ou non », et nous avons vu que les variables locales n'ont aucun lien (no linkage).

Les variables globales et les identifiants de fonctions peuvent avoir soit une liaison interne (internal linkage), soit une liaison externe (external linkage). Nous traiterons le cas de la liaison interne dans cette leçon, et celui de la liaison externe dans la leçon 7.7 -- Liaison externe et déclarations anticipées de variables.

Un identifiant ayant une liaison interne ne peut être vu et utilisé qu'au sein d'une seule unité de traduction, et il n'est pas accessible depuis d'autres unités de traduction. Cela signifie que si deux fichiers sources contiennent des identifiants portant le même nom et ayant une liaison interne, ces identifiants sont traités comme indépendants (et cela ne provoque pas de violation de la ODR pour définitions multiples).

Point clé

Les identifiants ayant une liaison interne peuvent ne pas être visibles du tout par l'éditeur de liens (linker). Dans d'autres cas, ils peuvent être visibles pour l'éditeur de liens, mais marqués comme utilisables uniquement dans une unité de traduction précise.

Contenu associé

Nous abordons les unités de traduction dans la leçon 2.10 -- Introduction au préprocesseur.

Variables globales à liaison interne

Les variables globales ayant une liaison interne sont parfois appelées variables internes.

Pour rendre une variable globale non constante interne, on utilise le mot-clé static.

#include <iostream>

static int g_x{}; // les globales non constantes ont une liaison externe par défaut, mais peuvent recevoir une liaison interne via le mot-clé static

const int g_y{ 1 }; // les globales const ont une liaison interne par défaut
constexpr int g_z{ 2 }; // les globales constexpr ont une liaison interne par défaut

int main()
{
    std::cout << g_x << ' ' << g_y << ' ' << g_z << '\n';
    return 0;
}

Les variables globales const et constexpr ont une liaison interne par défaut (elles n'ont donc pas besoin du mot-clé static -- s'il est utilisé, il sera ignoré).

Voici un exemple de plusieurs fichiers utilisant des variables internes :

a.cpp :

[[maybe_unused]] constexpr int g_x { 2 }; // ce g_x interne n'est accessible que dans a.cpp

main.cpp :

#include <iostream>

static int g_x { 3 }; // ce g_x interne distinct n'est accessible que dans main.cpp

int main()
{
    std::cout << g_x << '\n'; // utilise le g_x de main.cpp, affiche 3

    return 0;
}

Ce programme affiche :


3

Comme g_x est interne à chaque fichier, main.cpp ignore totalement que a.cpp possède une variable nommée g_x (et réciproquement).

Pour les lecteurs avancés

L'utilisation du mot-clé static ci-dessus est un exemple de spécificateur de classe de stockage (storage class specifier), qui définit à la fois la liaison du nom et sa durée de stockage. Les spécificateurs de classe de stockage les plus couramment utilisés sont static, extern et mutable. Le terme storage class specifier est surtout employé dans la documentation technique.

Pour les lecteurs avancés

La norme C++11 (annexe C) explique pourquoi les variables const ont une liaison interne par défaut : « Comme les objets const peuvent être utilisés comme valeurs à la compilation en C++, cette fonctionnalité incite les programmeurs à fournir des valeurs d'initialisation explicites pour chaque const. Cette fonctionnalité permet à l'utilisateur de placer des objets const dans des fichiers d'en-tête inclus dans de nombreuses unités de compilation. »

Les concepteurs de C++ visaient deux choses :

  • Les objets const doivent pouvoir être utilisés dans des expressions constantes. Pour être utilisable dans une expression constante, le compilateur doit avoir vu une définition (et non une déclaration) afin de pouvoir l'évaluer à la compilation.
  • Les objets const doivent pouvoir être propagés via des fichiers d'en-tête.

Les objets ayant une liaison externe ne peuvent être définis que dans une seule unité de traduction sans violer la ODR -- les autres unités de traduction doivent accéder à ces objets via une déclaration anticipée. Si les objets const avaient une liaison externe par défaut, ils ne pourraient être utilisés dans des expressions constantes que dans l'unité de traduction contenant la définition, et ils ne pourraient pas être propagés efficacement via des fichiers d'en-tête, car un #include de cet en-tête dans plus d'un fichier source provoquerait une violation de la ODR.

Les objets ayant une liaison interne peuvent avoir une définition dans chaque unité de traduction où ils sont nécessaires sans violer la ODR. Cela permet de placer des objets const dans un fichier d'en-tête et de l'inclure dans autant d'unités de traduction que souhaité sans violer la ODR. Et comme chaque unité de traduction contient une définition plutôt qu'une déclaration, cela garantit que ces constantes peuvent être utilisées dans des expressions constantes au sein de l'unité de traduction.

Les variables inline (qui peuvent avoir une liaison externe sans provoquer de violation de la ODR) n'ont été introduites qu'avec C++17.

Fonctions à liaison interne

Comme indiqué précédemment, les identifiants de fonctions ont également une liaison. Les fonctions ont par défaut une liaison externe (que nous verrons dans la prochaine leçon), mais peuvent recevoir une liaison interne via le mot-clé static :

add.cpp :

// Cette fonction est déclarée static et ne peut désormais être utilisée que dans ce fichier
// Une tentative d'y accéder depuis un autre fichier via une déclaration anticipée de fonction échouera
[[maybe_unused]] static int add(int x, int y)
{
    return x + y;
}

main.cpp :

#include <iostream>

int add(int x, int y); // déclaration anticipée de la fonction add

int main()
{
    std::cout << add(3, 4) << '\n';

    return 0;
}

Ce programme ne sera pas lié (édition de liens), car la fonction add n'est pas accessible en dehors de add.cpp.

La règle de définition unique et la liaison interne

Dans la leçon 2.7 -- Déclarations anticipées et définitions, nous avons indiqué que la règle de définition unique (ODR) stipule qu'un objet ou une fonction ne peut avoir plus d'une définition, que ce soit au sein d'un fichier ou d'un programme.

Il convient toutefois de noter que les objets internes (et fonctions internes) définis dans des fichiers différents sont considérés comme des entités indépendantes (même si leurs noms et types sont identiques), et il n'y a donc pas de violation de la ODR. Chaque objet interne ne possède qu'une seule définition.

static ou espaces de noms anonymes

En C++ moderne, l'usage du mot-clé static pour donner une liaison interne aux identifiants tend à être abandonné. Les espaces de noms anonymes (unnamed namespaces) peuvent donner une liaison interne à un éventail plus large d'identifiants (par exemple les identifiants de types), et ils sont mieux adaptés pour donner une liaison interne à de nombreux identifiants.

Nous traitons des espaces de noms anonymes dans la leçon 7.14 -- Espaces de noms anonymes et en ligne.

Pourquoi se donner la peine de donner une liaison interne aux identifiants ?

Il y a généralement deux raisons de donner une liaison interne à des identifiants :

  • Il existe un identifiant que l'on veut empêcher d'être accessible depuis d'autres fichiers. Il peut s'agir d'une variable globale que l'on ne veut pas voir modifiée, ou d'une fonction auxiliaire que l'on ne veut pas voir appelée.
  • Pour éviter scrupuleusement les collisions de noms. Comme les identifiants à liaison interne ne sont pas exposés à l'éditeur de liens, ils ne peuvent entrer en collision qu'avec des noms de la même unité de traduction, et non de tout le programme.

De nombreux guides de développement modernes recommandent de donner une liaison interne à toute variable et à toute fonction qui n'est pas destinée à être utilisée depuis un autre fichier. Si vous en avez la discipline, c'est une bonne recommandation.

Pour l'instant, nous recommandons une approche plus souple comme minimum : donnez une liaison interne à tout identifiant pour lequel vous avez une raison explicite d'interdire l'accès depuis d'autres fichiers.

Bonne pratique

Donnez une liaison interne aux identifiants lorsque vous avez une raison explicite d'interdire leur accès depuis d'autres fichiers.

Envisagez de donner une liaison interne à tous les identifiants que vous ne souhaitez pas rendre accessibles aux autres fichiers (utilisez un espace de noms anonyme pour cela).

Résumé rapide

// Définitions de variables globales internes :
static int g_x;          // définit une variable globale interne non initialisée (initialisée à zéro par défaut)
static int g_x{ 1 };     // définit une variable globale interne initialisée

const int g_y { 2 };     // définit une variable globale interne const initialisée
constexpr int g_y { 3 }; // définit une variable globale interne constexpr initialisée

// Définitions de fonctions internes :
static int foo() {};     // définit une fonction interne
