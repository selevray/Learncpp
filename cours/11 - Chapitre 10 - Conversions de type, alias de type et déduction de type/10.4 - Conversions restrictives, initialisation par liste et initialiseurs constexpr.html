10.4 — Conversions restrictives, initialisation par liste et initialiseurs constexpr

Dans la leçon précédente (10.3 -- Conversions numériques), nous avons étudié les conversions numériques, qui recouvrent un large éventail de conversions de types entre types fondamentaux.

Conversions restrictives

En C++, une conversion restrictive (narrowing conversion) est une conversion numérique potentiellement dangereuse, dans laquelle le type de destination peut ne pas être capable de représenter toutes les valeurs du type source.

Les conversions suivantes sont définies comme restrictives :

  • D'un type à virgule flottante vers un type entier.
  • D'un type à virgule flottante vers un type à virgule flottante plus étroit ou de rang inférieur, sauf si la valeur convertie est constexpr et se situe dans l'intervalle du type de destination (même si le type de destination n'a pas la précision nécessaire pour stocker tous les chiffres significatifs du nombre).
  • D'un type entier vers un type à virgule flottante, sauf si la valeur convertie est constexpr et si sa valeur peut être stockée exactement dans le type de destination.
  • D'un type entier vers un autre type entier qui ne peut pas représenter toutes les valeurs du type d'origine, sauf si la valeur convertie est constexpr et si sa valeur peut être stockée exactement dans le type de destination. Cela couvre aussi bien les conversions vers un type entier plus étroit que les conversions de signe entre entiers (signé vers non signé, ou inversement).

Dans la plupart des cas, les conversions restrictives implicites provoquent des avertissements du compilateur, à l'exception des conversions signé/non signé (qui peuvent ou non produire un avertissement, selon la configuration de votre compilateur).

Les conversions restrictives doivent être évitées autant que possible, car elles sont potentiellement dangereuses et donc sources d'erreurs potentielles.

Bonne pratique

Comme elles peuvent être dangereuses et sont sources d'erreurs, évitez les conversions restrictives chaque fois que c'est possible.

Rendre explicites les conversions restrictives intentionnelles

Les conversions restrictives ne sont pas toujours évitables. C'est particulièrement vrai pour les appels de fonctions, où le paramètre et l'argument peuvent avoir des types différents et nécessiter une conversion restrictive.

Dans ces cas, il est judicieux de transformer une conversion restrictive implicite en conversion restrictive explicite à l'aide de static_cast. Cela permet de documenter le fait que la conversion restrictive est intentionnelle, et supprime les avertissements ou erreurs du compilateur qui seraient autrement produits.

Par exemple :

void someFcn(int i)
{
}

int main()
{
    double d{ 5.0 };

    someFcn(d); // mauvais : la conversion restrictive implicite générera un avertissement du compilateur

    // bien : on indique explicitement au compilateur que cette conversion restrictive est intentionnelle
    someFcn(static_cast<int>(d)); // aucun avertissement généré

    return 0;
}

Bonne pratique

Si vous devez effectuer une conversion restrictive, utilisez static_cast pour la transformer en conversion explicite.

L'initialisation par accolades interdit les conversions restrictives

Les conversions restrictives sont interdites lors d'une initialisation par accolades (ce qui est l'une des principales raisons pour lesquelles cette forme d'initialisation est préférée), et toute tentative de le faire produira une erreur de compilation.

Par exemple :

int main()
{
    int i { 3.5 }; // ne compilera pas

    return 0;
}

Visual Studio produit l'erreur suivante :


error C2397: conversion from 'double' to 'int' requires a narrowing conversion

Si vous voulez réellement effectuer une conversion restrictive à l'intérieur d'une initialisation par accolades, utilisez static_cast pour transformer la conversion restrictive en conversion explicite :

int main()
{
    double d { 3.5 };

    // static_cast<int> convertit double en int, initialise i avec le résultat int
    int i { static_cast<int>(d) }; 

    return 0;
}

Certaines conversions constexpr ne sont pas considérées comme restrictives

Lorsque la valeur source d'une conversion restrictive n'est connue qu'à l'exécution, le résultat de la conversion ne peut lui aussi être déterminé qu'à l'exécution. Dans ce cas, le fait que la conversion restrictive préserve ou non la valeur ne peut pas non plus être déterminé avant l'exécution. Par exemple :

#include <iostream>

void print(unsigned int u) // remarque : unsigned
{
    std::cout << u << '\n';
}

int main()
{
    std::cout << "Entrez une valeur entière : ";
    int n{};
    std::cin >> n; // saisissez 5 ou -5
    print(n);      // la conversion en unsigned peut ou non préserver la valeur

    return 0;
}

Dans le programme ci-dessus, le compilateur ne sait pas quelle valeur sera saisie pour n. Lorsque print(n) est appelée, la conversion de int en unsigned int est effectuée à ce moment-là, et le résultat peut préserver la valeur ou non selon la valeur saisie pour n. Ainsi, un compilateur dont les avertissements sur les conversions signé/non signé sont activés émettra un avertissement dans ce cas.

Cependant, vous avez peut-être remarqué que la plupart des définitions de conversions restrictives comportent une clause d'exception qui commence par « sauf si la valeur convertie est constexpr et … ». Par exemple, une conversion est restrictive lorsqu'il s'agit d'« une conversion d'un type entier vers un autre type entier qui ne peut pas représenter toutes les valeurs du type d'origine, sauf si la valeur convertie est constexpr et si sa valeur peut être stockée exactement dans le type de destination ».

Lorsque la valeur source d'une conversion restrictive est constexpr, la valeur précise à convertir doit être connue du compilateur. Dans ces cas, le compilateur peut effectuer lui-même la conversion, puis vérifier si la valeur a été préservée. Si elle ne l'a pas été, le compilateur peut interrompre la compilation avec une erreur. Si elle l'a été, la conversion n'est pas considérée comme restrictive (et le compilateur peut remplacer toute la conversion par le résultat converti, sachant que cela est sans danger).

Par exemple :

#include <iostream>

int main()
{
    constexpr int n1{ 5 };   // remarque : constexpr
    unsigned int u1 { n1 };  // correct : la conversion n'est pas restrictive grâce à la clause d'exception

    constexpr int n2 { -5 }; // remarque : constexpr
    unsigned int u2 { n2 };  // erreur de compilation : conversion restrictive due à un changement de valeur

    return 0;
}

Appliquons la règle « D'un type entier vers un autre type entier qui ne peut pas représenter toutes les valeurs du type d'origine, sauf si la valeur convertie est constexpr et si sa valeur peut être stockée exactement dans le type de destination » aux deux conversions ci-dessus.

Dans le cas de n1 et u1, n1 est un int et u1 est un unsigned int : il s'agit donc d'une conversion d'un type entier vers un autre type entier qui ne peut pas représenter toutes les valeurs du type d'origine. Cependant, n1 est constexpr et sa valeur 5 peut être représentée exactement dans le type de destination (sous la forme de la valeur non signée 5). Cette conversion n'est donc pas considérée comme restrictive, et nous avons le droit d'initialiser u1 par liste à l'aide de n1.

Dans le cas de n2 et u2, la situation est similaire. Bien que n2 soit constexpr, sa valeur -5 ne peut pas être représentée exactement dans le type de destination. La conversion est donc considérée comme restrictive, et comme nous effectuons une initialisation par liste, le compilateur produit une erreur et interrompt la compilation.

Étrangement, les conversions d'un type à virgule flottante vers un type entier ne possèdent pas de clause d'exception constexpr. Elles sont donc toujours considérées comme restrictives, même lorsque la valeur à convertir est constexpr et se situe dans l'intervalle du type de destination :

int n { 5.0 }; // erreur de compilation : conversion restrictive

Plus étrangement encore, les conversions d'un type à virgule flottante constexpr vers un type à virgule flottante plus étroit ne sont pas considérées comme restrictives, même lorsqu'il y a perte de précision !

constexpr double d { 0.1 };
float f { d }; // non restrictive, bien qu'une perte de précision en résulte

Attention

La conversion d'un type à virgule flottante constexpr vers un type à virgule flottante plus étroit n'est pas considérée comme restrictive, même lorsqu'elle entraîne une perte de précision.

Initialisation par liste avec des initialiseurs constexpr

Ces clauses d'exception constexpr sont extrêmement utiles lors de l'initialisation par liste d'objets qui ne sont ni int ni double, car nous pouvons utiliser un littéral int ou double (ou un objet constexpr) comme valeur d'initialisation.

Cela nous permet d'éviter :

  • d'avoir à utiliser des suffixes littéraux dans la plupart des cas ;
  • d'encombrer nos initialisations avec un static_cast.

Par exemple :

int main()
{
    // Nous pouvons éviter les littéraux avec suffixes
    unsigned int u { 5 }; // correct (pas besoin d'écrire `5u`)
    float f { 1.5 };      // correct (pas besoin d'écrire `1.5f`)

    // Nous pouvons éviter les static_cast
    constexpr int n{ 5 };
    double d { n };       // correct (pas besoin de static_cast ici)
    short s { 5 };        // correct (il n'existe pas de suffixe pour short, pas besoin de static_cast ici)

    return 0;
}

Cela fonctionne également avec l'initialisation par copie et l'initialisation directe.

Une mise en garde mérite d'être mentionnée : initialiser un type à virgule flottante plus étroit ou de rang inférieur avec une valeur constexpr est autorisé tant que la valeur se situe dans l'intervalle du type de destination, même si ce type n'a pas assez de précision pour stocker exactement la valeur !

Point clé

Les types à virgule flottante sont classés dans cet ordre (du plus grand au plus petit) :

  • long double
  • double
  • float

Ainsi, une écriture comme celle-ci est légale et ne produit pas d'erreur :

int main()
{
    float f { 1.23456789 }; // non restrictive, bien qu'une précision soit perdue !

    return 0;
}

Cependant, votre compilateur peut tout de même émettre un avertissement dans ce cas (GCC et Clang le font si vous utilisez l'option de compilation -Wconversion).
