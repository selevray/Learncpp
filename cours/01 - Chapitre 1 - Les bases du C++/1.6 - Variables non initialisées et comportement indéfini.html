1.6 — Variables non initialisées et comportement indéfini

Variables non initialisées

Contrairement à certains langages de programmation, C/C++ n'initialise pas automatiquement la plupart des variables à une valeur donnée (comme zéro). Lorsqu'une variable non initialisée se voit attribuer une adresse mémoire pour y stocker des données, sa valeur par défaut est celle (une valeur quelconque, aléatoire) qui se trouve déjà à cette adresse mémoire ! Une variable à laquelle on n'a pas donné de valeur connue (par initialisation ou par affectation) est appelée une variable non initialisée.

Nomenclature

Beaucoup de lecteurs s'attendent à ce que les termes « initialisé » et « non initialisé » soient strictement opposés, mais ce n'est pas tout à fait le cas ! Dans le langage courant, « initialisé » signifie que l'objet a reçu une valeur initiale au moment de sa définition. « Non initialisé » signifie que l'objet n'a pas encore reçu de valeur connue (par n'importe quel moyen, y compris l'affectation). Par conséquent, un objet qui n'est pas initialisé mais auquel on affecte ensuite une valeur n'est plus non initialisé (puisqu'il a reçu une valeur connue).

En résumé :

  • Initialisé = L'objet reçoit une valeur connue au moment de sa définition.
  • Affectation = L'objet reçoit une valeur connue après le moment de sa définition.
  • Non initialisé = L'objet n'a pas encore reçu de valeur connue.

Dans le même ordre d'idées, considérez cette définition de variable :

int x;

Dans la leçon 1.4 -- Affectation et initialisation des variables, nous avons indiqué que lorsqu'aucun initialisateur n'est fourni, la variable est initialisée par défaut. Dans la plupart des cas (comme celui-ci), cette initialisation par défaut n'effectue aucune initialisation réelle. Ainsi, on dira que x est non initialisée. Nous nous concentrons sur le résultat (l'objet n'a pas reçu de valeur connue), et non sur le processus.

En passant…

Cette absence d'initialisation est une optimisation de performance héritée du C, à une époque où les ordinateurs étaient lents. Imaginez que vous deviez lire 100 000 valeurs depuis un fichier. Vous pourriez alors créer 100 000 variables, puis les remplir avec les données du fichier.

Si C++ initialisait toutes ces variables avec des valeurs par défaut lors de leur création, cela entraînerait 100 000 initialisations (ce qui serait lent), pour un bénéfice minime (puisque vous écrasez de toute façon ces valeurs).

Pour l'instant, vous devriez toujours initialiser vos variables, car le coût de cette opération est minime par rapport au bénéfice. Une fois que vous serez plus à l'aise avec le langage, il pourra exister certains cas où vous omettrez l'initialisation à des fins d'optimisation. Mais cela doit toujours être fait de manière sélective et réfléchie.

Utiliser les valeurs de variables non initialisées peut conduire à des résultats inattendus. Considérez le programme court suivant :

#include <iostream>

int main()
{
    // définit une variable entière nommée x
    int x; // cette variable n'est pas initialisée car nous ne lui avons pas donné de valeur

    // affiche la valeur de x à l'écran
    std::cout << x << '\n'; // qui sait ce que nous obtiendrons, car x n'est pas initialisée

    return 0;
}

Dans ce cas, l'ordinateur réserve une zone de mémoire inutilisée pour x. Il envoie ensuite la valeur présente à cet emplacement mémoire à std::cout, qui affiche cette valeur (interprétée comme un entier). Mais quelle valeur sera affichée ? La réponse est « qui sait ! », et cette réponse peut (ou non) changer à chaque exécution du programme. Lorsque l'auteur a exécuté ce programme dans Visual Studio, std::cout a affiché la valeur 7177728 une fois, puis 5277592 la fois suivante. N'hésitez pas à compiler et exécuter le programme vous-même (votre ordinateur n'explosera pas).

Attention

Certains compilateurs, comme Visual Studio, vont initialiser le contenu de la mémoire avec une valeur prédéfinie lorsque vous utilisez une configuration de compilation de débogage. Ce n'est pas le cas avec une configuration de compilation de version (release). Par conséquent, si vous voulez exécuter vous-même le programme ci-dessus, assurez-vous d'utiliser une configuration de compilation de version (consultez la leçon 0.9 -- Configurer votre compilateur : les configurations de compilation pour un rappel sur la façon de procéder).

Par exemple, si vous exécutez le programme ci-dessus dans une configuration de débogage de Visual Studio, il affichera systématiquement -858993460, car c'est la valeur (interprétée comme un entier) avec laquelle Visual Studio initialise la mémoire dans les configurations de débogage.

La plupart des compilateurs modernes essaient de détecter si une variable est utilisée sans avoir reçu de valeur. S'ils y parviennent, ils émettent généralement un avertissement ou une erreur à la compilation. Par exemple, la compilation du programme ci-dessus sous Visual Studio a produit l'avertissement suivant :

c:\VCprojects\test\test.cpp(11) : warning C4700: uninitialized local variable 'x' used

Si votre compilateur ne vous permet pas de compiler et d'exécuter le programme ci-dessus (par exemple parce qu'il traite le problème comme une erreur), voici une solution possible pour contourner ce problème :

#include <iostream>

void doNothing(int&) // Ne vous préoccupez pas de la signification de & pour le moment, nous l'utilisons simplement pour faire croire au compilateur que la variable x est utilisée
{
}

int main()
{
    // définit une variable entière nommée x
    int x; // cette variable n'est pas initialisée

    doNothing(x); // fait croire au compilateur que nous affectons une valeur à cette variable

    // affiche la valeur de x à l'écran (qui sait ce que nous obtiendrons, car x n'est pas initialisée)
    std::cout << x << '\n';

    return 0;
}

Utiliser des variables non initialisées est l'une des erreurs les plus courantes chez les programmeurs débutants et, malheureusement, c'est aussi l'une des plus difficiles à déboguer (parce que le programme peut tout à fait fonctionner si la variable non initialisée a été placée à un emplacement mémoire contenant une valeur raisonnable, comme 0).

C'est la principale raison de la bonne pratique « initialisez toujours vos variables ».

Comportement indéfini

Utiliser la valeur d'une variable non initialisée est notre premier exemple de comportement indéfini. Le comportement indéfini (souvent abrégé UB, pour undefined behavior) est le résultat de l'exécution d'un code dont le comportement n'est pas bien défini par le langage C++. Dans ce cas, le langage C++ ne contient aucune règle déterminant ce qui se produit si vous utilisez la valeur d'une variable à laquelle on n'a pas donné de valeur connue. Par conséquent, si vous faites effectivement cela, un comportement indéfini en résultera.

Un code présentant un comportement indéfini peut manifester l'un quelconque des symptômes suivants :

  • Votre programme produit des résultats différents à chaque exécution.
  • Votre programme produit systématiquement le même résultat incorrect.
  • Votre programme se comporte de manière incohérente (il produit parfois le bon résultat, parfois non).
  • Votre programme semble fonctionner, mais produit des résultats incorrects plus loin dans l'exécution.
  • Votre programme plante, immédiatement ou plus tard.
  • Votre programme fonctionne avec certains compilateurs mais pas avec d'autres.
  • Votre programme fonctionne jusqu'à ce que vous modifiiez un autre code apparemment sans rapport.

Ou, votre code peut tout de même produire le comportement correct.

Note de l'auteur

Le comportement indéfini est comme une boîte de chocolats. Vous ne savez jamais sur quoi vous allez tomber !

Le C++ contient de nombreux cas pouvant conduire à un comportement indéfini si vous n'y prenez pas garde. Nous les signalerons dans les prochaines leçons à chaque fois que nous les rencontrerons. Notez où se trouvent ces cas et veillez à les éviter.

Règle

Veillez à éviter toutes les situations qui entraînent un comportement indéfini, comme l'utilisation de variables non initialisées.

Note de l'auteur

L'un des commentaires les plus fréquents que nous recevons de la part de lecteurs dit : « Vous avez dit que je ne pouvais pas faire X, mais je l'ai fait quand même et mon programme fonctionne ! Pourquoi ? ».

Il y a deux réponses courantes. La plus fréquente est que votre programme présente en réalité un comportement indéfini, mais que ce comportement indéfini produit justement le résultat souhaité… pour l'instant. Demain (ou sur un autre compilateur ou une autre machine), ce ne sera peut-être plus le cas.

Autrement, il arrive que les auteurs de compilateurs prennent des libertés avec les exigences du langage lorsque ces exigences sont plus restrictives que nécessaire. Par exemple, la norme peut dire « vous devez faire X avant Y », alors qu'un auteur de compilateur peut estimer que c'est inutile et faire fonctionner Y même si vous ne faites pas X d'abord. Cela ne devrait pas affecter le fonctionnement des programmes correctement écrits, mais peut permettre à des programmes incorrectement écrits de fonctionner malgré tout. Une autre réponse possible à la question ci-dessus est donc que votre compilateur ne respecte peut-être tout simplement pas la norme ! Cela arrive. Vous pouvez éviter une grande partie de ces problèmes en vous assurant d'avoir désactivé les extensions du compilateur, comme décrit dans la leçon 0.10 -- Configurer votre compilateur : les extensions du compilateur.

Comportement défini par l'implémentation et comportement non spécifié

Un compilateur donné et la bibliothèque standard qui l'accompagne constituent une implémentation (puisque ce sont eux qui implémentent concrètement le langage C++). Dans certains cas, la norme du langage C++ permet à l'implémentation de déterminer comment un aspect du langage se comporte, afin que le compilateur puisse choisir un comportement efficace pour une plateforme donnée. Un comportement défini par l'implémentation est appelé comportement défini par l'implémentation (implementation-defined behavior). Ce comportement doit être documenté et rester cohérent pour une implémentation donnée.

Examinons un exemple simple de comportement défini par l'implémentation :

#include <iostream>

int main()
{
    std::cout << sizeof(int) << '\n'; // affiche le nombre d'octets de mémoire qu'occupe une valeur int

    return 0;
}

Sur la plupart des plateformes, ce programme affichera 4, mais sur d'autres il pourra afficher 2.

Contenu associé

Nous abordons sizeof() dans la leçon 4.3 -- Taille des objets et opérateur sizeof.

Le comportement non spécifié (unspecified behavior) est presque identique au comportement défini par l'implémentation, en ceci que le comportement est laissé à la charge de l'implémentation, mais que celle-ci n'est pas tenue de le documenter.

Nous voulons généralement éviter le comportement défini par l'implémentation et le comportement non spécifié, car cela signifie que notre programme risque de ne pas fonctionner comme prévu s'il est compilé avec un autre compilateur (ou même avec le même compilateur si nous modifions des paramètres de projet qui affectent le comportement de l'implémentation !).

Bonne pratique

Évitez autant que possible le comportement défini par l'implémentation et le comportement non spécifié, car ils peuvent entraîner un dysfonctionnement de votre programme sur d'autres implémentations.

Quiz

Question n° 1

Qu'est-ce qu'une variable non initialisée ? Pourquoi devriez-vous éviter de les utiliser ?

Solution

Une variable non initialisée est une variable à laquelle le programme n'a pas donné de valeur (généralement par initialisation ou par affectation). Utiliser la valeur stockée dans une variable non initialisée entraîne un comportement indéfini.

Question n° 2

Qu'est-ce que le comportement indéfini, et que peut-il se passer si vous faites quelque chose qui présente un comportement indéfini ?

Solution

Le comportement indéfini est le résultat de l'exécution d'un code dont le comportement n'est pas bien défini par le langage. Le résultat peut être à peu près n'importe quoi, y compris un comportement correct.
