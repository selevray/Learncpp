4.5 — Les entiers non signés et pourquoi les éviter

Les entiers non signés

Dans la leçon précédente (4.4 -- Les entiers signés), nous avons étudié les entiers signés, un ensemble de types pouvant stocker des nombres entiers positifs et négatifs, y compris 0.

C++ prend également en charge les entiers non signés. Les entiers non signés (unsigned integers) sont des entiers ne pouvant stocker que des nombres entiers positifs ou nuls.

Définir des entiers non signés

Pour définir un entier non signé, on utilise le mot-clé unsigned. Par convention, il est placé avant le type :

unsigned short us;
unsigned int ui;
unsigned long ul;
unsigned long long ull;

Intervalle des entiers non signés

Un entier non signé de 1 octet a un intervalle allant de 0 à 255. Comparez avec l'intervalle d'un entier signé de 1 octet, allant de -128 à 127. Les deux peuvent stocker 256 valeurs différentes, mais les entiers signés consacrent la moitié de leur intervalle aux nombres négatifs, alors que les entiers non signés peuvent stocker des nombres positifs deux fois plus grands.

Voici un tableau présentant l'intervalle des entiers non signés :

Taille/Type Intervalle
8 bits non signé 0 à 255
16 bits non signé 0 à 65 535
32 bits non signé 0 à 4 294 967 295
64 bits non signé 0 à 18 446 744 073 709 551 615

Une variable non signée de n bits a un intervalle allant de 0 à (2^n)-1.

Lorsque aucun nombre négatif n'est nécessaire, les entiers non signés conviennent bien aux réseaux et aux systèmes disposant de peu de mémoire, car ils peuvent stocker davantage de nombres positifs sans occuper de mémoire supplémentaire.

Retenir les termes signé et non signé

Les nouveaux programmeurs confondent parfois les termes signé et non signé. Voici un moyen simple de retenir la différence : pour distinguer les nombres négatifs des nombres positifs, on utilise un signe moins. Si aucun signe n'est indiqué, on suppose que le nombre est positif. Par conséquent, un entier avec un signe (un entier signé) peut faire la différence entre positif et négatif. Un entier sans signe (un entier non signé) suppose que toutes les valeurs sont positives.

Dépassement de capacité des entiers non signés

Que se passe-t-il si l'on essaie de stocker le nombre 280 (qui nécessite 9 bits pour être représenté) dans un entier non signé de 1 octet (8 bits) ? La réponse est un dépassement de capacité (overflow).

Note de l'auteur

Curieusement, la norme C++ affirme explicitement que « un calcul impliquant des opérandes non signés ne peut jamais provoquer de dépassement de capacité ». Cela va à l'encontre du consensus général des programmeurs, pour qui le dépassement d'entier concerne aussi bien les usages signés que non signés (source). Comme la plupart des programmeurs considéreraient cela comme un dépassement, nous l'appellerons ainsi, malgré les affirmations contraires de la norme C++.

Si une valeur non signée sort de l'intervalle, elle est divisée par un de plus que le plus grand nombre du type, et seul le reste est conservé.

Le nombre 280 est trop grand pour tenir dans notre intervalle de 1 octet, allant de 0 à 255. Un de plus que le plus grand nombre du type vaut 256. Nous divisons donc 280 par 256, ce qui donne 1 avec un reste de 24. C'est ce reste de 24 qui est stocké.

Voici une autre manière de voir la même chose. Tout nombre plus grand que le plus grand nombre représentable par le type « revient à zéro » (on parle parfois de « repli modulo »). 255 est dans l'intervalle d'un entier de 1 octet, donc 255 convient. 256, en revanche, est hors intervalle et revient donc à la valeur 0. 257 revient à la valeur 1. 280 revient à la valeur 24.

Observons cela avec des short de 2 octets :

#include <iostream>

int main()
{
    unsigned short x{ 65535 }; // plus grande valeur non signée 16 bits possible
    std::cout << "x valait : " << x << '\n';

    x = 65536; // 65536 est hors de notre intervalle, on obtient un repli modulo
    std::cout << "x vaut maintenant : " << x << '\n';

    x = 65537; // 65537 est hors de notre intervalle, on obtient un repli modulo
    std::cout << "x vaut maintenant : " << x << '\n';

    return 0;
}

Quel sera selon vous le résultat de ce programme ?

(Remarque : si vous essayez de compiler le programme ci-dessus, votre compilateur devrait émettre des avertissements concernant le dépassement de capacité ou la troncature. Vous devrez désactiver « traiter les avertissements comme des erreurs » pour exécuter le programme.)


x valait : 65535
x vaut maintenant : 0
x vaut maintenant : 1

Il est également possible de revenir dans l'autre sens. 0 est représentable dans un entier non signé de 2 octets, il n'y a donc aucun problème. -1 ne l'est pas : il revient donc au sommet de l'intervalle, en produisant la valeur 65535. -2 revient à 65534. Et ainsi de suite.

#include <iostream>

int main()
{
    unsigned short x{ 0 }; // plus petite valeur non signée 2 octets possible
    std::cout << "x valait : " << x << '\n';

    x = -1; // -1 est hors de notre intervalle, on obtient un repli modulo
    std::cout << "x vaut maintenant : " << x << '\n';

    x = -2; // -2 est hors de notre intervalle, on obtient un repli modulo
    std::cout << "x vaut maintenant : " << x << '\n';

    return 0;
}


x valait : 0
x vaut maintenant : 65535
x vaut maintenant : 65534

Le code ci-dessus déclenche un avertissement dans certains compilateurs, car le compilateur détecte que le littéral entier est hors intervalle pour le type donné. Si vous voulez tout de même compiler ce code, désactivez temporairement l'option « Traiter les avertissements comme des erreurs ».

En passant…

De nombreux bogues célèbres de l'histoire du jeu vidéo sont dus au comportement de repli des entiers non signés. Dans le jeu d'arcade Donkey Kong, il est impossible de dépasser le niveau 22 à cause d'un bogue de dépassement qui ne laisse pas au joueur assez de temps bonus pour terminer le niveau.

Dans le jeu PC Civilization, Gandhi était connu pour être souvent le premier à utiliser des armes nucléaires, ce qui semble contraire à sa nature pacifique attendue. Les joueurs avaient émis la théorie que le paramètre d'agressivité de Gandhi était initialement fixé à 1, mais que s'il choisissait un gouvernement démocratique, il obtenait un malus d'agressivité de -2 (réduisant son agressivité actuelle de 2). Cela faisait déboucher son agressivité sur un dépassement à 255, le rendant maximalement agressif ! Cependant, plus récemment, Sid Meier (l'auteur du jeu) a précisé que ce n'était pas réellement le cas.

La controverse autour des nombres non signés

De nombreux développeurs (et certaines grandes entreprises du secteur, comme Google) estiment que les développeurs devraient généralement éviter les entiers non signés.

Cela tient principalement à deux comportements qui peuvent poser problème.

Premièrement, avec les valeurs signées, il faut un peu d'effort pour dépasser accidentellement les bornes supérieure ou inférieure de l'intervalle, car ces valeurs sont éloignées de 0. Avec les nombres non signés, il est beaucoup plus facile de dépasser la borne inférieure, car celle-ci vaut 0, c'est-à-dire tout près de l'endroit où se trouve la majorité de nos valeurs.

Considérons la soustraction de deux nombres non signés, par exemple 2 et 3 :

#include <iostream>

// on suppose que int fait 4 octets
int main()
{
    unsigned int x{ 2 };
    unsigned int y{ 3 };

    std::cout << x - y << '\n'; // affiche 4294967295 (incorrect !)

    return 0;
}

Vous et moi savons que 2 - 3 vaut -1, mais -1 ne peut pas être représenté par un entier non signé. Nous obtenons donc un dépassement de capacité et le résultat suivant :


4294967295

Un autre repli indésirable courant se produit lorsqu'un entier non signé est décrémenté de 1 de manière répétée, jusqu'à tenter de descendre sous zéro. Vous en verrez un exemple lorsque les boucles seront présentées.

Deuxièmement, et de façon plus insidieuse, un comportement inattendu peut résulter du mélange d'entiers signés et non signés. En C++, si une opération mathématique (par exemple arithmétique ou de comparaison) porte sur un entier signé et un entier non signé, l'entier signé est généralement converti en entier non signé, et le résultat est donc non signé. Par exemple :

#include <iostream>

// on suppose que int fait 4 octets
int main()
{
    unsigned int u{ 2 };
    signed int s{ 3 };

    std::cout << u - s << '\n'; // 2 - 3 = 4294967295

    return 0;
}

Ce programme produit également le résultat :


4294967295

Dans ce cas, si u était signé, le résultat correct serait produit. Mais comme u est non signé (ce qui est facile à oublier), s est converti en non signé, et le résultat (-1) est traité comme une valeur non signée. Comme -1 ne peut pas être stocké dans une valeur non signée, nous obtenons un dépassement de capacité et une réponse inattendue.

Voici un autre exemple où les choses tournent mal :

#include <iostream>

// on suppose que int fait 4 octets
int main()
{
    signed int s { -1 };
    unsigned int u { 1 };

    if (s < u) // -1 est implicitement converti en 4294967295, et 4294967295 < 1 est faux
        std::cout << "-1 est inférieur à 1\n";
    else
        std::cout << "1 est inférieur à -1\n"; // cette instruction s'exécute

    return 0;
}

Ce programme affiche :


1 est inférieur à -1

Ce programme est bien formé, compile, et paraît logiquement cohérent à l'œil. Pourtant, il affiche une mauvaise réponse. Et bien que votre compilateur devrait vous avertir d'une incohérence signé/non signé dans ce cas, il générera aussi des avertissements identiques pour d'autres cas qui ne posent pas ce problème (par exemple lorsque les deux nombres sont positifs), ce qui rend difficile la détection d'un véritable problème.

Il existe en outre d'autres cas problématiques, difficiles à détecter. Considérons le code suivant :

#include <iostream>

// on suppose que int fait 4 octets
void doSomething(unsigned int x)
{
    // Exécute du code x fois

    std::cout << "x vaut " << x << '\n';
}

int main()
{
    doSomething(-1);

    return 0;
}

L'auteur de doSomething() attendait que l'on appelle cette fonction uniquement avec des nombres positifs. Mais l'appelant transmet -1 : une erreur évidente, mais commise malgré tout. Que se passe-t-il dans ce cas ?

L'argument signé -1 est implicitement converti en paramètre non signé. -1 n'appartient pas à l'intervalle d'un nombre non signé : il revient donc à 4294967295. Votre programme part alors dans tous les sens.

Plus problématique encore, il peut être difficile d'empêcher cela. À moins d'avoir configuré votre compilateur pour produire des avertissements agressifs sur les conversions signé/non signé (et vous devriez le faire), il ne se plaindra probablement même pas de ce problème.

Tous ces problèmes sont couramment rencontrés, produisent des comportements inattendus et sont difficiles à localiser, même à l'aide d'outils automatisés conçus pour détecter les cas problématiques.

Compte tenu de ce qui précède, la bonne pratique, quelque peu controversée, que nous recommandons est d'éviter les types non signés sauf dans des circonstances particulières.

Bonne pratique

Privilégiez les nombres signés aux nombres non signés pour représenter des quantités (même des quantités qui devraient être positives ou nulles) et pour les opérations mathématiques. Évitez de mélanger nombres signés et non signés.

Alors, quand faut-il utiliser des nombres non signés ?

Il existe encore quelques cas en C++ où il est acceptable, voire nécessaire, d'utiliser des nombres non signés.

Premièrement, les nombres non signés sont préférés lorsqu'il s'agit de manipulation de bits (abordée au chapitre O, avec un « o » minuscule et non un « 0 »). Ils sont également utiles lorsqu'un comportement de repli bien défini est requis (utile dans certains algorithmes, comme le chiffrement et la génération de nombres aléatoires).

Deuxièmement, l'usage de nombres non signés reste inévitable dans certains cas, principalement ceux liés à l'indexation de tableaux. Nous en parlerons davantage dans les leçons sur les tableaux et l'indexation de tableaux.

Notez aussi que si vous développez pour un système embarqué (par exemple un Arduino) ou tout autre contexte limité en processeur ou en mémoire, l'usage de nombres non signés est plus courant et accepté (et dans certains cas inévitable) pour des raisons de performance.
