2.12 — Gardes d'en-tête (header guards)

Le problème des définitions en double

Dans la leçon 2.7 -- Déclarations anticipées et définitions, nous avons vu qu'un identifiant de variable ou de fonction ne peut avoir qu'une seule définition (la règle de définition unique, ou ODR pour one definition rule). Ainsi, un programme qui définit plusieurs fois un même identifiant de variable provoquera une erreur de compilation :

int main()
{
    int x; // ceci est une définition de la variable x
    int x; // erreur de compilation : définition en double

    return 0;
}

De même, un programme qui définit plusieurs fois une même fonction provoquera une erreur de compilation :

#include <iostream>

int foo() // ceci est une définition de la fonction foo
{
    return 5;
}

int foo() // erreur de compilation : définition en double
{
    return 5;
}

int main()
{
    std::cout << foo();
    return 0;
}

Ces programmes sont faciles à corriger (il suffit de supprimer la définition en double). En revanche, avec les fichiers d'en-tête, il est très facile de se retrouver dans une situation où une définition contenue dans un fichier d'en-tête est incluse plus d'une fois. Cela peut arriver lorsqu'un fichier d'en-tête fait un #include d'un autre fichier d'en-tête, ce qui est courant.

Note de l'auteur

Dans les exemples qui suivent, nous définirons certaines fonctions à l'intérieur de fichiers d'en-tête. En général, vous ne devriez pas faire cela.

Nous le faisons ici car c'est la manière la plus efficace de illustrer certains concepts en utilisant des notions que nous avons déjà vues.

Considérons l'exemple académique suivant :

square.h :

int getSquareSides()
{
    return 4;
}

wave.h :

#include "square.h"

main.cpp :

#include "square.h"
#include "wave.h"

int main()
{
    return 0;
}

Ce programme, pourtant d'apparence anodine, ne compile pas ! Voici ce qui se passe. D'abord, main.cpp fait un #include de square.h, ce qui copie la définition de la fonction getSquareSides dans main.cpp. Ensuite, main.cpp fait un #include de wave.h, qui fait lui-même un #include de square.h. Le contenu de square.h (y compris la définition de la fonction getSquareSides) est donc copié dans wave.h, lequel est ensuite copié dans main.cpp.

Ainsi, une fois toutes les directives #include résolues, main.cpp ressemble à ceci :

int getSquareSides()  // issu de square.h
{
    return 4;
}

int getSquareSides() // issu de wave.h (via square.h)
{
    return 4;
}

int main()
{
    return 0;
}

Nous obtenons des définitions en double, et donc une erreur de compilation. Chaque fichier, pris isolément, est correct. Cependant, comme main.cpp finit par inclure deux fois le contenu de square.h, le problème survient. Si wave.h a besoin de getSquareSides(), et que main.cpp a besoin à la fois de wave.h et de square.h, comment résoudriez-vous ce problème ?

Les gardes d'en-tête

La bonne nouvelle est que nous pouvons éviter le problème ci-dessus grâce à un mécanisme appelé garde d'en-tête (header guard, ou include guard). Les gardes d'en-tête sont des directives de compilation conditionnelle qui prennent la forme suivante :

#ifndef SOME_UNIQUE_NAME_HERE
#define SOME_UNIQUE_NAME_HERE

// vos déclarations (et certains types de définitions) ici

#endif

Lorsque cet en-tête est inclus avec #include, le préprocesseur vérifie si SOME_UNIQUE_NAME_HERE a déjà été défini dans cette unité de traduction. S'il s'agit de la première inclusion de l'en-tête, SOME_UNIQUE_NAME_HERE n'a pas encore été défini. Par conséquent, le préprocesseur définit SOME_UNIQUE_NAME_HERE et inclut le contenu du fichier. Si l'en-tête est à nouveau inclus dans le même fichier, SOME_UNIQUE_NAME_HERE aura déjà été défini lors de la première inclusion, et le contenu de l'en-tête sera ignoré (grâce au #ifndef).

Tous vos fichiers d'en-tête devraient posséder des gardes d'en-tête. SOME_UNIQUE_NAME_HERE peut être le nom de votre choix, mais, par convention, il correspond au nom complet du fichier d'en-tête, écrit en majuscules, les espaces et la ponctuation étant remplacés par des tirets bas. Par exemple, square.h aurait pour garde :

square.h :

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides()
{
    return 4;
}

#endif

Même les en-têtes de la bibliothèque standard utilisent des gardes d'en-tête. Si vous examinez le fichier d'en-tête iostream de Visual Studio, vous verrez :

#ifndef _IOSTREAM_
#define _IOSTREAM_

// contenu ici

#endif

Pour les lecteurs avancés

Dans les grands programmes, il est possible d'avoir deux fichiers d'en-tête distincts (inclus depuis des répertoires différents) portant le même nom de fichier (par exemple directoryA\config.h et directoryB\config.h). Si seul le nom du fichier est utilisé pour la garde (par exemple CONFIG_H), ces deux fichiers peuvent finir par utiliser le même nom de garde. Dans ce cas, tout fichier qui inclut (directement ou indirectement) les deux fichiers config.h ne recevra pas le contenu du second fichier à inclure. Cela provoquera probablement une erreur de compilation.

En raison de ce risque de conflit de noms de gardes, de nombreux développeurs recommandent d'utiliser un nom de garde plus complexe et plus unique. Parmi les bonnes suggestions figurent une convention de nommage de la forme PROJET_CHEMIN_FICHIER_H, FICHIER_NOMBRE-ALÉATOIRE-GRAND_H, ou FICHIER_DATE-DE-CRÉATION_H.

Mise à jour de notre exemple précédent avec des gardes d'en-tête

Reprenons l'exemple de square.h, en utilisant désormais des gardes d'en-tête. Par souci de rigueur, nous ajouterons également des gardes à wave.h.

square.h :

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides()
{
    return 4;
}

#endif

wave.h :

#ifndef WAVE_H
#define WAVE_H

#include "square.h"

#endif

main.cpp :

#include "square.h"
#include "wave.h"

int main()
{
    return 0;
}

Une fois que le préprocesseur a résolu toutes les directives #include, ce programme devient :

main.cpp :

// square.h inclus depuis main.cpp
#ifndef SQUARE_H // square.h inclus depuis main.cpp
#define SQUARE_H // SQUARE_H est défini ici

// et tout ce contenu est inclus
int getSquareSides()
{
    return 4;
}

#endif // SQUARE_H

#ifndef WAVE_H // wave.h inclus depuis main.cpp
#define WAVE_H
#ifndef SQUARE_H // square.h inclus depuis wave.h, SQUARE_H est déjà défini plus haut
#define SQUARE_H // donc rien de ce contenu n'est inclus

int getSquareSides()
{
    return 4;
}

#endif // SQUARE_H
#endif // WAVE_H

int main()
{
    return 0;
}

Voyons comment cela s'évalue.

D'abord, le préprocesseur évalue #ifndef SQUARE_H. SQUARE_H n'a pas encore été défini, donc le code situé entre ce #ifndef et le #endif suivant est inclus dans la compilation. Ce code définit SQUARE_H et contient la définition de la fonction getSquareSides.

Ensuite, le #ifndef SQUARE_H suivant est évalué. Cette fois, SQUARE_H est défini (puisqu'il l'a été plus haut), donc le code situé entre ce #ifndef et le #endif suivant est exclu de la compilation.

Les gardes d'en-tête empêchent les inclusions en double, car la première fois qu'une garde est rencontrée, la macro de garde n'est pas définie, et le contenu protégé est donc inclus. À partir de ce moment, la macro de garde est définie, si bien que toute copie ultérieure du contenu protégé est exclue.

Les gardes d'en-tête n'empêchent pas un en-tête d'être inclus une fois dans différents fichiers de code

Notez que l'objectif des gardes d'en-tête est d'empêcher un fichier de code de recevoir plus d'une copie d'un en-tête protégé. Par conception, les gardes d'en-tête n'empêchent pas qu'un fichier d'en-tête donné soit inclus (une fois) dans des fichiers de code distincts. Cela peut aussi causer des problèmes inattendus. Considérons :

square.h :

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides()
{
    return 4;
}

int getSquarePerimeter(int sideLength); // déclaration anticipée de getSquarePerimeter

#endif

square.cpp :

#include "square.h"  // square.h est inclus une fois ici

int getSquarePerimeter(int sideLength)
{
    return sideLength * getSquareSides();
}

main.cpp :

#include "square.h" // square.h est aussi inclus une fois ici
#include <iostream>

int main()
{
    std::cout << "a square has " << getSquareSides() << " sides\n";
    std::cout << "a square of length 5 has perimeter length " << getSquarePerimeter(5) << '\n';

    return 0;
}

Notez que square.h est inclus à la fois depuis main.cpp et depuis square.cpp. Cela signifie que le contenu de square.h est inclus une fois dans square.cpp et une fois dans main.cpp.

Examinons plus en détail pourquoi cela se produit. Lorsque square.h est inclus depuis square.cpp, SQUARE_H est défini jusqu'à la fin de square.cpp. Cette définition empêche square.h d'être inclus une deuxième fois dans square.cpp (c'est précisément le rôle des gardes d'en-tête). Cependant, une fois square.cpp terminé, SQUARE_H n'est plus considéré comme défini. Cela signifie que, lorsque le préprocesseur traite main.cpp, SQUARE_H n'est pas défini au départ dans main.cpp.

Le résultat final est que square.cpp et main.cpp reçoivent chacun une copie de la définition de getSquareSides. Ce programme compile, mais l'éditeur de liens (linker) signalera que votre programme possède plusieurs définitions de l'identifiant getSquareSides !

La meilleure façon de contourner ce problème consiste simplement à placer la définition de la fonction dans l'un des fichiers .cpp, de sorte que l'en-tête ne contienne qu'une déclaration anticipée :

square.h :

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides(); // déclaration anticipée de getSquareSides
int getSquarePerimeter(int sideLength); // déclaration anticipée de getSquarePerimeter

#endif

square.cpp :

#include "square.h"

int getSquareSides() // définition effective de getSquareSides
{
    return 4;
}

int getSquarePerimeter(int sideLength)
{
    return sideLength * getSquareSides();
}

main.cpp :

#include "square.h" // square.h est aussi inclus une fois ici
#include <iostream>

int main()
{
    std::cout << "a square has " << getSquareSides() << " sides\n";
    std::cout << "a square of length 5 has perimeter length " << getSquarePerimeter(5) << '\n';

    return 0;
}

Désormais, lors de la compilation, la fonction getSquareSides ne possède qu'une seule définition (dans square.cpp), et l'éditeur de liens est satisfait. Le fichier main.cpp peut appeler cette fonction (bien qu'elle soit définie dans square.cpp) parce qu'il inclut square.h, qui contient une déclaration anticipée de la fonction (l'éditeur de liens relie l'appel à getSquareSides depuis main.cpp à la définition de getSquareSides dans square.cpp).

Ne peut-on pas simplement éviter les définitions dans les fichiers d'en-tête ?

Nous vous avons généralement déconseillé d'inclure des définitions de fonctions dans vos en-têtes. Vous vous demandez peut-être pourquoi il faudrait alors ajouter des gardes d'en-tête, puisqu'elles vous protègent contre quelque chose que vous ne devriez pas faire.

Il existe plusieurs cas, que nous vous présenterons plus tard, où il est nécessaire de placer des définitions autres que des fonctions dans un fichier d'en-tête. Par exemple, le C++ vous permet de créer vos propres types. Ces types personnalisés sont généralement définis dans des fichiers d'en-tête, afin que leurs définitions soient disponibles dans les fichiers de code qui en ont besoin. Sans garde d'en-tête, un fichier de code pourrait finir avec plusieurs copies (identiques) de la définition d'un même type, ce que le compilateur signalera comme une erreur.

Ainsi, même s'il n'est pas strictement nécessaire à ce stade du tutoriel d'utiliser des gardes d'en-tête, nous établissons dès maintenant de bonnes habitudes, afin que vous n'ayez pas à désapprendre de mauvaises habitudes plus tard.

#pragma once

Les compilateurs modernes prennent en charge une forme plus simple de gardes d'en-tête, à l'aide de la directive de préprocesseur #pragma :

#pragma once

// votre code ici

#pragma once a le même objectif que les gardes d'en-tête : empêcher qu'un fichier d'en-tête soit inclus plusieurs fois. Avec les gardes traditionnelles, le développeur est responsable de la protection de l'en-tête (en utilisant les directives de préprocesseur #ifndef, #define et #endif). Avec #pragma once, nous demandons au compilateur de protéger l'en-tête à notre place. La manière exacte dont il s'y prend relève d'un détail propre à chaque implémentation.

Pour les lecteurs avancés

Il existe un cas connu où #pragma once échoue généralement. Si un fichier d'en-tête est copié de sorte qu'il existe à plusieurs endroits du système de fichiers, et que, pour une raison quelconque, les deux copies de l'en-tête sont incluses, les gardes d'en-tête élimineront avec succès les doublons identiques, mais #pragma once ne le fera pas (car le compilateur ne reconnaîtra pas que leur contenu est réellement identique).

Pour la plupart des projets, #pragma once fonctionne parfaitement, et de nombreux développeurs le préfèrent désormais, car il est plus simple et source de moins d'erreurs. De nombreux environnements de développement (IDE) ajoutent aussi automatiquement #pragma once en haut d'un nouveau fichier d'en-tête créé via l'IDE.

Attention

La directive #pragma a été conçue pour que les implémenteurs de compilateurs l'utilisent à leur guise. Ainsi, les pragmas pris en charge et leur signification dépendent entièrement de l'implémentation. À l'exception de #pragma once, ne vous attendez pas à ce qu'un pragma fonctionnant sur un compilateur soit reconnu par un autre.

Comme #pragma once n'est pas défini par la norme C++, il est possible que certains compilateurs ne l'implémentent pas. Pour cette raison, certaines entreprises (comme Google) recommandent d'utiliser les gardes d'en-tête traditionnelles. Dans ce tutoriel, nous privilégierons les gardes d'en-tête, car elles constituent la méthode la plus conventionnelle pour protéger les en-têtes. Cependant, la prise en charge de #pragma once est aujourd'hui assez répandue, et si vous souhaitez utiliser #pragma once à la place, cela est généralement accepté en C++ moderne.

Résumé

Les gardes d'en-tête ont pour but de garantir que le contenu d'un fichier d'en-tête donné n'est pas copié plus d'une fois dans un même fichier, afin d'éviter les définitions en double.

Les déclarations en double ne posent pas de problème, mais même si votre fichier d'en-tête ne contient que des déclarations (aucune définition), il reste une bonne pratique d'y ajouter des gardes d'en-tête.

Notez que les gardes d'en-tête n'empêchent pas le contenu d'un fichier d'en-tête d'être copié (une fois) dans différents fichiers du projet. C'est une bonne chose, car nous avons souvent besoin de référencer le contenu d'un même en-tête depuis différents fichiers du projet.
