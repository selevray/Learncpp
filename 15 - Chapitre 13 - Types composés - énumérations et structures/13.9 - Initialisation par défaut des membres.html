13.9 — Initialisation par défaut des membres

Lorsque nous définissons un type struct (ou class), nous pouvons fournir une valeur d'initialisation par défaut pour chaque membre dans la définition du type. Pour les membres non marqués static, ce processus est parfois appelé initialisation des membres non statiques (non-static member initialization). La valeur d'initialisation est appelée initialiseur de membre par défaut (default member initializer).

Contenu associé

Nous abordons les membres statiques et leur initialisation dans la leçon 15.6 -- Variables membres statiques.

Voici un exemple :

struct Something
{
    int x;       // pas de valeur d'initialisation (mauvais)
    int y {};    // initialisée par valeur par défaut
    int z { 2 }; // valeur par défaut explicite
};

int main()
{
    Something s1; // s1.x est non initialisée, s1.y vaut 0 et s1.z vaut 2

    return 0;
}

Dans la définition ci-dessus de Something, x n'a pas de valeur par défaut, y est initialisée par valeur par défaut, et z a la valeur par défaut 2. Ces valeurs d'initialisation par défaut des membres sont utilisées si l'utilisateur ne fournit pas de valeur d'initialisation explicite lors de la création d'un objet de type Something.

Notre objet s1 n'a pas d'initialiseur, donc les membres de s1 sont initialisés avec leurs valeurs par défaut. s1.x n'a pas d'initialiseur par défaut, elle reste donc non initialisée. s1.y est initialisée par valeur par défaut, elle reçoit donc la valeur 0. Et s1.z est initialisée avec la valeur 2.

Notez que, même si nous n'avons pas fourni d'initialiseur explicite pour s1.z, elle est initialisée à une valeur non nulle grâce à l'initialiseur de membre par défaut fourni.

Point clé

Grâce aux initialiseurs de membres par défaut (ou aux autres mécanismes que nous verrons plus tard), les structs et les classes peuvent s'auto-initialiser même lorsqu'aucun initialiseur explicite n'est fourni !

Pour les lecteurs avancés

La déduction d'arguments de modèle de classe (CTAD, que nous abordons dans la leçon 13.14 -- Déduction d'arguments de modèle de classe (CTAD) et guides de déduction) ne peut pas être utilisée dans l'initialisation des membres non statiques.

Les valeurs d'initialisation explicites prévalent sur les valeurs par défaut

Les valeurs explicites dans une liste d'initialisation prévalent toujours sur les valeurs d'initialisation par défaut des membres.

struct Something
{
    int x;       // pas de valeur d'initialisation par défaut (mauvais)
    int y {};    // initialisée par valeur par défaut
    int z { 2 }; // valeur par défaut explicite
};

int main()
{
    Something s2 { 5, 6, 7 }; // utilise les initialiseurs explicites pour s2.x, s2.y et s2.z (aucune valeur par défaut n'est utilisée)

    return 0;
}

Dans le cas ci-dessus, s2 a des valeurs d'initialisation explicites pour chaque membre, donc les valeurs d'initialisation par défaut des membres ne sont pas du tout utilisées. Cela signifie que s2.x, s2.y et s2.z sont initialisés avec les valeurs 5, 6 et 7 respectivement.

Initialiseurs manquants dans une liste d'initialisation lorsque des valeurs par défaut existent

Dans la leçon précédente (13.8 -- Initialisation d'agrégats de structures), nous avons noté que si un agrégat est initialisé avec moins de valeurs que de membres, tous les membres restants sont initialisés par valeur. Cependant, si un initialiseur de membre par défaut est fourni pour un membre donné, c'est cet initialiseur par défaut qui sera utilisé à la place.

struct Something
{
    int x;       // pas de valeur d'initialisation par défaut (mauvais)
    int y {};    // initialisée par valeur par défaut
    int z { 2 }; // valeur par défaut explicite
};

int main()
{
    Something s3 {}; // initialise s3.x par valeur, utilise les valeurs par défaut pour s3.y et s3.z

    return 0;
}

Dans le cas ci-dessus, s3 est initialisé par liste avec une liste vide, donc tous les initialiseurs sont manquants. Cela signifie qu'un initialiseur de membre par défaut sera utilisé s'il existe, et qu'une initialisation par valeur aura lieu sinon. Ainsi, s3.x (qui n'a pas d'initialiseur de membre par défaut) est initialisée par valeur à 0, s3.y est initialisée par valeur par défaut à 0, et s3.z prend la valeur par défaut 2.

Récapitulatif des possibilités d'initialisation

Si un agrégat est défini avec une liste d'initialisation :

  • Si une valeur d'initialisation explicite existe, cette valeur explicite est utilisée.
  • Si un initialiseur est manquant et qu'un initialiseur de membre par défaut existe, la valeur par défaut est utilisée.
  • Si un initialiseur est manquant et qu'aucun initialiseur de membre par défaut n'existe, une initialisation par valeur a lieu.

Si un agrégat est défini sans liste d'initialisation :

  • Si un initialiseur de membre par défaut existe, la valeur par défaut est utilisée.
  • Si aucun initialiseur de membre par défaut n'existe, le membre reste non initialisé.

Les membres sont toujours initialisés dans l'ordre de leur déclaration.

L'exemple suivant récapitule toutes les possibilités :

struct Something
{
    int x;       // pas de valeur d'initialisation par défaut (mauvais)
    int y {};    // initialisée par valeur par défaut
    int z { 2 }; // valeur par défaut explicite
};

int main()
{
    Something s1;             // Sans liste d'initialisation : s1.x est non initialisée, s1.y et s1.z utilisent les valeurs par défaut
    Something s2 { 5, 6, 7 }; // Initialiseurs explicites : s2.x, s2.y et s2.z utilisent les valeurs explicites (aucune valeur par défaut n'est utilisée)
    Something s3 {};          // Initialiseurs manquants : s3.x est initialisée par valeur, s3.y et s3.z utilisent les valeurs par défaut

    return 0;
}

Le cas à surveiller est s1.x. Comme s1 n'a pas de liste d'initialisation et que x n'a pas d'initialiseur de membre par défaut, s1.x reste non initialisée (ce qui est mauvais, puisque nous devons toujours initialiser nos variables).

Fournissez toujours des valeurs par défaut pour vos membres

Pour éviter le risque de membres non initialisés, assurez-vous simplement que chaque membre possède une valeur par défaut (soit une valeur par défaut explicite, soit une paire d'accolades vide). Ainsi, nos membres seront initialisés avec une valeur, qu'une liste d'initialisation soit fournie ou non.

Considérons la struct suivante, dont tous les membres ont une valeur par défaut :

struct Fraction
{
    int numerator { }; // nous devrions utiliser { 0 } ici, mais pour l'exemple nous utilisons l'initialisation par valeur
    int denominator { 1 };
};

int main()
{
    Fraction f1;          // f1.numerator initialisé par valeur à 0, f1.denominator vaut 1 par défaut
    Fraction f2 {};       // f2.numerator initialisé par valeur à 0, f2.denominator vaut 1 par défaut
    Fraction f3 { 6 };    // f3.numerator initialisé à 6, f3.denominator vaut 1 par défaut
    Fraction f4 { 5, 8 }; // f4.numerator initialisé à 5, f4.denominator initialisé à 8

    return 0;
}

Dans tous les cas, nos membres sont initialisés avec des valeurs.

Bonne pratique

Fournissez une valeur par défaut pour tous les membres. Cela garantit que vos membres seront initialisés même si la définition de la variable ne comporte pas de liste d'initialisation.

Initialisation par défaut ou par valeur pour les agrégats

Revenons sur deux lignes de l'exemple ci-dessus :

    Fraction f1;          // f1.numerator initialisé par valeur à 0, f1.denominator vaut 1 par défaut
    Fraction f2 {};       // f2.numerator initialisé par valeur à 0, f2.denominator vaut 1 par défaut

Vous remarquerez que f1 est initialisée par défaut et f2 est initialisée par valeur, pourtant les résultats sont identiques (numerator vaut 0 et denominator vaut 1). Laquelle faut-il préférer ?

Le cas de l'initialisation par valeur (f2) est plus sûr, car il garantit que les membres sans valeur par défaut sont initialisés par valeur (et même si nous devons toujours fournir des valeurs par défaut pour les membres, cela protège contre le cas où l'on en oublierait une).

Préférer l'initialisation par valeur présente un avantage supplémentaire : elle est cohérente avec la façon dont nous initialisons les objets d'autres types. La cohérence aide à prévenir les erreurs.

Bonne pratique

Pour les agrégats, préférez l'initialisation par valeur (avec un initialiseur à accolades vides) à l'initialisation par défaut (sans accolades).

Cela dit, il n'est pas rare que les programmeurs utilisent l'initialisation par défaut plutôt que l'initialisation par valeur pour les types classe. Cela tient en partie à des raisons historiques (l'initialisation par valeur n'a été introduite qu'avec C++11), et en partie à un cas particulier (pour les non-agrégats) où l'initialisation par défaut peut être plus efficace que l'initialisation par valeur (nous abordons ce cas dans la leçon 14.11 -- Constructeurs par défaut et arguments par défaut).

Par conséquent, nous ne serons pas intransigeants sur l'usage de l'initialisation par valeur pour les structs et les classes dans ces tutoriels, mais nous la recommandons vivement.
