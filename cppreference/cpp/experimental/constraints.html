Contraintes et concepts

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Cette page décrit une fonctionnalité expérimentale du langage de base. Pour les exigences nommées sur les types utilisées dans la spécification de la bibliothèque standard, voir exigences nommées

Les modèles de classe, les modèles de fonction et les fonctions non template (généralement membres de modèles de classe) peuvent être associés à une contrainte, qui précise les exigences sur les arguments de modèle et peut servir à sélectionner la surcharge de fonction et la spécialisation de modèle les plus appropriées.

Les contraintes peuvent également servir à limiter la déduction automatique de type dans les déclarations de variables et les types de retour des fonctions aux seuls types satisfaisant les exigences spécifiées.

Les ensembles nommés de telles exigences sont appelés concepts. Chaque concept est un prédicat, évalué à la compilation, et fait partie de l'interface d'un modèle lorsqu'il est utilisé comme contrainte :

#include <string>
#include <locale>
using namespace std::literals;

// Déclaration du concept « EqualityComparable », satisfait par
// tout type T tel que, pour les valeurs a et b de type T,
// l'expression a==b se compile et son résultat est convertible en bool
template<typename T>
concept bool EqualityComparable = requires(T a, T b) {
    { a == b } -> bool;
};

void f(EqualityComparable&&); // déclaration d'un modèle de fonction contraint
// template<typename T>
// void f(T&&) requires EqualityComparable<T>; // forme longue équivalente

int main() {
  f("abc"s); // OK, std::string est EqualityComparable
  f(std::use_facet<std::ctype<char>>(std::locale{})); // Error: not EqualityComparable
}

Les violations de contraintes sont détectées à la compilation, tôt dans le processus d'instanciation du modèle, ce qui produit des messages d'erreur faciles à suivre.

std::list<int> l = {3,-1,10};
std::sort(l.begin(), l.end());
//Diagnostic typique du compilateur sans concepts :
//  invalid operands to binary expression ('std::_List_iterator<int>' and
//  'std::_List_iterator<int>')
//                           std::__lg(__last - __first) * 2);
//                                     ~~~~~~ ^ ~~~~~~~
// ... 50 lignes de sortie ...
//
//Diagnostic typique du compilateur avec concepts :
//  error: cannot call std::sort with std::_List_iterator<int>
//  note:  concept RandomAccessIterator<std::_List_iterator<int>> n'est pas satisfait

Le but des concepts est de modéliser des catégories sémantiques (Number, Range, RegularFunction) plutôt que des restrictions syntaxiques (HasPlus, Array). Selon les directives de base ISO C++ T.20, "La capacité de spécifier une sémantique significative est une caractéristique déterminante d'un véritable concept, par opposition à une contrainte syntaxique."

Si la prise en charge des tests de fonctionnalités est disponible, les fonctionnalités décrites ici sont indiquées par la constante macro __cpp_concepts dont la valeur est égale ou supérieure à 201507.

Espaces réservés

L'espace réservé sans contrainte auto et les espaces réservés contraints, qui ont la forme concept-name < template-argument-list(facultatif)>, sont des espaces réservés pour le type à déduire.

Les espaces réservés peuvent apparaître dans les déclarations de variables (auquel cas ils sont déduits de l'initialisation) ou dans les types de retour des fonctions (auquel cas ils sont déduits des instructions return).

std::pair<auto, auto> p2 = std::make_pair(0, 'a'); // le premier auto est int,
                                                   // le second auto est char

Sortable x = f(y); // le type de x est déduit du type de retour de f,
                   // ne compile que si le type satisfait la contrainte Sortable

auto f(Container) -> Sortable; // le type de retour est déduit de l'instruction return
                               // ne compile que si le type satisfait Sortable

Les espaces réservés peuvent aussi apparaître dans les paramètres, auquel cas ils transforment les déclarations de fonctions en déclarations de modèles (contraintes si l'espace réservé est contraint).

void f(std::pair<auto, EqualityComparable>); // il s'agit d'un modèle à deux paramètres :
       // un paramètre de type non contraint et un paramètre non-type contraint

Les espaces réservés contraints peuvent être utilisés partout où auto peut l'être, par exemple dans les déclarations de lambdas génériques.

auto gl = [](Assignable& a, auto* b) { a = *b; };

Si un spécificateur de type contraint désigne un élément qui n'est pas de type ou un modèle, mais est utilisé comme espace réservé contraint, le programme est mal formé :

template<size_t N> concept bool Even = (N%2 == 0);
struct S1 { int n; };
int Even::* p2 = &S1::n; // erreur, utilisation invalide d'un concept non-type
void f(std::array<auto, Even>); // erreur, utilisation invalide d'un concept non-type
template<Even N> void f(std::array<auto, N>); // OK

Modèles abrégés

Si un ou plusieurs espaces réservés apparaissent dans une liste de paramètres de fonction, la déclaration de fonction est en fait une déclaration de modèle de fonction, dont la liste de paramètres de modèle comprend un paramètre inventé pour chaque espace réservé unique, dans l'ordre d'apparition.

// forme courte
void g1(const EqualityComparable*, Incrementable&);
// forme longue :
// template<EqualityComparable T, Incrementable U> void g1(const T*, U&);
// forme plus longue :
// template<typename T, typename U>
// void g1(const T*, U&) requires EqualityComparable<T> && Incrementable<U>;

void f2(std::vector<auto*>...);
// forme longue : template<typename... T> void f2(std::vector<T*>...);

void f4(auto (auto::*)(auto));
// forme longue : template<typename T, typename U, typename V> void f4(T (U::*)(V));

Tous les espaces réservés introduits par des spécificateurs de type contraints équivalents ont le même paramètre de modèle inventé. En revanche, chaque spécificateur non contraint (auto) introduit toujours un paramètre de modèle différent.

void f0(Comparable a, Comparable* b);
// forme longue : template<Comparable T> void f0(T a, T* b);

void f1(auto a, auto* b);
// forme longue : template<typename T, typename U> f1(T a, U* b);

Les modèles de fonctions et les modèles de classes peuvent tous deux être déclarés à l'aide d'une introduction de modèle, de syntaxe concept-name { parameter-list(facultatif)} , auquel cas le mot-clé template n'est pas nécessaire : chaque paramètre de la parameter-list de l'introduction de modèle devient un paramètre de modèle dont la nature (type, non-type, modèle) est déterminée par la nature du paramètre correspondant du concept nommé.

En plus de déclarer un modèle, l'introduction de modèle associe une contrainte de prédicat (voir ci-dessous) qui nomme (pour les concepts de variables) ou invoque (pour les concepts de fonctions) le concept nommé par l'introduction.

EqualityComparable{T} class Foo;
// forme longue : template<EqualityComparable T> class Foo;
// forme plus longue : template<typename T> requires EqualityComparable<T> class Foo;

template<typename T, int N, typename... Xs> concept bool Example = ...;
Example{A, B, ...C} struct S1;
// forme longue template<class A, int B, class... C> requires Example<A,B,C...> struct S1;

Pour les modèles de fonctions, l'introduction de modèle peut être combinée avec des espaces réservés :

Sortable{T} void f(T, auto);
// forme longue : template<Sortable T, typename U> void f(T, U);
// variante utilisant uniquement des espaces réservés : void f(Sortable, auto);

Concepts

Un concept est un ensemble nommé d'exigences. La définition d'un concept apparaît dans la portée d'espace de noms et prend la forme d'une définition de modèle de fonction (auquel cas il est appelé concept de fonction) ou d'une définition de modèle de variable (auquel cas il est appelé concept de variable). La seule différence est que le mot-clé concept apparaît dans la decl-specifier-seq :

// concept de variable de la bibliothèque standard (Ranges TS)
template <class T, class U>
concept bool Derived = std::is_base_of<U, T>::value;

// concept de fonction de la bibliothèque standard (Ranges TS)
template <class T>
concept bool EqualityComparable() {
    return requires(T a, T b) { {a == b} -> Boolean; {a != b} -> Boolean; };
}

Les restrictions suivantes s'appliquent aux concepts de fonctions :

  • inline et constexpr ne sont pas autorisés, la fonction est automatiquement inline et constexpr
  • friend et virtual ne sont pas autorisés
  • la spécification d'exception n'est pas autorisée, la fonction est automatiquement noexcept(true).
  • ne peut pas être déclarée puis définie plus tard, ne peut pas être redéclarée
  • le type de retour doit être bool
  • la déduction du type de retour n'est pas autorisée
  • la liste de paramètres doit être vide
  • le corps de la fonction ne doit consister qu'en une instruction return, dont l'argument doit être une constraint-expression (contrainte de prédicat, conjonction/disjonction d'autres contraintes, ou une requires-expression, voir ci-dessous)

Les restrictions suivantes s'appliquent aux concepts de variables :

  • Doit avoir le type bool
  • ne peut pas être déclarée sans initialisateur
  • ne peut pas être déclarée ni être dans la portée de classe.
  • constexpr n'est pas autorisé, la variable est automatiquement constexpr
  • l'initialisateur doit être une expression de contrainte (contrainte de prédicat, conjonction/disjonction de contraintes, ou une requires-expression, voir ci-dessous)

Les concepts ne peuvent pas se référer récursivement à eux-mêmes dans le corps de la fonction ou dans l'initialisateur de la variable :

template<typename T>
concept bool F() { return F<typename T::type>(); } // error
template<typename T>
concept bool V = V<T*>; // error

Les instanciations explicites, les spécialisations explicites ou les spécialisations partielles de concepts ne sont pas autorisées (la signification de la définition originale d'une contrainte ne peut pas être modifiée)

Contraintes

Une contrainte est une séquence d'opérations logiques qui précise les exigences sur les arguments de modèle. Elles peuvent apparaître dans des requires-expressions (voir ci-dessous) et directement comme corps de concepts.

Il existe 9 types de contraintes :

conjonctions 1)

disjonctions 2)

  1. contraintes de prédicat

  2. contraintes d'expression (uniquement dans une requires-expression)

  3. contraintes de type (uniquement dans une requires-expression)

  4. contraintes de conversion implicite (uniquement dans une requires-expression)

  5. contraintes de déduction d'arguments (uniquement dans une requires-expression)

  6. contraintes d'exception (uniquement dans une requires-expression)

  7. contraintes paramétrées (uniquement dans une requires-expression)

Les trois premiers types de contraintes peuvent apparaître directement comme corps d'un concept ou comme clause requires ad hoc :

template<typename T>
requires // requires-clause (contrainte ad hoc)
sizeof(T) > 1 && get_value<T>() // conjonction de deux contraintes de prédicat
void f(T);

Lorsque plusieurs contraintes sont attachées à la même déclaration, la contrainte totale est une conjonction dans l'ordre suivant : la contrainte introduite par l'introduction de modèle, les contraintes de chaque paramètre de modèle dans l'ordre d'apparition, la clause requires après la liste de paramètres de modèle, les contraintes de chaque paramètre de fonction dans l'ordre d'apparition, puis la clause requires finale :

// les déclarations déclarent le même modèle de fonction contraint
// avec la contrainte Incrementable<T> && Decrementable<T>
template<Incrementable T> void f(T) requires Decrementable<T>;
template<typename T> requires Incrementable<T> && Decrementable<T> void f(T); // ok

// les deux déclarations suivantes ont des contraintes différentes :
// la première déclaration a Incrementable<T> && Decrementable<T>
// la seconde déclaration a Decrementable<T> && Incrementable<T>
// Bien qu'elles soient logiquement équivalentes.
// La seconde déclaration est mal formée, aucun diagnostic requis

template<Incrementable T> requires Decrementable<T> void g();
template<Decrementable T> requires Incrementable<T> void g(); // error

Conjonctions

La conjonction de contraintes P et Q est spécifiée comme P && Q.

// exemples de concepts de la bibliothèque standard (Ranges TS)
template <class T>
concept bool Integral = std::is_integral<T>::value;
template <class T>
concept bool SignedIntegral = Integral<T> && std::is_signed<T>::value;
template <class T>
concept bool UnsignedIntegral = Integral<T> && !SignedIntegral<T>;

Une conjonction de deux contraintes n'est satisfaite que si les deux contraintes sont satisfaites. Les conjonctions sont évaluées de gauche à droite et court-circuitées (si la contrainte de gauche n'est pas satisfaite, la substitution des arguments de modèle dans la contrainte de droite n'est pas tentée : cela évite les échecs dus à une substitution hors du contexte immédiat). Les surcharges définies par l'utilisateur de operator&& ne sont pas autorisées dans les conjonctions de contraintes.

Disjonctions

La disjonction de contraintes P et Q est spécifiée comme P || Q.

Une disjonction de deux contraintes est satisfaite si l'une des deux contraintes est satisfaite. Les disjonctions sont évaluées de gauche à droite et court-circuitées (si la contrainte de gauche est satisfaite, la déduction des arguments de modèle dans la contrainte de droite n'est pas tentée). Les surcharges définies par l'utilisateur de operator|| ne sont pas autorisées dans les disjonctions de contraintes.

// exemple de contrainte de la bibliothèque standard (Ranges TS)
template <class T = void>
requires EqualityComparable<T>() || Same<T, void>
struct equal_to;

Contraintes de prédicat

Une contrainte de prédicat est une expression constante de type bool. Elle n'est satisfaite que si elle s'évalue à true

template<typename T> concept bool Size32 = sizeof(T) == 4;

Les contraintes de prédicat peuvent spécifier des exigences sur les paramètres de modèle non typés et sur les arguments de modèle de modèle.

Les contraintes de prédicat doivent s'évaluer directement à bool, aucune conversion n'est autorisée :

template<typename T> struct S {
    constexpr explicit operator bool() const { return true; }
};
template<typename T>
requires S<T>{} // mauvaise contrainte de prédicat : S<T>{} n'est pas bool
void f(T);
f(0); // erreur : contrainte jamais satisfaite

Exigences

Le mot-clé requires est utilisé de deux manières :

  1. Pour introduire une requires-clause, qui spécifie des contraintes sur les arguments de modèle ou sur une déclaration de fonction.
template<typename T>
void f(T&&) requires Eq<T>; // peut apparaître comme dernier élément d'un déclarateur de fonction

template<typename T> requires Addable<T> // ou juste après une liste de paramètres de modèle
T add(T a, T b) { return a + b; }

Dans ce cas, le mot-clé requires doit être suivi d'une expression constante (il est donc possible d'écrire « requires true; »), mais l'intention est qu'un concept nommé (comme dans l'exemple ci-dessus), une conjonction ou une disjonction de concepts nommés, ou une requires-expression soit utilisé.

  1. Pour commencer une requires-expression, qui est une expression prvalue de type bool décrivant les contraintes sur certains arguments de modèle. Une telle expression vaut true si le concept correspondant est satisfait, et false sinon :
template<typename T>
concept bool Addable = requires (T x) { x + x; }; // requires-expression

template<typename T> requires Addable<T> // requires-clause, et non requires-expression
T add(T a, T b) { return a + b; }

template<typename T>
requires requires (T x) { x + x; } // contrainte ad hoc, notez que le mot-clé est utilisé deux fois
T add(T a, T b) { return a + b; }

La syntaxe de requires-expression est la suivante :

| | | | requires ( parameter-list(optionnel) ) { requirement-seq } | | | |

  • parameter-list — une liste de paramètres séparés par des virgules, comme dans une déclaration de fonction, à ceci près que les arguments par défaut ne sont pas autorisés et que le dernier paramètre ne peut pas être une ellipse. Ces paramètres n'ont ni stockage, ni liaison, ni durée de vie. Ces paramètres sont dans la portée jusqu'à la } fermante de la requirement-seq. Si aucun paramètre n'est utilisé, les parenthèses rondes peuvent aussi être omises
  • requirement-seq — suite d'exigences séparées par des espaces, décrites ci-dessous (chaque exigence se termine par un point-virgule). Chaque exigence ajoute une autre contrainte à la conjonction de contraintes que cette requires-expression définit.

Chaque exigence dans requirements-seq est l'une des suivantes :

  • exigence simple
  • exigences de type
  • exigences composées
  • exigences imbriquées

Les exigences peuvent faire référence aux paramètres de modèle dans la portée et aux paramètres locaux introduits dans parameter-list. Lorsqu'elle est paramétrée, une requires-expression est dite introduire une contrainte paramétrée

La substitution d'arguments de modèle dans une requires-expression peut entraîner la formation de types ou d'expressions invalides dans ses exigences. Dans de tels cas,

  • Si un échec de substitution se produit dans une requires-expression utilisée en dehors de la déclaration d'une entité templatisée, alors le programme est mal formé.
  • Si la requires-expression est utilisée dans la déclaration d'une entité templatisée, la contrainte correspondante est considérée comme « non satisfaite » et l'échec de substitution n'est pas une erreur, cependant
  • Si un échec de substitution se produirait dans une requires-expression pour chaque argument de modèle possible, le programme est mal formé, aucun diagnostic requis :
template<class T> concept bool C = requires {
    new int[-(int)sizeof(T)]; // invalide pour tout T : mal formé, aucun diagnostic requis
};

Exigences simples

Une exigence simple est une instruction d'expression arbitraire. L'exigence est que l'expression soit valide (il s'agit d'une contrainte d'expression). Contrairement aux contraintes de prédicat, l'évaluation n'a pas lieu : seule la correction du langage est vérifiée.

template<typename T>
concept bool Addable =
requires (T a, T b) {
    a + b; // "l'expression a+b est une expression valide qui compilera"
};

// exemple de contrainte de la bibliothèque standard (Ranges TS)
template <class T, class U = T>
concept bool Swappable = requires(T&& t, U&& u) {
    swap(std::forward<T>(t), std::forward<U>(u));
    swap(std::forward<U>(u), std::forward<T>(t));
};

Exigences de type

Une exigence de type est le mot-clé typename suivi d'un nom de type, éventuellement qualifié. L'exigence est que le type nommé existe (une contrainte de type) : cela peut servir à vérifier qu'un certain type imbriqué nommé existe, qu'une spécialisation de modèle de classe désigne un type, ou qu'un modèle d'alias désigne un type.

template<typename T> using Ref = T&;
template<typename T> concept bool C =
requires {
    typename T::inner; // nom de membre imbriqué requis
    typename S<T>;     // spécialisation de modèle de classe requise
    typename Ref<T>;   // substitution de modèle d'alias requise
};

//Exemple de concept de la bibliothèque standard (Ranges TS)
template <class T, class U> using CommonType = std::common_type_t<T, U>;
template <class T, class U> concept bool Common =
requires (T t, U u) {
    typename CommonType<T, U>; // CommonType<T, U> est valide et désigne un type
    { CommonType<T, U>{std::forward<T>(t)} };
    { CommonType<T, U>{std::forward<U>(u)} };
};

Exigences composées

Une exigence composée a la forme

| | | | { expression } noexcept(optionnel) trailing-return-type(optionnel) ; | | | |

et spécifie une conjonction des contraintes suivantes :

  1. expression est une expression valide (contrainte d'expression)

  2. Si noexcept est utilisé, l'expression doit aussi être noexcept (contrainte d'exception)

  3. Si trailing-return-type désigne un type qui utilise des placeholders, le type doit être déductible à partir du type de l'expression (contrainte de déduction d'argument)

  4. Si trailing-return-type désigne un type qui n'utilise pas de placeholders, alors deux contraintes supplémentaires sont ajoutées :

4a) le type désigné par trailing-return-type est valide (contrainte de type)

4b) le résultat de l'expression est implicitement convertible en ce type (contrainte de conversion implicite)

template<typename T> concept bool C2 =
requires(T x) {
    {*x} -> typename T::inner; // l'expression *x doit être valide
                               // ET le type T::inner doit être valide
                               // ET le résultat de *x doit être convertible en T::inner
};

// Exemple de concept de la bibliothèque standard (Ranges TS)
template <class T, class U> concept bool Same = std::is_same<T,U>::value;
template <class B> concept bool Boolean =
requires(B b1, B b2) {
    { bool(b1) }; // la contrainte d'initialisation directe doit utiliser une expression
    { !b1 } -> bool; // contrainte composée
    requires Same<decltype(b1 && b2), bool>; // contrainte imbriquée, voir ci-dessous
    requires Same<decltype(b1 || b2), bool>;
};

Exigences imbriquées

Une exigence imbriquée est une autre requires-clause, terminée par un point-virgule. Elle sert à introduire des contraintes de prédicat (voir ci-dessus) exprimées en termes d'autres concepts nommés appliqués aux paramètres locaux (en dehors d'une requires-clause, les contraintes de prédicat ne peuvent pas utiliser de paramètres, et placer directement une expression dans une requires-clause en fait une contrainte d'expression, qui n'est donc pas évaluée)

// exemple de contrainte des Ranges TS
template <class T>
concept bool Semiregular = DefaultConstructible<T> &&
    CopyConstructible<T> && Destructible<T> && CopyAssignable<T> &&
requires(T a, size_t n) {
    requires Same<T*, decltype(&a)>;  // imbriquée : "Same<...> s'évalue à true"
    { a.~T() } noexcept;  // composée : "a.~T()" est une expression valide qui ne lève pas d'exception
    requires Same<T*, decltype(new T)>; // imbriquée : "Same<...> s'évalue à true"
    requires Same<T*, decltype(new T[n])>; // nested
    { delete new T };  // compound
    { delete new T[n] }; // compound
};

Résolution de concept

Comme tout autre modèle de fonction, un concept de fonction (mais pas un concept de variable) peut être surchargé : plusieurs définitions de concept peuvent être fournies, toutes utilisant le même concept-name.

La résolution de concept est effectuée lorsqu'un concept-name (qui peut être qualifié) apparaît dans

  1. un spécificateur de type contraint void f(Concept); std::vector<Concept> x = ...;

  2. un paramètre contraint template<Concept T> void f();

  3. une introduction de modèle Concept{T} struct X;

  4. une constraint-expression template<typename T> void f() requires Concept<T>;

template<typename T> concept bool C() { return true; } // #1
template<typename T, typename U> concept bool C() { return true; } // #2
void f(C); // l'ensemble des concepts auxquels C fait référence inclut à la fois #1 et #2 ;
           // la résolution de concept (voir ci-dessous) sélectionne #1.

Pour effectuer la résolution de concept, les paramètres de modèle de chaque concept qui correspond au nom (et à la qualification, le cas échéant) sont mis en correspondance avec une suite d'arguments de concept, qui sont des arguments de modèle et des jokers. Un joker peut correspondre à un paramètre de modèle de n'importe quel genre (type, non typé, modèle). L'ensemble d'arguments est construit différemment selon le contexte

  1. Pour un nom de concept utilisé dans un spécificateur de type contraint ou un paramètre, si le nom de concept est utilisé sans liste de paramètres, la liste d'arguments est un unique joker.
template<typename T> concept bool C1() { return true; } // #1
template<typename T, typename U> concept bool C1() { return true; } // #2
void f1(const C1*); // <wildcard> correspond à <T>, sélectionne #1
  1. Pour un nom de concept utilisé dans un spécificateur de type contraint ou un paramètre, si le nom de concept est utilisé avec une liste d'arguments de modèle, la liste d'arguments est un unique joker suivi de cette liste d'arguments.
template<typename T> concept bool C1() { return true; } // #1
template<typename T, typename U> concept bool C1() { return true; } // #2
void f2(C1<char>); // <wildcard, char> correspond à <T, U>, sélectionne #2
  1. Si un concept apparaît dans une introduction de modèle, la liste d'arguments est une suite de placeholders de même longueur que la liste des paramètres de l'introduction de modèle
template<typename... Ts>
concept bool C3 = true;
C3{T} void q2();     // OK : <T> correspond à <...Ts>
C3{...Ts} void q1(); // OK : <...Ts> correspond à <...Ts>
  1. Si un concept apparaît comme nom d'un template-id, la liste d'arguments de concept est exactement la suite des arguments de ce template-id
template<typename T> concept bool C() { return true; } // #1
template<typename T, typename U> concept bool C() { return true; } // #2

template <typename T>
void f(T) requires C<T>(); // matches #1

La résolution de concept est effectuée en mettant en correspondance chaque argument avec le paramètre correspondant de chaque concept visible. Les arguments de modèle par défaut (s'ils sont utilisés) sont instanciés pour chaque paramètre qui ne correspond à aucun argument, puis ajoutés à la liste d'arguments. Un paramètre de modèle ne correspond à un argument que s'il est du même genre (type, non typé, modèle), sauf si l'argument est un joker. Un pack de paramètres correspond à zéro ou plusieurs arguments tant que tous les arguments correspondent au motif par leur genre (sauf s'il s'agit de jokers).

Si un argument ne correspond pas à son paramètre correspondant, ou s'il y a plus d'arguments que de paramètres et que le dernier paramètre n'est pas un pack, le concept n'est pas viable. S'il y a zéro concept viable, ou plus d'un, le programme est mal formé.

template<typename T> concept bool C2() { return true; }
template<int T> concept bool C2() { return true; }

template<C2<0> T> struct S1; // error: <wildcard, 0> correspond
                             // ni à <typename T> ni à <int T>
template<C2 T> struct S2; // #1 et #2 correspondent tous deux : erreur

Ordre partiel des contraintes

Avant toute analyse supplémentaire, les contraintes sont normalisées en substituant le corps de chaque concept nommé et de chaque requires-expression, jusqu'à ce qu'il ne reste qu'une suite de conjonctions et de disjonctions de contraintes atomiques, qui sont des contraintes de prédicat, contraintes d'expression, contraintes de type, contraintes de conversion implicite, contraintes de déduction d'argument et contraintes d'exception.

Le concept P est dit subsumer le concept Q s'il peut être prouvé que P implique Q sans analyser l'équivalence des types et des expressions (donc N >= 0 ne subsume pas N > 0)

Plus précisément, P est d'abord converti en forme normale disjonctive et Q est converti en forme normale conjonctive, puis ils sont comparés comme suit :

  • chaque contrainte atomique A subsume la contrainte atomique équivalente A
  • chaque contrainte atomique A subsume une disjonction A||B et ne subsume pas une conjonction A&&B
  • chaque conjonction A&&B subsume A, mais une disjonction A||B ne subsume pas A

La relation de subsomption définit un ordre partiel des contraintes, utilisé pour déterminer :

  • le meilleur candidat viable pour une fonction non template dans la résolution de surcharge
  • l'adresse d'une fonction non template dans un ensemble de surcharges
  • la meilleure correspondance pour un argument de modèle de modèle
  • l'ordre partiel des spécialisations de modèles de classe
  • ordre partiel des modèles de fonction

Si les déclarations D1 et D2 sont contraintes et que les contraintes normalisées de D1 subsument les contraintes normalisées de D2 (ou si D1 est contrainte et D2 non contrainte), alors D1 est dite au moins aussi contrainte que D2. Si D1 est au moins aussi contrainte que D2 et que D2 n'est pas au moins aussi contrainte que D1, alors D1 est plus contrainte que D2.

template<typename T>
concept bool Decrementable = requires(T t) { --t; };
template<typename T>
concept bool RevIterator = Decrementable<T> && requires(T t) { *t; };

// RevIterator subsume Decrementable, mais pas l'inverse
// RevIterator est plus contraint en tant que Decrementable

void f(Decrementable); // #1
void f(RevIterator);   // #2

f(0);       // int satisfait uniquement Decrementable, sélectionne #1
f((int*)0); // int* satisfait les deux contraintes, sélectionne #2 comme plus contraint

void g(auto);          // #3 (unconstrained)
void g(Decrementable); // #4

g(true);  // bool ne satisfait pas Decrementable, sélectionne #3
g(0);     // int satisfait Decrementable, sélectionne #4 car il est plus contraint
