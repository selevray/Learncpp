std::signal

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Défini dans l'en-tête <csignal>

/* signal-handler */* signal( int sig, /* signal-handler */* handler );  // (1)

extern "C" using /* signal-handler */ = void(int);  // (2) ( exposition uniquement* )

Modifie la gestion du signal sig. Selon handler, le signal peut être ignoré, remis à sa valeur par défaut ou pris en charge par une fonction définie par l'utilisateur.

Lorsqu'un gestionnaire de signal est défini comme une fonction et qu'un signal survient, il est défini par l'implémentation que std::signal(sig, SIG_DFL) soit exécuté immédiatement avant le début du gestionnaire de signal. De plus, l'implémentation peut empêcher certains ensembles de signaux définis par l'implémentation de survenir pendant l'exécution du gestionnaire de signal.

Pour certains signaux, l'implémentation peut appeler std::signal(sig, SIG_IGN) au démarrage du programme. Pour les autres, l'implémentation doit appeler std::signal(sig, SIG_DFL).

(Remarque : POSIX a introduit sigaction pour normaliser ces comportements définis par l'implémentation)

Paramètres

  • sig — le signal pour lequel définir le gestionnaire de signal. Il peut s'agir d'une valeur définie par l'implémentation ou de l'une des valeurs suivantes :

    • SIGABRTSIGFPESIGILLSIGINTSIGSEGVSIGTERM — définit les types de signaux (constante macro)

  • handler — le gestionnaire de signal. Il doit s'agir de l'une des valeurs suivantes :

    • macro SIG_DFL. Le gestionnaire de signal est défini sur le gestionnaire de signal par défaut.
    • macro SIG_IGN. Le signal est ignoré.
    • Un pointeur vers une fonction. La signature de la fonction doit être équivalente à la suivante :
    extern "C" void fun(int sig);

Valeur de retour

Gestionnaire de signal précédent en cas de succès, ou SIG_ERR en cas d'échec (la définition d'un gestionnaire de signal peut être désactivée sur certaines implémentations).

Gestionnaire de signal

Les limitations suivantes sont imposées à la fonction définie par l'utilisateur installée comme gestionnaire de signal.

Si le gestionnaire de signal n'est PAS appelé à la suite de std::abort ou de std::raise (signal asynchrone), le comportement est indéfini si

  • le gestionnaire de signal appelle une fonction quelconque de la bibliothèque standard, à l'exception de

  • std::abort

  • std::_Exit

  • std::quick_exit

  • std::signal avec pour premier argument le numéro du signal actuellement traité (le gestionnaire asynchrone peut se réenregistrer lui-même, mais pas d'autres signaux).

  • le gestionnaire de signal fait référence à un objet quelconque ayant une durée de stockage statique qui n'est pas std::atomic ou (depuis C++11)volatile std::sig_atomic_t.

(jusqu'à C++17)

Une opération atomique simple sans verrou est une invocation d'une fonction f de <atomic>ou <stdatomic.h> (depuis C++23), telle que :

  • f est la fonction std::atomic_is_lock_free,
  • f est la fonction membre is_lock_free (par exemple std::atomic::is_lock_free()),
  • f est une fonction membre non statique de std::atomic_flag,
  • f est une fonction non membre, et le premier paramètre de f a le type cv std::atomic_flag*,
  • f est une fonction membre non statique invoquée sur un objet obj, tel que obj.is_lock_free() donne true, ou
  • f est une fonction non membre, et pour chaque argument pointeur vers atomique arg passé à f, std::atomic_is_lock_free(arg) donne true.

Le comportement est indéfini si un gestionnaire de signal effectue l'une des opérations suivantes :

  • appel à une fonction de la bibliothèque quelconque, à l'exception des opérations atomiques simples sans verrou et des fonctions sûres vis-à-vis des signaux suivantes (notez, en particulier, que l'allocation dynamique n'est pas sûre vis-à-vis des signaux) :

  • std::signal avec pour premier argument le numéro du signal actuellement traité (le gestionnaire de signal peut se réenregistrer lui-même, mais pas d'autres signaux).

  • fonctions membres de std::numeric_limits

  • std::_Exit

  • std::abort

  • std::quick_exit

  • Les fonctions membres de std::initializer_list et les surcharges std::initializer_list de std::begin et std::end

  • std::forward, std::move, std::move_if_noexcept

  • Toutes les fonctions de <type_traits>

  • std::memcpy and std::memmove

  • accès à un objet ayant une durée de stockage de thread

  • une expression dynamic_cast

  • une expression throw

  • entrée dans un try block

  • initialisation d'une variable statique qui effectue une initialisation dynamique non locale (y compris celle différée jusqu'à la première utilisation ODR)

  • attente de la fin de l'initialisation d'une variable quelconque ayant une durée de stockage statique en raison d'une initialisation concurrente par un autre thread

(depuis C++17)

Si la fonction définie par l'utilisateur retourne lors du traitement de SIGFPE, SIGILL, SIGSEGV ou de tout autre signal défini par l'implémentation signalant une exception de calcul, le comportement est indéfini.

Si le gestionnaire de signal est appelé à la suite de std::abort ou de std::raise (signal synchrone), le comportement est indéfini si le gestionnaire de signal appelle std::raise.

À l'entrée dans le gestionnaire de signal, l'état de l'environnement en virgule flottante et les valeurs de tous les objets sont non spécifiés, à l'exception de

  • objets de type volatile std::sig_atomic_t
  • objets de types std::atomic sans verrou
  • effets de bord rendus visibles par std::atomic_signal_fence

(depuis C++11)

Au retour d'un gestionnaire de signal, la valeur de tout objet modifié par le gestionnaire de signal qui n'est pas volatile std::sig_atomic_t ou std::atomic sans verrou est indéterminée.

(jusqu'à C++14)

Un appel à la fonction signal() se synchronise avec toute invocation résultante du gestionnaire de signal.

Si un gestionnaire de signal est exécuté suite à un appel à std::raise (de manière synchrone), alors l'exécution du gestionnaire est séquencée après l'invocation de std::raise et séquencée avant le retour de celle-ci, et s'exécute sur le même thread que std::raise. L'exécution des gestionnaires pour les autres signaux est non séquencée par rapport au reste du programme et s'exécute sur un thread non spécifié.

Deux accès au même objet de type volatile std::sig_atomic_t ne produisent pas de course de données si les deux se produisent dans le même thread, même si l'un ou plusieurs d'entre eux se produisent dans un gestionnaire de signal. Pour chaque invocation de gestionnaire de signal, les évaluations effectuées par le thread invoquant un gestionnaire de signal peuvent être divisées en deux groupes A et B, de telle sorte qu'aucune évaluation de B se produit avant les évaluations de A, et que les évaluations de tels objets volatile std::sig_atomic_t prennent des valeurs comme si toutes les évaluations de A se produisaient avant l'exécution du gestionnaire de signal, et que l'exécution du gestionnaire de signal se produise avant toutes les évaluations de B.

(depuis C++14)

Notes

POSIX exige que signal soit thread-safe, et spécifie une liste de fonctions de bibliothèque async-signal-safe qui peuvent être appelées depuis n'importe quel gestionnaire de signal.

Les gestionnaires de signaux doivent avoir une liaison C et, en général, n'utiliser que les fonctionnalités du sous-ensemble commun de C et C++. Cependant, les implémentations courantes permettent d'utiliser une fonction ayant une liaison C++ comme gestionnaire de signal.

Exemple

#include <csignal>
#include <iostream>

namespace
{
    volatile std::sig_atomic_t gSignalStatus;
}

void signal_handler(int signal)
{
    gSignalStatus = signal;
}

int main()
{
    // Installer un gestionnaire de signal
    std::signal(SIGINT, signal_handler);

    std::cout << "SignalValue: " << gSignalStatus << '\n';
    std::cout << "Sending signal: " << SIGINT << '\n';
    std::raise(SIGINT);
    std::cout << "SignalValue: " << gSignalStatus << '\n';
}

Sortie possible :

SignalValue: 0
Sending signal: 2
SignalValue: 2
