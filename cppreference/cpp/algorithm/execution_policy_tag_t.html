  1. Le type de politique d'exécution utilisé comme type unique pour lever l'ambiguïté de la surcharge des algorithmes parallèles et exiger que l'exécution d'un algorithme parallèle ne puisse pas être parallélisée. Les invocations des fonctions d'accès aux éléments dans les algorithmes parallèles appelés avec cette politique (généralement spécifiée comme std::execution::seq) sont indéterminément séquencées dans le thread appelant.

  2. Le type de politique d'exécution utilisé comme type unique pour lever l'ambiguïté de la surcharge des algorithmes parallèles et indiquer que l'exécution d'un algorithme parallèle peut être parallélisée. Les invocations des fonctions d'accès aux éléments dans les algorithmes parallèles appelés avec cette politique (généralement spécifiée comme std::execution::par) peuvent être exécutées soit dans le thread appelant, soit dans un thread créé implicitement par la bibliothèque pour prendre en charge l'exécution de l'algorithme parallèle. Les invocations s'exécutant dans le même thread sont indéterminément séquencées les unes par rapport aux autres. Si les threads d'exécution créés par std::thread ou std::jthread garantissent une progression concurrente, alors les threads d'exécution créés par la bibliothèque garantissent une progression parallèle. Sinon, la garantie de progression fournie est définie par l'implémentation. Note : la progression parallèle garantit que si un thread d'exécution effectue un pas, il finira par en effectuer un autre, ce qui permet aux threads d'entrer dans des sections critiques et de prendre des verrous, car le thread qui détient le verrou sera à nouveau ordonnancé et pourra le libérer.

  3. Le type de politique d'exécution utilisé comme type unique pour lever l'ambiguïté de la surcharge des algorithmes parallèles et indiquer que l'exécution d'un algorithme parallèle peut être parallélisée, vectorisée ou migrée entre threads (par exemple par un ordonnanceur à vol de continuation). Les invocations des fonctions d'accès aux éléments dans les algorithmes parallèles appelés avec cette politique peuvent être exécutées de manière non ordonnée, dans des threads non spécifiés, et non séquencées les unes par rapport aux autres au sein de chaque thread. L'invocation de fonctions d'accès aux éléments dans les algorithmes parallèles appelés avec cette politique ne doit pas invoquer d'opérations non sûres pour la vectorisation, comme celles spécifiées par la bibliothèque standard pour la synchronisation, y compris celles de std::atomic et d'autres primitives de concurrence. Si les threads d'exécution créés par std::thread ou std::jthread garantissent une progression concurrente, alors les threads d'exécution créés par la bibliothèque garantissent une progression faiblement parallèle. Sinon, la garantie de progression fournie est celle du thread invoquant l'algorithme parallèle. Note : la progression faiblement parallèle garantit qu'un des threads d'exécution ayant effectué un pas en effectuera un autre, ce qui ne permet pas aux threads d'entrer dans des sections critiques ni de prendre des verrous, car le thread qui détient le verrou peut ne pas être ordonnancé à nouveau avant qu'un thread tentant de prendre le verrou ait quitté.

  4. Le type de politique d'exécution utilisé comme type unique pour lever l'ambiguïté de la surcharge des algorithmes parallèles et indiquer que l'exécution d'un algorithme parallèle peut être vectorisée, par exemple exécutée sur un seul thread à l'aide d'instructions opérant sur plusieurs données à la fois.

Pendant l'exécution d'un algorithme parallèle avec l'une de ces politiques d'exécution, si l'invocation d'une fonction d'accès aux éléments se termine par une exception non interceptée, std::terminate est appelée, mais les implémentations peuvent définir des politiques d'exécution supplémentaires qui traitent les exceptions différemment.

Notes

Lors de l'utilisation d'une politique d'exécution parallèle, il incombe au programmeur d'éviter les courses de données et les interblocages :

int a[] = {0, 1};
std::vector<int> v;
std::for_each(std::execution::par, std::begin(a), std::end(a), [&](int i)
{
    v.push_back(i * 2 + 1); // Erreur : course de données
});

std::atomic<int> x {0};
int a[] = {1, 2};
std::for_each(std::execution::par, std::begin(a), std::end(a), [&](int)
{
    x.fetch_add(1, std::memory_order_relaxed);
    while (x.load(std::memory_order_relaxed) == 1) { } // Erreur : suppose un ordre d'exécution
});

int x = 0;
std::mutex m;
int a[] = {1, 2};
std::for_each(std::execution::par, std::begin(a), std::end(a), [&](int)
{
    std::lock_guard<std::mutex> guard(m);
    ++x; // correct
});

Les politiques d'exécution non séquencées sont le seul cas où des appels de fonction sont non séquencés les uns par rapport aux autres, ce qui signifie qu'ils peuvent être entrelacés. Dans toutes les autres situations en C++, ils sont indéterminément séquencés (ne peuvent pas être entrelacés). Pour cette raison, il est interdit aux utilisateurs d'allouer ou de désallouer de la mémoire, d'acquérir des mutex, d'utiliser des spécialisations de std::atomic non sans verrou, ou, plus généralement, d'effectuer des opérations non sûres pour la vectorisation lorsqu'ils utilisent ces politiques (les fonctions non sûres pour la vectorisation sont celles qui se synchronisent avec une autre fonction, par exemple std::mutex::unlock se synchronise avec le std::mutex::lock suivant).

int x = 0;
std::mutex m;
int a[] = {1, 2};
std::for_each(std::execution::par_unseq, std::begin(a), std::end(a), [&](int)
{
    std::lock_guard<std::mutex> guard(m); // Erreur : le constructeur de lock_guard appelle m.lock()
    ++x;
});

Si l'implémentation ne peut pas paralléliser ou vectoriser (par exemple faute de ressources), toutes les politiques d'exécution standard peuvent se replier sur une exécution séquentielle.
