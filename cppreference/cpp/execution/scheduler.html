template< class Sch >
concept scheduler =
    std::derived_from<
        typename std::remove_cvref_t<Sch>::scheduler_concept,
        scheduler_t> &&
    /*queryable*/<Sch> &&
    requires(Sch&& sch)
    {
        {
            std::execution::schedule(std::forward<Sch>(sch))
        } -> std::execution::sender;
        {
            auto(
                std::execution::get_completion_scheduler<
                    std::execution::set_value_t>(
                        std::execution::get_env(
                            std::execution::schedule(
                                std::forward<Sch>(sch)))))
        } -> std::same_as<std::remove_cvref_t<Sch>>;
    } &&
    std::equality_comparable<std::remove_cvref_t<Sch>> &&
    std::copy_constructible<std::remove_cvref_t<Sch>>;
};  // (1) (depuis C++26)

Type d'étiquette auxiliaire

struct scheduler_t {};  // (2) (depuis C++26)

Le concept scheduler est modélisé par les types qui sont des ordonnanceurs, c'est-à-dire des gestionnaires légers de ressources d'exécution, comme des pools de threads, qui fonctionnent avec la bibliothèque d'exécution C++.

Exigences sémantiques

Étant donné un ordonnanceur de type Sch et un environnement d'exécution de type Env tel que sender_in<schedule_result_t<Sch>, Env> soit satisfait, alors /*sender-in-of*/<schedule_result_t<Sch>, Env> est modélisé.

Le constructeur de copie, le destructeur, la comparaison d'égalité et les fonctions membres d'échange de l'ordonnanceur doivent être non lançants.

Toutes ces fonctions membres ainsi que la fonction schedule du type d'ordonnanceur doivent être thread-safe.

Deux ordonnanceurs ne sont égaux que s'ils représentent la même ressource d'exécution.

Pour un ordonnanceur donné sch, l'expression get_completion_scheduler<set_value_t>(get_env(schedule(sch))) se compare égale à sch.

Pour un ordonnanceur donné sch, si l'expression get_domain(sch) est bien formée, alors l'expression get_domain(get_env(schedule(sch))) est également bien formée et a le même type.

Le destructeur d'un ordonnanceur ne doit pas bloquer l'achèvement en attente de tout récepteur connecté aux objets émetteurs retournés par schedule (la ressource sous-jacente peut fournir une API distincte pour attendre la fin des objets fonction soumis)

Exemples

simple enveloppe de std::execution::run_loop qui interroge en permanence la file de run_loop sur un thread dédié unique. Démonstration avec l'implémentation de référence du brouillon : <https://godbolt.org/z/146fY4Y91>

#include <execution>
#include <iostream>
#include <thread>

class single_thread_context
{
    std::execution::run_loop loop_{};
    std::jthread thread_;

public:
    single_thread_context()
        : thread_([this] { loop_.run(); })
    {}
    single_thread_context(single_thread_context&&) = delete;

    ~single_thread_context()
    {
        loop_.finish();
    }

    std::execution::scheduler auto get_scheduler() noexcept
    {
        return loop_.get_scheduler();
    }
};

int main()
{
    single_thread_context ctx;

    std::execution::sender auto snd =
        std::execution::schedule(ctx.get_scheduler())
        | std::execution::then([]
            {
                std::cout << "Hello world! Have an int.\n";
                return 015;
            })
        | std::execution::then([](int arg) { return arg + 42; });

    auto [i] = std::this_thread::sync_wait(snd).value();

    std::cout << "Back in the main thread, result is " << i << '\n';
}

Output:

Hello world! Have an int.
Back in the main thread, result is 55
