RAII

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Resource Acquisition Is Initialization ou RAII, est une technique de programmation C++[1][2] qui lie la durée de vie d'une ressource devant être acquise avant utilisation (mémoire allouée sur le tas, thread d'exécution, socket ouverte, fichier ouvert, mutex verrouillé, espace disque, connexion à une base de données — tout ce qui existe en quantité limitée) à la durée de vie d'un objet.

Le RAII garantit que la ressource est disponible pour toute fonction pouvant accéder à l'objet (la disponibilité de la ressource est un invariant de classe, ce qui élimine les tests redondants à l'exécution). Il garantit également que toutes les ressources sont libérées à la fin de la durée de vie de leur objet de contrôle, dans l'ordre inverse de leur acquisition. De même, si l'acquisition d'une ressource échoue (le constructeur se termine par une exception), toutes les ressources acquises par chaque sous-objet membre ou de base entièrement construit sont libérées dans l'ordre inverse de l'initialisation. Cela s'appuie sur les fonctionnalités de base du langage (durée de vie des objets, sortie de portée, ordre d'initialisation et déroulement de la pile) pour éliminer les fuites de ressources et garantir la sécurité en cas d'exception. Une autre appellation de cette technique est Scope-Bound Resource Management (SBRM), d'après le cas d'usage de base où la durée de vie d'un objet RAII se termine à la sortie de portée.

Le RAII peut se résumer comme suit :

  • encapsuler chaque ressource dans une classe, où

    • le constructeur acquiert la ressource et établit tous les invariants de classe, ou lève une exception si cela est impossible,
    • le destructeur libère la ressource et ne lève jamais d'exception ;

  • toujours utiliser la ressource via une instance d'une classe RAII qui

    • a une durée de stockage automatique ou une durée de vie temporaire elle-même, ou
    • a une durée de vie bornée par la durée de vie d'un objet automatique ou temporaire.

La sémantique de déplacement permet le transfert de ressources et de propriété entre objets, à l'intérieur et à l'extérieur des conteneurs, et entre threads, tout en garantissant la sûreté des ressources.

(depuis C++11)

Les classes dotées de fonctions membres open()/close(), lock()/unlock() ou init()/copyFrom()/destroy() sont des exemples typiques de classes non RAII :

std::mutex m;

void bad()
{
    m.lock();             // acquérir le mutex
    f();                  // si f() lève une exception, le mutex n'est jamais libéré
    if (!everything_ok())
        return;           // retour anticipé, le mutex n'est jamais libéré
    m.unlock();           // si bad() atteint cette instruction, le mutex est libéré
}

void good()
{
    std::lock_guard<std::mutex> lk(m); // Classe RAII : l'acquisition du mutex est l'initialisation
    f();                               // si f() lève une exception, le mutex est libéré
    if (!everything_ok())
        return;                        // retour anticipé, le mutex est libéré
}                                      // si good() retourne normalement, le mutex est libéré

La bibliothèque standard

Les classes de la bibliothèque C++ qui gèrent leurs propres ressources suivent le RAII : std::string, std::vector, std::jthread (depuis C++20), et bien d'autres acquièrent leurs ressources dans les constructeurs (qui lèvent des exceptions en cas d'erreur), les libèrent dans leurs destructeurs (qui ne lèvent jamais d'exception), et ne nécessitent aucun nettoyage explicite.

En outre, la bibliothèque standard propose plusieurs enveloppes RAII pour gérer les ressources fournies par l'utilisateur :

  • std::unique_ptr et std::shared_ptr à std::make_unique et std::make_shared pour gérer la mémoire allouée dynamiquement ;
  • std::lock_guard, std::unique_lock, std::shared_lock pour gérer les mutex.

(depuis C++11)

Notes

Le RAII ne s'applique pas à la gestion des ressources qui ne sont pas acquises avant utilisation : temps CPU, disponibilité des cœurs, capacité du cache, capacité du pool d'entropie, bande passante réseau, consommation électrique, mémoire de pile. Pour de telles ressources, le constructeur d'une classe C++ ne peut pas garantir la disponibilité de la ressource pendant la durée de vie de l'objet, et d'autres moyens de gestion des ressources doivent être utilisés.
