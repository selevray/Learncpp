Élision de copie

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Lorsque certains critères sont remplis, la création d'un objet de classe à partir d'un objet source de même type (sans tenir compte de la qualification cv) peut être omise, même si le constructeur sélectionné et/ou le destructeur de l'objet ont des effets de bord. Cette élision de création d'objet est appelée élision de copie ﻿.

Explication

L'élision de copie est permise dans les circonstances suivantes (qui peuvent être combinées pour éliminer plusieurs copies) :

  • Dans une instruction return d'une fonction à type de retour de classe, lorsque l'opérande est le nom d'un objet obj non volatile à durée de stockage automatique (autre qu'un paramètre de fonction ou un paramètre de gestionnaire), l'initialisation par copie de l'objet résultat peut être omise en construisant obj directement dans l'objet résultat de l'appel de fonction. Cette variante d'élision de copie est connue sous le nom d'optimisation de la valeur de retour nommée (NRVO).
  • Lorsqu'un objet de classe target est initialisé par copie avec un objet temporaire obj qui n'a pas été lié à une référence, l'initialisation par copie peut être omise en construisant obj directement dans target. Cette variante d'élision de copie est connue sous le nom d'optimisation de la valeur de retour non nommée (URVO). Depuis C++17, URVO est obligatoire et n'est plus considérée comme une forme d'élision de copie ; voir ci-dessous.

(jusqu'à C++17)

  • Dans une expression throw, lorsque l'opérande est le nom d'un objet obj non volatile à durée de stockage automatique (autre qu'un paramètre de fonction ou un paramètre de gestionnaire) appartenant à une portée qui ne contient pas le bloc try englobant le plus interne (s'il existe), l'initialisation par copie de l'objet d'exception peut être omise en construisant obj directement dans l'objet d'exception.
  • Dans un gestionnaire, l'initialisation par copie de l'argument du gestionnaire peut être omise en traitant le paramètre du gestionnaire comme un alias de l'objet d'exception si la signification du programme reste inchangée, à l'exception de l'exécution des constructeurs et destructeurs de l'argument du gestionnaire.

(depuis C++11)

  • Dans les coroutines, une copie d'un paramètre de coroutine peut être omise. Dans ce cas, les références à cette copie sont remplacées par des références au paramètre correspondant si la signification du programme reste inchangée, à l'exception de l'exécution d'un constructeur et d'un destructeur de l'objet copie du paramètre.

(depuis C++20)

Lorsqu'une élision de copie se produit, l'implémentation traite la source et la cible de l'initialisation omise comme simplement deux manières différentes de désigner le même objet.

La destruction a lieu au plus tard des deux instants où les deux objets auraient été détruits sans l'optimisation.

(jusqu'à C++11)

Si le premier paramètre du constructeur sélectionné est une référence rvalue vers le type de l'objet, la destruction de cet objet a lieu au moment où la cible aurait été détruite. Sinon, la destruction a lieu au plus tard des deux instants où les deux objets auraient été détruits sans l'optimisation.

(depuis C++11)

Sémantique des prvalues (« élision de copie garantie »)

Depuis C++17, une prvalue n'est matérialisée que lorsque c'est nécessaire, puis elle est construite directement dans le stockage de sa destination finale. Cela signifie parfois que, même lorsque la syntaxe du langage suggère visuellement une copie/un déplacement (par exemple initialisation par copie), aucune copie ni aucun déplacement n'est effectué, ce qui implique que le type n'a pas besoin de disposer d'un constructeur de copie/déplacement accessible. Parmi les exemples figurent :

  • Initialisation de l'objet renvoyé dans une instruction return, lorsque l'opérande est une prvalue du même type de classe (sans tenir compte de la qualification cv) que le type de retour de la fonction :
T f()
{
    return U(); // construit un temporaire de type U,
                // puis initialise le T renvoyé à partir du temporaire
}
T g()
{
    return T(); // construit directement le T renvoyé ; pas de déplacement
}

Le destructeur du type renvoyé doit être accessible au point de l'instruction return et ne pas être supprimé, bien qu'aucun objet T ne soit détruit.

  • Lors de l'initialisation d'un objet, lorsque l'expression d'initialisation est une prvalue du même type de classe (sans tenir compte de la qualification cv) que le type de la variable :
T x = T(T(f())); // x est initialisé directement par le résultat de f() ; pas de déplacement

Ceci ne peut s'appliquer que lorsque l'objet initialisé est connu pour ne pas être un sous-objet potentiellement qui se chevauche :

struct C { /* ... */ };
C f();

struct D;
D g();

struct D : C
{
    D() : C(f()) {}    // pas d'élision lors de l'initialisation d'un sous-objet de classe de base
    D(int) : D(g()) {} // pas d'élision car l'objet D en cours d'initialisation pourrait
                       // être un sous-objet de classe de base d'une autre classe
};

Remarque : cette règle ne spécifie pas une optimisation, et la norme ne la décrit pas formellement comme une « élision de copie » (car rien n'est élidé). En revanche, la spécification du langage C++17 concernant les prvalues et les temporaires diffère fondamentalement de celle des révisions antérieures de C++ : il n'existe plus de temporaire à partir duquel copier ou déplacer. Une autre façon de décrire le fonctionnement de C++17 est le « passage de valeur non matérialisée » ou « matérialisation différée des temporaires » : les prvalues sont renvoyées et utilisées sans jamais matérialiser de temporaire.

(depuis C++17)

Notes

L'élision de copie est [la seule forme d'optimisation autorisée (jusqu'à C++14) | l'une des deux formes d'optimisation autorisées, avec l'élision et l'extension d'allocation, (depuis C++14)] pouvant modifier les effets de bord observables. Comme certains compilateurs n'effectuent pas l'élision de copie dans toutes les situations où elle est autorisée (par exemple en mode débogage), les programmes qui reposent sur les effets de bord des constructeurs de copie/déplacement et des destructeurs ne sont pas portables.

Dans une return instruction ou une expression throw, si le compilateur ne peut pas effectuer l'élision de copie alors que les conditions en sont remplies, ou le seraient si la source n'était pas un paramètre de fonction, [le compilateur tentera d'utiliser le constructeur de déplacement même si l'opérande source est désigné par une lvalue (jusqu'à C++23) | l'opérande source sera traité comme une rvalue (depuis C++23)] ; voir l'instruction return pour plus de détails.

Dans une expression constante et une initialisation constante, l'élision de copie n'est jamais effectuée.

struct A
{
    void* p;
    constexpr A() : p(this) {}
    A(const A&); // Désactiver la copiabilité triviale
};

constexpr A a;  // OK : a.p pointe vers a

constexpr A f()
{
    A x;
    return x;
}
constexpr A b = f(); // erreur : b.p serait pendant et pointerait vers le x à l'intérieur de f

constexpr A c = A(); // (jusqu'à C++17) erreur : c.p serait pendant et pointerait vers un temporaire
                     // (depuis C++17) OK : c.p pointe vers c ; aucun temporaire n'est impliqué

(depuis C++11)

Exemple

#include <iostream>

struct Noisy
{
    Noisy() { std::cout << "constructed at " << this << '\n'; }
    Noisy(const Noisy&) { std::cout << "copy-constructed\n"; }
    Noisy(Noisy&&) { std::cout << "move-constructed\n"; }
    ~Noisy() { std::cout << "destructed at " << this << '\n'; }
};

Noisy f()
{
    Noisy v = Noisy(); // (jusqu'à C++17) élision de copie initialisant v à partir d'un temporaire ;
                       //               le constructeur de déplacement peut être appelé
                       // (depuis C++17) « élision de copie garantie »
    return v; // élision de copie (« NRVO ») de v vers l'objet résultat ;
              // le constructeur de déplacement peut être appelé
}

void g(Noisy arg)
{
    std::cout << "&arg = " << &arg << '\n';
}

int main()
{
    Noisy v = f(); // (jusqu'à C++17) élision de copie initialisant v à partir du résultat de f()
                   // (depuis C++17) « élision de copie garantie »

    std::cout << "&v = " << &v << '\n';

    g(f()); // (jusqu'à C++17) élision de copie initialisant arg à partir du résultat de f()
            // (depuis C++17) « élision de copie garantie »
}

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.
