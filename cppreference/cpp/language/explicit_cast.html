Convertit explicitement un nombre quelconque de valeurs en une valeur du type cible.

  1. Conversion de type explicite (notation de cast), aussi appelée cast de style C.

2-7) Conversion de type explicite (notation fonctionnelle), aussi appelée cast de style fonctionnel.

  • type-id — un type-id
  • unary-expression — une expression unaire (dont l'opérateur de plus haut niveau n'a pas une priorité supérieure à celle du cast de style C)
  • simple-type-specifier — un spécificateur de type simple
  • expression-list — une liste d'expressions séparées par des virgules (sauf les expressions virgule non parenthésées)
  • initializer-list — une liste de clauses d'initialisation séparées par des virgules
  • designated-initializer-list — une liste de clauses d'initialisation désignées séparées par des virgules
  • identifier — un identifiant (éventuellement qualifié) (y compris des identifiants de modèle)

Explication

  1. Lorsque le cast de style C est rencontré, le compilateur tente de l'interpréter comme les expressions de cast suivantes, dans cet ordre :

a) const_cast<type-id ﻿>(unary-expression ﻿);

b) static_cast<type-id ﻿>(unary-expression ﻿), avec extensions : un pointeur ou une référence vers une classe dérivée peut en outre être converti en pointeur ou référence vers une classe de base non ambiguë (et inversement), même si la classe de base est inaccessible (c'est-à-dire que ce cast ignore le spécificateur d'héritage privé). Il en va de même pour la conversion d'un pointeur vers membre en pointeur vers membre d'une base non virtuelle non ambiguë ;

c) un static_cast (avec extensions) suivi de const_cast ;

d) reinterpret_cast<type-id ﻿>(unary-expression ﻿);

e) un reinterpret_cast suivi de const_cast.

Le premier choix satisfaisant les exigences de l'opérateur de cast correspondant est retenu, même s'il est mal formé (voir l'exemple). Si un static_cast suivi d'un const_cast est utilisé et que la conversion peut être interprétée de plus d'une façon, la conversion est mal formée.

En outre, les casts de style C peuvent convertir depuis, vers et entre pointeurs vers des types classe incomplets. Si type-id et le type de unary-expression sont tous deux des pointeurs vers des types classe incomplets, il n'est pas spécifié lequel de static_cast ou reinterpret_cast est retenu.

2-7) Un cast de style fonctionnel spécifie un type (simple-type-specifier ﻿ou identifier ﻿ (depuis C++11)) et un initialiseur (les parties restantes) ; il construit une valeur du type cible T, déterminé à partir du type spécifiéet de l'initialiseur (depuis C++17) :

T est le type spécifié.

(jusqu'à C++17)

T est déterminé comme suit :

  • Si le type spécifié est un espace réservé pour un type classe déduit, T est le type de retour de la fonction sélectionnée par résolution de surcharge pour la déduction d'argument de modèle de classe.
  • Sinon, si le type spécifié contient un type réservé, T est le type déduit.

(depuis C++23)

  • Sinon, T est le type spécifié.

(depuis C++17)

Le résultat de la conversion est déterminé comme suit :

  • Si le cast de style fonctionnel est de la syntaxe (2), et qu'il y a exactement une expression entre parenthèses, ce cast est équivalent au cast de style C correspondant.
  • Sinon, si T est (éventuellement qualifié cv) void, le résultat est [une rvalue (jusqu'à C++11) | une prvalue (depuis C++11)] de type void qui n'effectue aucune initialisation.
  • Si l'initialiseur n'est pas (), le programme est mal formé.

(jusqu'à C++11)

  • Si l'initialiseur n'est pas () ou {} après l'expansion de paquet (le cas échéant), le programme est mal formé.

(depuis C++11)

  • Sinon, si T est un type référence, le cast de style fonctionnel a le même effet que l'initialisation directe d'une variable fictive t de type T à partir de l'initialiseur spécifié, et le résultat est la t initialisée.
  • Le résultat est une lvalue.

(jusqu'à C++11)

  • Si T est un type référence lvalue ou une référence rvalue vers un type fonction, le résultat est une lvalue.
  • Sinon, le résultat est une xvalue.

(depuis C++11)

  • Sinon, le résultat est [une rvalue (jusqu'à C++11) | une prvalue (depuis C++11)] de type T [désignant un temporaire (jusqu'à C++17) | dont l'objet résultat est (depuis C++17)] initialisé directement avec l'initialiseur spécifié.

Résolution d'ambiguïté

Instruction de déclaration ambiguë

En cas d'ambiguïté entre une instruction d'expression dont la sous-expression la plus à gauche est un cast de style fonctionnel et une instruction de déclaration, l'ambiguïté est résolue en la traitant comme une déclaration. Cette désambiguïsation est purement syntaxique : elle ne tient pas compte de la signification des noms apparaissant dans l'instruction, sauf pour savoir s'il s'agit de noms de types :

struct M {};
struct L { L(M&); };

M n;
void f()
{
    M(m);    // déclaration, équivalente à M m;
    L(n);    // déclaration mal formée, équivalente à L n;
    L(l)(m); // toujours une déclaration, équivalente à L l((m));
}

Cependant, si le déclarateur le plus externe de l'instruction de déclaration ambiguë a un type de retour final, l'instruction n'est traitée comme une instruction de déclaration que si le type de retour final commence par auto :

struct M;

struct S
{
    S* operator()();
    int N;
    int M;

    void mem(S s)
    {
        auto(s)()->M; // expression (S::M masque ::M), invalide avant C++23
    }
};

void f(S s)
{
    {
        auto(s)()->N; // expression, invalide avant C++23
        auto(s)()->M; // déclaration de fonction, équivalente à M s();
    }
    {
        S(s)()->N;    // expression
        S(s)()->M;    // expression
    }
}

(depuis C++11)

Paramètre de fonction ambigu

L'ambiguïté ci-dessus peut aussi se produire dans le contexte d'une déclaration. Dans ce cas, le choix se situe entre une déclaration d'objet avec un cast de style fonctionnel comme initialiseur et une déclaration impliquant un déclarateur de fonction avec un jeu de parenthèses superflu autour d'un nom de paramètre. La résolution consiste également à considérer comme déclaration toute construction, telle que la déclaration de paramètre potentielle, qui pourrait être une déclaration :

struct S
{
    S(int);
};

void foo(double a)
{
    S w(int(a)); // déclaration de fonction : a un paramètre `a` de type int
    S x(int());  // déclaration de fonction : a un paramètre sans nom de type int(*)()
                 // qui est ajusté depuis int()

    // Moyens d'éviter l'ambiguïté :
    S y((int(a))); // déclaration d'objet : paire de parenthèses supplémentaire
    S y((int)a);   // déclaration d'objet : transtypage de style C
    S z = int(a);  // déclaration d'objet : aucune ambiguïté pour cette syntaxe
}

Cependant, si le déclarateur le plus externe de la déclaration de paramètre ambiguë a un type de retour final, l'ambiguïté n'est résolue en déclaration que s'il commence par auto :

typedef struct BB { int C[2]; } *B, C;

void foo()
{
    S a(B()->C);    // déclaration d'objet : B()->C ne peut pas déclarer un paramètre
    S b(auto()->C); // déclaration de fonction : a un paramètre sans nom de type C(*)()
                    // qui est ajusté depuis C()
}

(depuis C++11)

Ambiguïté de type-id

Une ambiguïté peut survenir de la similitude entre un transtypage de style fonctionnel et un type-id. La résolution est que toute construction qui pourrait être un type-id dans son contexte syntaxique doit être considérée comme un type-id :

// `int()` et `int(unsigned(a))` peuvent tous deux être analysés comme type-id :
// `int()`            représente une fonction retournant int
//                    et ne prenant aucun argument
// `int(unsigned(a))` représente une fonction retournant int
//                    et prenant un argument de type unsigned
void foo(signed char a)
{
    sizeof(int());            // type-id (mal formé)
    sizeof(int(a));           // expression
    sizeof(int(unsigned(a))); // type-id (mal formé)

    (int()) + 1;            // type-id (mal formé)
    (int(a)) + 1;           // expression
    (int(unsigned(a))) + 1; // type-id (mal formé)
}

Cependant, si le abstract-declarator le plus externe du type-id ambigu possède un type de retour final, l'ambiguïté ne sera résolue en le traitant comme un type-id que s'il commence par auto :

typedef struct BB { int C[2]; } *B, C;

void foo()
{
    sizeof(B()->C[1]);    // OK, sizeof(expression)
    sizeof(auto()->C[1]); // error: sizeof d'une fonction retournant un tableau
}

(depuis C++11)

Exemple

#include <cassert>
#include <iostream>

double f = 3.14;
unsigned int n1 = (unsigned int)f; // transtypage de style C
unsigned int n2 = unsigned(f);     // transtypage de style fonctionnel

class C1;
class C2;
C2* foo(C1* p)
{
    return (C2*)p; // transtype un type incomplet en type incomplet
}

void cpp23_decay_copy_demo()
{
    auto inc_print = [](int& x, const int& y)
    {
        ++x;
        std::cout << "x:" << x << ", y:" << y << '\n';
    };

    int p{1};
    inc_print(p, p); // affiche x:2 y:2, car le paramètre y ici est un alias de p
    int q{1};
    inc_print(q, auto{q}); // affiche x:2 y:1, auto{q} (C++23) se transtype en prvalue,
                           // donc le paramètre y est une copie de q (et non un alias de q)
}

// Dans cet exemple, le transtypage de style C est interprété comme static_cast
// alors qu'il fonctionnerait comme reinterpret_cast
struct A {};
struct I1 : A {};
struct I2 : A {};
struct D : I1, I2 {};

int main()
{
    D* d = nullptr;
//  A* a = (A*)d;                   // erreur à la compilation
    A* a = reinterpret_cast<A*>(d); // ceci compile
    assert(a == nullptr);

    cpp23_decay_copy_demo();
}

Output:

x:2 y:2
x:2 y:1
