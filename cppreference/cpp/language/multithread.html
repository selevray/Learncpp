Exécutions multi-threads et courses de données (depuis C++11)

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Un fil d'exécution est un flux de contrôle au sein d'un programme qui commence par l'invocation d'une fonction de niveau supérieur spécifique (par std::thread, std::async, std::jthread (depuis C++20) ou par d'autres moyens), et comprend récursivement chaque appel de fonction ensuite exécuté par ce fil.

  • Lorsqu'un fil en crée un autre, l'appel initial de la fonction de niveau supérieur du nouveau fil est exécuté par le nouveau fil, et non par le fil créateur.

Tout fil peut potentiellement accéder à tout objet et à toute fonction du programme :

  • Les objets à durée de stockage automatique et locale au thread peuvent néanmoins être accédés par un autre thread, par l'intermédiaire d'un pointeur ou par référence.
  • Dans une implémentation hébergée, un programme C++ peut avoir plusieurs threads s'exécutant simultanément. L'exécution de chaque thread se déroule comme défini par le reste de cette page. L'exécution de l'ensemble du programme consiste en l'exécution de tous ses threads.
  • Dans une implémentation autonome, il est défini par l'implémentation qu'un programme puisse avoir plus d'un fil d'exécution.

Pour un gestionnaire de signal qui n'est pas exécuté à la suite d'un appel à std::raise, il n'est pas spécifié dans quel fil d'exécution se trouve l'invocation du gestionnaire de signal.

Courses de données

Différents fils d'exécution sont toujours autorisés à accéder (lire et modifier) simultanément à des emplacements mémoire différents, sans interférence et sans exigence de synchronisation.

Deux évaluations d'expressions entrent en conflit si l'une d'elles modifie un emplacement mémoire ou débute ou termine la durée de vie d'un objet dans un emplacement mémoire, et que l'autre lit ou modifie le même emplacement mémoire ou débute ou termine la durée de vie d'un objet occupant un stockage qui chevauche cet emplacement mémoire.

Un programme qui comporte deux évaluations en conflit présente une course de données, sauf si

  • les deux évaluations s'exécutent sur le même fil ou dans le même gestionnaire de signal, ou
  • les deux évaluations en conflit sont des opérations atomiques (voir std::atomic), ou
  • l'une des évaluations en conflit arrive avant l'autre (voir std::memory_order).

Si une course de données se produit, le comportement du programme est indéfini.

(En particulier, la libération d'un std::mutex est synchronisée avec l'acquisition du même mutex par un autre fil, et arrive donc avant cette acquisition, ce qui permet d'utiliser des verrous mutex pour se protéger des courses de données.)

int cnt = 0;
auto f = [&] { cnt++; };
std::thread t1{f}, t2{f}, t3{f}; // comportement indéfini

std::atomic<int> cnt{0};
auto f = [&] { cnt++; };
std::thread t1{f}, t2{f}, t3{f}; // OK

Courses de données sur les conteneurs

Tous les conteneurs de la bibliothèque standard, à l'exception de std::vector<bool>, garantissent que des modifications concurrentes du contenu de l'objet contenu dans des éléments différents d'un même conteneur ne provoqueront jamais de courses de données.

std::vector<int> vec = {1, 2, 3, 4};
auto f = [&](int index) { vec[index] = 5; };
std::thread t1{f, 0}, t2{f, 1}; // OK
std::thread t3{f, 2}, t4{f, 2}; // comportement indéfini

std::vector<bool> vec = {false, false};
auto f = [&](int index) { vec[index] = true; };
std::thread t1{f, 0}, t2{f, 1}; // comportement indéfini

Ordre mémoire

Lorsqu'un fil lit une valeur depuis un emplacement mémoire, il peut voir la valeur initiale, la valeur écrite dans le même fil, ou la valeur écrite dans un autre fil. Voir std::memory_order pour les détails sur l'ordre dans lequel les écritures effectuées par les fils deviennent visibles pour les autres fils.

Progression

Liberté d'obstruction

Lorsqu'un seul fil non bloqué dans une fonction de la bibliothèque standard exécute une fonction atomique sans verrou, cette exécution est garantie de se terminer (toutes les opérations sans verrou de la bibliothèque standard sont sans obstruction).

Liberté de verrou

Lorsqu'une ou plusieurs fonctions atomiques sans verrou s'exécutent simultanément, au moins l'une d'elles est garantie de se terminer (toutes les opérations sans verrou de la bibliothèque standard sont sans verrou : il incombe à l'implémentation de s'assurer qu'elles ne peuvent pas être bloquées indéfiniment en livelock par d'autres fils, par exemple en volant continuellement la ligne de cache).

Garantie de progression

Dans un programme C++ valide, chaque fil finit par effectuer l'une des opérations suivantes :

  • Termine le programme.
  • Invoque std::this_thread::yield.
  • Effectue un appel à une fonction d'entrée/sortie de la bibliothèque.
  • Effectue un accès via un glvalue volatile.
  • Effectue une opération atomique ou une opération de synchronisation.
  • Poursuit l'exécution d'une boucle infinie triviale (voir ci-dessous).

On dit qu'un thread progresse s'il effectue l'une des étapes d'exécution ci-dessus, se bloque dans une fonction de la bibliothèque standard, ou appelle une fonction atomique sans verrou qui ne se termine pas à cause d'un thread concurrent non bloqué.

Cela permet aux compilateurs de supprimer, fusionner et réordonner toutes les boucles sans comportement observable, sans avoir à prouver qu'elles finissent par se terminer, car ils peuvent supposer qu'aucun thread d'exécution ne peut s'exécuter indéfiniment sans effectuer l'un de ces comportements observables. Une exception est faite pour les boucles infinies triviales, qui ne peuvent ni être supprimées ni réordonnées.

Boucles infinies triviales

Une instruction d'itération trivialement vide est une instruction d'itération correspondant à l'une des formes suivantes :

| | | | while ( condition ) ; | (1) | | | | while ( condition ) { } | (2) | | | | do ; while ( condition ) ; | (3) | | | | do { } while ( condition ) ; | (4) | | | | for ( init-statement condition ﻿*(facultatif)* ; ) ; | (5) | | | | for ( init-statement condition ﻿*(facultatif)* ; ) { } | (6) | | |

  1. Une instruction while dont le corps de boucle est une instruction simple vide.

  2. Une instruction while dont le corps de boucle est une instruction composée vide.

  3. Une instruction do-while dont le corps de boucle est une instruction simple vide.

  4. Une instruction do-while dont le corps de boucle est une instruction composée vide.

  5. Une instruction for dont le corps de boucle est une instruction simple vide, l'instruction for n'ayant pas de iteration-expression.

  6. Une instruction for dont le corps de boucle est une instruction composée vide, l'instruction for n'ayant pas de iteration-expression.

L'expression de contrôle d'une instruction d'itération trivialement vide est :

1-4) condition.

5,6) condition si elle est présente, sinon true.

Une boucle infinie triviale est une instruction d'itération trivialement vide dont l'expression de contrôle convertie est une expression constante, lorsqu'elle est évaluée de manière constante manifeste, et vaut true.

Le corps d'une boucle infinie triviale est remplacé par un appel à la fonction std::this_thread::yield. Il est défini par l'implémentation que ce remplacement ait lieu ou non sur les implémentations autonomes.

for (;;); // boucle infinie triviale, bien définie depuis P2809
for (;;) { int x; } // comportement indéfini

Progression concurrente

Si un thread offre la garantie de progression concurrente, il progressera (au sens défini ci-dessus) en un temps fini, tant qu'il ne s'est pas terminé, que les autres threads (s'il y en a) progressent ou non.

La norme encourage, sans l'exiger, à ce que le thread principal et les threads lancés par std::thread et std::jthread (depuis C++20) offrent la garantie de progression concurrente.

Progression parallèle

Si un thread offre la garantie de progression parallèle, l'implémentation n'est pas tenue de garantir que ce thread finira par progresser s'il n'a encore exécuté aucune étape d'exécution (E/S, volatile, atomique ou synchronisation), mais une fois qu'il a exécuté une étape, il fournit des garanties de progression concurrente (cette règle décrit un thread d'un pool de threads qui exécute des tâches dans un ordre arbitraire).

Progression faiblement parallèle

Si un thread offre la garantie de progression faiblement parallèle, il ne garantit pas de finir par progresser, que les autres threads progressent ou non.

Ces threads peuvent malgré tout être garantis de progresser grâce à une délégation de garantie de progression lors du blocage : si un thread P se bloque de cette manière sur la fin d'un ensemble de threads S, alors au moins un thread de S offrira une garantie de progression égale ou supérieure à P. Une fois ce thread terminé, un autre thread de S sera de même renforcé. Une fois l'ensemble vide, P sera débloqué.

Les algorithmes parallèles de la bibliothèque standard C++ se bloquent avec délégation de progression lors de la fin d'un ensemble non spécifié de threads gérés par la bibliothèque.

(depuis C++17)

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.
