Phases de traduction

Les fichiers source C++ sont traités par le compilateur pour produire des programmes C++.

Processus de traduction

Le texte d'un programme C++ est conservé dans des unités appelées fichiers source.

Les fichiers source C++ subissent une traduction pour devenir une unité de traduction, qui consiste en les étapes suivantes :

  1. Associe chaque fichier source à une séquence de caractères.
  2. Convertit chaque séquence de caractères en une séquence de jetons de prétraitement, séparés par des espaces.
  3. Convertit chaque jeton de prétraitement en un jeton, formant une séquence de jetons.
  4. Convertit chaque séquence de jetons en une unité de traduction.

Un programme C++ peut être formé à partir d'unités de traduction traduites. Les unités de traduction peuvent être traduites séparément puis liées ultérieurement pour produire un programme exécutable.

Le processus ci-dessus peut être organisé en 9 phases de traduction.

Jetons de prétraitement

Un jeton de prétraitement est le plus petit élément lexical du langage dans les phases de traduction 3 à 6.

Les catégories de jetons de prétraitement sont :

  • noms d'en-têtes (comme <iostream> ou "myfile.h")
  • jetons de substitution produits par les directives de prétraitement import et module (c.-à-d. import XXX; et module XXX;)

(depuis C++20)

  • identifiers
  • nombres de prétraitement (voir ci-dessous)
  • littéraux de caractère, y compris les littéraux de caractère définis par l'utilisateur (depuis C++11)
  • littéraux de chaîne, y compris les littéraux de chaîne définis par l'utilisateur (depuis C++11)
  • opérateurs et signes de ponctuation, y compris les jetons alternatifs
  • caractères individuels non blancs qui n'entrent dans aucune autre catégorie Le programme est mal formé si le caractère correspondant à cette catégorie est
    • l'apostrophe (', U+0027),
    • le guillemet double (", U+0022), ou
    • un caractère n'appartenant pas au jeu de caractères de base.

Nombres de prétraitement

L'ensemble des jetons de prétraitement d'un nombre de prétraitement est un sur-ensemble de l'union des ensembles de jetons des littéraux entiers et des littéraux à virgule flottante :

| | | | .(facultatif) digit pp-continue-seq ﻿*(facultatif)* | | | |

  • digit — un des chiffres 0-9
  • pp-continue-seq — une séquence de pp-continue ﻿s

Chaque pp-continue est l'un des éléments suivants :

| | | | identifier-continue | (1) | | | | exp-char sign-char | (2) | | | | . | (3) | | | | ’ digit | (4) | (depuis C++14) | | | ’ nondigit | (5) | (depuis C++14) | |

  • identifier-continue — tout caractère autre que le premier d'un identificateur valide
  • exp-char — l'un des P, p, (depuis C++11) E et e
  • sign-char — l'un de + et -
  • digit — un des chiffres 0-9
  • nondigit — l'une des lettres latines A/a-Z/z ou le tiret bas

Un nombre de prétraitement n'a ni type ni valeur ; il les acquiert tous deux après une conversion réussie en un jeton de littéral entier ou à virgule flottante.

Espaces blancs

Les espaces blancs sont constitués de commentaires, de caractères d'espacement, ou des deux.

Les caractères suivants sont des caractères d'espacement :

  • tabulation horizontale (U+0009)
  • caractère de saut de ligne (U+000A)
  • tabulation verticale (U+000B)
  • saut de page (U+000C)
  • espace (U+0020)

Les espaces blancs servent généralement à séparer les jetons de prétraitement, avec les exceptions suivantes :

  • Ils ne sont pas séparateurs dans un nom d'en-tête, un littéral de caractère et un littéral de chaîne.
  • Des jetons de prétraitement séparés par des espaces blancs contenant des caractères de saut de ligne ne peuvent pas former des directives de prétraitement.
#include "my header"        // OK, using a header name containing whitespace

#include/*hello*/<iostream> // OK, using a comment as whitespace

#include
<iostream> // Error: #include ne peut pas s'étendre sur plusieurs lignes

"str ing"  // OK, un seul jeton de prétraitement (littéral de chaîne)
' '        // OK, un seul jeton de prétraitement (littéral de caractère)

Consommation maximale

Si l'entrée a été analysée en jetons de prétraitement jusqu'à un caractère donné, le jeton de prétraitement suivant est en général la plus longue séquence de caractères pouvant constituer un jeton de prétraitement, même si cela devait faire échouer l'analyse ultérieure. Ceci est communément appelé consommation maximale.

int foo = 1;
int bar = 0xE+foo;   // Error: nombre de prétraitement invalide 0xE+foo
int baz = 0xE + foo; // OK

En d'autres termes, la règle de consommation maximale privilégie les opérateurs et signes de ponctuation à plusieurs caractères :

int foo = 1;
int bar = 2;

int num1 = foo+++++bar; // Error: traité comme « foo++ ++ +baz », et non « foo++ + ++baz »
int num2 = -----foo;    // Error: traité comme « -- -- -foo », et non « - -- --foo »

La règle de consommation maximale comporte les exceptions suivantes :

  • Les jetons de prétraitement de nom d'en-tête ne sont formés que dans les cas suivants :
    • après le jeton de prétraitement include dans une directive #include
  • dans une __has_include expression

(depuis C++17)

  • après le jeton de prétraitement import dans une directive import

(depuis C++20)

std::vector<int> x; // OK, « int » n'est pas un nom d'en-tête
  • Si les trois caractères suivants sont <:: et que le caractère suivant n'est ni : ni >, le < est traité comme un jeton de prétraitement à part entière au lieu du premier caractère du jeton alternatif <:.
struct Foo { static const int v = 1; };
std::vector<::Foo> x;  // OK, <: n'est pas pris comme jeton de remplacement pour [
extern int y<::>;      // OK, équivalent à « extern int y[]; »
int z<:::Foo::value:>; // OK, équivalent à « int z[::Foo::value]; »
  • Si les deux caractères suivants sont >> et que l'un des caractères > peut compléter un identificateur de modèle, le caractère est traité comme un jeton de prétraitement seul au lieu de faire partie du jeton de prétraitement >>.
template<int i> class X { /* ... */ };
template<class T> class Y { /* ... */ };

Y<X<1>> x3;      // OK, déclare une variable « x3 » de type « Y<X<1> > »
Y<X<6>>1>> x4;   // Erreur de syntaxe
Y<X<(6>>1)>> x5; // OK
  • Si le caractère suivant commence une séquence de caractères qui peut être le préfixe et le guillemet double initial d'un littéral de chaîne brut, le jeton de prétraitement suivant est un littéral de chaîne brut. Le littéral est constitué de la plus courte séquence de caractères correspondant au motif de chaîne brute.
#define R "x"
const char* s = R"y";         // littéral de chaîne brut mal formé, et non "x" "y"
const char* s2 = R"(a)" "b)"; // un littéral de chaîne brut suivi d'un littéral de chaîne normal

(depuis C++11)

Jetons

Un jeton est le plus petit élément lexical du langage dans la phase de traduction 7.

Les catégories de jetons sont :

  • identifiers
  • keywords
  • literals
  • opérateurs et signes de ponctuation (à l'exception des opérateurs de prétraitement)

Phases de traduction

La traduction est effectuée comme si dans l'ordre de la phase 1 à la phase 9. Les implémentations se comportent comme si ces phases distinctes avaient lieu, bien qu'en pratique différentes phases puissent être fusionnées.

Phase 1 : Mise en correspondance des caractères source

  1. Les octets individuels du fichier de code source sont mis en correspondance (de manière définie par l'implémentation) avec les caractères du jeu de caractères source de base. En particulier, les indicateurs fin de ligne dépendants du système d'exploitation sont remplacés par des caractères de saut de ligne.

  2. L'ensemble des caractères de fichier source acceptés est défini par l'implémentation (depuis C++11). Tout caractère de fichier source qui ne peut pas être mis en correspondance avec un caractère du jeu de caractères source de base est remplacé par son nom universel de caractère (échappé avec \u ou \U) ou par une forme définie par l'implémentation traitée de manière équivalente.

  1. Les séquences de trigraphes sont remplacées par les représentations à caractère unique correspondantes.

(jusqu'à C++17)

(jusqu'à C++23)

Les fichiers d'entrée qui sont une séquence d'unités de code UTF-8 (fichiers UTF-8) sont garantis d'être pris en charge. L'ensemble des autres types de fichiers d'entrée pris en charge est défini par l'implémentation. Si cet ensemble n'est pas vide, le type d'un fichier d'entrée est déterminé de manière définie par l'implémentation, incluant un moyen de désigner des fichiers d'entrée comme fichiers UTF-8, indépendamment de leur contenu (la reconnaissance de la marque d'ordre des octets ne suffit pas).

  • Si un fichier d'entrée est déterminé comme fichier UTF-8, il doit être une séquence d'unités de code UTF-8 bien formée et il est décodé pour produire une séquence de valeurs scalaires Unicode. Une séquence d'éléments du jeu de caractères de traduction est alors formée en associant chaque valeur scalaire Unicode à l'élément correspondant du jeu de caractères de traduction. Dans la séquence résultante, chaque paire de caractères de la séquence d'entrée constituée d'un retour chariot (U+000D) suivi d'un saut de ligne (U+000A), ainsi que chaque retour chariot (U+000D) non immédiatement suivi d'un saut de ligne (U+000A), est remplacé par un seul caractère de saut de ligne.
  • Pour tout autre type de fichier d'entrée pris en charge par l'implémentation, les caractères sont associés (de manière définie par l'implémentation) à une séquence d'éléments du jeu de caractères de traduction. En particulier, les indicateurs de fin de ligne dépendants du système d'exploitation sont remplacés par des caractères de saut de ligne.

(depuis C++23)

Phase 2 : Épissage des lignes

  1. Si le premier caractère de traduction est la marque d'ordre des octets (U+FEFF), il est supprimé. *(depuis C++23)*Chaque fois qu'une barre oblique inverse (\) apparaît en fin de ligne (immédiatement suivie de zéro ou plusieurs caractères d'espacement autres que le saut de ligne suivis de (depuis C++23) le caractère de saut de ligne), ces caractères sont supprimés, ce qui combine deux lignes physiques du code source en une seule ligne logique. Il s'agit d'une opération en une seule passe ; une ligne se terminant par deux barres obliques inverses suivies d'une ligne vide ne combine pas trois lignes en une.

  2. Si un fichier source non vide ne se termine pas par un caractère de saut de ligne après cette étape (les barres obliques inverses en fin de ligne ne sont plus des épissures à ce stade), un caractère de saut de ligne final est ajouté.

Phase 3 : analyse lexicale

  1. Le fichier source est décomposé en jetons de prétraitement et espaces :
// La directive #include suivante peut être décomposée en 5 jetons de prétraitement :

//     signes de ponctuation (#, < et >)
//          │
// ┌────────┼────────┐
// │        │        │
   #include <iostream>
//     │        │
//     │        └── nom d'en-tête (iostream)
//     │
//     └─────────── identifiant (include)

Si un fichier source se termine par un jeton de prétraitement partiel ou par un commentaire partiel, le programme est mal formé :

// Error: littéral de chaîne partiel
"abc

// Error: commentaire partiel
/* comment

Au fur et à mesure que les caractères du fichier source sont consommés pour former le jeton de prétraitement suivant (c'est-à-dire qu'ils ne sont pas consommés dans un commentaire ou une autre forme d'espacement), les noms universels de caractères sont reconnus et remplacés par l'élément désigné du jeu de caractères de traduction, sauf lorsqu'ils correspondent à une séquence de caractères dans l'un des jetons de prétraitement suivants :

  • un littéral de caractère (c-char-sequence)
  • un littéral de chaîne (s-char-sequence et r-char-sequence), à l'exclusion des délimiteurs (d-char-sequence)
  • un nom d'en-tête (h-char-sequence et q-char-sequence)

(depuis C++23)

  1. Toutes les transformations effectuées lors des phases 1 et (jusqu'à C++23) 2 entre le guillemet double initial et final de tout littéral de chaîne brut sont annulées.

(depuis C++11)

  1. L'espacement est transformé :
  • Chaque commentaire est remplacé par un seul caractère d'espacement.
  • Les caractères de saut de ligne sont conservés.
  • Le fait que chaque séquence non vide de caractères d'espacement autres que le saut de ligne soit conservée ou remplacée par un seul caractère d'espacement est non spécifié.

Phase 4 : prétraitement

  1. Le préprocesseur est exécuté.

  2. Chaque fichier introduit par la directive #include passe par les phases 1 à 4, de manière récursive.

  3. À la fin de cette phase, toutes les directives du préprocesseur sont supprimées du code source.

Phase 5 : détermination des encodages communs des littéraux de chaîne

  1. Tous les caractères des littéraux de caractère et des littéraux de chaîne sont convertis du jeu de caractères source vers l'encodage (qui peut être un encodage à caractères multi-octets tel que UTF-8, à condition que les 96 caractères du jeu de caractères de base aient une représentation sur un seul octet).

  2. Les séquences d'échappement et les noms universels de caractères dans les littéraux de caractère et les littéraux de chaîne non bruts sont développés et convertis vers l'encodage des littéraux.

Si le caractère désigné par un nom universel de caractère ne peut pas être encodé comme un seul point de code dans l'encodage des littéraux correspondant, le résultat est défini par l'implémentation, mais il est garanti de ne pas être un caractère nul (large).

(jusqu'à C++23)

Pour une séquence de deux littéraux de chaîne adjacents ou plus, un préfixe d'encodage commun est déterminé comme décrit ici. Chaque jeton de littéral de chaîne est alors considéré comme ayant ce préfixe d'encodage commun. (La conversion des caractères est déplacée à la phase 3)

(depuis C++23)

Phase 6 : concaténation des littéraux de chaîne

Les littéraux de chaîne adjacents sont concaténés.

Phase 7 : compilation

La compilation a lieu : chaque jeton de prétraitement est converti en jeton. Les jetons sont analysés syntaxiquement et sémantiquement, puis traduits en unité de traduction.

Phase 8 : instanciation des modèles

Chaque unité de traduction est examinée afin de produire une liste des instanciations de modèles requises, y compris celles demandées par les instanciations explicites. Les définitions des modèles sont localisées et les instanciations requises sont effectuées pour produire des unités d'instanciation.

Phase 9 : édition de liens

Les unités de traduction, les unités d'instanciation et les composants de la bibliothèque nécessaires pour satisfaire les références externes sont rassemblés en une image de programme qui contient les informations nécessaires à l'exécution dans son environnement d'exécution.

Notes

Les fichiers source, les unités de traduction et les unités de traduction traduites n'ont pas nécessairement à être stockés sous forme de fichiers, et il n'a pas non plus à y avoir de correspondance biunivoque entre ces entités et une représentation externe quelconque. La description est uniquement conceptuelle et ne spécifie aucune implémentation particulière.

La conversion effectuée à la phase 5 peut être contrôlée par des options de ligne de commande dans certaines implémentations : gcc et clang utilisent -finput-charset pour spécifier l'encodage du jeu de caractères source, -fexec-charset et -fwide-exec-charset pour spécifier respectivement les encodages des littéraux ordinaires et larges, tandis que Visual Studio 2015 Update 2 et versions ultérieures utilisent /source-charset et /execution-charset pour spécifier respectivement le jeu de caractères source et l'encodage des littéraux.

(jusqu'à C++23)

Certains compilateurs n'implémentent pas les unités d'instanciation (aussi appelées dépôts de modèles ou registres de modèles) et compilent simplement chaque instanciation de modèle à la phase 7, en stockant le code dans le fichier objet où elle est implicitement ou explicitement demandée, puis l'éditeur de liens fusionne ces instanciations compilées en une seule à la phase 9.

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
CWG 787 C++98 le comportement était indéfini si un fichier source non vide ne se terminait pas par un caractère de saut de ligne à la fin de la phase 2 ajouter un caractère de saut de ligne final dans ce cas
CWG 1104 C++98 le jeton de remplacement <: faisait que std::vector<::std::string> était traité comme std::vector[:std::string> ajout d'une règle lexicale supplémentaire pour traiter ce cas
CWG 1775 C++11 la formation d'un nom universel de caractère à l'intérieur d'un littéral de chaîne brut à la phase 2 entraînait un comportement indéfini rendue bien définie
CWG 2747 C++98 la phase 2 vérifiait la fin de fichier après épissure, ce qui est inutile vérification supprimée
P2621R3 C++98 les noms universels de caractères ne pouvaient pas être formés par épissure de lignes ou concaténation de jetons allowed
