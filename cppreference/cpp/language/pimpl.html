PImpl

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

« Pointer to implementation » ou « pImpl » est une technique de programmation C++ qui retire les détails d'implémentation d'une classe de sa représentation objet en les plaçant dans une classe séparée, accessible par un pointeur opaque :

// --------------------
// interface (widget.h)
struct widget
{
    // membres publics
private:
    struct impl; // déclaration anticipée de la classe d'implémentation
    // Un exemple d'implémentation : voir ci-dessous pour d'autres options de conception et compromis
    std::experimental::propagate_const< // enveloppe de pointeur à redirection const
        std::unique_ptr<                // pointeur opaque à propriété unique
            impl>> pImpl;               // vers la classe d'implémentation déclarée par anticipation
};

// ---------------------------
// implémentation (widget.cpp)
struct widget::impl
{
    // détails d'implémentation
};

Cette technique est utilisée pour construire des interfaces de bibliothèques C++ à ABI stable et pour réduire les dépendances à la compilation.

Explication

Comme les membres de données privés d'une classe participent à sa représentation objet, en affectant la taille et la disposition, et comme les fonctions membres privées d'une classe participent à la résolution de surcharge (qui a lieu avant la vérification de l'accès aux membres), tout changement de ces détails d'implémentation impose la recompilation de tous les utilisateurs de la classe.

pImpl supprime cette dépendance de compilation ; les modifications de l'implémentation n'entraînent pas de recompilation. Par conséquent, si une bibliothèque utilise pImpl dans son ABI, les versions plus récentes de la bibliothèque peuvent modifier l'implémentation tout en restant compatibles en ABI avec les versions antérieures.

Compromis

Les alternatives à l'idiome pImpl sont

  • implémentation en ligne : les membres privés et les membres publics sont membres de la même classe.
  • classe abstraite pure (fabrique OOP) : les utilisateurs obtiennent un pointeur unique vers une classe de base légère ou abstraite, les détails d'implémentation se trouvent dans la classe dérivée qui redéfinit ses fonctions membres virtuelles.

Pare-feu de compilation

Dans les cas simples, pImpl comme la méthode de fabrique suppriment la dépendance à la compilation entre l'implémentation et les utilisateurs de l'interface de la classe. La méthode de fabrique crée une dépendance cachée sur la vtable, si bien que réordonner, ajouter ou supprimer des fonctions membres virtuelles casse l'ABI. L'approche pImpl n'a pas de dépendances cachées ; cependant, si la classe d'implémentation est une spécialisation de modèle de classe, le bénéfice du pare-feu de compilation est perdu : les utilisateurs de l'interface doivent voir toute la définition du modèle pour instancier la spécialisation correcte. Une approche de conception courante dans ce cas consiste à refactoriser l'implémentation de manière à éviter la paramétrisation, ce qui est un autre cas d'usage des Core Guidelines du C++ :

  • T.61 Do not over-parametrize members et
  • T.84 Utiliser une implémentation de base non basée sur un modèle pour fournir une interface stable en ABI.

Par exemple, le modèle de classe suivant n'utilise pas le type T dans son membre privé ni dans le corps de push_back :

template<class T>
class ptr_vector
{
    std::vector<void*> vp;
public:
    void push_back(T* p)
    {
        vp.push_back(p);
    }
};

Par conséquent, les membres privés peuvent être transférés tels quels dans l'implémentation, et push_back peut déléguer à une implémentation qui n'utilise pas non plus T dans l'interface :

// ---------------------
// en-tête (ptr_vector.hpp)
#include <memory>

class ptr_vector_base
{
    struct impl; // ne dépend pas de T
    std::unique_ptr<impl> pImpl;
protected:
    void push_back_fwd(void*);
    void print() const;
    // ... voir la section d'implémentation pour les fonctions membres spéciales
public:
    ptr_vector_base();
    ~ptr_vector_base();
};

template<class T>
class ptr_vector : private ptr_vector_base
{
public:
    void push_back(T* p) { push_back_fwd(p); }
    void print() const { ptr_vector_base::print(); }
};

// -----------------------
// source (ptr_vector.cpp)
// #include "ptr_vector.hpp"
#include <iostream>
#include <vector>

struct ptr_vector_base::impl
{
    std::vector<void*> vp;

    void push_back(void* p)
    {
        vp.push_back(p);
    }

    void print() const
    {
        for (void const * const p: vp) std::cout << p << '\n';
    }
};

void ptr_vector_base::push_back_fwd(void* p) { pImpl->push_back(p); }
ptr_vector_base::ptr_vector_base() : pImpl{std::make_unique<impl>()} {}
ptr_vector_base::~ptr_vector_base() {}
void ptr_vector_base::print() const { pImpl->print(); }

// ---------------
// utilisateur (main.cpp)
// #include "ptr_vector.hpp"

int main()
{
    int x{}, y{}, z{};
    ptr_vector<int> v;
    v.push_back(&x);
    v.push_back(&y);
    v.push_back(&z);
    v.print();
}

Surcoût à l'exécution

  • Surcoût d'accès : avec pImpl, chaque appel à une fonction membre privée passe par un pointeur. Chaque accès à un membre public effectué par un membre privé passe par un autre pointeur. Ces deux indirections traversent les frontières des unités de traduction et ne peuvent donc être supprimées que par l'optimisation à l'édition de liens. Notons que la fabrique OO impose une indirection entre unités de traduction pour accéder aux données publiques comme aux détails d'implémentation, et offre encore moins d'opportunités à l'optimiseur d'édition de liens en raison de l'appel virtuel.
  • Surcoût en mémoire : pImpl ajoute un pointeur au composant public et, si un membre privé doit accéder à un membre public, un autre pointeur est soit ajouté au composant d'implémentation, soit passé en paramètre à chaque appel du membre privé qui en a besoin. Si des allocateurs personnalisés avec état sont supportés, l'instance de l'allocateur doit aussi être stockée.
  • Surcoût de gestion de la durée de vie : pImpl (comme la fabrique OO) place l'objet d'implémentation sur le tas, ce qui impose un surcoût d'exécution important à la construction et à la destruction. Ce surcoût peut être partiellement compensé par des allocateurs personnalisés, car la taille d'allocation pour pImpl (mais pas pour la fabrique OO) est connue à la compilation.

En revanche, les classes pImpl sont compatibles avec le déplacement ; refactoriser une grande classe en pImpl déplaçable peut améliorer les performances des algorithmes manipulant des conteneurs de tels objets, bien que le pImpl déplaçable ait une source supplémentaire de surcoût à l'exécution : toute fonction membre publique autorisée sur un objet déplacé et qui a besoin d'accéder à l'implémentation privée provoque une vérification de pointeur nul.

Surcoût de maintenance

L'utilisation de pImpl exige une unité de traduction dédiée (une bibliothèque en-tête seule ne peut pas utiliser pImpl), introduit une classe supplémentaire, un ensemble de fonctions de délégation et, si des allocateurs sont utilisés, expose le détail d'implémentation de l'utilisation d'allocateurs dans l'interface publique.

Comme les membres virtuels font partie du composant d'interface de pImpl, simuler (mocker) un pImpl implique de simuler le seul composant d'interface. Un pImpl testable est généralement conçu pour permettre une couverture de test complète à travers l'interface disponible.

Implémentation

Comme l'objet du type d'interface contrôle la durée de vie de l'objet du type d'implémentation, le pointeur vers l'implémentation est généralement std::unique_ptr.

Comme std::unique_ptr exige que le type pointé soit un type complet dans tout contexte où le deleter est instancié, les fonctions membres spéciales doivent être déclarées par l'utilisateur et définies hors ligne, dans le fichier d'implémentation, où la classe d'implémentation est complète.

Car lorsqu'une fonction membre const appelle une fonction via un pointeur membre non const, la surcharge non const de la fonction d'implémentation est appelée ; le pointeur doit donc être enveloppé dans std::experimental::propagate_const ou un équivalent.

Tous les membres de données privés et toutes les fonctions membres privées non virtuelles sont placés dans la classe d'implémentation. Tous les membres publics, protégés et virtuels restent dans la classe d'interface (voir GOTW #100 pour la discussion des alternatives).

Si l'un des membres privés doit accéder à un membre public ou protégé, une référence ou un pointeur vers l'interface peut être passé à la fonction privée en paramètre. Sinon, la référence arrière peut être conservée comme partie de la classe d'implémentation.

Si des allocateurs non par défaut doivent être supportés pour l'allocation de l'objet d'implémentation, n'importe quel schéma usuel de prise en compte de l'allocateur peut être utilisé, notamment un paramètre de modèle allocateur valant par défaut std::allocator et un argument de constructeur de type std::pmr::memory_resource*.

Exemple

Illustre un pImpl avec propagation de const, avec référence arrière passée en paramètre, sans prise en compte des allocateurs, et déplaçable sans vérifications à l'exécution :

// ----------------------
// interface (widget.hpp)
#include <experimental/propagate_const>
#include <iostream>
#include <memory>

class widget
{
    class impl;
    std::experimental::propagate_const<std::unique_ptr<impl>> pImpl;
public:
    void draw() const; // API publique qui sera transmise à l'implémentation
    void draw();
    bool shown() const { return true; } // API publique que l'implémentation doit appeler

    widget(); // même le constructeur par défaut doit être défini dans le fichier d'implémentation
              // Note : appeler draw() sur un objet construit par défaut est un comportement indéfini
    explicit widget(int);
    ~widget(); // défini dans le fichier d'implémentation, où impl est un type complet
    widget(widget&&); // défini dans le fichier d'implémentation
                      // Note : appeler draw() sur un objet déplacé depuis est un comportement indéfini
    widget(const widget&) = delete;
    widget& operator=(widget&&); // défini dans le fichier d'implémentation
    widget& operator=(const widget&) = delete;
};

// ---------------------------
// implémentation (widget.cpp)
// #include "widget.hpp"

class widget::impl
{
    int n; // données privées
public:
    void draw(const widget& w) const
    {
        if (w.shown()) // cet appel à la fonction membre publique nécessite la référence arrière
            std::cout << "drawing a const widget " << n << '\n';
    }

    void draw(const widget& w)
    {
        if (w.shown())
            std::cout << "drawing a non-const widget " << n << '\n';
    }

    impl(int n) : n(n) {}
};

void widget::draw() const { pImpl->draw(*this); }
void widget::draw() { pImpl->draw(*this); }
widget::widget() = default;
widget::widget(int n) : pImpl{std::make_unique<impl>(n)} {}
widget::widget(widget&&) = default;
widget::~widget() = default;
widget& widget::operator=(widget&&) = default;

// ---------------
// utilisateur (main.cpp)
// #include "widget.hpp"

int main()
{
    widget w(7);
    const widget w2(8);
    w.draw();
    w2.draw();
}

drawing a non-const widget 7

La principale différence est que la mémoire de l'implémentation est réservée dans un membre de données qui est un tableau C opaque (à l'intérieur de la définition de la classe PImpl), tandis que dans le fichier cpp cette mémoire est associée (via reinterpret_cast ou placement-new) à la structure d'implémentation. Cette approche a ses propres avantages et inconvénients ; en particulier, un avantage évident est l'absence d'allocation supplémentaire, à condition qu'une mémoire suffisante ait été réservée initialement lors de la conception de la classe PImpl. (En revanche, parmi les inconvénients figure une moindre aptitude au déplacement.)
