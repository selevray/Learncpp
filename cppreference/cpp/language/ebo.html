Optimisation de la base vide

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Permet que la taille d'un sous-objet de base vide soit nulle.

Explication

La taille de tout objet ou sous-objet membre doit être d'au moins 1, même si le type est un type classe vide (c'est-à-dire une classe ou struct sans membre de données non statique), (sauf avec [[no_unique_address]], voir ci-dessous) (depuis C++20) afin de garantir que les adresses d'objets distincts de même type soient toujours distinctes.

Cependant, les sous-objets de classe de base ne sont pas soumis à cette contrainte et peuvent être entièrement optimisés hors de la disposition de l'objet :

struct Base {}; // classe vide

struct Derived1 : Base
{
    int i;
};

int main()
{
    // la taille de tout objet de type classe vide vaut au moins 1
    static_assert(sizeof(Base) >= 1);

    // l'optimisation de la base vide s'applique
    static_assert(sizeof(Derived1) == sizeof(int));
}

L'optimisation de la base vide est interdite si l'une des classes de base vides est aussi le type ou la base du type du premier membre de données non statique, car les deux sous-objets de base de même type doivent avoir des adresses différentes au sein de la représentation de l'objet le plus dérivé.

Un exemple typique de cette situation est l'implémentation naïve de std::reverse_iterator (dérivé de la base vide std::iterator), qui contient l'itérateur sous-jacent (également dérivé de std::iterator) comme premier membre de données non statique.

struct Base {}; // classe vide

struct Derived1 : Base
{
    int i;
};

struct Derived2 : Base
{
    Base c; // Base, occupe 1 octet, suivi d'un remplissage pour i
    int i;
};

struct Derived3 : Base
{
    Derived1 c; // dérivé de Base, occupe sizeof(int) octets
    int i;
};

int main()
{
    // l'optimisation de la base vide ne s'applique pas,
    // base occupe 1 octet, le membre Base occupe 1 octet
    // suivi de 2 octets de remplissage pour satisfaire les exigences d'alignement de int
    static_assert(sizeof(Derived2) == 2*sizeof(int));

    // l'optimisation de la base vide ne s'applique pas,
    // la base occupe au moins 1 octet plus le remplissage
    // pour satisfaire l'exigence d'alignement du premier membre (dont
    // l'alignement est le même que celui de int)
    static_assert(sizeof(Derived3) == 3*sizeof(int));
}

En cas d'héritage multiple, les optimisations spécifiques dépendent du compilateur.

  • Avec MSVC, l'optimisation de la base nulle n'est appliquée qu'à la dernière classe de base nulle ; les autres classes de base nulles ne bénéficient pas de cette optimisation et un octet est alloué.
  • Avec GCC, quel que soit le nombre de classes de base vides, l'optimisation s'applique sans allouer d'espace, et l'adresse de la classe de base vide est identique à la première adresse de l'objet de la classe dérivée.

L'optimisation de la base vide est requise pour les StandardLayoutTypes afin de maintenir l'exigence selon laquelle le pointeur vers un objet à disposition standard, converti à l'aide de reinterpret_cast, pointe vers son membre initial ; c'est pourquoi les exigences d'un type à disposition standard incluent « has all non-static data members declared in the same class (either all in the derived or all in some base) » et « has no base classes of the same type as the first non-static data member ».

(depuis C++11)

Les sous-objets membres vides peuvent être optimisés hors de l'objet comme les bases vides s'ils utilisent l'attribut [[no_unique_address]]. Prendre l'adresse d'un tel membre donne une adresse qui peut être égale à celle d'un autre membre du même objet.

struct Empty {}; // classe vide

struct X
{
    int i;
    [[no_unique_address]] Empty e;
};

int main()
{
    // la taille de tout objet de type classe vide vaut au moins 1
    static_assert(sizeof(Empty) >= 1);

    // membre vide optimisé :
    static_assert(sizeof(X) == sizeof(int));
}

(depuis C++20)

Notes

L'optimisation de la base vide est couramment utilisée par les classes de la bibliothèque standard prenant en charge les allocateurs (std::vector, std::function, std::shared_ptr, etc.) pour éviter d'occuper un espace de stockage supplémentaire pour leur membre allocateur lorsque celui-ci est sans état. Ceci est obtenu en stockant l'un des membres de données requis (par exemple begin, end, ou le pointeur capacity pour le vector) dans un équivalent de boost::compressed_pair avec l'allocateur.
