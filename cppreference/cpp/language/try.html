bloc try

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Une exception levée dans un bloc try peut éventuellement être traitée par un gestionnaire associé.

Syntaxe

| | | | try compound-statement handler-seq | (1) | | | | try ctor-initializer ﻿*(facultatif)* compound-statement handler-seq | (2) | | |

  1. Un bloc try ordinaire.

  2. Un bloc try de fonction. compound-statement doit être la composante instruction composée du corps d'une fonction.

  • compound-statement — une instruction composée
  • handler-seq — une séquence non vide de gestionnaires
  • ctor-initializer — liste d'initialisation des membres (pour les constructeurs uniquement)

Bloc try ordinaire

Un bloc try ordinaire est une instruction.

Si une exception est levée depuis son compound-statement, l'exception sera comparée aux gestionnaires de son handler-seq :

void f()
{
    throw 1;     // NON gérée par le gestionnaire ci-dessous
    try
    {
        throw 2; // gérée par le gestionnaire associé
    }
    catch (...)
    {
        // gère l'exception 2
    }
    throw 3;     // NON gérée par le gestionnaire ci-dessus
}

Bloc try de fonction

Un bloc try de fonction est un genre particulier de corps de fonction.

Si une exception est levée depuis son compound-statement ou son ctor-initializer (s'il existe), l'exception sera comparée aux gestionnaires de son handler-seq ﻿ :

int f(bool cond)
{
    if (cond)
        throw 1;
    return 0;
}

struct X
{
    int mem;

    X() try : mem(f(true)) {}
    catch (...)
    {
        // gère l'exception 1
    }

    X(int) try
    {
        throw 2;
    }
    catch (...)
    {
        // gère l'exception 2
    }
};

Les exceptions levées dans les destructeurs d'objets à durée de stockage statique ou dans les constructeurs d'objets associés à des variables hors bloc à durée de stockage statique ne sont pas interceptées par un bloc try de la fonction main.

Les exceptions levées dans les destructeurs d'objets à durée de stockage de thread ou dans les constructeurs d'objets associés à des variables hors bloc à durée de stockage de thread ne sont pas interceptées par un bloc try de la fonction initiale du thread.

(depuis C++11)

Atteindre la fin du compound-statement d'un gestionnaire d'un bloc try de fonction équivaut à atteindre la fin du compound-statement de ce bloc try de fonction, sauf si la fonction est un constructeur ou un destructeur (voir ci-dessous).

Bloc try de constructeur et de destructeur

Pour une classe C, si le corps de la définition de son constructeur ou destructeur est un bloc try de fonction, et qu'une exception est levée pendant l'initialisation ou la destruction, respectivement, des sous-objets de C, l'exception sera également comparée aux gestionnaires du handler-seq ﻿ de la fonction try :

int f(bool cond = true)
{
    if (cond)
        throw 1;
    return 0;
}

struct X
{
    int mem = f();

    ~X()
    {
        throw 2;
    }
};

struct Y
{
    X mem;

    Y() try {}
    catch (...)
    {
        // gère l'exception 1
    }

    ~Y() try {}
    catch (...)
    {
        // gère l'exception 2
    }
};

Référencer un membre non statique ou une classe de base d'un objet dans le gestionnaire d'un bloc try de fonction d'un constructeur ou d'un destructeur de cet objet entraîne un comportement indéfini.

Si une instruction return apparaît dans un gestionnaire du bloc try de fonction d'un constructeur, le programme est mal formé.

L'exception actuellement gérée est relancée si le flux d'exécution atteint la fin d'un gestionnaire du bloc try de fonction d'un constructeur ou d'un destructeur.

Flux de contrôle

Le compound-statement d'un bloc try est une instruction à flux de contrôle limité :

void f()
{
    goto label;     // error
    try
    {
        goto label; // OK
        label: ;
    }
    catch (...)
    {
        goto label; // error
    }
}

Une instruction de saut (goto, break, return, continue) peut être utilisée pour transférer le contrôle hors d'un bloc try (y compris ses gestionnaires). Dans ce cas, chaque variable déclarée dans le bloc try est détruite dans le contexte qui contient directement sa déclaration :

try
{
    T1 t1;
    try
    {
        T2 t2;
        goto label; // détruire t2 d'abord, puis t1
    }
    catch(...)
    {
        // exécuté si une exception est levée pendant la destruction de t2
    }
}
catch(...)
{
    // exécuté si une exception est levée pendant la destruction de t1
}
label: ;
