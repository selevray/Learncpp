Contraintes et concepts (depuis C++20)

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Les modèles de classe, modèles de fonction (y compris les lambdas génériques) et autres fonctions templatisées (généralement membres de modèles de classe) peuvent être associés à une contrainte, qui spécifie les exigences sur les arguments de modèle, et qui peut être utilisée pour sélectionner les surcharges de fonctions et les spécialisations de modèles les plus appropriées.

Les ensembles nommés de telles exigences sont appelés concepts. Chaque concept est un prédicat, évalué à la compilation, et devient une partie de l'interface d'un modèle où il est utilisé comme contrainte :

#include <cstddef>
#include <concepts>
#include <functional>
#include <string>

// Déclaration du concept « Hashable », satisfait par tout type « T »
// tel que, pour les valeurs « a » de type « T », l'expression std::hash<T>{}(a)
// compile et son résultat est convertible en std::size_t
template<typename T>
concept Hashable = requires(T a)
{
    { std::hash<T>{}(a) } -> std::convertible_to<std::size_t>;
};

struct meow {};

// Modèle de fonction C++20 contraint :
template<Hashable T>
void f(T) {}
//
// Alternatives pour appliquer la même contrainte :
// template<typename T>
//     requires Hashable<T>
// void f(T) {}
//
// template<typename T>
// void f(T) requires Hashable<T> {}
//
// void f(Hashable auto /* parameter-name */) {}

int main()
{
    using std::operator""s;

    f("abc"s);    // OK, std::string satisfait Hashable
    // f(meow{}); // Error : meow ne satisfait pas Hashable
}

Les violations de contraintes sont détectées à la compilation, tôt dans le processus d'instanciation du modèle, ce qui conduit à des messages d'erreur faciles à suivre :

std::list<int> l = {3, -1, 10};
std::sort(l.begin(), l.end());
// Diagnostic typique du compilateur sans concepts :
// invalid operands to binary expression ('std::_List_iterator<int>' and
// 'std::_List_iterator<int>')
//                           std::__lg(__last - __first) * 2);
//                                     ~~~~~~ ^ ~~~~~~~
// ... 50 lignes de sortie ...
//
// Diagnostic typique du compilateur avec concepts :
// error: cannot call std::sort with std::_List_iterator<int>
// note:  concept RandomAccessIterator<std::_List_iterator<int>> n'est pas satisfait

Le but des concepts est de modéliser des catégories sémantiques (Number, Range, RegularFunction) plutôt que des restrictions syntaxiques (HasPlus, Array). Selon ISO C++ core guideline T.20, « La capacité de spécifier une sémantique significative est une caractéristique définissant un véritable concept, par opposition à une contrainte syntaxique. »

Concepts

Un concept est un ensemble nommé de exigences. La définition d'un concept doit apparaître dans une portée d'espace de noms.

La définition d'un concept a la forme

template < template-parameter-list >

concept concept-name attr ﻿*(facultatif)* = constraint-expression;

  • attr — suite de zéro ou plusieurs attributs
// concept
template<class T, class U>
concept Derived = std::is_base_of<U, T>::value;

Les concepts ne peuvent pas se référer récursivement à eux-mêmes et ne peuvent pas être contraints :

template<typename T>
concept V = V<T*>; // error: recursive concept

template<class T>
concept C1 = true;
template<C1 T>
concept Error1 = true; // Error : C1 T tente de contraindre une définition de concept
template<class T> requires C1<T>
concept Error2 = true; // Error : la clause requires tente de contraindre un concept

Les instanciations explicites, les spécialisations explicites ou les spécialisations partielles de concepts ne sont pas autorisées (la signification de la définition originale d'une contrainte ne peut pas être modifiée).

Les concepts peuvent être nommés dans une id-expression. La valeur de l'id-expression est true si l'expression de contrainte est satisfaite, et false sinon.

Les concepts peuvent aussi être nommés dans une type-constraint, faisant partie

  • d'une déclaration de paramètre de modèle de type,
  • d'un spécificateur de type substitut,
  • d'une exigence composée.

Dans un type-constraint, un concept prend un argument de modèle de moins que ce que sa liste de paramètres exige, car le type déduit du contexte est implicitement utilisé comme premier argument du concept.

template<class T, class U>
concept Derived = std::is_base_of<U, T>::value;

template<Derived<Base> T>
void f(T); // T est contrainte par Derived<T, Base>

Contraintes

Une contrainte est une suite d'opérations logiques et d'opérandes qui spécifie des exigences sur les arguments de modèle. Elles peuvent apparaître dans des requires expressions ou directement comme corps de concepts.

Il existe [trois (jusqu'à C++26) | quatre (depuis C++26)] types de contraintes :

conjonctions 1)

disjonctions 2)

  1. contraintes atomiques
  1. contraintes d'expansion de pliage

(depuis C++26)

La contrainte associée à une déclaration est déterminée en normalisant une expression ET logique dont les opérandes sont, dans l'ordre suivant :

  1. l'expression de contrainte introduite pour chaque paramètre de modèle de type contraint ou paramètre de modèle non type déclaré avec un type substitut contraint, dans l'ordre d'apparition ;
  2. l'expression de contrainte de la clause requires qui suit la liste des paramètres de modèle ;
  3. l'expression de contrainte introduite pour chaque paramètre dont le type substitut est contraint dans une déclaration de modèle de fonction abrégé ;
  4. l'expression de contrainte de la clause requires finale.

Cet ordre détermine l'ordre dans lequel les contraintes sont instanciées lors de la vérification de la satisfaction.

Redéclarations

Une déclaration contrainte ne peut être redéclarée qu'avec la même forme syntaxique. Aucun diagnostic n'est requis :

// Ces deux premières déclarations de f sont correctes
template<Incrementable T>
void f(T) requires Decrementable<T>;

template<Incrementable T>
void f(T) requires Decrementable<T>; // OK, redéclaration

// L'inclusion de cette troisième déclaration de f, logiquement équivalente mais syntaxiquement différente,
// est mal formée, aucun diagnostic requis
template<typename T>
    requires Incrementable<T> && Decrementable<T>
void f(T);

// Les deux déclarations suivantes ont des contraintes différentes :
// la première déclaration a Incrementable<T> && Decrementable<T>
// la seconde déclaration a Decrementable<T> && Incrementable<T>
// Bien qu'elles soient logiquement équivalentes.

template<Incrementable T>
void g(T) requires Decrementable<T>;

template<Decrementable T>
void g(T) requires Incrementable<T>; // mal formé, aucun diagnostic requis

Conjonctions

La conjonction de deux contraintes est formée en utilisant l'opérateur && dans l'expression de contrainte :

template<class T>
concept Integral = std::is_integral<T>::value;
template<class T>
concept SignedIntegral = Integral<T> && std::is_signed<T>::value;
template<class T>
concept UnsignedIntegral = Integral<T> && !SignedIntegral<T>;

Une conjonction de deux contraintes n'est satisfaite que si les deux contraintes le sont. Les conjonctions sont évaluées de gauche à droite et court-circuitées (si la contrainte de gauche n'est pas satisfaite, la substitution des arguments de modèle dans la contrainte de droite n'est pas tentée : cela empêche les échecs dus à une substitution en dehors du contexte immédiat).

template<typename T>
constexpr bool get_value() { return T::value; }

template<typename T>
    requires (sizeof(T) > 1 && get_value<T>())
void f(T);   // #1

void f(int); // #2

void g()
{
    f('A'); // OK, appelle #2. Lors de la vérification des contraintes de #1,
            // 'sizeof(char) > 1' n'est pas satisfait, donc get_value<T>() n'est pas vérifié
}

Disjonctions

La disjonction de deux contraintes est formée en utilisant l'opérateur || dans l'expression de contrainte :

Une disjonction de deux contraintes est satisfaite si l'une des deux contraintes l'est. Les disjonctions sont évaluées de gauche à droite et court-circuitées (si la contrainte de gauche est satisfaite, la substitution des arguments de modèle dans la contrainte de droite n'est pas tentée).

template<class T = void>
    requires EqualityComparable<T> || Same<T, void>
struct equal_to;

Contraintes atomiques

Une contrainte atomique est constituée d'une expression E et d'une correspondance entre les paramètres de modèle qui apparaissent dans E et des arguments de modèle impliquant les paramètres de modèle de l'entité contrainte, appelée sa correspondance de paramètres.

Les contraintes atomiques sont formées lors de la normalisation des contraintes. E n'est jamais une expression ET logique ou OU logique (celles-ci forment respectivement des conjonctions et des disjonctions).

La satisfaction d'une contrainte atomique est vérifiée en substituant la correspondance de paramètres et les arguments de modèle dans l'expression E. Si la substitution aboutit à un type ou une expression invalide, la contrainte n'est pas satisfaite. Sinon, E, après une conversion lvalue-to-rvalue éventuelle, doit être une expression constante prvalue de type bool, et la contrainte est satisfaite si et seulement si elle s'évalue à true.

Le type de E après substitution doit être exactement bool. Aucune conversion n'est autorisée :

template<typename T>
struct S
{
    constexpr operator bool() const { return true; }
};

template<typename T>
    requires (S<T>{})
void f(T);   // #1

void f(int); // #2

void g()
{
    f(0); // error: S<int>{} n'a pas le type bool lors de la vérification de #1,
          // même si #2 correspond mieux
}

Deux contraintes atomiques sont considérées comme identiques si elles sont formées à partir de la même expression au niveau du code source et si leurs correspondances de paramètres sont équivalentes.

template<class T>
constexpr bool is_meowable = true;

template<class T>
constexpr bool is_cat = true;

template<class T>
concept Meowable = is_meowable<T>;

template<class T>
concept BadMeowableCat = is_meowable<T> && is_cat<T>;

template<class T>
concept GoodMeowableCat = Meowable<T> && is_cat<T>;

template<Meowable T>
void f1(T); // #1

template<BadMeowableCat T>
void f1(T); // #2

template<Meowable T>
void f2(T); // #3

template<GoodMeowableCat T>
void f2(T); // #4

void g()
{
    f1(0); // erreur, ambiguïté :
           // le is_meowable<T> dans Meowable et BadMeowableCat forme des
           // contraintes atomiques distinctes qui ne sont pas identiques (et ne se subsument donc pas mutuellement)

    f2(0); // OK, appelle #4, plus contrainte que #3
           // GoodMeowableCat a obtenu son is_meowable<T> de Meowable
}

Contraintes d'expansion de pliage

Une contrainte d'expansion de pliage est formée à partir d'une contrainte C et d'un opérateur de pliage (soit &&, soit ||). Une contrainte d'expansion de pliage est une expansion de pack.

Soit N le nombre d'éléments dans les paramètres de l'expansion de pack :

  • Si l'expansion de pack est invalide (par exemple en développant des packs de tailles différentes), la contrainte d'expansion de pliage n'est pas satisfaite.
  • Si N vaut 0, la contrainte d'expansion de pliage est satisfaite si l'opérateur de pliage est &&, ou non satisfaite si l'opérateur de pliage est ||.
  • Pour une contrainte d'expansion de pliage avec un N positif, pour chaque i dans [1,N], chaque paramètre de l'expansion de pack est remplacé par le ie élément correspondant, dans l'ordre croissant :
  • Pour les contraintes d'expansion de pliage dont l'opérateur de pliage est &&, si le remplacement du je élément viole C, la contrainte d'expansion de pliage n'est pas satisfaite. Dans ce cas, aucune substitution n'a lieu pour un i supérieur à j. Sinon, la contrainte d'expansion de pliage est satisfaite.
  • Pour les contraintes d'expansion de pliage dont l'opérateur de pliage est ||, si le remplacement du je élément satisfait C, la contrainte d'expansion de pliage est satisfaite. Dans ce cas, aucune substitution n'a lieu pour un i supérieur à j. Sinon, la contrainte d'expansion de pliage n'est pas satisfaite.
template <class T> concept A = std::is_move_constructible_v<T>;
template <class T> concept B = std::is_copy_constructible_v<T>;
template <class T> concept C = A<T> && B<T>;

// en C++23, ces deux surcharges de g() ont des contraintes atomiques distinctes
// qui ne sont pas identiques et ne se subsument donc pas mutuellement : les appels à g() sont ambigus
// en C++26, les pliages sont développés et la contrainte de la surcharge #2 (move et copy
// requis), subsume la contrainte de la surcharge #1 (seul le move est requis)
template <class... T>
requires (A<T> && ...) void g(T...); // #1

template <class... T>
requires (C<T> && ...) void g(T...); // #2

(depuis C++26)

Normalisation des contraintes

La normalisation des contraintes est le processus qui transforme une expression de contrainte en une suite de conjonctions et de disjonctions de contraintes atomiques. La forme normale d'une expression est définie comme suit :

  • La forme normale d'une expression (E) est la forme normale de E.
  • La forme normale d'une expression E1 && E2 est la conjonction des formes normales de E1 et E2.
  • La forme normale d'une expression E1 || E2 est la disjonction des formes normales de E1 et E2.
  • La forme normale d'une expression C<A1, A2, ... , AN>, où C désigne un concept, est la forme normale de l'expression de contrainte de C, après substitution de A1, A2, ... , AN aux paramètres de modèle respectifs de C dans les correspondances de paramètres de chaque contrainte atomique de C. Si une substitution quelconque dans les correspondances de paramètres aboutit à un type ou une expression invalide, le programme est mal formé, aucun diagnostic n'est requis.
template<typename T>
concept A = T::value || true;

template<typename U>
concept B = A<U*>; // OK : normalisée en la disjonction de
                   // - T::value (avec la correspondance T -> U*) et
                   // - true (avec une correspondance vide).
                   // Aucun type invalide dans la correspondance, alors que
                   // T::value est mal formé pour tous les types pointeurs

template<typename V>
concept C = B<V&>; // Se normalise en la disjonction de
                   // - T::value (avec la correspondance T-> V&*) et
                   // - true (avec une correspondance vide).
                   // Type invalide V&* formé dans la correspondance => mal formé, aucun diagnostic requis
  • La forme normale des expressions (E && ...) et (... && E) est une contrainte d'expansion de pliage, où C est la forme normale de E et l'opérateur de pliage est &&.
  • La forme normale des expressions (E || ...) et (... || E) est une contrainte d'expansion de pliage, où C est la forme normale de E et l'opérateur de pliage est ||.
  • Les formes normales des expressions (E1 && ... && E2) et (E1 || ... || E2) sont les formes normales de
  • (E1 && ...) && E2 et (E1 || ...) || E2 respectivement, si E1 contient un pack non développé, ou
  • E1 && (... && E2) et E1 || (... || E2) respectivement sinon.

(depuis C++26)

  • La forme normale de toute autre expression E est la contrainte atomique dont l'expression est E et dont la correspondance de paramètres est la correspondance identité. Cela inclut toutes les expressions de pliage, même celles pliant sur les opérateurs && ou ||.

Les surcharges définies par l'utilisateur de && ou || n'ont aucun effet sur la normalisation des contraintes.

clauses requires

Le mot-clé requires sert à introduire une clause requires, qui spécifie des contraintes sur les arguments de modèle ou sur une déclaration de fonction.

template<typename T>
void f(T&&) requires Eq<T>; // peut apparaître comme dernier élément d'un déclarateur de fonction

template<typename T> requires Addable<T> // ou juste après une liste de paramètres de modèle
T add(T a, T b) { return a + b; }

Dans ce cas, le mot-clé requires doit être suivi d'une expression constante quelconque (il est donc possible d'écrire requires true), mais l'intention est qu'un concept nommé (comme dans l'exemple ci-dessus), une conjonction ou une disjonction de concepts nommés, ou une expression requires soit utilisée.

L'expression doit avoir l'une des formes suivantes :

  • Une expression primaire, par exemple Swappable<T>, std::is_integral<T>::value, (std::is_object_v<Args> && ...), ou toute expression entre parenthèses.
  • Une suite d'expressions primaires reliées par l'opérateur &&.
  • Une suite des expressions précédentes reliées par l'opérateur ||.
template<class T>
constexpr bool is_meowable = true;

template<class T>
constexpr bool is_purrable() { return true; }

template<class T>
void f(T) requires is_meowable<T>; // OK

template<class T>
void g(T) requires is_purrable<T>(); // erreur, is_purrable<T>() n'est pas une expression primaire

template<class T>
void h(T) requires (is_purrable<T>()); // OK

Ordre partiel des contraintes

Avant toute analyse supplémentaire, les contraintes sont normalisées en substituant le corps de chaque concept nommé et de chaque expression requires, jusqu'à ce qu'il ne reste qu'une suite de conjonctions et de disjonctions de contraintes atomiques.

Une contrainte P est dite subsumer la contrainte Q s'il peut être démontré que P implique Q, à l'identité près des contraintes atomiques de P et Q. (Les types et expressions ne sont pas analysés pour l'équivalence : N > 0 ne subsume pas N >= 0).

Plus précisément, P est d'abord converti en forme normale disjonctive et Q en forme normale conjonctive. P subsume Q si et seulement si :

  • chaque clause disjonctive de la forme normale disjonctive de P subsume chaque clause conjonctive de la forme normale conjonctive de Q, où
  • une clause disjonctive subsume une clause conjonctive si et seulement s'il existe une contrainte atomique U dans la clause disjonctive et une contrainte atomique V dans la clause conjonctive telles que U subsume V ;
  • une contrainte atomique A subsume une contrainte atomique B si et seulement si elles sont identiques selon les règles décrites ci-dessus.
  • Une contrainte d'expansion de pliage A subsume une autre contrainte d'expansion de pliage B si elles ont le même opérateur de pliage, la contrainte C de A subsume celle de B, et si C contiennent toutes deux un pack non développé équivalent.

(depuis C++26)

La relation de subsomption définit un ordre partiel des contraintes, utilisé pour déterminer :

  • le meilleur candidat viable pour une fonction non template dans la résolution de surcharge
  • l'adresse d'une fonction non template dans un ensemble de surcharges
  • la meilleure correspondance pour un argument de modèle de modèle
  • l'ordre partiel des spécialisations de modèles de classe
  • ordre partiel des modèles de fonction

Si les déclarations D1 et D2 sont contraintes et que les contraintes associées à D1 subsument les contraintes associées à D2 (ou si D2 n'est pas contrainte), alors D1 est dite au moins aussi contrainte que D2. Si D1 est au moins aussi contrainte que D2, et si D2 n'est pas au moins aussi contrainte que D1, alors D1 est plus contrainte que D2.

Si toutes les conditions suivantes sont satisfaites, une fonction non modèle F1 est plus contrainte selon l'ordre partiel qu'une fonction non modèle F2 :

  • Elles ont la même liste de types de paramètres, en omettant les types des paramètres objets explicites (depuis C++23).
  • S'il s'agit de fonctions membres, toutes deux sont membres directs de la même classe.
  • Si toutes deux sont des fonctions membres non statiques, elles ont les mêmes types pour leurs paramètres objets.
  • F1 est plus contrainte que F2.
template<typename T>
concept Decrementable = requires(T t) { --t; };
template<typename T>
concept RevIterator = Decrementable<T> && requires(T t) { *t; };

// RevIterator subsume Decrementable, mais pas l'inverse

template<Decrementable T>
void f(T); // #1

template<RevIterator T>
void f(T); // #2, plus contraint que #1

f(0);       // int satisfait uniquement Decrementable, sélectionne #1
f((int*)0); // int* satisfait les deux contraintes, sélectionne #2 comme plus contraint

template<class T>
void g(T); // #3 (unconstrained)

template<Decrementable T>
void g(T); // #4

g(true); // bool ne satisfait pas Decrementable, sélectionne #3
g(0);    // int satisfait Decrementable, sélectionne #4 car il est plus contraint

template<typename T>
concept RevIterator2 = requires(T t) { --t; *t; };

template<Decrementable T>
void h(T); // #5

template<RevIterator2 T>
void h(T); // #6

h((int*)0); // ambiguous
