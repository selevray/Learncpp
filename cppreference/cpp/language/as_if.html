La règle du « comme si »

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Autorise toutes les transformations de code qui ne modifient pas le comportement observable du programme.

Explication

Le compilateur C++ peut effectuer toute modification du programme, à condition que ce qui suit reste vrai :

  1. À chaque point de séquence, les valeurs de tous les objets volatile sont stables (les évaluations précédentes sont terminées, les nouvelles ne sont pas commencées).

(jusqu'à C++11)

  1. Les accès (lectures et écritures) aux objets volatile se produisent strictement selon la sémantique des expressions dans lesquelles ils apparaissent. En particulier, ils ne sont pas réordonnés par rapport aux autres accès volatile sur le même thread.

(depuis C++11)

  1. À la fin du programme, les données écrites dans les fichiers sont exactement celles qui seraient produites si le programme était exécuté tel qu'écrit.

  2. Le texte d'invite envoyé aux périphériques interactifs sera affiché avant que le programme n'attende une entrée.

  3. Si le pragma ISO C #pragma STDC FENV_ACCESS est pris en charge et vaut ON, les modifications de l'environnement à virgule flottante (exceptions et modes d'arrondi en virgule flottante) sont garanties d'être prises en compte par les opérateurs arithmétiques et les appels de fonction à virgule flottante comme si le programme était exécuté tel qu'écrit, à l'exception du fait que

  • le résultat de toute expression à virgule flottante autre qu'une conversion explicite ou une affectation peut avoir l'intervalle et la précision d'un type à virgule flottante différent du type de l'expression (voir FLT_EVAL_METHOD),
  • nonobstant ce qui précède, les résultats intermédiaires de toute expression à virgule flottante peuvent être calculés comme s'ils avaient une étendue et une précision infinies (sauf si #pragma STDC FP_CONTRACT vaut OFF).

Notes

Le compilateur étant (en général) incapable d'analyser le code d'une bibliothèque externe pour déterminer si elle effectue ou non des E/S ou des accès volatile, les appels aux bibliothèques tierces ne sont pas non plus affectés par l'optimisation. Toutefois, les appels à la bibliothèque standard peuvent être remplacés par d'autres appels, supprimés ou ajoutés au programme pendant l'optimisation. Le code de bibliothèques tierces liées statiquement peut être soumis à l'optimisation à l'édition de liens.

Les programmes présentant un comportement indéfini, par exemple à cause d'un accès à un tableau hors bornes, d'une modification d'un objet const, de violations de l'ordre d'évaluation, etc., échappent à la règle du comme si : ils changent souvent de comportement observable lorsqu'ils sont recompilés avec d'autres options d'optimisation. Par exemple, si un test de dépassement de capacité d'un entier signé repose sur le résultat de ce dépassement, par exemple if (n + 1 < n) abort();, il est entièrement supprimé par certains compilateurs parce que le dépassement signé est un comportement indéfini et que l'optimiseur est libre de supposer qu'il ne se produit jamais, le test étant alors redondant.

L'élision de copie est une exception à la règle du comme si : le compilateur peut supprimer les appels aux constructeurs de déplacement et de copie, ainsi que les appels correspondants aux destructeurs des objets temporaires, même si ces appels ont des effets de bord observables.

L'expression new constitue une autre exception à la règle du comme si : le compilateur peut supprimer les appels aux fonctions d'allocation remplaçables, même si un remplacement défini par l'utilisateur est fourni et présente des effets de bord observables.

(depuis C++14)

Le nombre et l'ordre des exceptions en virgule flottante peuvent être modifiés par l'optimisation, à condition que l'état observé par l'opération en virgule flottante suivante soit le même que si aucune optimisation n'avait eu lieu :

#pragma STDC FENV_ACCESS ON
for (i = 0; i < n; ++i)
    x + 1; // x + 1 est du code mort, mais peut lever des exceptions FP
           // (sauf si l'optimiseur peut prouver le contraire). Cependant, l'exécuter n fois
           // lèvera la même exception encore et encore. Ceci peut donc être optimisé en :
if (0 < n)
    x + 1;

Exemple

int& preinc(int& n) { return ++n; }
int add(int n, int m) { return n + m; }

// entrée volatile pour empêcher le repliement de constantes
volatile int input = 7;

// sortie volatile pour que le résultat constitue un effet de bord visible
volatile int result;

int main()
{
    int n = input;
// utiliser les opérateurs intégrés invoquerait un comportement indéfini
//  int m = ++n + ++n;
// mais utiliser des fonctions garantit que le code s'exécute comme si
// les fonctions ne se chevauchaient pas
    int m = add(preinc(n), preinc(n));
    result = m;
}

Output:

# full code of the main() function as produced by the GCC compiler
# x86 (Intel) platform:
        movl    input(%rip), %eax   # eax = input
        leal    3(%rax,%rax), %eax  # eax = 3 + eax + eax
        movl    %eax, result(%rip)  # result = eax
        xorl    %eax, %eax          # eax = 0 (the return value of main())
        ret

# PowerPC (IBM) platform:
        lwz 9,LC..1(2)
        li 3,0          # r3 = 0 (the return value of main())
        lwz 11,0(9)     # r11 = input;
        slwi 11,11,1    # r11 = r11 << 1;
        addi 0,11,3     # r0 = r11 + 3;
        stw 0,4(9)      # result = r0;
        blr

# Sparc (Sun) platform:
        sethi   %hi(result), %g2
        sethi   %hi(input), %g1
        mov     0, %o0                 # o0 = 0 (the return value of main)
        ld      [%g1+%lo(input)], %g1  # g1 = input
        add     %g1, %g1, %g1          # g1 = g1 + g1
        add     %g1, 3, %g1            # g1 = 3 + g1
        st      %g1, [%g2+%lo(result)] # result = g1
        jmp     %o7+8
        nop

# in all cases, the side effects of preinc() were eliminated, and the
# entire main() function was reduced to the equivalent of result = 2 * input + 3;
