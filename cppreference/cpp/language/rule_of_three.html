Règle du trois

Si une classe nécessite un destructeur défini par l'utilisateur, un constructeur de copie défini par l'utilisateur ou un opérateur d'affectation par copie défini par l'utilisateur, elle en nécessite presque certainement les trois.

Parce que C++ copie et affecte par copie des objets de types définis par l'utilisateur dans diverses situations (passage ou retour par valeur, manipulation d'un conteneur, etc.), ces fonctions membres spéciales seront appelées, si elles sont accessibles, et si elles ne sont pas définies par l'utilisateur, elles sont définies implicitement par le compilateur.

Les fonctions membres spéciales définies implicitement ne doivent pas être utilisées si la classe gère une ressource dont le descripteur ne détruit pas lui-même la ressource (pointeur brut, descripteur de fichier POSIX, etc.), dont le destructeur ne fait rien et dont le constructeur de copie et l'opérateur d'affectation par copie ne font que copier la valeur du descripteur, sans dupliquer la ressource sous-jacente.

#include <cstddef>
#include <cstring>
#include <iostream>
#include <utility>

class rule_of_three
{
    char* cstring; // pointeur brut utilisé comme descripteur d'un
                   // bloc de mémoire alloué dynamiquement

public:
    rule_of_three(const char* s, std::size_t n)
        : cstring(new char[n + 1]) // allocate
    {
        std::memcpy(cstring, s, n); // populate
        cstring[n] = '\0';          // tail 0
    }

    explicit rule_of_three(const char* s = "")
        : rule_of_three(s, std::strlen(s))
    {
    }

    ~rule_of_three() // I. destructeur
    {
        delete[] cstring; // deallocate
    }

    rule_of_three(const rule_of_three& other) // II. constructeur de copie
        : rule_of_three(other.cstring)
    {
    }

    rule_of_three& operator=(const rule_of_three& other) // III. affectation par copie
    {
        if (this == &other)
            return *this;

        rule_of_three temp(other); // utilise le constructeur de copie
        std::swap(cstring, temp.cstring); // échange la ressource sous-jacente

        return *this;
    }

    const char* c_str() const // accessor
    {
        return cstring;
    }
};

int main()
{
    rule_of_three o1{"abc"};
    std::cout << o1.c_str() << ' ';
    auto o2{o1}; // II. utilise le constructeur de copie
    std::cout << o2.c_str() << ' ';
    rule_of_three o3{"def"};
    std::cout << o3.c_str() << ' ';
    o3 = o2; // III. utilise l'affectation par copie
    std::cout << o3.c_str() << '\n';
}   // I. tous les destructeurs sont appelés ici

Output:

abc abc def abc

Les classes qui gèrent des ressources non copiables via des descripteurs copiables peuvent devoir [déclarer le constructeur de copie et l'opérateur d'affectation par copie private sans en fournir les définitions (jusqu'à C++11) | définir le constructeur de copie et l'opérateur d'affectation par copie comme = delete (depuis C++11)]. C'est une autre application de la règle du trois : supprimer l'un et laisser l'autre être défini implicitement est généralement incorrect.

Règle du cinq

Parce que la présence d'un destructeur, d'un constructeur de copie ou d'un opérateur d'affectation par copie défini par l'utilisateur (y compris déclaré via = default ou = delete) empêche la définition implicite du constructeur de déplacement et de l'opérateur d'affectation par déplacement, toute classe pour laquelle la sémantique de déplacement est souhaitable doit déclarer les cinq fonctions membres spéciales :

#include <cstddef>
#include <cstring>
#include <utility>

class rule_of_five
{
    char* cstring; // pointeur brut utilisé comme descripteur d'un
                   // bloc de mémoire alloué dynamiquement

public:
    rule_of_five(const char* s, std::size_t n)
        : cstring(new char[n + 1]) // allocate
    {
        std::memcpy(cstring, s, n); // populate
        cstring[n] = '\0';          // tail 0
    }

    explicit rule_of_five(const char* s)
        : rule_of_five(s, std::strlen(s))
    {
    }

    ~rule_of_five() // I. destructeur
    {
        delete[] cstring; // deallocate
    }

    rule_of_five(const rule_of_five& other) // II. constructeur de copie
        : rule_of_five(other.cstring)
    {
    }

    rule_of_five& operator=(const rule_of_five& other) // III. affectation par copie
    {
        if (this == &other)
            return *this;

        rule_of_five temp(other); // utilise le constructeur de copie
        std::swap(cstring, temp.cstring); // échange la ressource sous-jacente

        return *this;
    }

    rule_of_five(rule_of_five&& other) noexcept // IV. constructeur de déplacement
        : cstring(std::exchange(other.cstring, nullptr))
    {
    }

    rule_of_five& operator=(rule_of_five&& other) noexcept // V. affectation par déplacement
    {
        rule_of_five temp(std::move(other));
        std::swap(cstring, temp.cstring);
        return *this;
    }
};

Contrairement à la règle du trois, ne pas fournir le constructeur de déplacement et l'opérateur d'affectation par déplacement n'est généralement pas une erreur, mais cela entraîne une perte de performance.

Règle du zéro

Les classes qui ont des destructeurs, des constructeurs de copie/déplacement ou des opérateurs d'affectation par copie/déplacement personnalisés doivent traiter exclusivement de la propriété (ce qui découle du principe de responsabilité unique). Les autres classes ne devraient pas avoir de destructeurs, constructeurs de copie/déplacement ou opérateurs d'affectation par copie/déplacement personnalisés[1].

Cette règle apparaît aussi dans les C++ Core Guidelines sous la forme C.20 : Si vous pouvez éviter de définir les opérations par défaut, faites-le.

class rule_of_zero
{
    std::string cppstring;
public:
    // redondant, la définition implicite est préférable
    // rule_of_zero(const std::string& arg) : cppstring(arg) {}
};

Lorsqu'une classe de base est destinée à un usage polymorphe, son destructeur peut devoir être déclaré public et virtual. Cela bloque les déplacements implicites (et déprécie les copies implicites), de sorte que les fonctions membres spéciales doivent être définies comme = default[2].

class base_of_five_defaults
{
public:
    base_of_five_defaults(const base_of_five_defaults&) = default;
    base_of_five_defaults(base_of_five_defaults&&) = default;
    base_of_five_defaults& operator=(const base_of_five_defaults&) = default;
    base_of_five_defaults& operator=(base_of_five_defaults&&) = default;
    virtual ~base_of_five_defaults() = default;
};

Cependant, cela rend la classe sujette au découpage (slicing), c'est pourquoi les classes polymorphes définissent souvent la copie comme = delete (voir C.67 : Une classe polymorphe doit supprimer la copie et le déplacement publics dans les C++ Core Guidelines), ce qui conduit à la formulation générique suivante de la règle du cinq :

C.21 : Si vous définissez ou =delete une fonction de copie, de déplacement ou un destructeur, définissez ou =delete-les toutes.
