Mémoire transactionnelle (TM TS)

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

La mémoire transactionnelle est un mécanisme de synchronisation de concurrence qui regroupe des ensembles d'instructions dans des transactions, qui sont

  • atomiques (soit toutes les instructions ont lieu, soit aucune n'a lieu)
  • isolées (les instructions d'une transaction ne peuvent pas observer des écritures à moitié effectuées par une autre transaction, même si elles s'exécutent en parallèle)

Les implémentations typiques utilisent la mémoire transactionnelle matérielle lorsqu'elle est prise en charge, et dans la limite de sa disponibilité (par exemple jusqu'à saturation de l'ensemble des modifications), et se replient sur la mémoire transactionnelle logicielle, généralement implémentée avec une concurrence optimiste : si une autre transaction a mis à jour certaines variables utilisées par une transaction, celle-ci est silencieusement réessayée. Pour cette raison, les transactions réessayables («blocs atomiques») ne peuvent appeler que des fonctions sûres pour les transactions.

Notez qu'accéder à une variable dans une transaction et en dehors d'une transaction sans autre synchronisation externe constitue une situation de course (data race).

Si la prise en charge des tests de fonctionnalités est disponible, les fonctionnalités décrites ici sont indiquées par la constante macro __cpp_transactional_memory dont la valeur est égale ou supérieure à 201505.

Blocs synchronisés

synchronized compound-statement

Exécute l'instruction composée comme si elle était sous un verrou global : tous les blocs synchronisés les plus externes du programme s'exécutent dans un ordre total unique. La fin de chaque bloc synchronisé se synchronise avec le début du bloc synchronisé suivant dans cet ordre. Les blocs synchronisés imbriqués dans d'autres blocs synchronisés n'ont pas de sémantique particulière.

Les blocs synchronisés ne sont pas des transactions (contrairement aux blocs atomiques ci-dessous) et peuvent appeler des fonctions non sûres pour les transactions.

#include <iostream>
#include <thread>
#include <vector>

int f()
{
    static int i = 0;
    synchronized { // début du bloc synchronisé
        std::cout << i << " -> ";
        ++i;       // chaque appel à f() obtient une valeur unique de i
        std::cout << i << '\n';
        return i;  // fin du bloc synchronisé
    }
}

int main()
{
    std::vector<std::thread> v(10);
    for (auto& t : v)
        t = std::thread([] { for (int n = 0; n < 10; ++n) f(); });
    for (auto& t : v)
        t.join();
}

Output:

0 -> 1
1 -> 2
2 -> 3
...
99 -> 100

Quitter un bloc synchronisé par tout moyen (atteindre la fin, exécuter goto, break, continue ou return, ou lever une exception) quitte le bloc et se synchronise avec le bloc suivant dans l'ordre total unique si le bloc quitté était un bloc externe. Le comportement est indéfini si std::longjmp est utilisé pour quitter un bloc synchronisé.

Entrer dans un bloc synchronisé par goto ou switch n'est pas autorisé.

Bien que les blocs synchronisés s'exécutent comme s'ils étaient sous un verrou global, les implémentations doivent examiner le code de chaque bloc et utiliser une concurrence optimiste (soutenue par la mémoire transactionnelle matérielle lorsqu'elle est disponible) pour le code sûr pour les transactions, et un verrouillage minimal pour le code non sûr. Lorsqu'un bloc synchronisé appelle une fonction non incorporée, le compilateur peut devoir abandonner l'exécution spéculative et maintenir un verrou autour de l'appel entier, sauf si la fonction est déclarée transaction_safe (voir ci-dessous) ou si l'attribut [[optimize_for_synchronized]] (voir ci-dessous) est utilisé.

  1. Si une exception est levée, std::abort est appelée.

  2. Si une exception est levée, std::abort est appelée, sauf si l'exception fait partie de celles utilisées pour l'annulation de transaction (voir ci-dessous), auquel cas la transaction est annulée : les valeurs de tous les emplacements mémoire du programme modifiés par les effets de bord des opérations du bloc atomique sont restaurées aux valeurs qu'ils avaient au moment de l'exécution du début du bloc atomique, et l'exception poursuit le déroulement de la pile comme d'habitude.

  3. Si une exception est levée, la transaction est validée normalement.

Les exceptions utilisées pour l'annulation de transaction dans les blocs atomic_cancel sont std::bad_alloc, std::bad_array_new_length, std::bad_cast, std::bad_typeid, std::bad_exception, std::exception et toutes les exceptions de la bibliothèque standard qui en dérivent, ainsi que le type d'exception spécial std::tx_exception<T>.

Le compound-statement dans un bloc atomique ne doit exécuter aucune expression ni instruction et n'appeler aucune fonction qui ne soit pas transaction_safe (il s'agit d'une erreur à la compilation).

// chaque appel à f() récupère une valeur unique de i, même lorsqu'il est exécuté en parallèle
int f()
{
    static int i = 0;
    atomic_noexcept { // début de la transaction
//  printf("before %d\n", i); // erreur : impossible d'appeler une fonction non sûre pour les transactions
        ++i;
        return i; // fin de la transaction
    }
}

Sortir d'un bloc atomique par tout autre moyen que l'exception (atteindre la fin, goto, break, continue, return) valide la transaction. Le comportement est indéfini si std::longjmp est utilisé pour sortir d'un bloc atomique.

extern volatile int * p = 0;
struct S
{
    virtual ~S();
};
int f() transaction_safe
{
    int x = 0;  // ok : non volatile
    p = &x;     // ok : le pointeur n'est pas volatile
    int i = *p; // error : lecture via une glvalue volatile
    S s;        // error : appel d'un destructeur non sûr
}

int f(int x) { // implicitement sûr vis-à-vis des transactions
    if (x <= 0)
        return 0;
    return x + f(x - 1);
}

Si une fonction qui n'est pas sûre pour les transactions est appelée via une référence ou un pointeur vers une fonction sûre pour les transactions, le comportement est indéfini.

Les pointeurs vers des fonctions sûres pour les transactions et les pointeurs vers des fonctions membres sûres pour les transactions sont implicitement convertibles en pointeurs vers des fonctions et en pointeurs vers des fonctions membres respectivement. Il est non spécifié si le pointeur obtenu compare égal à l'original.

Bibliothèque standard

Outre l'introduction du nouveau modèle d'exception std::tx_exception, la spécification technique de mémoire transactionnelle apporte les modifications suivantes à la bibliothèque standard :

  • rend explicitement transaction_safe les fonctions suivantes :

    • std::forward, std::move, std::move_if_noexcept, std::align, std::abort, opérateur global par défaut operator new, opérateur global par défaut operator delete, std::allocator::construct si le constructeur invoqué est sûr pour les transactions, std::allocator::destroy si le destructeur invoqué est sûr pour les transactions, std::get_temporary_buffer, std::return_temporary_buffer, std::addressof, std::pointer_traits::pointer_to, chaque fonction membre non virtuelle de tous les types d'exception prenant en charge l'annulation de transaction (voir atomic_cancel ci-dessus)

Attributs

L'attribut [[optimize_for_synchronized]] peut être appliqué à un déclarateur dans une déclaration de fonction et doit apparaître dans la première déclaration de la fonction.

Si une fonction est déclarée [[optimize_for_synchronized]] dans une unité de traduction et que la même fonction est déclarée sans [[optimize_for_synchronized]] dans une autre unité de traduction, le programme est mal formé ; aucun diagnostic requis.

Il indique que la définition de la fonction doit être optimisée pour son invocation depuis une instruction synchronized. En particulier, il évite de sérialiser les blocs synchronisés qui appellent une fonction sûre pour les transactions dans la majorité des appels, mais pas dans tous (par exemple une insertion dans une table de hachage qui peut devoir se réorganiser, un allocateur qui peut devoir demander un nouveau bloc, une fonction simple pouvant rarement journaliser).

std::atomic<bool> rehash{false};

// le thread de maintenance exécute cette boucle
void maintenance_thread(void*)
{
    while (!shutdown)
    {
        synchronized
        {
            if (rehash)
            {
                hash.rehash();
                rehash = false;
            }
        }
    }
}

// les threads de travail exécutent des centaines de milliers d'appels à cette fonction
// chaque seconde. Les appels à insert_key() depuis des blocs synchronized d'autres
// unités de traduction provoqueront la sérialisation de ces blocs, à moins que insert_key()
// est marqué [[optimize_for_synchronized]]
[[optimize_for_synchronized]] void insert_key(char* key, char* value)
{
    bool concern = hash.insert(key, value);
    if (concern)
        rehash = true;
}
