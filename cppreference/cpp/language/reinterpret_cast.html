Conversion reinterpret_cast

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Convertit entre types en réinterprétant le motif binaire sous-jacent.

Syntaxe

| | | | reinterpret_cast< target-type >( expression ) | | | |

Renvoie une valeur de type target-type.

Explication

Contrairement à static_cast, mais comme const_cast, l'expression reinterpret_cast ne se compile en aucune instruction du processeur (sauf lors de conversions entre entiers et pointeurs, ou entre pointeurs sur des architectures obscures où la représentation du pointeur dépend de son type). Il s'agit principalement d'une directive à la compilation qui demande au compilateur de traiter expression comme s'il avait le type target-type.

Seules les conversions suivantes peuvent être effectuées avec reinterpret_cast, sauf lorsque ces conversions supprimeraient la constness (ou la volatilité).

  1. Une expression de type entier, énumération, pointeur ou pointeur vers membre peut être convertie vers son propre type. La valeur résultante est la même que la valeur de expression.

  2. Un pointeur peut être converti vers tout type entier suffisamment grand pour contenir toutes les valeurs de son type (par exemple vers std::uintptr_t).

  3. Une valeur de tout type entier ou énumération peut être convertie vers un type pointeur. Un pointeur converti en entier de taille suffisante puis reconverti vers le même type de pointeur a garanti sa valeur d'origine ; sinon, le pointeur résultant ne peut pas être déréférencé en toute sécurité (la conversion aller-retour dans l'autre sens n'est pas garantie ; un même pointeur peut avoir plusieurs représentations entières). La constante de pointeur nul NULL ou l'entier zéro n'est pas garanti de produire la valeur de pointeur nul du type cible ; static_cast ou conversion implicite doit être utilisé à cette fin.

  1. Toute valeur de type std::nullptr_t, y compris nullptr, peut être convertie vers tout type entier comme si elle était (void*)0, mais aucune valeur, pas même nullptr, ne peut être convertie vers std::nullptr_t : static_cast doit être utilisé à cette fin.

(depuis C++11)

  1. Tout type de pointeur vers objet T1* peut être converti vers un autre type de pointeur vers objet cv T2*. Ceci est exactement équivalent à static_cast<cv T2*>(static_cast<cv void*>(expression)) (ce qui implique que si l'exigence d'alignement de T2 n'est pas plus stricte que celle de T1, la valeur du pointeur ne change pas et la reconversion du pointeur résultant vers son type d'origine donne la valeur d'origine). Dans tous les cas, le pointeur résultant ne peut être déréférencé en toute sécurité que si la valeur déréférencée est accessible par type.

  2. Une expression [lvalue (jusqu'à C++11) | glvalue (depuis C++11)] de type T1 peut être convertie en référence vers un autre type T2. Le résultat est celui de *reinterpret_cast<T2*>(p), où p est un pointeur de type « pointeur vers T1 » vers l'objet ou la fonction désigné par expression. Aucun temporaire n'est matérialisé ni (depuis C++17) créé, aucune copie n'est faite, aucun constructeur ni fonction de conversion n'est appelé. La référence résultante ne peut être utilisée en toute sécurité que si elle est accessible par type.

  3. Tout pointeur vers fonction peut être converti vers un pointeur vers un type de fonction différent. Le résultat n'est pas spécifié, mais la conversion de ce pointeur vers le type de fonction d'origine donne le pointeur vers la fonction d'origine. Le pointeur résultant ne peut être appelé en toute sécurité que si son type de fonction est compatible à l'appel avec le type de fonction d'origine.

  4. Sur certaines implémentations (en particulier, sur tout système compatible POSIX comme l'exige dlsym), un pointeur de fonction peut être converti vers void* ou tout autre pointeur vers objet, et inversement. Si l'implémentation prend en charge la conversion dans les deux sens, la conversion vers le type d'origine donne la valeur d'origine ; sinon, le pointeur résultant ne peut pas être déréférencé ni appelé en toute sécurité.

  5. La valeur de pointeur nul de tout type de pointeur peut être convertie vers tout autre type de pointeur, donnant la valeur de pointeur nul de ce type. Notez que la constante de pointeur nul nullptr ou toute autre valeur de type std::nullptr_t ne peut pas être convertie en pointeur avec reinterpret_cast : la conversion implicite ou static_cast doit être utilisée à cette fin.

  6. Un pointeur vers fonction membre peut être converti vers un pointeur vers une fonction membre différente d'un type différent. La conversion vers le type d'origine donne la valeur d'origine ; sinon, le pointeur résultant ne peut pas être utilisé en toute sécurité.

  7. Un pointeur vers objet membre d'une certaine classe T1 peut être converti vers un pointeur vers un autre objet membre d'une autre classe T2. Si l'alignement de T2 n'est pas plus strict que celui de T1, la conversion vers le type d'origine T1 donne la valeur d'origine ; sinon, le pointeur résultant ne peut pas être utilisé en toute sécurité.

Comme pour toutes les expressions de transtypage, le résultat est :

  • une lvalue si target-type est de type référence lvalueou référence rvalue vers un type fonction (depuis C++11) ;
  • une xvalue si target-type est une référence rvalue vers un type objet ;

(depuis C++11)

  • une prvalue sinon.

Aliasing de type

Accessibilité de type

Si un type T_ref est similaire à l'un des types suivants, un objet de type dynamique T_obj est accessible par type à travers une [lvalue (jusqu'à C++11) | glvalue (depuis C++11)] de type T_ref :

  • char
  • unsigned char
  • std::byte

(depuis C++17)

  • T_obj
  • le type signé ou non signé correspondant à T_obj

Si un programme tente de lire ou de modifier la valeur stockée d'un objet à travers une [lvalue (jusqu'à C++11) | glvalue (depuis C++11)] à travers laquelle il n'est pas accessible par type, le comportement est indéfini.

Cette règle permet l'analyse d'alias fondée sur le type, dans laquelle un compilateur suppose que la valeur lue à travers une glvalue d'un type n'est pas modifiée par une écriture à travers une glvalue d'un type différent (sous réserve des exceptions mentionnées ci-dessus).

Notez que de nombreux compilateurs C++ assouplissent cette règle, en tant qu'extension de langage non standard, pour autoriser l'accès de mauvais type via le membre inactif d'une union (un tel accès n'est pas indéfini en C).

Compatibilité d'appel

Si l'une des conditions suivantes est satisfaite, un type T_call est compatible à l'appel avec un type de fonction T_func :

  • T_call est le même type que T_func.
  • T_func* peut être converti en T_call* via une conversion de pointeur de fonction.

(depuis C++17)

Si une fonction est appelée à travers une expression dont le type de fonction n'est pas compatible à l'appel avec le type de la définition de la fonction appelée, le comportement est indéfini.

Notes

En supposant que les exigences d'alignement sont respectées, un reinterpret_cast ne modifie pas la valeur d'un pointeur en dehors de quelques cas limités concernant les objets interconvertibles par pointeur :

struct S1 { int a; } s1;
struct S2 { int a; private: int b; } s2; // not standard-layout
union U { int a; double b; } u = {0};
int arr[2];

int* p1 = reinterpret_cast<int*>(&s1); // la valeur de p1 est « pointeur vers s1.a » car
                                       // s1.a et s1 sont interconvertibles par pointeur

int* p2 = reinterpret_cast<int*>(&s2); // la valeur de p2 est inchangée par reinterpret_cast
                                       // et vaut « pointeur vers s2 ».

int* p3 = reinterpret_cast<int*>(&u);  // la valeur de p3 est « pointeur vers u.a » :
                                       // u.a et u sont interconvertibles par pointeur

double* p4 = reinterpret_cast<double*>(p3); // la valeur de p4 est « pointeur vers u.b » : u.a et
                                            // u.b sont interconvertibles par pointeur car
                                            // tous deux sont interconvertibles par pointeur avec u

int* p5 = reinterpret_cast<int*>(&arr); // la valeur de p5 est inchangée par reinterpret_cast
                                        // et vaut « pointeur vers arr »

Effectuer un accès à un membre de classe désignant un membre de donnée non statique ou une fonction membre non statique sur une glvalue qui ne désigne pas réellement un objet du type approprié - comme celle obtenue via un reinterpret_cast - entraîne un comportement indéfini :

struct S { int x; };
struct T { int x; int f(); };
struct S1 : S {};    // standard-layout
struct ST : S, T {}; // not standard-layout

S s = {};
auto p = reinterpret_cast<T*>(&s); // la valeur de p est « pointeur vers s »
auto i = p->x; // l'accès à un membre de classe est un comportement indéfini ;
               // s n'est pas un objet T
p->x = 1; // comportement indéfini
p->f();   // comportement indéfini

S1 s1 = {};
auto p1 = reinterpret_cast<S*>(&s1); // la valeur de p1 est « pointeur vers le sous-objet S de s1 »
auto i = p1->x; // OK
p1->x = 1;      // OK

ST st = {};
auto p2 = reinterpret_cast<S*>(&st); // la valeur de p2 est « pointeur vers st »
auto i = p2->x; // comportement indéfini
p2->x = 1;      // comportement indéfini

De nombreux compilateurs émettent des avertissements « strict aliasing » dans de tels cas, même si, techniquement, ces constructions enfreignent autre chose que le paragraphe communément appelé « règle de strict aliasing ».

Le but de la règle de strict aliasing et des règles associées est de permettre l'analyse d'alias fondée sur le type, qui serait compromise si un programme pouvait valablement créer une situation où deux pointeurs vers des types sans rapport (par exemple un int* et un float*) pourraient exister simultanément et être tous deux utilisés pour lire ou écrire la même mémoire (voir ce courriel sur le relais SG12). Ainsi, toute technique qui semble capable de créer une telle situation invoque nécessairement un comportement indéfini.

Lorsqu'il est nécessaire d'interpréter les octets d'un objet comme une valeur d'un type différent, std::memcpy ou std::bit_cast (depuis C++20) peut être utilisé :

double d = 0.1;
std::int64_t n;
static_assert(sizeof n == sizeof d);
// n = *reinterpret_cast<std::int64_t*>(&d); // Comportement indéfini
std::memcpy(&n, &d, sizeof d);               // OK
n = std::bit_cast<std::int64_t>(d);          // aussi OK

Si l'implémentation fournit std::intptr_t et/ou std::uintptr_t, alors une conversion d'un pointeur vers un type objet ou cv void vers ces types est toujours bien définie. Cependant, ceci n'est pas garanti pour un pointeur de fonction.

(depuis C++11)

En C, la copie et l'affectation d'agrégats accèdent à l'agrégat objet dans son ensemble. En C++, en revanche, de telles actions sont toujours effectuées via un appel de fonction membre, qui accède aux sous-objets individuels plutôt qu'à l'objet entier (ou, dans le cas des unions, copie la représentation de l'objet, c.-à-d. via unsigned char).

Mots-clés

reinterpret_cast

Exemple

Démontre quelques utilisations de reinterpret_cast :

#include <cassert>
#include <cstdint>
#include <iostream>

int f() { return 42; }

int main()
{
    int i = 7;

    // pointeur vers entier, puis retour
    std::uintptr_t v1 = reinterpret_cast<std::uintptr_t>(&i); // static_cast est une erreur
    std::cout << "The value of &i is " << std::showbase << std::hex << v1 << '\n';
    int* p1 = reinterpret_cast<int*>(v1);
    assert(p1 == &i);

    // pointeur vers fonction vers un autre, puis retour
    void(*fp1)() = reinterpret_cast<void(*)()>(f);
    // fp1(); comportement indéfini
    int(*fp2)() = reinterpret_cast<int(*)()>(fp1);
    std::cout << std::dec << fp2() << '\n'; // safe

    // aliasing de type via un pointeur
    char* p2 = reinterpret_cast<char*>(&i);
    std::cout << (p2[0] == '\x7' ? "This system is little-endian\n"
                                 : "This system is big-endian\n");

    // aliasing de type via une référence
    reinterpret_cast<unsigned int&>(i) = 42;
    std::cout << i << '\n';

    [[maybe_unused]] const int &const_iref = i;
    // int &iref = reinterpret_cast<int&>(
    //     const_iref); // erreur de compilation : impossible de supprimer const
    // Il faut utiliser const_cast à la place : int &iref = const_cast<int&>(const_iref);
}

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
CWG 195 C++98 conversion entre pointeurs de fonction et pointeurs d'objets non autorisée rendu à support conditionnel
CWG 658 C++98 le résultat des conversions de pointeurs était non spécifié (sauf pour les conversions vers le type d'origine) spécification fournie pour les pointeurs dont les types pointés satisfont les exigences d'alignement
CWG 799 C++98 on ne savait pas quelle conversion d'identité pouvait être effectuée par reinterpret_cast rendu clair
CWG 1268 C++11 reinterpret_cast ne pouvait convertir que des lvalues vers des types référence les xvalues étaient également autorisées
CWG 2780 C++98 reinterpret_cast ne pouvait pas convertir des lvalues de fonction vers d'autres types référence allowed
CWG 2939 C++17 reinterpret_cast pouvait convertir des prvalues vers des types référence rvalue non autorisé
