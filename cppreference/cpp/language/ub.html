Comportement indéfini

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Rend le programme entier dénué de sens si certaines règles du langage sont violées.

Explication

La norme C++ définit précisément le comportement observable de chaque programme C++ qui n'appartient à aucune des classes suivantes :

  • mal formé - Le programme contient des erreurs de syntaxe ou des erreurs sémantiques détectables.

    • Un compilateur C++ conforme est tenu d'émettre un diagnostic, même s'il définit une extension du langage qui donne un sens à ce code (comme avec les tableaux de taille variable).
    • Le texte de la norme utilise shall, shall not et ill-formed pour indiquer ces exigences.

  • mal formé, aucun diagnostic requis - Le programme contient des erreurs sémantiques qui peuvent ne pas être détectables dans le cas général (par exemple des violations de la ODR ou d'autres erreurs détectables seulement à l'édition des liens).

    • Le comportement est indéfini si un tel programme est exécuté.

  • comportement défini par l'implémentation - Le comportement du programme varie selon les implémentations, et l'implémentation conforme doit documenter les effets de chaque comportement.

    • Par exemple, le type de std::size_t ou le nombre de bits d'un octet, ou le texte de std::bad_alloc::what.
    • Un sous-ensemble du comportement défini par l'implémentation est le comportement spécifique à la locale, qui dépend de la locale fournie par l'implémentation.

  • comportement non spécifié - Le comportement du programme varie selon les implémentations, et l'implémentation conforme n'est pas tenue de documenter les effets de chaque comportement.

    • Par exemple, l'ordre d'évaluation, le fait que des littéraux de chaîne identiques soient distincts, la quantité de surcharge d'allocation des tableaux, etc.
    • Chaque comportement non spécifié produit l'un d'un ensemble de résultats valides.
  • comportement erroné - Le comportement (incorrect) que l'implémentation est encouragée à diagnostiquer.
  • Un comportement erroné résulte toujours d'un code de programme incorrect.
  • L'évaluation d'une expression constante ne produit jamais de comportement erroné.
  • Si l'exécution contient une opération spécifiée comme ayant un comportement erroné, l'implémentation est autorisée et encouragée à émettre un diagnostic, et peut arrêter l'exécution à un moment non spécifié après cette opération.
  • Une implémentation peut émettre un diagnostic si elle peut déterminer qu'un comportement erroné est atteignable selon un ensemble d'hypothèses propres à l'implémentation sur le comportement du programme, ce qui peut produire des faux positifs.

Exemples de comportements erronés

#include <cassert>
#include <cstring>

void f()
{
    int d1, d2;       // d1, d2 ont des valeurs erronées
    int e1 = d1;      // comportement erroné
    int e2 = d1;      // comportement erroné
    assert(e1 == e2); // holds
    assert(e1 == d1); // holds, comportement erroné
    assert(e2 == d1); // holds, comportement erroné

    std::memcpy(&d2, &d1, sizeof(int)); // pas de comportement erroné, mais
                                        // d2 a une valeur erronée

    assert(e1 == d2); // holds, comportement erroné
    assert(e2 == d2); // holds, comportement erroné
}

unsigned char g(bool b)
{
    unsigned char c;     // c a une valeur erronée
    unsigned char d = c; // pas de comportement erroné, mais d a une valeur erronée
    assert(c == d);      // holds, les deux promotions intégrales ont un comportement erroné
    int e = d;           // comportement erroné
    return b ? d : 0;    // comportement erroné si b est vrai
}

(depuis C++26)

  • comportement indéfini - Il n'existe aucune restriction sur le comportement du programme.
    • Quelques exemples de comportement indéfini sont les courses de données, les accès mémoire en dehors des bornes d'un tableau, le dépassement de capacité des entiers signés, le déréférencement d'un pointeur nul, plus d'une modification du même scalaire dans une expression [sans aucun point de séquence intermédiaire (jusqu'à C++11) | qui est non séquencée (depuis C++11)], l'accès à un objet via un pointeur d'un type différent, etc.
    • Les implémentations ne sont pas tenues de diagnostiquer le comportement indéfini (bien que de nombreuses situations simples soient diagnostiquées), et le programme compilé n'est pas tenu de faire quoi que ce soit de significatif.
  • comportement indéfini à l'exécution - Comportement indéfini sauf lorsqu'il se produit pendant l'évaluation d'une expression en tant qu'expression constante de base.

(depuis C++11)

UB et optimisation

Parce que les programmes C++ corrects sont exempts de comportement indéfini, les compilateurs peuvent produire des résultats inattendus lorsqu'un programme qui présente réellement un UB est compilé avec l'optimisation activée :

Par exemple,

Dépassement de capacité signé

int foo(int x)
{
    return x + 1 > x; // soit vrai, soit UB dû au dépassement de capacité signé
}

peut être compilé comme (démo)

foo(int):
        mov     eax, 1
        ret

Accès hors bornes

int table[4] = {};
bool exists_in_table(int v)
{
    // renvoie true dans l'une des 4 premières itérations, ou UB dû à un accès hors bornes
    for (int i = 0; i <= 4; i++)
        if (table[i] == v)
            return true;
    return false;
}

Peut être compilé comme (démo)

exists_in_table(int):
        mov     eax, 1
        ret

Scalaire non initialisé

std::size_t f(int x)
{
    std::size_t a;
    if (x) // soit x non nul, soit UB
        a = 42;
    return a;
}

Peut être compilé comme (démo)

f(int):
        mov     eax, 42
        ret

La sortie présentée a été observée avec une version plus ancienne de gcc

#include <cstdio>

int main()
{
    bool p; // variable locale non initialisée
    if (p)  // accès UB à un scalaire non initialisé
        std::puts("p is true");
    if (!p) // accès UB à un scalaire non initialisé
        std::puts("p is false");
}

Sortie possible :

p is true
p is false

Scalaire invalide

int f()
{
    bool b = true;
    unsigned char* p = reinterpret_cast<unsigned char*>(&b);
    *p = 10;
    // la lecture de b est désormais UB
    return b == 0;
}

Peut être compilé comme (démo)

f():
        mov     eax, 11
        ret

Déréférencement d'un pointeur nul

Les exemples montrent la lecture du résultat du déréférencement d'un pointeur nul.

int foo(int* p)
{
    int x = *p;
    if (!p)
        return x; // Soit UB ci-dessus, soit cette branche n'est jamais prise
    else
        return 0;
}

int bar()
{
    int* p = nullptr;
    return *p; // UB inconditionnel
}

peut être compilé comme (démo)

foo(int*):
        xor     eax, eax
        ret
bar():
        ret

Accès à un pointeur passé à std::realloc

Choisissez clang pour observer la sortie présentée

#include <cstdlib>
#include <iostream>

int main()
{
    int* p = (int*)std::malloc(sizeof(int));
    int* q = (int*)std::realloc(p, sizeof(int));
    *p = 1; // accès UB à un pointeur qui a été passé à realloc
    *q = 2;
    if (p == q) // accès UB à un pointeur qui a été passé à realloc
        std::cout << *p << *q << '\n';
}

Boucle infinie sans effets de bord

Choisissez clang ou la dernière version de gcc pour observer la sortie présentée.

#include <iostream>

bool fermat()
{
    const int max_value = 1000;

    // Une boucle infinie non triviale sans effets de bord est UB
    for (int a = 1, b = 1, c = 1; true; )
    {
        if (((a * a * a) == ((b * b * b) + (c * c * c))))
            return true; // disproved :()
        a++;
        if (a > max_value)
        {
            a = 1;
            b++;
        }
        if (b > max_value)
        {
            b = 1;
            c++;
        }
        if (c > max_value)
            c = 1;
    }

    return false; // non réfuté
}

int main()
{
    std::cout << "Fermat's Last Theorem ";
    fermat()
        ? std::cout << "has been disproved!\n"
        : std::cout << "has not been disproved.\n";
}

Sortie possible :

Fermat's Last Theorem has been disproved!

Mal formé avec message de diagnostic

Notez que les compilateurs sont autorisés à étendre le langage d'une manière qui donne un sens aux programmes mal formés. La seule chose que la norme C++ exige dans ces cas est un message de diagnostic (avertissement du compilateur), sauf si le programme est « mal formé, aucun diagnostic requis ».

Par exemple, à moins que les extensions du langage ne soient désactivées via --pedantic-errors, GCC compilera l'exemple suivant avec seulement un avertissement alors qu'il apparaît dans la norme C++ comme exemple d'« erreur » (voir aussi GCC Bugzilla #55783)

#include <iostream>

// Modification d'exemple, ne pas utiliser constant
double a{1.0};

// Norme C++23, §9.4.5 List-initialization [dcl.init.list], Exemple #6 :
struct S
{
    // aucun constructeur à liste d'initialisation
    S(int, double, double); // #1
    S();                    // #2
    // ...
};

S s1 = {1, 2, 3.0}; // OK, appeler #1
S s2{a, 2, 3}; // error: narrowing
S s3{}; // OK, appeler #2
// — fin de l'exemple]

S::S(int, double, double) {}
S::S() {}

int main()
{
    std::cout << "All checks have passed.\n";
}

Sortie possible :

main.cpp:17:6: error: type 'double' cannot be narrowed to 'int' in initializer ⮠
list [-Wc++11-narrowing]

     ^
