Ajout de déclarations dans std

Il s'agit d'un comportement indéfini que d'ajouter des déclarations ou des définitions à l'espace de noms std ou à tout espace de noms imbriqué dans std, à quelques exceptions près indiquées ci-dessous.

#include <utility>

namespace std
{
    // une définition de fonction ajoutée à l'espace de noms std : comportement indéfini
    pair<int, int> operator+(pair<int, int> a, pair<int, int> b)
    {
        return {a.first + b.first, a.second + b.second};
    }
}

Ajout de spécialisations de modèles

Modèles de classes

Il est permis d'ajouter des spécialisations de modèles pour tout modèle de classe de la bibliothèque standard dans l'espace de noms std uniquement si la déclaration dépend d'au moins un type défini par le programme et si la spécialisation satisfait toutes les exigences du modèle d'origine, sauf lorsque de telles spécialisations sont interdites.

// Obtenir la déclaration du modèle primaire std::hash.
// Nous n'avons pas le droit de la déclarer nous-mêmes.
// <typeindex> garantit de fournir une telle déclaration,
// et son inclusion coûte beaucoup moins cher que celle de <functional>.

#include <typeindex>

// Spécialiser std::hash afin que MyType puisse être utilisé comme clé dans
// std::unordered_set et std::unordered_map.  Ouvrir l'espace de noms
// std peut introduire accidentellement un comportement indéfini, et n'est pas
// nécessaire pour spécialiser des modèles de classe.
template<>
struct std::hash<MyType>
{
    std::size_t operator()(const MyType& t) const { return t.hash(); }
};

  • La spécialisation du modèle std::complex pour tout type autre que float, double et long double est non spécifiée.

  • Les spécialisations de std::numeric_limits doivent définir tous les membres déclarés [static const (jusqu'à C++11) | static constexpr (depuis C++11)] dans le modèle primaire, de manière à pouvoir être utilisés comme expressions constantes intégrales.

  • Aucun des modèles définis dans <type_traits> ne peut être spécialisé pour un type défini par le programme, sauf pour std::common_typeet std::basic_common_reference (depuis C++20). Cela inclut les traits de types et le modèle de classe std::integral_constant.

  • Les spécialisations de std::hash pour les types définis par le programme doivent satisfaire les exigences Hash.

  • Les spécialisations de std::atomic doivent avoir un constructeur de copie supprimé, un opérateur d'affectation par copie supprimé et un constructeur de valeur constexpr.

  • Les spécialisations de std::shared_ptr et std::weak_ptr doivent être CopyConstructible et CopyAssignable. De plus, les spécialisations de std::shared_ptr doivent être LessThanComparable et convertibles en bool.

  • Les spécialisations de std::istreambuf_iterator doivent avoir un constructeur de copie trivial, un constructeur par défaut constexpr et un destructeur trivial.

(depuis C++11)

  • std::unary_function et std::binary_function ne peuvent pas être spécialisés.

(jusqu'à C++17)

Modèles de variables

Il s'agit d'un comportement indéfini que de déclarer une spécialisation complète ou partielle de tout modèle de variable de la bibliothèque standard, sauf lorsque cela est explicitement autorisé.

  • Les spécialisations de std::disable_sized_sentinel_for, std::ranges::disable_sized_range, std::ranges::enable_view et std::ranges::enable_borrowed_range doivent être utilisables dans des expressions constantes et avoir le type const bool. Et
  • std::disable_sized_sentinel_for peut être spécialisé pour les types d'objets non tableaux qualifiés cv S et I, dont au moins un est un type défini par le programme.
  • std::ranges::disable_sized_range, std::ranges::enable_view et std::ranges::enable_borrowed_range peuvent être spécialisés pour les types définis par le programme qualifiés cv.
  • Chaque modèle de variable de constante mathématique peut être partiellement ou explicitement spécialisé, à condition que la spécialisation dépende d'un type défini par le programme.

Autres restrictions

L'espace de noms std ne peut pas être déclaré comme espace de noms en ligne.

Restriction sur l'adressage

Le comportement d'un programme C++ est non spécifié (potentiellement mal formé) s'il tente explicitement ou implicitement de former un pointeur, une référence (pour les fonctions libres et les fonctions membres statiques) ou un pointeur vers membre (pour les fonctions membres non statiques) vers une fonction de la bibliothèque standard ou une instanciation d'un modèle de fonction de la bibliothèque standard, sauf si elle est désignée comme fonction adressable (voir ci-dessous).

Le code suivant était bien défini en C++17, mais conduit à des comportements non spécifiés et peut ne pas compiler depuis C++20 :

#include <cmath>
#include <memory>

int main()
{
    // par l'opérateur unaire &
    auto fptr0 = &static_cast<float(&)(float, float)>(std::betaf);

    // par std::addressof
    auto fptr1 = std::addressof(static_cast<float(&)(float, float)>(std::betaf));

    // par conversion implicite fonction-vers-pointeur
    auto fptr2 = static_cast<float(&)(float)>(std::riemann_zetaf);

    // en formant une référence
    auto& fref = static_cast<float(&)(float)>(std::riemann_zetaf);
}
