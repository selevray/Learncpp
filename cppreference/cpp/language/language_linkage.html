Liaison de langage

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Permet la liaison entre des unités de programme écrites dans différents langages de programmation.

Cela peut aussi servir à détacher une déclaration de son module. Voir Propriété des modules.

(depuis C++20)

| | | | extern string-literal { declaration-seq ﻿*(facultatif)* } | (1) | | | | extern string-literal declaration | (2) | | |

  1. Applique la spécification de langage string-literal à tous les types de fonctions, aux noms de fonctions à liaison externe et aux variables à liaison externe déclarés dans declaration-seq.

  2. Applique la spécification de langage string-literal à une seule déclaration ou définition.

  • string-literal — une chaîne littérale non évaluée qui nomme la liaison de langage requise
  • declaration-seq — une suite de déclarations, pouvant inclure des spécifications de liaison imbriquées
  • declaration — une déclaration

Explication

Chaque type de fonction, chaque nom de fonction à liaison externe et chaque nom de variable à liaison externe possède une propriété appelée liaison de langage. La liaison de langage encapsule l'ensemble des exigences nécessaires pour se lier à une unité de programme écrite dans un autre langage de programmation : convention d'appel, algorithme de décoration de noms (name decoration), etc.

Seules deux liaisons de langage sont garanties comme prises en charge :

  1. "C++", la liaison de langage par défaut.
  2. "C", qui permet de se lier à des fonctions écrites en langage C, et de définir, dans un programme C++, des fonctions pouvant être appelées depuis des unités écrites en C.
extern "C"
{
    int open(const char *path_name, int flags); // Déclaration de fonction C
}

int main()
{
    int fd = open("test.txt", 0); // appelle une fonction C depuis un programme C++
}

// Cette fonction C++ peut être appelée depuis du code C
extern "C" void handler(int)
{
    std::cout << "Callback invoked\n"; // Elle peut utiliser C++
}

La liaison de langage faisant partie de chaque type de fonction, les pointeurs vers des fonctions conservent également cette liaison de langage. La liaison de langage des types de fonctions (qui représente la convention d'appel) et celle des noms de fonctions (qui représente la décoration de noms) sont indépendantes l'une de l'autre :

extern "C" void f1(void(*pf)()); // déclare une fonction f1 à liaison C,
                             // qui renvoie void et prend un pointeur vers une fonction C
                             // qui renvoie void et ne prend aucun paramètre

extern "C" typedef void FUNC(); // déclare FUNC comme un type de fonction C renvoyant void
                                // et ne prenant aucun paramètre

FUNC f2;            // le nom f2 a une liaison C++, mais son type est une fonction C
extern "C" FUNC f3; // le nom f3 a une liaison C et son type est la fonction C void()
void (*pf2)(FUNC*); // le nom pf2 a une liaison C++, et son type est
                    // « pointeur vers une fonction C++ renvoyant void et prenant un
                    // argument de type 'pointeur vers la fonction C renvoyant void
                    // et ne prenant aucun paramètre' »

extern "C"
{
    static void f4(); // le nom de la fonction f4 a une liaison interne (pas de langage)
                      // mais le type de la fonction a une liaison de langage C
}

Si deux déclarations d'une même entité lui donnent des liaisons de langage différentes, le programme est mal formé ; aucun diagnostic n'est requis si aucune des deux déclarations n'est accessible depuis l'autre. Une redéclaration d'une entité sans spécification de liaison hérite de la liaison de langage de l'entité et de son type (s'il existe).

extern "C" int f();
extern "C++" int f(); // Erreur : liaisons de langage différentes

extern "C" int g();
int g(); // OK, a une liaison de langage C

int h(); // a une liaison de langage C++ par défaut
extern "C" int h(); // Erreur : liaisons de langage différentes

Règles particulières pour la liaison "C"

Lorsque des membres de classe, des fonctions amies avec une clause finale requires, (depuis C++20) ou des fonctions membres non statiques apparaissent dans un bloc de liaison "C", la liaison de leurs types reste "C++" (mais les types des paramètres, s'il y en a, restent "C") :

extern "C"
{
    class X
    {
        void mf();           // la fonction mf et son type ont une liaison de langage C++
        void mf2(void(*)()); // la fonction mf2 a une liaison de langage C++ ;
                             // le paramètre a pour type « pointeur vers fonction C »
    };
}

template<typename T>
struct A { struct B; };

extern "C"
{
    template<typename T>
    struct A<T>::B
    {
        friend void f(B*) requires true {} // liaison de langage C ignorée
    };
}

namespace Q
{
    extern "C" void f(); // non mal formé
}

Soit C une déclaration qui déclare une fonction ou une variable avec une liaison de langage "C". Si une autre déclaration D déclare une entité portant le même nom, et qu'elle satisfait l'une des conditions suivantes, C et D déclarent la même entité :

  • D déclare une variable appartenant à la portée globale.
  • Si C déclare une variable, D déclare aussi une variable.
  • Si C déclare une fonction, D déclare aussi une fonction.

Contrairement aux redéclarations ordinaires, C et D peuvent avoir des portées cibles différentes :

extern "C"
{
    int x;
    int f();
    int g() { return 1; }
}

namespace A
{
    int x;                // Erreur : redéfinit « x »
    int f();              // OK, redéclare « f »
    int g() { return 1; } // Erreur : redéfinit « g »
}

Toutefois, les restrictions applicables à de telles déclarations s'appliquent toujours, ce qui signifie qu'elles doivent soit déclarer toutes deux des fonctions, soit déclarer toutes deux des variables, et que les entités déclarées doivent avoir le même type :

namespace A
{
    extern "C" int x();
    extern "C" int y();
}

int x; // Erreur : redéclare « x » comme une entité d'un autre genre

namespace B
{
    void y(); // Erreur : redéclare « y » avec un type différent
}

Notes

Les spécifications de langage ne peuvent apparaître que dans la portée de l'espace de noms.

Les accolades de la spécification de langage n'établissent pas de portée.

Lorsque des spécifications de langage sont imbriquées, c'est la spécification la plus interne qui est en vigueur.

Une déclaration directement contenue dans une spécification de liaison de langage est traitée comme si elle contenait le spécificateur extern pour déterminer la liaison du nom déclaré et si elle est une définition.

extern "C" int x; // une déclaration et non une définition
// La ligne ci-dessus est équivalente à extern "C" { extern int x; }

extern "C" { int x; } // une déclaration et une définition

extern "C" double f();
static double f(); // erreur : conflit de liaison

extern "C" static void g(); // erreur : conflit de liaison

extern "C" permet d'inclure dans un programme C++ des fichiers d'en-tête contenant des déclarations de fonctions de la bibliothèque C, mais si ce même fichier d'en-tête est partagé avec un programme C, extern "C" (ce qui n'est pas permis en C) doit être masqué à l'aide d'un #ifdef approprié, généralement __cplusplus :

#ifdef __cplusplus
extern "C" int foo(int, int); // Le compilateur C++ voit ceci
#else
int foo(int, int);            // Le compilateur C voit ceci
#endif

Le seul compilateur moderne qui différencie les types de fonctions avec les liaisons de langage "C" et "C++" est Oracle Studio ; les autres ne permettent pas les surcharges qui ne diffèrent que par la liaison de langage, y compris les ensembles de surcharges requis par la norme C++ (std::qsort, std::bsearch, std::signal, std::atexit et std::at_quick_exit) : GCC bug 2316, Clang bug 6277, CWG issue 1555.

extern "C"   using c_predfun   = int(const void*, const void*);
extern "C++" using cpp_predfun = int(const void*, const void*);

// mal formé, mais accepté par la plupart des compilateurs
static_assert(std::is_same<c_predfun, cpp_predfun>::value,
              "C and C++ language linkages shall not differentiate function types.");

// les déclarations suivantes ne déclarent pas de surcharges dans la plupart des compilateurs
// car c_predfun et cpp_predfun sont considérés comme étant le même type
void qsort(void* base, std::size_t nmemb, std::size_t size, c_predfun*   compar);
void qsort(void* base, std::size_t nmemb, std::size_t size, cpp_predfun* compar);

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
CWG 4 C++98 les noms à liaison interne peuvent avoir des liaisons de langage limité aux noms à liaison externe
CWG 341 C++98 une fonction à liaison de langage "C" peut avoir le même nom qu'une variable globale le programme est mal formé dans ce cas (aucun diagnostic requis si elles apparaissent dans des unités de traduction différentes)
CWG 564 C++98 le programme était mal formé si deux déclarations ne différaient que par les spécifications de liaison de langage (c.-à-d. des chaînes littérales différentes après 'extern') ce sont plutôt les liaisons de langage effectives données par les déclarations qui sont comparées
CWG 2460 C++20 les fonctions amies avec une clause finale requires et une liaison de langage "C" présentaient des comportements conflictuels "C" liaison de langage est ignorée dans ce cas
CWG 2483 C++98 la liaison des types des fonctions membres statiques apparaissant dans des blocs de liaison "C" était "C++" la liaison est "C"
