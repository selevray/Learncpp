Spécificateurs de classe de stockage

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Les spécificateurs de classe de stockage font partie de la decl-specifier-seq de la syntaxe de déclaration d'un nom. Avec la portée du nom, ils contrôlent deux propriétés indépendantes du nom : sa durée de stockage et sa liaison.

Durée de stockage

La durée de stockage est la propriété d'un objet qui définit la durée de vie potentielle minimale du stockage contenant l'objet. La durée de stockage est déterminée par la construction utilisée pour créer l'objet et est l'une des suivantes :

  • durée de stockage statique
  • durée de stockage thread

(depuis C++11)

  • durée de stockage automatique
  • durée de stockage dynamique

Les durées de stockage statique, thread, (depuis C++11) et automatique sont associées aux objets introduits par des déclarations et aux objets temporaires. La durée de stockage dynamique est associée aux objets créés par une new expression ou aux objets créés implicitement.

Les catégories de durée de stockage s'appliquent également aux références.

La durée de stockage des sous-objets et des membres de référence est celle de leur objet complet.

Spécificateurs

Les mots-clés suivants sont des spécificateurs de classe de stockage ﻿:

  • auto

(jusqu'à C++11)

  • register

(jusqu'à C++17)

  • static
  • thread_local

(depuis C++11)

  • extern
  • mutable

Dans une decl-specifier-seq, il ne peut y avoir au plus qu'un spécificateur de classe de stockage, sauf que thread_local peut apparaître avec static ou extern (depuis C++11).

mutable n'a aucun effet sur la durée de stockage. Pour son usage, voir const/volatile.

D'autres spécificateurs de classe de stockage peuvent apparaître dans les decl-specifier-seq des déclarations suivantes :

Les unions anonymes peuvent aussi être déclarées avec static.

register est une indication que la variable ainsi déclarée sera fortement utilisée, afin que sa valeur puisse être stockée dans un registre du processeur. L'indication peut être ignorée, et dans la plupart des implémentations elle le sera si l'adresse de la variable est prise. Cet usage est obsolète.

(jusqu'à C++17)

Durée de stockage statique

Une variable satisfaisant toutes les conditions suivantes a une durée de stockage statique ﻿:

  • Elle appartient à une portée d'espace de noms ou est d'abord déclarée avec static ou extern.
  • Elle n'a pas de durée de stockage thread.

(depuis C++11)

Le stockage de ces entités dure pendant toute la durée du programme.

Durée de stockage thread

Toutes les variables déclarées avec thread_local ont une durée de stockage thread.

Le stockage de ces entités dure pendant la durée du thread dans lequel elles sont créées. Il existe un objet ou une référence distinct par thread, et l'utilisation du nom déclaré désigne l'entité associée au thread courant.

(depuis C++11)

Durée de stockage automatique

Les variables suivantes ont une durée de stockage automatique ﻿:

  • Les variables appartenant à une portée de bloc et qui ne sont pas explicitement déclarées static, thread_local, (depuis C++11) ou extern. Le stockage de ces variables dure jusqu'à la sortie du bloc dans lequel elles sont créées.
  • Les variables appartenant à une portée de paramètres (c'est-à-dire les paramètres de fonction). Le stockage d'un paramètre de fonction dure jusqu'immédiatement après sa destruction.

Durée de stockage dynamique

Les objets créés par les méthodes suivantes pendant l'exécution du programme ont une durée de stockage dynamique ﻿:

  • expressions new. Le stockage de ces objets est alloué par des fonctions d'allocation et désalloué par des fonctions de désallocation.
  • Création implicite par d'autres moyens. Le stockage de ces objets chevauche un stockage existant.
  • Objets d'exception. Le stockage de ces objets est alloué et désalloué de manière non spécifiée.

Liaison

Un nom peut avoir une liaison externe ﻿, liaison de module (depuis C++20), une liaison interne, ou aucune liaison :

  • Une entité dont le nom a une liaison externe peut être redéclarée dans une autre unité de traduction, et la redéclaration peut être rattachée à un module différent (depuis C++20).
  • Une entité dont le nom a une liaison de module peut être redéclarée dans une autre unité de traduction, à condition que la redéclaration soit rattachée au même module.

(depuis C++20)

  • Une entité dont le nom a une liaison interne peut être redéclarée dans une autre portée de la même unité de traduction.
  • Une entité dont le nom n'a aucune liaison ne peut être redéclarée que dans la même portée.

Les liaisons suivantes sont reconnues :

Aucune liaison

Les noms suivants déclarés dans une portée de bloc n'ont aucune liaison :

  • les variables qui ne sont pas explicitement déclarées extern (indépendamment du modificateur static) ;
  • les classes locales et leurs fonctions membres ;
  • les autres noms déclarés dans une portée de bloc, tels que les typedef, les énumérations et les énumérateurs.

Les noms qui ne sont pas spécifiés avec une liaison externe, de module, (depuis C++20) ou interne n'ont pas non plus de liaison, quelle que soit la portée dans laquelle ils sont déclarés.

Liaison interne

Les noms suivants déclarés dans une portée d'espace de noms ont une liaison interne :

  • variables, modèles de variables (depuis C++14), fonctions ou modèles de fonctions déclarés static ;
  • non-modèles *(depuis C++14)*variables de type qualifié const non volatile, sauf si
  • elles sont inline,

(depuis C++17)

  • elles sont déclarées dans la portée d'une unité d'interface de module (en dehors du fragment de module privé, le cas échéant) ou d'une partition de module,

(depuis C++20)

  • elles sont explicitement déclarées extern, ou

  • elles ont été déclarées précédemment et la déclaration antérieure n'avait pas de liaison interne ;

  • membres de données des unions anonymes.

De plus, tous les noms déclarés dans des espaces de noms anonymes ou dans un espace de noms situé dans un espace de noms anonyme, même ceux explicitement déclarés extern, ont une liaison interne.

(depuis C++11)

Liaison externe

Les variables et fonctions à liaison externe ont aussi une liaison de langage, qui permet de lier des unités de traduction écrites dans différents langages de programmation.

Les noms suivants déclarés dans une portée d'espace de noms ont une liaison externe, sauf s'ils sont déclarés dans un espace de noms anonymeou si leurs déclarations sont rattachées à un module nommé et ne sont pas exportées (depuis C++20) :

  • variables et fonctions non listées ci-dessus (c'est-à-dire les fonctions non déclarées static, les variables non const non déclarées static, et les variables déclarées extern) ;
  • enumerations;
  • noms de classes, de leurs fonctions membres, de leurs membres de données statiques (const ou non), des classes et énumérations imbriquées, et des fonctions introduites pour la première fois par des déclarations friend dans les corps de classes ;
  • noms de tous les modèles non listés ci-dessus (c'est-à-dire les modèles de fonctions non déclarés static).

Les noms suivants, déclarés pour la première fois dans une portée de bloc, ont une liaison externe :

  • noms des variables déclarées extern ;
  • noms de fonctions.

Liaison de module

Les noms déclarés dans une portée d'espace de noms ont une liaison de module si leurs déclarations sont rattachées à un module nommé et ne sont pas exportées, et n'ont pas de liaison interne.

(depuis C++20)

Variables statiques de bloc

Les variables de bloc à durée de stockage statiqueou thread (depuis C++11) sont initialisées la première fois que le flot d'exécution passe par leur déclaration (sauf si leur initialisation est une initialisation nulle ou constante, qui peut être effectuée avant la première entrée dans le bloc). Lors de tous les appels suivants, la déclaration est ignorée.

  • Si l'initialisation lève une exception, la variable n'est pas considérée comme initialisée, et l'initialisation sera de nouveau tentée la prochaine fois que le flot d'exécution passera par la déclaration.
  • Si l'initialisation entre récursivement dans le bloc où la variable est en cours d'initialisation, le comportement est indéfini.
  • Si plusieurs threads tentent d'initialiser simultanément la même variable locale statique, l'initialisation a lieu exactement une fois (un comportement similaire peut être obtenu pour des fonctions arbitraires avec std::call_once).
  • Les implémentations usuelles de cette fonctionnalité utilisent des variantes du motif de verrouillage à double vérification, qui réduit la surcharge à l'exécution pour les variables locales statiques déjà initialisées à une seule comparaison booléenne non atomique.

(depuis C++11)

Le destructeur d'une variable de bloc à durée de stockage statique est appelé à la fin du programme, mais seulement si l'initialisation a réussi.

Les variables à durée de stockage statique dans toutes les définitions d'une même fonction inline (qui peut être implicitement inline) désignent toutes le même objet défini dans une seule unité de traduction, tant que la fonction a une liaison externe.

Entités locales à l'unité de traduction

Le concept d'entités locales à l'unité de traduction est normalisé en C++20, voir cette page pour plus de détails.

Une entité est locale à l'unité de traduction (ou TU-locale en abrégé) si

  • elle a un nom à liaison interne, ou
  • elle n'a pas de nom ayant une liaison et est introduite dans la définition d'une entité locale à l'unité de traduction, ou
  • c'est un modèle ou une spécialisation de modèle dont l'argument de modèle ou la déclaration de modèle utilise une entité locale à l'unité de traduction.

Des situations graves (généralement une violation de l'ODR) peuvent se produire si le type d'une entité non locale à l'unité de traduction dépend d'une entité locale à l'unité de traduction, ou si une déclaration de, ou un guide de déduction pour, (depuis C++17) une entité non locale à l'unité de traduction désigne une entité locale à l'unité de traduction en dehors de son

  • corps de fonction pour une fonction non inline ou un modèle de fonction
  • initialiseur d'une variable ou d'un modèle de variable
  • déclarations friend dans une définition de classe
  • utilisation de la valeur d'une variable, si la variable est utilisable dans des expressions constantes

De telles utilisations sont interdites dans une unité d'interface de module (en dehors de son private-module-fragment, le cas échéant) ou dans une partition de module, et sont dépréciées dans tout autre contexte.

Une déclaration qui apparaît dans une unité de traduction ne peut pas désigner une entité locale à l'unité de traduction déclarée dans une autre unité de traduction qui n'est pas une unité d'en-tête. Une déclaration instanciée pour un modèle apparaît au point d'instanciation de la spécialisation.

(depuis C++20)

Notes

Les noms situés dans la portée d'espace de noms de plus haut niveau (portée de fichier en C) qui sont const et non extern ont une liaison externe en C, mais une liaison interne en C++.

Depuis C++11, auto n'est plus un spécificateur de classe de stockage ; il sert à indiquer la déduction de type.

En C, l'adresse d'une variable register ne peut pas être prise, mais en C++, une variable déclarée register est sémantiquement indiscernable d'une variable déclarée sans aucun spécificateur de classe de stockage.

(jusqu'à C++17)

En C++, contrairement au C, les variables ne peuvent pas être déclarées register.

(depuis C++17)

Les noms de variables thread_local à liaison interne ou externe référencées depuis des portées différentes peuvent désigner la même instance ou des instances différentes, selon que le code s'exécute dans le même thread ou dans des threads différents.

Le mot-clé extern peut aussi servir à spécifier une liaison de langage et des déclarations d'instanciation explicite de modèles, mais ce n'est pas un spécificateur de classe de stockage dans ces cas (sauf lorsqu'une déclaration est directement contenue dans une spécification de liaison de langage, auquel cas elle est traitée comme si elle contenait le spécificateur extern).

Les spécificateurs de classe de stockage, à l'exception de thread_local, ne sont pas autorisés sur les spécialisations explicites et les instanciations explicites :

template<class T>
struct S
{
    thread_local static int tlm;
};

template<>
thread_local int S<float>::tlm = 0; // « static » n'apparaît pas ici

Une variable de modèle const (pouvant être impliquée par constexpr) avait auparavant une liaison interne par défaut, ce qui était incohérent avec les autres entités templatisées. Le rapport de défaut CWG2387 a corrigé cela.

(depuis C++14)

inline sert de contournement au CWG2387 en donnant une liaison externe par défaut. C'est pourquoi le inline a été ajouté à de nombreux modèles de variables puis retiré après l'acceptation de CWG2387. Les implémentations de la bibliothèque standard doivent aussi utiliser inline tant qu'un compilateur pris en charge n'a pas implémenté CWG2387. Voir GCC Bugzilla #109126 et MSVC STL PR #4546.

(depuis C++17)

Mots-clés

auto, register, static, extern, thread_local, mutable

Exemple

#include <iostream>
#include <mutex>
#include <string>
#include <thread>

thread_local unsigned int rage = 1;
std::mutex cout_mutex;

void increase_rage(const std::string& thread_name)
{
    ++rage; // la modification hors d'un verrou est acceptable ; il s'agit d'une variable à stockage thread_local
    std::lock_guard<std::mutex> lock(cout_mutex);
    std::cout << "Rage counter for " << thread_name << ": " << rage << '\n';
}

int main()
{
    std::thread a(increase_rage, "a"), b(increase_rage, "b");

    {
        std::lock_guard<std::mutex> lock(cout_mutex);
        std::cout << "Rage counter for main: " << rage << '\n';
    }

    a.join();
    b.join();
}

Sortie possible :

Rage counter for a: 2
Rage counter for main: 1
Rage counter for b: 2
