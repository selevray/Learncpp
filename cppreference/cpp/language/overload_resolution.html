Résolution de surcharge

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Pour compiler un appel de fonction, le compilateur doit d'abord effectuer une recherche de nom, qui, pour les fonctions, peut impliquer une recherche dépendante des arguments, et pour les modèles de fonction peut être suivie d'une déduction d'arguments de modèle.

Si le nom désigne plus d'une entité, il est dit surchargé, et le compilateur doit déterminer quelle surcharge appeler. En termes simples, la surcharge dont les paramètres correspondent le plus étroitement aux arguments est celle qui est appelée.

Plus précisément, la résolution de surcharge procède selon les étapes suivantes :

  1. Construction de l'ensemble des fonctions candidates.
  2. Réduction de l'ensemble aux seules fonctions viables.
  3. Analyse de l'ensemble pour déterminer l'unique meilleure fonction viable (cela peut impliquer le classement des séquences de conversion implicites).
void f(long);
void f(float);

f(0L); // appelle f(long)
f(0);  // erreur : surcharge ambiguë

Outre les appels de fonction, les noms de fonctions surchargées peuvent apparaître dans plusieurs contextes supplémentaires, où des règles différentes s'appliquent : voir Adresse d'une fonction surchargée.

Si une fonction ne peut pas être sélectionnée par la résolution de surcharge, elle ne peut pas être utilisée (par ex. c'est une entité basée sur un modèle dont la contrainte n'est pas satisfaite).

Fonctions candidates

Avant que la résolution de surcharge ne commence, les fonctions sélectionnées par la recherche de nom et la déduction d'arguments de modèle sont combinées pour former l'ensemble des fonctions candidates. Les détails exacts dépendent du contexte dans lequel la résolution de surcharge aura lieu.

Appel d'une fonction nommée

Si E dans une expression d'appel de fonction E(args) désigne un ensemble de fonctions surchargées et/ou de modèles de fonction (mais pas d'objets appelables), les règles suivantes s'appliquent :

  • Si l'expression E a la forme PA->B ou A.B (où A a le type de classe cv T), alors B est recherché comme fonction membre de T. Les déclarations de fonctions trouvées par cette recherche sont les fonctions candidates. La liste d'arguments, pour les besoins de la résolution de surcharge, comporte l'argument objet implicite de type cv T.
  • Si l'expression E est une expression primaire, le nom est recherché selon les règles normales des appels de fonction (ce qui peut impliquer une ADL). Les déclarations de fonctions trouvées par cette recherche sont (en raison du fonctionnement de la recherche) soit :
    • toutes des fonctions non membres (auquel cas la liste d'arguments pour la résolution de surcharge est exactement la liste d'arguments utilisée dans l'expression d'appel de fonction)
    • toutes des fonctions membres d'une classe T, auquel cas, si this est dans la portée et est un pointeur vers T ou vers une classe dérivée de T, *this est utilisé comme argument objet implicite. Sinon (si this n'est pas dans la portée ou ne pointe pas vers T), un faux objet de type T est utilisé comme argument objet implicite, et si la résolution de surcharge sélectionne ensuite une fonction membre non statique, le programme est mal formé.

Appel d'un objet de classe

Si E dans une expression d'appel de fonction E(args) a le type de classe cv T, alors

  • Les opérateurs d'appel de fonction de T sont obtenus par une recherche ordinaire du nom operator() dans le contexte de l'expression (E).operator(), et chaque déclaration trouvée est ajoutée à l'ensemble des fonctions candidates.
  • Pour chaque fonction de conversion définie par l'utilisateur non explicit dans T ou dans une base de T (sauf si masquée), dont les qualificateurs cv sont identiques ou plus stricts que ceux de T, et où la fonction de conversion convertit en :
    • pointeur vers fonction
    • référence vers pointeur vers fonction
    • référence vers fonctionalors une fonction d'appel substitut de nom unique dont le premier paramètre est le résultat de la conversion, dont les paramètres restants sont la liste de paramètres acceptée par le résultat de la conversion, et dont le type de retour est le type de retour du résultat de la conversion, est ajoutée à l'ensemble des fonctions candidates. Si cette fonction substitut est sélectionnée par la résolution de surcharge ultérieure, alors la fonction de conversion définie par l'utilisateur sera appelée, puis le résultat de la conversion sera appelé.

Dans tous les cas, la liste d'arguments pour la résolution de surcharge est la liste d'arguments de l'expression d'appel de fonction précédée de l'argument objet implicite E (lorsqu'on fait correspondre la fonction substitut, la conversion définie par l'utilisateur convertira automatiquement l'argument objet implicite en premier argument de la fonction substitut).

int f1(int);
int f2(float);

struct A
{
    using fp1 = int(*)(int);
    operator fp1() { return f1; } // fonction de conversion vers un pointeur sur fonction
    using fp2 = int(*)(float);
    operator fp2() { return f2; } // fonction de conversion vers un pointeur sur fonction
} a;

int i = a(1); // appelle f1 via le pointeur renvoyé par la fonction de conversion

Appel d'un opérateur surchargé

Si au moins un des arguments d'un opérateur dans une expression a un type de classe ou un type énumération, les opérateurs intégrés et les surcharges d'opérateurs définies par l'utilisateur participent tous deux à la résolution de surcharge, l'ensemble des fonctions candidates étant sélectionné comme suit :

Pour un opérateur unaire @ dont l'argument a le type T1 (après suppression des qualificateurs cv), ou un opérateur binaire @ dont l'opérande gauche a le type T1 et l'opérande droit le type T2 (après suppression des qualificateurs cv), les ensembles suivants de fonctions candidates sont préparés :

  1. candidats membres : si T1 est une classe complète ou une classe en cours de définition, l'ensemble des candidats membres est le résultat de la recherche de nom qualifiée de T1::operator@. Dans tous les autres cas, l'ensemble des candidats membres est vide.

  2. candidats non membres : pour les opérateurs dont la surcharge d'opérateurs permet une forme non membre, toutes les déclarations trouvées par recherche de nom non qualifiée de operator@ dans le contexte de l'expression (qui peut impliquer une ADL), à l'exception des déclarations de fonctions membres, qui sont ignorées et n'empêchent pas la recherche de se poursuivre dans la portée englobante suivante. Si les deux opérandes d'un opérateur binaire ou l'unique opérande d'un opérateur unaire ont un type énumération, les seules fonctions de l'ensemble de recherche qui deviennent des candidats non membres sont celles dont le paramètre a ce type énumération (ou une référence vers ce type énumération)

  3. candidats intégrés : pour operator,, l'unaire operator& et operator->, l'ensemble des candidats intégrés est vide. Pour les autres opérateurs, les candidats intégrés sont ceux listés dans les pages des opérateurs intégrés tant que tous les opérandes peuvent être implicitement convertis en leurs paramètres. Si un candidat intégré a la même liste de paramètres qu'un candidat non membreou candidat non membre réécrit (depuis C++20) qui n'est pas une spécialisation de modèle de fonction, il n'est pas ajouté à la liste des candidats intégrés. Lorsque les opérateurs d'affectation intégrés sont considérés, les conversions de leurs premiers paramètres sont restreintes : seules les séquences de conversion standard sont considérées.

  1. candidats réécrits :
  • Pour les quatre expressions d'opérateurs relationnels x < y, x <= y, x > y et x >= y, tous les operator<=> membres, non membres et intégrés trouvés sont ajoutés à l'ensemble.
  • Pour les quatre expressions d'opérateurs relationnels x < y, x <= y, x > y et x >= y, ainsi que l'expression de comparaison à trois voies x <=> y, un candidat synthétisé avec l'ordre des deux paramètres inversé est ajouté pour chaque operator<=> membre, non membre et intégré trouvé.
  • Pour x != y, tous les operator== membres, non membres et intégrés trouvés sont ajoutés à l'ensemble, sauf s'il existe un operator!= correspondant.
  • Pour les expressions d'opérateurs d'égalité x == y et x != y, un candidat synthétisé avec l'ordre des deux paramètres inversé est ajouté pour chaque operator== membre, non membre et intégré trouvé, sauf s'il existe un operator!= correspondant.

Dans tous les cas, les candidats réécrits ne sont pas considérés dans le contexte de l'expression réécrite. Pour tous les autres opérateurs, l'ensemble des candidats réécrits est vide.

(depuis C++20)

L'ensemble des fonctions candidates soumis à la résolution de surcharge est l'union des ensembles ci-dessus. La liste d'arguments pour la résolution de surcharge est constituée des opérandes de l'opérateur, à l'exception de operator->, dont le second opérande n'est pas un argument de l'appel de fonction (voir opérateur d'accès membre).

struct A
{
    operator int();              // conversion définie par l'utilisateur
};
A operator+(const A&, const A&); // opérateur défini par l'utilisateur non membre

void m()
{
    A a, b;
    a + b; // candidats membres : aucun
           // candidats non membres : operator+(a, b)
           // candidats intégrés : int(a) + int(b)
           // la résolution de surcharge choisit operator+(a, b)
}

Si la résolution de surcharge sélectionne un candidat intégré, la séquence de conversion définie par l'utilisateur à partir d'un opérande de type classe ne doit pas avoir une seconde séquence de conversion standard : la fonction de conversion définie par l'utilisateur doit fournir directement le type d'opérande attendu :

struct Y { operator int*(); }; // Y est convertible en int*
int *a = Y() + 100.0;          // erreur : pas d'operator+ entre un pointeur et un double

Pour operator,, l'unaire operator& et operator->, si l'ensemble des fonctions candidates ne contient aucune fonction viable (voir ci-dessous), l'opérateur est réinterprété comme intégré.

Si un candidat operator<=> réécrit est sélectionné par la résolution de surcharge pour un opérateur @, x @ y est interprété comme l'expression réécrite : 0 @ (y <=> x) si le candidat sélectionné est un candidat synthétisé avec l'ordre des paramètres inversé, ou (x <=> y) @ 0 sinon, en utilisant le candidat operator<=> réécrit sélectionné.

Si un candidat operator== réécrit est sélectionné par la résolution de surcharge pour un opérateur @ (qui est soit ==, soit !=), son type de retour doit être (éventuellement qualifié cv) bool, et x @ y est interprété comme l'expression réécrite : y == x ou !(y == x) si le candidat sélectionné est un candidat synthétisé avec l'ordre des paramètres inversé, ou !(x == y) sinon, en utilisant le candidat operator== réécrit sélectionné.

La résolution de surcharge dans ce cas comporte un dernier critère de départage qui préfère les candidats non réécrits aux candidats réécrits, et préfère les candidats réécrits non synthétisés aux candidats réécrits synthétisés.

Cette recherche avec l'ordre inversé des arguments permet d'écrire simplement operator<=>(std::string, const char*) et operator==(std::string, const char*) pour générer toutes les comparaisons entre std::string et const char*, dans les deux sens. Voir comparaisons par défaut pour plus de détails.

(depuis C++20)

Initialisation par constructeur

Lorsqu'un objet de type classe est initialisé directement ou initialisé par défaut(y compris l'initialisation par défaut dans le contexte de l'initialisation par copie de liste) (depuis C++11), les fonctions candidates sont tous les constructeurs de la classe initialisée. La liste d'arguments est la liste d'expressions de l'initialiseur.

Sinon, les fonctions candidates sont tous les constructeurs convertisseurs de la classe initialisée. La liste d'arguments est l'expression de l'initialiseur.

Pour l'initialisation par défaut dans le contexte de l'initialisation par copie de liste, si un explicit constructeur est choisi, l'initialisation est mal formée.

(depuis C++11)

Initialisation par copie par conversion

Si l'initialisation par copie d'un objet de type classe nécessite l'appel d'une conversion définie par l'utilisateur pour convertir l'expression d'initialisation de type cv S vers le type cv T de l'objet initialisé, les fonctions suivantes sont des fonctions candidates :

  • tous les constructeurs convertisseurs de T
  • les fonctions de conversion non explicit de S et de ses classes de base (sauf si masquées) vers T ou une classe dérivée de T, ou une référence vers celle-ci. Si cette initialisation par copie fait partie de la séquence d'initialisation directe de cv T (initialisation d'une référence devant être liée au premier paramètre d'un constructeur qui prend une référence vers cv T), alors les fonctions de conversion explicites sont également prises en compte.

Dans les deux cas, la liste d'arguments, pour la résolution de surcharge, se compose d'un seul argument, qui est l'expression d'initialisation, laquelle sera comparée au premier argument du constructeur ou à l'argument objet implicite de la fonction de conversion.

Initialisation non de classe par conversion

Lorsque l'initialisation d'un objet de type non classe cv1 T nécessite une fonction de conversion définie par l'utilisateur pour convertir depuis une expression d'initialisation de type classe cv S, les fonctions suivantes sont candidates :

  • les fonctions de conversion définies par l'utilisateur non explicites de S et de ses classes de base (sauf si masquées) qui produisent le type T ou un type convertible en T par une séquence de conversions standard, ou une référence vers un tel type. Les qualificatifs cv du type retourné sont ignorés pour la sélection des fonctions candidates.
  • si c'est une initialisation directe, les fonctions de conversion définies par l'utilisateur explicites de S et de ses classes de base (sauf si masquées) qui produisent le type T ou un type convertible en T par une conversion de qualification, ou une référence vers un tel type, sont également prises en compte.

Dans les deux cas, la liste d'arguments, pour la résolution de surcharge, se compose d'un seul argument, qui est l'expression d'initialisation, laquelle sera comparée à l'argument objet implicite de la fonction de conversion.

Initialisation de référence par conversion

Lors de l'initialisation de référence, où la référence vers cv1 T est liée à la valeur lvalue ou rvalue résultant d'une conversion de l'expression d'initialisation de type classe cv2 S, les fonctions suivantes sont retenues pour l'ensemble des candidats :

  • Les fonctions de conversion définies par l'utilisateur non explicites de S et de ses classes de base (sauf si masquées) vers le type

    • (lors d'une conversion vers une lvalue) référence lvalue vers cv2 T2
    • (lors d'une conversion vers une rvalue ou une lvalue de type fonction) cv2 T2 ou référence rvalue vers cv2 T2 où cv2 T2 est compatible en référence avec cv1 T.

  • Pour l'initialisation directe, les fonctions de conversion définies par l'utilisateur explicites sont également prises en compte si T2 est du même type que T ou peut être converti vers le type T par une conversion de qualification.

Dans les deux cas, la liste d'arguments, pour la résolution de surcharge, se compose d'un seul argument, qui est l'expression d'initialisation, laquelle sera comparée à l'argument objet implicite de la fonction de conversion.

Initialisation par liste

Lorsqu'un objet de type classe non agrégat T est initialisé par liste, une résolution de surcharge en deux phases a lieu.

  • à la phase 1, les fonctions candidates sont tous les constructeurs de T prenant une liste d'initialisation, et la liste d'arguments, pour la résolution de surcharge, se compose d'un seul argument de type liste d'initialisation
  • si la résolution de surcharge échoue à la phase 1, la phase 2 est entamée, où les fonctions candidates sont tous les constructeurs de T et la liste d'arguments, pour la résolution de surcharge, se compose des éléments individuels de la liste d'initialisation.

Si la liste d'initialisation est vide et que T possède un constructeur par défaut, la phase 1 est ignorée.

Lors de l'initialisation par copie de liste, si la phase 2 sélectionne un constructeur explicite, l'initialisation est mal formée (contrairement à toutes les initialisations par copie où les constructeurs explicites ne sont même pas pris en compte).

Règles supplémentaires pour les candidats modèles de fonction

Si la recherche de nom a trouvé un modèle de fonction, la déduction d'arguments de modèle et la vérification de tous les arguments de modèle explicites sont effectuées pour trouver les valeurs d'arguments de modèle (le cas échéant) pouvant être utilisées dans ce cas :

  • Si les deux réussissent, les arguments de modèle sont utilisés pour synthétiser les déclarations des spécialisations de modèle de fonction correspondantes, qui sont ajoutées à l'ensemble des candidats, et ces spécialisations sont traitées comme des fonctions non modèles, sauf indication contraire dans les règles de départage ci-dessous.
  • Si la déduction d'arguments échoue ou si la spécialisation de modèle de fonction synthétisée serait mal formée, aucune telle fonction n'est ajoutée à l'ensemble des candidats (voir SFINAE).

Si un nom désigne un ou plusieurs modèles de fonction et également un ensemble de fonctions non modèles surchargées, ces fonctions ainsi que les spécialisations générées à partir des modèles sont toutes des candidates.

Voir surcharge de modèles de fonction pour plus de détails.

Si un modèle de constructeur ou un modèle de fonction de conversion possède un spécificateur explicite conditionnel qui se trouve être dépendant de la valeur, après déduction, si le contexte requiert un candidat non explicite et que la spécialisation générée est explicite, elle est retirée de l'ensemble des candidats.

(depuis C++20)

Règles supplémentaires pour les candidats constructeurs

Les constructeurs de déplacement et opérateurs d'affectation par déplacement par défaut qui sont définis comme supprimés sont exclus de l'ensemble des fonctions candidates.

Un constructeur hérité de la classe C qui possède un premier paramètre de type « référence vers P » (y compris un tel constructeur instancié à partir d'un modèle) est exclu de l'ensemble des fonctions candidates lors de la construction d'un objet de type D si toutes les conditions suivantes sont satisfaites :

  • La liste d'arguments comporte exactement un argument.
  • C est lié par référence à P.
  • P est lié par référence à D.

(depuis C++11)

Règles supplémentaires pour les candidats fonctions membres

Si une fonction candidate est une fonction membre (statique ou non statique)qui ne possède pas de paramètre objet explicite (depuis C++23), mais pas un constructeur, elle est traitée comme si elle possédait un paramètre supplémentaire (paramètre objet implicite) qui représente l'objet pour lequel elle est appelée et qui apparaît avant le premier des paramètres effectifs.

De même, l'objet sur lequel une fonction membre est appelée est placé en tête de la liste d'arguments comme argument objet implicite.

Pour les fonctions membres de la classe X, le type du paramètre objet implicite est affecté par les qualificatifs cv et les qualificatifs ref de la fonction membre, comme décrit dans fonctions membres.

Les fonctions de conversion définies par l'utilisateur sont considérées comme membres de l'argument objet implicite pour déterminer le type du paramètre objet implicite.

Les fonctions membres introduites dans une classe dérivée par une déclaration using sont considérées comme membres de la classe dérivée pour définir le type du paramètre objet implicite*.*

Pour les fonctions membres statiques, le paramètre objet implicite est considéré comme correspondant à tout objet : son type n'est pas examiné et aucune séquence de conversion n'est tentée pour lui.

(jusqu'à C++23)

Pour le reste de la résolution de surcharge, l'argument objet implicite est indiscernable des autres arguments, mais les règles spéciales suivantes s'appliquent au paramètre objet implicite :

Les conversions définies par l'utilisateur 1) ne peuvent pas être appliquées au paramètre objet implicite

Les rvalues 2) peuvent être liées à un paramètre objet implicite non const (sauf s'il s'agit d'une fonction membre qualifiée par ref) (depuis C++11) et n'affectent pas le classement des conversions implicites.

struct B { void f(int); };
struct A { operator B&(); };

A a;
a.B::f(1); // Erreur : les conversions définies par l'utilisateur ne peuvent pas être appliquées
           // au paramètre objet implicite
static_cast<B&>(a).f(1); // OK

Fonctions viables

Étant donné l'ensemble des fonctions candidates, construit comme décrit ci-dessus, l'étape suivante de la résolution de surcharge consiste à examiner les arguments et les paramètres pour réduire l'ensemble aux fonctions viables

Pour être incluse dans l'ensemble des fonctions viables, la fonction candidate doit satisfaire les conditions suivantes :

  1. S'il y a M arguments, la fonction candidate qui possède exactement M paramètres est viable

  2. Si la fonction candidate possède moins de M paramètres, mais possède un paramètre ellipse, elle est viable.

  3. Si la fonction candidate possède plus de M paramètres et que le M+1e paramètre ainsi que tous les paramètres suivants ont des arguments par défaut, elle est viable. Pour le reste de la résolution de surcharge, la liste des paramètres est tronquée à M.

  1. Si la fonction possède une contrainte associée, celle-ci doit être satisfaite

(depuis C++20)

  1. Pour chaque argument, il doit exister au moins une séquence de conversion implicite qui le convertit vers le paramètre correspondant.

  2. Si un paramètre possède un type référence, la liaison de référence est prise en compte à cette étape : si un argument rvalue correspond à un paramètre de référence lvalue non const, ou un argument lvalue correspond à un paramètre de référence rvalue, la fonction n'est pas viable.

Les conversions définies par l'utilisateur (à la fois les constructeurs convertisseurs et les fonctions de conversion définies par l'utilisateur) sont interdites de participer à une séquence de conversion implicite lorsque cela permettrait d'appliquer plus d'une conversion définie par l'utilisateur. Plus précisément, elles ne sont pas considérées si la cible de la conversion est le premier paramètre d'un constructeur ou le paramètre objet implicite d'une fonction de conversion définie par l'utilisateur, et que ce constructeur/cette fonction de conversion est candidat(e) pour

  • initialisation par copie d'une classe par conversion définie par l'utilisateur,
  • initialisation d'un type non classe par une fonction de conversion,
  • initialisation par fonction de conversion pour la liaison directe de référence,
  • initialisation par constructeur lors de la deuxième étape (initialisation directe) de l'initialisation par copie d'une classe,
  • initialisation par liste lorsque la liste d'initialisation comporte exactement un élément qui est lui-même une liste d'initialisation, et que la cible est le premier paramètre d'un constructeur de la classe X, et que la conversion se fait vers X ou une référence vers X (éventuellement qualifié cv) :
struct A { A(int); };
struct B { B(A); };

B b{{0}}; // initialisation par liste de B

// candidats : B(const B&), B(B&&), B(A)
// {0} -> B&& non viable : il faudrait appeler B(A)
// {0} -> const B& : non viable : il faudrait se lier à une valeur de droite, il faudrait appeler B(A)
// {0} -> A viable. Appelle A(int) : la conversion définie par l'utilisateur vers A n'est pas interdite

(depuis C++11)

Meilleure fonction viable

Pour chaque paire de fonctions viables F1 et F2, les séquences de conversion implicites du i-ième argument vers le i-ième paramètre sont classées afin de déterminer laquelle est la meilleure (à l'exception du premier argument, l'argument objet implicite des fonctions membres statiques n'a aucun effet sur le classement)

F1 est déterminée comme meilleure fonction que F2 si les conversions implicites de tous les arguments de F1 ne sont pas moins bonnes que les conversions implicites de tous les arguments de F2, et

  1. il existe au moins un argument de F1 dont la conversion implicite est meilleure que la conversion implicite correspondante pour cet argument de F2, ou, sinon,

  2. (uniquement dans le contexte d'une initialisation par conversion de type non classe), la séquence de conversion standard allant du résultat de F1 vers le type initialisé est meilleure que la séquence de conversion standard allant du résultat de F2, ou, si ce n'est pas le cas,

  1. (uniquement dans le contexte d'une initialisation par fonction de conversion pour la liaison directe d'une référence à un type fonction), le résultat de F1 est du même genre de référence (lvalue ou rvalue) que la référence initialisée, et le résultat de F2 ne l'est pas, ou, si ce n'est pas le cas,

(depuis C++11)

  1. F1 est une fonction non template alors que F2 est une spécialisation de modèle, ou, si ce n'est pas le cas,

  2. F1 et F2 sont toutes deux des spécialisations de modèles et F1 est plus spécialisée selon les règles d'ordre partiel pour les spécialisations de modèles, ou, si ce n'est pas le cas,

  1. F1 et F2 sont des fonctions non template et F1 est plus contrainte selon l'ordre partiel que F2 :
template<typename T = int>
struct S
{
    constexpr void f(); // #1
    constexpr void f(this S&) requires true; // #2
};

void test()
{
    S<> s;
    s.f(); // calls #2
}

, ou, si ce n'est pas le cas,

(depuis C++20)

  1. F1 est un constructeur de la classe D, F2 est un constructeur de la classe de base B de D, et pour tous les arguments les paramètres correspondants de F1 et F2 ont le même type :
struct A
{
    A(int = 0);
};

struct B: A
{
    using A::A;

    B();
};

B b; // OK, B::B()

, ou, si ce n'est pas le cas,

(depuis C++11)

  1. F2 est un candidat réécrit et F1 ne l'est pas, ou, si ce n'est pas le cas,

  2. F1 et F2 sont tous deux des candidats réécrits, et F2 est un candidat réécrit synthétisé avec ordre inverse des paramètres et F1 ne l'est pas, ou, si ce n'est pas le cas,

(depuis C++20)

  1. F1 est généré à partir d'un guide de déduction défini par l'utilisateur et F2 ne l'est pas, ou, si ce n'est pas le cas,

  2. F1 est le candidat de déduction par copie et F2 ne l'est pas, ou, si ce n'est pas le cas,

  3. F1 est généré à partir d'un constructeur non template et F2 est généré à partir d'un modèle de constructeur :

template<class T>
struct A
{
    using value_type = T;
    A(value_type);  // #1
    A(const A&);    // #2
    A(T, T, int);   // #3

    template<class U>
    A(int, T, U);   // #4
};                  // #5 est A(A), le candidat de déduction de copie

A x(1, 2, 3); // utilise #3, généré à partir d'un constructeur non template

template<class T>
A(T) -> A<T>;       // #6, moins spécialisé que #5

A a (42); // utilise #6 pour déduire A<int> et #1 pour l'initialisation
A b = a;  // utilise #5 pour déduire A<int> et #2 pour l'initialisation

template<class T>
A(A<T>) -> A<A<T>>; // #7, aussi spécialisé que #5
A b2 = a; // utilise #7 pour déduire A<A<int>> et #1 pour l'initialisation

(depuis C++17)

Ces comparaisons deux à deux sont appliquées à toutes les fonctions viables. Si exactement une fonction viable est meilleure que toutes les autres, la résolution de surcharge réussit et cette fonction est appelée. Sinon, la compilation échoue.

void Fcn(const int*, short); // overload #1
void Fcn(int*, int);         // overload #2

int i;
short s = 0;

void f()
{
    Fcn(&i, 1L);  // 1er argument : &i -> int* est meilleur que &i -> const int*
                  // 2e argument : 1L -> short et 1L -> int sont équivalents
                  // appelle Fcn(int*, int)

    Fcn(&i, 'c'); // 1er argument : &i -> int* est meilleur que &i -> const int*
                  // 2e argument : 'c' -> int est meilleur que 'c' -> short
                  // appelle Fcn(int*, int)

    Fcn(&i, s);   // 1er argument : &i -> int* est meilleur que &i -> const int*
                  // 2e argument : s -> short est meilleur que s -> int
                  // aucun vainqueur, erreur de compilation
}

Si la meilleure fonction viable correspond à une fonction pour laquelle plusieurs déclarations ont été trouvées, et si deux de ces déclarations quelconques occupent des portées différentes et spécifient un argument par défaut qui rend la fonction viable, le programme est mal formé.

namespace A
{
    extern "C" void f(int = 5);
}

namespace B
{
    extern "C" void f(int = 5);
}

using A::f;
using B::f;

void use()
{
    f(3); // OK, l'argument par défaut n'a pas été utilisé pour la viabilité
    f();  // erreur : argument par défaut trouvé deux fois
}

Classement des séquences de conversion implicites

Les séquences de conversion implicites argument-paramètre considérées par la résolution de surcharge correspondent aux conversions implicites utilisées en initialisation par copie (pour les paramètres non référence), sauf que, lors de la prise en compte de la conversion vers le paramètre objet implicite ou vers le membre gauche d'un opérateur d'affectation, les conversions créant des objets temporaires ne sont pas considérées. Lorsque le paramètre est le paramètre objet implicite d'une fonction membre statique, la séquence de conversion implicite est une séquence de conversion standard qui n'est ni meilleure ni pire que toute autre séquence de conversion standard. (depuis C++23)

Chaque type de séquence de conversion standard se voit attribuer l'un de trois rangs :

  1. Correspondance exacte : aucune conversion requise, conversion lvalue-to-rvalue, conversion de qualification, conversion de pointeur de fonction, (depuis C++17) conversion définie par l'utilisateur d'un type classe vers la même classe

  2. Promotion : promotion entière, promotion en virgule flottante

  3. Conversion : conversion entière, conversion en virgule flottante, conversion virgule flottante vers entier, conversion de pointeur, conversion de pointeur vers membre, conversion booléenne, conversion définie par l'utilisateur d'une classe dérivée vers sa base

Le rang de la séquence de conversion standard est le pire des rangs des conversions standard qu'elle contient (il peut y avoir jusqu'à trois conversions)

La liaison d'un paramètre référence directement à l'expression d'argument est soit une identité, soit une conversion de dérivée vers base :

struct Base {};
struct Derived : Base {} d;

int f(Base&);    // overload #1
int f(Derived&); // overload #2

int i = f(d); // d -> Derived& a le rang Exact Match
              // d -> Base& a le rang Conversion
              // appelle f(Derived&)

Comme le classement des séquences de conversion ne porte que sur les types et les catégories de valeurs, un champ de bits peut se lier à un argument référence pour le classement, mais si cette fonction est sélectionnée, le programme sera mal formé.

  1. Une séquence de conversion standard est toujours meilleure qu'une séquence de conversion définie par l'utilisateur ou qu'une séquence de conversion par ellipse.

  2. Une séquence de conversion définie par l'utilisateur est toujours meilleure qu'une séquence de conversion par ellipse.

  3. Une séquence de conversion standard S1 est meilleure qu'une séquence de conversion standard S2 si

a) S1 est une sous-séquence propre de S2, à l'exclusion des transformations lvalue ; la séquence de conversion identité est considérée comme une sous-séquence de toute conversion non identité, ou, si ce n'est pas le cas,

b) le rang de S1 est meilleur que le rang de S2, ou, si ce n'est pas le cas,

c) S1 et S2 se lient toutes deux à un paramètre référence vers autre chose que le paramètre objet implicite d'une fonction membre à qualificateur ref, et S1 lie une référence rvalue à une rvalue tandis que S2 lie une référence lvalue à une rvalue :

int i;
int f1();

int g(const int&);  // overload #1
int g(const int&&); // overload #2

int j = g(i);    // lvalue int -> const int& est la seule conversion valide
int k = g(f1()); // rvalue int -> const int&& est meilleur que rvalue int -> const int&

ou, si ce n'est pas le cas,

d) S1 et S2 se lient toutes deux à un paramètre référence et S1 lie une référence lvalue à une fonction tandis que S2 lie une référence rvalue à une fonction :

int f(void(&)());  // overload #1
int f(void(&&)()); // overload #2

void g();
int i1 = f(g); // calls #1

ou, si ce n'est pas le cas,

e) S1 et S2 ne diffèrent que par une conversion de qualification, et

le qualificateur cv du résultat de S1 est un sous-ensemble propre du qualificateur cv du résultat de S2, et S1 n'est pas la conversion obsolète de tableau de littéral chaîne vers pointeur (jusqu'à C++11).

(jusqu'à C++20)

le résultat de S1 peut être converti en le résultat de S2 par une conversion de qualification.

(depuis C++20)

int f(const int*);
int f(int*);

int i;
int j = f(&i); // &i -> int* est meilleur que &i -> const int*, appelle f(int*)

ou, si ce n'est pas le cas,

f) S1 et S2 se lient toutes deux à des paramètres référence ne différant que par le qualificateur cv de premier niveau, et le type de S1 est moins qualifié cv que celui de S2 :

int f(const int &); // overload #1
int f(int &);       // surcharge #2 (deux références)

int g(const int &); // overload #1
int g(int);         // overload #2

int i;
int j = f(i); // lvalue i -> int& est meilleur que lvalue int -> const int&
              // appelle f(int&)
int k = g(i); // lvalue i -> const int& a le rang Exact Match
              // lvalue i -> rvalue int a le rang Exact Match
              // surcharge ambiguë : erreur de compilation

ou, si ce n'est pas le cas,

g) S1 et S2 lient le même type de référence « référence vers T » et ont pour types source V1 et V2, respectivement, où la séquence de conversion standard de V1* vers T* est meilleure que la séquence de conversion standard de V2* vers T* :

struct Z {};

struct A
{
    operator Z&();
    operator const Z&();  // overload #1
};

struct B
{
    operator Z();
    operator const Z&&(); // overload #2
};

const Z& r1 = A();        // OK, utilise #1
const Z&& r2 = B();       // OK, utilise #2
  1. Une séquence de conversion définie par l'utilisateur U1 est meilleure qu'une séquence de conversion définie par l'utilisateur U2 si elles appellent le même constructeur ou la même fonction de conversion définie par l'utilisateur, ou initialisent la même classe par initialisation agrégée, et dans les deux cas la seconde séquence de conversion standard de U1 est meilleure que la seconde séquence de conversion standard de U2
struct A
{
    operator short(); // fonction de conversion définie par l'utilisateur
} a;

int f(int);   // overload #1
int f(float); // overload #2

int i = f(a); // A -> short, suivi de short -> int (rang Promotion)
              // A -> short, suivi de short -> float (rang Conversion)
              // appelle f(int)
  1. Une séquence d'initialisation par liste L1 est meilleure que la séquence d'initialisation par liste L2 si L1 initialise un paramètre std::initializer_list, alors que L2 ne le fait pas.
void f1(int);                                 // #1
void f1(std::initializer_list<long>);         // #2
void g1() { f1({42}); }                       // chooses #2

void f2(std::pair<const char*, const char*>); // #3
void f2(std::initializer_list<std::string>);  // #4
void g2() { f2({"foo", "bar"}); }             // chooses #4
  1. Une séquence d'initialisation par liste L1 est meilleure que la séquence d'initialisation par liste L2 si les paramètres correspondants sont des références à des tableaux, et L1 se convertit en type « tableau de N1 T », L2 se convertit en type « tableau de N2 T », et N1 est plus petit que N2.

(depuis C++11) (jusqu'à C++20)

  1. Une séquence d'initialisation par liste L1 est meilleure que la séquence d'initialisation par liste L2 si les paramètres correspondants sont des références à des tableaux, et L1 et L2 se convertissent en tableaux de même type d'élément, et soit
  • le nombre d'éléments N1 initialisés par L1 est inférieur au nombre d'éléments N2 initialisés par L2, soit
  • N1 est égal à N2 et L2 se convertit en tableau de borne inconnue et L1 ne le fait pas.
void f(int    (&&)[] ); // overload #1
void f(double (&&)[] ); // overload #2
void f(int    (&&)[2]); // overload #3

f({1});        // #1 : meilleur que #2 grâce à la conversion, meilleur que #3 grâce aux bornes
f({1.0});      // #2 : double -> double est meilleur que double -> int
f({1.0, 2.0}); // #2 : double -> double est meilleur que double -> int
f({1, 2});     // #3 : -> int[2] est meilleur que -> int[],
               //     et int -> int est meilleur que int -> double

(depuis C++20)

Si deux séquences de conversion sont indistinguables parce qu'elles ont le même rang, les règles supplémentaires suivantes s'appliquent :

  1. Une conversion qui ne concerne ni un pointeur vers bool ni un pointeur vers membre vers bool est meilleure que celle qui le fait.
  1. Une conversion qui promeut une énumération dont le type sous-jacent est fixe vers son type sous-jacent est meilleure que celle qui promeut vers le type sous-jacent promu, si les deux types sont différents.
enum num : char { one = '0' };
std::cout << num::one; // '0', not 48

(depuis C++11)

  1. Une conversion, dans l'un ou l'autre sens, entre le type virgule flottante FP1 et le type virgule flottante FP2 est meilleure qu'une conversion dans le même sens entre FP1 et le type arithmétique T3 si
  • le rang de conversion en virgule flottante de FP1 est égal au rang de FP2, et
  • T3 n'est pas un type virgule flottante, ou
  • T3 est un type virgule flottante dont le rang n'est pas égal au rang de FP1, ou
  • le sous-rang de conversion en virgule flottante de FP2 est supérieur au sous-rang de T3.
int f(std::float32_t);
int f(std::float64_t);
int f(long long);

float x;
std::float16_t y;

int i = f(x); // appelle f(std::float32_t) sur les implémentations où
              // float et std::float32_t ont des rangs de conversion égaux
int j = f(y); // erreur : ambiguë, aucun rang de conversion égal

(depuis C++23)

  1. Une conversion de pointeur vers dérivé en pointeur vers base est meilleure que la conversion de pointeur vers dérivé en pointeur vers void, et la conversion de pointeur vers base en void est meilleure que celle de pointeur vers dérivé en void.

  2. Si Mid dérive (directement ou indirectement) de Base, et Derived dérive (directement ou indirectement) de Mid

a) Derived* vers Mid* est meilleure que Derived* vers Base*

b) Derived vers Mid& ou Mid&& est meilleure que Derived vers Base& ou Base&&

c) Base::* vers Mid::* est meilleure que Base::* vers Derived::*

d) Derived vers Mid est meilleure que Derived vers Base

e) Mid* vers Base* est meilleure que Derived* vers Base*

f) Mid vers Base& ou Base&& est meilleure que Derived vers Base& ou Base&&

g) Mid::* vers Derived::* est meilleure que Base::* vers Derived::*

h) Mid vers Base est meilleure que Derived vers Base

Les séquences de conversion ambiguës sont classées comme des séquences de conversion définies par l'utilisateur, car plusieurs séquences de conversion pour un argument ne peuvent exister que si elles impliquent différentes conversions définies par l'utilisateur :

class B;

class A { A (B&);};         // constructeur de conversion
class B { operator A (); }; // fonction de conversion définie par l'utilisateur
class C { C (B&); };        // constructeur de conversion

void f(A) {} // overload #1
void f(C) {} // overload #2

B b;
f(b); // B -> A via constructeur ou B -> A via fonction (conversion ambiguë)
      // b -> C via constructeur (conversion définie par l'utilisateur)
      // les conversions pour la surcharge #1 et pour la surcharge #2
      // sont indiscernables ; la compilation échoue

Séquence de conversion implicite en initialisation par liste

En initialisation par liste, l'argument est un braced-init-list, qui n'est pas une expression ; la séquence de conversion implicite vers le type du paramètre, pour la résolution de surcharge, est donc déterminée par les règles spéciales suivantes :

  • Si le type du paramètre est un agrégat X et que la liste d'initialisation se compose exactement d'un élément de la même classe ou d'une classe dérivée (éventuellement qualifiée cv), la séquence de conversion implicite est celle nécessaire pour convertir cet élément vers le type du paramètre.
  • Sinon, si le type du paramètre est une référence à un tableau de caractères et que la liste d'initialisation a un seul élément qui est un littéral chaîne de type approprié, la séquence de conversion implicite est la conversion identité.
  • Sinon, si le type du paramètre est std::initializer_list<X>, et qu'il existe une conversion implicite non restrictive de chaque élément de la liste d'initialisation vers X, la séquence de conversion implicite pour la résolution de surcharge est la pire conversion nécessaire. Si la liste d'initialisation entre accolades est vide, la séquence de conversion est la conversion identité.
struct A
{
    A(std::initializer_list<double>);          // #1
    A(std::initializer_list<complex<double>>); // #2
    A(std::initializer_list<std::string>);     // #3
};
A a{1.0, 2.0};     // sélectionne #1 (double valeur de droite -> double : conversion d'identité)

void g(A);
g({"foo", "bar"}); // sélectionne #3 (lvalue const char[4] -> std::string : conv. définie par l'utilisateur)
  • Sinon, si le type du paramètre est « tableau de N T » (ce cas ne se produit que pour les références à des tableaux), la liste d'initialisation doit comporter au plus N éléments, et la pire conversion implicite nécessaire pour convertir chaque élément de la liste (ou la paire d'accolades vide {} si la liste est plus courte que N) vers T est celle utilisée.
  • Sinon, si le type du paramètre est « tableau de borne inconnue de T » (ce cas ne se produit que pour les références à des tableaux), la pire conversion implicite nécessaire pour convertir chaque élément de la liste vers T est celle utilisée.

(depuis C++20)

typedef int IA[3];

void h(const IA&);
void g(int (&&)[]);

h({1, 2, 3}); // conversion d'identité int -> int
g({1, 2, 3}); // identique à ci-dessus depuis C++20
  • Sinon, si le type du paramètre est un type classe non agrégat X, la résolution de surcharge choisit le constructeur C de X pour initialiser à partir de la liste d'initialisation en argument
    • Si C n'est pas un constructeur à liste d'initialisation et que la liste d'initialisation a un seul élément de type X éventuellement qualifié cv, la séquence de conversion implicite a le rang Correspondance exacte. Si la liste d'initialisation a un seul élément de type éventuellement qualifié cv dérivé de X, la séquence de conversion implicite a le rang Conversion. (note : la différence avec les agrégats est que les agrégats s'initialisent directement à partir d'une liste à un seul élément avant de considérer l'initialisation agrégée, alors que les non-agrégats considèrent d'abord les constructeurs initializer_list avant les autres constructeurs)
    • sinon, la séquence de conversion implicite est une séquence de conversion définie par l'utilisateur dont la seconde séquence de conversion standard est une conversion identité.

Si plusieurs constructeurs sont viables mais qu'aucun n'est meilleur que les autres, la séquence de conversion implicite est la séquence de conversion ambiguë.

struct A { A(std::initializer_list<int>); };
void f(A);

struct B { B(int, double); };
void g(B);

g({'a', 'b'});    // appelle g(B(int, double)), conversion définie par l'utilisateur
// g({1.0, 1,0}); // erreur : double -> int est un rétrécissement, non autorisé dans l'initialisation par liste

void f(B);
// f({'a', 'b'}); // f(A) et f(B) sont toutes deux des conversions définies par l'utilisateur
  • Sinon, si le type du paramètre est un agrégat pouvant être initialisé à partir de la liste d'initialisation selon l'initialisation agrégée, la séquence de conversion implicite est une séquence de conversion définie par l'utilisateur dont la seconde séquence de conversion standard est une conversion identité.
struct A { int m1; double m2; };

void f(A);
f({'a', 'b'}); // appelle f(A(int, double)), conversion définie par l'utilisateur
  • Sinon, si le paramètre est une référence, les règles d'initialisation des références s'appliquent
struct A { int m1; double m2; };

void f(const A&);
f({'a', 'b'}); // un temporaire est créé, f(A(int, double)) est appelée. Conversion définie par l'utilisateur
  • Sinon, si le type du paramètre n'est pas une classe et que la liste d'initialisation a un seul élément, la séquence de conversion implicite est celle nécessaire pour convertir cet élément vers le type du paramètre
  • Sinon, si le type du paramètre n'est pas un type classe et si la liste d'initialisation ne contient aucun élément, la séquence de conversion implicite est la conversion identité.

Si l'argument est une liste d'initialisation désignée et que le paramètre n'est pas une référence, une conversion n'est possible que si le paramètre a un type agrégat pouvant être initialisé à partir de cette liste d'initialisation selon les règles de l'initialisation d'agrégat, auquel cas la séquence de conversion implicite est une séquence de conversion définie par l'utilisateur dont la seconde séquence de conversion standard est une conversion identité.

Si, après la résolution de surcharge, l'ordre de déclaration des membres de l'agrégat ne correspond pas pour la surcharge sélectionnée, l'initialisation du paramètre sera mal formée.

struct A { int x, y; };
struct B { int y, x; };

void f(A a, int); // #1
void f(B b, ...); // #2
void g(A a);      // #3
void g(B b);      // #4

void h()
{
    f({.x = 1, .y = 2}, 0); // OK ; appelle #1
    f({.y = 2, .x = 1}, 0); // erreur : sélectionne #1, l'initialisation de a échoue
                            // en raison d'un ordre des membres non concordant
    g({.x = 1, .y = 2});    // erreur : ambiguë entre #3 et #4
}

(depuis C++20)
