spécificateur inline

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Le spécificateur inline, lorsqu'il est utilisé dans une decl-specifier-seq de fonction, déclare la fonction comme une fonction inline.

Une fonction définie entièrement à l'intérieur d'une définition de classe/struct/union, qu'il s'agisse d'une fonction membre ou d'une fonction friend non membre, est implicitement une fonction inlinesauf si elle est rattachée à un module nommé (depuis C++20).

Une fonction déclarée constexprou consteval (depuis C++20) lors de sa première déclaration est implicitement une fonction inline.

Une fonction supprimée est implicitement une fonction inline : sa définition (supprimée) peut apparaître dans plusieurs unités de traduction.

(depuis C++11)

Le spécificateur inline, lorsqu'il est utilisé dans une decl-specifier-seq d'une variable à durée de stockage statique (membre de classe statique ou variable de portée d'espace de noms), déclare la variable comme une variable inline.

Un membre de donnée statique déclaré constexpr lors de sa première déclaration est implicitement une variable inline.

(depuis C++17)

Explication

Une fonction inline ou variable inline (depuis C++17) possède les propriétés suivantes :

  • La définition d'une fonction inline ou variable (depuis C++17) doit être accessible dans l'unité de traduction où elle est utilisée (pas nécessairement avant le point d'utilisation).
  • Une fonction inline ou variable (depuis C++17) à liaison externe (par exemple non déclarée static) possède les propriétés supplémentaires suivantes :
    • Il peut exister plus d'une définition d'une fonction inlineou variable (depuis C++17) dans le programme, à condition que chaque définition figure dans une unité de traduction différente et que (pour les fonctions inline non statiqueset les variables (depuis C++17)) toutes les définitions soient identiques. Par exemple, une fonction inlineou une variable inline (depuis C++17) peut être définie dans un fichier d'en-tête inclus dans plusieurs fichiers source.
    • Elle doit être déclarée inline dans chaque unité de traduction.
    • Elle a la même adresse dans toutes les unités de traduction.

Dans une fonction inline,

  • Les objets static locaux à une fonction, dans toutes les définitions de fonctions, sont partagés entre toutes les unités de traduction (ils désignent tous le même objet défini dans une seule unité de traduction).
  • Les types définis dans toutes les définitions de fonctions sont également les mêmes dans toutes les unités de traduction.

Les variables const inline de portée d'espace de noms ont par défaut une liaison externe (contrairement aux variables const non inline et non volatile).

(depuis C++17)

Le but initial du mot-clé inline était d'indiquer à l'optimiseur que la substitution inline d'une fonction est préférable à l'appel de fonction, c'est-à-dire qu'au lieu d'exécuter l'instruction CPU d'appel pour transférer le contrôle au corps de la fonction, une copie du corps de la fonction est exécutée sans générer d'appel. Cela évite la surcharge due à l'appel de fonction (passage des arguments et récupération du résultat), mais peut produire un exécutable plus volumineux, car le code de la fonction doit être répété plusieurs fois.

La substitution inline n'étant pas observable dans la sémantique standard, les compilateurs sont libres d'utiliser la substitution inline pour toute fonction qui n'est pas marquée inline, et sont libres de générer des appels de fonction vers toute fonction marquée inline. Ces choix d'optimisation ne modifient pas les règles concernant les définitions multiples et les statiques partagés énumérées ci-dessus.

Le sens du mot-clé inline pour les fonctions est devenu « des définitions multiples sont autorisées » plutôt que « l'inlining est préférable » depuis C++98 ; ce sens a ensuite été étendu aux variables.

(depuis C++17)

Notes

Si une fonction inlineou variable (depuis C++17) à liaison externe est définie différemment dans différentes unités de traduction, le programme est mal formé, aucun diagnostic requis.

Le spécificateur inline ne peut pas être utilisé avec une déclaration de fonctionou de variable (depuis C++17) en portée de bloc (à l'intérieur d'une autre fonction).

Le spécificateur inline ne peut pas redéclarer une fonctionou une variable (depuis C++17) déjà définie dans l'unité de traduction comme non inline.

Les fonctions membres générées implicitement, ainsi que toute fonction membre déclarée comme defaulted lors de sa première déclaration, sont inline comme toute autre fonction définie dans une définition de classe.

Si une fonction inline est déclarée dans différentes unités de traduction, les ensembles cumulés d'arguments par défaut doivent être identiques à la fin de chaque unité de traduction.

En C, les fonctions inline n'ont pas besoin d'être déclarées inline dans chaque unité de traduction (au plus une peut être non-inline ou extern inline), les définitions de fonctions n'ont pas besoin d'être identiques (mais le comportement du programme est non spécifié s'il dépend de celle qui est appelée), et les statiques locales à la fonction sont distinctes entre différentes définitions de la même fonction.

Voir membres de données statiques pour des règles supplémentaires concernant les membres statiques inline.

Les variables inline éliminent le principal obstacle à l'empaquetage du code C++ sous forme de bibliothèques en-tête seul.

(depuis C++17)

Exemple

En-tête « example.h » :

#ifndef EXAMPLE_H
#define EXAMPLE_H

#include <atomic>

// Une fonction incluse dans plusieurs fichiers source doit être inline
inline int sum(int a, int b)
{
    return a + b;
}

// Une variable à liaison externe incluse dans plusieurs fichiers source doit être inline
inline std::atomic<int> counter(0);

#endif

Fichier source #1 :

#include "example.h"

int a()
{
    ++counter;
    return sum(1, 2);
}

Fichier source #2 :

#include "example.h"

int b()
{
    ++counter;
    return sum(3, 4);
}

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
CWG 281 C++98 une déclaration de fonction amie pouvait utiliser le spécificateur inline même si la fonction amie n'est pas une fonction inline interdire de tels usages
CWG 317 C++98 une fonction pouvait être déclarée inline même si elle possédait une définition non inline dans la même unité de traduction avant la déclaration le programme est mal formé dans ce cas
CWG 765 C++98 un type défini dans une fonction inline pouvait être différent selon les unités de traduction de tels types sont identiques dans toutes les unités de traduction
CWG 1823 C++98 les littéraux de chaîne dans toutes les définitions d'une fonction inline étaient partagés entre toutes les unités de traduction cette exigence est supprimée pour des raisons de cohérence et d'implémentations
CWG 2531 C++17 un membre de donnée statique pouvait être implicitement inline même s'il n'était pas déclaré constexpr lors de sa première déclaration il n'est pas implicitement inline dans ce cas
