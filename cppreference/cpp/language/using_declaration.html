Déclaration using

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Introduit un nom défini ailleurs dans la région déclarative où cette déclaration using apparaît. Voir using enum et (depuis C++20)using namespace pour d'autres déclarations associées.

| | | | using typename(facultatif) nested-name-specifier unqualified-id ; | | (jusqu'à C++17) | | | using declarator-list ; | | (depuis C++17) | |

  • typename — le mot-clé typename peut être utilisé si nécessaire pour résoudre les noms dépendants, lorsque la déclaration using introduit un type membre d'une classe de base dans un modèle de classe
  • nested-name-specifier — une suite de noms et d'opérateurs de résolution de portée ::, se terminant par un opérateur de résolution de portée. Un :: seul désigne l'espace de noms global.
  • unqualified-id — un id-expression
  • declarator-list — liste séparée par des virgules d'un ou plusieurs déclarateurs de typename(facultatif) nested-name-specifier unqualified-id. Certains ou tous les déclarateurs peuvent être suivis d'une ellipse ... pour indiquer une expansion de pack

Explication

Les déclarations using peuvent être utilisées pour introduire des membres d'espaces de noms dans d'autres espaces de noms et portées de bloc, ou pour introduire des membres de classe de base dans les définitions de classes dérivées, ou pour introduire des énumérateurs dans les portées d'espaces de noms, de blocs et de classes (depuis C++20).

Une déclaration using comportant plusieurs déclarateurs using est équivalente à une suite correspondante de déclarations using comportant chacune un seul déclarateur using.

(depuis C++17)

Dans une portée d'espace de noms et de bloc

Les déclarations using introduisent un membre d'un autre espace de noms dans la portée courante d'espace de noms ou de bloc.

#include <iostream>
#include <string>

using std::string;

int main()
{
    string str = "Example";
    using std::cout;
    cout << str;
}

Voir espace de noms pour plus de détails.

Dans une définition de classe

Une déclaration using introduit un membre d'une classe de base dans la définition de la classe dérivée, par exemple pour exposer un membre protégé de la base comme membre public de la classe dérivée. Dans ce cas, nested-name-specifier doit désigner une classe de base de celle en cours de définition. Si le nom est celui d'une fonction membre surchargée de la classe de base, toutes les fonctions membres de la classe de base portant ce nom sont introduites. Si la classe dérivée possède déjà un membre de même nom, même liste de paramètres et mêmes qualificatifs, le membre de la classe dérivée masque ou redéfinit (il n'y a pas de conflit avec) le membre introduit depuis la classe de base.

#include <iostream>

struct B
{
    virtual void f(int) { std::cout << "B::f\n"; }
    void g(char)        { std::cout << "B::g\n"; }
    void h(int)         { std::cout << "B::h\n"; }
protected:
    int m; // B::m est protégé
    typedef int value_type;
};

struct D : B
{
    using B::m;          // D::m est public
    using B::value_type; // D::value_type est public

    using B::f;
    void f(int) override { std::cout << "D::f\n"; } // D::f(int) redéfinit B::f(int)

    using B::g;
    void g(int) { std::cout << "D::g\n"; } // g(int) et g(char) sont tous deux visibles

    using B::h;
    void h(int) { std::cout << "D::h\n"; } // D::h(int) masque B::h(int)
};

int main()
{
    D d;
    B& b = d;

//  b.m = 2;  // Erreur : B::m est protégé
    d.m = 1;  // B::m protégé est accessible comme D::m public

    b.f(1);   // appelle f() dérivée
    d.f(1);   // appelle f() dérivée
    std::cout << "----------\n";

    d.g(1);   // appelle g(int) dérivée
    d.g('a'); // appelle g(char) de la base, exposée via using B::g;
    std::cout << "----------\n";

    b.h(1);   // appelle h() de la base
    d.h(1);   // appelle h() dérivée
}

Output:

D::f
D::f
----------
D::g
B::g
----------
B::h
D::h

Constructeurs hérités

Si la déclaration using désigne un constructeur d'une base directe de la classe en cours de définition (par exemple using Base::Base;), tous les constructeurs de cette base (sans tenir compte de l'accès aux membres) deviennent visibles pour la résolution de surcharge lors de l'initialisation de la classe dérivée.

Si la résolution de surcharge sélectionne un constructeur hérité, celui-ci est accessible s'il l'aurait été lorsqu'il est utilisé pour construire un objet de la classe de base correspondante : l'accessibilité de la déclaration using qui l'a introduit est ignorée.

Si la résolution de surcharge sélectionne l'un des constructeurs hérités lors de l'initialisation d'un objet d'une telle classe dérivée, alors le sous-objet Base dont le constructeur a été hérité est initialisé à l'aide du constructeur hérité, et toutes les autres bases et tous les autres membres de Derived sont initialisés comme par le constructeur par défaut défini par défaut (les initialiseurs de membres par défaut sont utilisés s'ils sont fournis, sinon une initialisation par défaut a lieu). L'initialisation complète est traitée comme un seul appel de fonction : l'initialisation des paramètres du constructeur hérité est séquencée avant l'initialisation de toute base ou de tout membre de l'objet dérivé.

struct B1 { B1(int, ...) {} };
struct B2 { B2(double)   {} };

int get();

struct D1 : B1
{
    using B1::B1; // hérite de B1(int, ...)
    int x;
    int y = get();
};

void test()
{
    D1 d(2, 3, 4); // OK : B1 est initialisée en appelant B1(2, 3, 4),
                   // puis d.x est initialisée par défaut (aucune initialisation n'est effectuée),
                   // puis d.y est initialisée en appelant get()

    D1 e;          // Erreur : D1 n'a pas de constructeur par défaut
}

struct D2 : B2
{
    using B2::B2; // hérite de B2(double)
    B1 b;
};

D2 f(1.0); // erreur : B1 n'a pas de constructeur par défaut

struct W { W(int); };

struct X : virtual W
{
    using W::W; // hérite de W(int)
    X() = delete;
};

struct Y : X
{
    using X::X;
};

struct Z : Y, virtual W
{
    using Y::Y;
};

Z z(0); // OK : l'initialisation de Y n'appelle pas le constructeur par défaut de X

Si le sous-objet de la classe de base Base ne doit pas être initialisé dans le cadre de l'objet Derived (c'est-à-dire si Base est une classe de base virtuelle de Derived, et que l'objet Derived n'est pas l'objet le plus dérivé), l'appel du constructeur hérité, y compris l'évaluation de ses éventuels arguments, est omis :

struct V
{
    V() = default;
    V(int);
};

struct Q { Q(); };

struct A : virtual V, Q
{
    using V::V;
    A() = delete;
};

int bar() { return 42; }

struct B : A
{
    B() : A(bar()) {} // OK
};

struct C : B {};

void foo()
{
    C c; // « bar » n'est pas appelé, car le sous-objet V
         // n'est pas initialisé dans le cadre de B
         // (le sous-objet V est initialisé dans le cadre de C,
         //  car « c » est l'objet le plus dérivé)
}

Si le constructeur a été hérité de plusieurs sous-objets de classe de base de type Base, le programme est mal formé, de manière similaire aux fonctions membres non statiques héritées multiplement :

struct A { A(int); };
struct B : A { using A::A; };
struct C1 : B { using B::B; };
struct C2 : B { using B::B; };

struct D1 : C1, C2
{
    using C1::C1;
    using C2::C2;
};
D1 d1(0); // mal formé : constructeur hérité de différents sous-objets de base B

struct V1 : virtual B { using B::B; };
struct V2 : virtual B { using B::B; };

struct D2 : V1, V2
{
    using V1::V1;
    using V2::V2;
};
D2 d2(0); // OK : il n'existe qu'un seul sous-objet B.
          // Ceci initialise la classe de base virtuelle B,
          //   qui initialise la classe de base A
          // puis initialise les classes de base V1 et V2
          //   comme par un constructeur par défaut défini par défaut

Comme pour les déclarations using de toutes les autres fonctions membres non statiques, si un constructeur hérité a la même signature qu'un des constructeurs de Derived, il est masqué pour la recherche par la version trouvée dans Derived. Si l'un des constructeurs hérités de Base a par hasard la signature d'un constructeur de copie/déplacement de Derived, cela n'empêche pas la génération implicite de Derived constructeur de copie/déplacement (qui masque alors la version héritée, de manière similaire à using operator=).

struct B1 { B1(int); };
struct B2 { B2(int); };

struct D2 : B1, B2
{
    using B1::B1;
    using B2::B2;

    D2(int); // OK : D2::D2(int) masque à la fois B1::B1(int) et B2::B2(int)
};
D2 d2(0);    // appelle D2::D2(int)

Dans une classe modèle, si une déclaration using désigne un nom dépendant, celui-ci est considéré comme désignant un constructeur si le nested-name-specifier a un nom terminal identique à celui de unqualified-id.

template<class T>
struct A : T
{
    using T::T; // OK, hérite des constructeurs de T
};

template<class T, class U>
struct B : T, A<U>
{
    using A<U>::A; // OK, hérite des constructeurs de A<U>
    using T::A;    // n'hérite pas du constructeur de T
                   // même si T peut être une spécialisation de A<>
};

(depuis C++11)

Introduction d'énumérateurs à portée

En plus des membres d'un autre espace de noms et des membres des classes de base, une déclaration using peut aussi introduire les énumérateurs d'énumérations dans les portées d'espace de noms, de bloc et de classe.

Une déclaration using peut également être utilisée avec des énumérateurs non à portée.

enum class button { up, down };

struct S
{
    using button::up;
    button b = up; // OK
};

using button::down;
constexpr button non_up = down; // OK

constexpr auto get_button(bool is_up)
{
    using button::up, button::down;
    return is_up ? up : down; // OK
}

enum unscoped { val };
using unscoped::val; // OK, bien que superflu

(depuis C++20)

Notes

Seul le nom explicitement mentionné dans la déclaration using est transféré dans la portée déclarative : en particulier, les énumérateurs ne sont pas transférés lorsque le nom du type d'énumération fait l'objet d'une déclaration using.

Une déclaration using ne peut pas désigner un espace de noms, un énumérateur à portée (jusqu'à C++20), un destructeur d'une classe de base, ni une spécialisation d'un modèle de membre pour une fonction de conversion définie par l'utilisateur.

Une déclaration using ne peut pas désigner une spécialisation de modèle de membre (un template-id n'est pas autorisé par la grammaire) :

struct B
{
    template<class T>
    void f();
};

struct D : B
{
    using B::f;      // OK : désigne un modèle
//  using B::f<int>; // Erreur : désigne une spécialisation de modèle

    void g() { f<int>(); }
};

Une déclaration using ne peut pas non plus introduire le nom d'un modèle de membre dépendant comme nom de modèle (le désambiguïsateur template pour les noms dépendants n'est pas autorisé).

template<class X>
struct B
{
    template<class T>
    void f(T);
};

template<class Y>
struct D : B<Y>
{
//  using B<Y>::template f; // Erreur : désambiguïsation non autorisée
    using B<Y>::f;          // compile, mais f n'est pas un nom de modèle

    void g()
    {
//      f<int>(0);          // Erreur : f n'est pas connu comme nom de modèle,
                            // donc < ne commence pas une liste d'arguments de modèle
        f(0);               // OK
    }
};

Si une déclaration using introduit dans la classe dérivée l'opérateur d'affectation de la classe de base, dont la signature correspond par hasard à l'opérateur d'affectation par copie ou par déplacement de la classe dérivée, cet opérateur est masqué par l'opérateur d'affectation par copie/déplacement implicitement déclaré de la classe dérivée. Il en va de même pour une déclaration using héritant d'un constructeur de la classe de base qui correspond par hasard au constructeur de copie/déplacement de la classe dérivée (depuis C++11).

La sémantique des constructeurs hérités a été modifiée rétroactivement par un rapport de défaut contre C++11. Auparavant, la déclaration d'un constructeur hérité injectait un ensemble de déclarations de constructeurs synthétisées dans la classe dérivée, ce qui entraînait des copies/déplacements d'arguments redondants, posait des problèmes d'interaction avec certaines formes de SFINAE, et pouvait dans certains cas être impossible à implémenter sur les principaux ABI. Les compilateurs anciens peuvent encore implémenter l'ancienne sémantique.

Ancienne sémantique des constructeurs hérités

Si la déclaration using désigne un constructeur d'une base directe de la classe en cours de définition (par exemple using Base::Base;), les constructeurs de cette classe de base sont hérités, selon les règles suivantes :

  1. Un ensemble de constructeurs hérités candidats est composé de

a) Tous les constructeurs non modèles de la classe de base (après omission des paramètres ellipse, le cas échéant) (depuis C++14)

b) Pour chaque constructeur ayant des arguments par défaut ou un paramètre ellipse, toutes les signatures de constructeurs formées en supprimant l'ellipse et en omettant un à un les arguments par défaut en fin de liste d'arguments

c) Tous les modèles de constructeurs de la classe de base (après omission des paramètres ellipse, le cas échéant) (depuis C++14)

d) Pour chaque modèle de constructeur avec des arguments par défaut ou l'ellipse, toutes les signatures de constructeur obtenues en supprimant l'ellipse et en omettant un à un les arguments par défaut en fin de listes d'arguments

  1. Tous les constructeurs hérités candidats qui ne sont ni le constructeur par défaut ni le constructeur de copie/déplacement, et dont les signatures ne correspondent pas à des constructeurs définis par l'utilisateur dans la classe dérivée, sont implicitement déclarés dans la classe dérivée. Les paramètres par défaut ne sont pas hérités :
struct B1
{
    B1(int);
};

struct D1 : B1
{
    using B1::B1;

    // L'ensemble des constructeurs hérités candidats est
    // 1. B1(const B1&)
    // 2. B1(B1&&)
    // 3. B1(int)

    // D1 possède les constructeurs suivants :
    // 1. D1() = delete
    // 2. D1(const D1&)
    // 3. D1(D1&&)
    // 4. D1(int) <- hérité
};

struct B2
{
    B2(int = 13, int = 42);
};

struct D2 : B2
{
    using B2::B2;

    // L'ensemble des constructeurs hérités candidats est
    // 1. B2(const B2&)
    // 2. B2(B2&&)
    // 3. B2(int = 13, int = 42)
    // 4. B2(int = 13)
    // 5. B2()

    // D2 possède les constructeurs suivants :
    // 1. D2()
    // 2. D2(const D2&)
    // 3. D2(D2&&)
    // 4. D2(int, int) <- hérité
    // 5. D2(int) <- hérité
};

Les constructeurs hérités sont équivalents à des constructeurs définis par l'utilisateur, avec un corps vide et une liste d'initialisation de membres constituée d'un seul nested-name-specifier, qui transmet tous ses arguments au constructeur de la classe de base.

Il a le même accès que le constructeur de base correspondant. Il est constexpr si le constructeur défini par l'utilisateur aurait satisfait les exigences de constructeur constexpr. Il est supprimé si le constructeur de base correspondant est supprimé ou si un constructeur par défaut défini par défaut serait supprimé (sauf que la construction de la base dont le constructeur est hérité ne compte pas). Un constructeur hérité ne peut pas être explicitement instancié ni explicitement spécialisé.

Si deux using-declarations héritent du constructeur de même signature (de deux classes de base directes), le programme est mal formé.

Un modèle de constructeur hérité ne doit pas être explicitement instancié ni explicitement spécialisé.

(depuis C++11)

Les expansions de packs dans les déclarations using permettent de former une classe exposant les membres surchargés de bases variadiques sans récursion :

template<typename... Ts>
struct Overloader : Ts...
{
    using Ts::operator()...; // expose operator() de chaque base
};

template<typename... T>
Overloader(T...) -> Overloader<T...>; // guide de déduction C++17, non nécessaire en C++20

int main()
{
    auto o = Overloader{ [] (auto const& a) {std::cout << a;},
                         [] (float f) {std::cout << std::setprecision(3) << f;} };
}

(depuis C++17)
