Objet

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Les programmes C++ créent, détruisent, font référence à, accèdent et manipulent des objets.

Un objet, en C++, possède

  • taille (déterminable avec sizeof) ;
  • exigence d'alignement (déterminable avec alignof) ;
  • durée de stockage (automatique, statique, dynamique, thread-local) ;
  • durée de vie (bornée par la durée de stockage ou temporaire) ;
  • type;
  • valeur (qui peut être indéterminée, par exemple pour les types non classes initialisés par défaut) ;
  • éventuellement, un nom.

Les entités suivantes ne sont pas des objets : valeur, référence, fonction, énumérateur, type, membre de classe non statique, modèle, spécialisation de modèle de classe ou de fonction, espace de noms, pack de paramètres et this.

Une variable est un objet ou une référence qui n'est pas un membre de données non statique, introduit par une déclaration.

Création d'objets

Des objets peuvent être créés explicitement par des définitions, des expressions new, des expressions throw, par changement du membre actif d'une union et par l'évaluation d'expressions qui nécessitent des objets temporaires. L'objet créé est défini de manière unique lors de la création explicite d'objet.

Des objets de types à durée de vie implicite peuvent aussi être créés implicitement par

  • sauf pendant l'évaluation constante, les opérations qui commencent la durée de vie d'un tableau de type unsigned charou std::byte (depuis C++17), auquel cas ces objets sont créés dans le tableau,
  • appel aux fonctions d'allocation suivantes, auquel cas ces objets sont créés dans le stockage alloué :
    • operator new (sauf pendant l'évaluation constante)
    • operator new[] (sauf pendant l'évaluation constante)
    • std::malloc
    • std::calloc
    • std::realloc
  • std::aligned_alloc

(depuis C++17)

  • appel aux fonctions suivantes de copie de représentation d'objet, auquel cas ces objets sont créés dans la région de destination du stockage ou dans le résultat :
    • std::memcpy
    • std::memmove
  • std::bit_cast

(depuis C++20)

  • appel aux fonctions spécifiques suivantes, auquel cas ces objets sont créés dans la région de stockage spécifiée :
  • std::start_lifetime_as
  • std::start_lifetime_as_array

(depuis C++23)

Zéro ou plusieurs objets peuvent être créés dans la même région de stockage, tant que cela donne au programme un comportement défini. Si une telle création est impossible, par exemple à cause d'opérations en conflit, le comportement du programme est indéfini. Si plusieurs ensembles d'objets créés implicitement donneraient au programme un comportement défini, l'ensemble qui est créé n'est pas spécifié. En d'autres termes, les objets créés implicitement ne sont pas tenus d'être définis de manière unique.

Après la création implicite d'objets dans une région de stockage spécifiée, certaines opérations produisent un pointeur vers un objet créé approprié. L'objet créé approprié a la même adresse que la région de stockage. De même, le comportement est indéfini si et seulement si aucune valeur de pointeur de ce type ne peut donner au programme un comportement défini, et la valeur de pointeur produite n'est pas spécifiée s'il existe plusieurs valeurs donnant un comportement défini.

#include <cstdlib>

struct X { int a, b; };

X* MakeX()
{
    // L'un des comportements définis possibles :
    // l'appel à std::malloc crée implicitement un objet de type X
    // et ses sous-objets a et b, et renvoie un pointeur vers cet objet X
    X* p = static_cast<X*>(std::malloc(sizeof(X)));
    p->a = 1;
    p->b = 2;
    return p;
}

L'appel à std::allocator::allocate ou aux fonctions membres spéciales de copie et de déplacement implicitement définies des types union peut aussi créer des objets.

Représentation d'objet et représentation de valeur

Certains types et objets ont des représentations d'objet et des représentations de valeur, définies dans le tableau ci-dessous :

Entité Représentation d'objet Représentation de valeur
un type objet complet T la séquence des N unsigned char objets occupés par un objet complet non champ de bits de type T, où N vaut sizeof(T) l'ensemble des bits de la représentation d'objet de T qui participent à la représentation d'une valeur de type T
un objet complet obj qui n'est pas un champ de bits, de type T les octets de obj correspondant à la représentation d'objet de T les bits de obj correspondant à la représentation de valeur de T
un objet bf de type champ de bits la séquence de bits N occupée par bf, où N est la largeur du champ de bits l'ensemble des bits de la représentation d'objet de bf qui participent à la représentation de la valeur de bf

Les bits de la représentation d'objet d'un type ou d'un objet qui ne font pas partie de la représentation de valeur sont des bits de remplissage.

Pour les types TriviallyCopyable, la représentation de valeur fait partie de la représentation d'objet, ce qui signifie que copier les octets occupés par l'objet en mémoire suffit à produire un autre objet de même valeur (sauf si l'objet est un sous-objet potentiellement chevauchant, ou si la valeur est une représentation piège de son type et que son chargement dans le processeur lève une exception matérielle, comme les valeurs à virgule flottante SNaN (« signalling not-a-number ») ou les entiers NaT (« not-a-thing »)).

Bien que la plupart des implémentations n'autorisent ni représentations pièges, ni bits de remplissage, ni représentations multiples pour les types entiers, il existe des exceptions ; par exemple, une valeur d'un type entier sur Itanium peut être une représentation piège.

L'inverse n'est pas nécessairement vrai : deux objets de type TriviallyCopyable ayant des représentations d'objet différentes peuvent représenter la même valeur. Par exemple, plusieurs motifs de bits à virgule flottante représentent la même valeur spéciale NaN. Plus couramment, des bits de remplissage peuvent être introduits pour satisfaire les exigences d'alignement, les tailles des champs de bits, etc.

#include <cassert>

struct S
{
    char c;  // valeur de 1 octet
             // 3 octets de bits de remplissage (en supposant alignof(float) == 4)
    float f; // valeur de 4 octets (en supposant sizeof(float) == 4)

    bool operator==(const S& arg) const // égalité fondée sur la valeur
    {
        return c == arg.c && f == arg.f;
    }
};

void f()
{
    assert(sizeof(S) == 8);
    S s1 = {'a', 3.14};
    S s2 = s1;
    reinterpret_cast<unsigned char*>(&s1)[2] = 'b'; // modifier certains bits de remplissage
    assert(s1 == s2); // la valeur n'a pas changé
}

Pour les objets de type char, signed char et unsigned char (sauf s'ils sont des champs de bits surdimensionnés), chaque bit de la représentation d'objet doit participer à la représentation de valeur, et chaque motif de bits possible représente une valeur distincte (aucun bit de remplissage, bit piège ou représentation multiple n'est autorisé).

Sous-objets

Un objet peut avoir des sous-objets. Ceux-ci comprennent

  • les objets membres
  • les sous-objets de classes de base
  • les éléments de tableau

Un objet qui n'est le sous-objet d'aucun autre objet est appelé objet complet.

Les objets complets, les objets membres et les éléments de tableau sont aussi appelés objets les plus dérivés, pour les distinguer des sous-objets de classes de base.

Pour une classe,

  • ses membres de données non statiques,
  • ses classes de base directes non virtuelles et,
  • si la classe n'est pas abstraite, ses classes de base virtuelles

sont appelés ses sous-objets potentiellement construits.

Taille

Un sous-objet est un sous-objet potentiellement chevauchant s'il s'agit d'un sous-objet de classe de baseou d'un membre de données non statique déclaré avec l'attribut [[no_unique_address]] (depuis C++20).

Un objet obj ne peut avoir une taille nulle que si toutes les conditions suivantes sont satisfaites :

  • obj est un sous-objet potentiellement chevauchant.
  • obj est d'un type classe sans fonctions membres virtuelles ni classes de base virtuelles.
  • obj ne possède aucun sous-objet de taille non nulle ni aucun champ de bits sans nom de longueur non nulle.

Pour un objet obj satisfaisant toutes les conditions ci-dessus :

  • Si obj est un sous-objet de classe de base d'un type classe à disposition standard (depuis C++11) sans membre de données non statique, sa taille est nulle.
  • Sinon, les circonstances dans lesquelles obj a une taille nulle sont définies par l'implémentation.

Voir optimisation de la base vide pour plus de détails.

Tout objet qui n'est pas un champ de bits et dont la taille est non nulle doit occuper un ou plusieurs octets de stockage, y compris chaque octet occupé (en totalité ou en partie) par l'un de ses sous-objets. Le stockage occupé doit être contigu si l'objet est de type trivialement copiableou à disposition standard (depuis C++11).

Adresse

Sauf si un objet est un champ de bits ou un sous-objet de taille nulle, l'adresse de cet objet est l'adresse du premier octet qu'il occupe.

Un objet peut en contenir d'autres, auquel cas les objets contenus sont imbriqués dans le premier objet. Un objet a est imbriqué dans un autre objet b si l'une quelconque des conditions suivantes est satisfaite :

  • a est un sous-objet de b.
  • b fournit le stockage de a.
  • Il existe un objet c tel que a est imbriqué dans c, et c est imbriqué dans b.

Un objet est un objet potentiellement non unique s'il s'agit de l'un des objets suivants :

  • Un objet littéral de chaîne.
  • Le tableau de support d'une liste d'initialisation.

(depuis C++11)

  • Un sous-objet d'un objet potentiellement non unique.

Pour deux objets quelconques qui ne sont pas des champs de bits et dont les durées de vie se chevauchent :

  • Si l'une quelconque des conditions suivantes est satisfaite, ils peuvent avoir la même adresse :

    • L'un d'eux est imbriqué dans l'autre.
    • L'un d'eux est un sous-objet de taille nulle, et leurs types ne sont pas similaires.
    • Ils sont tous deux des objets potentiellement non uniques.

  • Sinon, ils ont toujours des adresses distinctes et occupent des octets de stockage disjoints.

// les littéraux de caractère sont toujours uniques
static const char test1 = 'x';
static const char test2 = 'x';
const bool b = &test1 != &test2;      // toujours vrai

// le caractère 'x' accédé depuis « r », « s » et « il »
// peuvent avoir la même adresse (c'est-à-dire que ces objets peuvent partager le stockage)
static const char (&r) [] = "x";
static const char *s = "x";
static std::initializer_list<char> il = {'x'};
const bool b2 = r != il.begin();      // résultat non spécifié
const bool b3 = r != s;               // résultat non spécifié
const bool b4 = il.begin() != &test1; // toujours vrai
const bool b5 = r != &test1;          // toujours vrai

Objets polymorphes

Les objets d'un type classe qui déclare ou hérite d'au moins une fonction virtuelle sont des objets polymorphes. Au sein de chaque objet polymorphe, l'implémentation stocke des informations supplémentaires (dans toutes les implémentations existantes, il s'agit d'un pointeur, sauf s'il est optimisé), utilisées lors des appels de fonctions virtuelles et par les fonctionnalités RTTI (dynamic_cast et typeid) pour déterminer, à l'exécution, le type avec lequel l'objet a été créé, quelle que soit l'expression dans laquelle il est utilisé.

Pour les objets non polymorphes, l'interprétation de la valeur est déterminée par l'expression dans laquelle l'objet est utilisé, et elle est décidée à la compilation.

#include <iostream>
#include <typeinfo>

struct Base1
{
    // type polymorphe : déclare un membre virtuel
    virtual ~Base1() {}
};

struct Derived1 : Base1
{
     // type polymorphe : hérite d'un membre virtuel
};

struct Base2
{
     // type non polymorphe
};

struct Derived2 : Base2
{
     // type non polymorphe
};

int main()
{
    Derived1 obj1; // object1 créé avec le type Derived1
    Derived2 obj2; // object2 créé avec le type Derived2

    Base1& b1 = obj1; // b1 fait référence à l'objet obj1
    Base2& b2 = obj2; // b2 fait référence à l'objet obj2

    std::cout << "Expression type of b1: " << typeid(decltype(b1)).name() << '\n'
              << "Expression type of b2: " << typeid(decltype(b2)).name() << '\n'
              << "Object type of b1: " << typeid(b1).name() << '\n'
              << "Object type of b2: " << typeid(b2).name() << '\n'
              << "Size of b1: " << sizeof b1 << '\n'
              << "Size of b2: " << sizeof b2 << '\n';
}

Sortie possible :

Expression type of b1: Base1
Expression type of b2: Base2
Object type of b1: Derived1
Object type of b2: Base2
Size of b1: 8
Size of b2: 1

Alias strict

Accéder à un objet à l'aide d'une expression d'un type autre que le type avec lequel il a été créé constitue, dans de nombreux cas, un comportement indéfini, voir reinterpret_cast pour la liste des exceptions et des exemples.

Alignement

Chaque type d'objet possède la propriété appelée exigence d'alignement, qui est une valeur entière non négative (de type std::size_t, et toujours une puissance de deux) représentant le nombre d'octets entre des adresses successives auxquelles des objets de ce type peuvent être alloués.

L'exigence d'alignement d'un type peut être obtenue avec alignof ou std::alignment_of. La fonction d'alignement de pointeur std::align peut être utilisée pour obtenir un pointeur convenablement aligné dans un tampon, et std::aligned_storage peut être utilisée pour obtenir un stockage convenablement aligné.

(depuis C++11)

Chaque type d'objet impose son exigence d'alignement à chaque objet de ce type; un alignement plus strict (à exigence d'alignement plus grande) peut être demandé à l'aide de alignas (depuis C++11). Tenter de créer un objet dans un stockage qui ne satisfait pas l'exigence d'alignement du type de l'objet est un comportement indéfini.

Afin de satisfaire les exigences d'alignement de tous les membres non statiques d'une classe, des bits de remplissage peuvent être insérés après certains de ses membres.

#include <iostream>

// les objets de type S peuvent être alloués à n'importe quelle adresse
// car S.a et S.b peuvent tous deux être alloués à n'importe quelle adresse
struct S
{
    char a; // size: 1, alignment: 1
    char b; // size: 1, alignment: 1
}; // size: 2, alignment: 1

// les objets de type X doivent être alloués sur des frontières de 4 octets
// car X.n doit être alloué sur des frontières de 4 octets
// car l'exigence d'alignement de int est (généralement) 4
struct X
{
    int n;  // size: 4, alignment: 4
    char c; // size: 1, alignment: 1
    // trois octets de bits de remplissage
}; // size: 8, alignment: 4

int main()
{
    std::cout << "alignof(S) = " << alignof(S) << '\n'
              << "sizeof(S)  = " << sizeof(S) << '\n'
              << "alignof(X) = " << alignof(X) << '\n'
              << "sizeof(X)  = " << sizeof(X) << '\n';
}

Sortie possible :

alignof(S) = 1
sizeof(S)  = 2
alignof(X) = 4
sizeof(X)  = 8

L'alignement le plus faible (la plus petite exigence d'alignement) est celui de char, signed char et unsigned char, qui vaut 1 ; le plus grand alignement fondamental de tout type est défini par l'implémentationet égal à l'alignement de std::max_align_t (depuis C++11).

Les alignements fondamentaux sont pris en charge pour les objets de tous les types de durées de stockage.

Si l'alignement d'un type est rendu plus strict (plus grand) que std::max_align_t à l'aide de alignas, on parle d'un type à exigence d'alignement étendu. Un type dont l'alignement est étendu, ou un type classe dont un membre de données non statique a un alignement étendu, est un type sur-aligné.

Les types Allocator doivent gérer correctement les types sur-alignés.

(depuis C++11)

Il est défini par l'implémentation si les expressions new et (jusqu'à C++17) std::get_temporary_buffer prennent en charge les types sur-alignés.

(depuis C++11) (jusqu'à C++20)

Notes

Les objets en C++ ont une signification différente de celle des objets en programmation orientée objet (POO) :

Objets en C++ Objets en POO
peuvent avoir n'importe quel type d'objet (voir std::is_object) doivent avoir un type classe
aucune notion d'« instance » ont la notion d'« instance » (et il existe des mécanismes comme instanceof pour détecter la relation « instance-de »)
aucune notion d'« interface » ont la notion d'« interface » (et il existe des mécanismes comme instanceof pour détecter si une interface est implémentée)
le polymorphisme doit être explicitement activé via des membres virtuels le polymorphisme est toujours activé

Dans le rapport de défaut P0593R6, la création implicite d'objets était considérée comme se produisant lors de la création d'un tableau d'octets ou lors de l'appel d'une fonction d'allocation (éventuellement définie par l'utilisateur et constexpr) pendant l'évaluation constante. Cependant, une telle permission provoquait un indéterminisme dans l'évaluation constante, indésirable et non implémentable sur certains aspects. En conséquence, P2747R2 a interdit une telle création implicite d'objets dans l'évaluation constante. Nous considérons volontairement ce changement comme un rapport de défaut, bien que l'article entier ne le soit pas.
