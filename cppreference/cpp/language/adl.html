Recherche dépendante des arguments

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

La recherche dépendante des arguments (ADL), aussi appelée recherche de Koenig[1], est l'ensemble des règles de recherche des noms de fonctions non qualifiés dans les expressions d'appel de fonction, y compris les appels implicites aux opérateurs surchargés. Ces noms de fonctions sont recherchés dans les espaces de noms de leurs arguments, en plus des portées et espaces de noms considérés par la recherche de nom non qualifiée habituelle.

La recherche dépendante des arguments permet d'utiliser des opérateurs définis dans un autre espace de noms. Exemple :

#include <iostream>

int main()
{
    std::cout << "Test\n"; // Il n'existe pas d'operator<< dans l'espace de noms global, mais ADL
                           // examine l'espace de noms std car l'argument de gauche est dans
                           // std et trouve std::operator<<(std::ostream&, const char*)
    operator<<(std::cout, "Test\n"); // Idem, en utilisant la notation d'appel de fonction

    // Cependant,
    std::cout << endl; // Erreur : « endl » n'est pas déclaré dans cet espace de noms.
                       // Ce n'est pas un appel de fonction à endl(), donc ADL ne s'applique pas

    endl(std::cout); // OK : c'est un appel de fonction : ADL examine l'espace de noms std
                     // car l'argument de endl est dans std, et trouve std::endl

    (endl)(std::cout); // Erreur : « endl » n'est pas déclaré dans cet espace de noms.
                       // La sous-expression (endl) n'est pas un unqualified-id
}

Détails

Tout d'abord, la recherche dépendante des arguments n'est pas prise en compte si l'ensemble de recherche produit par la recherche non qualifiée habituelle contient l'un des éléments suivants :

  1. une déclaration de membre de classe.

  2. une déclaration de fonction à portée de bloc (qui n'est pas une using déclaration).

  3. toute déclaration qui n'est ni une fonction ni un modèle de fonction (par ex. un objet fonction ou une autre variable dont le nom entre en conflit avec celui de la fonction recherchée).

Sinon, pour chaque argument d'une expression d'appel de fonction, son type est examiné afin de déterminer l'ensemble associé d'espaces de noms et de classes qu'il ajoutera à la recherche.

  1. Pour les arguments de type fondamental, l'ensemble associé d'espaces de noms et de classes est vide.

  2. Pour les arguments de type classe (y compris union), l'ensemble se compose de :

a) La classe elle-même.

b) Si la classe est complète, toutes ses classes de base directes et indirectes.

c) Si la classe est un membre d'une autre classe, la classe dont elle est membre.

d) Les espaces de noms englobants les plus internes des classes ajoutées à l'ensemble.

  1. Pour les arguments dont le type est une spécialisation de modèle de classe, en plus des règles des classes, les classes et espaces de noms associés suivants sont ajoutés à l'ensemble.

a) Les types de tous les arguments de modèle fournis pour les paramètres de modèle de type (en ignorant les paramètres de modèle non typés et les paramètres de modèle template).

b) Les espaces de noms dont sont membres les éventuels arguments de modèle template.

c) Les classes dont sont membres les éventuels arguments de modèle template (s'il s'agit de modèles membres de classe).

  1. Pour les arguments de type énumération, l'espace de noms englobant le plus interne de la déclaration du type énumération est ajouté à l'ensemble. Si le type énumération est membre d'une classe, cette classe est ajoutée à l'ensemble.

  2. Pour les arguments de type pointeur vers T ou pointeur vers un tableau de T, le type T est examiné et son ensemble associé de classes et d'espaces de noms est ajouté à l'ensemble.

  3. Pour les arguments de type fonction, les types des paramètres de la fonction et le type de retour de la fonction sont examinés, et leur ensemble associé de classes et d'espaces de noms est ajouté à l'ensemble.

  4. Pour les arguments de type pointeur vers fonction membre F de la classe X, les types des paramètres de la fonction, le type de retour de la fonction et la classe X sont examinés, et leurs ensembles associés de classes et d'espaces de noms sont ajoutés à l'ensemble.

  5. Pour les arguments de type pointeur vers membre de donnée T de la classe X, le type du membre et le type X sont tous deux examinés, et leurs ensembles associés de classes et d'espaces de noms sont ajoutés à l'ensemble.

  6. Si l'argument est le nom ou l'expression d'adresse d'un ensemble de fonctions surchargées (ou de modèles de fonctions), chaque fonction de l'ensemble de surcharges est examinée et son ensemble associé de classes et d'espaces de noms est ajouté à l'ensemble.

  • De plus, si l'ensemble de surcharges est désigné par un identifiant de modèle, tous ses arguments de modèle de type et arguments de modèle template (mais pas les arguments de modèle non typés) sont examinés, et leurs ensembles associés de classes et d'espaces de noms sont ajoutés à l'ensemble.

Si un espace de noms de l'ensemble associé de classes et d'espaces de noms est un espace de noms en ligne, son espace de noms englobant est également ajouté à l'ensemble.

Si un espace de noms de l'ensemble associé de classes et d'espaces de noms contient directement un espace de noms en ligne, cet espace de noms en ligne est ajouté à l'ensemble.

(depuis C++11)

Une fois l'ensemble associé de classes et d'espaces de noms déterminé, toutes les déclarations trouvées dans les classes de cet ensemble sont écartées pour la suite du traitement ADL, à l'exception des fonctions amies et des modèles de fonctions amis de portée d'espace de noms, comme indiqué au point 2 ci-dessous.

L'ensemble des déclarations trouvées par la recherche non qualifiée ordinaire et l'ensemble des déclarations trouvées dans tous les éléments de l'ensemble associé produit par ADL sont fusionnés, avec les règles particulières suivantes :

Les 1) directives using dans les espaces de noms associés sont ignorées.

Les fonctions amies (et modèles de fonctions) de portée d'espace de noms qui sont déclarées dans une classe associée sont visibles par ADL même si elles ne le sont pas par la recherche ordinaire. 2)

  1. tous les noms, à l'exception des fonctions et des modèles de fonctions, sont ignorés (pas de collision avec les variables).

Notes

En raison de la recherche dépendante des arguments, les fonctions non membres et les opérateurs non membres définis dans le même espace de noms qu'une classe sont considérés comme faisant partie de l'interface publique de cette classe (s'ils sont trouvés par ADL) [2].

ADL est à l'origine de l'idiome établi pour échanger deux objets dans du code générique : using std::swap; swap(obj1, obj2); car appeler std::swap(obj1, obj2) directement ne prendrait pas en compte les fonctions swap() définies par l'utilisateur qui pourraient se trouver dans le même espace de noms que les types de obj1 ou obj2, et appeler simplement swap(obj1, obj2) sans qualification n'appellerait rien si aucune surcharge définie par l'utilisateur n'était fournie. En particulier, std::iter_swap ainsi que tous les autres algorithmes de la bibliothèque standard utilisent cette approche pour les types Swappable.

Les règles de recherche de noms rendent peu pratique la déclaration d'opérateurs dans l'espace de noms global ou dans un espace de noms défini par l'utilisateur, opérant sur des types de l'espace de noms std, par exemple un operator>> ou un operator+ personnalisé pour std::vector ou pour std::pair (sauf si les types d'éléments du vector/pair sont des types définis par l'utilisateur, ce qui ajouterait leur espace de noms à ADL). De tels opérateurs ne seraient pas recherchés depuis les instanciations de modèles, comme les algorithmes de la bibliothèque standard. Voir noms dépendants pour plus de détails.

ADL peut trouver une fonction amie (généralement un opérateur surchargé) entièrement définie dans une classe ou un modèle de classe, même si elle n'a jamais été déclarée au niveau de l'espace de noms.

template<typename T>
struct number
{
    number(int);
    friend number gcd(number x, number y) { return 0; }; // Définition dans
                                                         // un modèle de classe
};

// Sauf si une déclaration correspondante est fournie, gcd est
// un membre invisible (sauf par ADL) de cet espace de noms
void g()
{
    number<double> a(3), b(4);
    a = gcd(a, b); // Trouve gcd car number<double> est une classe associée,
                   // rendant gcd visible dans son espace de noms (portée globale)
//  b = gcd(3, 4); // Erreur ; gcd n'est pas visible
}

Bien qu'un appel de fonction puisse être résolu par ADL même si la recherche ordinaire ne trouve rien, un appel à un modèle de fonction avec des arguments de modèle explicitement spécifiés exige qu'une déclaration du modèle soit trouvée par la recherche ordinaire (sinon, c'est une erreur de syntaxe de rencontrer un nom inconnu suivi d'un caractère inférieur à).

namespace N1
{
    struct S {};

    template<int X>
    void f(S);
}

namespace N2
{
    template<class T>
    void f(T t);
}

void g(N1::S s)
{
    f<3>(s);     // Erreur de syntaxe jusqu'à C++20 (la recherche non qualifiée ne trouve aucun f)
    N1::f<3>(s); // OK, la recherche qualifiée trouve le modèle « f »
    N2::f<3>(s); // Erreur : N2::f ne prend pas de paramètre non-type
                 //        N1::f n'est pas recherché car ADL ne fonctionne qu'
                 //              avec les noms non qualifiés

    using N2::f;
    f<3>(s); // OK : la recherche non qualifiée trouve désormais N2::f
             //     puis ADL entre en jeu car ce nom est non qualifié
             //     et trouve N1::f
}

(jusqu'à C++20)

Dans les contextes suivants, seule une recherche ADL (c'est-à-dire une recherche uniquement dans les espaces de noms associés) a lieu :

  • la recherche des fonctions non membres begin et end effectuée par la boucle range-for si la recherche de membres échoue.

(depuis C++11)

  • la recherche de noms dépendants à partir du point d'instanciation du modèle.
  • la recherche de la fonction non membre get effectuée par la déclaration de liaison structurée pour les types semblables à des tuples.

(depuis C++17)

Exemple tiré de <http://www.gotw.ca/gotw/030.htm>

namespace A
{
    struct X;
    struct Y;

    void f(int);
    void g(X);
}

namespace B
{
    void f(int i)
    {
        f(i); // Appelle B::f (récursion infinie)
    }

    void g(A::X x)
    {
        g(x); // Erreur : ambiguïté entre B::g (recherche ordinaire)
              //        et A::g (recherche dépendante des arguments)
    }

    void h(A::Y y)
    {
        h(y); // Appelle B::h (récursion infinie) : ADL examine l'espace de noms A
              // mais ne trouve pas de A::h, donc seul B::h de la recherche ordinaire est utilisé
    }
}

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
CWG 33 C++98 les espaces de noms ou classes associés ne sont pas spécifiés si un argument utilisé pour la recherche est l'adresse d'un groupe de fonctions surchargées ou d'un modèle de fonction specified
CWG 90 C++98 les classes associées d'une classe imbriquée non union n'incluaient pas sa classe englobante, mais une union imbriquée était associée à sa classe englobante les non-unions sont aussi associées
CWG 239 C++98 une déclaration de fonction de portée de bloc trouvée lors de la recherche non qualifiée ordinaire n'empêchait pas ADL de s'appliquer ADL n'était pas pris en compte, sauf pour les déclarations using
CWG 997 C++98 les types de paramètres et les types de retour dépendants étaient exclus de la détermination des classes et espaces de noms associés d'un modèle de fonction included
CWG 1690 C++98 C++11 ADL ne pouvait pas trouver les lambdas (C++11) ni les objets de types de classes locales (C++98) qui sont renvoyés ils peuvent être trouvés
CWG 1691 C++11 ADL avait des comportements surprenants pour les déclarations d'énumérations opaques fixed
CWG 1692 C++98 les classes doublement imbriquées n'avaient pas d'espaces de noms associés (leurs classes englobantes ne sont membres d'aucun espace de noms) les espaces de noms associés sont étendus aux espaces de noms englobants les plus internes
CWG 2857 C++98 les classes associées d'un type de classe incomplet incluaient ses classes de base non incluses
