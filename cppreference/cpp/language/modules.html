Modules (depuis C++20)

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

La plupart des projets C++ utilisent plusieurs unités de traduction ; ils ont donc besoin de partager des déclarations et des définitions entre ces unités. L'usage des en-têtes est très répandu à cette fin, la bibliothèque standard en étant un exemple : ses déclarations sont fournies par l'inclusion de l'en-tête correspondant.

Les modules sont une fonctionnalité du langage permettant de partager des déclarations et des définitions entre unités de traduction. Ils constituent une alternative à certains cas d'usage des en-têtes.

Les modules sont orthogonaux aux espaces de noms.

// helloworld.cpp
export module helloworld; // déclaration de module

import <iostream>;        // déclaration d'importation

export void hello()       // déclaration d'exportation
{
    std::cout << "Hello world!\n";
}

// main.cpp
import helloworld; // déclaration d'importation

int main()
{
    hello();
}

Déclarations de module

Une unité de traduction peut avoir une déclaration de module, auquel cas elle est considérée comme une unité de module. La déclaration de module, si elle est fournie, doit être la première déclaration de l'unité de traduction (à l'exception du fragment de module global, traité plus loin). Chaque unité de module est associée à un nom de module (et éventuellement à une partition), fourni dans la déclaration de module.

| | | | export(facultatif) module module-name module-partition ﻿*(facultatif)* attr ﻿*(facultatif)* ; | | | |

Le nom de module est constitué d'un ou plusieurs identificateurs séparés par des points (par exemple : mymodule, mymodule.mysubmodule, mymodule2...). Les points n'ont pas de signification intrinsèque, mais sont utilisés informellement pour représenter une hiérarchie.

Si un identificateur du nom de module ou de la partition de module est défini comme macro de type objet, le programme est mal formé.

Un module nommé est l'ensemble des unités de module ayant le même nom de module.

Les unités de module dont la déclaration comporte le mot-clé export sont appelées unités d'interface de module ; toutes les autres unités de module sont appelées unités d'implémentation de module.

Pour chaque module nommé, il doit exister exactement une unité d'interface de module ne spécifiant aucune partition de module ; cette unité est appelée unité d'interface de module primaire. Son contenu exporté sera disponible lors de l'importation du module nommé correspondant.

// (chaque ligne représente une unité de traduction distincte)

export module A;   // déclare l'unité d'interface de module primaire du module nommé 'A'
module A;          // déclare une unité d'implémentation de module pour le module nommé 'A'
module A;          // déclare une autre unité d'implémentation de module pour le module nommé 'A'
export module A.B; // déclare l'unité d'interface de module primaire du module nommé 'A.B'
module A.B;        // déclare une unité d'implémentation de module pour le module nommé 'A.B'

Exportation de déclarations et de définitions

Les unités d'interface de module peuvent exporter des déclarations (y compris des définitions), qui peuvent être importées par d'autres unités de traduction. Pour exporter une déclaration, soit la faire précéder du mot-clé export, soit la placer dans un bloc export.

| | | | export declaration | | | | | export { declaration-seq ﻿*(facultatif)* } | | | |

export module A; // déclare l'unité d'interface de module primaire du module nommé 'A'

// hello() sera visible par les unités de traduction important 'A'
export char const* hello() { return "hello"; }

// world() ne sera PAS visible.
char const* world() { return "world"; }

// one() et zero() seront tous deux visibles.
export
{
    int one()  { return 1; }
    int zero() { return 0; }
}

// L'exportation d'espaces de noms fonctionne aussi : hi::english() et hi::french() seront visibles.
export namespace hi
{
    char const* english() { return "Hi!"; }
    char const* french()  { return "Salut!"; }
}

Importation de modules et d'unités d'en-tête

Les modules sont importés via une déclaration d'importation :

| | | | export(facultatif) import module-name attr ﻿*(facultatif)* ; | | | |

Toutes les déclarations et définitions exportées dans les unités d'interface du module nommé donné seront disponibles dans l'unité de traduction utilisant la déclaration d'importation.

Les déclarations d'importation peuvent être exportées dans une unité d'interface de module. Autrement dit, si le module B export-imports A, alors l'importation de B rendra également visibles toutes les exportations de A.

Dans les unités de module, toutes les déclarations d'importation (y compris les export-imports) doivent être regroupées après la déclaration de module et avant toutes les autres déclarations.

/////// A.cpp (unité d'interface de module primaire de 'A')
export module A;

export char const* hello() { return "hello"; }

/////// B.cpp (unité d'interface de module primaire de 'B')
export module B;

export import A;

export char const* world() { return "world"; }

/////// main.cpp (pas une unité de module)
#include <iostream>
import B;

int main()
{
    std::cout << hello() << ' ' << world() << '\n';
}

#include ne doit pas être utilisé dans une unité de module (en dehors du fragment de module global), car toutes les déclarations et définitions incluses seraient considérées comme faisant partie du module. On peut à la place importer les en-têtes comme unités d'en-tête avec une déclaration d'importation :

| | | | export(facultatif) import header-name attr ﻿*(facultatif)* ; | | | |

Une unité d'en-tête est une unité de traduction distincte synthétisée à partir d'un en-tête. Importer une unité d'en-tête rend accessibles toutes ses définitions et déclarations. Les macros du préprocesseur le sont aussi (car les déclarations d'importation sont reconnues par le préprocesseur).

Toutefois, contrairement à #include, les macros de préprocesseur déjà définies au point de la déclaration d'importation n'affectent pas le traitement de l'en-tête. Cela peut être gênant dans certains cas (certains en-têtes utilisent des macros de préprocesseur comme forme de configuration) ; il faut alors utiliser un fragment de module global.

/////// A.cpp (unité d'interface de module primaire de 'A')
export module A;

import <iostream>;
export import <string_view>;

export void print(std::string_view message)
{
    std::cout << message << std::endl;
}

/////// main.cpp (pas une unité de module)
import A;

int main()
{
    std::string_view message = "Hello, world!";
    print(message);
}

Fragment de module global

Les unités de module peuvent être précédées d'un fragment de module global, qui permet d'inclure des en-têtes lorsque leur importation n'est pas possible (notamment lorsque l'en-tête utilise des macros de préprocesseur comme configuration).

module;

preprocessing-directives ﻿*(facultatif)*

module-declaration

Si une unité de module possède un fragment de module global, sa première déclaration doit être module;. Ensuite, seules des directives de préprocesseur peuvent apparaître dans le fragment de module global. Puis une déclaration de module standard marque la fin du fragment de module global et le début du contenu du module.

/////// A.cpp (unité d'interface de module primaire de 'A')
module;

// La définition de _POSIX_C_SOURCE ajoute des fonctions aux en-têtes standard,
// conformément à la norme POSIX.
#define _POSIX_C_SOURCE 200809L
#include <stdlib.h>

export module A;

import <ctime>;

// Uniquement à des fins de démonstration (mauvaise source d'aléa).
// Utilisez plutôt le <random> du C++.
export double weak_random()
{
    std::timespec ts;
    std::timespec_get(&ts, TIME_UTC); // depuis <ctime>

    // Fourni dans <stdlib.h> conformément à la norme POSIX.
    srand48(ts.tv_nsec);

    // drand48() renvoie un nombre aléatoire entre 0 et 1.
    return drand48();
}

/////// main.cpp (pas une unité de module)
import <iostream>;
import A;

int main()
{
    std::cout << "Random value between 0 and 1: " << weak_random() << '\n';
}

Fragment de module privé

L'unité d'interface de module primaire peut être suivie d'un fragment de module privé, qui permet de représenter un module comme une seule unité de traduction sans rendre tout son contenu accessible aux importateurs.

module : private;

declaration-seq ﻿*(facultatif)*

Le fragment de module privé termine la partie de l'unité d'interface de module pouvant affecter le comportement des autres unités de traduction. Si une unité de module contient un fragment de module privé, elle sera la seule unité de module de son module.

export module foo;

export int f();

module : private; // termine la partie de l'unité d'interface de module qui
                  // peut affecter le comportement d'autres unités de traduction
                  // débute un fragment privé de module

int f()           // définition non accessible depuis les importateurs de foo
{
    return 42;
}

Partitions de module

Un module peut avoir des unités de partition de module. Ce sont des unités de module dont la déclaration de module comprend une partition de module, qui commence par un deux-points : et est placée après le nom du module.

export module A:B; // Déclare une unité d'interface de module pour le module 'A', partition ':B'.

Une partition de module représente exactement une unité de module (deux unités de module ne peuvent pas désigner la même partition de module). Elles ne sont visibles qu'à l'intérieur du module nommé (les unités de traduction extérieures au module nommé ne peuvent pas importer directement une partition de module).

Une partition de module peut être importée par les unités de module du même module nommé.

| | | | export(facultatif) import module-partition attr ﻿*(facultatif)* ; | | | |

/////// A-B.cpp
export module A:B;
...

/////// A-C.cpp
module A:C;
...

/////// A.cpp
export module A;

import :C;
export import :B;

...

Toutes les définitions et déclarations d'une partition de module sont visibles par l'unité de module qui l'importe, qu'elles soient exportées ou non.

Les partitions de module peuvent être des unités d'interface de module (lorsque leurs déclarations de module comportent export). Elles doivent être export-importées par l'unité d'interface de module primaire, et leurs instructions exportées seront visibles lorsque le module sera importé.

| | | | export(facultatif) import module-partition attr ﻿*(facultatif)* ; | | | |

///////  A.cpp
export module A;     // unité d'interface de module primaire

export import :B;    // Hello() est visible lors de l'importation de 'A'.
import :C;           // WorldImpl() n'est désormais visible que pour 'A.cpp'.
// export import :C; // ERREUR : impossible d'exporter une unité d'implémentation de module.

// World() est visible par toute unité de traduction important 'A'.
export char const* World()
{
    return WorldImpl();
}

/////// A-B.cpp
export module A:B; // unité d'interface de module de partition

// Hello() est visible par toute unité de traduction important 'A'.
export char const* Hello() { return "Hello"; }

/////// A-C.cpp
module A:C; // unité d'implémentation de module de partition

// WorldImpl() est visible par toute unité de module de 'A' important ':C'.
char const* WorldImpl() { return "World"; }

/////// main.cpp
import A;
import <iostream>;

int main()
{
    std::cout << Hello() << ' ' << World() << '\n';
    // WorldImpl(); // ERREUR : WorldImpl() n'est pas visible.
}

Appartenance à un module

En général, si une déclaration apparaît après la déclaration de module dans une unité de module, elle est rattachée à ce module.

Si la déclaration d'une entité est rattachée à un module nommé, cette entité ne peut être définie que dans ce module. Toutes les déclarations d'une telle entité doivent être rattachées au même module.

Si une déclaration est rattachée à un module nommé et n'est pas exportée, le nom déclaré possède une liaison de module.

export module lib_A;

int f() { return 0; } // f a une liaison de module
export int x = f();   // x vaut 0

export module lib_B;

int f() { return 1; } // OK, f dans lib_A et f dans lib_B désignent des entités différentes
export int y = f(); // y vaut 1

Si deux déclarations d'une entité sont rattachées à des modules différents, le programme est mal formé ; aucun diagnostic n'est requis si aucune des deux n'est accessible depuis l'autre.

/////// decls.h
int f(); // #1, rattachée au module global
int g(); // #2, rattachée au module global

/////// Interface du module M
module;
#include "decls.h"
export module M;
export using ::f; // OK, ne déclare aucune entité, exporte #1
int g();          // Erreur : correspond à #2, mais rattachée à M
export int h();   // #3
export int k();   // #4

/////// Autre unité de traduction
import M;
static int h();   // Erreur : correspond à #3
int k();          // Erreur : correspond à #4

Les déclarations suivantes ne sont rattachées à aucun module nommé (l'entité déclarée peut donc être définie en dehors du module) :

  • définitions d'espaces de noms à liaison externe ;
  • déclarations à l'intérieur d'une spécification de liaison de langage.
export module lib_A;

namespace ns // ns n'est pas rattaché à lib_A.
{
    export extern "C++" int f(); // f n'est pas rattachée à lib_A.
           extern "C++" int g(); // g n'est pas rattachée à lib_A.
    export              int h(); // h est rattachée à lib_A.
}
// ns::h doit être définie dans lib_A, mais ns::f et ns::g peuvent être définies ailleurs (par exemple
// dans un fichier source traditionnel).
