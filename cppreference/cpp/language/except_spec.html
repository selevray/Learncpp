Spécification dynamique d'exceptions (jusqu'à C++17)

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Liste les exceptions qu'une fonction peut lever directement ou indirectement.

Syntaxe

| | | | throw(type-id-list ﻿*(facultatif)*) | (1) | (obsolète en C++11) (supprimé en C++17) | |

  1. Spécification dynamique explicite d'exceptions.
  • type-id-list — liste séparée par des virgules de type-ids, un type-id représentant une expansion de pack est suivi d'une ellipse (...) (depuis C++11)

Une spécification dynamique explicite d'exceptions ne doit apparaître que dans un déclarateur de fonction pour un type de fonction, un type pointeur vers fonction, un type référence vers fonction, ou un type pointeur vers fonction membre, qui est le type de plus haut niveau d'une déclaration ou d'une définition, ou sur un tel type apparaissant comme type de paramètre ou de retour dans un déclarateur de fonction.

void f() throw(int);            // OK : déclaration de fonction
void (*pf)() throw (int);       // OK : déclaration de pointeur vers fonction
void g(void pfa() throw(int));  // OK : déclaration de paramètre de pointeur vers fonction
typedef int (*pf)() throw(int); // Erreur : déclaration typedef

Explication

Si une fonction est déclarée avec le type T listé dans sa spécification dynamique d'exceptions, la fonction peut lever des exceptions de ce type ou d'un type dérivé de celui-ci.

Les types incomplets, les pointeurs ou références vers des types incomplets autres que qualifiés cv void*, et les types référence rvalue (depuis C++11) ne sont pas autorisés dans la spécification d'exceptions. Les types tableau et fonction, s'ils sont utilisés, sont ajustés vers les types pointeurs correspondants, et les qualificateurs cv de plus haut niveau sont également supprimés. Les packs de paramètres sont autorisés (depuis C++11).

Une spécification dynamique d'exceptions dont l'ensemble des types ajustés est vide (après expansion de tous les packs) (depuis C++11) est sans lancer d'exception. Une fonction dont la spécification dynamique d'exceptions est sans lancer n'autorise aucune exception.

Une spécification dynamique d'exceptions ne fait pas partie du type d'une fonction.

Si la fonction lève une exception d'un type non listé dans sa spécification d'exceptions, la fonction std::unexpected est appelée. La fonction par défaut appelle std::terminate, mais elle peut être remplacée par une fonction fournie par l'utilisateur (via std::set_unexpected) qui peut appeler std::terminate ou lever une exception. Si l'exception levée par std::unexpected est acceptée par la spécification d'exceptions, le déroulement de la pile se poursuit normalement. Sinon, si std::bad_exception est autorisée par la spécification d'exceptions, std::bad_exception est levée. Dans le cas contraire, std::terminate est appelée.

Instanciation

La spécification dynamique d'exceptions d'une spécialisation de modèle de fonction n'est pas instanciée avec la déclaration de la fonction ; elle n'est instanciée que lorsqu'elle est nécessaire (comme défini ci-dessous).

La spécification dynamique d'exceptions d'une fonction membre spéciale déclarée implicitement n'est aussi évaluée que lorsqu'elle est nécessaire (en particulier, la déclaration implicite d'une fonction membre d'une classe dérivée n'impose pas l'instanciation de la spécification d'exceptions d'une fonction membre de la classe de base).

Lorsque la spécification dynamique d'exceptions d'une spécialisation de modèle de fonction est nécessaire mais n'a pas encore été instanciée, les noms dépendants sont recherchés et les modèles utilisés dans la expression sont instanciés comme pour la déclaration de la spécialisation.

Une spécification dynamique d'exceptions d'une fonction est considérée comme nécessaire dans les contextes suivants :

  • dans une expression, lorsque la fonction est sélectionnée par résolution de surcharge
  • la fonction est odr-used
  • la fonction serait odr-used mais apparaît dans un opérande non évalué
template<class T>
T f() throw(std::array<char, sizeof(T)>);

int main()
{
    decltype(f<void>()) *p; // f non évaluée, mais la spécification d'exception est nécessaire
                            // erreur due à l'instanciation de la spécification d'exception
                            // calcule sizeof(void)
}
  • la spécification est nécessaire pour être comparée à une autre déclaration de fonction (par exemple sur un remplaçant de fonction virtuelle ou sur une spécialisation explicite d'un modèle de fonction)
  • dans une définition de fonction
  • la spécification est nécessaire parce qu'une fonction membre spéciale par défaut doit la vérifier afin de décider de sa propre spécification d'exceptions (ce qui n'a lieu que lorsque la spécification de la fonction membre spéciale par défaut est, elle-même, nécessaire).

Exceptions potentielles

Chaque fonction f, pointeur vers fonction pf et pointeur vers fonction membre pmf possède un ensemble d'exceptions potentielles, constitué des types qui pourraient être levés. L'ensemble de tous les types indique que n'importe quelle exception peut être levée. Cet ensemble est défini comme suit :

  1. Si la déclaration de f, pf ou pmf utilise une spécification d'exception dynamiquequi n'autorise pas toutes les exceptions (jusqu'à C++11), l'ensemble est constitué des types listés dans cette spécification.
  1. Sinon, si la déclaration de f, pf ou pmf utilise noexcept(true), l'ensemble est vide.

(depuis C++11)

  1. Sinon, l'ensemble est l'ensemble de tous les types.

Remarque : pour les fonctions membres spéciales déclarées implicitement (constructeurs, opérateurs d'affectation et destructeurs)ainsi que pour les constructeurs hérités (depuis C++11), l'ensemble des exceptions potentielles est une combinaison des ensembles des exceptions potentielles de tout ce qu'elles appelleraient : constructeurs, opérateurs d'affectation et destructeurs des membres de données non variants non statiques, des bases directes et, le cas échéant, des bases virtuelles (y compris les expressions d'arguments par défaut, comme toujours).

Chaque expression e possède un ensemble d'exceptions potentielles. L'ensemble est vide si e est une expression constante de cœur, sinon il s'agit de l'union des ensembles d'exceptions potentielles de toutes les sous-expressions immédiates de e (y compris les expressions d'arguments par défaut), combinée à un autre ensemble qui dépend de la forme de e, comme suit :

  1. Si e est une expression d'appel de fonction, soit g désignant la fonction, le pointeur vers fonction ou le pointeur vers fonction membre appelé, alors
  • si la déclaration de g utilise une spécification d'exception dynamique, l'ensemble des exceptions potentielles de g est ajouté à l'ensemble ;
  • si la déclaration de g utilise noexcept(true), l'ensemble est vide ;

(depuis C++11)

  • sinon, l'ensemble est l'ensemble de tous les types.

  1. Si e appelle une fonction implicitement (il s'agit d'une expression d'opérateur et l'opérateur est surchargé, c'est une expression new et la fonction d'allocation est surchargée, ou c'est une expression complète et le destructeur d'un temporaire est appelé), alors l'ensemble est celui de cette fonction.

  2. Si e est une expression throw, l'ensemble est l'exception qui serait initialisée par son opérande, ou l'ensemble de tous les types pour l'expression throw de relance (sans opérande).

  3. Si e est une dynamic_cast vers une référence à un type polymorphe, l'ensemble est constitué de std::bad_cast.

  4. Si e est une typeid appliqué à un pointeur déréférencé vers un type polymorphe, l'ensemble est constitué de std::bad_typeid.

  1. Si e est une expression new avec une taille de tableau non constante, et que la fonction d'allocation sélectionnée a un ensemble d'exceptions potentielles non vide, l'ensemble est constitué de std::bad_array_new_length.

(depuis C++11)

void f() throw(int); // l'ensemble de f() est "int"
void g();            // l'ensemble de g() est l'ensemble de tous les types

struct A { A(); };                  // l'ensemble de "new A" est l'ensemble de tous les types
struct B { B() noexcept; };         // l'ensemble de "B()" est vide
struct D() { D() throw (double); }; // l'ensemble de new D est l'ensemble de tous les types

Toutes les fonctions membres déclarées implicitement et les constructeurs hérités *(depuis C++11)*possèdent des spécifications d'exception, sélectionnées comme suit :

  • Si l'ensemble des exceptions potentielles est l'ensemble de tous les types, la spécification d'exception implicite [autorise toutes les exceptions (la spécification d'exception est considérée comme présente, bien qu'elle ne puisse pas être exprimée dans le code et se comporte comme s'il n'y avait aucune spécification d'exception) (jusqu'à C++11) | est noexcept(false) (depuis C++11)].
  • Sinon, si l'ensemble des exceptions potentielles n'est pas vide, la spécification d'exception implicite énumère chaque type de l'ensemble.
  • Sinon, la spécification d'exception implicite est [throw() (jusqu'à C++11) | noexcept(true) (depuis C++11)].
struct A
{
    A(int = (A(5), 0)) noexcept;
    A(const A&) throw();
    A(A&&) throw();
    ~A() throw(X);
};

struct B
{
    B() throw();
    B(const B&) = default; // la spécification d'exception est "noexcept(true)"
    B(B&&, int = (throw Y(), 0)) noexcept;
    ~B() throw(Y);
};

int n = 7;
struct D : public A, public B
{
    // Peut lever une exception d'un type qui correspondrait à un gestionnaire de type
    // std​::​bad_array_new_length, mais ne lève pas d'exception d'allocation défaillante (bad allocation)
    (void*) new (std::nothrow) int[n];

    // D peut avoir les membres déclarés implicitement suivants :
    // D::D() throw(X, std::bad_array_new_length);
    // D::D(const D&) noexcept(true);
    // D::D(D&&) throw(Y);
    // D::~D() throw(X, Y);
};

Notes

Clang considère que la règle d'instanciation des spécifications d'exception dynamiques a été modifiée en C++11 par CWG1330, voir LLVM #56349.

Exemple

Remarque : il vaut mieux compiler en mode C++98 pour éviter les avertissements. Incompatible avec C++17 et les révisions plus récentes.

#include <cstdlib>
#include <exception>
#include <iostream>

class X {};
class Y {};
class Z : public X {};
class W {};

void f() throw(X, Y)
{
    bool n = false;

    if (n)
        throw X(); // OK, appellerait std::terminate()
    if (n)
        throw Z(); // aussi OK

    throw W(); // appellera std::unexpected()
}

void handler()
{
    std::cerr << "That was unexpected!\n"; // vidage nécessaire
    std::abort();
}

int main()
{
    std::set_unexpected(handler);
    f();
}

Output:

That was unexpected!

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
CWG 25 C++98 le comportement de l'affectation et de l'initialisation entre pointeurs vers membres ayant des spécifications d'exception différentes était non spécifié appliquer la restriction aux pointeurs de fonction et aux références
CWG 973 C++98 une spécification d'exception pouvait contenir des types de fonctions, mais la conversion de pointeur de fonction correspondante n'était pas spécifiée specified
CWG 1330 C++98 une spécification d'exception pouvait être instanciée de manière anticipée elle n'est instanciée que si nécessaire
CWG 1267 C++11 les types de références rvalue étaient autorisés dans les spécifications d'exception non autorisé
CWG 1351 C++98 C++11 l'argument par défaut (C++98) et l'initialiseur de membre par défaut (C++11) étaient ignorés dans la spécification d'exception implicite rendu pris en compte
CWG 1777 C++11 throw(T...) n'était pas une spécification non levante même si T est un pack vide elle est non levante si le pack est vide
CWG 2191 C++98 l'ensemble des exceptions potentielles d'une expression typeid pouvait contenir bad_typeid même si elle ne pouvait pas être levée contient bad_typeid seulement si elle peut être levée
