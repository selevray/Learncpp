Classes dérivées

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Tout type de classe (qu'il soit déclaré avec class-key class ou struct) peut être déclaré dérivé d'une ou plusieurs classes de base, lesquelles peuvent à leur tour dériver de leurs propres classes de base, formant une hiérarchie d'héritage.

Syntaxe

La liste des classes de base est fournie dans base-clause de la syntaxe de déclaration de classe. Le base-clause consiste en le caractère : suivi d'une liste, séparée par des virgules, d'un ou plusieurs base-specifier.

  1. spécifie un héritage non virtuel avec l'accessibilité des membres par défaut.

  2. spécifie un héritage virtuel avec l'accessibilité des membres par défaut.

  3. spécifie un héritage non virtuel avec l'accessibilité des membres donnée.

  4. spécifie un héritage virtuel avec l'accessibilité des membres donnée.

  5. Identique à 4), virtual et access-specifier peuvent apparaître dans n'importe quel ordre.

Un spécificateur de type elaborated ne peut pas apparaître directement comme class-or-computed en raison de limitations de syntaxe.

Les base-specifiers dans un base-clause peuvent être des expansions de paquets.

Une classe ou structure déclarée final ne peut pas être désignée par class-or-computed.

(depuis C++11)

Si access-specifier est omis, il vaut par défaut public pour les classes dérivées déclarées avec class-key struct, et private pour les classes dérivées déclarées avec class-key class.

struct Base
{
    int a, b, c;
};

// chaque objet de type Derived inclut Base comme sous-objet
struct Derived : Base
{
    int b;
};

// chaque objet de type Derived2 inclut Derived et Base comme sous-objets
struct Derived2 : Derived
{
    int c;
};

Les classes désignées par les class-or-computed listés dans base-clause sont des classes de base directes. Leurs bases sont des classes de base indirectes. Une même classe ne peut pas être spécifiée comme classe de base directe plus d'une fois, mais une même classe peut être à la fois classe de base directe et indirecte.

Chaque classe de base directe et indirecte est présente, en tant que sous-objet de classe de base, dans la représentation objet de la classe dérivée, à un décalage dépendant de l'ABI. Les classes de base vides n'augmentent généralement pas la taille de l'objet dérivé grâce à l'optimisation de la base vide. Les constructeurs des sous-objets de classes de base sont appelés par le constructeur de la classe dérivée : des arguments peuvent être fournis à ces constructeurs dans la liste d'initialisation des membres.

Classes de base virtuelles

Pour chaque classe de base distincte spécifiée virtual, l'objet le plus dérivé ne contient qu'un seul sous-objet de classe de base de ce type, même si la classe apparaît plusieurs fois dans la hiérarchie d'héritage (tant qu'elle est héritée virtual à chaque fois).

struct B { int n; };
class X : public virtual B {};
class Y : virtual public B {};
class Z : public B {};

// chaque objet de type AA possède un X, un Y, un Z et deux B :
// l'un qui est la base de Z et l'autre qui est partagé par X et Y
struct AA : X, Y, Z
{
    AA()
    {
        X::n = 1; // modifie le membre du sous-objet B virtuel
        Y::n = 2; // modifie le membre du même sous-objet B virtuel
        Z::n = 3; // modifie le membre du sous-objet B non virtuel

        std::cout << X::n << Y::n << Z::n << '\n'; // prints 223
    }
};

Un exemple de hiérarchie d'héritage avec des classes de base virtuelles est la hiérarchie des iostreams de la bibliothèque standard : std::istream et std::ostream dérivent de std::ios par héritage virtuel. std::iostream dérive à la fois de std::istream et de std::ostream, donc chaque instance de std::iostream contient un sous-objet std::ostream, un sous-objet std::istream et un seul sous-objet std::ios (et, par conséquent, un std::ios_base).

Tous les sous-objets de base virtuels sont initialisés avant tout sous-objet de base non virtuel, donc seule la classe la plus dérivée appelle les constructeurs des bases virtuelles dans sa liste d'initialisation des membres :

struct B
{
    int n;

    B(int x) : n(x) {}
};

struct X : virtual B { X() : B(1) {} };
struct Y : virtual B { Y() : B(2) {} };
struct AA : X, Y     { AA() : B(3), X(), Y() {} };

// le constructeur par défaut de AA appelle les constructeurs par défaut de X et Y
// mais ces constructeurs n'appellent pas le constructeur de B car B est une base virtuelle
AA a; // a.n == 3

// le constructeur par défaut de X appelle le constructeur de B
X x;  // x.n == 1

Il existe des règles particulières pour la recherche de nom non qualifiée des membres de classe lorsque l'héritage virtuel est impliqué (parfois appelées règles de dominance).

Héritage public

Lorsqu'une classe utilise public spécificateur d'accès membre pour dériver d'une base, tous les membres publics de la classe de base sont accessibles en tant que membres publics de la classe dérivée, et tous les membres protégés de la classe de base sont accessibles en tant que membres protégés de la classe dérivée (les membres privés de la base ne sont jamais accessibles, sauf si la classe est déclarée amie).

L'héritage public modélise la relation de sous-typage de la programmation orientée objet : un objet de la classe dérivée EST UN objet de la classe de base. Les références et pointeurs vers un objet dérivé doivent pouvoir être utilisés par tout code attendant des références ou pointeurs vers l'une de ses bases publiques (voir LSP) ou, en termes de DbC, une classe dérivée doit préserver les invariants de classe de ses bases publiques, et ne doit renforcer aucune précondition ni affaiblir aucune postcondition d'une fonction membre qu'elle redéfinit.

#include <iostream>
#include <string>
#include <vector>

struct MenuOption { std::string title; };

// Menu est un vector de MenuOption : des options peuvent être insérées, supprimées, réordonnées...
// et possède un titre.
class Menu : public std::vector<MenuOption>
{
public:
    std::string title;

    void print() const
    {
        std::cout << title << ":\n";
        for (std::size_t i = 0, s = size(); i < s; ++i)
            std::cout << "  " << (i + 1) << ". " << at(i).title << '\n';
    }
};
// Remarque : Menu::title ne pose pas de problème car son rôle est indépendant de la classe de base.

enum class Color { WHITE, RED, BLUE, GREEN };

void apply_terminal_color(Color) { /* Spécifique à l'OS */ }

// C'EST MAUVAIS !
// ColorMenu est un Menu dont chaque option possède une couleur personnalisée.
class ColorMenu : public Menu
{
public:
    std::vector<Color> colors;

    void print() const
    {
        std::cout << title << ":\n";

        for (std::size_t i = 0, s = size(); i < s; ++i)
        {
            std::cout << "  " << (i + 1) << ". ";
            apply_terminal_color(colors[i]);
            std::cout << at(i).title << '\n';
            apply_terminal_color(Color::WHITE);
        }
    }
};
// ColorMenu nécessite les invariants suivants qui ne peuvent pas être satisfaits
// par un héritage public de Menu, par exemple :
// - ColorMenu::colors et Menu doivent avoir le même nombre d'éléments
// - Pour que cela ait un sens, l'appel à erase() doit aussi supprimer des éléments de colors,
//   afin de permettre aux options de conserver leurs couleurs
// En fait, presque chaque appel non const à une méthode de std::vector violera l'invariant
// de ColorMenu et l'utilisateur devra le corriger en gérant correctement colors.

int main()
{
    ColorMenu color_menu;

    // Le gros problème de cette classe est que nous devons garder ColorMenu::Color
    // synchronisé avec Menu.
    color_menu.push_back(MenuOption{"Some choice"});

    // color_menu.print(); // ERREUR ! colors[i] dans print() est hors limites

    color_menu.colors.push_back(Color::RED);

    color_menu.print(); // OK : colors et Menu ont le même nombre d'éléments
}

Héritage protégé

Lorsqu'une classe utilise protected spécificateur d'accès membre pour dériver d'une base, tous les membres publics et protégés de la classe de base sont accessibles en tant que membres protégés de la classe dérivée (les membres privés de la base ne sont jamais accessibles, sauf si la classe est déclarée amie).

L'héritage protégé peut être utilisé pour un « polymorphisme contrôlé » : à l'intérieur des membres de Derived, ainsi que dans les membres de toutes les classes dérivées plus loin, la classe dérivée EST UNE base : les références et pointeurs vers Derived peuvent être utilisés là où des références et pointeurs vers Base sont attendus.

Héritage privé

Lorsqu'une classe utilise private spécificateur d'accès membre pour dériver d'une base, tous les membres publics et protégés de la classe de base sont accessibles en tant que membres privés de la classe dérivée (les membres privés de la base ne sont jamais accessibles, sauf si la classe est déclarée amie).

L'héritage privé est couramment utilisé dans la conception basée sur les politiques, car les politiques sont généralement des classes vides ; les utiliser comme bases permet à la fois un polymorphisme statique et tire parti de l'optimisation de base vide.

L'héritage privé peut aussi servir à implémenter la relation de composition (le sous-objet de classe de base est un détail d'implémentation de l'objet de la classe dérivée). Utiliser un membre offre une meilleure encapsulation et est généralement préféré, sauf si la classe dérivée a besoin d'accéder aux membres protégés (y compris les constructeurs) de la base, doit redéfinir un membre virtuel de la base, a besoin que la base soit construite avant et détruite après un autre sous-objet de base, a besoin de partager une base virtuelle ou doit contrôler la construction d'une base virtuelle. L'utilisation de membres pour implémenter la composition n'est pas non plus applicable dans le cas d'un héritage multiple à partir d'un pack de paramètres ou lorsque l'identité des classes de base est déterminée à la compilation par métaprogrammation de modèles.

De même que l'héritage protégé, l'héritage privé peut aussi servir au polymorphisme contrôlé : à l'intérieur des membres de la classe dérivée (mais pas dans les classes plus dérivées encore), la classe dérivée EST UNE base.

template<typename Transport>
class service : private Transport // héritage privé de la politique de transport Transport
{
public:
    void transmit()
    {
        this->send(...); // envoie en utilisant le transport fourni
    }
};

// politique de transport TCP
class tcp
{
public:
    void send(...);
};

// politique de transport UDP
class udp
{
public:
    void send(...);
};

service<tcp> service(host, port);
service.transmit(...); // envoie via TCP
