Définitions et ODR (Règle de définition unique)

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Les définitions sont des déclarations qui définissent entièrement l'entité introduite par la déclaration. Toute déclaration est une définition, à l'exception des suivantes :

  • Une déclaration de fonction sans corps de fonction :
int f(int); // déclare, mais ne définit pas f
  • Toute déclaration avec un extern spécificateur de classe de stockage ou avec un spécificateur de liaison de langage (tel que extern "C") sans initialisateur :
extern const int a;     // déclare, mais ne définit pas a
extern const int b = 1; // définit b
  • Déclaration d'un non-inline (depuis C++17) membre de donnée statique à l'intérieur d'une définition de classe :
struct S
{
    int n;               // définit S::n
    static int i;        // déclare, mais ne définit pas S::i
    inline static int x; // définit S::x
};                       // définit S

int S::i;                // définit S::i
  • (obsolète) Déclaration, dans la portée d'espace de noms, d'un membre de donnée statique défini dans la classe avec le spécificateur constexpr :
struct S
{
    static constexpr int x = 42; // implicitement inline, définit S::x
};

constexpr int S::x; // déclare S::x, ce n'est pas une redéfinition

(depuis C++17)

  • Déclaration d'un nom de classe (par déclaration anticipée ou par l'utilisation du spécificateur de type élaboré dans une autre déclaration) :
struct S;             // déclare, mais ne définit pas S

class Y f(class T p); // déclare, mais ne définit pas Y et T (ainsi que f et p)
  • Une déclaration opaque d'énumération :
enum Color : int; // déclare, mais ne définit pas Color

(depuis C++11)

  • Déclaration d'un paramètre de modèle :
template<typename T> // déclare, mais ne définit pas T
  • Une déclaration de paramètre dans une déclaration de fonction qui n'est pas une définition :
int f(int x); // déclare, mais ne définit pas f et x

int f(int x)  // définit f et x
{
    return x + a;
}
  • Une déclaration typedef :
typedef S S2; // déclare, mais ne définit pas S2 (S peut être incomplet)
  • Une déclaration d'alias :
using S2 = S; // déclare, mais ne définit pas S2 (S peut être incomplet)

(depuis C++11)

  • Une déclaration using :
using N::d; // déclare, mais ne définit pas d
  • Déclaration d'un guide de déduction (ne définit aucune entité)

(depuis C++17)

  • Une déclaration static_assert (ne définit aucune entité)
  • Une déclaration d'attribut (ne définit aucune entité)

(depuis C++11)

  • Une déclaration vide (ne définit aucune entité)
  • Une directive using (ne définit aucune entité)
  • Une déclaration d'instanciation explicite (un « extern template ») :
extern template
f<int, char>; // déclare, mais ne définit pas f<int, char>

(depuis C++11)

  • Une spécialisation explicite dont la déclaration n'est pas une définition :
template<>
struct A<int>; // déclare, mais ne définit pas A<int>

Une déclaration asm ne définit aucune entité, mais elle est classée comme une définition.

Lorsque nécessaire, le compilateur peut définir implicitement le constructeur par défaut, le constructeur de copie, le constructeur de déplacement, l'opérateur d'affectation par copie, l'opérateur d'affectation par déplacement et le destructeur.

Si la définition d'un objet quelconque aboutit à un objet de type incomplet ou de type classe abstraite, le programme est mal formé.

Règle de la définition unique

Une seule définition de toute variable, fonction, type classe, type énumération, concept (depuis C++20) ou modèle est autorisée dans une même unité de traduction (certaines peuvent avoir plusieurs déclarations, mais une seule définition est autorisée).

Une et une seule définition de chaque fonction ou variable non-inline qui est odr-used (voir ci-dessous) doit apparaître dans l'ensemble du programme (y compris toutes les bibliothèques standard et définies par l'utilisateur). Le compilateur n'est pas tenu de diagnostiquer cette violation, mais le comportement du programme qui la viole est indéfini.

Pour une fonction inline ou une variable inline (depuis C++17), une définition est requise dans chaque unité de traduction où elle est odr-used.

Pour une classe, une définition est requise partout où la classe est utilisée d'une manière qui exige qu'elle soit complète.

Un programme peut contenir plus d'une définition de chacun des éléments suivants : type classe, type énumération, fonction inline, variable inline (depuis C++17), entité templatisée (modèle ou membre de modèle, mais pas une spécialisation de modèle complète), à condition que toutes les conditions suivantes soient satisfaites :

  • Chaque définition apparaît dans une unité de traduction différente.
  • Les définitions ne sont pas rattachées à un module nommé.

(depuis C++20)

  • Chaque définition est constituée de la même suite de jetons (en général, elle apparaît dans le même en-tête).
  • La recherche de nom effectuée depuis chaque définition trouve les mêmes entités (après résolution de surcharge), à l'exception près que :
    • Les constantes à liaison interne ou sans liaison peuvent faire référence à des objets différents tant qu'elles ne sont pas odr-used et qu'elles ont les mêmes valeurs dans chaque définition.
  • Les expressions lambda qui ne figurent pas dans un argument par défautou un argument de modèle par défaut (depuis C++20) sont identifiées de manière unique par la suite de jetons utilisée pour les définir.

(depuis C++11)

  • Les opérateurs surchargés, y compris les fonctions de conversion, d'allocation et de désallocation, désignent la même fonction dans chaque définition (sauf s'ils désignent une fonction définie dans la définition elle-même).
  • Les entités correspondantes ont la même liaison de langage dans chaque définition (par exemple, le fichier d'inclusion ne se trouve pas dans un bloc extern "C").
  • Si un objet const est initialisé en constante dans l'une des définitions, il est initialisé en constante dans chaque définition.
  • Les règles ci-dessus s'appliquent à chaque argument par défaut utilisé dans chaque définition.
  • Si la définition concerne une classe possédant un constructeur déclaré implicitement, chaque unité de traduction où elle est odr-used doit appeler le même constructeur pour la base et les membres.
  • Si la définition concerne une classe possédant un opérateur de comparaison à trois voies par défaut, chaque unité de traduction où elle est odr-used doit appeler le même opérateur de comparaison pour la base et les membres.

(depuis C++20)

  • Si la définition concerne un modèle, alors toutes ces exigences s'appliquent aux noms au point de définition ainsi qu'aux noms dépendants au point d'instanciation.

Si toutes ces exigences sont satisfaites, le programme se comporte comme s'il n'existait qu'une seule définition dans l'ensemble du programme. Sinon, le programme est mal formé, aucun diagnostic requis.

Note : en C, il n'existe pas d'ODR à l'échelle du programme pour les types, et même des déclarations extern de la même variable dans différentes unités de traduction peuvent avoir des types différents tant qu'ils sont compatibles. En C++, les jetons de code source utilisés dans les déclarations d'un même type doivent être identiques, comme décrit ci-dessus : si un fichier .cpp définit struct S { int x; }; et l'autre fichier .cpp définit struct S { int y; };, le comportement du programme qui les lie ensemble est indéfini. Ceci se résout généralement avec des espaces de noms sans nom.

Désignation d'une entité

Une variable est désignée par une expression si l'expression est une expression d'identifiant qui la dénote.

Une fonction est désignée par une expression ou une conversion dans les cas suivants :

  • Une fonction dont le nom apparaît comme expression ou conversion (y compris une fonction nommée, un opérateur surchargé, une conversion définie par l'utilisateur, les formes de placement définies par l'utilisateur de operator new, l'initialisation non par défaut) est désignée par cette expression si elle est sélectionnée par la résolution de surcharge, sauf s'il s'agit d'une fonction membre virtuelle pure non qualifiée ou d'un pointeur vers membre désignant une fonction virtuelle pure.
  • Une fonction d'allocation ou de désallocation d'une classe est désignée par une expression new apparaissant dans une expression.
  • Une fonction de désallocation d'une classe est désignée par une expression delete apparaissant dans une expression.
  • Un constructeur sélectionné pour copier ou déplacer un objet est considéré comme désigné par l'expression ou la conversion, même si une élision de copie a lieu. L'utilisation d'une prvalue dans certains contextes ne copie ni ne déplace un objet, voir élision obligatoire. (depuis C++17)

Une expression ou conversion potentiellement évaluée odr-use une fonction si elle la désigne.

Une expression ou conversion potentiellement évaluée en constante qui désigne une fonction constexpr la rend nécessaire à l'évaluation constante, ce qui déclenche la définition d'une fonction par défaut ou l'instanciation d'une spécialisation de modèle de fonction, même si l'expression n'est pas évaluée.

(depuis C++11)

Résultats potentiels

L'ensemble des résultats potentiels d'une expression E est un ensemble (éventuellement vide) d'expressions d'identifiant apparaissant dans E, combinées comme suit :

  • Si E est une expression d'identifiant, l'expression E en est le seul résultat potentiel.
  • Si E est une expression d'indexation (E1[E2]) où l'un des opérandes est un tableau, les résultats potentiels de cet opérande sont inclus dans l'ensemble.
  • Si E est une expression d'accès à un membre de classe de la forme E1.E2 ou E1.template E2 désignant un membre de données non statique, les résultats potentiels de E1 sont inclus dans l'ensemble.
  • Si E est une expression d'accès à un membre de classe désignant un membre de données statique, l'expression d'identifiant désignant le membre de données est incluse dans l'ensemble.
  • Si E est une expression d'accès à un pointeur vers membre de la forme E1.*E2 ou E1.*template E2 dont le second opérande est une expression constante, les résultats potentiels de E1 sont inclus dans l'ensemble.
  • Si E est une expression entre parenthèses ((E1)), les résultats potentiels de E1 sont inclus dans l'ensemble.
  • Si E est une expression conditionnelle de glvalue (E1 ? E2 : E3, où E2 et E3 sont des glvalues), l'union des résultats potentiels de E2 et de E3 sont tous deux inclus dans l'ensemble.
  • Si E est une expression virgule (E1, E2), les résultats potentiels de E2 sont dans l'ensemble des résultats potentiels.
  • Sinon, l'ensemble est vide.

ODR-use (définition informelle)

Un objet est odr-used si sa valeur est lue (sauf s'il s'agit d'une constante de compilation) ou écrite, si son adresse est prise, ou si une référence y est liée,

Une référence est odr-used si elle est utilisée et que son référent n'est pas connu à la compilation,

Une fonction est odr-used si un appel de fonction est effectué vers elle ou si son adresse est prise.

Si une entité est odr-used, sa définition doit exister quelque part dans le programme ; une violation de cette règle se traduit généralement par une erreur d'édition de liens.

struct S
{
    static const int x = 0; // membre de données statique
    // une définition hors de la classe est requise s'il est odr-utilisé
};

const int& f(const int& r);

int n = b ? (1, S::x) // S::x n'est pas odr-utilisé ici
          : f(S::x);  // S::x est odr-utilisé ici : une définition est requise

ODR-use (définition formelle)

Une variable x désignée par une expression potentiellement évaluée expr qui apparaît en un point P est odr-used par expr, sauf si l'une des conditions suivantes est satisfaite :

  • x est une référence utilisable dans les expressions constantes en P.
  • x n'est pas une référence et (jusqu'à C++26)expr est un élément de l'ensemble des résultats potentiels d'une expression E, et l'une des conditions suivantes est satisfaite :
    • E est une expression de valeur ignorée, et aucune conversion lvalue-vers-rvalue ne lui est appliquée.
    • x est un objet non volatile (depuis C++26) utilisable dans les expressions constantes en P et ne possédant aucun sous-objet mutable, et l'une des conditions suivantes est satisfaite :
  • E est une expression d'accès à un membre de classe désignant un membre de données non statique de type référence et dont l'expression d'objet a un type non qualifié volatile.

(depuis C++26)

  • E a un type non classe non qualifié volatile, et la conversion lvalue-vers-rvalue lui est appliquée.
struct S { static const int x = 1; }; // application de la conversion de lvalue en rvalue
                                      // à S::x donne une expression constante

int f()
{
    S::x;        // l'expression à valeur ignorée n'odr-utilise pas S::x

    return S::x; // expression à laquelle la conversion de lvalue en rvalue
                 // s'applique n'odr-utilise pas S::x
}

*this est odr-used si this apparaît comme expression potentiellement évaluée (y compris le this implicite dans une expression d'appel de fonction membre non statique).

Une liaison structurée est odr-used si elle apparaît comme expression potentiellement évaluée.

(depuis C++17)

Une fonction est odr-used dans les cas suivants :

  • Une fonction est odr-used si elle est désignée (voir ci-dessous) par une expression ou conversion potentiellement évaluée.
  • Une fonction membre virtuelle est odr-used si elle n'est pas une fonction membre virtuelle pure (les adresses des fonctions membres virtuelles sont nécessaires pour construire la vtable).
  • Une fonction d'allocation ou de désallocation non placement d'une classe est odr-used par la définition d'un constructeur de cette classe.
  • Une fonction de désallocation non placement d'une classe est odr-used par la définition du destructeur de cette classe, ou par le fait d'être sélectionnée par la recherche au point de définition d'un destructeur virtuel.
  • Un opérateur d'affectation dans une classe T qui est un membre ou une base d'une autre classe U est odr-used par les fonctions d'affectation par copie ou par déplacement implicitement définies de U.
  • Un constructeur (y compris les constructeurs par défaut) d'une classe est odr-used par l'initialisation qui le sélectionne.
  • Un destructeur d'une classe est odr-used s'il est potentiellement invoqué.
