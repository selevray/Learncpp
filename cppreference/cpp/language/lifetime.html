Durée de vie

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Chaque objet et référence a une durée de vie, qui est une propriété d'exécution : pour tout objet ou référence, il existe un point d'exécution du programme où sa durée de vie commence, et un moment où elle se termine.

La durée de vie d'un objet commence lorsque :

  • un stockage ayant l'alignement et la taille appropriés à son type est obtenu, et
  • son initialisation (le cas échéant) est terminée (y compris l'initialisation par défaut sans constructeur ou avec un constructeur par défaut trivial), sauf que
    • si l'objet est un membre d'union ou un sous-objet de celui-ci, sa durée de vie ne commence que si ce membre d'union est le membre initialisé de l'union, ou s'il est rendu actif,
    • si l'objet est imbriqué dans un objet union, sa durée de vie peut commencer si l'objet union englobant est affecté ou construit par une fonction membre spéciale triviale,
    • la durée de vie d'un objet tableau peut également commencer s'il est alloué par std::allocator::allocate.

Certaines opérations créent implicitement des objets de types à durée de vie implicite dans une région donnée de stockage et en démarrent la durée de vie. Si un sous-objet d'un objet créé implicitement n'est pas d'un type à durée de vie implicite, sa durée de vie ne commence pas implicitement.

La durée de vie d'un objet se termine lorsque :

  • s'il est d'un type non classe, l'objet est détruit (éventuellement via un appel de pseudo-destructeur), ou
  • s'il est d'un type classe, l'appel du destructeur commence, ou
  • le stockage occupé par l'objet est libéré, ou est réutilisé par un objet qui n'est pas imbriqué dans celui-ci.

La durée de vie d'un objet est égale ou est imbriquée dans la durée de vie de son stockage, voir durée de stockage.

La durée de vie d'une référence commence lorsque son initialisation est terminée et se termine comme s'il s'agissait d'un objet scalaire.

Remarque : la durée de vie de l'objet référencé peut se terminer avant la fin de la durée de vie de la référence, ce qui rend possibles des références pendantes.

Les durées de vie des membres de données non statiques et des sous-objets de base commencent et se terminent selon l'ordre d'initialisation de la classe.

Durée de vie des objets temporaires

Des objets temporaires sont créés lorsqu'une prvalue est matérialisée afin de pouvoir être utilisée comme glvalue, ce qui se produit (depuis C++17) dans les situations suivantes :

  • liaison d'une référence à une prvalue
  • initialisation d'un objet de type std::initializer_list<T> à partir d'une liste d'initialisation entre accolades

(depuis C++11)

  • renvoi d'une prvalue depuis une fonction
  • conversion qui crée une prvalue (y compris T(a, b, c) et T{})
  • expression lambda

(depuis C++11)

  • initialisation par copie qui nécessite la conversion de l'initialisateur,
  • initialisation de référence vers un type différent mais convertible, ou vers un champ de bits.

(jusqu'à C++17)

  • lors de l'accès à un membre sur une prvalue de classe
  • lors d'une conversion tableau-vers-pointeur ou d'un indexage sur une prvalue de tableau
  • pour les opérandes non évalués dans sizeof et typeid
  • lorsqu'une prvalue apparaît comme une expression de valeur ignorée

(depuis C++17)

Par ailleurs, des objets temporaires sont créés :

  • si l'implémentation le permet, lors du passage ou du renvoi d'un objet de type trivialement copiable dans une expression d'appel de fonction (ceci permet de passer des structures dans les registres du processeur)

La matérialisation d'un objet temporaire est généralement retardée autant que possible afin d'éviter la création d'objets temporaires inutiles : voir élision de copie.

(depuis C++17)

Tous les objets temporaires sont détruits en dernière étape de l'évaluation de l'expression complète qui contient (lexicalement) le point où ils ont été créés ; et si plusieurs objets temporaires ont été créés, ils sont détruits dans l'ordre inverse de leur création. Ceci reste vrai même si cette évaluation se termine par le lancement d'une exception.

Il existe les exceptions suivantes à cette règle :

  • La durée de vie d'un objet temporaire peut être prolongée par liaison à une référence, voir initialisation de référence pour plus de détails.
  • La durée de vie d'un objet temporaire créé lors de l'évaluation des arguments par défaut d'un constructeur par défaut ou de copie utilisé pour initialiser ou copier un élément d'un tableau se termine avant que l'élément suivant du tableau ne commence son initialisation.
  • La durée de vie d'un objet temporaire créé dans une déclaration de liaison structurée (introduite par l'initialisateur d'une variable de nom unique) est prolongée jusqu'à la fin de la déclaration de liaison structurée.

(depuis C++17)

  • La durée de vie d'un objet temporaire créé dans le range-initializer d'une instruction range-for qui serait autrement détruit à la fin du range-initializer est prolongée jusqu'à la fin du corps de la boucle.

(depuis C++23)

Réutilisation du stockage

Un programme n'est pas tenu d'appeler le destructeur d'un objet pour terminer sa durée de vie si l'objet est trivialement destructible (attention, le comportement correct du programme peut dépendre du destructeur). Cependant, si un programme termine explicitement la durée de vie d'un objet non trivialement destructible qui est une variable, il doit s'assurer qu'un nouvel objet du même type est construit sur place (par exemple via un placement new) avant que le destructeur ne puisse être appelé implicitement, c'est-à-dire à la sortie de portée ou à cause d'une exception pour les objets automatiques, à la sortie du thread pour les objets thread-local, (depuis C++11) ou à la fin du programme pour les objets statiques ; sinon le comportement est indéfini.

class T {}; // trivial

struct B
{
    ~B() {} // non trivial
};

void x()
{
    long long n; // automatique, trivial
    new (&n) double(3.14); // réutilisation avec un type différent acceptable
} // okay

void h()
{
    B b; // automatique non trivialement destructible
    b.~B(); // fin de durée de vie (non requise, car sans effets de bord)
    new (&b) T; // mauvais type : acceptable jusqu'à l'appel du destructeur
} // appel du destructeur : comportement indéfini

Il y a comportement indéfini à réutiliser le stockage occupé ou ayant été occupé par un objet complet const de durée de stockage statique, thread-local, (depuis C++11) ou automatique, car ces objets peuvent être stockés en mémoire en lecture seule :

struct B
{
    B(); // non trivial
    ~B(); // non trivial
};
const B b; // const static

void h()
{
    b.~B(); // fin de la durée de vie de b
    new (const_cast<B*>(&b)) const B; // comportement indéfini : tentative de réutilisation d'un const
}

Lors de l'évaluation d'une expression new, le stockage est considéré comme réutilisé après son renvoi par la fonction d'allocation, mais avant l'évaluation de l'initializer de l'expression new :

struct S
{
    int m;
};

void f()
{
    S x{1};
    new(&x) S(x.m); // comportement indéfini : le stockage est réutilisé
}

Si un nouvel objet est créé à l'adresse occupée par un autre objet, alors tous les pointeurs, toutes les références et le nom de l'objet original feront automatiquement référence au nouvel objet et, une fois que la durée de vie du nouvel objet commence, pourront être utilisés pour manipuler le nouvel objet, mais seulement si l'objet original est remplaçable de manière transparente par le nouvel objet.

Si toutes les conditions suivantes sont satisfaites, l'objet x est remplaçable de manière transparente par l'objet y :

  • Le stockage de y recouvre exactement l'emplacement de stockage qu'occupait x.
  • y est du même type que x (en ignorant les qualificateurs cv de premier niveau).
  • x n'est pas un objet const complet.
  • Ni x ni y ne sont un sous-objet de classe de base, ni un sous-objet membre déclaré avec [[no_unique_address]] (depuis C++20).
  • L'une des conditions suivantes est satisfaite :
    • x et y sont tous deux des objets complets.
    • x et y sont des sous-objets directs des objets ox et oy respectivement, et ox est remplaçable de manière transparente par oy.
struct C
{
    int i;
    void f();
    const C& operator=(const C&);
};

const C& C::operator=(const C& other)
{
    if (this != &other)
    {
        this->~C();          // la durée de vie de *this se termine
        new (this) C(other); // nouvel objet de type C créé
        f();                 // bien défini
    }
    return *this;
}

C c1;
C c2;
c1 = c2; // bien défini
c1.f();  // bien défini ; c1 fait référence à un nouvel objet de type C

Si les conditions énumérées ci-dessus ne sont pas remplies, un pointeur valide vers le nouvel objet peut tout de même être obtenu en appliquant la barrière d'optimisation de pointeur std::launder :

struct A
{
    virtual int transmogrify();
};

struct B : A
{
    int transmogrify() override { ::new(this) A; return 2; }
};

inline int A::transmogrify() { ::new(this) B; return 1; }

void test()
{
    A i;
    int n = i.transmogrify();
    // int m = i.transmogrify(); // comportement indéfini :
    // le nouvel objet A est un sous-objet de base, tandis que l'ancien est un objet complet
    int m = std::launder(&i)->transmogrify(); // OK
    assert(m + n == 3);
}

(depuis C++17)

De même, si un objet est créé dans le stockage d'un membre de classe ou d'un élément de tableau, l'objet créé n'est un sous-objet (membre ou élément) de l'objet englobant de l'objet original que si :

  • la durée de vie de l'objet englobant a commencé et ne s'est pas terminée
  • le stockage du nouvel objet recouvre exactement le stockage de l'objet original
  • le nouvel objet est du même type que l'objet original (en ignorant la qualification cv).

Sinon, le nom du sous-objet original ne peut pas être utilisé pour accéder au nouvel objet sans std::launder :

Fourniture de stockage

À titre particulier, des objets peuvent être créés dans des tableaux de unsigned charou std::byte (depuis C++17) (auquel cas on dit que le tableau fournit le stockage pour l'objet) si

  • la durée de vie du tableau a commencé et ne s'est pas terminée
  • le stockage du nouvel objet tient entièrement dans le tableau
  • il n'existe aucun objet tableau satisfaisant ces contraintes imbriqué dans le tableau.

Si cette portion du tableau fournissait précédemment le stockage à un autre objet, la durée de vie de cet objet se termine car son stockage a été réutilisé ; cependant, la durée de vie du tableau lui-même ne se termine pas (son stockage n'est pas considéré comme ayant été réutilisé).

template<typename... T>
struct AlignedUnion
{
    alignas(T...) unsigned char data[max(sizeof(T)...)];
};

int f()
{
    AlignedUnion<int, char> au;
    int *p = new (au.data) int;     // OK, au.data fournit le stockage
    char *c = new (au.data) char(); // OK, termine la durée de vie de *p
    char *d = new (au.data + 1) char();
    return *c + *d; // OK
}

Accès en dehors de la durée de vie

Avant que la durée de vie d'un objet ait commencé mais après que le stockage que l'objet occupera a été alloué, ou après que la durée de vie d'un objet s'est terminée et avant que le stockage qu'il occupait soit réutilisé ou libéré, les comportements des utilisations suivantes de l'expression glvalue qui identifie cet objet sont indéfinis, sauf si l'objet est en cours de construction ou de destruction (un ensemble de règles distinct s'applique) :

  1. Conversion lvalue-vers-rvalue (par exemple appel d'une fonction qui prend une valeur).
  2. Accès à un membre de données non statique ou appel d'une fonction membre non statique.
  3. Liaison d'une référence à un sous-objet de classe de base virtuelle.
  4. Expressions dynamic_cast ou typeid.

Les règles ci-dessus s'appliquent également aux pointeurs (la liaison d'une référence à une base virtuelle est remplacée par une conversion implicite en pointeur vers la base virtuelle), avec deux règles supplémentaires :

  1. static_cast d'un pointeur vers un stockage sans objet n'est autorisé que lors d'un transtypage vers void* (éventuellement qualifié cv).
  2. Les pointeurs vers du stockage sans objet, convertis en pointeurs vers void* potentiellement qualifié cv, ne peuvent être static_cast que vers des pointeurs vers char potentiellement qualifié cv, ou vers unsigned char potentiellement qualifié cv, ou vers std::byte, potentiellement qualifié cv (depuis C++17).

Pendant la construction et la destruction, il est généralement permis d'appeler des fonctions membres non statiques, d'accéder aux membres de données non statiques et d'utiliser typeid et dynamic_cast. Cependant, comme la durée de vie n'a pas encore commencé (pendant la construction) ou est déjà terminée (pendant la destruction), seules certaines opérations spécifiques sont autorisées. Pour une restriction, voir appels de fonctions virtuelles pendant la construction et la destruction.

Notes

Jusqu'à la résolution de CWG issue 2256, les règles de fin de durée de vie diffèrent entre les objets non classes (fin de la durée de stockage) et les objets classes (ordre inverse de construction) :

struct A
{
    int* p;
    ~A() { std::cout << *p; } // comportement indéfini depuis CWG2256 : n ne survit pas à a
                              // bien défini jusqu'à CWG2256 : affiche 123
};

void f()
{
    A a;
    int n = 123; // si n ne survivait pas à a, ceci pouvait être optimisé (store mort)
    a.p = &n;
}

Jusqu'à la résolution de RU007, un membre non statique de type qualifié const ou de type référence empêche son objet englobant d'être remplaçable de manière transparente, ce qui rend std::vector et std::deque difficiles à implémenter :

struct X { const int n; };
union U { X x; float f; };

void tong()
{
    U u = { {1} };
    u.f = 5.f;                          // OK : crée un nouveau sous-objet de 'u'
    X *p = new (&u.x) X {2};            // OK : crée un nouveau sous-objet de 'u'
    assert(p->n == 2);                  // OK
    assert(u.x.n == 2);                 // non défini jusqu'à RU007 :
                                        // « u.x » ne désigne pas le nouveau sous-objet
    assert(*std::launder(&u.x.n) == 2); // OK même jusqu'à RU007
}
