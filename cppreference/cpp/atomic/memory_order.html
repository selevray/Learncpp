std::memory_order précise comment les accès mémoire, y compris les accès mémoire ordinaires non atomiques, doivent être ordonnés autour d'une opération atomique. Faute de contraintes sur un système multicœur, lorsque plusieurs threads lisent et écrivent simultanément plusieurs variables, un thread peut observer les changements de valeurs dans un ordre différent de celui dans lequel un autre thread les a écrites. En effet, l'ordre apparent des changements peut même différer entre plusieurs threads lecteurs. Certains effets similaires peuvent aussi se produire sur des systèmes monoprocesseurs, en raison des transformations du compilateur permises par le modèle mémoire.

Le comportement par défaut de toutes les opérations atomiques de la bibliothèque garantit un ordre séquentiellement cohérent (voir la discussion ci-dessous). Ce comportement par défaut peut pénaliser les performances, mais les opérations atomiques de la bibliothèque peuvent recevoir un argument std::memory_order supplémentaire afin de préciser les contraintes exactes, au-delà de l'atomicité, que le compilateur et le processeur doivent imposer à cette opération.

Constantes

Défini dans l'en-tête <atomic>

Nom Explication

  • memory_order_relaxed — Opération relâchée : aucune contrainte de synchronisation ou d'ordre n'est imposée aux autres lectures ou écritures, seule l'atomicité de cette opération est garantie (voir Ordre relâché ci-dessous).
  • memory_order_consume — Une opération de chargement avec cet ordre mémoire effectue une opération consume sur l'emplacement mémoire concerné : aucune lecture ni écriture du thread courant dépendant de la valeur actuellement chargée ne peut être réordonnée avant ce chargement. Les écritures dans des variables dépendant des données, effectuées par d'autres threads qui libèrent la même variable atomique, sont visibles dans le thread courant. Sur la plupart des plates-formes, cela n'affecte que les optimisations du compilateur (voir Ordre release-consume ci-dessous).
  • memory_order_acquire — Une opération de chargement avec cet ordre mémoire effectue l'opération acquire sur l'emplacement mémoire concerné : aucune lecture ni écriture du thread courant ne peut être réordonnée avant ce chargement. Toutes les écritures des autres threads qui libèrent la même variable atomique sont visibles dans le thread courant (voir Ordre release-acquire ci-dessous).
  • memory_order_release — Une opération de stockage avec cet ordre mémoire effectue l'opération release : aucune lecture ni écriture du thread courant ne peut être réordonnée après ce stockage. Toutes les écritures du thread courant sont visibles dans les autres threads qui acquièrent la même variable atomique (voir Ordre release-acquire ci-dessous), et les écritures portant une dépendance vers la variable atomique deviennent visibles dans les autres threads qui consomment la même variable atomique (voir Ordre release-consume ci-dessous).
  • memory_order_acq_rel — Une opération read-modify-write avec cet ordre mémoire est à la fois une opération acquire et une opération release. Aucune lecture ni écriture mémoire du thread courant ne peut être réordonnée avant le chargement, ni après le stockage. Toutes les écritures des autres threads qui libèrent la même variable atomique sont visibles avant la modification, et la modification est visible dans les autres threads qui acquièrent la même variable atomique.
  • memory_order_seq_cst — Une opération de chargement avec cet ordre mémoire effectue une opération acquire, un stockage effectue une opération release, et une opération read-modify-write effectue à la fois une opération acquire et une opération release, et il existe un ordre total unique dans lequel tous les threads observent toutes les modifications dans le même ordre (voir Ordre séquentiellement cohérent ci-dessous).

Description formelle

La synchronisation inter-threads et l'ordre mémoire déterminent comment les évaluations et les effets de bord des expressions sont ordonnés entre différents threads d'exécution. Ils sont définis dans les termes suivants :

Séquencé avant

Dans un même thread, l'évaluation A peut être séquencée avant l'évaluation B, comme décrit dans l'ordre d'évaluation.

Transport de dépendance

Dans un même thread, l'évaluation A, séquencée avant l'évaluation B, peut aussi transporter une dépendance vers B (c'est-à-dire que B dépend de A) si l'une des conditions suivantes est vraie :

  1. La valeur de A est utilisée comme opérande de B, sauf

a) si B est un appel à std::kill_dependency,

b) si A est l'opérande de gauche des opérateurs intégrés &&, ||, ?: ou ,.

  1. A écrit dans un objet scalaire M, B lit depuis M.

  2. A porte une dépendance vers une autre évaluation X, et X porte une dépendance vers B.

Ordre de modification

Toutes les modifications d'une variable atomique donnée se produisent dans un ordre total propre à cette seule variable atomique.

Les quatre exigences suivantes sont garanties pour toutes les opérations atomiques :

  1. Cohérence écriture-écriture : si l'évaluation A qui modifie une atomique M (une écriture) happens-before l'évaluation B qui modifie M, alors A apparaît avant B dans l'ordre de modification de M.

  2. Cohérence lecture-lecture : si le calcul de valeur A d'une atomique M (une lecture) happens-before un calcul de valeur B sur M, et si la valeur de A provient d'une écriture X sur M, alors la valeur de B est soit la valeur stockée par X, soit la valeur stockée par un effet de bord Y sur M qui apparaît après X dans l'ordre de modification de M.

  3. Cohérence lecture-écriture : si le calcul de valeur A d'une atomique M (une lecture) happens-before une opération B sur M (une écriture), alors la valeur de A provient d'un effet de bord (une écriture) X qui apparaît avant B dans l'ordre de modification de M.

  4. Cohérence écriture-lecture : si un effet de bord (une écriture) X sur un objet atomique M happens-before un calcul de valeur (une lecture) B de M, alors l'évaluation B doit prendre sa valeur de X ou d'un effet de bord Y qui suit X dans l'ordre de modification de M.

Séquence de libération

Après qu'une opération de libération A a été effectuée sur un objet atomique M, la plus longue sous-séquence continue de l'ordre de modification de M constituée :

  1. des écritures effectuées par le même fil d'exécution que celui qui a effectué A.

(jusqu'à C++20)

  1. des opérations atomiques de lecture-modification-écriture effectuées sur M par n'importe quel fil d'exécution.

est appelée séquence de libération dont la tête est A.

Se synchronise avec

Si un stockage atomique dans le fil A est une opération de libération, un chargement atomique dans le fil B depuis la même variable est une opération d'acquisition, et si le chargement dans le fil B lit une valeur écrite par le stockage dans le fil A, alors le stockage dans le fil A se synchronise avec le chargement dans le fil B.

De plus, certains appels de bibliothèque peuvent être définis pour se synchroniser avec d'autres appels de bibliothèque sur d'autres fils d'exécution.

Ordonné par dépendance avant

Entre fils d'exécution, l'évaluation A est ordonnée par dépendance avant l'évaluation B si l'une quelconque des conditions suivantes est vraie :

  1. A effectue une opération de libération sur une atomique M, et, dans un fil différent, B effectue une opération de consommation sur la même atomique M, et B lit une valeur écrite par une partie quelconque de la séquence de libération dont la tête est (jusqu'à C++20) A.

  2. A est ordonnée par dépendance avant X et X porte une dépendance vers B.

Happens-before inter-fils

Entre fils d'exécution, l'évaluation A happens-before inter-fils l'évaluation B si l'une quelconque des conditions suivantes est vraie :

  1. A se synchronise avec B.

  2. A est ordonnée par dépendance avant B.

  3. A se synchronise avec une évaluation X, et X est séquencée avant B.

  4. A est séquencée avant une évaluation X, et X happens-before inter-fils B.

  5. A happens-before inter-fils une évaluation X, et X happens-before inter-fils B.

Happens-before

Indépendamment des fils d'exécution, l'évaluation A happens-before l'évaluation B si l'une quelconque des conditions suivantes est vraie :

  1. A est séquencée avant B.

  2. A happens-before inter-fils B.

L'implémentation doit garantir que la relation happens-before est acyclique, en introduisant si nécessaire une synchronisation supplémentaire (ce ne peut être nécessaire que si une opération de consommation est impliquée, voir Batty et al).

Si une évaluation modifie un emplacement mémoire, et si l'autre lit ou modifie le même emplacement mémoire, et si au moins l'une des évaluations n'est pas une opération atomique, le comportement du programme est indéfini (le programme présente une course de données), sauf s'il existe une relation happens-before entre ces deux évaluations.

Simplement happens-before

Indépendamment des fils d'exécution, l'évaluation A simplement happens-before l'évaluation B si l'une quelconque des conditions suivantes est vraie :

  1. A est séquencée avant B.

  2. A se synchronise avec B.

  3. A simplement happens-before X, et X simplement happens-before B.

Remarque : sans opérations de consommation, les relations simplement happens-before et happens-before sont identiques.

(depuis C++20)

Fortement happens-before

Indépendamment des fils d'exécution, l'évaluation A fortement happens-before l'évaluation B si l'une quelconque des conditions suivantes est vraie :

  1. A est séquencée avant B.

  2. A se synchronise avec B.

  3. A fortement happens-before X, et X fortement happens-before B.

(jusqu'à C++20)

  1. A est séquencée avant B.

  2. A se synchronise avec B, et A et B sont toutes deux des opérations atomiques à cohérence séquentielle.

  3. A est séquencée avant X, X simplement happens-before Y, et Y est séquencée avant B.

  4. A fortement happens-before X, et X fortement happens-before B.

Remarque : informellement, si A fortement happens-before B, alors A semble être évaluée avant B dans tous les contextes.

Remarque : fortement happens-before exclut les opérations de consommation.

(depuis C++20)

Effets de bord visibles

L'effet de bord A sur un scalaire M (une écriture) est visible relativement au calcul de valeur B sur M (une lecture) si les deux conditions suivantes sont vraies :

  1. A happens-before B.

  2. Il n'existe aucun autre effet de bord X sur M tel que A happens-before X et X happens-before B.

Si l'effet de bord A est visible relativement au calcul de valeur B, alors le plus long sous-ensemble continu des effets de bord sur M, dans l'ordre de modification, pour lequel B ne happens-before pas, est appelé séquence visible d'effets de bord (la valeur de M, déterminée par B, sera la valeur stockée par l'un de ces effets de bord).

Remarque : la synchronisation inter-fils se résume à empêcher les courses de données (en établissant des relations happens-before) et à définir quels effets de bord deviennent visibles et dans quelles conditions.

Opération de consommation

Un chargement atomique avec memory_order_consume ou plus fort est une opération de consommation. Notez que std::atomic_thread_fence impose des exigences de synchronisation plus fortes qu'une opération de consommation.

Opération d'acquisition

Un chargement atomique avec memory_order_acquire ou plus fort est une opération d'acquisition. L'opération lock() sur un Mutex est également une opération d'acquisition. Notez que std::atomic_thread_fence impose des exigences de synchronisation plus fortes qu'une opération d'acquisition.

Opération de libération

Un stockage atomique avec memory_order_release ou plus fort est une opération de libération. L'opération unlock() sur un Mutex est également une opération de libération. Notez que std::atomic_thread_fence impose des exigences de synchronisation plus fortes qu'une opération de libération.

Explication

Ordonnancement relâché

Les opérations atomiques marquées memory_order_relaxed ne sont pas des opérations de synchronisation ; elles n'imposent aucun ordre entre les accès mémoire concurrents. Elles garantissent seulement l'atomicité et la cohérence de l'ordre de modification.

Par exemple, avec x et y initialement à zéro,

// Thread 1 :
r1 = y.load(std::memory_order_relaxed); // A
x.store(r1, std::memory_order_relaxed); // B
// Thread 2 :
r2 = x.load(std::memory_order_relaxed); // C
y.store(42, std::memory_order_relaxed); // D

peut produire r1 == r2 == 42 car, bien que A soit séquencée avant B dans le fil 1 et que C soit séquencée avant D dans le fil 2, rien n'empêche D d'apparaître avant A dans l'ordre de modification de y, ni B d'apparaître avant C dans l'ordre de modification de x. L'effet de bord de D sur y peut être visible pour le chargement A du fil 1 tandis que l'effet de bord de B sur x peut être visible pour le chargement C du fil 2. En particulier, cela peut se produire si D est terminée avant C dans le fil 2, que ce soit à cause d'une réorganisation par le compilateur ou à l'exécution.

Même avec le modèle mémoire relâché, les valeurs « sorties de nulle part » (out-of-thin-air) ne peuvent pas dépendre circulairement de leurs propres calculs, par exemple, avec x et y initialement à zéro,

// Thread 1 :
r1 = y.load(std::memory_order_relaxed);
if (r1 == 42)
    x.store(r1, std::memory_order_relaxed);
// Thread 2 :
r2 = x.load(std::memory_order_relaxed);
if (r2 == 42)
    y.store(42, std::memory_order_relaxed);

ne peut pas produire r1 == r2 == 42 puisque le stockage de 42 dans y n'est possible que si le stockage dans x enregistre 42, ce qui dépend circulairement du stockage dans y enregistrant 42. Notez que jusqu'à C++14, cela était techniquement autorisé par la spécification, mais déconseillé aux implémenteurs.

(depuis C++14)

L'usage typique de l'ordonnancement mémoire relâché est l'incrémentation de compteurs, tels que les compteurs de références de std::shared_ptr, car cela ne nécessite que l'atomicité, mais ni ordre ni synchronisation (notez que la décrémentation des compteurs std::shared_ptr nécessite une synchronisation acquisition-libération avec le destructeur).

#include <atomic>
#include <iostream>
#include <thread>
#include <vector>

std::atomic<int> cnt = {0};

void f()
{
    for (int n = 0; n < 1000; ++n)
        cnt.fetch_add(1, std::memory_order_relaxed);
}

int main()
{
    std::vector<std::thread> v;
    for (int n = 0; n < 10; ++n)
        v.emplace_back(f);
    for (auto& t : v)
        t.join();
    std::cout << "Final counter value is " << cnt << '\n';
}

Output:

Final counter value is 10000

Ordonnancement libération-acquisition

Si un stockage atomique dans le fil A est marqué memory_order_release, un chargement atomique dans le fil B depuis la même variable est marqué memory_order_acquire, et si le chargement dans le fil B lit une valeur écrite par le stockage dans le fil A, alors le stockage dans le fil A se synchronise avec le chargement dans le fil B.

Toutes les écritures mémoire (y compris non atomiques et atomiques relâchées) qui ont eu lieu avant le stockage atomique du point de vue du fil A deviennent des effets de bord visibles dans le fil B. Autrement dit, une fois le chargement atomique terminé, le fil B est assuré de voir tout ce que le fil A a écrit en mémoire. Cette garantie n'est valable que si B renvoie effectivement la valeur que A a stockée, ou une valeur provenant d'un point ultérieur de la séquence de libération.

La synchronisation n'est établie qu'entre les fils qui libèrent et acquièrent la même variable atomique. D'autres fils peuvent observer un ordre des accès mémoire différent de celui de l'un ou des deux fils synchronisés.

Sur les systèmes à ordre fort — x86, SPARC TSO, mainframes IBM, etc. — l'ordonnancement libération-acquisition est automatique pour la majorité des opérations. Aucune instruction CPU supplémentaire n'est émise pour ce mode de synchronisation ; seules certaines optimisations du compilateur sont affectées (par exemple, le compilateur ne peut pas déplacer des stockages non atomiques au-delà du stockage-libération atomique, ni effectuer des chargements non atomiques plus tôt que le chargement-acquisition atomique). Sur les systèmes à ordre faible (ARM, Itanium, PowerPC), des instructions CPU spéciales de chargement ou de barrière mémoire sont utilisées.

Les verrous d'exclusion mutuelle, tels que std::mutex ou verrou tournant atomique, sont un exemple de synchronisation libération-acquisition : lorsque le verrou est libéré par le fil A et acquis par le fil B, tout ce qui s'est déroulé dans la section critique (avant la libération) dans le contexte du fil A doit être visible pour le fil B (après l'acquisition) qui exécute la même section critique.

#include <atomic>
#include <cassert>
#include <string>
#include <thread>

std::atomic<std::string*> ptr;
int data;

void producer()
{
    std::string* p = new std::string("Hello");
    data = 42;
    ptr.store(p, std::memory_order_release);
}

void consumer()
{
    std::string* p2;
    while (!(p2 = ptr.load(std::memory_order_acquire)))
        ;
    assert(*p2 == "Hello"); // ne se déclenche jamais
    assert(data == 42); // ne se déclenche jamais
}

int main()
{
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join(); t2.join();
}

L'exemple suivant montre un ordonnancement libération-acquisition transitif entre trois fils, à l'aide d'une séquence de libération.

#include <atomic>
#include <cassert>
#include <thread>
#include <vector>

std::vector<int> data;
std::atomic<int> flag = {0};

void thread_1()
{
    data.push_back(42);
    flag.store(1, std::memory_order_release);
}

void thread_2()
{
    int expected = 1;
    // memory_order_relaxed est acceptable car il s'agit d'une RMW,
    // et les RMW (quel que soit l'ordre) qui suivent un release forment une séquence de libération
    while (!flag.compare_exchange_strong(expected, 2, std::memory_order_relaxed))
    {
        expected = 1;
    }
}

void thread_3()
{
    while (flag.load(std::memory_order_acquire) < 2)
        ;
    // si nous lisons la valeur 2 depuis l'atomique flag, nous voyons 42 dans le vector
    assert(data.at(0) == 42); // ne se déclenchera jamais
}

int main()
{
    std::thread a(thread_1);
    std::thread b(thread_2);
    std::thread c(thread_3);
    a.join(); b.join(); c.join();
}

Ordonnancement libération-consommation

Si un stockage atomique dans le fil A est marqué memory_order_release, un chargement atomique dans le fil B depuis la même variable est marqué memory_order_consume, et si le chargement dans le fil B lit une valeur écrite par le stockage dans le fil A, alors le stockage dans le fil A est ordonné par dépendance avant le chargement dans le fil B.

Toutes les écritures mémoire (non atomiques et atomiques relâchées) qui ont eu lieu avant le stockage atomique du point de vue du fil A deviennent des effets de bord visibles au sein des opérations du fil B dans lesquelles le chargement porte une dépendance, c'est-à-dire qu'une fois le chargement atomique terminé, les opérateurs et fonctions du fil B qui utilisent la valeur obtenue par ce chargement sont assurés de voir ce que le fil A a écrit en mémoire.

La synchronisation n'est établie qu'entre les fils qui libèrent et consomment la même variable atomique. D'autres fils peuvent observer un ordre des accès mémoire différent de celui de l'un ou des deux fils synchronisés.

Sur tous les processeurs courants, à l'exception du DEC Alpha, l'ordonnancement par dépendance est automatique ; aucune instruction CPU supplémentaire n'est émise pour ce mode de synchronisation, seules certaines optimisations du compilateur sont affectées (par exemple, le compilateur ne peut pas effectuer de chargements spéculatifs sur les objets impliqués dans la chaîne de dépendance).

Les cas d'utilisation typiques de cet ordonnancement concernent la lecture de structures de données concurrentes rarement écrites (tables de routage, configuration, politiques de sécurité, règles de pare-feu, etc.) et les situations éditeur-abonné avec publication par pointeur, c'est-à-dire lorsque le producteur publie un pointeur par lequel le consommateur peut accéder à des informations : il n'est pas nécessaire de rendre visible au consommateur tout le reste que le producteur a écrit en mémoire (ce qui peut être une opération coûteuse sur les architectures à ordre faible). Un exemple d'un tel scénario est rcu_dereference.

Voir aussi std::kill_dependency et [[carries_dependency]] pour un contrôle fin des chaînes de dépendance.

Notez qu'actuellement (2/2015) aucun compilateur de production connu ne suit les chaînes de dépendance : les opérations consume sont remontées en opérations acquire.

La spécification de l'ordonnancement release-consume est en cours de révision, et l'utilisation de memory_order_consume est temporairement déconseillée.

(depuis C++17)

Cet exemple illustre la synchronisation ordonnée par dépendance pour une publication médiée par pointeur : les données entières ne sont pas liées au pointeur vers la chaîne par une relation de dépendance de données ; leur valeur est donc indéfinie côté consommateur.

#include <atomic>
#include <cassert>
#include <string>
#include <thread>

std::atomic<std::string*> ptr;
int data;

void producer()
{
    std::string* p = new std::string("Hello");
    data = 42;
    ptr.store(p, std::memory_order_release);
}

void consumer()
{
    std::string* p2;
    while (!(p2 = ptr.load(std::memory_order_consume)))
        ;
    assert(*p2 == "Hello"); // ne se déclenche jamais : *p2 porte la dépendance depuis ptr
    assert(data == 42); // peut ou non se déclencher : data ne porte pas la dépendance depuis ptr
}

int main()
{
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join(); t2.join();
}

Ordonnancement séquentiellement cohérent

Les opérations atomiques marquées memory_order_seq_cst ordonnent non seulement la mémoire de la même façon que l'ordonnancement release/acquire (tout ce qui happens-before une écriture dans un thread devient un effet de bord visible dans le thread qui effectue une lecture), mais établissent également un ordre de modification total unique de toutes les opérations atomiques ainsi marquées.

Formellement,

chaque opération memory_order_seq_cst B qui lit depuis la variable atomique M observe l'un des cas suivants :

  • le résultat de la dernière opération A ayant modifié M, qui apparaît avant B dans l'ordre total unique,
  • OU, s'il existe une telle A, B peut observer le résultat d'une modification de M qui n'est pas memory_order_seq_cst et qui ne happens-before pas A,
  • OU, s'il n'existe pas une telle A, B peut observer le résultat d'une modification non liée de M qui n'est pas memory_order_seq_cst.

S'il existait une opération memory_order_seq_cst std::atomic_thread_fence X sequenced-before B, alors B observe l'un des cas suivants :

  • la dernière modification memory_order_seq_cst de M qui apparaît avant X dans l'ordre total unique,
  • une modification non liée de M qui apparaît plus tard dans l'ordre de modification de M.

Pour une paire d'opérations atomiques sur M appelées A et B, où A écrit et B lit la valeur de M, s'il existe deux memory_order_seq_cst std::atomic_thread_fence X et Y, si A est sequenced-before X, Y est sequenced-before B, et X apparaît avant Y dans l'ordre total unique, alors B observe soit :

  • l'effet de A,
  • une modification non liée de M qui apparaît après A dans l'ordre de modification de M.

Pour une paire de modifications atomiques de M appelées A et B, B a lieu après A dans l'ordre de modification de M si

  • il existe une memory_order_seq_cst std::atomic_thread_fence X telle que A est sequenced-before X et X apparaît avant B dans l'ordre total unique,
  • ou il existe une memory_order_seq_cst std::atomic_thread_fence Y telle que Y est sequenced-before B et A apparaît avant Y dans l'ordre total unique,
  • ou il existe des memory_order_seq_cst std::atomic_thread_fence X et Y telles que A est sequenced-before X, Y est sequenced-before B, et X apparaît avant Y dans l'ordre total unique.

Notez que cela signifie que :

  1. dès que des opérations atomiques qui ne sont pas marquées memory_order_seq_cst entrent en jeu, la cohérence séquentielle est perdue,

  2. les barrières séquentiellement cohérentes n'établissent un ordre total que pour les barrières elles-mêmes, et non pour les opérations atomiques en général (sequenced-before n'est pas une relation inter-threads, contrairement à happens-before).

(jusqu'à C++20)

Formellement,

une opération atomique A sur un objet atomique M est coherence-ordered-before une autre opération atomique B sur M si l'une des conditions suivantes est vraie :

  1. A est une modification, et B lit la valeur stockée par A,

  2. A précède B dans l'ordre de modification de M,

  3. A lit la valeur stockée par une modification atomique X, X précède B dans l'ordre de modification, et A et B ne sont pas la même opération atomique de lecture-modification-écriture,

  4. A est coherence-ordered-before X, et X est coherence-ordered-before B.

Il existe un ordre total unique S sur toutes les opérations memory_order_seq_cst, barrières comprises, qui satisfait les contraintes suivantes :

  1. si A et B sont des opérations memory_order_seq_cst, et A strongly happens-before B, alors A précède B dans S,

  2. pour toute paire d'opérations atomiques A et B sur un objet M, où A est coherence-ordered-before B :

a) si A et B sont toutes deux des opérations memory_order_seq_cst, alors A précède B dans S,

b) si A est une opération memory_order_seq_cst, et B happens-before une barrière memory_order_seq_cst Y, alors A précède Y dans S,

c) si une barrière memory_order_seq_cst X happens-before A, et B est une opération memory_order_seq_cst, alors X précède B dans S,

d) si une barrière memory_order_seq_cst X happens-before A, et B happens-before une barrière memory_order_seq_cst Y, alors X précède Y dans S.

La définition formelle garantit que :

  1. l'ordre total unique est cohérent avec l'ordre de modification de tout objet atomique,

  2. un chargement memory_order_seq_cst obtient sa valeur soit de la dernière modification memory_order_seq_cst, soit d'une modification non-memory_order_seq_cst qui ne happens-before pas les modifications memory_order_seq_cst qui la précèdent.

L'ordre total unique peut ne pas être cohérent avec happens-before. Cela permet une implémentation plus efficace de memory_order_acquire et memory_order_release sur certains processeurs. Cela peut produire des résultats surprenants lorsque memory_order_acquire et memory_order_release sont mélangés avec memory_order_seq_cst.

Par exemple, avec x et y initialement à zéro,

// Thread 1 :
x.store(1, std::memory_order_seq_cst); // A
y.store(1, std::memory_order_release); // B
// Thread 2 :
r1 = y.fetch_add(1, std::memory_order_seq_cst); // C
r2 = y.load(std::memory_order_relaxed); // D
// Thread 3 :
y.store(3, std::memory_order_seq_cst); // E
r3 = x.load(std::memory_order_seq_cst); // F

peut produire r1 == 1 && r2 == 3 && r3 == 0, où A happens-before C, mais C précède A dans l'ordre total unique C-E-F-A de memory_order_seq_cst (voir Lahav et al).

Notez que :

  1. dès que des opérations atomiques qui ne sont pas marquées memory_order_seq_cst entrent en jeu, la garantie de cohérence séquentielle du programme est perdue,

  2. dans de nombreux cas, les opérations atomiques memory_order_seq_cst peuvent être réordonnées par rapport aux autres opérations atomiques effectuées par le même thread.

(depuis C++20)

L'ordre séquentiel peut être nécessaire pour les situations à plusieurs producteurs et plusieurs consommateurs où tous les consommateurs doivent observer les actions de tous les producteurs dans le même ordre.

L'ordre séquentiel total nécessite une instruction CPU de barrière mémoire complète sur tous les systèmes multicœurs. Cela peut devenir un goulot d'étranglement de performance, car cela force la propagation des accès mémoire concernés vers chaque cœur.

Cet exemple illustre une situation où l'ordre séquentiel est nécessaire. Tout autre ordre peut déclencher l'assertion, car il serait possible que les threads c et d observent les changements des atomiques x et y dans l'ordre inverse.

#include <atomic>
#include <cassert>
#include <thread>

std::atomic<bool> x = {false};
std::atomic<bool> y = {false};
std::atomic<int> z = {0};

void write_x()
{
    x.store(true, std::memory_order_seq_cst);
}

void write_y()
{
    y.store(true, std::memory_order_seq_cst);
}

void read_x_then_y()
{
    while (!x.load(std::memory_order_seq_cst))
        ;
    if (y.load(std::memory_order_seq_cst))
        ++z;
}

void read_y_then_x()
{
    while (!y.load(std::memory_order_seq_cst))
        ;
    if (x.load(std::memory_order_seq_cst))
        ++z;
}

int main()
{
    std::thread a(write_x);
    std::thread b(write_y);
    std::thread c(read_x_then_y);
    std::thread d(read_y_then_x);
    a.join(); b.join(); c.join(); d.join();
    assert(z.load() != 0); // n'arrivera jamais
}

Relation avec volatile

Au sein d'un fil d'exécution, les accès (lectures et écritures) effectués via des glvalues volatile ne peuvent pas être réordonnés au-delà des effets de bord observables (y compris d'autres accès volatile) qui sont sequenced-before ou sequenced-after dans le même thread, mais cet ordre n'est pas garanti d'être observé par un autre thread, car l'accès volatile n'établit pas de synchronisation inter-threads.

De plus, les accès volatile ne sont pas atomiques (une lecture et une écriture concurrentes constituent une course aux données) et n'ordonnent pas la mémoire (les accès mémoire non volatile peuvent être librement réordonnés autour de l'accès volatile).

Une exception notable est Visual Studio, où, avec les paramètres par défaut, chaque écriture volatile a une sémantique release et chaque lecture volatile a une sémantique acquire (Microsoft Docs), de sorte que les volatile peuvent être utilisés pour la synchronisation inter-threads. La sémantique standard de volatile n'est pas applicable à la programmation multithread, bien qu'elle soit suffisante, par exemple, pour communiquer avec un gestionnaire std::signal qui s'exécute dans le même thread lorsqu'elle est appliquée à des variables sig_atomic_t.
