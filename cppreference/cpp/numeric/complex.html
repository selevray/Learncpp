Les spécialisations de std::complex pour les types standard (jusqu'à C++23) à virgule flottante non qualifiés cv sont TriviallyCopyable (depuis C++23) LiteralTypes permettant de représenter et de manipuler des nombres complexes.

Paramètres de modèle

  • T — le type des parties réelle et imaginaire. Le comportement n'est pas spécifié (et peut ne pas compiler) si T n'est pas un type standard (jusqu'à C++23) à virgule flottante non qualifié cv, et indéfini si T n'est pas NumericType.

Accès orienté tableau

Pour tout objet z de type std::complex<T>, reinterpret_cast<T(&)[2]>(z)[0] est la partie réelle de z et reinterpret_cast<T(&)[2]>(z)[1] est la partie imaginaire de z.

Pour tout pointeur vers un élément d'un tableau de std::complex<T> nommé p et tout indice de tableau valide i, reinterpret_cast<T*>(p)[2 * i] est la partie réelle du nombre complexe p[i], et reinterpret_cast<T*>(p)[2 * i + 1] est la partie imaginaire du nombre complexe p[i].

Le but de cette exigence est de préserver la compatibilité binaire entre les types de nombres complexes de la bibliothèque C++ et les types de nombres complexes du langage C (et les tableaux de ceux-ci), qui ont une exigence de représentation objet identique.

Notes d'implémentation

Pour satisfaire aux exigences d'accès orienté tableau, une implémentation est contrainte de stocker les parties réelle et imaginaire d'une spécialisation de std::complex dans des emplacements mémoire distincts et adjacents. Voici des déclarations possibles pour ses membres de données non statiques :

  • un tableau de type value_type[2], dont le premier élément contient la partie réelle et le second la partie imaginaire (par exemple Microsoft Visual Studio) ;
  • un unique membre de type value_type _Complex (encapsulant le type correspondant de nombre complexe du langage C) (par exemple GNU libstdc++) ;
  • deux membres de type value_type, avec le même accès membre, contenant respectivement les parties réelle et imaginaire (par exemple LLVM libc++).

Une implémentation ne peut pas déclarer de membres de données non statiques supplémentaires qui occuperaient un stockage disjoint de celui des parties réelle et imaginaire, et doit garantir que la spécialisation de modèle de classe ne contient aucun bit de remplissage. L'implémentation doit aussi garantir que les optimisations de l'accès aux tableaux tiennent compte de la possibilité qu'un pointeur vers value_type alias une spécialisation std::complex ou un tableau de celles-ci.

Exemple

#include <cmath>
#include <complex>
#include <iomanip>
#include <iostream>
#include <ranges>

int main()
{
    using namespace std::complex_literals;
    std::cout << std::fixed << std::setprecision(1);

    std::complex<double> z1 = 1i * 1i; // carré de l'unité imaginaire
    std::cout << "i * i = " << z1 << '\n';

    std::complex<double> z2 = std::pow(1i, 2); // carré de l'unité imaginaire
    std::cout << "pow(i, 2) = " << z2 << '\n';

    const double PI = std::acos(-1); // ou std::numbers::pi en C++20
    std::complex<double> z3 = std::exp(1i * PI); // Formule d'Euler
    std::cout << "exp(i * pi) = " << z3 << '\n';

    std::complex<double> z4 = 1.0 + 2i, z5 = 1.0 - 2i; // conjugates
    std::cout << "(1 + 2i) * (1 - 2i) = " << z4 * z5 << '\n';

    const auto zz = {0.0 + 1i, 2.0 + 3i, 4.0 + 5i};
#if __cpp_lib_tuple_like >= 202311L
    for (double re : zz | std::views::keys)
        std::cout << re << ' ';
    std::cout << '\n';
    for (double im : zz | std::views::values)
        std::cout << im << ' ';
    std::cout << '\n';
#else
    for (double re : zz | std::views::transform([](auto z){ return z.real(); }))
        std::cout << re << ' ';
    std::cout << '\n';
    for (double im : zz | std::views::transform([](auto z){ return z.imag(); }))
        std::cout << im << ' ';
    std::cout << '\n';
#endif
}

Output:

i * i = (-1.0,0.0)
pow(i, 2) = (-1.0,0.0)
exp(i * pi) = (-1.0,0.0)
(1 + 2i) * (1 - 2i) = (5.0,0.0)
0.0 2.0 4.0
1.0 3.0 5.0
