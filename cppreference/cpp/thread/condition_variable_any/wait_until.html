std::condition_variable_any::wait_until

wait_until bloque le thread courant jusqu'à ce que la variable de condition soit notifiée, que la durée donnée soit écoulée, ou qu'un réveil parasite se produise. pred peut être fourni facultativement pour détecter les réveils parasites.

  1. Appelle atomiquement lock.unlock() et bloque sur *this.

Le thread sera débloqué lorsque notify_all() ou notify_one() sera exécuté, ou lorsque abs_time sera atteint. Il peut aussi être débloqué de façon parasite.

Une fois débloqué, appelle lock.lock() (éventuellement en bloquant sur le verrou), puis retourne.

2,3) Attend qu'une condition particulière devienne vraie ; peut être utilisée pour ignorer les réveils parasites.

  1. Équivalent à while (!pred()) if (wait_until(lock, abs_time) == std::cv_status::timeout) return pred();return true;.

  2. Enregistre *this pour la durée de cet appel, afin d'être notifié si une demande d'arrêt est faite sur l'état d'arrêt associé à stoken ; il est alors équivalent à while (!stoken.stop_requested()){ if (pred()) return true; if (wait_until(lock, abs_time) == std::cv_status::timeout) return pred();}return pred();.

Juste après le retour de wait_until, lock est verrouillé par le thread appelant. Si cette postcondition ne peut pas être satisfaite[1], appelle std::terminate.

  1. ↑ Cela peut se produire si le reverrouillage du mutex lève une exception.

Paramètres

  • lock — un lock qui doit être verrouillé par le thread appelant
  • stoken — un jeton d'arrêt pour lequel enregistrer l'interruption
  • abs_time — le point temporel où l'attente expire
  • pred — le prédicat permettant de vérifier si l'attente peut être terminée

Exigences sur les types

  • Lock doit satisfaire aux exigences de BasicLockable.
  • Predicate doit satisfaire aux exigences de FunctionObject.
  • pred() doit être une expression valide, et son type et sa catégorie de valeur doivent satisfaire les exigences BooleanTestable.

Valeur de retour

  1. std::cv_status::timeout si abs_time a été atteint, sinon std::cv_status::no_timeout.

2,3) La dernière valeur de pred() avant le retour à l'appelant.

Exceptions

  1. Exceptions liées aux délais d'attente.

2,3) Exceptions liées aux délais d'attente, et toute exception levée par pred.

Notes

La norme recommande d'utiliser l'horloge liée à abs_time pour mesurer le temps ; cette horloge n'est pas tenue d'être monotone. Aucune garantie n'est donnée quant au comportement de cette fonction si l'horloge est ajustée de manière discontinue, mais les implémentations existantes convertissent abs_time de Clock vers std::chrono::system_clock et délèguent à POSIX pthread_cond_timedwait afin que l'attente tienne compte des ajustements de l'horloge système, mais pas de ceux de Clock fournie par l'utilisateur. Dans tous les cas, la fonction peut aussi attendre plus longtemps que jusqu'à abs_time, en raison de délais d'ordonnancement ou de contention sur les ressources.

Même si l'horloge utilisée est std::chrono::steady_clock ou une autre horloge monotone, un ajustement de l'horloge système peut provoquer un réveil parasite.

Les effets de notify_one()/notify_all() et de chacune des trois parties atomiques de wait()/wait_for()/wait_until() (déverrouillage+attente, réveil et verrouillage) ont lieu selon un ordre total unique qui peut être vu comme l'ordre de modification d'une variable atomique : cet ordre est propre à cette variable de condition. Il est ainsi impossible à notify_one() de, par exemple, être retardé et de débloquer un thread qui a commencé à attendre juste après l'appel à notify_one().

Exemple

#include <chrono>
#include <condition_variable>
#include <iostream>
#include <thread>

std::condition_variable_any cv;
std::mutex cv_m; // Ce mutex sert à trois choses :
                 // 1) synchroniser les accès à i
                 // 2) synchroniser les accès à std::cerr
                 // 3) pour la variable de condition cv
int i = 0;

void waits()
{
    std::unique_lock<std::mutex> lk(cv_m);
    std::cerr << "Waiting... \n";
    cv.wait(lk, []{ return i == 1; });
    std::cerr << "...finished waiting. i == 1\n";
}

void signals()
{
    std::this_thread::sleep_for(std::chrono::seconds(1));
    {
        std::lock_guard<std::mutex> lk(cv_m);
        std::cerr << "Notifying...\n";
    }
    cv.notify_all();

    std::this_thread::sleep_for(std::chrono::seconds(1));

    {
        std::lock_guard<std::mutex> lk(cv_m);
        i = 1;
        std::cerr << "Notifying again...\n";
    }
    cv.notify_all();
}

int main()
{
    std::thread t1(waits), t2(waits), t3(waits), t4(signals);
    t1.join();
    t2.join();
    t3.join();
    t4.join();
}

Sortie possible :

Waiting...
Waiting...
Waiting...
Notifying...
Notifying again...
...finished waiting. i == 1
...finished waiting. i == 1
...finished waiting. i == 1

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
LWG 2093 C++11 les exceptions liées aux délais d'attente étaient absentes de la spécification mentionne ces exceptions
LWG 2114 (P2167R3) C++11 la convertibilité vers bool était trop faible pour refléter les attentes des implémentations exigences renforcées
LWG 2135 C++11 le comportement était peu clair si lock.lock() lève une exception appelle std::terminate dans ce cas
