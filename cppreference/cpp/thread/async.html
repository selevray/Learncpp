std::async

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Défini dans l'en-tête <future>

template< class F, class... Args >
std::future</* voir ci-dessous */> async( F&& f, Args&&... args );  // (1) (depuis C++11)

template< class F, class... Args >
std::future</* voir ci-dessous */> async( std::launch policy,
                                    F&& f, Args&&... args );  // (2) (depuis C++11)

Le modèle de fonction std::async exécute la fonction f de manière asynchrone (potentiellement dans un thread séparé, pouvant faire partie d'un pool de threads) et renvoie un std::future qui contiendra à terme le résultat de cet appel de fonction.

  1. Se comporte comme si (2) était appelé avec policy valant std::launch::async | std::launch::deferred.

  2. Appelle une fonction f avec les arguments args selon une politique de lancement spécifique policy (voir ci-dessous).

Le type de retour de std::async est std::future<V>, où V est :

typename std::result_of<typename std::decay<F>::type(
typename std::decay<Args>::type...)>::type.

(jusqu'à C++17)

std::invoke_result_t<std::decay_t<F>, std::decay_t<Args>...>.

(depuis C++17)

Si l'une des conditions suivantes est satisfaite, le programme est mal formé :

  • F n'est pas MoveConstructible.
  • Tout type dans Args n'est pas MoveConstructible.
  • INVOKE(decay-copy(std::forward<F>(f)), decay-copy(std::forward<Args>(args))...) n'est pas une expression valide.

(jusqu'à C++20)

Si l'un des éléments suivants est false, le programme est mal formé :

  • std::is_constructible_v<std::decay_t<F>, F>
  • (std::is_constructible_v<std::decay_t<Args>, Args> && ...)
  • std::is_invocable_v<std::decay_t<F>, std::decay_t<Args>...>

(depuis C++20)

L'appel à std::async se synchronise avec l'appel à f, et la fin de f est séquencée avant la mise à l'état prêt de l'état partagé.

Paramètres

  • f — Callable objet à appeler
  • args — paramètres à passer à f
  • policy — valeur de masque binaire, où chaque bit contrôle les méthodes d'exécution autorisées

Valeur de retour

std::future faisant référence à l'état partagé créé par cet appel à std::async.

Politiques de lancement

Invocation asynchrone

Si le drapeau async est positionné, c'est-à-dire (policy & std::launch::async) != 0, alors std::async appelle

INVOKE(decay-copy(std::forward<F>(f)), decay-copy(std::forward<Args>(args))...)

(jusqu'à C++23)

std::invoke(auto(std::forward<F>(f)), auto(std::forward<Args>(args))...)

(depuis C++23)

comme dans un nouveau fil d'exécution représenté par un objet std::thread.

Les appels de decay-copy sont évalués dans le fil courant.

(jusqu'à C++23)

Les valeurs produites par auto sont matérialisées dans le fil courant.

(depuis C++23)

Si la fonction f renvoie une valeur ou lève une exception, celle-ci est stockée dans l'état partagé accessible par le std::future que std::async renvoie à l'appelant.

Invocation différée

Si le drapeau deferred est positionné (c'est-à-dire (policy & std::launch::deferred) != 0), alors std::async stocke

decay-copy(std::forward<F>(f)) et decay-copy(std::forward<Args>(args))... dans l'état partagé.

(jusqu'à C++23)

auto(std::forward<F>(f)) et auto(std::forward<Args>(args))... dans l'état partagé.

(depuis C++23)

L'évaluation paresseuse est effectuée :

  • Le premier appel à une fonction d'attente non temporisée sur le std::future que std::async a renvoyé à l'appelant évaluera INVOKE(std::move(g), std::move(xyz)) dans le fil qui a appelé la fonction d'attente (qui n'a pas besoin d'être le fil ayant initialement appelé std::async), où
  • g est la valeur stockée de decay-copy(std::forward<F>(f)) et
  • xyz est la copie stockée de decay-copy(std::forward<Args>(args))....

(jusqu'à C++23)

  • g est la valeur stockée de auto(std::forward<F>(f)) et
  • xyz est la copie stockée de auto(std::forward<Args>(args))....

(depuis C++23)

  • Le résultat ou l'exception est placé dans l'état partagé associé au std::future renvoyé, et seulement ensuite il est mis à l'état prêt. Tous les accès ultérieurs au même std::future renverront le résultat immédiatement.

Autres politiques

Si ni std::launch::async ni std::launch::deferred, ni aucun drapeau de politique défini par l'implémentation n'est défini dans policy, le comportement est indéfini.

Sélection de la politique

Si plusieurs drapeaux sont définis, la politique sélectionnée est définie par l'implémentation. Pour la valeur par défaut (les drapeaux std::launch::async et std::launch::deferred sont tous deux définis dans policy), la norme recommande (sans l'exiger) d'utiliser la concurrence disponible et de différer les tâches supplémentaires.

Si la politique std::launch::async est choisie,

  • un appel à une fonction d'attente sur un objet de retour asynchrone partageant l'état partagé créé par cet appel std::async bloque jusqu'à ce que le thread associé se termine, comme s'il avait été joint, ou expire ; et
  • la fin du thread associé se synchronise avec le retour réussi de la première fonction qui attend sur l'état partagé, ou avec le retour de la dernière fonction qui libère l'état partagé, selon ce qui survient en premier.

Exceptions

Lève

  • std::bad_alloc, si la mémoire des structures de données internes ne peut pas être allouée, ou
  • std::system_error avec la condition d'erreur std::errc::resource_unavailable_try_again, si policy == std::launch::async et que l'implémentation ne peut pas démarrer un nouveau thread.
    • Si policy vaut std::launch::async | std::launch::deferred ou possède des bits supplémentaires définis, il se rabat sur l'invocation différée ou sur les politiques définies par l'implémentation dans ce cas.

Notes

L'implémentation peut étendre le comportement de la première surcharge de std::async en activant des bits supplémentaires (définis par l'implémentation) dans la politique de lancement par défaut.

Exemples de politiques de lancement définies par l'implémentation : la politique sync (exécution immédiate, dans l'appel std::async) et la politique task (similaire à std::async, mais les thread-locals ne sont pas effacées)

Si le std::future obtenu à partir de std::async n'est ni déplacé ni lié à une référence, le destructeur de std::future bloque à la fin de l'expression complète jusqu'à ce que l'opération asynchrone se termine, rendant en pratique synchrone du code tel que le suivant :

std::async(std::launch::async, []{ f(); }); // le destructeur du temporaire attend f()
std::async(std::launch::async, []{ g(); }); // ne démarre pas tant que f() n'est pas terminé

Notez que les destructeurs des std::future obtenus par un moyen autre qu'un appel à std::async ne bloquent jamais.

Exemple

#include <algorithm>
#include <future>
#include <iostream>
#include <mutex>
#include <numeric>
#include <string>
#include <vector>

std::mutex m;

struct X
{
    void foo(int i, const std::string& str)
    {
        std::lock_guard<std::mutex> lk(m);
        std::cout << str << ' ' << i << '\n';
    }

    void bar(const std::string& str)
    {
        std::lock_guard<std::mutex> lk(m);
        std::cout << str << '\n';
    }

    int operator()(int i)
    {
        std::lock_guard<std::mutex> lk(m);
        std::cout << i << '\n';
        return i + 10;
    }
};

template<typename RandomIt>
int parallel_sum(RandomIt beg, RandomIt end)
{
    auto len = end - beg;
    if (len < 1000)
        return std::accumulate(beg, end, 0);

    RandomIt mid = beg + len / 2;
    auto handle = std::async(std::launch::async,
                             parallel_sum<RandomIt>, mid, end);
    int sum = parallel_sum(beg, mid);
    return sum + handle.get();
}

int main()
{
    std::vector<int> v(10000, 1);
    std::cout << "The sum is " << parallel_sum(v.begin(), v.end()) << '\n';

    X x;
    // Appelle (&x)->foo(42, "Hello") avec la politique par défaut :
    // peut afficher "Hello 42" de façon concurrente ou différer l'exécution
    auto a1 = std::async(&X::foo, &x, 42, "Hello");
    // Appelle x.bar("world!") avec la politique différée
    // affiche "world!" lorsque a2.get() ou a2.wait() est appelé
    auto a2 = std::async(std::launch::deferred, &X::bar, x, "world!");
    // Appelle X()(43); avec la politique async
    // affiche "43" de façon concurrente
    auto a3 = std::async(std::launch::async, X(), 43);
    a2.wait();                     // affiche "world!"
    std::cout << a3.get() << '\n'; // prints "53"
} // si a1 n'est pas terminé à ce stade, le destructeur de a1 affiche "Hello 42" ici

Sortie possible :

The sum is 10000
43
world!
53
Hello 42

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
LWG 2021 C++11 type de retour incorrect et catégorie de valeur des arguments peu claire dans le cas différé type de retour corrigé et précisé que des rvalues sont utilisées
LWG 2078 C++11 on ne savait pas si std::system_error pouvait être levée lorsque policy spécifie d'autres politiques de lancement que std::launch::async ne peut être levée que si policy == std::launch::async
LWG 2100 C++11 les fonctions d'attente temporisées ne pouvaient pas expirer si la politique std::launch::async est utilisée allowed
LWG 2120 C++11 le comportement était peu clair si aucune politique standard ou définie par l'implémentation n'est définie le comportement est indéfini dans ce cas
LWG 2186 C++11 on ne savait pas comment la valeur retournée et l' exception levée par l'évaluation paresseuse étaient traitées elles sont stockées dans l'état partagé
LWG 2752 C++11 std::async pourrait ne pas lever std::bad_alloc si la mémoire des structures de données internes ne peut pas être allouée throws
LWG 3476 C++20 (les types décayés de) F et les types des arguments étaient directement exigés comme constructibles par déplacement ces exigences ont été supprimées[1]
  1. ↑ La constructibilité par déplacement est déjà exigée indirectement par std::is_constructible_v.
