std::list<T,Allocator>::merge

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

void merge( list& other );  // (1)

void merge( list&& other );  // (2) (depuis C++11)

template< class Compare >
void merge( list& other, Compare comp );  // (3)

template< class Compare >
void merge( list&& other, Compare comp );  // (4) (depuis C++11)

La fonction ne fait rien si other fait référence au même objet que *this.

Sinon, fusionne other dans *this. Les deux listes doivent être triées. Aucun élément n'est copié, et le conteneur other devient vide après la fusion. Cette opération est stable : pour les éléments équivalents des deux listes, les éléments de *this précèdent toujours ceux de other, et l'ordre des éléments équivalents de *this et de other ne change pas.

Aucun itérateur ni aucune référence ne sont invalidés. Les pointeurs et références vers les éléments déplacés depuis *this, ainsi que les itérateurs désignant ces éléments, désigneront les mêmes éléments de *this, au lieu de other.

1,2) Les éléments sont comparés à l'aide de [std::less<T>() (jusqu'à C++14) | std::less<>() (depuis C++14)].

3,4) Les éléments sont comparés à l'aide de comp.

Si *this ou other n'est pas trié selon le comparateur correspondant, ou get_allocator() != other.get_allocator(), le comportement est indéfini.

Paramètres

  • other — un autre conteneur à fusionner

  • comp — objet fonction de comparaison (c'est-à-dire un objet qui satisfait aux exigences de Compare) qui renvoie true si le premier argument est inférieur au second (c'est-à-dire est ordonné avant).

    La signature de la fonction de comparaison doit être équivalente à la suivante :

    bool cmp(const Type1& a, const Type2& b);

    Bien que la signature n'ait pas besoin de comporter const&, la fonction ne doit pas modifier les objets qui lui sont passés et doit pouvoir accepter toutes les valeurs de type (éventuellement const) Type1 et Type2 quelle que soit la catégorie de valeur (ainsi, Type1& n'est pas autorisé, ni Type1 sauf si pour Type1 un déplacement est équivalent à une copie (depuis C++11)).
    Les types Type1 et Type2 doivent être tels qu'un objet de type list<T, Allocator>::const_iterator puisse être déréférencé puis implicitement converti en chacun d'eux.

Exigences sur les types

  • Compare doit satisfaire aux exigences de Compare.

Valeur de retour

(aucune)

Exceptions

Si une exception est levée pour quelque raison que ce soit, ces fonctions n'ont aucun effet (garantie forte d'exception). Sauf si l'exception provient d'une comparaison.

Complexité

Si other fait référence au même objet que *this, aucune comparaison n'est effectuée.

Sinon, en notant (\scriptsize N)N comme std::distance(begin(), end()) et (\scriptsize R)R comme std::distance(other.begin(), other.end()) :

1,2) Au plus (\scriptsize N+R-1)N+R-1 comparaisons utilisant operator<.

3,4) Au plus (\scriptsize N+R-1)N+R-1 appels de la fonction de comparaison comp.

Exemple

#include <iostream>
#include <list>

std::ostream& operator<<(std::ostream& ostr, const std::list<int>& list)
{
    for (const int i : list)
        ostr << ' ' << i;
    return ostr;
}

int main()
{
    std::list<int> list1 = {5, 9, 1, 3, 3};
    std::list<int> list2 = {8, 7, 2, 3, 4, 4};

    list1.sort();
    list2.sort();
    std::cout << "list1: " << list1 << '\n';
    std::cout << "list2: " << list2 << '\n';

    list1.merge(list2);
    std::cout << "merged:" << list1 << '\n';
}

Output:

list1:  1 3 3 5 9
list2:  2 3 4 4 7 8
merged: 1 2 3 3 3 4 4 5 7 8 9

Rapports de défauts

Les rapports de défauts suivants modifiant le comportement ont été appliqués rétroactivement aux normes C++ publiées précédemment.

DR Appliqué à Comportement publié Comportement correct
LWG 300 C++98 l'effet lorsque *this et other référencent le même objet n'était pas spécifié spécifié comme une opération sans effet
LWG 1207 C++98 il n'était pas clair si les itérateurs et/ou les références seraient invalidés restent valides
LWG 1215 C++98 La complexité O(1) du déplacement de nœuds ne pouvait pas être garantie si get_allocator() != other.get_allocator() le comportement est indéfini dans ce cas
LWG 3088 C++98 operator< pouvait mal se comporter pour les éléments pointeurs défini par l'implémentation ordre total strict utilisé
