Exigences nommées C++ : Allocator

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Encapsule les stratégies d'accès/adressage, d'allocation/désallocation et de construction/destruction des objets.

Tout composant de la bibliothèque standard qui peut avoir besoin d'allouer ou de libérer du stockage, depuis std::string, std::vector, et chaque conteneur[, à l'exception de std::array (depuis C++11) | et std::inplace_vector (depuis C++26)], jusqu'à std::shared_ptret std::function (jusqu'à C++17), le fait par l'intermédiaire d'un Allocator : un objet d'un type classe qui satisfait les exigences suivantes.

L'implémentation de nombreuses exigences d'allocateur est facultative car tous les AllocatorAwareContainer accèdent aux allocateurs indirectement par std::allocator_traits, et std::allocator_traits fournit l'implémentation par défaut de ces exigences.

Exigences

Soient

  • T, un [type non const et non référence (jusqu'à C++11) | type objet non const (depuis C++11) (jusqu'à C++17) | type objet non qualifié cv (depuis C++17)],
  • A, un type Allocator pour le type T,
  • a, un objet de type A,
  • B, le type Allocator correspondant pour un certain type objet non qualifié cv U (tel qu'obtenu en rebindant A),
  • b, un objet de type B,
  • p, une valeur de type std::allocator_traits<A>::pointer, obtenue en appelant std::allocator_traits<A>::allocate(),
  • cp, une valeur de type std::allocator_traits<A>::const_pointer, obtenue par conversion depuis p,
  • vp, une valeur de type std::allocator_traits<A>::void_pointer, obtenue par conversion depuis p,
  • cvp, une valeur de type std::allocator_traits<A>::const_void_pointer, obtenue par conversion depuis cp ou depuis vp,
  • xp, un pointeur déréférençable vers un certain type objet non qualifié cv X,
  • r, une lvalue de type T obtenue par l'expression *p,
  • n, une valeur de type std::allocator_traits<A>::size_type.

A::propagate_on_container_copy_assignment
(facultatif) | std::true_type ou std::false_type ou dérivé de l'un d'eux. |

  • std::true_type ou dérivé de celui-ci si l'allocateur de type A doit être copié lorsque le conteneur qui l'utilise est affecté par copie.
  • Si ce membre est std::true_type ou dérivé de celui-ci, alors A doit satisfaire CopyAssignable et l'opération de copie ne doit lever aucune exception.
  • Notez que si les allocateurs des conteneurs source et cible ne se comparent pas comme égaux, l'affectation par copie doit désallouer la mémoire de la cible à l'aide de l'ancien allocateur, puis l'allouer à l'aide du nouvel allocateur avant de copier les éléments (et l'allocateur).

A::propagate_on_container_move_assignment
(facultatif) |

  • std::true_type ou dérivé de celui-ci si l'allocateur de type A doit être déplacé lorsque le conteneur qui l'utilise subit une affectation par déplacement.
  • Si ce membre est std::true_type ou dérivé de celui-ci, alors A doit satisfaire MoveAssignable et l'opération de déplacement ne doit pas lever d'exceptions.
  • Si ce membre n'est pas fourni ni dérivé de std::false_type, et que les allocateurs des conteneurs source et cible ne se comparent pas égaux, l'affectation par déplacement ne peut pas s'approprier la mémoire source et doit affecter ou construire par déplacement les éléments individuellement, en redimensionnant sa propre mémoire si nécessaire.

A::propagate_on_container_swap
(facultatif) |

  • std::true_type ou dérivé de celui-ci si les allocateurs de type A doivent être échangés lorsque deux conteneurs qui les utilisent sont échangés.
  • Si ce membre est std::true_type ou dérivé de celui-ci, le type A doit satisfaire Swappable et l'opération d'échange ne doit pas lever d'exceptions.
  • Si ce membre n'est pas fourni ni dérivé de std::false_type, et que les allocateurs des deux conteneurs ne se comparent pas égaux, le comportement de l'échange de conteneurs est indéfini.

Exigences de complétude des allocateurs

Un type d'allocateur X pour le type T satisfait en outre les exigences de complétude des allocateurs si les deux conditions suivantes sont vraies, indépendamment du fait que T soit un type complet :

  • X est un type complet.
  • À l'exception de value_type, tous les types membres de std::allocator_traits<X> sont des types complets.

(depuis C++17)

Allocateurs avec et sans état

Chaque type Allocator est soit avec état, soit sans état. En général, un type d'allocateur avec état peut avoir des valeurs différentes qui désignent des ressources mémoire distinctes, tandis qu'un type d'allocateur sans état désigne une seule ressource mémoire.

Bien que les allocateurs personnalisés ne soient pas tenus d'être sans état, la manière dont la bibliothèque standard utilise (ou non) les allocateurs avec état est définie par l'implémentation. L'utilisation de valeurs d'allocateur différentes peut entraîner des erreurs d'exécution ou un comportement indéfini définis par l'implémentation si celle-ci ne prend pas en charge une telle utilisation.

(jusqu'à C++11)

Les allocateurs personnalisés peuvent avoir un état. Chaque conteneur ou autre objet sensible aux allocateurs stocke une instance de l'allocateur fourni et contrôle le remplacement de l'allocateur par std::allocator_traits.

(depuis C++11)

Les instances d'un type d'allocateur sans état sont toujours égales entre elles. Les types d'allocateurs sans état sont généralement implémentés sous forme de classes vides et conviennent à l'optimisation de classe de base vide.

Le type membre is_always_equal de std::allocator_traits est destiné à déterminer si un type d'allocateur est sans état.

(depuis C++11)

Pointeurs élaborés

Lorsque le type membre pointer n'est pas un type de pointeur brut, on parle couramment de « pointeur élaboré ». Ces pointeurs ont été introduits pour prendre en charge les architectures mémoire segmentées et sont aujourd'hui utilisés pour accéder à des objets alloués dans des espaces d'adresses différents de l'espace d'adressage virtuel homogène auquel accèdent les pointeurs bruts. Un exemple de pointeur élaboré est le pointeur indépendant de l'adressage par correspondance boost::interprocess::offset_ptr, qui permet d'allouer dans une mémoire partagée et dans des fichiers mappés en mémoire, mappés à des adresses différentes dans chaque processus, des structures de données basées sur des nœuds telles que std::set. Les pointeurs élaborés peuvent être utilisés indépendamment de l'allocateur qui les a fournis, par l'intermédiaire du modèle de classe std::pointer_traits (depuis C++11). La fonction std::to_address peut être utilisée pour obtenir un pointeur brut à partir d'un pointeur élaboré. (depuis C++20)

L'utilisation de pointeurs élaborés et d'une taille ou d'un type différent personnalisés dans la bibliothèque standard est conditionnellement prise en charge. Les implémentations peuvent exiger que les types membres pointer, const_pointer, size_type et difference_type soient respectivement value_type*, const value_type*, std::size_t et std::ptrdiff_t.

(jusqu'à C++11)

Concept

Pour la définition de l'objet de requête std::get_allocator, le concept suivant, réservé à l'exposé, est défini.

template<class Alloc>
concept /*simple-allocator*/ = requires(Alloc alloc, std::size_t n)
{
    { *alloc.allocate(n) } -> std::same_as<typename Alloc::value_type&>;
    { alloc.deallocate(alloc.allocate(n), n) };
} && std::copy_constructible<Alloc>
  && std::equality_comparable<Alloc>;

Le concept /*simple-allocator*/, réservé à l'exposé, définit les contraintes d'utilisabilité minimales de l'exigence Allocator.

(depuis C++26)

Bibliothèque standard

Les composants suivants de la bibliothèque standard satisfont aux exigences de Allocator :

  • allocator — l'allocateur par défaut (modèle de classe)
  • scoped_allocator_adaptor (C++11) — implémente un allocateur multiniveau pour les conteneurs multiniveaux (modèle de classe)
  • polymorphic_allocator (C++17) — un allocateur prenant en charge le polymorphisme à l'exécution basé sur la std::pmr::memory_resource avec laquelle il est construit (modèle de classe)

Exemples

Illustre un allocateur C++11, à l'exception de [[nodiscard]] ajouté pour correspondre au style C++20.

#include <cstdlib>
#include <iostream>
#include <limits>
#include <new>
#include <vector>

template<class T>
struct Mallocator
{
    typedef T value_type;

    Mallocator() = default;

    template<class U>
    constexpr Mallocator(const Mallocator <U>&) noexcept {}

    [[nodiscard]] T* allocate(std::size_t n)
    {
        if (n > std::numeric_limits<std::size_t>::max() / sizeof(T))
            throw std::bad_array_new_length();

        if (auto p = static_cast<T*>(std::malloc(n * sizeof(T))))
        {
            report(p, n);
            return p;
        }

        throw std::bad_alloc();
    }

    void deallocate(T* p, std::size_t n) noexcept
    {
        report(p, n, 0);
        std::free(p);
    }
private:
    void report(T* p, std::size_t n, bool alloc = true) const
    {
        std::cout << (alloc ? "Alloc: " : "Dealloc: ") << sizeof(T) * n
                  << " bytes at " << std::hex << std::showbase
                  << reinterpret_cast<void*>(p) << std::dec << '\n';
    }
};

template<class T, class U>
bool operator==(const Mallocator <T>&, const Mallocator <U>&) { return true; }

template<class T, class U>
bool operator!=(const Mallocator <T>&, const Mallocator <U>&) { return false; }

int main()
{
    std::vector<int, Mallocator<int>> v(8);
    v.push_back(42);
}
