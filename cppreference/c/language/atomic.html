Syntaxe

| | | | _Atomic ( type-name ) | (1) | (depuis C11) | | | _Atomic type-name | (2) | (depuis C11) | |

  1. Utilisé comme spécificateur de type ; il désigne un nouveau type atomique

  2. Utilisé comme qualificateur de type ; il désigne la version atomique de type-name. Dans ce rôle, il peut être combiné avec const, volatile et restrict, bien que, contrairement aux autres qualificateurs, la version atomique de type-name puisse avoir une taille, un alignement et une représentation d'objet différents.

  • type-name — tout type autre qu'un tableau ou une fonction. Pour (1), type-name ne peut pas non plus être atomique ou qualifié cvr

L'en-tête <stdatomic.h> définit de nombreux alias de types pratiques, de atomic_bool à atomic_uintmax_t, qui simplifient l'utilisation de ce mot-clé avec les types intégrés et les types de la bibliothèque.

_Atomic const int* p1;  // p est un pointeur vers un int const atomique
const atomic_int* p2;   // same
const _Atomic(int)* p3; // same

Si la constante macro __STDC_NO_ATOMICS__ est définie par le compilateur, le mot-clé _Atomic n'est pas fourni.

Explication

Les objets de types atomiques sont les seuls objets exempts de courses de données ; c'est-à-dire qu'ils peuvent être modifiés par deux threads simultanément ou modifiés par l'un et lus par un autre.

Chaque objet atomique possède sa propre modification order, qui est un ordre total des modifications effectuées sur cet objet. Si, du point de vue d'un thread, la modification A d'un atomique M happens-before la modification B du même atomique M, alors dans l'ordre de modification de M, A se produit avant B.

Notez que, bien que chaque objet atomique possède son propre ordre de modification, il n'existe pas d'ordre total unique ; différents threads peuvent observer les modifications de différents objets atomiques dans des ordres différents.

Quatre types de cohérence sont garantis pour toutes les opérations atomiques :

  • cohérence écriture-écriture : si une opération A qui modifie un objet atomique M happens-before une opération B qui modifie M, alors A apparaît plus tôt que B dans l'ordre de modification de M.
  • cohérence lecture-lecture : si un calcul de valeur A d'un objet atomique M se produit avant un calcul de valeur B de M, et que A prend sa valeur d'un effet de bord X sur M, alors la valeur calculée par B est soit la valeur stockée par X, soit la valeur stockée par un effet de bord Y sur M, où Y apparaît plus tard que X dans l'ordre de modification de M.
  • cohérence lecture-écriture : si un calcul de valeur A d'un objet atomique M happens-before une opération B sur M, alors A prend sa valeur d'un effet de bord X sur M, où X apparaît avant B dans l'ordre de modification de M.
  • cohérence écriture-lecture : si un effet de bord X sur un objet atomique M happens-before un calcul de valeur B de M, alors l'évaluation B prend sa valeur de X ou d'un effet de bord Y qui apparaît après X dans l'ordre de modification de M.

Certaines opérations atomiques sont également des opérations de synchronisation ; elles peuvent avoir une sémantique de libération (release), d'acquisition (acquire) ou séquentiellement cohérente. Voir memory_order.

Les opérateurs d'incrémentation et de décrémentation intégrés et l'affectation composée sont des opérations atomiques de lecture-modification-écriture avec un ordre total séquentiellement cohérent (comme si l'on utilisait memory_order_seq_cst). Si une sémantique de synchronisation moins stricte est souhaitée, les fonctions de la bibliothèque standard peuvent être utilisées à la place.

Les propriétés atomiques n'ont de sens que pour les expressions lvalue. La conversion lvalue-vers-rvalue (qui modélise une lecture mémoire depuis un emplacement atomique vers un registre du processeur) supprime l'atomicité avec les autres qualificateurs.

Notes

Accéder à un membre d'une struct/union atomique est un comportement indéfini.

Le type de bibliothèque sig_atomic_t ne fournit ni synchronisation inter-threads ni ordonnancement mémoire, seulement l'atomicité.

Les types volatile ne fournissent ni synchronisation inter-threads, ni ordonnancement mémoire, ni atomicité.

Il est recommandé aux implémentations de garantir que la représentation de _Atomic(T) en C est identique à celle de std::atomic<T> en C++ pour tout type possible T. Les mécanismes utilisés pour garantir l'atomicité et l'ordonnancement mémoire doivent être compatibles.

Exemple

#include <stdatomic.h>
#include <stdio.h>
#include <threads.h>

atomic_int acnt;
int cnt;

int f(void* thr_data)
{
    for (int n = 0; n < 1000; ++n)
    {
        ++cnt;
        ++acnt;
        // pour cet exemple, l'ordre mémoire relaxed suffit, par exemple
        // atomic_fetch_add_explicit(&acnt, 1, memory_order_relaxed);
    }
    return 0;
}

int main(void)
{
    thrd_t thr[10];
    for (int n = 0; n < 10; ++n)
        thrd_create(&thr[n], f, NULL);
    for (int n = 0; n < 10; ++n)
        thrd_join(thr[n], NULL);

    printf("The atomic counter is %u\n", acnt);
    printf("The non-atomic counter is %u\n", cnt);
}

The atomic counter is 10000
The non-atomic counter is 8644
