qualificateur de type restrict (depuis C99)

Traduction automatique (Claude Haiku 5.5) de cppreference.com, sous licence CC-BY-SA 3.0.

Chaque type individuel du système de types du C possède plusieurs versions qualifiées de ce type, correspondant à un, deux ou aux trois qualificateurs const, volatile et, pour les pointeurs vers des types objets, restrict. Cette page décrit les effets du qualificateur restrict.

Seul un pointeur vers un type objet ou un tableau (éventuellement multidimensionnel) de tels types (depuis C23) peut être qualifié restrict ; en particulier, les éléments suivants sont erronés :

  • int restrict *p
  • float (* restrict f9)(void)

La sémantique de restrict ne s'applique qu'aux expressions lvalue ; par exemple, un transtypage vers un pointeur qualifié restrict ou un appel de fonction renvoyant un pointeur qualifié restrict ne sont pas des lvalues et le qualificateur n'a aucun effet.

Lors de chaque exécution d'un bloc dans lequel un pointeur restreint P est déclaré (typiquement chaque exécution d'un corps de fonction dans lequel P est un paramètre de fonction), si un objet accessible via P (directement ou indirectement) est modifié, par quelque moyen que ce soit, alors tous les accès à cet objet (lectures comme écritures) dans ce bloc doivent se faire via P (directement ou indirectement), sinon le comportement est indéfini :

void f(int n, int * restrict p, int * restrict q)
{
    while (n-- > 0)
        *p++ = *q++; // aucun des objets modifiés via *p n'est le même
                     // que l'un quelconque des objets lus via *q
                     // le compilateur est libre d'optimiser, de vectoriser, de mapper les pages, etc.
}

void g(void)
{
    extern int d[100];
    f(50, d + 50, d); // OK
    f(50, d + 1, d);  // Comportement indéfini : d[1] est accédé à la fois via p et q dans f
}

Si l'objet n'est jamais modifié, il peut être aliasé et accédé via différents pointeurs qualifiés restrict (notez que si les objets pointés par des pointeurs qualifiés restrict aliasés sont à leur tour des pointeurs, cet aliasing peut empêcher certaines optimisations).

L'affectation d'un pointeur restreint à un autre pointeur restreint est un comportement indéfini, sauf lorsqu'on affecte un pointeur vers un objet d'un bloc externe à un pointeur d'un bloc interne (y compris en utilisant un argument pointeur restreint lors de l'appel d'une fonction ayant un paramètre pointeur restreint) ou lors d'un retour de fonction (et autrement lorsque le bloc du pointeur source s'est terminé) :

int* restrict p1 = &a;
int* restrict p2 = &b;
p1 = p2; // comportement indéfini

Les pointeurs restreints peuvent être affectés librement à des pointeurs non restreints ; les possibilités d'optimisation demeurent tant que le compilateur est capable d'analyser le code :

void f(int n, float * restrict r, float * restrict s)
{
    float *p = r, *q = s; // OK
    while (n-- > 0)
        *p++ = *q++; // presque certainement optimisé exactement comme *r++ = *s++
}

Si un type tableau est déclaré avec le qualificateur de type restrict (par l'intermédiaire de typedef), le type tableau n'est pas qualifié restrict, mais son type d'élément l'est :

(jusqu'à C23)

Un type tableau et son type d'élément sont toujours considérés comme ayant le même qualificatif restrict :

(depuis C23)

typedef int *array_t[10];

restrict array_t a; // le type de a est int *restrict[10]
// Notes : clang et icc rejettent ceci au motif que array_t n'est pas un type pointeur

void *unqual_ptr = &a; // OK jusqu'à C23 ; erreur depuis C23
// Notes : clang applique la règle en C++/C23 même en modes C89-C17

Dans une déclaration de fonction, le mot-clé restrict peut apparaître entre les crochets utilisés pour déclarer un type tableau d'un paramètre de fonction. Il qualifie le type pointeur vers lequel le type tableau est transformé :

void f(int m, int n, float a[restrict m][n], float b[restrict m][n]);

void g12(int n, float (*p)[n])
{
   f(10, n, p, p+10); // OK
   f(20, n, p, p+10); // comportement éventuellement indéfini (selon ce que fait f)
}

Notes

Le but de l'utilisation du qualificateur restrict (comme celui de la classe de stockage register) est de favoriser l'optimisation, et supprimer toutes les occurrences du qualificateur de toutes les unités de traduction prétraitées composant un programme conforme ne modifie pas sa signification (c'est-à-dire son comportement observable).

Le compilateur est libre d'ignorer tout ou partie des implications d'aliasing des utilisations de restrict.

Pour éviter un comportement indéfini, le programmeur doit s'assurer que les assertions d'aliasing faites par les pointeurs qualifiés restrict ne sont pas violées.

De nombreux compilateurs fournissent, comme extension du langage, l'inverse de restrict : un attribut indiquant que des pointeurs peuvent être aliasés même si leurs types diffèrent : may_alias (gcc),

Schémas d'utilisation

Il existe plusieurs schémas d'utilisation courants pour les pointeurs qualifiés restrict :

Portée de fichier

Un pointeur qualifié restrict de portée fichier doit pointer vers un unique objet tableau pendant toute la durée du programme. Cet objet tableau ne peut pas être référencé à la fois via le pointeur restreint et via son nom déclaré (s'il en a un) ou via un autre pointeur restreint.

Les pointeurs restreints de portée fichier sont utiles pour fournir un accès à des tableaux globaux alloués dynamiquement ; la sémantique de restrict permet d'optimiser les références via ce pointeur aussi efficacement que les références à un tableau statique via son nom déclaré :

float *restrict a, *restrict b;
float c[100];

int init(int n)
{
   float * t = malloc(2*n*sizeof(float));
   a = t;      // a désigne la première moitié
   b = t + n;  // b désigne la seconde moitié
}
// le compilateur peut déduire des qualificateurs restrict que
// il n'existe aucun aliasing potentiel entre les noms a, b et c

Paramètre de fonction

Le cas d'utilisation le plus courant des pointeurs qualifiés restrict est leur emploi comme paramètres de fonction.

Dans l'exemple suivant, le compilateur peut déduire qu'il n'y a aucun aliasing d'objets modifiés, et donc optimiser agressivement la boucle. À l'entrée de f, le pointeur restreint a doit fournir un accès exclusif au tableau qui lui est associé. En particulier, dans f, ni b ni c ne peuvent pointer dans le tableau associé à a, car aucun des deux ne reçoit de valeur de pointeur basée sur a. Pour b, cela est évident grâce au qualificateur const dans sa déclaration, mais pour c, il faut examiner le corps de f :

float x[100];
float *c;

void f(int n, float * restrict a, float * const b)
{
    int i;
    for ( i=0; i<n; i++ )
       a[i] = b[i] + c[i];
}

void g3(void)
{
    float d[100], e[100];
    c = x; f(100,   d,    e); // OK
           f( 50,   d, d+50); // OK
           f( 99, d+1,    d); // comportement indéfini
    c = d; f( 99, d+1,    e); // comportement indéfini
           f( 99,   e,  d+1); // OK
}

Notez qu'il est permis à c de pointer dans le tableau associé à b. Notez également que, pour ces besoins, le « tableau » associé à un pointeur particulier désigne seulement la portion d'un objet tableau qui est effectivement référencée via ce pointeur.

Notez que dans l'exemple ci-dessus, le compilateur peut déduire que a et b ne sont pas aliasés, car le caractère const de b garantit qu'il ne peut pas dépendre de a dans le corps de la fonction. De manière équivalente, le programmeur pourrait écrire void f(int n, float * a, float const * restrict b), auquel cas le compilateur peut raisonner que les objets référencés via b ne peuvent pas être modifiés, et donc aucun objet modifié ne peut être référencé à la fois via b et a. Si le programmeur devait écrire void f(int n, float * restrict a, float * b), le compilateur ne pourrait pas déduire l'absence d'aliasing entre a et b sans examiner le corps de la fonction.

En général, il est préférable d'annoter explicitement tous les pointeurs sans aliasing dans le prototype d'une fonction avec restrict.

Portée de bloc

Un pointeur qualifié restrict de portée de bloc fait une assertion d'aliasing limitée à son bloc. Il permet des assertions locales ne s'appliquant qu'aux blocs importants, comme les boucles serrées. Il permet aussi de transformer une fonction prenant des pointeurs qualifiés restrict en macro :

float x[100];
float *c;

#define f3(N, A, B)                                    \
do                                                     \
{   int n = (N);                                       \
    float * restrict a = (A);                          \
    float * const    b = (B);                          \
    int i;                                             \
    for ( i=0; i<n; i++ )                              \
        a[i] = b[i] + c[i];                            \
} while(0)

Membres de struct

La portée de l'assertion d'aliasing faite par un pointeur qualifié restrict membre d'une struct est la portée de l'identifiant utilisé pour accéder à la struct.

Même si la struct est déclarée en portée fichier, lorsque l'identifiant utilisé pour accéder à la struct a une portée de bloc, les assertions d'aliasing de la struct ont aussi une portée de bloc ; les assertions d'aliasing ne sont en vigueur que pendant l'exécution d'un bloc ou un appel de fonction, selon la manière dont l'objet de ce type struct a été créé :

struct t      // Les pointeurs restreints affirment que
{
   int n;     // les membres pointent vers des zones de stockage disjointes.
   float * restrict p;
   float * restrict q;
};

void ff(struct t r, struct t s)
{
   struct t u;
   // r, s, u ont une portée de bloc
   // r.p, r.q, s.p, s.q, u.p, u.q doivent tous pointer vers
   // des zones de stockage disjointes pendant chaque exécution de ff.
   // ...
}

Exemple

exemple de génération de code ; compiler avec -S (gcc, clang, etc.) ou /FA (Visual Studio)

int foo(int *a, int *b)
{
    *a = 5;
    *b = 6;
    return *a + *b;
}

int rfoo(int *restrict a, int *restrict b)
{
    *a = 5;
    *b = 6;
    return *a + *b;
}

Sortie possible :

; generated code on 64bit Intel platform:
foo:
    movl    $5, (%rdi)    ; store 5 in *a
    movl    $6, (%rsi)    ; store 6 in *b
    movl    (%rdi), %eax  ; read back from *a in case previous store modified it
    addl    $6, %eax      ; add 6 to the value read from *a
    ret

rfoo:
    movl      $11, %eax   ; the result is 11, a compile-time constant
    movl      $5, (%rdi)  ; store 5 in *a
    movl      $6, (%rsi)  ; store 6 in *b
    ret
