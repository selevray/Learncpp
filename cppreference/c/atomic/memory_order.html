enum memory_order
{
    memory_order_relaxed,
    memory_order_consume,
    memory_order_acquire,
    memory_order_release,
    memory_order_acq_rel,
    memory_order_seq_cst
};  // (depuis C11)

memory_order précise comment les accès mémoire, y compris les accès mémoire ordinaires non atomiques, doivent être ordonnés autour d'une opération atomique. Faute de contraintes sur un système multicœur, lorsque plusieurs threads lisent et écrivent simultanément plusieurs variables, un thread peut observer les changements de valeurs dans un ordre différent de celui dans lequel un autre thread les a écrites. En effet, l'ordre apparent des changements peut même différer entre plusieurs threads lecteurs. Certains effets similaires peuvent aussi se produire sur des systèmes monoprocesseurs, en raison des transformations du compilateur permises par le modèle mémoire.

Le comportement par défaut de toutes les opérations atomiques du langage et de la bibliothèque fournit un ordre séquentiellement cohérent (voir la discussion ci-dessous). Ce comportement par défaut peut nuire aux performances, mais les opérations atomiques de la bibliothèque peuvent recevoir un argument supplémentaire memory_order afin de préciser les contraintes exactes, au-delà de l'atomicité, que le compilateur et le processeur doivent appliquer à cette opération.

Constantes

Défini dans l'en-tête <stdatomic.h>

Valeur Explication

  • memory_order_relaxed — Opération relâchée : aucune contrainte de synchronisation ou d'ordre n'est imposée aux autres lectures ou écritures, seule l'atomicité de cette opération est garantie (voir Ordre relâché ci-dessous).
  • memory_order_consume — Une opération de chargement avec cet ordre mémoire effectue une opération consume sur l'emplacement mémoire concerné : aucune lecture ni écriture du thread courant dépendant de la valeur actuellement chargée ne peut être réordonnée avant ce chargement. Les écritures dans des variables dépendant des données, effectuées par d'autres threads qui libèrent la même variable atomique, sont visibles dans le thread courant. Sur la plupart des plates-formes, cela n'affecte que les optimisations du compilateur (voir Ordre release-consume ci-dessous).
  • memory_order_acquire — Une opération de chargement avec cet ordre mémoire effectue l'opération acquire sur l'emplacement mémoire concerné : aucune lecture ni écriture du thread courant ne peut être réordonnée avant ce chargement. Toutes les écritures des autres threads qui libèrent la même variable atomique sont visibles dans le thread courant (voir Ordre release-acquire ci-dessous).
  • memory_order_release — Une opération de stockage avec cet ordre mémoire effectue l'opération release : aucune lecture ni écriture du thread courant ne peut être réordonnée après ce stockage. Toutes les écritures du thread courant sont visibles dans les autres threads qui acquièrent la même variable atomique (voir Ordre release-acquire ci-dessous), et les écritures portant une dépendance vers la variable atomique deviennent visibles dans les autres threads qui consomment la même variable atomique (voir Ordre release-consume ci-dessous).
  • memory_order_acq_rel — Une opération read-modify-write avec cet ordre mémoire est à la fois une opération acquire et une opération release. Aucune lecture ni écriture mémoire du thread courant ne peut être réordonnée avant le chargement, ni après le stockage. Toutes les écritures des autres threads qui libèrent la même variable atomique sont visibles avant la modification, et la modification est visible dans les autres threads qui acquièrent la même variable atomique.
  • memory_order_seq_cst — Une opération de chargement avec cet ordre mémoire effectue une opération acquire, un stockage effectue une opération release, et une opération read-modify-write effectue à la fois une opération acquire et une opération release, et il existe un ordre total unique dans lequel tous les threads observent toutes les modifications dans le même ordre (voir Ordre séquentiellement cohérent ci-dessous).

Ordonnancement relâché

Les opérations atomiques marquées memory_order_relaxed ne sont pas des opérations de synchronisation ; elles n'imposent aucun ordre entre les accès mémoire concurrents. Elles garantissent seulement l'atomicité et la cohérence de l'ordre de modification.

Par exemple, avec x et y initialement à zéro,

// Thread 1 : r1 = atomic_load_explicit(y, memory_order_relaxed); // A atomic_store_explicit(x, r1, memory_order_relaxed); // B // Thread 2 : r2 = atomic_load_explicit(x, memory_order_relaxed); // C atomic_store_explicit(y, 42, memory_order_relaxed); // D peut produire r1 == r2 == 42 car, bien que A soit séquencé avant B dans le thread 1 et que C soit séquencé avant D dans le thread 2, rien n'empêche D d'apparaître avant A dans l'ordre de modification de y, ni B d'apparaître avant C dans l'ordre de modification de x. L'effet de bord de D sur y pourrait être visible par le chargement A dans le thread 1, tandis que l'effet de bord de B sur x pourrait être visible par le chargement C dans le thread 2. En particulier, cela peut se produire si D est terminé avant C dans le thread 2, soit à cause d'une réorganisation par le compilateur, soit à l'exécution.

L'usage typique de l'ordre mémoire relâché consiste à incrémenter des compteurs, comme les compteurs de références , car cela ne requiert que l'atomicité, mais ni ordre ni synchronisation .

Ordonnancement libération-consommation

Si un stockage atomique dans le fil A est marqué memory_order_release, un chargement atomique dans le fil B depuis la même variable est marqué memory_order_consume, et si le chargement dans le fil B lit une valeur écrite par le stockage dans le fil A, alors le stockage dans le fil A est ordonné par dépendance avant le chargement dans le fil B.

Toutes les écritures mémoire (non atomiques et atomiques relâchées) qui ont eu lieu avant le stockage atomique du point de vue du fil A deviennent des effets de bord visibles au sein des opérations du fil B dans lesquelles le chargement porte une dépendance, c'est-à-dire qu'une fois le chargement atomique terminé, les opérateurs et fonctions du fil B qui utilisent la valeur obtenue par ce chargement sont assurés de voir ce que le fil A a écrit en mémoire.

La synchronisation n'est établie qu'entre les fils qui libèrent et consomment la même variable atomique. D'autres fils peuvent observer un ordre des accès mémoire différent de celui de l'un ou des deux fils synchronisés.

Sur tous les processeurs courants, à l'exception du DEC Alpha, l'ordonnancement par dépendance est automatique ; aucune instruction CPU supplémentaire n'est émise pour ce mode de synchronisation, seules certaines optimisations du compilateur sont affectées (par exemple, le compilateur ne peut pas effectuer de chargements spéculatifs sur les objets impliqués dans la chaîne de dépendance).

Les cas d'utilisation typiques de cet ordonnancement concernent la lecture de structures de données concurrentes rarement écrites (tables de routage, configuration, politiques de sécurité, règles de pare-feu, etc.) et les situations éditeur-abonné avec publication par pointeur, c'est-à-dire lorsque le producteur publie un pointeur par lequel le consommateur peut accéder à des informations : il n'est pas nécessaire de rendre visible au consommateur tout le reste que le producteur a écrit en mémoire (ce qui peut être une opération coûteuse sur les architectures à ordre faible). Un exemple d'un tel scénario est rcu_dereference.

Notez qu'actuellement (2/2015) aucun compilateur de production connu ne suit les chaînes de dépendance : les opérations consume sont remontées en opérations acquire.

Séquence de libération

Si un atomique est écrit avec une sémantique release et que plusieurs autres threads effectuent des opérations de lecture-modification-écriture sur cet atomique, une « séquence de libération » (release sequence) se forme : tous les threads qui effectuent les lectures-modifications-écritures sur le même atomique se synchronisent avec le premier thread et entre eux, même s'ils n'ont aucune sémantique memory_order_release. Cela rend possibles les situations à un producteur et plusieurs consommateurs, sans imposer de synchronisation inutile entre les threads consommateurs.

Ordonnancement libération-acquisition

Si un stockage atomique dans le fil A est marqué memory_order_release, un chargement atomique dans le fil B depuis la même variable est marqué memory_order_acquire, et si le chargement dans le fil B lit une valeur écrite par le stockage dans le fil A, alors le stockage dans le fil A se synchronise avec le chargement dans le fil B.

Toutes les écritures mémoire (y compris non atomiques et atomiques relâchées) qui ont eu lieu avant le stockage atomique du point de vue du fil A deviennent des effets de bord visibles dans le fil B. Autrement dit, une fois le chargement atomique terminé, le fil B est assuré de voir tout ce que le fil A a écrit en mémoire. Cette garantie n'est valable que si B renvoie effectivement la valeur que A a stockée, ou une valeur provenant d'un point ultérieur de la séquence de libération.

La synchronisation n'est établie qu'entre les fils qui libèrent et acquièrent la même variable atomique. D'autres fils peuvent observer un ordre des accès mémoire différent de celui de l'un ou des deux fils synchronisés.

Sur les systèmes à ordre fort — x86, SPARC TSO, mainframes IBM, etc. — l'ordonnancement libération-acquisition est automatique pour la majorité des opérations. Aucune instruction CPU supplémentaire n'est émise pour ce mode de synchronisation ; seules certaines optimisations du compilateur sont affectées (par exemple, le compilateur ne peut pas déplacer des stockages non atomiques au-delà du stockage-libération atomique, ni effectuer des chargements non atomiques plus tôt que le chargement-acquisition atomique). Sur les systèmes à ordre faible (ARM, Itanium, PowerPC), des instructions CPU spéciales de chargement ou de barrière mémoire sont utilisées.

Les verrous d'exclusion mutuelle, comme les mutex ou les verrous tournants atomiques, sont un exemple de synchronisation release-acquire : lorsque le verrou est libéré par le thread A et acquis par le thread B, tout ce qui s'est produit dans la section critique (avant la libération) dans le contexte du thread A doit être visible par le thread B (après l'acquisition) qui exécute la même section critique.

Ordonnancement séquentiellement cohérent

Les opérations atomiques marquées memory_order_seq_cst ordonnent non seulement la mémoire de la même façon que l'ordonnancement release/acquire (tout ce qui happens-before une écriture dans un thread devient un effet de bord visible dans le thread qui effectue une lecture), mais établissent également un ordre de modification total unique de toutes les opérations atomiques ainsi marquées.

Formellement,

chaque opération memory_order_seq_cst B qui lit depuis la variable atomique M observe l'un des cas suivants :

  • le résultat de la dernière opération A ayant modifié M, qui apparaît avant B dans l'ordre total unique,
  • OU, s'il existe une telle A, B peut observer le résultat d'une modification de M qui n'est pas memory_order_seq_cst et qui ne happens-before pas A,
  • OU, s'il n'existe pas une telle A, B peut observer le résultat d'une modification non liée de M qui n'est pas memory_order_seq_cst.

S'il existait une opération memory_order_seq_cst atomic_thread_fence X sequenced-before B, alors B observe l'un des cas suivants :

  • la dernière modification memory_order_seq_cst de M qui apparaît avant X dans l'ordre total unique,
  • une modification non liée de M qui apparaît plus tard dans l'ordre de modification de M.

Pour une paire d'opérations atomiques sur M appelées A et B, où A écrit et B lit la valeur de M, s'il existe deux memory_order_seq_cst atomic_thread_fence X et Y, si A est sequenced-before X, Y est sequenced-before B, et X apparaît avant Y dans l'ordre total unique, alors B observe soit :

  • l'effet de A,
  • une modification non liée de M qui apparaît après A dans l'ordre de modification de M.

Pour une paire de modifications atomiques de M appelées A et B, B a lieu après A dans l'ordre de modification de M si

  • il existe une memory_order_seq_cst atomic_thread_fence X telle que A est sequenced-before X et X apparaît avant B dans l'ordre total unique,
  • ou il existe une memory_order_seq_cst atomic_thread_fence Y telle que Y est sequenced-before B et A apparaît avant Y dans l'ordre total unique,
  • ou il existe des memory_order_seq_cst atomic_thread_fence X et Y telles que A est sequenced-before X, Y est sequenced-before B, et X apparaît avant Y dans l'ordre total unique.

Notez que cela signifie que :

  1. dès que des opérations atomiques qui ne sont pas marquées memory_order_seq_cst entrent en jeu, la cohérence séquentielle est perdue,

  2. les barrières séquentiellement cohérentes n'établissent un ordre total que pour les barrières elles-mêmes, et non pour les opérations atomiques en général (sequenced-before n'est pas une relation inter-threads, contrairement à happens-before).

L'ordre séquentiel peut être nécessaire pour les situations à plusieurs producteurs et plusieurs consommateurs où tous les consommateurs doivent observer les actions de tous les producteurs dans le même ordre.

L'ordre séquentiel total nécessite une instruction CPU de barrière mémoire complète sur tous les systèmes multicœurs. Cela peut devenir un goulot d'étranglement de performance, car cela force la propagation des accès mémoire concernés vers chaque cœur.

Relation avec volatile

Au sein d'un fil d'exécution, les accès (lectures et écritures) via des lvalues volatiles ne peuvent pas être réordonnés au-delà d'effets de bord observables (y compris d'autres accès volatiles) séparés par un point de séquence dans le même thread, mais cet ordre n'est pas garanti d'être observé par un autre thread, puisque l'accès volatile n'établit pas de synchronisation entre threads.

De plus, les accès volatile ne sont pas atomiques (une lecture et une écriture concurrentes constituent une course aux données) et n'ordonnent pas la mémoire (les accès mémoire non volatile peuvent être librement réordonnés autour de l'accès volatile).

Une exception notable est Visual Studio, où, avec les paramètres par défaut, chaque écriture volatile a une sémantique release et chaque lecture volatile a une sémantique acquire (Microsoft Docs), de sorte que les volatile peuvent être utilisés pour la synchronisation inter-threads. La sémantique standard de volatile n'est pas applicable à la programmation multithread, bien qu'elle soit suffisante, par exemple, pour communiquer avec un gestionnaire signal qui s'exécute dans le même thread lorsqu'elle est appliquée à des variables sig_atomic_t.
