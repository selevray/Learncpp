22.3 — Constructeurs de déplacement et affectation par déplacement

Dans la leçon 22.1 -- Introduction aux pointeurs intelligents et à la sémantique de déplacement, nous avons étudié std::auto_ptr, expliqué le besoin de sémantique de déplacement et observé certains inconvénients qui apparaissent lorsque les fonctions conçues pour la sémantique de copie (constructeurs de copie et opérateurs d'affectation par copie) sont redéfinies pour implémenter la sémantique de déplacement.

Dans cette leçon, nous allons examiner plus en détail comment le C++11 résout ces problèmes grâce aux constructeurs de déplacement et à l'affectation par déplacement.

Rappel sur les constructeurs de copie et l'affectation par copie

Commençons par un rappel de la sémantique de copie.

Les constructeurs de copie servent à initialiser une classe en créant une copie d'un objet de cette même classe. L'affectation par copie sert à copier un objet de classe dans un autre objet de classe déjà existant. Par défaut, le C++ fournit un constructeur de copie et un opérateur d'affectation par copie si vous n'en définissez pas explicitement. Ces fonctions fournies par le compilateur effectuent des copies superficielles (shallow copies), ce qui peut poser problème pour les classes qui allouent de la mémoire dynamique. Les classes qui gèrent de la mémoire dynamique doivent donc redéfinir ces fonctions pour effectuer des copies profondes (deep copies).

Revenons à notre exemple de pointeur intelligent Auto_ptr de la première leçon de ce chapitre. Voici une version qui implémente un constructeur de copie et un opérateur d'affectation par copie effectuant des copies profondes, accompagnée d'un programme qui les utilise :

#include <iostream>

template<typename T>
class Auto_ptr3
{
    T* m_ptr {};
public:
    Auto_ptr3(T* ptr = nullptr)
        : m_ptr { ptr }
    {
    }

    ~Auto_ptr3()
    {
        delete m_ptr;
    }

    // Constructeur de copie
    // Copie profonde de a.m_ptr dans m_ptr
    Auto_ptr3(const Auto_ptr3& a)
    {
        m_ptr = new T;
        *m_ptr = *a.m_ptr;
    }

    // Affectation par copie
    // Copie profonde de a.m_ptr dans m_ptr
    Auto_ptr3& operator=(const Auto_ptr3& a)
    {
        // Détection de l'auto-affectation
        if (&a == this)
            return *this;

        // Libérer la ressource que nous détenons
        delete m_ptr;

        // Copier la ressource
        m_ptr = new T;
        *m_ptr = *a.m_ptr;

        return *this;
    }

    T& operator*() const { return *m_ptr; }
    T* operator->() const { return m_ptr; }
    bool isNull() const { return m_ptr == nullptr; }
};

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

Auto_ptr3<Resource> generateResource()
{
    Auto_ptr3<Resource> res{new Resource};
    return res; // cette valeur de retour va invoquer le constructeur de copie
}

int main()
{
    Auto_ptr3<Resource> mainres;
    mainres = generateResource(); // cette affectation va invoquer l'affectation par copie

    return 0;
}

Dans ce programme, la fonction generateResource() crée un pointeur intelligent encapsulant une ressource, qui est ensuite renvoyé à la fonction main(). Celle-ci l'affecte alors à un objet Auto_ptr3 existant.

Lorsque ce programme est exécuté, il affiche :


Resource acquired
Resource acquired
Resource destroyed
Resource acquired
Resource destroyed
Resource destroyed

(Remarque : vous ne verrez peut-être que 4 lignes si votre compilateur élide la valeur de retour de la fonction generateResource().)

Beaucoup de création et de destruction de ressources pour un programme aussi simple ! Que se passe-t-il ?

Examinons cela de plus près. Ce programme comporte 6 étapes clés (une par message affiché) :

  1. Dans generateResource(), la variable locale res est créée et initialisée avec une Resource allouée dynamiquement, ce qui produit le premier « Resource acquired ».
  2. res est renvoyé à main() par valeur. Nous renvoyons par valeur ici car res est une variable locale : elle ne peut pas être renvoyée par adresse ni par référence, puisqu'elle sera détruite à la fin de generateResource(). res est donc copié par construction dans un objet temporaire. Comme notre constructeur de copie effectue une copie profonde, une nouvelle Resource est allouée ici, ce qui produit le deuxième « Resource acquired ».
  3. res sort de sa portée, ce qui détruit la Resource créée à l'origine, produisant le premier « Resource destroyed ».
  4. L'objet temporaire est affecté à mainres par affectation par copie. Comme notre affectation par copie effectue aussi une copie profonde, une nouvelle Resource est allouée, produisant encore un « Resource acquired ».
  5. L'expression d'affectation se termine, l'objet temporaire sort de sa portée d'expression et est détruit, produisant un « Resource destroyed ».
  6. À la fin de main(), mainres sort de sa portée, et notre dernier « Resource destroyed » est affiché.

En bref, parce que nous appelons une fois le constructeur de copie pour copier res dans un temporaire, puis une fois l'affectation par copie pour copier le temporaire dans mainres, nous allouons et détruisons au total 3 objets distincts.

C'est inefficace, mais au moins cela ne plante pas !

Avec la sémantique de déplacement, nous pouvons faire mieux.

Constructeurs de déplacement et affectation par déplacement

Le C++11 définit deux nouvelles fonctions au service de la sémantique de déplacement : un constructeur de déplacement et un opérateur d'affectation par déplacement. Alors que le but du constructeur de copie et de l'affectation par copie est de copier un objet dans un autre, le but du constructeur de déplacement et de l'affectation par déplacement est de transférer la propriété des ressources d'un objet à un autre (ce qui coûte généralement beaucoup moins cher qu'une copie).

La définition d'un constructeur de déplacement et d'une affectation par déplacement fonctionne de manière analogue à leurs équivalents de copie. Cependant, alors que les versions « copie » de ces fonctions prennent un paramètre de référence lvalue constante (qui se lie à à peu près n'importe quoi), les versions « déplacement » prennent un paramètre de référence rvalue non constante (qui ne se lie qu'à des rvalues).

Voici la même classe Auto_ptr3 que précédemment, avec un constructeur de déplacement et un opérateur d'affectation par déplacement ajoutés. Nous avons conservé le constructeur de copie et l'opérateur d'affectation par copie effectuant des copies profondes, à des fins de comparaison.

#include <iostream>

template<typename T>
class Auto_ptr4
{
    T* m_ptr {};
public:
    Auto_ptr4(T* ptr = nullptr)
        : m_ptr { ptr }
    {
    }

    ~Auto_ptr4()
    {
        delete m_ptr;
    }

    // Constructeur de copie
    // Copie profonde de a.m_ptr dans m_ptr
    Auto_ptr4(const Auto_ptr4& a)
    {
        m_ptr = new T;
        *m_ptr = *a.m_ptr;
    }

    // Constructeur de déplacement
    // Transfert de la propriété de a.m_ptr à m_ptr
    Auto_ptr4(Auto_ptr4&& a) noexcept
        : m_ptr { a.m_ptr }
    {
        a.m_ptr = nullptr; // nous reviendrons plus loin sur cette ligne
    }

    // Affectation par copie
    // Copie profonde de a.m_ptr dans m_ptr
    Auto_ptr4& operator=(const Auto_ptr4& a)
    {
        // Détection de l'auto-affectation
        if (&a == this)
            return *this;

        // Libérer la ressource que nous détenons
        delete m_ptr;

        // Copier la ressource
        m_ptr = new T;
        *m_ptr = *a.m_ptr;

        return *this;
    }

    // Affectation par déplacement
    // Transfert de la propriété de a.m_ptr à m_ptr
    Auto_ptr4& operator=(Auto_ptr4&& a) noexcept
    {
        // Détection de l'auto-affectation
        if (&a == this)
            return *this;

        // Libérer la ressource que nous détenons
        delete m_ptr;

        // Transférer la propriété de a.m_ptr à m_ptr
        m_ptr = a.m_ptr;
        a.m_ptr = nullptr; // nous reviendrons plus loin sur cette ligne

        return *this;
    }

    T& operator*() const { return *m_ptr; }
    T* operator->() const { return m_ptr; }
    bool isNull() const { return m_ptr == nullptr; }
};

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

Auto_ptr4<Resource> generateResource()
{
    Auto_ptr4<Resource> res{new Resource};
    return res; // cette valeur de retour va invoquer le constructeur de déplacement
}

int main()
{
    Auto_ptr4<Resource> mainres;
    mainres = generateResource(); // cette affectation va invoquer l'affectation par déplacement

    return 0;
}

Le constructeur de déplacement et l'opérateur d'affectation par déplacement sont simples. Au lieu de copier profondément l'objet source (a) dans l'objet destination (l'objet implicite), nous déplaçons (nous « volons ») simplement les ressources de l'objet source. Cela consiste à copier superficiellement le pointeur source dans l'objet implicite, puis à mettre le pointeur source à null.

Lorsqu'il est exécuté, ce programme affiche :


Resource acquired
Resource destroyed

C'est bien mieux !

Le déroulement du programme est exactement le même qu'auparavant. Cependant, au lieu d'appeler le constructeur de copie et l'affectation par copie, ce programme appelle le constructeur de déplacement et l'affectation par déplacement. En regardant de plus près :

  1. Dans generateResource(), la variable locale res est créée et initialisée avec une Resource allouée dynamiquement, ce qui produit le premier « Resource acquired ».
  2. res est renvoyé à main() par valeur. res est construit par déplacement dans un objet temporaire, transférant l'objet alloué dynamiquement stocké dans res vers le temporaire. Nous verrons plus loin pourquoi cela se produit.
  3. res sort de sa portée. Comme res ne gère plus de pointeur (il a été déplacé vers le temporaire), rien d'intéressant ne se produit ici.
  4. Le temporaire est affecté à mainres par déplacement. Cela transfère l'objet alloué dynamiquement stocké dans le temporaire vers mainres.
  5. L'expression d'affectation se termine, et l'objet temporaire sort de sa portée d'expression et est détruit. Mais comme le temporaire ne gère plus de pointeur (il a été déplacé vers mainres), rien d'intéressant ne se produit non plus.
  6. À la fin de main(), mainres sort de sa portée, et notre dernier « Resource destroyed » est affiché.

Ainsi, au lieu de copier notre Resource deux fois (une fois pour le constructeur de copie et une fois pour l'affectation par copie), nous la transférons deux fois. C'est plus efficace, car Resource n'est construite et détruite qu'une seule fois au lieu de trois.

Contenu associé

Les constructeurs de déplacement et l'affectation par déplacement devraient être marqués noexcept. Cela indique au compilateur que ces fonctions ne lèveront pas d'exceptions.

Nous présentons noexcept dans la leçon 27.9 -- Spécifications d'exception et noexcept et expliquons pourquoi les constructeurs de déplacement et l'affectation par déplacement sont marqués noexcept dans la leçon 27.10 -- std::move_if_noexcept.

Quand le constructeur de déplacement et l'affectation par déplacement sont-ils appelés ?

Le constructeur de déplacement et l'affectation par déplacement sont appelés lorsque ces fonctions ont été définies et que l'argument de la construction ou de l'affectation est une rvalue. Le plus souvent, cette rvalue sera un littéral ou une valeur temporaire.

Le constructeur de copie et l'affectation par copie sont utilisés dans les autres cas (lorsque l'argument est une lvalue, ou lorsque l'argument est une rvalue et que le constructeur de déplacement ou l'affectation par déplacement ne sont pas définis).

Constructeur de déplacement et opérateur d'affectation par déplacement implicites

Le compilateur crée un constructeur de déplacement et un opérateur d'affectation par déplacement implicites si toutes les conditions suivantes sont réunies :

  • Il n'existe pas de constructeur de copie ni d'opérateur d'affectation par copie déclarés par l'utilisateur.
  • Il n'existe pas de constructeur de déplacement ni d'opérateur d'affectation par déplacement déclarés par l'utilisateur.
  • Il n'existe pas de destructeur déclaré par l'utilisateur.

Ces fonctions effectuent un déplacement membre à membre, qui se comporte ainsi :

  • Si le membre possède un constructeur de déplacement ou une affectation par déplacement (selon le cas), celui-ci est invoqué.
  • Sinon, le membre est copié.

Notamment, cela signifie que les pointeurs sont copiés, et non déplacés !

Attention

Le constructeur de déplacement et l'affectation par déplacement implicites copient les pointeurs, sans les déplacer. Si vous voulez déplacer un membre pointeur, vous devez définir vous-même le constructeur de déplacement et l'affectation par déplacement.

L'idée clé derrière la sémantique de déplacement

Vous disposez maintenant du contexte nécessaire pour comprendre l'idée clé de la sémantique de déplacement.

Si nous construisons un objet ou effectuons une affectation dont l'argument est une lvalue, la seule chose raisonnable à faire est de copier cette lvalue. Nous ne pouvons pas supposer qu'il est sûr de la modifier, car elle peut être utilisée à nouveau plus tard dans le programme. Pour l'expression « a = b » (où b est une lvalue), nous ne nous attendrions raisonnablement pas à ce que b soit modifié d'une quelconque façon.

En revanche, si nous construisons un objet ou effectuons une affectation dont l'argument est une rvalue, alors nous savons que cette rvalue est un objet temporaire d'une sorte ou d'une autre. Au lieu de le copier (ce qui peut être coûteux), nous pouvons simplement transférer ses ressources (ce qui est peu coûteux) vers l'objet que nous sommes en train de construire ou d'affecter. C'est sûr, car le temporaire sera de toute façon détruit à la fin de l'expression, donc nous savons qu'il ne sera plus jamais utilisé !

Le C++11, grâce aux références rvalue, nous donne la possibilité de fournir des comportements différents selon que l'argument est une rvalue ou une lvalue, ce qui nous permet de prendre des décisions plus intelligentes et plus efficaces quant au comportement de nos objets.

Point clé

La sémantique de déplacement est une opportunité d'optimisation.

Les fonctions de déplacement doivent toujours laisser les deux objets dans un état valide

Dans les exemples ci-dessus, le constructeur de déplacement et l'affectation par déplacement mettent tous deux a.m_ptr à nullptr. Cela peut sembler superflu : après tout, si a est une rvalue temporaire, pourquoi se donner la peine de faire ce « nettoyage » alors que le paramètre a va de toute façon être détruit ?

La réponse est simple : lorsque a sort de sa portée, le destructeur de a est appelé, et a.m_ptr est supprimé. Si, à ce moment-là, a.m_ptr pointe encore vers le même objet que m_ptr, alors m_ptr resterait un pointeur pendant (dangling pointer). Lorsque l'objet contenant m_ptr sera finalement utilisé (ou détruit), nous obtiendrons un comportement indéfini.

Lors de l'implémentation de la sémantique de déplacement, il est donc important de s'assurer que l'objet source laissé après le déplacement reste dans un état valide, afin qu'il puisse être détruit correctement (sans provoquer de comportement indéfini).

Les lvalues automatiques renvoyées par valeur peuvent être déplacées plutôt que copiées

Dans la fonction generateResource() de l'exemple Auto_ptr4 ci-dessus, lorsque la variable res est renvoyée par valeur, elle est déplacée au lieu d'être copiée, bien que res soit une lvalue. La spécification du C++ contient une règle spéciale selon laquelle les objets automatiques renvoyés par valeur par une fonction peuvent être déplacés même s'il s'agit de lvalues. C'est logique, puisque res allait de toute façon être détruit à la fin de la fonction ! Autant voler ses ressources plutôt que de faire une copie coûteuse et inutile.

Bien que le compilateur puisse déplacer les valeurs de retour lvalue, dans certains cas il peut faire encore mieux en éliminant simplement la copie (ce qui évite de devoir effectuer une copie ou un déplacement). Dans un tel cas, ni le constructeur de copie ni le constructeur de déplacement ne seraient appelés.

Interdire la copie

Dans la classe Auto_ptr4 ci-dessus, nous avons conservé le constructeur de copie et l'opérateur d'affectation à des fins de comparaison. Mais dans les classes compatibles avec le déplacement, il est parfois souhaitable de supprimer le constructeur de copie et l'affectation par copie afin d'empêcher que des copies soient faites. Dans le cas de notre classe Auto_ptr, nous ne voulons pas copier notre objet templaté T : d'abord parce que c'est coûteux, ensuite parce que la classe T peut ne même pas supporter la copie !

Voici une version d'Auto_ptr qui prend en charge la sémantique de déplacement mais pas la sémantique de copie :

#include <iostream>

template<typename T>
class Auto_ptr5
{
    T* m_ptr {};
public:
    Auto_ptr5(T* ptr = nullptr)
        : m_ptr { ptr }
    {
    }

    ~Auto_ptr5()
    {
        delete m_ptr;
    }

    // Constructeur de copie -- copie interdite !
    Auto_ptr5(const Auto_ptr5& a) = delete;

    // Constructeur de déplacement
    // Transfert de la propriété de a.m_ptr à m_ptr
    Auto_ptr5(Auto_ptr5&& a) noexcept
        : m_ptr { a.m_ptr }
    {
        a.m_ptr = nullptr;
    }

    // Affectation par copie -- copie interdite !
    Auto_ptr5& operator=(const Auto_ptr5& a) = delete;

    // Affectation par déplacement
    // Transfert de la propriété de a.m_ptr à m_ptr
    Auto_ptr5& operator=(Auto_ptr5&& a) noexcept
    {
        // Détection de l'auto-affectation
        if (&a == this)
            return *this;

        // Libérer la ressource que nous détenons
        delete m_ptr;

        // Transférer la propriété de a.m_ptr à m_ptr
        m_ptr = a.m_ptr;
        a.m_ptr = nullptr;

        return *this;
    }

    T& operator*() const { return *m_ptr; }
    T* operator->() const { return m_ptr; }
    bool isNull() const { return m_ptr == nullptr; }
};

Si vous essayez de passer une lvalue Auto_ptr5 à une fonction par valeur, le compilateur signalera que le constructeur de copie nécessaire à l'initialisation du paramètre a été supprimé. C'est une bonne chose, car il vaudrait de toute façon mieux passer Auto_ptr5 par référence lvalue constante !

Auto_ptr5 est (enfin) une bonne classe de pointeur intelligent. D'ailleurs, la bibliothèque standard contient une classe très proche de celle-ci (que vous devriez utiliser à la place), nommée std::unique_ptr. Nous reviendrons plus en détail sur std::unique_ptr plus loin dans ce chapitre.

Un autre exemple

Examinons une autre classe qui utilise la mémoire dynamique : un simple tableau dynamique templaté. Cette classe contient un constructeur de copie et un opérateur d'affectation par copie effectuant des copies profondes.

#include <cstddef> // pour std::size_t

template <typename T>
class DynamicArray
{
private:
    T* m_array {};
    int m_length {};

    void alloc(int length)
    {
        m_array = new T[static_cast<std::size_t>(length)];
            m_length = length;
    }
public:
    DynamicArray(int length)
    {
        alloc(length);
    }

    ~DynamicArray()
    {
        delete[] m_array;
    }

    // Constructeur de copie
    DynamicArray(const DynamicArray &arr)
    {
        alloc(arr.m_length);
        std::copy_n(arr.m_array, m_length, m_array); // copie m_length éléments de arr vers m_array
    }

    // Affectation par copie
    DynamicArray& operator=(const DynamicArray &arr)
    {
        if (&arr == this)
            return *this;

        delete[] m_array;

        alloc(arr.m_length);

        std::copy_n(arr.m_array, m_length, m_array); // copie m_length éléments de arr vers m_array

        return *this;
    }

    int getLength() const { return m_length; }
    T& operator[](int index) { return m_array[index]; }
    const T& operator[](int index) const { return m_array[index]; }
};

Utilisons maintenant cette classe dans un programme. Pour montrer le comportement de cette classe lorsque nous allouons un million d'entiers sur le tas, nous allons nous appuyer sur la classe Timer que nous avons développée dans la leçon 18.4 -- Mesurer le temps d'exécution de votre code. Nous utiliserons la classe Timer pour mesurer la vitesse d'exécution de notre code, et montrer la différence de performance entre copie et déplacement.

#include <algorithm> // pour std::copy_n
#include <chrono> // pour les fonctions de std::chrono
#include <iostream>

// Utilise la classe DynamicArray ci-dessus

class Timer
{
private:
    // Alias de types pour faciliter l'accès au type imbriqué
    using Clock = std::chrono::high_resolution_clock;
    using Second = std::chrono::duration<double, std::ratio<1> >;

    std::chrono::time_point<Clock> m_beg { Clock::now() };

public:
    void reset()
    {
        m_beg = Clock::now();
    }

    double elapsed() const
    {
        return std::chrono::duration_cast<Second>(Clock::now() - m_beg).count();
    }
};

// Renvoie une copie de arr dont toutes les valeurs sont doublées
DynamicArray<int> cloneArrayAndDouble(const DynamicArray<int> &arr)
{
    DynamicArray<int> dbl(arr.getLength());
    for (int i = 0; i < arr.getLength(); ++i)
        dbl[i] = arr[i] * 2;

    return dbl;
}

int main()
{
    Timer t;

    DynamicArray<int> arr(1000000);

    for (int i = 0; i < arr.getLength(); i++)
        arr[i] = i;

    arr = cloneArrayAndDouble(arr);

    std::cout << t.elapsed();
}

Sur l'une des machines de l'auteur, en mode release, ce programme s'est exécuté en 0,00825559 seconde.

Mettons maintenant à jour DynamicArray en remplaçant le constructeur de copie et l'affectation par copie par un constructeur de déplacement et une affectation par déplacement, puis relançons le programme :

#include <cstddef> // pour std::size_t

template <typename T>
class DynamicArray
{
private:
    T* m_array {};
    int m_length {};

    void alloc(int length)
    {
        m_array = new T[static_cast<std::size_t>(length)];
        m_length = length;
    }
public:
    DynamicArray(int length)
    {
        alloc(length);
    }

    ~DynamicArray()
    {
        delete[] m_array;
    }

    // Constructeur de copie
    DynamicArray(const DynamicArray &arr) = delete;

    // Affectation par copie
    DynamicArray& operator=(const DynamicArray &arr) = delete;

    // Constructeur de déplacement
    DynamicArray(DynamicArray &&arr) noexcept
        :  m_array { arr.m_array }, m_length { arr.m_length }
    {
        arr.m_length = 0;
        arr.m_array = nullptr;
    }

    // Affectation par déplacement
    DynamicArray& operator=(DynamicArray &&arr) noexcept
    {
        if (&arr == this)
            return *this;

        delete[] m_array;

        m_length = arr.m_length;
        m_array = arr.m_array;
        arr.m_length = 0;
        arr.m_array = nullptr;

        return *this;
    }

    int getLength() const { return m_length; }
    T& operator[](int index) { return m_array[index]; }
    const T& operator[](int index) const { return m_array[index]; }
};

#include <iostream>
#include <chrono> // pour les fonctions de std::chrono

class Timer
{
private:
    // Alias de types pour faciliter l'accès au type imbriqué
    using Clock = std::chrono::high_resolution_clock;
    using Second = std::chrono::duration<double, std::ratio<1> >;

    std::chrono::time_point<Clock> m_beg { Clock::now() };

public:
    void reset()
    {
        m_beg = Clock::now();
    }

    double elapsed() const
    {
        return std::chrono::duration_cast<Second>(Clock::now() - m_beg).count();
    }
};

// Renvoie une copie de arr dont toutes les valeurs sont doublées
DynamicArray<int> cloneArrayAndDouble(const DynamicArray<int> &arr)
{
    DynamicArray<int> dbl(arr.getLength());
    for (int i = 0; i < arr.getLength(); ++i)
        dbl[i] = arr[i] * 2;

    return dbl;
}

int main()
{
    Timer t;

    DynamicArray<int> arr(1000000);

    for (int i = 0; i < arr.getLength(); i++)
        arr[i] = i;

    arr = cloneArrayAndDouble(arr);

    std::cout << t.elapsed();
}

Sur la même machine, ce programme s'est exécuté en 0,0056 seconde.

En comparant les temps d'exécution des deux programmes, (0,00825559 - 0,0056) / 0,00825559 * 100 = 32,1 % plus rapide !

Supprimer le constructeur de déplacement et l'affectation par déplacement

Vous pouvez supprimer le constructeur de déplacement et l'affectation par déplacement à l'aide de la syntaxe = delete, exactement de la même manière que pour le constructeur de copie et l'affectation par copie.

#include <iostream>
#include <string>
#include <string_view>

class Name
{
private:
    std::string m_name {};

public:
    Name(std::string_view name) : m_name{ name }
    {
    }

    Name(const Name& name) = delete;
    Name& operator=(const Name& name) = delete;
    Name(Name&& name) = delete;
    Name& operator=(Name&& name) = delete;

    const std::string& get() const { return m_name; }
};

int main()
{
    Name n1{ "Alex" };
    n1 = Name{ "Joe" }; // erreur : l'affectation par déplacement est supprimée

    std::cout << n1.get() << '\n';

    return 0;
}

Si vous supprimez le constructeur de copie, le compilateur ne génère pas de constructeur de déplacement implicite (vos objets ne sont alors ni copiables ni déplaçables). Il est donc utile, lorsque vous supprimez le constructeur de copie, d'être explicite quant au comportement souhaité pour vos constructeurs de déplacement. Soit vous les supprimez explicitement (ce qui indique clairement le comportement voulu), soit vous les mettez par défaut (= default), ce qui rend la classe uniquement déplaçable.

Point clé

La règle des cinq indique que si le constructeur de copie, l'affectation par copie, le constructeur de déplacement, l'affectation par déplacement ou le destructeur sont définis ou supprimés, alors chacune de ces fonctions doit être définie ou supprimée.

Bien que supprimer uniquement le constructeur de déplacement et l'affectation par déplacement puisse sembler une bonne idée si vous voulez un objet copiable mais non déplaçable, cela a le fâcheux inconvénient de rendre la classe impossible à renvoyer par valeur dans les cas où l'élision de copie obligatoire ne s'applique pas. Cela tient au fait qu'un constructeur de déplacement supprimé reste une fonction déclarée, donc éligible à la résolution de surcharge. Or le renvoi par valeur privilégiera un constructeur de déplacement supprimé par rapport à un constructeur de copie non supprimé. Le programme suivant l'illustre :

#include <iostream>
#include <string>
#include <string_view>

class Name
{
private:
    std::string m_name {};

public:
    Name(std::string_view name) : m_name{ name }
    {
    }

    Name(const Name& name) = default;
    Name& operator=(const Name& name) = default;

    Name(Name&& name) = delete;
    Name& operator=(Name&& name) = delete;

    const std::string& get() const { return m_name; }
};

Name getJoe()
{
    Name joe{ "Joe" };
    return joe; // erreur : le constructeur de déplacement a été supprimé
}

int main()
{
    Name n{ getJoe() };

    std::cout << n.get() << '\n';

    return 0;
}

Problèmes liés à la sémantique de déplacement et à std::swap (avancé)

Dans la leçon 21.12 -- Surcharge de l'opérateur d'affectation, nous avons mentionné l'idiome copie-et-échange (copy and swap). Copier-et-échanger fonctionne aussi pour la sémantique de déplacement : nous pouvons donc implémenter le constructeur de déplacement et l'affectation par déplacement en échangeant les ressources avec l'objet qui va être détruit.

Cela présente deux avantages :

  • L'objet persistant contrôle désormais les ressources qui appartenaient auparavant à l'objet en cours de destruction (ce qui était notre objectif principal).
  • L'objet en cours de destruction contrôle désormais les ressources qui appartenaient auparavant à l'objet persistant. Lorsque cet objet est réellement détruit, il peut effectuer tout nettoyage nécessaire sur ces ressources.

Lorsqu'on pense à l'échange, la première chose qui vient généralement à l'esprit est std::swap(). Cependant, implémenter le constructeur de déplacement et l'affectation par déplacement à l'aide de std::swap() pose problème, car std::swap() appelle à la fois le constructeur de déplacement et l'affectation par déplacement sur les objets pouvant être déplacés. Il en résulte un problème de récursion infinie.

Vous pouvez le constater dans l'exemple suivant :

#include <iostream>
#include <string>
#include <string_view>

class Name
{
private:
    std::string m_name {}; // std::string peut être déplacé

public:
    Name(std::string_view name) : m_name{ name }
    {
    }

    Name(const Name& name) = delete;
    Name& operator=(const Name& name) = delete;

    Name(Name&& name) noexcept
    {
        std::cout << "Move ctor\n";

        std::swap(*this, name); // mauvais !
    }

    Name& operator=(Name&& name) noexcept
    {
        std::cout << "Move assign\n";

        std::swap(*this, name); // mauvais !

        return *this;
    }

    const std::string& get() const { return m_name; }
};

int main()
{
    Name n1{ "Alex" };
    n1 = Name{"Joe"}; // invoque l'affectation par déplacement

    std::cout << n1.get() << '\n';

    return 0;
}

Move ctor
Move ctor
Move ctor

Et ainsi de suite… jusqu'à ce que la pile déborde.

Vous pouvez implémenter le constructeur de déplacement et l'affectation par déplacement à l'aide de votre propre fonction d'échange, à condition que votre fonction membre d'échange n'appelle ni le constructeur de déplacement ni l'affectation par déplacement. Voici un exemple de réalisation :

#include <iostream>
#include <string>
#include <string_view>

class Name
{
private:
    std::string m_name {};

public:
    Name(std::string_view name) : m_name{ name }
    {
    }

    Name(const Name& name) = delete;
    Name& operator=(const Name& name) = delete;

    // Créer notre propre fonction amie d'échange pour échanger les membres de Name
    friend void swap(Name& a, Name& b) noexcept
    {
        // Nous évitons les appels récursifs en invoquant std::swap sur le membre std::string,
        // et non sur Name
        std::swap(a.m_name, b.m_name);
    }

    Name(Name&& name) noexcept
    {
        std::cout << "Move ctor\n";

        swap(*this, name); // appelle maintenant notre swap, et non std::swap
    }

    Name& operator=(Name&& name) noexcept
    {
        std::cout << "Move assign\n";

        swap(*this, name); // appelle maintenant notre swap, et non std::swap

        return *this;
    }

    const std::string& get() const { return m_name; }
};

int main()
{
    Name n1{ "Alex" };
    n1 = Name{"Joe"}; // invoque l'affectation par déplacement

    std::cout << n1.get() << '\n';

    return 0;
}

Cela fonctionne comme prévu et affiche :


Move assign
Joe
