22.6 — std::shared_ptr

Contrairement à std::unique_ptr, qui est conçu pour posséder et gérer seul une ressource, std::shared_ptr sert à résoudre le cas où plusieurs pointeurs intelligents doivent co-posséder une même ressource.

Il est donc permis d'avoir plusieurs std::shared_ptr pointant vers la même ressource. En interne, std::shared_ptr garde la trace du nombre de std::shared_ptr qui partagent la ressource. Tant qu'au moins un std::shared_ptr pointe vers la ressource, celle-ci n'est pas désallouée, même si certains std::shared_ptr sont détruits. Dès que le dernier std::shared_ptr gérant la ressource sort de portée (ou est réaffecté pour pointer vers autre chose), la ressource est désallouée.

Comme std::unique_ptr, std::shared_ptr se trouve dans l'en-tête <memory>.

#include <iostream>
#include <memory> // for std::shared_ptr

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    // alloue un objet Resource et le confie à un std::shared_ptr
    Resource* res { new Resource };
    std::shared_ptr<Resource> ptr1{ res };
    {
        std::shared_ptr<Resource> ptr2 { ptr1 }; // crée un autre std::shared_ptr pointant vers la même chose

        std::cout << "Killing one shared pointer\n";
    } // ptr2 sort de portée ici, mais rien ne se passe

    std::cout << "Killing another shared pointer\n";

    return 0;
} // ptr1 sort de portée ici, et la Resource allouée est détruite

Ce programme affiche :


Resource acquired
Killing one shared pointer
Killing another shared pointer
Resource destroyed

Dans le code ci-dessus, nous créons un objet Resource dynamique et un std::shared_ptr nommé ptr1 le gère. Dans le bloc imbriqué, nous utilisons le constructeur de copie pour créer un second std::shared_ptr (ptr2) pointant vers la même Resource. Lorsque ptr2 sort de portée, la Resource n'est pas désallouée, car ptr1 pointe toujours vers elle. Lorsque ptr1 sort de portée, ptr1 constate qu'aucun autre std::shared_ptr ne gère la Resource, et il la désalloue.

Notez que nous avons créé le second pointeur partagé à partir du premier. C'est important. Considérez le programme suivant, similaire :

#include <iostream>
#include <memory> // for std::shared_ptr

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    Resource* res { new Resource };
    std::shared_ptr<Resource> ptr1 { res };
    {
        std::shared_ptr<Resource> ptr2 { res }; // crée ptr2 directement à partir de res (et non de ptr1)

        std::cout << "Killing one shared pointer\n";
    } // ptr2 sort de portée ici, et la Resource allouée est détruite

    std::cout << "Killing another shared pointer\n";

    return 0;
} // ptr1 sort de portée ici, et la Resource allouée est de nouveau détruite

Ce programme affiche :


Resource acquired
Killing one shared pointer
Resource destroyed
Killing another shared pointer
Resource destroyed

puis plante (du moins sur la machine de l'auteur).

La différence tient au fait que nous avons créé deux std::shared_ptr indépendamment l'un de l'autre. Par conséquent, bien qu'ils pointent tous deux vers la même Resource, ils ne se connaissent pas. Lorsque ptr2 sort de portée, il pense être le seul propriétaire de la Resource et la désalloue. Lorsque ptr1 sort de portée plus tard, il pense la même chose et tente de supprimer de nouveau la Resource. Des choses fâcheuses se produisent alors.

Heureusement, cela s'évite facilement : si vous avez besoin de plus d'un std::shared_ptr vers une ressource donnée, copiez un std::shared_ptr existant.

Bonne pratique

Copiez toujours un std::shared_ptr existant si vous avez besoin de plusieurs std::shared_ptr pointant vers la même ressource.

Comme std::unique_ptr, std::shared_ptr peut être un pointeur nul ; vérifiez donc sa validité avant de l'utiliser.

std::make_shared

De même que std::make_unique() peut servir à créer un std::unique_ptr en C++14, std::make_shared() peut (et doit) être utilisé pour créer un std::shared_ptr. std::make_shared() est disponible depuis le C++11.

Voici notre exemple initial, utilisant std::make_shared() :

#include <iostream>
#include <memory> // for std::shared_ptr

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    // alloue un objet Resource et le confie à un std::shared_ptr
    auto ptr1 { std::make_shared<Resource>() };
    {
        auto ptr2 { ptr1 }; // crée ptr2 par copie de ptr1

        std::cout << "Killing one shared pointer\n";
    } // ptr2 sort de portée ici, mais rien ne se passe

    std::cout << "Killing another shared pointer\n";

    return 0;
} // ptr1 sort de portée ici, et la Resource allouée est détruite

Les raisons d'utiliser std::make_shared() sont les mêmes que pour std::make_unique() : std::make_shared() est plus simple et plus sûr (cette méthode ne permet pas de créer deux std::shared_ptr indépendants pointant vers la même ressource sans qu'ils se connaissent). Cependant, std::make_shared() est aussi plus performant que son absence d'utilisation. La raison tient à la manière dont std::shared_ptr garde la trace du nombre de pointeurs pointant vers une ressource donnée.

Au cœur de std::shared_ptr

Contrairement à std::unique_ptr, qui utilise en interne un seul pointeur, std::shared_ptr en utilise deux. L'un pointe vers la ressource gérée. L'autre pointe vers un « bloc de contrôle » (control block), un objet alloué dynamiquement qui conserve diverses informations, dont le nombre de std::shared_ptr pointant vers la ressource. Lorsqu'un std::shared_ptr est créé via un constructeur de std::shared_ptr, la mémoire de l'objet géré (généralement passé en argument) et celle du bloc de contrôle (que le constructeur crée) sont allouées séparément. En revanche, avec std::make_shared(), cette opération peut être optimisée en une allocation mémoire unique, ce qui améliore les performances.

Cela explique aussi pourquoi la création indépendante de deux std::shared_ptr pointant vers la même ressource pose problème. Chaque std::shared_ptr possède un pointeur vers la ressource. Cependant, chacun alloue indépendamment son propre bloc de contrôle, qui indique qu'il est le seul pointeur à posséder cette ressource. Ainsi, lorsque ce std::shared_ptr sort de portée, il désalloue la ressource, sans savoir que d'autres std::shared_ptr tentent également de la gérer.

En revanche, lorsqu'un std::shared_ptr est cloné par affectation par copie, les données du bloc de contrôle peuvent être mises à jour pour indiquer qu'il existe désormais des std::shared_ptr supplémentaires co-gérant la ressource.

Les pointeurs partagés peuvent être créés à partir de pointeurs uniques

Un std::unique_ptr peut être converti en std::shared_ptr grâce à un constructeur spécial de std::shared_ptr qui accepte une r-value de std::unique_ptr. Le contenu du std::unique_ptr est alors déplacé vers le std::shared_ptr.

En revanche, un std::shared_ptr ne peut pas être converti en std::unique_ptr de manière sûre. Ainsi, si vous écrivez une fonction devant renvoyer un pointeur intelligent, il vaut mieux renvoyer un std::unique_ptr, quitte à l'affecter à un std::shared_ptr si et quand cela est approprié.

Les dangers de std::shared_ptr

std::shared_ptr présente certains des mêmes problèmes que std::unique_ptr : si le std::shared_ptr n'est pas correctement détruit (soit parce qu'il a été alloué dynamiquement et jamais supprimé, soit parce qu'il faisait partie d'un objet alloué dynamiquement et jamais supprimé), alors la ressource qu'il gère ne sera pas non plus désallouée. Avec std::unique_ptr, vous n'avez à vous soucier que d'un seul pointeur intelligent devant être correctement détruit. Avec std::shared_ptr, vous devez veiller à tous les détruire. Si l'un des std::shared_ptr gérant une ressource n'est pas correctement détruit, la ressource ne sera pas désallouée correctement.

std::shared_ptr et les tableaux

En C++17 et versions antérieures, std::shared_ptr ne prend pas correctement en charge la gestion de tableaux, et ne doit pas être utilisé pour gérer un tableau de style C. À partir du C++20, std::shared_ptr prend en charge les tableaux.

Conclusion

std::shared_ptr est conçu pour le cas où plusieurs pointeurs intelligents doivent co-gérer une même ressource. La ressource est désallouée lorsque le dernier std::shared_ptr qui la gère est détruit.
