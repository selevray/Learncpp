22.7 — Problèmes de dépendances circulaires avec std::shared_ptr, et std::weak_ptr

Dans la leçon précédente, nous avons vu comment std::shared_ptr permet à plusieurs pointeurs intelligents de copropriétaire la même ressource. Cependant, dans certains cas, cela peut poser problème. Considérons l'exemple suivant, où les pointeurs partagés de deux objets distincts pointent chacun vers l'autre objet :

#include <iostream>
#include <memory> // for std::shared_ptr
#include <string>

class Person
{
    std::string m_name;
    std::shared_ptr<Person> m_partner; // initialement créé vide

public:

    Person(const std::string &name): m_name(name)
    {
        std::cout << m_name << " created\n";
    }
    ~Person()
    {
        std::cout << m_name << " destroyed\n";
    }

    friend bool partnerUp(std::shared_ptr<Person> &p1, std::shared_ptr<Person> &p2)
    {
        if (!p1 || !p2)
            return false;

        p1->m_partner = p2;
        p2->m_partner = p1;

        std::cout << p1->m_name << " is now partnered with " << p2->m_name << '\n';

        return true;
    }
};

int main()
{
    auto lucy { std::make_shared<Person>("Lucy") }; // crée une Person nommée "Lucy"
    auto ricky { std::make_shared<Person>("Ricky") }; // crée une Person nommée "Ricky"

    partnerUp(lucy, ricky); // fait pointer "Lucy" vers "Ricky" et inversement

    return 0;
}

Dans l'exemple ci-dessus, nous allouons dynamiquement deux Person, « Lucy » et « Ricky », à l'aide de make_shared() (afin que lucy et ricky soient détruits à la fin de main()). Ensuite, nous les associons en couple. Cela fait pointer le std::shared_ptr contenu dans « Lucy » vers « Ricky », et le std::shared_ptr contenu dans « Ricky » vers « Lucy ». Les pointeurs partagés sont faits pour être partagés : il est donc normal que le pointeur partagé lucy et le membre m_partner de Ricky pointent tous deux vers « Lucy » (et inversement).

Pourtant, ce programme ne s'exécute pas comme prévu :


Lucy created
Ricky created
Lucy is now partnered with Ricky

Et c'est tout. Aucune désallocation n'a eu lieu. Oups. Que s'est-il passé ?

Après l'appel à partnerUp(), deux pointeurs partagés pointent vers « Ricky » (ricky, et m_partner de Lucy) et deux pointeurs partagés pointent vers « Lucy » (lucy, et m_partner de Ricky).

À la fin de main(), le pointeur partagé ricky sort de portée en premier. Lorsque cela se produit, ricky vérifie s'il existe d'autres pointeurs partagés qui copropriétaient la Person « Ricky ». Il en existe un (m_partner de Lucy). Pour cette raison, il ne désalloue pas « Ricky » (si c'était le cas, m_partner de Lucy deviendrait un pointeur pendant). À ce stade, il ne reste qu'un pointeur partagé vers « Ricky » (m_partner de Lucy) et deux pointeurs partagés vers « Lucy » (lucy, et m_partner de Ricky).

Ensuite, le pointeur partagé lucy sort de portée, et la même chose se produit. Le pointeur partagé lucy vérifie s'il existe d'autres pointeurs partagés qui copropriétaient la Person « Lucy ». Il en existe un (m_partner de Ricky), donc « Lucy » n'est pas désallouée. À ce stade, il ne reste qu'un pointeur partagé vers « Lucy » (m_partner de Ricky) et un pointeur partagé vers « Ricky » (m_partner de Lucy).

Puis le programme se termine, et ni la Person « Lucy » ni la Person « Ricky » n'ont été désallouées ! En résumé, « Lucy » empêche « Ricky » d'être détruite, et « Ricky » empêche « Lucy » d'être détruite.

Il s'avère que ce phénomène peut se produire chaque fois que des pointeurs partagés forment une référence circulaire.

Références circulaires

Une référence circulaire (aussi appelée référence cyclique ou cycle) est une suite de références dans laquelle chaque objet référence le suivant, et le dernier objet référence le premier, ce qui crée une boucle de références. Ces références ne doivent pas nécessairement être de véritables références C++ : il peut s'agir de pointeurs, d'identifiants uniques ou de tout autre moyen permettant d'identifier des objets précis.

Dans le contexte des pointeurs partagés, les références seront des pointeurs.

C'est exactement ce que nous observons dans le cas précédent : « Lucy » pointe vers « Ricky », et « Ricky » pointe vers « Lucy ». Avec trois pointeurs, on obtiendrait le même résultat si A pointait vers B, B vers C, et C vers A. L'effet concret d'un cycle de pointeurs partagés est que chaque objet finit par maintenir en vie l'objet suivant, le dernier maintenant en vie le premier. Ainsi, aucun objet de la suite ne peut être désalloué, car chacun pense qu'un autre objet a encore besoin de lui !

Un cas réduit

Il s'avère que ce problème de référence circulaire peut même survenir avec un seul std::shared_ptr : un std::shared_ptr qui référence l'objet qui le contient forme encore un cycle (simplement un cycle réduit). Bien qu'il soit assez peu probable que cela arrive en pratique, nous vous le montrons pour une meilleure compréhension :

#include <iostream>
#include <memory> // for std::shared_ptr

class Resource
{
public:
    std::shared_ptr<Resource> m_ptr {}; // initialement créé vide

    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    auto ptr1 { std::make_shared<Resource>() };

    ptr1->m_ptr = ptr1; // m_ptr partage désormais la Resource qui le contient

    return 0;
}

Dans l'exemple ci-dessus, lorsque ptr1 sort de portée, la Resource n'est pas désallouée, car m_ptr de la Resource partage la Resource. À ce stade, la seule façon de libérer la Resource serait de changer m_ptr pour qu'il pointe vers autre chose (ainsi, plus rien ne partage la Resource). Mais nous ne pouvons pas accéder à m_ptr, car ptr1 est hors de portée : nous n'avons donc plus aucun moyen de le faire. La Resource est devenue une fuite de mémoire.

Ainsi, le programme affiche :


Resource acquired

et c'est tout.

Alors, à quoi sert std::weak_ptr ?

std::weak_ptr a été conçu pour résoudre le problème de « propriété cyclique » décrit ci-dessus. Un std::weak_ptr est un observateur : il peut observer et accéder au même objet qu'un std::shared_ptr (ou d'autres std::weak_ptr), mais il n'est pas considéré comme un propriétaire. Rappelez-vous que lorsqu'un std::shared_ptr sort de portée, il vérifie uniquement si d'autres std::shared_ptr copropriétent l'objet. std::weak_ptr n'est pas pris en compte !

Résolvons le problème de nos Person à l'aide d'un std::weak_ptr :

#include <iostream>
#include <memory> // for std::shared_ptr and std::weak_ptr
#include <string>

class Person
{
    std::string m_name;
    std::weak_ptr<Person> m_partner; // note : il s'agit maintenant d'un std::weak_ptr

public:

    Person(const std::string &name): m_name(name)
    {
        std::cout << m_name << " created\n";
    }
    ~Person()
    {
        std::cout << m_name << " destroyed\n";
    }

    friend bool partnerUp(std::shared_ptr<Person> &p1, std::shared_ptr<Person> &p2)
    {
        if (!p1 || !p2)
            return false;

        p1->m_partner = p2;
        p2->m_partner = p1;

        std::cout << p1->m_name << " is now partnered with " << p2->m_name << '\n';

        return true;
    }
};

int main()
{
    auto lucy { std::make_shared<Person>("Lucy") };
    auto ricky { std::make_shared<Person>("Ricky") };

    partnerUp(lucy, ricky);

    return 0;
}

Ce code se comporte correctement :


Lucy created
Ricky created
Lucy is now partnered with Ricky
Ricky destroyed
Lucy destroyed

Fonctionnellement, il fonctionne presque de la même façon que l'exemple problématique. Cependant, désormais, lorsque ricky sort de portée, il constate qu'aucun autre std::shared_ptr ne pointe vers « Ricky » (le std::weak_ptr de « Lucy » ne compte pas). Il désalloue donc « Ricky ». Il en va de même pour lucy.

Utiliser std::weak_ptr

L'un des inconvénients de std::weak_ptr est qu'on ne peut pas l'utiliser directement (il n'a pas d'operator->). Pour utiliser un std::weak_ptr, vous devez d'abord le convertir en std::shared_ptr. Vous pouvez alors utiliser ce std::shared_ptr. Pour convertir un std::weak_ptr en std::shared_ptr, vous pouvez utiliser la fonction membre lock(). Voici l'exemple précédent, mis à jour pour illustrer cette opération :

#include <iostream>
#include <memory> // for std::shared_ptr and std::weak_ptr
#include <string>

class Person
{
    std::string m_name;
    std::weak_ptr<Person> m_partner; // note : il s'agit maintenant d'un std::weak_ptr

public:

    Person(const std::string &name) : m_name(name)
    {
        std::cout << m_name << " created\n";
    }
    ~Person()
    {
        std::cout << m_name << " destroyed\n";
    }

    friend bool partnerUp(std::shared_ptr<Person> &p1, std::shared_ptr<Person> &p2)
    {
        if (!p1 || !p2)
            return false;

        p1->m_partner = p2;
        p2->m_partner = p1;

        std::cout << p1->m_name << " is now partnered with " << p2->m_name << '\n';

        return true;
    }

    std::shared_ptr<Person> getPartner() const { return m_partner.lock(); } // utilise lock() pour convertir le weak_ptr en shared_ptr
    const std::string& getName() const { return m_name; }
};

int main()
{
    auto lucy { std::make_shared<Person>("Lucy") };
    auto ricky { std::make_shared<Person>("Ricky") };

    partnerUp(lucy, ricky);

    auto partner = ricky->getPartner(); // obtient un shared_ptr vers le partenaire de Ricky
    std::cout << ricky->getName() << "'s partner is: " << partner->getName() << '\n';

    return 0;
}

Ce programme affiche :


Lucy created
Ricky created
Lucy is now partnered with Ricky
Ricky's partner is: Lucy
Ricky destroyed
Lucy destroyed

Nous n'avons pas à nous soucier de dépendances circulaires avec la variable std::shared_ptr « partner », puisqu'il s'agit simplement d'une variable locale à la fonction. Elle sortira de portée à la fin de la fonction, et le compteur de références sera décrémenté de 1.

Éviter les pointeurs pendants avec std::weak_ptr

Considérons le cas où un pointeur « classique » (dumb) contient l'adresse d'un objet, puis que cet objet est détruit. Un tel pointeur est pendant, et le déréférencer entraîne un comportement indéfini. Malheureusement, il n'existe aucun moyen de déterminer si un pointeur contenant une adresse non nulle est pendant ou non. C'est en grande partie pour cette raison que les pointeurs classiques sont dangereux.

Comme std::weak_ptr ne maintient pas en vie la ressource qu'il observe, il peut de même arriver qu'un std::weak_ptr soit laissé pointant vers une ressource désallouée par un std::shared_ptr. Cependant, std::weak_ptr a un atout dans sa manche : comme il a accès au compteur de références d'un objet, il peut déterminer s'il pointe vers un objet valide ou non ! Si le compteur de références est non nul, la ressource est encore valide. S'il vaut zéro, la ressource a été détruite.

La façon la plus simple de tester si un std::weak_ptr est valide consiste à utiliser la fonction membre expired(), qui renvoie true si le std::weak_ptr pointe vers un objet invalide, et false sinon.

Voici un exemple simple illustrant cette différence de comportement :

// Merci au lecteur Waldo pour une première version de cet exemple
#include <iostream>
#include <memory>

class Resource
{
public:
    Resource() { std::cerr << "Resource acquired\n"; }
    ~Resource() { std::cerr << "Resource destroyed\n"; }
};

// Renvoie un std::weak_ptr vers un objet invalide
std::weak_ptr<Resource> getWeakPtr()
{
    auto ptr{ std::make_shared<Resource>() };
    return std::weak_ptr<Resource>{ ptr };
} // ptr sort de portée, Resource détruite

// Renvoie un pointeur classique vers un objet invalide
Resource* getDumbPtr()
{
    auto ptr{ std::make_unique<Resource>() };
    return ptr.get();
} // ptr sort de portée, Resource détruite

int main()
{
    auto dumb{ getDumbPtr() };
    std::cout << "Our dumb ptr is: " << ((dumb == nullptr) ? "nullptr\n" : "non-null\n");

    auto weak{ getWeakPtr() };
    std::cout << "Our weak ptr is: " << ((weak.expired()) ? "expired\n" : "valid\n");

    return 0;
}

Ce programme affiche :


Resource acquired
Resource destroyed
Our dumb ptr is: non-null
Resource acquired
Resource destroyed
Our weak ptr is: expired

getDumbPtr() et getWeakPtr() utilisent tous deux un pointeur intelligent pour allouer une Resource : ce pointeur intelligent garantit que la Resource allouée sera détruite à la fin de la fonction. Lorsque getDumbPtr() renvoie un Resource*, il renvoie un pointeur pendant (car std::unique_ptr a détruit la Resource à la fin de la fonction). Lorsque getWeakPtr() renvoie un std::weak_ptr, celui-ci pointe de même vers un objet invalide (car std::shared_ptr a détruit la Resource à la fin de la fonction).

Dans main(), nous testons d'abord si le pointeur classique renvoyé est nullptr. Comme ce pointeur contient toujours l'adresse de la ressource désallouée, ce test échoue. Il n'existe aucun moyen pour main() de savoir si ce pointeur est pendant ou non. Dans le cas présent, comme il s'agit d'un pointeur pendant, si nous le déréférencions, cela entraînerait un comportement indéfini.

Ensuite, nous testons si weak.expired() vaut true. Comme le compteur de références de l'objet pointé par weak vaut 0 (puisque l'objet pointé a déjà été détruit), l'expression vaut true. Le code de main() peut donc détecter que weak pointe vers un objet invalide, et nous pouvons adapter notre code en conséquence !

Notez que si un std::weak_ptr est expiré, nous ne devons pas appeler lock() dessus, car l'objet pointé a déjà été détruit et il n'y a donc plus d'objet à partager. Si vous appelez lock() sur un std::weak_ptr expiré, il renverra un std::shared_ptr vers nullptr.

Conclusion

std::shared_ptr peut être utilisé lorsque vous avez besoin de plusieurs pointeurs intelligents capables de copropriétaire une ressource. La ressource sera désallouée lorsque le dernier std::shared_ptr sortira de portée. std::weak_ptr peut être utilisé lorsque vous voulez un pointeur intelligent qui peut voir et utiliser une ressource partagée, mais qui ne participe pas à la propriété de cette ressource.
