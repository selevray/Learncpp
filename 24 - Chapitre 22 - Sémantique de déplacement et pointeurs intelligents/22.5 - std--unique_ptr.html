22.5 — std::unique_ptr

Au début du chapitre, nous avons vu que l'utilisation de pointeurs peut provoquer des bugs et des fuites mémoire dans certaines situations. Par exemple, cela peut se produire lorsqu'une fonction retourne prématurément, ou lève une exception, et que le pointeur n'est pas correctement supprimé.

#include <iostream>

void someFunction()
{
    auto* ptr{ new Resource() };

    int x{};
    std::cout << "Enter an integer: ";
    std::cin >> x;

    if (x == 0)
        throw 0; // the function returns early, and ptr won’t be deleted!

    // do stuff with ptr here

    delete ptr;
}

Maintenant que nous avons couvert les bases de la sémantique de déplacement, nous pouvons revenir au sujet des classes de pointeurs intelligents (smart pointers). Bien que les pointeurs intelligents puissent offrir d'autres fonctionnalités, la caractéristique qui les définit est qu'ils gèrent une ressource allouée dynamiquement fournie par l'utilisateur du pointeur intelligent, et qu'ils garantissent que l'objet alloué dynamiquement est correctement libéré au moment approprié (généralement lorsque le pointeur intelligent sort de sa portée).

Pour cette raison, les pointeurs intelligents ne doivent jamais être eux-mêmes alloués dynamiquement (sinon, le pointeur intelligent risque de ne pas être correctement désalloué, ce qui signifie que l'objet qu'il possède ne serait pas désalloué, provoquant une fuite mémoire). En allouant toujours les pointeurs intelligents sur la pile (en tant que variables locales ou membres de composition d'une classe), nous sommes certains que le pointeur intelligent sortira correctement de sa portée lorsque la fonction ou l'objet qui le contient se termine, garantissant ainsi que l'objet possédé par le pointeur intelligent est correctement désalloué.

La bibliothèque standard de C++11 fournit 4 classes de pointeurs intelligents : std::auto_ptr (supprimée en C++17), std::unique_ptr, std::shared_ptr et std::weak_ptr. std::unique_ptr est de loin la classe de pointeur intelligent la plus utilisée, nous commencerons donc par elle. Dans les leçons suivantes, nous aborderons std::shared_ptr et std::weak_ptr.

std::unique_ptr

std::unique_ptr est le remplaçant de std::auto_ptr introduit en C++11. Il doit être utilisé pour gérer tout objet alloué dynamiquement qui n'est pas partagé par plusieurs objets. Autrement dit, std::unique_ptr doit posséder entièrement l'objet qu'il gère, sans partager cette possession avec d'autres classes. std::unique_ptr se trouve dans l'en-tête <memory>.

Examinons un exemple simple de pointeur intelligent :

#include <iostream>
#include <memory> // for std::unique_ptr

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    // allocate a Resource object and have it owned by std::unique_ptr
    std::unique_ptr<Resource> res{ new Resource() };

    return 0;
} // res goes out of scope here, and the allocated Resource is destroyed

Comme le std::unique_ptr est alloué sur la pile ici, il est garanti qu'il finira par sortir de sa portée et, lorsqu'il le fera, il supprimera la ressource Resource qu'il gère.

Contrairement à std::auto_ptr, std::unique_ptr implémente correctement la sémantique de déplacement.

#include <iostream>
#include <memory> // for std::unique_ptr
#include <utility> // for std::move

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
    std::unique_ptr<Resource> res1{ new Resource{} }; // Resource created here
    std::unique_ptr<Resource> res2{}; // Start as nullptr

    std::cout << "res1 is " << (res1 ? "not null\n" : "null\n");
    std::cout << "res2 is " << (res2 ? "not null\n" : "null\n");

    // res2 = res1; // Won't compile: copy assignment is disabled
    res2 = std::move(res1); // res2 assumes ownership, res1 is set to null

    std::cout << "Ownership transferred\n";

    std::cout << "res1 is " << (res1 ? "not null\n" : "null\n");
    std::cout << "res2 is " << (res2 ? "not null\n" : "null\n");

    return 0;
} // Resource destroyed here when res2 goes out of scope

Ce programme affiche :


Resource acquired
res1 is not null
res2 is null
Ownership transferred
res1 is null
res2 is not null
Resource destroyed

Comme std::unique_ptr est conçu en tenant compte de la sémantique de déplacement, l'initialisation par copie et l'affectation par copie sont désactivées. Si vous voulez transférer le contenu géré par std::unique_ptr, vous devez utiliser la sémantique de déplacement. Dans le programme ci-dessus, nous y parvenons grâce à std::move (qui convertit res1 en valeur r, ce qui déclenche une affectation par déplacement au lieu d'une affectation par copie).

Accéder à l'objet géré

std::unique_ptr possède des opérateurs operator* et operator-> surchargés qui permettent de retourner la ressource gérée. L'opérateur operator* retourne une référence à la ressource gérée, et l'opérateur operator-> retourne un pointeur.

Rappelez-vous que std::unique_ptr peut ne pas toujours gérer un objet, soit parce qu'il a été créé vide (en utilisant le constructeur par défaut ou en passant nullptr en paramètre), soit parce que la ressource qu'il gérait a été déplacée vers un autre std::unique_ptr. Il faut donc vérifier, avant d'utiliser l'un de ces opérateurs, que le std::unique_ptr possède bien une ressource. Heureusement, c'est facile : std::unique_ptr dispose d'une conversion vers bool qui retourne true si le std::unique_ptr gère une ressource.

Voici un exemple :

#include <iostream>
#include <memory> // for std::unique_ptr

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

std::ostream& operator<<(std::ostream& out, const Resource&)
{
    out << "I am a resource";
    return out;
}

int main()
{
    std::unique_ptr<Resource> res{ new Resource{} };

    if (res) // use implicit cast to bool to ensure res contains a Resource
        std::cout << *res << '\n'; // print the Resource that res is owning

    return 0;
}

Ce programme affiche :


Resource acquired
I am a resource
Resource destroyed

Dans le programme ci-dessus, nous utilisons l'opérateur operator* surchargé pour obtenir l'objet Resource possédé par le std::unique_ptr res, que nous envoyons ensuite à std::cout pour l'afficher.

std::unique_ptr et les tableaux

Contrairement à std::auto_ptr, std::unique_ptr est suffisamment intelligent pour savoir s'il doit utiliser delete scalaire ou delete de tableau. On peut donc utiliser std::unique_ptr aussi bien avec des objets scalaires qu'avec des tableaux.

Cependant, std::array, std::vector (ou std::string) sont presque toujours de meilleurs choix que std::unique_ptr avec un tableau de taille fixe, un tableau dynamique ou une chaîne de style C.

Bonne pratique

Privilégiez std::array, std::vector ou std::string plutôt qu'un pointeur intelligent gérant un tableau de taille fixe, un tableau dynamique ou une chaîne de style C.

std::make_unique

C++14 apporte une fonction supplémentaire nommée std::make_unique(). Cette fonction template construit un objet du type template et l'initialise avec les arguments passés à la fonction.

#include <memory> // for std::unique_ptr and std::make_unique
#include <iostream>

class Fraction
{
private:
    int m_numerator{ 0 };
    int m_denominator{ 1 };

public:
    Fraction(int numerator = 0, int denominator = 1) :
        m_numerator{ numerator }, m_denominator{ denominator }
    {
    }

    friend std::ostream& operator<<(std::ostream& out, const Fraction &f1)
    {
        out << f1.m_numerator << '/' << f1.m_denominator;
        return out;
    }
};


int main()
{
    // Create a single dynamically allocated Fraction with numerator 3 and denominator 5
    // We can also use automatic type deduction to good effect here
    auto f1{ std::make_unique<Fraction>(3, 5) };
    std::cout << *f1 << '\n';

    // Create a dynamically allocated array of Fractions of length 4
    auto f2{ std::make_unique<Fraction[]>(4) };
    std::cout << f2[0] << '\n';

    return 0;
}

Le code ci-dessus affiche :


3/5
0/1

L'utilisation de std::make_unique() est facultative, mais elle est recommandée plutôt que de créer soi-même un std::unique_ptr. En effet, le code utilisant std::make_unique est plus simple et demande moins de saisie (lorsqu'il est combiné à la déduction automatique de type). De plus, en C++14, elle résout un problème de sécurité face aux exceptions qui découle du fait que C++ laisse non spécifié l'ordre d'évaluation des arguments d'une fonction.

Bonne pratique

Utilisez std::make_unique() au lieu de créer un std::unique_ptr et d'utiliser new vous-même.

Le problème de sécurité face aux exceptions en détail

Pour ceux qui se demandent ce qu'est le « problème de sécurité face aux exceptions » mentionné plus haut, voici une description de ce problème.

Considérons une expression de ce type :

some_function(std::unique_ptr<T>(new T), function_that_can_throw_exception());

Le compilateur dispose d'une grande liberté quant à la manière de traiter cet appel. Il pourrait créer un nouveau T, puis appeler function_that_can_throw_exception(), puis créer le std::unique_ptr qui gère le T alloué dynamiquement. Si function_that_can_throw_exception() lève une exception, le T alloué ne sera pas désalloué, car le pointeur intelligent chargé de la désallocation n'a pas encore été créé. Cela conduit à une fuite du T.

std::make_unique() n'est pas concerné par ce problème, car la création de l'objet T et celle du std::unique_ptr ont lieu à l'intérieur de la fonction std::make_unique(), où l'ordre d'exécution ne prête à aucune ambiguïté.

Ce problème a été corrigé en C++17, l'évaluation des arguments de fonction ne pouvant plus être entrelacée.

Retourner un std::unique_ptr depuis une fonction

std::unique_ptr peut être retourné en toute sécurité par valeur depuis une fonction :

#include <memory> // for std::unique_ptr

std::unique_ptr<Resource> createResource()
{
     return std::make_unique<Resource>();
}

int main()
{
    auto ptr{ createResource() };

    // do whatever

    return 0;
}

Dans le code ci-dessus, createResource() retourne un std::unique_ptr par valeur. Si cette valeur n'est affectée à rien, la valeur de retour temporaire sort de sa portée et la ressource Resource est nettoyée. Si elle est affectée (comme dans main()), en C++14 ou antérieur, la sémantique de déplacement est utilisée pour transférer la ressource Resource de la valeur de retour vers l'objet auquel elle est affectée (dans l'exemple ci-dessus, ptr), et en C++17 ou ultérieur, le retour est élidé. Retourner une ressource par std::unique_ptr est donc bien plus sûr que de retourner des pointeurs bruts !

En général, vous ne devez jamais retourner un std::unique_ptr par pointeur (jamais) ni par référence (sauf raison particulière impérieuse).

Passer un std::unique_ptr à une fonction

Si vous voulez que la fonction prenne possession du contenu du pointeur, passez le std::unique_ptr par valeur. Notez que, la copie étant désactivée, vous devrez utiliser std::move pour passer effectivement la variable.

#include <iostream>
#include <memory> // for std::unique_ptr
#include <utility> // for std::move

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

std::ostream& operator<<(std::ostream& out, const Resource&)
{
    out << "I am a resource";
    return out;
}

// This function takes ownership of the Resource, which isn't what we want
void takeOwnership(std::unique_ptr<Resource> res)
{
     if (res)
          std::cout << *res << '\n';
} // the Resource is destroyed here

int main()
{
    auto ptr{ std::make_unique<Resource>() };

//    takeOwnership(ptr); // This doesn't work, need to use move semantics
    takeOwnership(std::move(ptr)); // ok: use move semantics

    std::cout << "Ending program\n";

    return 0;
}

Le programme ci-dessus affiche :


Resource acquired
I am a resource
Resource destroyed
Ending program

Notez que, dans ce cas, la possession de la ressource Resource a été transférée à takeOwnership(), de sorte que la ressource a été détruite à la fin de takeOwnership() plutôt qu'à la fin de main().

Cependant, la plupart du temps, vous ne voudrez pas que la fonction prenne possession de la ressource.

Bien que vous puissiez passer un std::unique_ptr par référence constante (ce qui permet à la fonction d'utiliser l'objet sans en prendre la possession), il est préférable de passer la ressource elle-même (par pointeur ou par référence, selon que la valeur nulle est un argument valide ou non). Cela permet à la fonction de rester indépendante de la manière dont l'appelant gère ses ressources.

Pour obtenir un pointeur brut à partir d'un std::unique_ptr, vous pouvez utiliser la fonction membre get() :

#include <memory> // for std::unique_ptr
#include <iostream>

class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

std::ostream& operator<<(std::ostream& out, const Resource&)
{
    out << "I am a resource";
    return out;
}

// The function only uses the resource, so we'll accept a pointer to the resource, not a reference to the whole std::unique_ptr<Resource>
void useResource(const Resource* res)
{
    if (res)
        std::cout << *res << '\n';
    else
        std::cout << "No resource\n";
}

int main()
{
    auto ptr{ std::make_unique<Resource>() };

    useResource(ptr.get()); // note: get() used here to get a pointer to the Resource

    std::cout << "Ending program\n";

    return 0;
} // The Resource is destroyed here

Le programme ci-dessus affiche :


Resource acquired
I am a resource
Ending program
Resource destroyed

std::unique_ptr et les classes

Vous pouvez bien sûr utiliser std::unique_ptr comme membre de composition de votre classe. Ainsi, vous n'avez pas à vous soucier de faire en sorte que le destructeur de votre classe supprime la mémoire dynamique, car le std::unique_ptr sera automatiquement détruit lorsque l'objet de la classe sera détruit.

Toutefois, si l'objet de la classe n'est pas correctement détruit (par exemple s'il a été alloué dynamiquement et n'a pas été correctement désalloué), alors le membre std::unique_ptr ne sera pas détruit non plus, et l'objet géré par ce std::unique_ptr ne sera pas désalloué.

Mauvaise utilisation de std::unique_ptr

Il existe deux façons simples d'utiliser incorrectement les std::unique_ptr, toutes deux faciles à éviter. Premièrement, ne laissez jamais plusieurs objets gérer la même ressource. Par exemple :

Resource* res{ new Resource() };
std::unique_ptr<Resource> res1{ res };
std::unique_ptr<Resource> res2{ res };

Bien que ce code soit syntaxiquement valide, le résultat final est que res1 et res2 essaieront tous deux de supprimer la ressource Resource, ce qui conduit à un comportement indéfini.

Deuxièmement, ne supprimez pas manuellement la ressource en dessous du std::unique_ptr.

Resource* res{ new Resource() };
std::unique_ptr<Resource> res1{ res };
delete res;

Si vous le faites, le std::unique_ptr essaiera de supprimer une ressource déjà supprimée, ce qui conduit là encore à un comportement indéfini.

Notez que std::make_unique() empêche l'un et l'autre de ces cas de se produire par inadvertance.

Solution 
#include <memory> // for std::unique_ptr
#include <iostream>

class Fraction
{
private:
    int m_numerator{ 0 };
    int m_denominator{ 1 };

public:
    Fraction(int numerator = 0, int denominator = 1) :
        m_numerator{ numerator }, m_denominator{ denominator }
    {
    }

    friend std::ostream& operator<<(std::ostream& out, const Fraction &f1)
    {
        out << f1.m_numerator << '/' << f1.m_denominator;
        return out;
    }
};

// This function uses a Fraction object, so we just pass the Fraction itself
// That way we don't have to worry about what kind of smart pointer (if any) the caller may be using
void printFraction(const Fraction* ptr)
{
    if (ptr)
        std::cout << *ptr << '\n';
    else
        std::cout << "No fraction\n";
}

int main()
{
    auto ptr{ std::make_unique<Fraction>(3, 5) };

    printFraction(ptr.get());

    return 0;
}
