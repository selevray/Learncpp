F.2 — Fonctions constexpr (partie 2)

Appels de fonctions constexpr dans des expressions constantes non requises

On pourrait penser qu'une fonction constexpr sera évaluée à la compilation chaque fois que c'est possible, mais malheureusement ce n'est pas le cas.

Dans la leçon 5.5 -- Expressions constantes, nous avons indiqué que, dans les contextes où une expression constante n'est pas requise, le compilateur peut choisir d'évaluer une expression constante à la compilation ou à l'exécution. Par conséquent, tout appel de fonction constexpr faisant partie d'une expression constante non requise peut être évalué à la compilation ou à l'exécution.

Par exemple :

#include <iostream>

constexpr int getValue(int x)
{
    return x;
}

int main()
{
    int x { getValue(5) }; // peut être évalué à l'exécution ou à la compilation

    return 0;
}

Dans l'exemple ci-dessus, comme getValue() est constexpr, l'appel getValue(5) est une expression constante. Cependant, comme la variable x n'est pas constexpr, son initialiseur n'a pas besoin d'être une expression constante. Ainsi, même si nous avons fourni un initialiseur constant, le compilateur est libre de choisir si getValue(5) est évalué à l'exécution ou à la compilation.

Point clé

L'évaluation à la compilation des fonctions constexpr n'est garantie que lorsqu'une expression constante est requise.

Diagnostic des fonctions constexpr dans des expressions constantes requises

Le compilateur n'est pas tenu de déterminer si une fonction constexpr peut être évaluée à la compilation tant qu'elle n'est pas effectivement évaluée à la compilation. Il est assez facile d'écrire une fonction constexpr qui compile correctement pour une utilisation à l'exécution, mais qui échoue à la compilation lorsqu'elle est évaluée à la compilation.

Voici un exemple absurde de ce cas :

#include <iostream>

int getValue(int x)
{
    return x;
}

// Cette fonction peut être évaluée à l'exécution
// Lorsqu'elle est évaluée à la compilation, la fonction produira une erreur de compilation
// car l'appel à getValue(x) ne peut pas être résolu à la compilation
constexpr int foo(int x)
{
    if (x < 0) return 0; // nécessaire avant l'adoption de P2448R1 en C++23 (voir la note ci-dessous)
    return getValue(x);  // appel à une fonction non constexpr ici
}

int main()
{
    int x { foo(5) };           // correct : sera évalué à l'exécution
    constexpr int y { foo(5) }; // erreur de compilation : foo(5) ne peut pas être évalué à la compilation

    return 0;
}

Dans l'exemple ci-dessus, lorsque foo(5) est utilisé comme initialiseur de la variable non constexpr x, il sera évalué à l'exécution. Cela fonctionne très bien et renvoie la valeur 5.

En revanche, lorsque foo(5) est utilisé comme initialiseur de la variable constexpr y, il doit être évalué à la compilation. À ce moment, le compilateur déterminera que l'appel à foo(5) ne peut pas être évalué à la compilation, car getValue() n'est pas une fonction constexpr.

Par conséquent, lorsque vous écrivez une fonction constexpr, vérifiez toujours explicitement qu'elle compile lorsqu'elle est évaluée à la compilation (en l'appelant dans un contexte où une expression constante est requise, par exemple dans l'initialisation d'une variable constexpr).

Bonne pratique

Toutes les fonctions constexpr devraient pouvoir être évaluées à la compilation, car elles devront le faire dans les contextes qui requièrent une expression constante.

Testez toujours vos fonctions constexpr dans un contexte qui requiert une expression constante, car une fonction constexpr peut fonctionner lorsqu'elle est évaluée à l'exécution mais échouer lorsqu'elle est évaluée à la compilation.

Pour les lecteurs avancés

Avant C++23, si aucune valeur d'argument ne permettait à une fonction constexpr d'être évaluée à la compilation, le programme était mal formé (aucun diagnostic requis). Sans la ligne if (x < 0) return 0, l'exemple ci-dessus ne contiendrait aucun ensemble d'arguments permettant l'évaluation à la compilation de la fonction, rendant le programme mal formé. Comme aucun diagnostic n'est requis, le compilateur peut ne pas appliquer cette règle.

Cette exigence a été abrogée en C++23 (P2448R1).

Les paramètres des fonctions constexpr/consteval ne sont pas constexpr

Les paramètres d'une fonction constexpr ne sont pas implicitement constexpr, et ils ne peuvent pas non plus être déclarés constexpr.

Point clé

Un paramètre constexpr impliquerait que la fonction ne puisse être appelée qu'avec un argument constexpr. Or ce n'est pas le cas : les fonctions constexpr peuvent être appelées avec des arguments non constexpr lorsqu'elles sont évaluées à l'exécution.

Comme ces paramètres ne sont pas constexpr, ils ne peuvent pas être utilisés dans des expressions constantes à l'intérieur de la fonction.

consteval int goo(int c)    // c n'est pas constexpr et ne peut pas être utilisé dans des expressions constantes
{
    return c;
}

constexpr int foo(int b)    // b n'est pas constexpr et ne peut pas être utilisé dans des expressions constantes
{
    constexpr int b2 { b }; // erreur de compilation : une variable constexpr exige un initialiseur constant

    return goo(b);          // erreur de compilation : l'appel à une fonction consteval exige un argument constant
}

int main()
{
    constexpr int a { 5 };

    std::cout << foo(a); // correct : l'expression constante a peut être utilisée comme argument de la fonction constexpr foo()

    return 0;
}

Dans l'exemple ci-dessus, le paramètre de fonction b n'est pas constexpr (même si l'argument a est une expression constante). Cela signifie que b ne peut pas être utilisé partout où une expression constante est requise, comme dans l'initialiseur d'une variable constexpr (par exemple b2) ou dans un appel à une fonction consteval (goo(b)).

Les paramètres des fonctions constexpr peuvent être déclarés const, auquel cas ils sont traités comme des constantes d'exécution.

Contenu connexe

Si vous avez besoin de paramètres qui sont des expressions constantes, consultez la leçon 11.9 -- Paramètres non-type de modèles.

Les fonctions constexpr sont implicitement inline

Lorsqu'une fonction constexpr est évaluée à la compilation, le compilateur doit pouvoir voir la définition complète de la fonction constexpr avant ces appels (afin de pouvoir effectuer lui-même l'évaluation). Une déclaration anticipée ne suffit pas dans ce cas, même si la définition réelle de la fonction apparaît plus loin dans la même unité de compilation.

Cela signifie qu'une fonction constexpr appelée dans plusieurs fichiers doit voir sa définition incluse dans chaque unité de traduction, ce qui violerait normalement la règle de définition unique (ODR). Pour éviter ces problèmes, les fonctions constexpr sont implicitement inline, ce qui les exempte de la règle de définition unique.

Par conséquent, les fonctions constexpr sont souvent définies dans des fichiers d'en-tête, afin de pouvoir être incluses avec #include dans tout fichier .cpp qui a besoin de la définition complète.

Règle

Le compilateur doit pouvoir voir la définition complète d'une fonction constexpr (ou consteval), et non seulement une déclaration anticipée.

Bonne pratique

Les fonctions constexpr/consteval utilisées dans un seul fichier source (.cpp) doivent être définies dans ce fichier source, au-dessus de l'endroit où elles sont utilisées.

Les fonctions constexpr/consteval utilisées dans plusieurs fichiers source doivent être définies dans un fichier d'en-tête afin de pouvoir être incluses dans chaque fichier source.

Pour les appels de fonctions constexpr qui ne sont évalués qu'à l'exécution, une déclaration anticipée suffit à satisfaire le compilateur. Cela signifie que vous pouvez utiliser une déclaration anticipée pour appeler une fonction constexpr définie dans une autre unité de traduction, mais uniquement si vous l'invoquez dans un contexte qui n'exige pas d'évaluation à la compilation.

Pour les lecteurs avancés

Selon CWG2166, l'exigence réelle concernant la déclaration anticipée des fonctions constexpr évaluées à la compilation est que « la fonction constexpr doit être définie avant l'évaluation la plus externe qui aboutit finalement à son invocation ». Par conséquent, ceci est autorisé :

#include <iostream>

constexpr int foo(int);

constexpr int goo(int c)
{
    return foo(c);   // notez que foo n'est pas encore définie
}

constexpr int foo(int b) // correct car foo est toujours définie avant tout appel à goo
{
    return b;
}

int main()
{
     constexpr int a{ goo(5) }; // il s'agit de l'invocation la plus externe

    return 0;
}

L'intention ici est de permettre des fonctions constexpr mutuellement récursives (où deux fonctions constexpr s'appellent l'une l'autre), ce qui ne serait pas possible autrement.

Récapitulatif

Marquer une fonction comme constexpr signifie qu'elle peut être utilisée dans une expression constante. Cela ne signifie pas « sera évaluée à la compilation ».

Une expression constante (qui peut contenir des appels de fonctions constexpr) n'est tenue d'être évaluée à la compilation que dans les contextes où une expression constante est requise.

Dans les contextes qui ne requièrent pas d'expression constante, le compilateur peut choisir d'évaluer une expression constante (qui peut contenir des appels de fonctions constexpr) à la compilation ou à l'exécution.

Une expression d'exécution (non constante), qui peut contenir des appels de fonctions constexpr ou non constexpr, sera évaluée à l'exécution.

Un autre exemple

Examinons un autre exemple pour explorer plus en détail à quel moment une fonction constexpr sera, ou est susceptible d'être, évaluée :

#include <iostream>

constexpr int greater(int x, int y)
{
    return (x > y ? x : y);
}

int main()
{
    constexpr int g { greater(5, 6) };              // cas 1 : toujours évalué à la compilation
    std::cout << g << " est le plus grand !\n";

    std::cout << greater(5, 6) << " est le plus grand !\n"; // cas 2 : peut être évalué à l'exécution ou à la compilation

    int x{ 5 }; // non constexpr mais la valeur est connue à la compilation
    std::cout << greater(x, 6) << " est le plus grand !\n"; // cas 3 : probablement évalué à l'exécution

    std::cin >> x;
    std::cout << greater(x, 6) << " est le plus grand !\n"; // cas 4 : toujours évalué à l'exécution

    return 0;
}

Dans le cas 1, nous appelons greater() dans un contexte qui requiert une expression constante. Ainsi, greater() doit être évaluée à la compilation.

Dans le cas 2, la fonction greater() est appelée dans un contexte qui ne requiert pas d'expression constante, puisque les instructions d'affichage doivent être exécutées à l'exécution. Cependant, comme les arguments sont des expressions constantes, la fonction est éligible à une évaluation à la compilation. Le compilateur est donc libre de choisir si cet appel à greater() sera évalué à la compilation ou à l'exécution.

Dans le cas 3, nous appelons greater() avec un argument qui n'est pas une expression constante. Cet appel s'exécutera donc généralement à l'exécution.

Toutefois, la valeur de cet argument est connue à la compilation. En vertu de la règle as-if, le compilateur pourrait décider de traiter l'évaluation de x comme une expression constante, et d'évaluer cet appel à greater() à la compilation. Mais il est plus probable qu'il l'évalue à l'exécution.

Contenu connexe

Nous abordons la règle as-if dans la leçon 5.5 -- Expressions constantes.

Notez que même des fonctions non constexpr pourraient être évaluées à la compilation en vertu de la règle as-if !

Dans le cas 4, la valeur de l'argument x ne peut pas être connue à la compilation, donc cet appel à greater() sera toujours évalué à l'exécution.

Point clé

Autrement dit, on peut classer la probabilité qu'une fonction soit effectivement évaluée à la compilation de la manière suivante :

Toujours (exigé par la norme) :

  • Une fonction constexpr est appelée là où une expression constante est requise.
  • Une fonction constexpr est appelée depuis une autre fonction évaluée à la compilation.

Probablement (il y a peu de raisons de ne pas le faire) :

  • Une fonction constexpr est appelée là où une expression constante n'est pas requise, et tous ses arguments sont des expressions constantes.

Éventuellement (si optimisé en vertu de la règle as-if) :

  • Une fonction constexpr est appelée là où une expression constante n'est pas requise, certains arguments ne sont pas des expressions constantes mais leurs valeurs sont connues à la compilation.
  • Une fonction non constexpr capable d'être évaluée à la compilation, dont tous les arguments sont des expressions constantes.

Jamais (impossible) :

  • Une fonction constexpr est appelée là où une expression constante n'est pas requise, et certains arguments ont des valeurs qui ne sont pas connues à la compilation.

Notez que le niveau d'optimisation de votre compilateur peut influer sur sa décision d'évaluer une fonction à la compilation ou à l'exécution. Cela signifie également que votre compilateur peut faire des choix différents pour les compilations de débogage et de publication (les compilations de débogage désactivant généralement les optimisations).

Par exemple, gcc comme Clang n'évalueront pas à la compilation une fonction constexpr appelée là où une expression constante n'est pas requise, sauf si vous demandez au compilateur d'optimiser le code (par exemple avec l'option -O2).

Pour les lecteurs avancés

Le compilateur peut également choisir d'intégrer (inliner) un appel de fonction, voire de supprimer entièrement un appel de fonction par optimisation. Ces deux mécanismes peuvent affecter le moment (ou même la possibilité) où le contenu de l'appel est évalué.
