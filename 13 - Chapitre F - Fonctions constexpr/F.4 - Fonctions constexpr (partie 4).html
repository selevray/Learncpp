F.4 — Fonctions constexpr (partie 4)

Les fonctions constexpr/consteval peuvent utiliser des variables locales non const

Au sein d'une fonction constexpr ou consteval, nous pouvons utiliser des variables locales qui ne sont pas constexpr, et la valeur de ces variables peut être modifiée.

Voici un exemple simpliste :

#include <iostream>

consteval int doSomething(int x, int y) // la fonction est consteval
{
    x = x + 2;       // nous pouvons modifier la valeur des paramètres de fonction non const

    int z { x + y }; // nous pouvons instancier des variables locales non const
    if (x > y)
        z = z - 1;   // et ensuite modifier leurs valeurs

    return z;
}

int main()
{
    constexpr int g { doSomething(5, 6) };
    std::cout << g << '\n';

    return 0;
}

Lorsque de telles fonctions sont évaluées à la compilation, le compilateur « exécute » essentiellement la fonction et renvoie la valeur calculée.

Les fonctions constexpr/consteval peuvent utiliser des paramètres de fonction et des variables locales comme arguments dans un appel de fonction constexpr

Plus haut, nous avons noté : « Lorsqu'une fonction constexpr (ou consteval) est évaluée à la compilation, toutes les autres fonctions qu'elle appelle doivent également être évaluées à la compilation. »

Peut-être de façon surprenante, une fonction constexpr ou consteval peut utiliser ses paramètres de fonction (qui ne sont pas constexpr), voire des variables locales (qui peuvent ne pas être du tout const), comme arguments dans un appel de fonction constexpr. Lorsqu'une fonction constexpr ou consteval est évaluée à la compilation, la valeur de tous les paramètres de fonction et de toutes les variables locales doit être connue du compilateur (sinon il ne pourrait pas les évaluer à la compilation). Par conséquent, dans ce contexte précis, C++ autorise l'utilisation de ces valeurs comme arguments d'un appel à une fonction constexpr, et cet appel peut tout de même être évalué à la compilation.

#include <iostream>

constexpr int goo(int c) // goo() est maintenant constexpr
{
    return c;
}

constexpr int foo(int b) // b n'est pas une expression constante dans foo()
{
    return goo(b);       // si foo() est résolue à la compilation, alors `goo(b)` peut aussi l'être
}

int main()
{
    std::cout << foo(5);

    return 0;
}

Dans l'exemple ci-dessus, foo(5) peut ou non être évaluée à la compilation. Si c'est le cas, le compilateur sait que b vaut 5. Et même si b n'est pas constexpr, le compilateur peut traiter l'appel goo(b) comme s'il s'agissait de goo(5) et évaluer cet appel de fonction à la compilation. Si foo(5) est au contraire résolue à l'exécution, alors goo(b) le sera aussi.

Une fonction constexpr peut-elle appeler une fonction non constexpr ?

La réponse est oui, mais uniquement lorsque la fonction constexpr est évaluée dans un contexte non constant. Une fonction non constexpr ne peut pas être appelée lorsqu'une fonction constexpr est évaluée dans un contexte constant (car la fonction constexpr ne pourrait alors pas produire une valeur constante à la compilation), et un tel appel produira une erreur de compilation.

L'appel à une fonction non constexpr est autorisé afin qu'une fonction constexpr puisse faire quelque chose comme ceci :

#include <type_traits> // pour std::is_constant_evaluated

constexpr int someFunction()
{
    if (std::is_constant_evaluated()) // si l'évaluation se fait dans un contexte constant
        return someConstexprFcn();
    else
        return someNonConstexprFcn();
}

Considérons maintenant cette variante :

constexpr int someFunction(bool b)
{
    if (b)
        return someConstexprFcn();
    else
        return someNonConstexprFcn();
}

Ceci est légal tant que someFunction(false) n'est jamais appelée dans une expression constante.

En aparté…

Avant C++23, la norme C++ indiquait qu'une fonction constexpr doit renvoyer une valeur constexpr pour au moins un jeu d'arguments, sans quoi elle était techniquement mal formée. Appeler inconditionnellement une fonction non constexpr dans une fonction constexpr rend la fonction constexpr mal formée. Cependant, les compilateurs ne sont pas tenus de générer des erreurs ou des avertissements dans ces cas : le compilateur ne se plaindra donc probablement pas, sauf si vous essayez d'appeler une telle fonction constexpr dans un contexte constant. En C++23, cette exigence a été supprimée.

Pour de meilleurs résultats, nous vous conseillons ce qui suit :

  1. Évitez, si possible, d'appeler des fonctions non constexpr depuis une fonction constexpr.
  2. Si votre fonction constexpr a besoin d'un comportement différent selon les contextes constant et non constant, conditionnez ce comportement avec if (std::is_constant_evaluated()) (en C++20) ou if consteval (à partir de C++23).
  3. Testez toujours vos fonctions constexpr dans un contexte constant, car elles peuvent fonctionner lorsqu'elles sont appelées dans un contexte non constant mais échouer dans un contexte constant.

Quand faut-il rendre une fonction constexpr ?

De manière générale, si une fonction peut être évaluée dans le cadre d'une expression constante requise, elle doit être rendue constexpr.

Une fonction pure (pure function) est une fonction qui satisfait les critères suivants :

  • la fonction renvoie toujours le même résultat lorsqu'on lui donne les mêmes arguments ;
  • la fonction n'a aucun effet de bord (elle ne modifie pas la valeur de variables statiques locales ou globales, n'effectue pas d'entrées ou de sorties, etc.).

Les fonctions pures devraient généralement être rendues constexpr.

En aparté…

Les fonctions constexpr n'ont pas toujours besoin d'être pures. En C++23, les fonctions constexpr peuvent utiliser et modifier des variables locales statiques. Comme la valeur d'une variable statique locale persiste d'un appel de fonction à l'autre, modifier une variable statique locale est considéré comme un effet de bord.

Cela dit, si votre programme est trivial ou jetable et que vous ne rendez pas une fonction constexpr, le monde ne va pas s'effondrer. Espérons-le.

Bonne pratique

Sauf raison particulière, une fonction pouvant être évaluée dans le cadre d'une expression constante doit être rendue constexpr (même si elle n'est pas utilisée ainsi pour le moment).

Une fonction qui ne peut pas être évaluée dans le cadre d'une expression constante requise ne doit pas être marquée constexpr.

Pourquoi ne pas rendre constexpr toutes les fonctions ?

Il existe quelques raisons de ne pas vouloir rendre une fonction constexpr :

  1. constexpr indique qu'une fonction peut être utilisée dans une expression constante. Si votre fonction ne peut pas être évaluée dans le cadre d'une expression constante, elle ne doit pas être marquée constexpr.
  2. constexpr fait partie de l'interface d'une fonction. Une fois qu'une fonction est rendue constexpr, elle peut être appelée par d'autres fonctions constexpr ou utilisée dans des contextes qui exigent des expressions constantes. Retirer le constexpr par la suite cassera ce code.
  3. Les fonctions constexpr peuvent être plus difficiles à déboguer, car vous ne pouvez pas placer de point d'arrêt dans leur exécution ni les parcourir pas à pas avec un débogueur.

Pourquoi rendre constexpr une fonction qui n'est pas réellement évaluée à la compilation ?

Les programmeurs débutants demandent parfois : « Pourquoi rendre constexpr une fonction qui n'est évaluée qu'à l'exécution dans mon programme (par exemple parce que les arguments de l'appel ne sont pas const) ? »

Il y a plusieurs raisons :

  1. Utiliser constexpr a peu d'inconvénients, et cela peut aider le compilateur à optimiser votre programme pour le rendre plus petit et plus rapide.
  2. Le fait que vous n'appeliez pas la fonction dans un contexte évaluable à la compilation pour le moment ne signifie pas que vous ne le ferez pas lorsque vous modifierez ou étendrez votre programme. Et si vous n'avez pas déjà rendu la fonction constexpr, vous n'y penserez peut-être pas lorsque vous commencerez à l'appeler dans un tel contexte, et vous passerez alors à côté des gains de performance. Ou vous serez peut-être contraint de la rendre constexpr plus tard, lorsque vous aurez besoin d'utiliser sa valeur de retour dans un contexte exigeant une expression constante.
  3. La répétition aide à ancrer les bonnes pratiques.

Sur un projet non trivial, il est judicieux d'implémenter vos fonctions en gardant à l'esprit qu'elles pourront être réutilisées ou étendues à l'avenir. Chaque fois que vous modifiez une fonction existante, vous risquez de la casser, ce qui impose de la retester, un travail qui demande du temps et de l'énergie. Il vaut souvent la peine de consacrer une minute ou deux supplémentaires à « bien faire les choses dès la première fois » afin de ne pas avoir à la refaire (et retester) plus tard.
