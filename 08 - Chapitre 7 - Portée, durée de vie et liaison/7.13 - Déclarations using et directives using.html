7.13 — Déclarations using et directives using

Vous avez sans doute déjà vu ce programme dans de nombreux manuels et tutoriels :

#include <iostream>

using namespace std;

int main()
{
    cout << "Hello world!\n";

    return 0;
}

Si vous voyez cela, fuyez. Votre manuel ou votre tutoriel est probablement obsolète. Dans cette leçon, nous allons voir pourquoi.

Astuce

Certains IDE créent également automatiquement, pour les nouveaux projets C++, un programme similaire (afin que vous puissiez compiler quelque chose immédiatement, plutôt que de partir d'un fichier vide).

Un bref retour historique

Avant que C++ ne prenne en charge les espaces de noms (namespaces), tous les noms qui se trouvent aujourd'hui dans l'espace de noms std appartenaient à l'espace de noms global. Cela provoquait des collisions de noms entre les identifiants du programme et ceux de la bibliothèque standard. Des programmes qui fonctionnaient avec une version de C++ pouvaient présenter un conflit de noms avec une version plus récente.

En 1995, les espaces de noms ont été normalisés, et toutes les fonctionnalités de la bibliothèque standard ont été déplacées hors de l'espace de noms global, dans l'espace de noms std. Ce changement a cassé le code plus ancien qui utilisait encore des noms sans std::.

Comme le sait quiconque a travaillé sur une grande base de code, toute modification d'une base de code (même minime) risque de casser le programme. Ajouter le préfixe std:: à chaque nom désormais déplacé dans l'espace de noms std représentait un risque considérable. Une solution était donc nécessaire.

De nos jours, si vous utilisez beaucoup la bibliothèque standard, taper std:: devant tout ce que vous employez peut devenir répétitif et, dans certains cas, nuire à la lisibilité du code.

C++ propose des solutions à ces deux problèmes, sous la forme d'instructions using.

Mais auparavant, définissons deux termes.

Noms qualifiés et noms non qualifiés

Un nom peut être soit qualifié, soit non qualifié.

Un nom qualifié (qualified name) est un nom accompagné de la portée à laquelle il est associé. Le plus souvent, un nom est qualifié par un espace de noms à l'aide de l'opérateur de résolution de portée (::). Par exemple :

std::cout // l'identifiant cout est qualifié par l'espace de noms std
::foo // l'identifiant foo est qualifié par l'espace de noms global

Pour les lecteurs avancés

Un nom peut aussi être qualifié par un nom de classe à l'aide de l'opérateur de résolution de portée (::), ou par un objet de classe à l'aide des opérateurs de sélection de membre (. ou ->). Par exemple :

class C; // une classe quelconque

C::s_member; // s_member est qualifié par la classe C
obj.x; // x est qualifié par l'objet de classe obj
ptr->y; // y est qualifié par le pointeur vers l'objet de classe ptr

Un nom non qualifié (unqualified name) est un nom sans qualificateur de portée. Par exemple, cout et x sont des noms non qualifiés, car ils ne sont associés à aucune portée.

Déclarations using

Une façon de réduire la répétition du préfixe std:: consiste à utiliser une déclaration using. Une déclaration using (using declaration) nous permet d'utiliser un nom non qualifié (sans portée) comme alias d'un nom qualifié.

Voici notre programme Hello world de base, avec une déclaration using à la ligne 5 :

#include <iostream>

int main()
{
   using std::cout; // cette déclaration using indique au compilateur que cout doit être résolu en std::cout
   cout << "Hello world!\n"; // donc aucun préfixe std:: n'est nécessaire ici !

   return 0;
} // la déclaration using expire à la fin de la portée courante

La déclaration using using std::cout; indique au compilateur que nous allons utiliser l'objet cout de l'espace de noms std. Ainsi, chaque fois qu'il rencontre cout, il considère qu'il s'agit de std::cout. S'il existe un conflit de noms entre std::cout et un autre cout visible depuis main(), c'est std::cout qui est privilégié. Par conséquent, à la ligne 6, nous pouvons écrire cout au lieu de std::cout.

Dans cet exemple trivial, cela ne fait pas beaucoup gagner de temps, mais si vous utilisez cout de nombreuses fois dans une fonction, une déclaration using peut rendre votre code plus lisible. Notez qu'il faut une déclaration using distincte pour chaque nom (par exemple une pour std::cout, une pour std::cin, etc.).

La déclaration using est active du point de déclaration jusqu'à la fin de la portée dans laquelle elle a été déclarée.

Bien que les déclarations using soient moins explicites que l'utilisation du préfixe std::, elles sont généralement considérées comme sûres et acceptables dans les fichiers source (.cpp), à une exception près que nous allons aborder plus loin.

Directives using

Une autre façon de simplifier les choses consiste à utiliser une directive using. Une directive using (using directive) permet de référencer tous les identifiants d'un espace de noms donné sans qualification, depuis la portée de la directive.

Pour les lecteurs avancés

Pour des raisons techniques, les directives using n'introduisent pas réellement de nouvelles significations pour les noms dans la portée courante : elles en introduisent dans une portée externe (vous trouverez davantage de détails sur le choix de cette portée externe ici).

Voici à nouveau notre programme Hello world, avec une directive using à la ligne 5 :

#include <iostream>

int main()
{
   using namespace std; // tous les noms de l'espace de noms std sont désormais accessibles sans qualification
   cout << "Hello world!\n"; // donc aucun préfixe std:: n'est nécessaire ici

   return 0;
} // la directive using se termine à la fin de la portée courante

La directive using using namespace std; indique au compilateur que tous les noms de l'espace de noms std doivent être accessibles sans qualification dans la portée courante (ici, celle de la fonction main()). Lorsque nous utilisons ensuite l'identifiant non qualifié cout, il est résolu en std::cout.

Les directives using constituent la solution prévue pour les anciennes bases de code antérieures aux espaces de noms, qui utilisaient des noms non qualifiés pour la bibliothèque standard. Plutôt que de devoir mettre à jour manuellement chaque nom non qualifié en nom qualifié (ce qui était risqué), une seule directive using (using namespace std;) pouvait être placée en haut de chaque fichier, et tous les noms déplacés dans l'espace de noms std pouvaient continuer à être utilisés sans qualification.

Problèmes posés par les directives using (ou pourquoi vous devriez éviter « using namespace std; »)

En C++ moderne, les directives using n'apportent en général que peu d'avantages (un peu de frappe en moins) par rapport aux risques encourus. Cela tient à deux facteurs :

  1. Les directives using permettent un accès non qualifié à tous les noms d'un espace de noms (y compris potentiellement de nombreux noms que vous n'utiliserez jamais).
  2. Les directives using ne privilégient pas les noms de l'espace de noms désigné par la directive par rapport aux autres noms.

Il en résulte que la probabilité de collisions de noms augmente considérablement (surtout si vous importez l'espace de noms std).

Commençons par examiner un exemple illustrant une collision de noms causée par des directives using :

#include <iostream>

namespace A
{
    int x { 10 };
}

namespace B
{
    int x{ 20 };
}

int main()
{
    using namespace A;
    using namespace B;

    std::cout << x << '\n';

    return 0;
}

Dans l'exemple ci-dessus, le compilateur ne peut pas déterminer si le x de main désigne A::x ou B::x. Il échoue alors à la compilation avec une erreur de « symbole ambigu ». Nous pourrions résoudre le problème en supprimant l'une des directives using, en utilisant une déclaration using à la place, ou en qualifiant x (en A::x ou B::x).

Voici un autre exemple, plus subtil :

#include <iostream> // importe la déclaration de std::cout

int cout() // déclare notre propre fonction « cout »
{
    return 5;
}

int main()
{
    using namespace std; // rend std::cout accessible sous le nom « cout »
    cout << "Hello, world!\n"; // oups ! Quel cout voulons-nous ici ? Celui de l'espace de noms std ou celui que nous avons défini plus haut ?

    return 0;
}

Dans cet exemple, le compilateur ne peut pas déterminer si notre utilisation non qualifiée de cout désigne std::cout ou la fonction cout que nous avons définie, et échoue encore une fois à la compilation avec une erreur de « symbole ambigu ». Bien que cet exemple soit trivial, si nous avions explicitement préfixé std::cout ainsi :

    std::cout << "Hello, world!\n"; // indique au compilateur que nous voulons std::cout

ou utilisé une déclaration using au lieu d'une directive using :

    using std::cout; // indique au compilateur que cout désigne std::cout
    cout << "Hello, world!\n"; // donc ceci désigne std::cout

alors notre programme n'aurait posé aucun problème. Et même si vous n'êtes probablement pas enclin à écrire une fonction nommée « cout », l'espace de noms std contient des centaines d'autres noms qui ne demandent qu'à entrer en collision avec les vôtres.

Même lorsqu'une directive using ne provoque pas de collision aujourd'hui, elle rend votre code plus vulnérable aux collisions futures. Par exemple, si votre code contient une directive using pour une bibliothèque qui est ensuite mise à jour, tous les nouveaux noms introduits dans la version mise à jour deviennent des candidats à une collision avec votre code existant.

Par exemple, le programme suivant compile et s'exécute sans problème :

FooLib.h (faisant partie d'une bibliothèque tierce) :

#ifndef FOOLIB
#define FOOLIB

namespace Foo
{
    int a { 20 };
}

#endif

main.cpp :

#include <iostream>
#include <FooLib.h> // une bibliothèque tierce installée en dehors du répertoire de notre projet, d'où l'usage des chevrons

void print()
{
    std::cout << "Hello\n";
}

int main()
{
    using namespace Foo; // Parce que nous sommes fainéants et voulons accéder aux noms qualifiés Foo:: sans taper le préfixe Foo::

    std::cout << a << '\n'; // utilise Foo::a
    print(); // appelle ::print()

    return 0;
}

Supposons maintenant que vous mettiez FooLib à jour en une nouvelle version, et que FooLib.h devienne :

FooLib.h (mis à jour) :

#ifndef FOOLIB
#define FOOLIB

namespace Foo
{
    int a { 20 };
    void print() { std::cout << "Timmah!"; } // Cette fonction a été ajoutée
}
#endif

Votre main.cpp n'a pas changé, mais il ne compile plus ! En effet, notre directive using rend Foo::print() accessible simplement sous le nom print(), et il devient ambigu de savoir si l'appel à print() désigne ::print() ou Foo::print().

Il existe aussi une version plus insidieuse de ce problème. La bibliothèque mise à jour peut introduire une fonction qui non seulement porte le même nom, mais qui correspond en fait mieux à un appel de fonction donné. Dans ce cas, le compilateur peut décider de privilégier la nouvelle fonction, et le comportement de votre programme changera de façon inattendue et silencieuse.

Considérez le programme suivant :

Foolib.h (faisant partie d'une bibliothèque tierce) :

#ifndef FOOLIB_H
#define FOOLIB_H

namespace Foo
{
    int a { 20 };
}
#endif

main.cpp :

#include <iostream>
#include <Foolib.h> // une bibliothèque tierce installée en dehors du répertoire de notre projet, d'où l'usage des chevrons

int get(long)
{
    return 1;
}

int main()
{
    using namespace Foo; // Parce que nous sommes fainéants et voulons accéder aux noms qualifiés Foo:: sans taper le préfixe Foo::
    std::cout << a << '\n'; // utilise Foo::a

    std::cout << get(0) << '\n'; // appelle ::get(long)

    return 0;
}

Ce programme s'exécute et affiche 1.

Maintenant, supposons que nous mettions à jour la bibliothèque Foolib, qui comprend un Foolib.h mis à jour ressemblant à ceci :

Foolib.h (mis à jour) :

#ifndef FOOLIB_H
#define FOOLIB_H

namespace Foo
{
    int a { 20 };

    int get(int) { return 2; } // nouvelle fonction ajoutée
}
#endif

Une fois encore, notre main.cpp n'a pas du tout changé, mais ce programme compile maintenant, s'exécute et affiche 2 !

Lorsque le compilateur rencontre un appel de fonction, il doit déterminer quelle définition de fonction correspond à cet appel. Parmi un ensemble de fonctions potentiellement correspondantes, il privilégie une fonction qui ne nécessite aucune conversion d'arguments par rapport à une fonction qui en nécessite. Comme le littéral 0 est un entier, C++ préférera associer get(0) à la nouvelle fonction get(int) (sans conversion) plutôt qu'à get(long) (qui nécessite une conversion de int en long). Cela provoque un changement inattendu du comportement de notre programme.

Dans ce cas, le changement de comportement est assez évident. Mais dans un programme plus complexe, où la valeur retournée n'est pas simplement affichée, ce problème pourrait être très difficile à détecter.

Cela ne se serait pas produit si nous avions utilisé une déclaration using ou un qualificateur de portée explicite.

Enfin, l'absence de préfixes de portée explicites rend plus difficile, pour le lecteur, la distinction entre les fonctions qui font partie d'une bibliothèque et celles qui font partie de votre programme. Par exemple, si nous utilisons une directive using :

using namespace NS;

int main()
{
    foo(); // ce foo est-il une fonction définie par l'utilisateur, ou fait-il partie de la bibliothèque NS ?
}

Il n'est pas clair de savoir si l'appel à foo() est en réalité un appel à NS::foo() ou à un foo() défini par l'utilisateur. Les IDE modernes devraient pouvoir lever cette ambiguïté lorsque vous survolez un nom, mais devoir survoler chaque nom simplement pour savoir d'où il provient est fastidieux.

Sans la directive using, c'est beaucoup plus clair :

int main()
{
    NS::foo(); // fait clairement partie de la bibliothèque NS
    foo(); // probablement une fonction définie par l'utilisateur
}

Dans cette version, l'appel à NS::foo() est clairement un appel de bibliothèque. L'appel à foo() simple est probablement un appel à une fonction définie par l'utilisateur (certaines bibliothèques, y compris certains en-têtes de la bibliothèque standard, placent effectivement des noms dans l'espace de noms global, il ne s'agit donc pas d'une garantie).

La portée des instructions using

Si une déclaration using ou une directive using est utilisée à l'intérieur d'un bloc, les noms ne s'appliquent qu'à ce bloc (elle suit les règles habituelles de portée des blocs). C'est une bonne chose, car cela réduit les risques de collisions de noms à ce seul bloc.

Si une déclaration using ou une directive using est utilisée dans un espace de noms (y compris l'espace de noms global), les noms s'appliquent à tout le reste du fichier (ils ont une portée de fichier).

Ne pas utiliser d'instructions using dans les fichiers d'en-tête, ni avant une directive #include

Une bonne règle empirique consiste à ne jamais placer d'instructions using à un endroit où elles pourraient avoir un impact sur le code d'un autre fichier. Ni à un endroit où le code d'un autre fichier pourrait les influencer.

Plus précisément, cela signifie que les instructions using ne doivent pas être utilisées dans les fichiers d'en-tête, ni avant une directive #include.

Par exemple, si vous placez une instruction using dans l'espace de noms global d'un fichier d'en-tête, alors chaque autre fichier qui #include cet en-tête recevra également cette instruction using. C'est clairement néfaste. Cela s'applique également aux espaces de noms situés dans des fichiers d'en-tête, pour la même raison.

Mais qu'en est-il des instructions using placées dans des fonctions définies dans des fichiers d'en-tête ? On pourrait penser que ce n'est pas un problème, puisque la portée de l'instruction using est limitée à la fonction, non ? Eh bien, c'est encore non. Et pour la même raison que nous ne devons pas utiliser d'instructions using avant une directive #include.

Il s'avère que le comportement des instructions using dépend des identifiants déjà introduits. Elles sont donc dépendantes de l'ordre, car leur fonctionnement peut changer si les identifiants introduits auparavant changent.

Illustrons cela par un exemple :

FooInt.h :

namespace Foo
{
    void print(int)
    {
        std::cout << "print(int)\n" << std::endl;
    }
}

FooDouble.h :

namespace Foo
{
    void print(double)
    {
        std::cout << "print(double)\n" << std::endl;
    }
}

main.cpp (correct) :

#include <iostream>

#include "FooDouble.h"
#include "FooInt.h"

using Foo::print; // print désigne Foo::print

int main()
{
    print(5);  // Appelle Foo::print(int)
}

À l'exécution, ce programme appelle Foo::print(int), qui affiche print(int).

Modifions maintenant légèrement main.cpp.

main.cpp (incorrect) :

#include <iostream>

#include "FooDouble.h"

using Foo::print; // nous avons déplacé l'instruction using ici, avant la directive #include
#include "FooInt.h"

int main()
{
    print(5);  // Appelle Foo::print(double)
}

Nous avons simplement déplacé using Foo::print; avant #include "FooInt.h", et notre programme affiche maintenant print(double) ! Quelle que soit la raison de ce comportement, vous conviendrez sans doute qu'il s'agit du type de comportement que nous voulons éviter !

Pour revenir à notre point de départ : si nous ne devons pas utiliser d'instructions using dans les fonctions définies dans des fichiers d'en-tête, c'est pour la même raison. Nous ne pouvons pas contrôler quels autres en-têtes peuvent être #include avant le nôtre, et ces en-têtes pourraient faire quelque chose qui modifie le comportement de notre instruction using !

Le seul endroit où il est véritablement sûr d'utiliser des instructions using est dans nos fichiers source (.cpp), après tous les #include.

Pour les lecteurs avancés

Cet exemple utilise un concept que nous n'avons pas encore abordé, appelé « surcharge de fonctions » (nous le traitons dans la leçon 11.1 -- Introduction à la surcharge de fonctions). Pour cet exemple, il vous suffit de savoir que deux fonctions de même portée peuvent porter le même nom, à condition que leurs paramètres soient distincts. Comme int et double sont des types distincts, il n'y a aucun problème à avoir Foo::print(int) et Foo::print(double) côte à côte.

Dans la version correcte, lorsque le compilateur rencontre using Foo::print, il a déjà vu Foo::print(int) et Foo::print(double), il rend donc les deux accessibles sous le nom simple print(). Comme Foo::print(int) correspond mieux que Foo::print(double), c'est Foo::print(int) qui est appelée.

Dans la version incorrecte, lorsque le compilateur rencontre using Foo::print, il n'a vu qu'une déclaration de Foo::print(double), il ne rend donc accessible sous le nom non qualifié que Foo::print(double). Ainsi, lorsque nous appelons print(5), seule Foo::print(double) peut être retenue. C'est donc Foo::print(double) qui est appelée !

Annuler ou remplacer une instruction using

Une fois qu'une instruction using a été déclarée, il n'est plus possible de l'annuler, ni de la remplacer par une autre instruction using, dans la portée où elle a été déclarée.

int main()
{
    using namespace Foo;

    // il n'existe aucun moyen d'annuler le « using namespace Foo » ici !
    // il n'existe pas non plus de moyen de remplacer « using namespace Foo » par une autre instruction using

    return 0;
} // using namespace Foo se termine ici

La meilleure solution consiste à limiter volontairement la portée de l'instruction using dès le départ, en utilisant les règles de portée des blocs.

int main()
{
    {
        using namespace Foo;
        // appels aux éléments de Foo:: ici
    } // using namespace Foo expire

    {
        using namespace Goo;
        // appels aux éléments de Goo:: ici
    } // using namespace Goo expire

    return 0;
}

Bien entendu, tous ces tracas peuvent être évités en utilisant directement, dès le départ, l'opérateur de résolution de portée (::).

Bonnes pratiques concernant les instructions using

Bonne pratique

Privilégiez les qualificateurs d'espace de noms explicites aux instructions using.

Évitez complètement les directives using (à l'exception de using namespace std::literals pour accéder aux suffixes littéraux s et sv). Les déclarations using sont acceptables dans les fichiers .cpp, après les directives #include. N'utilisez pas d'instructions using dans les fichiers d'en-tête (en particulier dans l'espace de noms global des fichiers d'en-tête).

Contenu associé

Le mot-clé using sert également à définir des alias de types, qui n'ont aucun rapport avec les instructions using. Nous traitons des alias de types dans la leçon 10.7 -- Typedefs et alias de types.
