7.2 — Espaces de noms définis par l'utilisateur et opérateur de résolution de portée

Dans la leçon 2.9 -- Collisions de noms et introduction aux espaces de noms, nous avons présenté les notions de collision de noms et d'espace de noms. Pour rappel, une collision de noms se produit lorsque deux identifiants identiques sont introduits dans la même portée, et que le compilateur ne peut pas déterminer lequel utiliser. Dans ce cas, le compilateur ou l'éditeur de liens (linker) produit une erreur, car il ne dispose pas de suffisamment d'informations pour lever l'ambiguïté.

Point clé

À mesure que les programmes grossissent, le nombre d'identifiants augmente, ce qui fait croître de façon significative la probabilité d'une collision de noms. Comme chaque nom d'une portée donnée peut entrer en collision avec chaque autre nom de cette même portée, une augmentation linéaire du nombre d'identifiants entraîne une augmentation exponentielle des collisions potentielles ! C'est l'une des raisons principales de définir les identifiants dans la portée la plus petite possible.

Reprenons un exemple de collision de noms, puis voyons comment les espaces de noms permettent d'améliorer la situation. Dans l'exemple suivant, foo.cpp et goo.cpp sont des fichiers sources contenant des fonctions qui font des choses différentes, mais portent le même nom et ont les mêmes paramètres.

foo.cpp :

// Ce doSomething() additionne la valeur de ses paramètres
int doSomething(int x, int y)
{
    return x + y;
}

goo.cpp :

// Ce doSomething() soustrait la valeur de ses paramètres
int doSomething(int x, int y)
{
    return x - y;
}

main.cpp :

#include <iostream>

int doSomething(int x, int y); // déclaration anticipée de doSomething

int main()
{
    std::cout << doSomething(4, 3) << '\n'; // quel doSomething allons-nous obtenir ?
    return 0;
}

Si le projet ne contient que foo.cpp ou goo.cpp (mais pas les deux), il compile et s'exécute sans problème. En revanche, en compilant les deux dans le même programme, nous avons introduit deux fonctions différentes portant le même nom et les mêmes paramètres dans la même portée (la portée globale), ce qui provoque une collision de noms. En conséquence, l'éditeur de liens émet une erreur :


goo.cpp:3: multiple definition of `doSomething(int, int)'; foo.cpp:3: first defined here

Notez que cette erreur se produit au point de redéfinition : peu importe donc que la fonction doSomething soit appelée ou non.

Une façon de résoudre le problème serait de renommer l'une des fonctions pour que les noms n'entrent plus en collision. Mais cela oblige aussi à modifier le nom de tous les appels de fonction, ce qui peut être fastidieux et source d'erreurs. Une meilleure façon d'éviter les collisions consiste à placer vos fonctions dans vos propres espaces de noms. C'est pour cette raison que la bibliothèque standard a été placée dans l'espace de noms std.

Définir vos propres espaces de noms

C++ nous permet de définir nos propres espaces de noms grâce au mot-clé namespace. Les espaces de noms que vous créez dans vos programmes sont couramment appelés espaces de noms définis par l'utilisateur (user-defined namespaces), même s'il serait plus exact de les appeler espaces de noms définis par le programme (program-defined namespaces).

La syntaxe d'un espace de noms est la suivante :


namespace NomEspaceDeNoms
{
    // contenu de l'espace de noms ici
}

On commence par le mot-clé namespace, suivi de l'identifiant de l'espace de noms, puis des accolades contenant le contenu de l'espace de noms.

Historiquement, les noms d'espaces de noms ne commençaient pas par une majuscule, et de nombreux guides de style recommandent encore cette convention.

Pour les lecteurs avancés

Quelques raisons de préférer des noms d'espaces de noms commençant par une majuscule :

  • Il est d'usage de nommer les types définis par le programme avec une majuscule initiale. Utiliser la même convention pour les espaces de noms définis par le programme est cohérent (surtout lorsqu'on utilise un nom qualifié comme Foo::x, où Foo peut être un espace de noms ou un type classe).
  • Cela aide à éviter les collisions de noms avec d'autres noms en minuscules fournis par le système ou par des bibliothèques.
  • Le document de norme C++20 utilise ce style.
  • Le document des C++ Core Guidelines utilise ce style.

Nous recommandons de commencer les noms d'espaces de noms par une majuscule. Cependant, les deux styles peuvent être considérés comme acceptables.

Un espace de noms doit être défini soit dans la portée globale, soit à l'intérieur d'un autre espace de noms. Comme pour le contenu d'une fonction, le contenu d'un espace de noms est conventionnellement indenté d'un niveau. On voit parfois un point-virgule facultatif placé après l'accolade fermante d'un espace de noms.

Voici un exemple où les fichiers de l'exemple précédent sont réécrits en utilisant des espaces de noms :

foo.cpp :

namespace Foo // définit un espace de noms nommé Foo
{
    // Ce doSomething() appartient à l'espace de noms Foo
    int doSomething(int x, int y)
    {
        return x + y;
    }
}

goo.cpp :

namespace Goo // définit un espace de noms nommé Goo
{
    // Ce doSomething() appartient à l'espace de noms Goo
    int doSomething(int x, int y)
    {
        return x - y;
    }
}

Désormais, doSomething() dans foo.cpp se trouve dans l'espace de noms Foo, et doSomething() dans goo.cpp se trouve dans l'espace de noms Goo. Voyons ce qui se passe lorsque nous recompilons le programme.

main.cpp :

int doSomething(int x, int y); // déclaration anticipée de doSomething

int main()
{
    std::cout << doSomething(4, 3) << '\n'; // quel doSomething allons-nous obtenir ?
    return 0;
}

La réponse est que nous obtenons maintenant une autre erreur !


ConsoleApplication1.obj : error LNK2019: unresolved external symbol "int __cdecl doSomething(int,int)" (?doSomething@@YAHHH@Z) referenced in function _main

Dans ce cas, le compilateur est satisfait (grâce à notre déclaration anticipée), mais l'éditeur de liens ne parvient pas à trouver une définition de doSomething dans l'espace de noms global. En effet, nos deux versions de doSomething ne se trouvent plus dans l'espace de noms global : elles sont désormais dans la portée de leurs espaces de noms respectifs !

Il existe deux façons différentes d'indiquer au compilateur la version de doSomething() à utiliser : via l'opérateur de résolution de portée (scope resolution operator), ou via les directives using (que nous verrons dans une leçon ultérieure de ce chapitre).

Dans les exemples suivants, nous réduirons nos exemples à une solution d'un seul fichier, pour faciliter la lecture.

Accéder à un espace de noms avec l'opérateur de résolution de portée (::)

La meilleure façon d'indiquer au compilateur de chercher un identifiant dans un espace de noms particulier consiste à utiliser l'opérateur de résolution de portée (::). Cet opérateur indique au compilateur que l'identifiant spécifié par l'opérande de droite doit être recherché dans la portée de l'opérande de gauche.

Voici un exemple utilisant l'opérateur de résolution de portée pour indiquer au compilateur que nous voulons explicitement utiliser la version de doSomething() qui se trouve dans l'espace de noms Foo :

#include <iostream>

namespace Foo // définit un espace de noms nommé Foo
{
    // Ce doSomething() appartient à l'espace de noms Foo
    int doSomething(int x, int y)
    {
        return x + y;
    }
}

namespace Goo // définit un espace de noms nommé Goo
{
    // Ce doSomething() appartient à l'espace de noms Goo
    int doSomething(int x, int y)
    {
        return x - y;
    }
}

int main()
{
    std::cout << Foo::doSomething(4, 3) << '\n'; // utilise le doSomething() qui existe dans l'espace de noms Foo
    return 0;
}

namespace Foo // définit un espace de noms nommé Foo

    }

L'opérateur de résolution de portée est très pratique, car il nous permet de choisir explicitement l'espace de noms dans lequel chercher, ce qui supprime toute ambiguïté potentielle. Nous pouvons même faire ceci :

#include <iostream>

namespace Foo // définit un espace de noms nommé Foo
{
    // Ce doSomething() appartient à l'espace de noms Foo
    int doSomething(int x, int y)
    {
        return x + y;
    }

        return x - y;
    }
}

int main()
{

Utiliser l'opérateur de résolution de portée sans préfixe de nom

L'opérateur de résolution de portée peut aussi être placé devant un identifiant sans nom d'espace de noms (par exemple ::doSomething). Dans ce cas, l'identifiant (ici doSomething) est recherché dans l'espace de noms global.

#include <iostream>

void print() // ce print() se trouve dans l'espace de noms global
{
    std::cout << " there\n";
}

namespace Foo
{
    void print() // ce print() se trouve dans l'espace de noms Foo
    {
        std::cout << "Hello";
    }
}

int main()
{
    Foo::print(); // appelle print() dans l'espace de noms Foo
    ::print();    // appelle print() dans l'espace de noms global (identique à un simple print() dans ce cas)

    return 0;
}

Dans l'exemple ci-dessus, ::print() produit le même effet que si nous avions appelé print() sans résolution de portée : l'utilisation de l'opérateur de résolution de portée est donc superflue dans ce cas. Mais l'exemple suivant montrera un cas où l'opérateur de résolution de portée sans espace de noms est utile.

Résolution des identifiants depuis l'intérieur d'un espace de noms

Si un identifiant utilisé à l'intérieur d'un espace de noms n'est accompagné d'aucune résolution de portée, le compilateur cherche d'abord une déclaration correspondante dans ce même espace de noms. Si aucun identifiant correspondant n'est trouvé, le compilateur examine ensuite successivement chaque espace de noms englobant, l'espace de noms global étant examiné en dernier.

#include <iostream>

void print() // ce print() se trouve dans l'espace de noms global
{
    std::cout << " there\n";
}

namespace Foo
{
    void print() // ce print() se trouve dans l'espace de noms Foo
    {
        std::cout << "Hello";
    }

    void printHelloThere()
    {
        print();   // appelle print() dans l'espace de noms Foo
        ::print(); // appelle print() dans l'espace de noms global
    }
}

int main()
{
    Foo::printHelloThere();

    return 0;
}

Ce programme affiche :


Hello there

Dans l'exemple ci-dessus, print() est appelé sans résolution de portée. Comme cet appel de print() se trouve à l'intérieur de l'espace de noms Foo, le compilateur vérifie d'abord s'il existe une déclaration de Foo::print(). Comme c'est le cas, Foo::print() est appelé.

Si Foo::print() n'avait pas été trouvé, le compilateur aurait examiné l'espace de noms englobant (ici, l'espace de noms global) pour voir s'il pouvait y trouver une correspondance pour print().

Notez que nous utilisons aussi l'opérateur de résolution de portée sans espace de noms (::print()) pour appeler explicitement la version globale de print().

Déclaration anticipée de contenu dans les espaces de noms

Dans la leçon 2.11 -- Fichiers d'en-tête, nous avons vu comment utiliser les fichiers d'en-tête pour propager les déclarations anticipées. Pour les identifiants situés dans un espace de noms, ces déclarations anticipées doivent également se trouver dans le même espace de noms :

add.h

#ifndef ADD_H
#define ADD_H

namespace BasicMath
{
    // la fonction add() fait partie de l'espace de noms BasicMath
    int add(int x, int y);
}

#endif

add.cpp

#include "add.h"

namespace BasicMath
{
    // définit la fonction add() dans l'espace de noms BasicMath
    int add(int x, int y)
    {
        return x + y;
    }
}

main.cpp

#include "add.h" // pour BasicMath::add()

#include <iostream>

int main()
{
    std::cout << BasicMath::add(4, 3) << '\n';

    return 0;
}

Si la déclaration anticipée de add() n'était pas placée dans l'espace de noms BasicMath, add() serait alors déclarée dans l'espace de noms global, et le compilateur se plaindrait de ne pas avoir vu de déclaration pour l'appel BasicMath::add(4, 3). Si la définition de la fonction add() ne se trouvait pas dans l'espace de noms BasicMath, l'éditeur de liens se plaindrait de ne pas trouver de définition correspondant à l'appel BasicMath::add(4, 3).

Plusieurs blocs d'espace de noms sont autorisés

Il est légal de déclarer des blocs d'espace de noms à plusieurs endroits, que ce soit dans plusieurs fichiers ou à plusieurs emplacements d'un même fichier. Toutes les déclarations appartenant à l'espace de noms sont considérées comme faisant partie de celui-ci.

circle.h :

#ifndef CIRCLE_H
#define CIRCLE_H

namespace BasicMath
{
    constexpr double pi{ 3.14 };
}

#endif

growth.h :

#ifndef GROWTH_H
#define GROWTH_H

namespace BasicMath
{
    // la constante e fait aussi partie de l'espace de noms BasicMath
    constexpr double e{ 2.7 };
}

#endif

main.cpp :

#include "circle.h" // pour BasicMath::pi
#include "growth.h" // pour BasicMath::e

#include <iostream>

int main()
{
    std::cout << BasicMath::pi << '\n';
    std::cout << BasicMath::e << '\n';

    return 0;
}

Cela fonctionne exactement comme on pourrait s'y attendre :


3.14
2.7

La bibliothèque standard exploite largement cette fonctionnalité, puisque chaque fichier d'en-tête de la bibliothèque standard contient ses déclarations dans un bloc namespace std situé dans ce fichier d'en-tête. Sans cela, la bibliothèque standard entière devrait être définie dans un seul fichier d'en-tête !

Notez que cette possibilité signifie également que vous pourriez ajouter vos propres fonctionnalités à l'espace de noms std. Or, cela provoque la plupart du temps un comportement indéfini, car l'espace de noms std interdit spécialement l'extension par du code utilisateur.

Avertissement

N'ajoutez pas de fonctionnalités personnalisées à l'espace de noms std.

Espaces de noms imbriqués

Les espaces de noms peuvent être imbriqués dans d'autres espaces de noms. Par exemple :

#include <iostream>

namespace Foo
{
    namespace Goo // Goo est un espace de noms à l'intérieur de l'espace de noms Foo
    {
        int add(int x, int y)
        {
            return x + y;
        }
    }
}

int main()
{
    std::cout << Foo::Goo::add(1, 2) << '\n';
    return 0;
}

Notez que, comme l'espace de noms Goo se trouve dans l'espace de noms Foo, nous accédons à add par Foo::Goo::add.

Depuis C++17, les espaces de noms imbriqués peuvent aussi être déclarés de cette manière :

#include <iostream>

namespace Foo::Goo // Goo est un espace de noms à l'intérieur de l'espace de noms Foo (style C++17)
{
    int add(int x, int y)
    {
        return x + y;
    }
}

int main()
{
    std::cout << Foo::Goo::add(1, 2) << '\n';
    return 0;
}

C'est équivalent à l'exemple précédent.

Si vous avez besoin plus tard d'ajouter des déclarations uniquement à l'espace de noms Foo, vous pouvez définir un espace de noms Foo séparé à cet effet :

#include <iostream>

namespace Foo::Goo // Goo est un espace de noms à l'intérieur de l'espace de noms Foo (style C++17)
{
    int add(int x, int y)
    {
        return x + y;
    }
}

namespace Foo
{
     void someFcn() {} // Cette fonction se trouve uniquement dans Foo
}

int main()
{
    std::cout << Foo::Goo::add(1, 2) << '\n';
    return 0;
}

Le choix de conserver une définition séparée de Foo::Goo ou d'imbriquer Goo dans Foo relève du style.

Alias d'espaces de noms

Comme écrire le nom qualifié d'une variable ou d'une fonction située dans un espace de noms imbriqué peut être fastidieux, C++ permet de créer des alias d'espaces de noms (namespace aliases), qui nous permettent de raccourcir temporairement une longue suite d'espaces de noms :

#include <iostream>

namespace Foo::Goo
{
    int add(int x, int y)
    {
        return x + y;
    }
}

int main()
{
    namespace Active = Foo::Goo; // Active désigne maintenant Foo::Goo

    std::cout << Active::add(1, 2) << '\n'; // Il s'agit en réalité de Foo::Goo::add()

    return 0;
} // L'alias Active prend fin ici

Un avantage intéressant des alias d'espaces de noms : si vous voulez un jour déplacer les fonctionnalités de Foo::Goo vers un autre emplacement, il vous suffit de mettre à jour l'alias Active pour refléter la nouvelle destination, au lieu de devoir rechercher et remplacer chaque occurrence de Foo::Goo.

#include <iostream>

namespace Foo::Goo
{
}

namespace V2
{
    int add(int x, int y)
    {
        return x + y;
    }
}

int main()
{
    namespace Active = V2; // Active désigne maintenant V2

    std::cout << Active::add(1, 2) << '\n'; // Nous n'avons pas besoin de modifier cette ligne

    return 0;
}

Comment utiliser les espaces de noms

Il est utile de noter que les espaces de noms en C++ n'ont pas été conçus à l'origine pour mettre en place une hiérarchie d'informations : ils ont été conçus principalement comme un mécanisme pour éviter les collisions de noms. Pour s'en convaincre, notez que l'intégralité de la bibliothèque standard se trouve sous l'unique espace de noms de premier niveau std. Les fonctionnalités plus récentes de la bibliothèque standard, qui introduisent beaucoup de noms, ont commencé à utiliser des espaces de noms imbriqués (par exemple std::ranges) pour éviter les collisions de noms à l'intérieur de std.

  • Les petites applications développées pour votre usage personnel n'ont généralement pas besoin d'être placées dans des espaces de noms. En revanche, pour les projets personnels plus importants qui incluent beaucoup de bibliothèques tierces, placer votre code dans un espace de noms peut aider à éviter les collisions avec des bibliothèques qui ne sont pas correctement organisées en espaces de noms.

Note de l'auteur

Les exemples de ces tutoriels ne seront généralement pas placés dans des espaces de noms, sauf si nous illustrons quelque chose de précis sur les espaces de noms, afin de garder les exemples concis.

  • Tout code destiné à être distribué à d'autres personnes doit absolument être placé dans un espace de noms, afin d'éviter les conflits avec le code dans lequel il sera intégré. Un seul espace de noms de premier niveau suffit souvent (par exemple Foologger). Autre avantage : placer le code d'une bibliothèque dans un espace de noms permet à l'utilisateur de voir le contenu de votre bibliothèque grâce à la fonctionnalité de complétion automatique et de suggestions de son éditeur (par exemple, si vous tapez Foologger, la complétion automatique affichera tous les noms situés dans Foologger).
  • Dans les organisations comptant plusieurs équipes, des espaces de noms à deux niveaux, voire à trois niveaux, sont souvent utilisés pour éviter les conflits de noms entre le code produit par différentes équipes. Ils prennent souvent l'une des formes suivantes :
  1. Projet ou bibliothèque :: module (par exemple Foologger::Lang)
  2. Entreprise ou organisation :: projet ou bibliothèque (par exemple Foosoft::Foologger)
  3. Entreprise ou organisation :: projet ou bibliothèque :: module (par exemple Foosoft::Foologger::Lang)

Les espaces de noms au niveau des modules permettent de séparer le code susceptible d'être réutilisé plus tard du code spécifique à l'application, qui ne le sera pas. Par exemple, les fonctions de physique et de mathématiques pourraient être regroupées dans un espace de noms (par exemple Math::), et les fonctions de langue et de localisation dans un autre (par exemple Lang::). Cependant, l'arborescence des répertoires peut aussi servir à cela (avec le code propre à l'application dans l'arborescence du projet, et le code réutilisable dans une arborescence partagée distincte).

En règle générale, évitez les espaces de noms profondément imbriqués (plus de 3 niveaux).
