7.9 — Fonctions et variables inline

Considérons le cas où vous devez écrire du code pour accomplir une tâche bien précise, comme lire une saisie de l'utilisateur, écrire quelque chose dans un fichier ou calculer une valeur particulière. Pour implémenter ce code, vous avez essentiellement deux options :

  1. Écrire le code dans une fonction existante (on parle alors de code écrit « in-place » ou « inline »).
  2. Créer une nouvelle fonction (et éventuellement des sous-fonctions) pour gérer la tâche.

Placer le code dans une nouvelle fonction apporte de nombreux avantages, car les petites fonctions :

  • Sont plus faciles à lire et à comprendre dans le contexte global du programme.
  • Sont plus faciles à réutiliser, car les fonctions sont naturellement modulaires.
  • Sont plus faciles à mettre à jour, car le code n'a besoin d'être modifié qu'à un seul endroit.

Cependant, l'un des inconvénients d'utiliser une nouvelle fonction est que chaque appel de fonction entraîne un certain surcoût de performance. Considérons l'exemple suivant :

#include <iostream>

int min(int x, int y)
{
    return (x < y) ? x : y;
}

int main()
{
    std::cout << min(5, 6) << '\n';
    std::cout << min(3, 2) << '\n';
    return 0;
}

Lorsqu'un appel à min() est rencontré, le processeur doit sauvegarder l'adresse de l'instruction qu'il est en train d'exécuter (afin de savoir où revenir plus tard) ainsi que les valeurs de différents registres du processeur (afin de pouvoir les restaurer au retour). Ensuite, les paramètres x et y doivent être instanciés puis initialisés. Le flux d'exécution doit alors sauter vers le code de la fonction min(). Lorsque la fonction se termine, le programme doit revenir à l'emplacement de l'appel, et la valeur de retour doit être copiée afin de pouvoir être affichée. Ce travail doit être effectué pour chaque appel de fonction.
Tout le travail supplémentaire nécessaire pour préparer, faciliter et/ou nettoyer après une tâche (dans ce cas, l'appel d'une fonction) s'appelle le surcoût (overhead).

Pour les fonctions volumineuses et/ou effectuant des tâches complexes, le surcoût de l'appel est généralement négligeable par rapport au temps d'exécution de la fonction. En revanche, pour les petites fonctions (comme min() ci-dessus), le coût du surcoût peut être supérieur au temps nécessaire à l'exécution du code de la fonction elle-même ! Lorsqu'une petite fonction est appelée souvent, l'utiliser peut entraîner une perte de performance significative par rapport à l'écriture du même code en place.

L'expansion inline

Heureusement, le compilateur C++ dispose d'une astuce pour éviter ce surcoût : l'expansion inline (inline expansion) est un processus au cours duquel un appel de fonction est remplacé par le code de la définition de la fonction appelée.

Par exemple, si le compilateur expansait les appels à min() dans l'exemple précédent, le code résultant ressemblerait à ceci :

#include <iostream>

int main()
{
    std::cout << ((5 < 6) ? 5 : 6) << '\n';
    std::cout << ((3 < 2) ? 3 : 2) << '\n';
    return 0;
}

Notez que les deux appels à la fonction min() ont été remplacés par le code du corps de la fonction min() (les valeurs des arguments étant substituées aux paramètres). Cela nous permet d'éviter le surcoût de ces appels, tout en conservant les résultats du code.

La performance du code inline

Au-delà de la suppression du coût de l'appel de fonction, l'expansion inline permet également au compilateur d'optimiser plus efficacement le code résultant. Par exemple, comme l'expression ((5 < 6) ? 5 : 6) est désormais une expression constante, le compilateur peut optimiser davantage la première instruction de main() en std::cout << 5 << '\n';.

Cependant, l'expansion inline a aussi son propre coût potentiel : si le corps de la fonction développée comporte plus d'instructions que l'appel de fonction remplacé, chaque expansion inline augmentera la taille de l'exécutable. Or, les exécutables plus volumineux tendent à être plus lents (car ils tiennent moins bien dans les mémoires cache).

La décision de savoir si une fonction bénéficierait d'être rendue inline (car la suppression du surcoût d'appel l'emporte sur l'augmentation de la taille de l'exécutable) n'est pas simple. L'expansion inline peut améliorer les performances, les dégrader, ou ne rien changer du tout, selon le coût relatif d'un appel de fonction, la taille de la fonction et les autres optimisations pouvant être appliquées.

L'expansion inline convient surtout aux fonctions simples et courtes (par exemple, pas plus de quelques instructions), en particulier lorsqu'un même appel peut être exécuté plusieurs fois (par exemple, des appels de fonction dans une boucle).

Quand l'expansion inline se produit

Chaque fonction entre dans l'une des deux catégories suivantes, concernant les appels à la fonction :

  • Ils peuvent être développés en ligne (la plupart des fonctions sont dans cette catégorie).
  • Ils ne peuvent pas être développés en ligne.

La plupart des fonctions appartiennent à la catégorie « peuvent » : leurs appels peuvent être développés en ligne si et quand cela s'avère bénéfique. Pour les fonctions de cette catégorie, un compilateur moderne évalue chaque fonction et chaque appel pour déterminer si cet appel particulier bénéficierait de l'expansion inline. Un compilateur peut décider de n'en développer aucun, certains, ou tous les appels d'une fonction donnée.

Remarque

Les compilateurs modernes optimisants décident eux-mêmes quand les fonctions doivent être développées en ligne.

Le type de fonction le plus courant qui ne peut pas être développé en ligne est celui dont la définition se trouve dans une autre unité de traduction. Comme le compilateur ne peut pas voir la définition d'une telle fonction, il ne sait pas par quoi remplacer l'appel !

Le mot-clé inline, historiquement

Historiquement, les compilateurs ne savaient pas toujours déterminer si l'expansion inline serait bénéfique, ou ne le faisaient pas très bien. C'est pourquoi le C++ a fourni le mot-clé inline, qui était à l'origine destiné à indiquer au compilateur qu'une fonction bénéficierait (probablement) d'être développée en ligne.

Une fonction déclarée avec le mot-clé inline est appelée une fonction inline.

Voici un exemple d'utilisation du mot-clé inline :

#include <iostream>

inline int min(int x, int y) // le mot-clé inline signifie que cette fonction est une fonction inline
{
    return (x < y) ? x : y;
}

int main()
{
    std::cout << min(5, 6) << '\n';
    std::cout << min(3, 2) << '\n';
    return 0;
}

Cependant, en C++ moderne, le mot-clé inline n'est plus utilisé pour demander l'expansion inline d'une fonction. Plusieurs raisons à cela :

  • Utiliser inline pour demander une expansion inline relève d'une optimisation prématurée, et un mauvais usage peut même nuire aux performances.
  • Le mot-clé inline n'est qu'une indication destinée à aider le compilateur à choisir où effectuer l'expansion inline. Le compilateur est totalement libre d'ignorer cette demande, et il le fait très souvent. Il est également libre d'effectuer l'expansion inline de fonctions qui n'utilisent pas le mot-clé inline, dans le cadre de son ensemble normal d'optimisations.
  • Le mot-clé inline est défini à un mauvais niveau de granularité. Nous l'utilisons sur une définition de fonction, alors que l'expansion inline se détermine pour chaque appel de fonction. Il peut être bénéfique de développer certains appels et néfaste d'en développer d'autres, et aucune syntaxe ne permet d'influer sur ce point.

Les compilateurs optimisants modernes savent généralement bien déterminer quels appels doivent être développés en ligne, souvent mieux que les humains. En conséquence, le compilateur ignorera probablement, ou dévaluera, toute utilisation de inline destinée à demander l'expansion inline de vos fonctions.

Bonne pratique

N'utilisez pas le mot-clé inline pour demander l'expansion inline de vos fonctions.

Le mot-clé inline, aujourd'hui

Dans les chapitres précédents, nous avons indiqué qu'il ne faut pas implémenter des fonctions (à liaison externe) dans des fichiers d'en-tête, car lorsque ces en-têtes sont inclus dans plusieurs fichiers .cpp, la définition de la fonction est copiée dans plusieurs fichiers .cpp. Ces fichiers sont ensuite compilés, et l'éditeur de liens (linker) signale une erreur, car il constate que vous avez défini la même fonction plus d'une fois, ce qui viole la règle de la définition unique (ODR).

En C++ moderne, le terme inline a évolué pour signifier « les définitions multiples sont autorisées ». Ainsi, une fonction inline est une fonction qui peut être définie dans plusieurs unités de traduction sans violer la règle ODR.

Les fonctions inline ont deux exigences principales :

  • Le compilateur doit pouvoir voir la définition complète d'une fonction inline dans chaque unité de traduction où la fonction est utilisée (une déclaration anticipée ne suffit pas à elle seule). Une seule telle définition peut apparaître par unité de traduction, sans quoi une erreur de compilation se produit.
  • La définition peut apparaître après le point d'utilisation si une déclaration anticipée est également fournie. Cependant, le compilateur ne pourra probablement pas effectuer l'expansion inline avant d'avoir vu la définition (donc les utilisations situées entre la déclaration et la définition ne seront probablement pas candidates à l'expansion inline).
  • Toutes les définitions d'une fonction inline (à liaison externe, ce qui est le cas par défaut des fonctions) doivent être identiques, sans quoi il en résulte un comportement indéfini.

Règle

Le compilateur doit pouvoir voir la définition complète d'une fonction inline partout où elle est utilisée, et toutes les définitions d'une fonction inline (à liaison externe) doivent être identiques (sans quoi il en résulte un comportement indéfini).

Contenu associé

Nous traitons de la liaison interne dans la leçon 7.6 -- Internal linkage et de la liaison externe dans la leçon 7.7 -- External linkage and variable forward declarations.

L'éditeur de liens consolide toutes les définitions de fonctions inline pour un identifiant en une seule définition (en respectant ainsi la règle de la définition unique).

Voici un exemple :

main.cpp :

#include <iostream>

double circumference(double radius); // déclaration anticipée

inline double pi() { return 3.14159; }

int main()
{
    std::cout << pi() << '\n';
    std::cout << circumference(2.0) << '\n';

    return 0;
}

math.cpp

inline double pi() { return 3.14159; }

double circumference(double radius)
{
    return 2.0 * pi() * radius;
}

Remarquez que les deux fichiers contiennent une définition de la fonction pi(). Cependant, comme cette fonction est marquée inline, c'est acceptable, et l'éditeur de liens les fusionnera. Si vous retirez le mot-clé inline des deux définitions de pi(), vous obtiendrez une violation de la règle ODR (les définitions multiples de fonctions non inline sont interdites).

Lecture facultative

Bien que l'usage historique de inline (pour effectuer l'expansion inline) et l'usage moderne (pour autoriser les définitions multiples) puissent sembler un peu sans rapport, ils sont très étroitement liés.

Historiquement, supposons que nous ayons une fonction triviale qui se prête parfaitement à l'expansion inline, nous la marquons donc inline. Pour pouvoir réellement développer un appel de cette fonction en ligne, le compilateur doit voir la définition complète de cette fonction dans chaque unité de traduction où elle est utilisée, sans quoi il ne saurait pas par quoi remplacer chaque appel. Une fonction définie dans une autre unité de traduction ne peut pas être développée en ligne dans l'unité de traduction en cours de compilation.

Il est courant que de petites fonctions inline triviales soient nécessaires dans plusieurs unités de traduction. Mais dès que nous copions la définition de la fonction dans chaque unité de traduction (conformément à l'exigence précédente), nous violons la règle ODR qui impose une seule définition par programme. La meilleure solution à ce problème a été de dispenser les fonctions inline de cette exigence de l'ODR.

Ainsi, historiquement, nous utilisions inline pour demander l'expansion inline, et l'exemption vis-à-vis de l'ODR était un détail nécessaire pour que ces fonctions puissent être développées en ligne à travers plusieurs unités de traduction. Aujourd'hui, nous utilisons inline pour l'exemption vis-à-vis de l'ODR, et nous laissons le compilateur gérer l'expansion inline. Le fonctionnement mécanique des fonctions inline n'a pas changé, c'est notre point de vue qui a changé.

Vous vous demandez peut-être pourquoi les fonctions inline ont pu être exemptées de l'ODR alors que les fonctions non inline doivent toujours respecter cette partie de la règle. Pour les fonctions non inline, on attend qu'une fonction soit définie exactement une fois (dans une seule unité de traduction). Si l'éditeur de liens rencontre plusieurs définitions d'une fonction non inline, il suppose qu'il s'agit d'un conflit de noms entre deux fonctions définies indépendamment. Et tout appel à une fonction non inline ayant plus d'une définition conduirait à une ambiguïté quant à la définition correcte à appeler. Mais avec les fonctions inline, toutes les définitions sont considérées comme étant celles de la même fonction inline, donc les appels à cette fonction dans l'unité de traduction peuvent être développés en ligne. Et si un appel n'est pas développé en ligne, il n'y a aucune ambiguïté quant à la définition à laquelle il correspond : n'importe laquelle convient !

Les fonctions inline sont généralement définies dans des fichiers d'en-tête, qui peuvent être inclus avec #include en tête de tout fichier de code ayant besoin de voir la définition complète de l'identifiant. Cela garantit que toutes les définitions inline d'un identifiant sont identiques.

pi.h :

#ifndef PI_H
#define PI_H

inline double pi() { return 3.14159; }

#endif

main.cpp :

#include "pi.h" // une copie de pi() sera incluse ici
#include <iostream>

double circumference(double radius); // déclaration anticipée

int main()
{
    std::cout << pi() << '\n';
    std::cout << circumference(2.0) << '\n';

    return 0;
}

math.cpp

#include "pi.h" // une copie de pi() sera incluse ici

double circumference(double radius)
{
    return 2.0 * pi() * radius;
}

Ceci est particulièrement utile pour les bibliothèques en-tête seules (header-only libraries), c'est-à-dire un ou plusieurs fichiers d'en-tête implémentant une fonctionnalité (aucun fichier .cpp n'est inclus). Ces bibliothèques sont populaires, car il n'y a aucun fichier source à ajouter au projet pour les utiliser et rien à lier. Il suffit d'inclure l'en-tête avec #include, et vous pouvez ensuite l'utiliser.

Pour les lecteurs avancés

Les fonctions suivantes sont implicitement inline :

  • Les fonctions définies à l'intérieur d'une définition de classe, de structure ou d'union (14.3 -- Member functions).
  • Les fonctions constexpr / consteval (F.1 -- Constexpr functions).
  • Les fonctions instanciées implicitement à partir de modèles de fonctions (11.7 -- Function template instantiation).

Dans la plupart des cas, vous ne devriez pas marquer vos fonctions ou variables comme inline, sauf si vous les définissez dans un fichier d'en-tête (et qu'elles ne sont pas déjà implicitement inline).

Bonne pratique

Évitez d'utiliser le mot-clé inline sauf si vous avez une raison spécifique et convaincante de le faire (par exemple, si vous définissez ces fonctions ou variables dans un fichier d'en-tête).

Pourquoi ne pas rendre toutes les fonctions inline et les définir dans un fichier d'en-tête ?

Principalement parce que cela peut augmenter considérablement les temps de compilation.

Lorsqu'un en-tête contenant une fonction inline est inclus dans un fichier source, la définition de cette fonction est compilée dans le cadre de cette unité de traduction. Une fonction inline incluse dans 6 unités de traduction verra sa définition compilée 6 fois (avant que l'éditeur de liens ne fusionne les définitions). À l'inverse, une fonction définie dans un fichier source ne verra sa définition compilée qu'une seule fois, quel que soit le nombre d'unités de traduction où sa déclaration anticipée est incluse.

Ensuite, si une fonction définie dans un fichier source change, seul ce fichier source doit être recompilé. Lorsqu'une fonction inline située dans un fichier d'en-tête change, chaque fichier de code qui inclut cet en-tête (directement ou via un autre en-tête) doit être recompilé. Dans les grands projets, cela peut provoquer une cascade de recompilations et avoir un impact considérable.

Variables inline (C++17)

Dans l'exemple ci-dessus, pi() était écrit comme une fonction renvoyant une valeur constante. Il serait plus direct d'implémenter pi comme une variable (const). Cependant, avant C++17, cela présentait certains obstacles et inefficacités.

C++17 introduit les variables inline, qui sont des variables autorisées à être définies dans plusieurs fichiers. Les variables inline fonctionnent de façon similaire aux fonctions inline et ont les mêmes exigences (le compilateur doit pouvoir voir une définition complète et identique partout où la variable est utilisée).

Pour les lecteurs avancés

Les variables suivantes sont implicitement inline :

  • Les membres de données statiques constexpr 15.6 -- Static member variables.

Contrairement aux fonctions constexpr, les variables constexpr ne sont pas inline par défaut (à l'exception de celles mentionnées ci-dessus) !

Nous illustrerons un usage courant des variables inline dans la leçon 7.10 -- Sharing global constants across multiple files (using inline variables).
