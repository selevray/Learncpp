7.8 — Pourquoi les variables globales (non constantes) sont néfastes

Si vous demandiez à un programmeur chevronné un seul conseil sur les bonnes pratiques de programmation, après réflexion, la réponse la plus probable serait : « Évitez les variables globales ! ». Et c'est pour une bonne raison : les variables globales sont l'un des concepts du langage les plus abusés au fil de l'histoire. Bien qu'elles puissent sembler inoffensives dans les petits programmes académiques, elles posent souvent problème dans les programmes plus importants.

Les nouveaux programmeurs sont souvent tentés d'utiliser de nombreuses variables globales, car elles sont faciles à manipuler, surtout lorsque plusieurs appels à différentes fonctions sont impliqués (transmettre des données par les paramètres de fonctions est pénible). Cependant, c'est généralement une mauvaise idée. De nombreux développeurs pensent que les variables globales non constantes doivent être évitées complètement !

Mais avant d'expliquer pourquoi, il faut apporter une précision. Lorsque des développeurs affirment que les variables globales sont néfastes, ils ne parlent généralement pas de toutes les variables globales. Ils visent surtout les variables globales non constantes.

Pourquoi les variables globales (non constantes) sont néfastes

La raison de loin la plus importante pour laquelle les variables globales non constantes sont dangereuses tient au fait que leurs valeurs peuvent être modifiées par n'importe quelle fonction appelée, et qu'il n'existe pas de moyen simple pour le programmeur de savoir que cela va se produire. Considérez le programme suivant :

#include <iostream>

int g_mode; // déclare une variable globale (initialisée à zéro par défaut)

void doSomething()
{
    g_mode = 2; // affecte la valeur 2 à la variable globale g_mode
}

int main()
{
    g_mode = 1; // note : ceci affecte la valeur 1 à la variable globale g_mode. Ce n'est pas la déclaration d'une variable locale g_mode !

    doSomething();

    // Le programmeur s'attend toujours à ce que g_mode vaille 1
    // Mais doSomething l'a fait passer à 2 !

    if (g_mode == 1)
    {
        std::cout << "Aucune menace détectée.\n";
    }
    else
    {
        std::cout << "Lancement des missiles nucléaires...\n";
    }

    return 0;
}

Notez que le programmeur a affecté la valeur 1 à la variable g_mode, puis a appelé doSomething(). À moins que le programmeur ne sache explicitement que doSomething() allait modifier la valeur de g_mode, il ne s'attendait probablement pas à ce que doSomething() change cette valeur ! Par conséquent, la suite de main() ne fonctionne pas comme le programmeur l'attend (et le monde est anéanti).

En bref, les variables globales rendent l'état du programme imprévisible. Chaque appel de fonction devient potentiellement dangereux, et le programmeur n'a pas de moyen simple de savoir lesquels sont dangereux et lesquels ne le sont pas ! Les variables locales sont bien plus sûres, car les autres fonctions ne peuvent pas les modifier directement.

Il existe bien d'autres bonnes raisons de ne pas utiliser de globales non constantes.

Avec les variables globales, il n'est pas rare de trouver un code de ce type :

void someFunction()
{
    // code utile

    if (g_mode == 4)
    {
        // faire quelque chose de bien
    }
}

Après débogage, vous constatez que votre programme ne fonctionne pas correctement parce que g_mode vaut 3, et non 4. Comment corriger le problème ? Il faut maintenant trouver tous les endroits où g_mode pourrait valoir 3, et retracer comment cette valeur a été affectée au départ. Il est possible que cela se trouve dans un morceau de code totalement sans rapport !

L'une des raisons essentielles de déclarer les variables locales le plus près possible de l'endroit où elles sont utilisées est que cela minimise la quantité de code à parcourir pour comprendre le rôle de la variable. Les variables globales sont à l'extrême opposé : comme elles sont accessibles partout, il peut être nécessaire de parcourir tout le programme pour comprendre leur utilisation. Dans les petits programmes, cela peut ne pas poser de problème. Dans les grands, ce sera le cas.

Par exemple, vous pourriez constater que g_mode est référencée 442 fois dans votre programme. À moins que g_mode ne soit bien documentée, vous devrez potentiellement examiner chacune de ses utilisations pour comprendre comment elle est employée selon les cas, quelles sont ses valeurs valides et quel est son rôle global.

Les variables globales rendent aussi votre programme moins modulaire et moins flexible. Une fonction qui n'utilise que ses paramètres et n'a aucun effet de bord est parfaitement modulaire. La modularité facilite à la fois la compréhension de ce que fait un programme et la réutilisation du code. Les variables globales réduisent considérablement la modularité.

En particulier, évitez d'utiliser des variables globales pour les variables de « point de décision » importantes (c'est-à-dire les variables que vous utiliseriez dans une instruction conditionnelle, comme la variable g_mode de l'exemple ci-dessus). Votre programme risque peu de casser si une variable globale contenant une information secondaire change (par exemple le nom de l'utilisateur). Il est bien plus probable qu'il casse si vous modifiez une variable globale qui influence la façon dont le programme fonctionne réellement.

Bonne pratique

Utilisez des variables locales plutôt que des variables globales chaque fois que c'est possible.

Le problème de l'ordre d'initialisation des variables globales

L'initialisation des variables statiques (ce qui inclut les variables globales) a lieu lors du démarrage du programme, avant l'exécution de la fonction main. Elle se déroule en deux phases.

La première phase s'appelle initialisation statique (static initialization). Elle comporte elle-même deux sous-étapes :

  • Les variables globales dont l'initialiseur est constexpr (y compris les littéraux) sont initialisées avec ces valeurs. On parle d'initialisation constante (constant initialization).
  • Les variables globales sans initialiseur sont initialisées à zéro (zero-initialization). L'initialisation à zéro est considérée comme une forme d'initialisation statique, puisque 0 est une valeur constexpr.

La seconde phase s'appelle initialisation dynamique (dynamic initialization). Elle est plus complexe et plus nuancée, mais l'idée générale est que les variables globales dont l'initialiseur n'est pas constexpr sont initialisées à ce moment-là.

Voici un exemple d'initialiseur non constexpr :

int init()
{
    return 5;
}

int g_something{ init() }; // initialisation non constexpr

Dans un même fichier, pour chaque phase, les variables globales sont généralement initialisées dans l'ordre de leur définition (il existe quelques exceptions à cette règle pour la phase d'initialisation dynamique). Il faut donc veiller à ne pas faire dépendre une variable de la valeur d'initialisation d'une autre variable qui ne sera initialisée que plus tard. Par exemple :

#include <iostream>

int initX();  // déclaration anticipée
int initY();  // déclaration anticipée

int g_x{ initX() }; // g_x est initialisée en premier
int g_y{ initY() };

int initX()
{
    return g_y; // g_y n'est pas encore initialisée au moment de cet appel
}

int initY()
{
    return 5;
}

int main()
{
    std::cout << g_x << ' ' << g_y << '\n';
}

Ce programme affiche :


0 5

Plus problématique encore, l'ordre d'initialisation des objets statiques entre différentes unités de traduction est indéterminé.

Étant donné deux fichiers, a.cpp et b.cpp, l'un ou l'autre peut voir ses variables globales initialisées en premier. Si une variable à durée de stockage statique de a.cpp est initialisée à partir d'une variable à durée statique définie dans b.cpp, il y a 50 % de chances que la variable de b.cpp ne soit pas encore initialisée.

Terminologie

L'indétermination de l'ordre d'initialisation des objets à durée de stockage statique situés dans des unités de traduction différentes est souvent appelée static initialization order fiasco.

Attention

Évitez d'initialiser des objets à durée statique à l'aide d'autres objets à durée statique provenant d'une autre unité de traduction.

L'initialisation dynamique des variables globales est également sujette à des problèmes d'ordre d'initialisation et doit être évitée chaque fois que c'est possible.

Alors, quelles sont les très bonnes raisons d'utiliser des variables globales non constantes ?

Il n'y en a pas beaucoup. Dans la plupart des cas, il est préférable d'utiliser des variables locales et de les passer en arguments aux autres fonctions. Mais dans certains cas, un usage judicieux de variables globales non constantes peut effectivement réduire la complexité du programme, et dans ces rares cas, leur usage peut être préférable aux alternatives.

Un bon exemple est un fichier journal, dans lequel on peut écrire des informations d'erreur ou de débogage. Il est sans doute pertinent de le définir comme globale, car vous n'aurez probablement qu'un seul journal dans le programme, qui sera utilisé presque partout. Un autre bon exemple est un générateur de nombres aléatoires (nous en montrons un exemple dans la leçon 8.15 -- Nombres aléatoires globaux (Random.h)).

Pour information, les objets std::cout et std::cin sont eux-mêmes implémentés comme des variables globales (dans l'espace de noms std).

En règle générale, toute utilisation d'une variable globale doit satisfaire au moins les deux critères suivants : il ne doit exister qu'une seule instance de ce que représente la variable dans le programme, et son utilisation doit être omniprésente dans le programme.

De nombreux nouveaux programmeurs commettent l'erreur de penser qu'une chose peut être implémentée comme globale parce qu'une seule est nécessaire pour le moment. Par exemple, vous pourriez penser que, comme vous réalisez un jeu à un seul joueur, vous n'avez besoin que d'un seul joueur. Mais que se passera-t-il plus tard si vous voulez ajouter un mode multijoueur (versus ou hotseat) ?

Se protéger de la destruction globale

Si vous trouvez tout de même une bonne utilisation pour une variable globale non constante, quelques conseils utiles permettent de limiter les ennuis. Ces conseils ne concernent pas seulement les variables globales non constantes, ils peuvent aider avec toutes les variables globales.

Tout d'abord, préfixez toutes les variables globales sans espace de noms par « g » ou « g_ », ou mieux encore, placez-les dans un espace de noms (abordé dans la leçon 7.2 -- Espaces de noms définis par l'utilisateur et opérateur de résolution de portée), afin de réduire le risque de collisions de noms.

Par exemple, au lieu de :

#include <iostream>

constexpr double gravity { 9.8 }; // risque de collision avec une autre variable globale nommée gravity

int main()
{
    std::cout << gravity << '\n'; // on ne sait pas, à partir du nom seul, s'il s'agit d'une variable locale ou globale

    return 0;
}

Faites plutôt ceci :

#include <iostream>

namespace constants
{
    constexpr double gravity { 9.8 }; // n'entrera pas en collision avec d'autres variables globales nommées gravity
}

int main()
{
    std::cout << constants::gravity << '\n'; // il est clair qu'il s'agit d'une variable globale (puisque les espaces de noms sont globaux)

    return 0;
}

Ensuite, plutôt que d'autoriser un accès direct à la variable globale, il est préférable d'« encapsuler » la variable. Assurez-vous que la variable ne soit accessible que depuis le fichier dans lequel elle est déclarée, par exemple en la rendant static ou const, puis fournissez des « fonctions d'accès » globales externes pour manipuler la variable. Ces fonctions peuvent garantir que l'utilisation reste correcte (par exemple en effectuant une validation des entrées, un contrôle de bornes, etc.). De plus, si vous décidez un jour de changer l'implémentation sous-jacente (par exemple passer d'une base de données à une autre), vous n'aurez à modifier que les fonctions d'accès, au lieu de chaque portion de code qui utilise directement la variable globale.

Par exemple, au lieu de ceci :

constants.cpp :

namespace constants
{
    extern const double gravity { 9.8 }; // possède une liaison externe, accessible depuis d'autres fichiers
}

main.cpp :

#include <iostream>

namespace constants
{
    extern const double gravity; // déclaration anticipée
}

int main()
{
    std::cout << constants::gravity << '\n'; // accès direct à la variable globale

    return 0;
}

Faites plutôt ceci :

constants.cpp :

namespace constants
{
    constexpr double gravity { 9.8 }; // possède une liaison interne, n'est accessible que dans ce fichier
}

double getGravity() // possède une liaison externe, accessible depuis d'autres fichiers
{
    // On pourra ajouter ici de la logique si besoin
    // ou changer l'implémentation de façon transparente pour les appelants
    return constants::gravity;
}

main.cpp :

#include <iostream>

double getGravity(); // déclaration anticipée

int main()
{
    std::cout << getGravity() << '\n';

    return 0;
}

Rappel

Les variables globales const ont par défaut une liaison interne, gravity n'a donc pas besoin d'être static.

Troisièmement, lorsque vous écrivez une fonction autonome qui utilise la variable globale, n'utilisez pas directement la variable dans le corps de la fonction. Passez-la plutôt en argument. Ainsi, si votre fonction doit un jour utiliser une valeur différente dans certaines circonstances, il vous suffit de changer l'argument. Cela contribue à préserver la modularité.

Au lieu de :

#include <iostream>

namespace constants
{
    constexpr double gravity { 9.8 };
}

// Cette fonction n'est utile que pour calculer la vitesse instantanée à partir de la gravité globale
double instantVelocity(int time)
{
    return constants::gravity * time;
}

int main()
{
    std::cout << instantVelocity(5) << '\n';

    return 0;

}

Faites plutôt ceci :

#include <iostream>

namespace constants
{
    constexpr double gravity { 9.8 };
}

// Cette fonction peut calculer la vitesse instantanée pour n'importe quelle valeur de gravité (plus utile)
double instantVelocity(int time, double gravity)
{
    return gravity * time;
}

int main()
{
    std::cout << instantVelocity(5, constants::gravity) << '\n'; // on transmet notre constante à la fonction en tant que paramètre

    return 0;
}
