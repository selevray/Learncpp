A.4 — FAQ C++

Certaines questions reviennent sans cesse. Cette FAQ tente de répondre aux plus courantes.

Q1 : Pourquoi ne faut-il pas utiliser « using namespace std » ?

L'instruction using namespace std; est une directive using (using-directive). Une directive using permet d'accéder à tous les identifiants d'un espace de noms donné à l'intérieur de la portée de cette directive.

Vous avez peut-être déjà vu quelque chose comme ceci :

#include <iostream>

using namespace std;

int main()
{
    cout << "Hello world!";

    return 0;
}

Cela nous permet d'utiliser les noms de l'espace de noms std sans avoir à écrire std:: encore et encore. Dans le programme ci-dessus, nous pouvons simplement écrire cout au lieu de std::cout. Cela paraît formidable, non ?

Cependant, lorsque le compilateur rencontre using namespace std, il rend disponible dans la portée globale (puisque c'est là que la directive est placée) chaque identifiant de l'espace de noms std. Cela pose 3 problèmes majeurs :

  • Le risque de collision de noms entre un nom que vous avez choisi et un nom déjà présent dans l'espace de noms std augmente considérablement.
  • Les nouvelles versions de la bibliothèque standard peuvent casser votre programme qui fonctionne actuellement. Ces versions futures pourraient introduire de nouveaux noms provoquant de nouvelles collisions ou, au pire, le comportement de votre programme pourrait changer silencieusement et de façon inattendue !
  • L'absence de préfixe std:: rend plus difficile pour le lecteur la distinction entre un nom de la bibliothèque standard et un nom défini par l'utilisateur.

Pour ces raisons, nous recommandons d'éviter complètement using namespace std (ou toute autre directive using). La petite économie de frappe ne vaut pas les maux de tête supplémentaires et les risques futurs.

Q2 : Pourquoi puis-je utiliser une fonction ou un type sans inclure l'en-tête qui le déclare ?

Par exemple, de nombreux lecteurs demandent pourquoi leur programme qui utilise std::string_view doit #include <string_view> alors qu'il semble fonctionner sans cette directive #include.

Les en-têtes peuvent eux-mêmes inclure d'autres en-têtes. Lorsque vous incluez un en-tête, vous obtenez aussi tous les en-têtes supplémentaires qu'il inclut (et tous ceux que ces derniers incluent à leur tour). Les en-têtes supplémentaires qui arrivent ainsi sans que vous les ayez explicitement inclus sont appelés « inclusions transitives » (transitive includes).

Dans votre fichier main.cpp, vous incluez probablement #include <iostream>. Avec votre compilateur, si l'en-tête <iostream> inclut l'en-tête <string_view> (pour son propre usage), alors en incluant <iostream> vous obtenez le contenu de <string_view> (ainsi que celui de tous les autres en-têtes inclus par <iostream>). Cela signifie que votre main.cpp peut utiliser le type std::string_view sans inclure explicitement <string_view>.

Même si cela compile avec votre compilateur, vous ne devez pas vous y fier. Ce qui compile chez vous aujourd'hui peut ne pas compiler avec un autre compilateur, ou même avec une version future du vôtre.

Il n'existe aucun moyen de signaler ce phénomène ni de l'empêcher. Le mieux que vous puissiez faire est de veiller à inclure explicitement les bons en-têtes pour tout ce que vous utilisez. Compiler votre programme avec plusieurs compilateurs différents peut aider à repérer les en-têtes inclus de façon transitive sur d'autres compilateurs.

Q3 : Mon code qui provoque un comportement indéfini semble fonctionner correctement. Est-ce acceptable ?

Alias : « J'ai fait ce que vous m'aviez dit de ne pas faire, et ça a marché. Quel est le problème ? »

Un comportement indéfini (undefined behavior) survient lorsque vous effectuez une opération dont le comportement n'est pas défini par le langage C++. Le code qui provoque un comportement indéfini peut présenter n'importe lequel des symptômes suivants :

  • Votre programme produit un résultat différent à chaque exécution.
  • Votre programme se comporte de façon incohérente (parfois il produit le résultat voulu, parfois non).
  • Votre programme produit systématiquement le même résultat incorrect.
  • Votre programme semble d'abord fonctionner, mais produit un résultat incorrect plus loin dans le programme.
  • Votre programme plante, immédiatement ou plus tard.
  • Votre programme fonctionne sur certains compilateurs ou plateformes mais pas sur d'autres.
  • Votre programme fonctionne jusqu'à ce que vous modifiiez un autre code apparemment sans rapport.
  • Votre programme semble tout de même produire le résultat voulu.

L'un des plus gros problèmes du comportement indéfini est que le comportement manifesté par le programme peut changer à tout moment, pour n'importe quelle raison. Ainsi, un tel code peut sembler fonctionner aujourd'hui, mais rien ne garantit qu'il fonctionnera encore lors d'une exécution ultérieure.

Q4 : Pourquoi mon code qui provoque un comportement indéfini produit-il un certain résultat ?

Les lecteurs demandent souvent ce qui se passe pour produire un résultat précis sur leur système. Dans la plupart des cas, il est difficile de le dire, car le résultat peut dépendre de l'état courant du programme, des options de votre compilateur, de la façon dont le compilateur implémente une fonctionnalité, de l'architecture de l'ordinateur et/ou du système d'exploitation. Par exemple, si vous affichez la valeur d'une variable non initialisée, vous pouvez obtenir des valeurs aléatoires, ou toujours une valeur particulière. Cela dépend du type de la variable, de la façon dont le compilateur dispose la variable en mémoire, et de ce qui se trouvait précédemment dans cette mémoire (ce qui peut être influencé par le système d'exploitation ou par l'état du programme jusqu'à ce point).

Une telle réponse peut être intéressante d'un point de vue mécanique, mais elle est rarement utile en pratique (et susceptible de changer dès que quelque chose d'autre change). C'est comme demander : « Quand je passe ma ceinture de sécurité dans le volant et que je la relie à l'accélérateur, pourquoi la voiture part-elle à gauche quand je tourne la tête un jour de pluie ? » La meilleure réponse n'est pas une explication physique de ce qui se produit, c'est : « Ne faites pas ça ».

Q5 : Pourquoi ai-je une erreur de compilation lorsque j'essaie de compiler un exemple qui devrait fonctionner ?

La cause la plus fréquente est que votre projet est compilé avec la mauvaise norme du langage.

C++ introduit de nombreuses nouvelles fonctionnalités avec chaque nouvelle norme. Si l'un de nos exemples utilise une fonctionnalité introduite en C++17, mais que votre programme est compilé selon la norme C++14, il ne compilera probablement pas, car la fonctionnalité utilisée n'est pas prise en charge par la norme choisie.

Essayez de configurer votre norme de langage sur la dernière version prise en charge par votre compilateur, et voyez si cela résout le problème. Vous pouvez aussi vérifier que votre compilateur est bien configuré pour la norme attendue en exécutant le programme présenté ici : 0.13 -- Quelle norme du langage mon compilateur utilise-t-il ?.

Q6 : Pourquoi devrais-je faire #include « foo.h » depuis foo.cpp ?

C'est une bonne pratique pour un fichier source (par exemple foo.cpp) d'inclure son en-tête associé (par exemple foo.h). Dans de nombreux cas, foo.h contient des définitions dont foo.cpp a besoin pour compiler correctement.

Cependant, même si foo.cpp compile sans foo.h, inclure l'en-tête associé permet au compilateur de détecter certains types d'incohérences entre les deux fichiers (par exemple lorsque le type de retour d'une fonction ne correspond pas à celui de sa déclaration anticipée). Sans cette inclusion, cela pourrait provoquer un comportement indéfini.

Le coût de la directive #include est négligeable, il y a donc peu d'inconvénients à inclure l'en-tête.

Q7 : Pourquoi mon projet ne compile-t-il que lorsque j'utilise #include « foo.cpp » dans « main.cpp » ?

Cela est presque toujours dû à un oubli d'ajouter foo.cpp au projet et/ou à la ligne de commande de compilation. Mettez à jour votre projet et/ou votre ligne de commande pour inclure chaque fichier source (.cpp). Lorsque vous compilez votre projet, vous devriez voir chaque fichier source être compilé.

Normalement, dans un projet comportant plusieurs fichiers, le compilateur compile chaque fichier source (.cpp) individuellement. Une fois tous les fichiers sources compilés, l'éditeur de liens (linker) les relie et crée le fichier de sortie (par exemple un exécutable). En revanche, si vous répartissez votre code entre deux fichiers ou plus (par exemple main.cpp et foo.cpp) et ne compilez que main.cpp, vous obtiendrez probablement une erreur de compilation ou d'édition de liens, car une partie du code nécessaire au projet n'est pas compilée.

Les programmeurs débutants découvrent parfois qu'ils peuvent faire fonctionner leur programme en ajoutant #include "foo.cpp" dans main.cpp, au lieu d'ajouter foo.cpp au projet ou à la ligne de commande. Dans ce cas, lorsque main.cpp est compilé, le préprocesseur crée une unité de traduction (translation unit) constituée du code de foo.cpp et de main.cpp, qui est ensuite compilée et liée. Dans les petits projets, cela peut fonctionner. Alors pourquoi ne pas le faire ?

Il y a plusieurs raisons :

  1. Cela peut provoquer des collisions de noms entre fichiers.
  2. Il peut être difficile d'éviter les violations de la règle de définition unique (ODR).
  3. Toute modification d'un fichier .cpp entraîne la recompilation de l'ensemble du projet. Cela peut prendre beaucoup de temps.

Q8 : Pourquoi dois-je écrire return 0 à la fin de main ?

Vous n'en avez pas besoin. La fonction main() est particulière : elle retourne implicitement 0 si vous ne fournissez pas d'instruction return.

En revanche, toute autre fonction renvoyant une valeur qui atteint la fin de son corps sans rencontrer d'instruction return provoque un comportement indéfini.

Par cohérence, nous recommandons de retourner explicitement 0 depuis main(). Mais si vous préférez omettre l'instruction return dans main() pour être plus concis, vous le pouvez. Veillez simplement à ne pas croire que les autres fonctions renvoyant une valeur fonctionnent de la même façon.

Q9 : Lorsque je compile un exemple de ce site, j'obtiens une erreur du type « argument list for class template XXX is missing ». Pourquoi ?

La raison la plus probable est que l'exemple utilise une fonctionnalité appelée déduction des arguments de modèle de classe (Class Template Argument Deduction, CTAD), qui est une fonctionnalité de C++17. De nombreux compilateurs sont configurés par défaut sur C++14, qui ne prend pas en charge cette fonctionnalité.

Si le programme suivant ne compile pas chez vous, c'est la raison :

#include <utility> // for std::pair

int main()
{
    std::pair p2{ 1, 2 }; // CTAD used to deduce std::pair<int, int> from the initializers (C++17)

    return 0;
}

Q10 : Pourquoi ne met-on pas const sur les paramètres de fonction ou les types de retour lors d'un passage ou d'un retour par valeur ?

On n'utilise généralement pas const sur les paramètres passés par valeur, car :

  • Rendre ces paramètres const n'apporte aucun avantage réel à l'appelant de la fonction, mais alourdit l'interface de la fonction.
  • Nous ne nous soucions généralement pas du fait que la fonction modifie ces paramètres, puisqu'il s'agit de copies qui seront de toute façon détruites à la fin de la fonction.

On n'utilise pas non plus const sur les valeurs de retour passées par valeur, car :

  • Si le type de retour n'est pas un type classe (par exemple un type fondamental), le const sera de toute façon ignoré.
  • Si le type de retour est un type classe, const peut empêcher certains types d'optimisations (par exemple la sémantique de déplacement).

Remarque : const est pertinent lorsque l'on passe ou retourne par adresse ou par référence.

Q11 : Pourquoi devrais-je utiliser constexpr ?

constexpr et les autres techniques de programmation à la compilation offrent de nombreux avantages, notamment :

  • Un code plus petit et plus rapide.
  • Le compilateur peut détecter certains types d'erreurs et interrompre la compilation si elles surviennent.
  • Le comportement indéfini n'est pas autorisé à la compilation.
  • La possibilité d'utiliser des variables et des fonctions aux endroits où une expression constante est requise.

Le dernier point est peut-être le plus incontournable, car certaines fonctionnalités de C++ exigent des valeurs connues à la compilation.

Q12 : Pourquoi rendre constexpr une fonction éligible alors que je sais qu'elle ne sera évaluée qu'à l'exécution ?

Il y a plusieurs raisons possibles :

  1. Utiliser constexpr présente peu d'inconvénients, et peut aider le compilateur à optimiser même dans des contextes où la fonction n'est pas évaluée à la compilation.
  2. Ne pas appeler la fonction dans un contexte évaluable à la compilation aujourd'hui ne signifie pas que vous ne le ferez pas demain, lorsque vous modifierez ou étendrez votre programme. Et si vous n'avez pas déjà déclaré la fonction constexpr, vous n'y penserez peut-être pas quand vous l'utiliserez dans un tel contexte, et vous passerez alors à côté des gains de performance. Ou vous serez peut-être contraint de la rendre constexpr plus tard, lorsque vous aurez besoin de sa valeur de retour dans un contexte exigeant une expression constante.
  3. La répétition aide à ancrer les bonnes pratiques.

Dans un projet non trivial, il est judicieux de concevoir vos fonctions en gardant à l'esprit qu'elles pourront être réutilisées ou étendues à l'avenir. Chaque modification d'une fonction existante risque de la casser, ce qui impose de la retester, une tâche qui prend du temps et de l'énergie. Il vaut souvent la peine de consacrer une minute ou deux supplémentaires à « bien faire dès la première fois », pour ne pas avoir à la refaire (et la retester) plus tard.

Q13 : Pourquoi ne faut-il pas appeler plusieurs fois la même fonction de saisie dans une même expression ?

Dans la plupart des cas, la norme C++ ne précise pas l'ordre dans lequel les opérandes (y compris les arguments de fonction) sont évalués. La priorité et l'associativité des opérateurs ne servent qu'à déterminer comment les opérandes sont regroupés avec les opérateurs, ainsi que l'ordre du calcul des valeurs.

Par exemple, avec l'instruction std::cout << subtract(getUserInput(), getUserInput()), l'argument de gauche ou celui de droite dans l'appel à subtract() peut être évalué en premier. Supposons que l'utilisateur saisisse les valeurs 5 et 2. Si l'argument de gauche est évalué en premier, il vaut 5, et l'argument de droite vaut 2. 5 - 2 vaut 3. Si l'argument de droite est évalué en premier, il vaut 5, et celui de gauche vaut 2. 2 - 5 vaut -3. Ainsi, cette instruction peut afficher 3 ou -3.

Pour lever cette ambiguïté, il suffit de placer chaque appel à getUserInput() dans une instruction séparée (l'ordre est alors déterminé), et de stocker la valeur de retour dans une variable jusqu'à ce qu'elle soit nécessaire.

Q14 : Il n'y a pas assez de quiz ! Où puis-je trouver davantage d'exercices ?

Nous recommandons https://www.codewars.com/, qui propose de nombreux exercices courts pour améliorer vos compétences générales de résolution de problèmes et d'implémentation en C++. C'est aussi amusant !

Une fois que vous avez une solution, vous pouvez la comparer avec celles des autres pour découvrir d'autres approches, ou repérer les améliorations possibles de votre propre code.

Cependant, comme les exercices jetables ont des corrigés jetables, résoudre ce type de quiz n'encourage pas vraiment l'écriture de code de haute qualité, et ne montre pas ce qui se passe lorsqu'on ne suit pas les bonnes pratiques. Pour cela, rien ne vaut la création de votre propre projet.

Commencez par quelque chose de petit : un jeu simple ou une simulation. Ajoutez ensuite des fonctionnalités au fil du temps. À mesure que la complexité de votre projet augmente, vous verrez apparaître les différentes faiblesses de votre code. Cela vous aidera à identifier les parties de votre code qui ont besoin d'améliorations de qualité.
