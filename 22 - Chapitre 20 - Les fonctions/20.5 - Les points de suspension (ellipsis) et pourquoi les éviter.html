20.5 — Les points de suspension (ellipsis) et pourquoi les éviter

Dans toutes les fonctions que nous avons vues jusqu'à présent, le nombre de paramètres qu'une fonction accepte doit être connu à l'avance (même s'ils possèdent des valeurs par défaut). Cependant, il existe certains cas où il peut être utile de pouvoir passer un nombre variable de paramètres à une fonction. C++ fournit un spécificateur particulier, connu sous le nom d'ellipsis (ou « ... »), qui permet de faire exactement cela.

Comme les ellipsis sont rarement utilisées, potentiellement dangereuses, et que nous recommandons de les éviter, cette section peut être considérée comme une lecture facultative.

Les fonctions qui utilisent une ellipsis ont la forme suivante :


type_de_retour nom_de_fonction(liste_d_arguments, ...)

La liste_d_arguments est constituée d'un ou plusieurs paramètres de fonction normaux. Notez que les fonctions qui utilisent une ellipsis doivent posséder au moins un paramètre qui n'est pas une ellipsis. Les arguments passés à la fonction doivent d'abord correspondre aux paramètres de la liste_d_arguments.

L'ellipsis (qui s'écrit sous la forme de trois points consécutifs) doit toujours être le dernier paramètre de la fonction. Elle capture les arguments supplémentaires éventuels. Bien que ce ne soit pas tout à fait exact, il est utile conceptuellement de considérer l'ellipsis comme un tableau qui contient les paramètres supplémentaires au-delà de ceux de la liste_d_arguments.

Un exemple avec ellipsis

La meilleure façon d'apprendre les ellipsis est de passer par un exemple. Écrivons donc un programme simple qui utilise une ellipsis. Supposons que nous voulions écrire une fonction qui calcule la moyenne d'un ensemble d'entiers. Nous procéderions ainsi :

#include <iostream>
#include <cstdarg> // nécessaire pour utiliser une ellipsis

// L'ellipsis doit être le dernier paramètre
// count est le nombre d'arguments supplémentaires que nous passons
double findAverage(int count, ...)
{
    int sum{ 0 };

    // Nous accédons à l'ellipsis à travers une va_list, déclarons donc une va_list
    std::va_list list;

    // Nous initialisons la va_list avec va_start. Le premier argument est
    // la liste à initialiser. Le second argument est le dernier paramètre
    // qui n'est pas une ellipsis.
    va_start(list, count);

    // Parcourir toutes les valeurs de l'ellipsis
    for (int arg{ 0 }; arg < count; ++arg)
    {
         // Nous utilisons va_arg pour extraire des valeurs de l'ellipsis
         // Le premier argument est la va_list utilisée
         // Le second argument est le type de la valeur
         sum += va_arg(list, int);
    }

    // Nettoyer la va_list lorsque nous avons terminé.
    va_end(list);

    return static_cast<double>(sum) / count;
}

int main()
{
    std::cout << findAverage(5, 1, 2, 3, 4, 5) << '\n';
    std::cout << findAverage(6, 1, 2, 3, 4, 5, 6) << '\n';

    return 0;
}

Ce code affiche :


3
3.5

Comme vous pouvez le voir, cette fonction accepte un nombre variable de paramètres ! Examinons maintenant les composants de cet exemple.

Tout d'abord, nous devons inclure l'en-tête cstdarg. Cet en-tête définit va_list, va_arg, va_start et va_end, qui sont des macros nécessaires pour accéder aux paramètres faisant partie de l'ellipsis.

Nous déclarons ensuite notre fonction qui utilise l'ellipsis. Rappelez-vous que la liste d'arguments doit contenir un ou plusieurs paramètres fixes. Ici, nous passons un seul entier qui indique combien de nombres il faut moyenner. L'ellipsis vient toujours en dernier.

Notez que le paramètre ellipsis n'a pas de nom ! Nous accédons plutôt aux valeurs de l'ellipsis par l'intermédiaire d'un type spécial appelé va_list. Il est utile conceptuellement de considérer va_list comme un pointeur qui pointe vers le tableau de l'ellipsis. Nous commençons donc par déclarer une va_list, que nous avons nommée « list » par simplicité.

La prochaine étape consiste à faire pointer list vers nos paramètres de l'ellipsis. Pour cela, nous appelons va_start(). va_start() prend deux paramètres : la va_list elle-même, et le nom du dernier paramètre de la fonction qui n'est pas une ellipsis. Une fois va_start() appelée, va_list pointe vers le premier paramètre de l'ellipsis.

Pour obtenir la valeur du paramètre vers lequel va_list pointe actuellement, nous utilisons va_arg(). va_arg() prend également deux paramètres : la va_list elle-même, et le type du paramètre auquel nous essayons d'accéder. Notez que va_arg() déplace aussi va_list vers le paramètre suivant de l'ellipsis !

Enfin, pour nettoyer lorsque nous avons terminé, nous appelons va_end(), avec va_list comme paramètre.

Notez que va_start() peut être appelée à nouveau à tout moment pour réinitialiser va_list afin qu'elle pointe de nouveau vers le premier paramètre de l'ellipsis.

Pourquoi les ellipsis sont dangereuses : la vérification de type est suspendue

Les ellipsis offrent au programmeur une grande souplesse pour implémenter des fonctions qui acceptent un nombre variable de paramètres. Cependant, cette souplesse a quelques inconvénients.

Avec les paramètres de fonction ordinaires, le compilateur utilise la vérification de type pour s'assurer que les types des arguments correspondent aux types des paramètres (ou peuvent être convertis implicitement pour correspondre). Cela permet d'éviter de passer à une fonction un entier alors qu'elle attend une chaîne, ou l'inverse. Cependant, notez que les paramètres ellipsis n'ont aucune déclaration de type. Lorsqu'on utilise une ellipsis, le compilateur suspend complètement la vérification de type pour ces paramètres. Cela signifie qu'il est possible d'envoyer des arguments de n'importe quel type à l'ellipsis ! L'inconvénient est que le compilateur ne peut plus vous avertir si vous appelez la fonction avec des arguments ellipsis qui n'ont pas de sens. Lorsqu'on utilise l'ellipsis, il appartient entièrement à l'appelant de s'assurer que la fonction est appelée avec des arguments que celle-ci sait traiter. Cela laisse évidemment une grande place aux erreurs (surtout si l'appelant n'est pas celui qui a écrit la fonction).

Examinons un exemple d'erreur assez subtile :

    std::cout << findAverage(6, 1.0, 2, 3, 4, 5, 6) << '\n';

Bien que cela semble anodin à première vue, notez que le deuxième argument (le premier argument de l'ellipsis) est un double et non un entier. Cela compile sans problème et produit un résultat plutôt surprenant :


1.78782e+008

soit un nombre VRAIMENT énorme. Comment cela s'est-il produit ?

Comme vous l'avez appris dans les leçons précédentes, un ordinateur stocke toutes les données sous forme de suites de bits. Le type d'une variable indique à l'ordinateur comment interpréter cette suite de bits pour en tirer une valeur significative. Or, vous venez d'apprendre que l'ellipsis élimine le type des variables ! Par conséquent, la seule façon d'obtenir une valeur exploitable depuis l'ellipsis est d'indiquer manuellement à va_arg() quel est le type attendu du prochain paramètre. C'est précisément le rôle du second paramètre de va_arg(). Si le type réel du paramètre ne correspond pas au type attendu, de mauvaises choses se produisent généralement.

Dans le programme findAverage ci-dessus, nous avons indiqué à va_arg() que nos variables devaient toutes être de type int. Par conséquent, chaque appel à va_arg() renvoie la prochaine suite de bits interprétée comme un entier.

Dans ce cas, le problème vient du fait que le double passé comme premier argument de l'ellipsis occupe 8 octets, alors que va_arg(list, int) ne renvoie que 4 octets de données à chaque appel. Ainsi, le premier appel à va_arg ne lit que les 4 premiers octets du double (produisant un résultat aberrant), et le second appel lit les 4 octets suivants du double (produisant un autre résultat aberrant). Notre résultat global est donc n'importe quoi.

Comme la vérification de type est suspendue, le compilateur ne se plaindra même pas si nous faisons quelque chose de totalement absurde, comme ceci :

    int value{ 7 };
    std::cout << findAverage(6, 1.0, 2, "Hello, world!", 'G', &value, &findAverage) << '\n';

Incroyable mais vrai, cela compile sans problème et produit sur la machine de l'auteur le résultat suivant :


1.79766e+008

Ce résultat illustre parfaitement l'expression « Garbage in, garbage out » (des données absurdes en entrée donnent des résultats absurdes en sortie), une expression populaire en informatique, « utilisée principalement pour attirer l'attention sur le fait que les ordinateurs, contrairement aux humains, traitent sans broncher les données d'entrée les plus absurdes et produisent des résultats absurdes » (Wikipédia).

En résumé, la vérification de type des paramètres est suspendue, et nous devons faire confiance à l'appelant pour passer les bons types de paramètres. Si ce n'est pas le cas, le compilateur ne dira rien : notre programme produira simplement des résultats aberrants (ou plantera peut-être).

Pourquoi les ellipsis sont dangereuses : les ellipsis ne connaissent pas le nombre de paramètres passés

Non seulement les ellipsis éliminent le type des paramètres, mais elles éliminent aussi le nombre de paramètres de l'ellipsis. Cela signifie que nous devons trouver nous-mêmes une solution pour garder la trace du nombre de paramètres passés à l'ellipsis. En général, cela se fait de l'une des trois façons suivantes.

Méthode 1 : passer un paramètre de longueur

La méthode n° 1 consiste à utiliser l'un des paramètres fixes pour représenter le nombre de paramètres optionnels passés. C'est la solution que nous avons utilisée dans l'exemple findAverage() ci-dessus.

Cependant, même ici, nous rencontrons des difficultés. Par exemple, considérons l'appel suivant :

    std::cout << findAverage(6, 1, 2, 3, 4, 5) << '\n';

Sur la machine de l'auteur, au moment de la rédaction, cela a produit le résultat :


699773

Que s'est-il passé ? Nous avons indiqué à findAverage() que nous allions fournir 6 valeurs supplémentaires, mais nous n'en avons donné que 5. Par conséquent, les cinq premières valeurs renvoyées par va_arg() sont celles que nous avons passées. La sixième valeur renvoyée est une valeur aléatoire située quelque part dans la pile. Nous obtenons donc un résultat aberrant.

Un cas plus sournois :

    std::cout << findAverage(6, 1, 2, 3, 4, 5, 6, 7) << '\n';

Cela produit la réponse 3.5, qui peut sembler correcte à première vue, mais qui omet le dernier nombre de la moyenne, car nous n'avons indiqué que 6 valeurs supplémentaires (alors que nous en avons réellement fourni 7). Ce genre d'erreur peut être très difficile à détecter.

Méthode 2 : utiliser une valeur sentinelle

La méthode n° 2 consiste à utiliser une valeur sentinelle. Une sentinelle est une valeur particulière qui termine une boucle lorsqu'elle est rencontrée. Par exemple, pour les chaînes de caractères, le caractère nul de fin sert de sentinelle pour marquer la fin de la chaîne. Avec les ellipsis, la sentinelle est généralement passée comme dernier paramètre. Voici un exemple de findAverage() réécrit pour utiliser la valeur sentinelle -1 :

#include <iostream>
#include <cstdarg> // nécessaire pour utiliser une ellipsis

// L'ellipsis doit être le dernier paramètre
double findAverage(int first, ...)
{
    // Nous devons traiter le premier nombre à part
    int sum{ first };

    // Nous accédons à l'ellipsis à travers une va_list, déclarons donc une va_list
    std::va_list list;

    // Nous initialisons la va_list avec va_start. Le premier argument est
    // la liste à initialiser. Le second argument est le dernier paramètre
    // qui n'est pas une ellipsis.
    va_start(list, first);

    int count{ 1 };
    // Boucle infinie
    while (true)
    {
        // Nous utilisons va_arg pour extraire des valeurs de l'ellipsis
        // Le premier argument est la va_list utilisée
        // Le second argument est le type de la valeur
        int arg{ va_arg(list, int) };

        // Si ce paramètre est notre valeur sentinelle, on arrête la boucle
        if (arg == -1)
            break;

        sum += arg;
        ++count;
    }

    // Nettoyer la va_list lorsque nous avons terminé.
    va_end(list);

    return static_cast<double>(sum) / count;
}

int main()
{
    std::cout << findAverage(1, 2, 3, 4, 5, -1) << '\n';
    std::cout << findAverage(1, 2, 3, 4, 5, 6, -1) << '\n';

    return 0;
}

Notez que nous n'avons plus besoin de passer une longueur explicite comme premier paramètre. Nous passons à la place une valeur sentinelle comme dernier paramètre.

Cependant, cette approche pose quelques difficultés. Premièrement, C++ exige que nous passions au moins un paramètre fixe. Dans l'exemple précédent, il s'agissait de notre variable count. Dans cet exemple, la première valeur fait en réalité partie des nombres à moyenner. Plutôt que de traiter cette première valeur comme faisant partie des paramètres de l'ellipsis, nous la déclarons explicitement comme paramètre normal. Nous devons alors la traiter de façon particulière dans la fonction (dans ce cas, nous initialisons sum à first au lieu de 0).

Deuxièmement, cela oblige l'utilisateur à passer la sentinelle comme dernière valeur. Si l'utilisateur oublie de passer la valeur sentinelle (ou passe une mauvaise valeur), la fonction bouclera indéfiniment jusqu'à tomber sur une donnée aberrante qui correspond à la sentinelle (ou plantera).

Enfin, notez que nous avons choisi -1 comme sentinelle. C'est acceptable si nous ne voulons calculer la moyenne que de nombres positifs, mais que faire si nous voulions inclure les nombres négatifs ? Les valeurs sentinelles ne fonctionnent bien que s'il existe une valeur située en dehors de l'ensemble des valeurs valides pour le problème à résoudre.

Méthode 3 : utiliser une chaîne de décodage

La méthode n° 3 consiste à passer une « chaîne de décodage » qui indique au programme comment interpréter les paramètres.

#include <iostream>
#include <string_view>
#include <cstdarg> // nécessaire pour utiliser une ellipsis

// L'ellipsis doit être le dernier paramètre
double findAverage(std::string_view decoder, ...)
{
    double sum{ 0 };

    // Nous accédons à l'ellipsis à travers une va_list, déclarons donc une va_list
    std::va_list list;

    // Nous initialisons la va_list avec va_start. Le premier argument est
    // la liste à initialiser. Le second argument est le dernier paramètre
    // qui n'est pas une ellipsis.
    va_start(list, decoder);

    for (auto codetype: decoder)
    {
        switch (codetype)
        {
        case 'i':
            sum += va_arg(list, int);
            break;

        case 'd':
            sum += va_arg(list, double);
            break;
        }
    }

    // Nettoyer la va_list lorsque nous avons terminé.
    va_end(list);

    return sum / std::size(decoder);
}

int main()
{
    std::cout << findAverage("iiiii", 1, 2, 3, 4, 5) << '\n';
    std::cout << findAverage("iiiiii", 1, 2, 3, 4, 5, 6) << '\n';
    std::cout << findAverage("iiddi", 1, 2, 3.5, 4.5, 5) << '\n';

    return 0;
}

Dans cet exemple, nous passons une chaîne qui encode à la fois le nombre de variables optionnelles et leurs types. L'avantage est que cela nous permet de traiter des paramètres de types différents. Cependant, cette méthode a aussi des inconvénients : la chaîne de décodage peut être assez cryptique, et si le nombre ou les types des paramètres optionnels ne correspondent pas précisément à la chaîne de décodage, de mauvaises choses peuvent arriver.

Pour ceux d'entre vous qui viennent du C, c'est exactement ce que fait printf !

Recommandations pour une utilisation plus sûre des ellipsis

Premièrement, si possible, n'utilisez pas du tout les ellipsis ! Il existe souvent d'autres solutions raisonnables, même si elles demandent un peu plus de travail. Par exemple, dans notre programme findAverage(), nous aurions pu passer un tableau d'entiers de taille dynamique. Cela aurait assuré une vérification de type stricte (pour empêcher l'appelant de faire quelque chose d'absurde) tout en conservant la possibilité de passer un nombre variable d'entiers à moyenner.

Deuxièmement, si vous utilisez des ellipsis, il est préférable que toutes les valeurs passées au paramètre ellipsis soient du même type (par exemple toutes des int, ou toutes des double, et non un mélange). Mélanger les types augmente considérablement la possibilité que l'appelant passe par inadvertance des données du mauvais type, et que va_arg() produise un résultat aberrant.

Troisièmement, utiliser un paramètre de comptage ou une chaîne de décodage est généralement plus sûr qu'une valeur sentinelle. Cela oblige l'utilisateur à choisir une valeur appropriée pour le paramètre de comptage ou de décodage, ce qui garantit que la boucle sur l'ellipsis se termine après un nombre raisonnable d'itérations, même si elle produit une valeur aberrante.

Pour les lecteurs avancés

Pour améliorer les fonctionnalités de type ellipsis, C++11 a introduit les packs de paramètres (parameter packs) et les modèles variadiques (variadic templates), qui offrent des fonctionnalités similaires aux ellipsis, mais avec une vérification de type stricte. Cependant, d'importantes difficultés d'utilisation ont freiné l'adoption de cette fonctionnalité.

En C++17, les expressions de pliage (fold expressions) ont été ajoutées, ce qui améliore considérablement l'utilisabilité des packs de paramètres, au point qu'ils constituent désormais une option viable.

Nous espérons présenter des leçons sur ces sujets dans une future mise à jour du site.
