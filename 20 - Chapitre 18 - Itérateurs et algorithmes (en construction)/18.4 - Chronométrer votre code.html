18.4 — Chronométrer votre code

Lorsque vous écrivez du code, il arrive que vous ne sachiez pas si une méthode sera plus performante qu'une autre. Comment le savoir ?

Une solution simple consiste à chronométrer votre code pour mesurer le temps qu'il met à s'exécuter. C++11 fournit des fonctionnalités dans la bibliothèque chrono pour cela. Cependant, l'utilisation de la bibliothèque chrono est un peu ésotérique. La bonne nouvelle, c'est que nous pouvons facilement encapsuler toute la fonctionnalité de chronométrage dont nous avons besoin dans une classe, que nous pourrons ensuite utiliser dans nos propres programmes.

Voici la classe :

#include <chrono> // pour les fonctions de std::chrono

class Timer
{
private:
    // Alias de type pour faciliter l'accès au type imbriqué
    using Clock = std::chrono::steady_clock;
    using Second = std::chrono::duration<double, std::ratio<1> >;

    std::chrono::time_point<Clock> m_beg { Clock::now() };

public:
    void reset()
    {
        m_beg = Clock::now();
    }

    double elapsed() const
    {
        return std::chrono::duration_cast<Second>(Clock::now() - m_beg).count();
    }
};

C'est tout ! Pour l'utiliser, nous instancions un objet Timer en haut de notre fonction main (ou à l'endroit où nous voulons commencer le chronométrage), puis nous appelons la fonction membre elapsed() chaque fois que nous voulons savoir combien de temps le programme a mis à s'exécuter jusqu'à ce point.

#include <iostream>

int main()
{
    Timer t;

    // Le code à chronométrer se trouve ici

    std::cout << "Time elapsed: " << t.elapsed() << " seconds\n";

    return 0;
}

Maintenant, utilisons cela dans un exemple concret où nous trions un tableau de 10000 éléments. Commençons par l'algorithme de tri par sélection que nous avons développé dans un chapitre précédent :

#include <array>
#include <chrono> // pour les fonctions de std::chrono
#include <cstddef> // pour std::size_t
#include <iostream>
#include <numeric> // pour std::iota

const int g_arrayElements { 10000 };

class Timer
{
private:
    // Alias de type pour faciliter l'accès au type imbriqué
    using Clock = std::chrono::steady_clock;
    using Second = std::chrono::duration<double, std::ratio<1> >;

    std::chrono::time_point<Clock> m_beg{ Clock::now() };

public:

    void reset()
    {
        m_beg = Clock::now();
    }

    double elapsed() const
    {
        return std::chrono::duration_cast<Second>(Clock::now() - m_beg).count();
    }
};

void sortArray(std::array<int, g_arrayElements>& array)
{

    // Parcourir chaque élément du tableau
    // (sauf le dernier, qui sera déjà trié à ce moment-là)
    for (std::size_t startIndex{ 0 }; startIndex < (g_arrayElements - 1); ++startIndex)
    {
        // smallestIndex est l'indice du plus petit élément rencontré à cette itération
        // On suppose d'abord que le plus petit élément est le premier élément de cette itération
        std::size_t smallestIndex{ startIndex };

        // Puis on cherche un élément plus petit dans le reste du tableau
        for (std::size_t currentIndex{ startIndex + 1 }; currentIndex < g_arrayElements; ++currentIndex)
        {
            // Si nous avons trouvé un élément plus petit que le plus petit trouvé précédemment
            if (array[currentIndex] < array[smallestIndex])
            {
                // alors on le mémorise
                smallestIndex = currentIndex;
            }
        }

        // smallestIndex est maintenant l'indice du plus petit élément du tableau restant
        // on échange notre élément de départ avec le plus petit (ce qui le place à la bonne position)
        std::swap(array[startIndex], array[smallestIndex]);
    }
}

int main()
{
    std::array<int, g_arrayElements> array;
    std::iota(array.rbegin(), array.rend(), 1); // remplit le tableau avec les valeurs de 10000 à 1

    Timer t;

    sortArray(array);

    std::cout << "Time taken: " << t.elapsed() << " seconds\n";

    return 0;
}

Sur la machine de l'auteur, trois exécutions ont donné des temps de 0,0507, 0,0506 et 0,0498. On peut donc dire qu'il s'agit d'environ 0,05 seconde.

Refaisons maintenant le même test avec std::sort de la bibliothèque standard.

#include <algorithm> // pour std::sort
#include <array>
#include <chrono> // pour les fonctions de std::chrono
#include <cstddef> // pour std::size_t
#include <iostream>
#include <numeric> // pour std::iota

const int g_arrayElements { 10000 };

class Timer
{
private:
    // Alias de type pour faciliter l'accès au type imbriqué
    using Clock = std::chrono::steady_clock;
    using Second = std::chrono::duration<double, std::ratio<1> >;

    std::chrono::time_point<Clock> m_beg{ Clock::now() };

public:

    void reset()
    {
        m_beg = Clock::now();
    }

    double elapsed() const
    {
        return std::chrono::duration_cast<Second>(Clock::now() - m_beg).count();
    }
};

int main()
{
    std::array<int, g_arrayElements> array;
    std::iota(array.rbegin(), array.rend(), 1); // remplit le tableau avec les valeurs de 10000 à 1

    Timer t;

    std::ranges::sort(array); // Depuis C++20
    // Si votre compilateur n'est pas compatible avec C++20
    // std::sort(array.begin(), array.end());

    std::cout << "Time taken: " << t.elapsed() << " seconds\n";

    return 0;
}

Sur la machine de l'auteur, ce programme a donné les résultats suivants : 0,000693, 0,000692 et 0,000699. Soit à peu près 0,0007.

Autrement dit, dans ce cas, std::sort est 100 fois plus rapide que le tri par sélection que nous avons écrit nous-mêmes !

Ce qui peut influencer les performances de votre programme

Chronométrer une exécution de votre programme est assez simple, mais vos résultats peuvent être sensiblement influencés par plusieurs facteurs. Il est important de savoir comment mesurer correctement et quels éléments peuvent perturber la mesure.

Premièrement, assurez-vous d'utiliser une cible de compilation en mode release et non en mode debug. Les cibles en mode debug désactivent généralement l'optimisation, et cette optimisation peut avoir un impact important sur les résultats. Par exemple, avec une cible en mode debug, l'exemple ci-dessus utilisant std::sort a pris 0,0235 seconde sur la machine de l'auteur, soit 33 fois plus longtemps !

Deuxièmement, vos résultats peuvent être influencés par d'autres tâches que votre système effectue en arrière-plan. Assurez-vous que votre système n'effectue aucune tâche intensive pour le processeur, la mémoire ou le disque dur (par exemple jouer à un jeu, rechercher un fichier, lancer une analyse antivirus ou installer une mise à jour en arrière-plan). Des éléments en apparence anodins, comme des navigateurs web inactifs, peuvent faire passer temporairement le processeur à 100 % d'utilisation lorsque l'onglet actif affiche une nouvelle bannière publicitaire et doit analyser beaucoup de code JavaScript. Plus vous fermez d'applications avant la mesure, moins vos résultats risquent de varier.

Troisièmement, si votre programme utilise un générateur de nombres aléatoires, la séquence particulière de nombres générés peut influencer le temps d'exécution. Par exemple, si vous triez un tableau rempli de nombres aléatoires, les résultats varieront probablement d'une exécution à l'autre, car le nombre d'échanges nécessaires pour trier le tableau change à chaque fois. Pour obtenir des résultats plus cohérents d'une exécution à l'autre, vous pouvez initialiser temporairement votre générateur de nombres aléatoires avec une valeur littérale (plutôt qu'avec std::random_device ou l'horloge système), afin qu'il génère la même séquence de nombres à chaque exécution. Toutefois, si les performances de votre programme dépendent fortement de la séquence aléatoire particulière générée, cela peut aussi conduire à des résultats globalement trompeurs.

Quatrièmement, assurez-vous de ne pas chronométrer l'attente d'une saisie utilisateur, car le temps que met l'utilisateur à saisir quelque chose ne doit pas faire partie de votre mesure. Si une saisie est nécessaire, envisagez d'ajouter un moyen de fournir cette saisie sans attendre l'utilisateur (par exemple en ligne de commande, depuis un fichier, ou via un chemin de code qui contourne la saisie).

Mesurer les performances

Lorsque vous mesurez les performances de votre programme, recueillez au moins 3 résultats. Si ces résultats sont tous semblables, ils représentent probablement les performances réelles de votre programme sur cette machine. Sinon, poursuivez les mesures jusqu'à obtenir un ensemble de résultats similaires (et identifiez les autres résultats qui sont des valeurs aberrantes). Il n'est pas rare d'avoir une ou plusieurs valeurs aberrantes, à cause de tâches effectuées par votre système en arrière-plan pendant certaines de ces exécutions.

Si vos résultats présentent une forte dispersion (et ne se regroupent pas bien), votre programme est probablement fortement affecté par d'autres activités du système, ou par les effets de la randomisation dans votre application.

Comme les mesures de performance sont influencées par de nombreux facteurs (en particulier la vitesse du matériel, mais aussi le système d'exploitation, les applications en cours d'exécution, etc.), les mesures de performance absolues (par exemple « le programme s'exécute en 10 secondes ») sont généralement peu utiles, sauf pour comprendre comment le programme se comporte sur une machine particulière qui vous intéresse. Sur une autre machine, ce même programme peut s'exécuter en 1 seconde, en 10 secondes ou en 1 minute. Il est difficile de le savoir sans mesurer réellement sur un éventail de matériels différents.

En revanche, sur une même machine, les mesures de performance relatives peuvent être utiles. Nous pouvons recueillir les résultats de performance de plusieurs variantes d'un programme pour déterminer laquelle est la plus performante. Par exemple, si la variante 1 s'exécute en 10 secondes et la variante 2 en 8 secondes, la variante 2 sera probablement plus rapide sur toutes les machines similaires, quelle que soit la vitesse absolue de chaque machine.

Après avoir mesuré la deuxième variante, une bonne vérification de cohérence consiste à mesurer à nouveau la première variante. Si les résultats de la première variante sont cohérents avec vos mesures initiales pour cette variante, alors les résultats des deux variantes sont raisonnablement comparables. Par exemple, si la variante 1 s'exécute en 10 secondes, la variante 2 en 8 secondes, puis que nous mesurons à nouveau la variante 1 et obtenons 10 secondes, nous pouvons raisonnablement conclure que les mesures des deux variantes sont correctes et que la variante 2 est plus rapide.

En revanche, si les résultats de la première variante ne sont plus cohérents avec vos mesures initiales, cela signifie que quelque chose s'est produit sur la machine et affecte maintenant les performances. Il sera alors difficile de savoir si les différences de mesure sont dues à la variante ou à la machine elle-même. Dans ce cas, le mieux est d'abandonner les résultats existants et de recommencer les mesures.
