Passage par adresse pour des arguments « optionnels »

L'un des usages les plus courants du passage par adresse consiste à permettre à une fonction d'accepter un argument « optionnel ». C'est plus facile à illustrer par un exemple qu'à décrire :

#include <iostream>

void printIDNumber(const int *id=nullptr)
{
    if (id)
        std::cout << "Your ID number is " << *id << ".\n";
    else
        std::cout << "Your ID number is not known.\n";
}

int main()
{
    printIDNumber(); // we don't know the user's ID yet

    int userid { 34 };
    printIDNumber(&userid); // we know the user's ID now

    return 0;
}

Ce programme affiche :


Your ID number is not known.
Your ID number is 34.

Dans ce programme, la fonction printIDNumber() possède un paramètre passé par adresse, dont la valeur par défaut est nullptr. Dans main(), nous appelons cette fonction deux fois. Au premier appel, nous ne connaissons pas l'identifiant de l'utilisateur ; nous appelons donc printIDNumber() sans argument. Le paramètre id prend la valeur par défaut nullptr, et la fonction affiche Your ID number is not known.. Au second appel, nous disposons désormais d'un identifiant valide, nous appelons donc printIDNumber(&userid). Le paramètre id reçoit l'adresse de userid, et la fonction affiche Your ID number is 34..

Cependant, dans de nombreux cas, la surcharge de fonctions est une meilleure alternative pour obtenir le même résultat :

#include <iostream>

void printIDNumber()
{
    std::cout << "Your ID is not known\n";
}

void printIDNumber(int id)
{
    std::cout << "Your ID is " << id << "\n";
}

int main()
{
    printIDNumber(); // we don't know the user's ID yet

    int userid { 34 };
    printIDNumber(userid); // we know the user is 34

    printIDNumber(62); // now also works with rvalue arguments

    return 0;
}

Cette approche présente plusieurs avantages : nous n'avons plus à nous soucier des déréférencements de pointeurs nuls, et nous pouvons passer des littéraux ou d'autres valeurs (rvalues) en argument.

Modifier ce que pointe un paramètre pointeur

Lorsque nous passons une adresse à une fonction, cette adresse est copiée de l'argument vers le paramètre pointeur (ce qui est acceptable, car copier une adresse est rapide). Considérons maintenant le programme suivant :

#include <iostream>

// [[maybe_unused]] gets rid of compiler warnings about ptr2 being set but not used
void nullify([[maybe_unused]] int* ptr2)
{
    ptr2 = nullptr; // Make the function parameter a null pointer
}

int main()
{
    int x{ 5 };
    int* ptr{ &x }; // ptr points to x

    std::cout << "ptr is " << (ptr ? "non-null\n" : "null\n");

    nullify(ptr);

    std::cout << "ptr is " << (ptr ? "non-null\n" : "null\n");
    return 0;
}

Ce programme affiche :


ptr is non-null
ptr is non-null

Comme vous pouvez le voir, modifier l'adresse contenue dans le paramètre pointeur n'a aucun effet sur l'adresse contenue dans l'argument (ptr pointe toujours sur x). Lorsque la fonction nullify() est appelée, ptr2 reçoit une copie de l'adresse passée (dans ce cas, l'adresse contenue dans ptr, c'est-à-dire l'adresse de x). Lorsque la fonction modifie ce que pointe ptr2, cela n'affecte que la copie détenue par ptr2.

Que faire alors si nous voulons permettre à une fonction de modifier ce que pointe un argument pointeur ?

Passage par adresse… par référence ?

Oui, c'est possible. De même que nous pouvons passer une variable ordinaire par référence, nous pouvons également passer des pointeurs par référence. Voici le même programme que ci-dessus, dans lequel ptr2 est remplacé par une référence à une adresse :

#include <iostream>

void nullify(int*& refptr) // refptr is now a reference to a pointer
{
    refptr = nullptr; // Make the function parameter a null pointer
}

int main()
{
    int x{ 5 };
    int* ptr{ &x }; // ptr points to x

    std::cout << "ptr is " << (ptr ? "non-null\n" : "null\n");

    nullify(ptr);

    std::cout << "ptr is " << (ptr ? "non-null\n" : "null\n");
    return 0;
}

Ce programme affiche :


ptr is non-null
ptr is null

Comme refptr est désormais une référence à un pointeur, lorsque ptr est passé en argument, refptr est lié à ptr. Cela signifie que toute modification de refptr est appliquée à ptr.

En passant…

Les références à des pointeurs étant assez rares, il est facile de confondre la syntaxe (faut-il écrire int*& ou int&* ?). Heureusement, si vous l'écrivez à l'envers, le compilateur signalera une erreur, car il n'est pas possible d'avoir un pointeur vers une référence (les pointeurs doivent contenir l'adresse d'un objet, et les références ne sont pas des objets). Il vous suffit alors de réécrire la déclaration dans le bon ordre.

Pourquoi utiliser 0 ou NULL n'est plus recommandé (facultatif)

Dans cette sous-section, nous expliquons pourquoi utiliser 0 ou NULL n'est plus recommandé.

Le littéral 0 peut être interprété soit comme un littéral entier, soit comme un littéral de pointeur nul. Dans certains cas, il peut être ambigu de savoir laquelle de ces interprétations est voulue, et dans certains de ces cas, le compilateur peut supposer que nous voulons l'une alors que nous voulions l'autre, avec des conséquences involontaires sur le comportement de notre programme.

La définition de la macro de préprocesseur NULL n'est pas fixée par la norme du langage. Elle peut être définie comme 0, 0L, ((void*)0), ou par autre chose encore.

Dans la leçon 11.1 -- Introduction à la surcharge de fonctions, nous avons vu que les fonctions peuvent être surchargées (plusieurs fonctions peuvent porter le même nom, à condition de pouvoir être distinguées par le nombre ou le type de leurs paramètres). Le compilateur peut déterminer quelle fonction surchargée vous souhaitez appeler grâce aux arguments passés lors de l'appel.

Utiliser 0 ou NULL peut poser des problèmes :

#include <iostream>
#include <cstddef> // for NULL

void print(int x) // this function accepts an integer
{
    std::cout << "print(int): " << x << '\n';
}

void print(int* ptr) // this function accepts an integer pointer
{
    std::cout << "print(int*): " << (ptr ? "non-null\n" : "null\n");
}

int main()
{
    int x{ 5 };
    int* ptr{ &x };

    print(ptr);  // always calls print(int*) because ptr has type int* (good)
    print(0);    // always calls print(int) because 0 is an integer literal (hopefully this is what we expected)

    print(NULL); // this statement could do any of the following:
    // call print(int) (Visual Studio does this)
    // call print(int*)
    // result in an ambiguous function call compilation error (gcc and Clang do this)

    print(nullptr); // always calls print(int*)

    return 0;
}

Sur la machine de l'auteur (avec Visual Studio), ce programme affiche :


print(int*): non-null
print(int): 0
print(int): 0
print(int*): null

Lorsque l'on passe la valeur entière 0 comme paramètre, le compilateur préfère print(int) à print(int*). Cela peut conduire à des résultats inattendus lorsque nous voulions appeler print(int*) avec un argument de pointeur nul.

Dans le cas où NULL est défini comme la valeur 0, print(NULL) appellera également print(int), et non print(int*) comme on pourrait s'y attendre pour un littéral de pointeur nul. Lorsque NULL n'est pas défini comme 0, d'autres comportements peuvent se produire, comme un appel à print(int*) ou une erreur de compilation.

Utiliser nullptr supprime cette ambiguïté (il appellera toujours print(int*)), puisque nullptr ne correspond qu'à un type pointeur.

std::nullptr_t (facultatif)

Comme nullptr peut être distingué des valeurs entières lors de la surcharge de fonctions, il doit posséder un type différent. Quel est donc le type de nullptr ? La réponse est que nullptr a pour type std::nullptr_t (défini dans l'en-tête <cstddef>). std::nullptr_t ne peut contenir qu'une seule valeur : nullptr ! Bien que cela puisse sembler plutôt absurde, c'est utile dans une situation. Si nous voulons écrire une fonction qui n'accepte qu'un littéral nullptr en argument, nous pouvons faire en sorte que le paramètre soit de type std::nullptr_t.

#include <iostream>
#include <cstddef> // for std::nullptr_t

void print(std::nullptr_t)
{
    std::cout << "in print(std::nullptr_t)\n";
}

void print(int*)
{
    std::cout << "in print(int*)\n";
}

int main()
{
    print(nullptr); // calls print(std::nullptr_t)

    int x { 5 };
    int* ptr { &x };

    print(ptr); // calls print(int*)

    ptr = nullptr;
    print(ptr); // calls print(int*) (since ptr has type int*)

    return 0;
}

Dans l'exemple ci-dessus, l'appel print(nullptr) correspond à la fonction print(std::nullptr_t) plutôt qu'à print(int*), car il ne nécessite aucune conversion.

Le cas qui peut paraître un peu déroutant est l'appel print(ptr) lorsque ptr contient la valeur nullptr. Rappelez-vous que la surcharge de fonctions se fait sur les types et non sur les valeurs, et que ptr a pour type int*. C'est donc print(int*) qui est retenue. print(std::nullptr_t) n'est même pas considérée dans ce cas, car les types pointeurs ne se convertissent pas implicitement en std::nullptr_t.

Vous n'aurez probablement jamais besoin de cela, mais il est bon de le savoir, au cas où.

Il n'existe que le passage par valeur

Maintenant que vous comprenez les différences fondamentales entre le passage par référence, par adresse et par valeur, simplifions un instant les choses. :)

Bien que le compilateur puisse souvent supprimer entièrement les références lors de l'optimisation, il existe des cas où cela n'est pas possible et où une référence est réellement nécessaire. Les références sont généralement implémentées par le compilateur à l'aide de pointeurs. Cela signifie qu'en coulisse, le passage par référence n'est essentiellement qu'un passage par adresse.

Et dans la leçon précédente, nous avons indiqué que le passage par adresse ne fait que copier une adresse de l'appelant vers la fonction appelée, ce qui revient à passer une adresse par valeur.

Nous pouvons donc conclure que C++ passe véritablement tout par valeur ! Les propriétés du passage par adresse (et par référence) proviennent uniquement du fait que nous pouvons déréférencer l'adresse passée pour modifier l'argument, ce que nous ne pouvons pas faire avec un paramètre ordinaire passé par valeur !
