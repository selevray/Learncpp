12.6 — Passage par référence constante vers une lvalue

Contrairement à une référence vers un objet non constant (qui ne peut se lier qu'à des lvalues modifiables), une référence constante peut se lier à des lvalues modifiables, à des lvalues non modifiables et à des rvalues. Par conséquent, si nous rendons constant un paramètre référence, il pourra se lier à tout type d'argument :

#include <iostream>

void printRef(const int& y) // y est une référence constante
{
    std::cout << y << '\n';
}

int main()
{
    int x { 5 };
    printRef(x);   // ok : x est une lvalue modifiable, y se lie à x

    const int z { 5 };
    printRef(z);   // ok : z est une lvalue non modifiable, y se lie à z

    printRef(5);   // ok : 5 est un littéral rvalue, y se lie à un objet int temporaire

    return 0;
}

Le passage par référence constante offre le même avantage principal que le passage par référence non constante (éviter la copie de l'argument), tout en garantissant que la fonction ne peut pas modifier la valeur référencée.

Par exemple, le code suivant est interdit, car ref est constant :

void addOne(const int& ref)
{
    ++ref; // interdit : ref est constant
}

Dans la plupart des cas, nous ne voulons pas que nos fonctions modifient la valeur de leurs arguments.

Bonne pratique

Privilégiez le passage par référence constante plutôt que par référence non constante, sauf si vous avez une raison particulière de faire autrement (par exemple, si la fonction doit modifier la valeur d'un argument).

Nous pouvons maintenant comprendre la raison pour laquelle les références constantes vers une lvalue peuvent se lier à des rvalues : sans cette capacité, il serait impossible de passer des littéraux (ou d'autres rvalues) à des fonctions utilisant le passage par référence !

Passer des arguments d'un type différent à un paramètre de référence constante vers une lvalue

Dans la leçon 12.4 -- Références lvalue vers const, nous avons remarqué qu'une référence lvalue constante peut se lier à une valeur d'un type différent, à condition que cette valeur soit convertible vers le type de la référence. La conversion crée un objet temporaire auquel le paramètre référence peut ensuite se lier.

La principale motivation de cette possibilité est de pouvoir passer une valeur comme argument, de la même façon, à un paramètre passé par valeur ou à un paramètre de référence constante :

#include <iostream>

void printVal(double d)
{
    std::cout << d << '\n';
}

void printRef(const double& d)
{
    std::cout << d << '\n';
}

int main()
{
    printVal(5); // 5 converti en double temporaire, copié dans le paramètre d
    printRef(5); // 5 converti en double temporaire, lié au paramètre d

    return 0;
}

Avec le passage par valeur, nous nous attendons à ce qu'une copie soit faite. Si une conversion a lieu avant (ce qui entraîne une copie supplémentaire), cela pose rarement problème (et le compilateur supprimera probablement l'une des deux copies par optimisation).

En revanche, nous utilisons souvent le passage par référence précisément parce que nous ne voulons pas qu'une copie soit faite. Si une conversion a lieu au préalable, cela entraîne généralement la création d'une copie (potentiellement coûteuse), ce qui peut être sous-optimal.

Attention

Avec le passage par référence, assurez-vous que le type de l'argument correspond au type de la référence, sinon une conversion inattendue (et potentiellement coûteuse) aura lieu.

Mélanger passage par valeur et passage par référence

Une fonction ayant plusieurs paramètres peut déterminer individuellement si chaque paramètre est passé par valeur ou par référence.

Par exemple :

#include <string>

void foo(int a, int& b, const std::string& c)
{
}

int main()
{
    int x { 5 };
    const std::string s { "Hello, world!" };

    foo(5, x, s);

    return 0;
}

Dans l'exemple ci-dessus, le premier argument est passé par valeur, le deuxième par référence, et le troisième par référence constante.

Quand utiliser le passage par valeur ou le passage par référence

Pour la plupart des débutants en C++, le choix entre passage par valeur et passage par référence n'est pas très évident. Heureusement, il existe une règle empirique simple qui vous servira dans la majorité des cas.

  • Les types fondamentaux et les types énumérés sont peu coûteux à copier, ils sont donc généralement passés par valeur.
  • Les types classe peuvent être coûteux à copier (parfois très coûteux), ils sont donc généralement passés par référence constante.

Bonne pratique

En règle générale, passez les types fondamentaux par valeur et les types classe par référence constante.

Si vous ne savez pas quoi faire, passez par référence constante, car vous serez moins susceptible de rencontrer un comportement inattendu.

Astuce

Voici une liste partielle d'autres cas intéressants :

Les éléments suivants sont souvent passés par valeur (car c'est plus efficace) :

  • Les types énumérés (énumérations sans portée et avec portée).
  • Les vues et les spans (par exemple std::string_view, std::span).
  • Les types qui imitent des références ou des pointeurs (non propriétaires) (par exemple les itérateurs, std::reference_wrapper).
  • Les types classe peu coûteux à copier qui ont une sémantique de valeur (par exemple std::pair avec des éléments de types fondamentaux, std::optional, std::expected).

Le passage par référence doit être utilisé pour les cas suivants :

  • Les arguments qui doivent être modifiés par la fonction.
  • Les types non copiables (comme std::ostream).
  • Les types pour lesquels la copie a des implications sur la propriété que nous voulons éviter (par exemple std::unique_ptr, std::shared_ptr).
  • Les types qui possèdent des fonctions virtuelles ou dont on est susceptible d'hériter (à cause des problèmes de découpage d'objet (object slicing), abordés dans la leçon 25.9 -- Découpage d'objet).

Le coût du passage par valeur par rapport au passage par référence (Avancé)

Tous les types classe n'ont pas besoin d'être passés par référence (c'est le cas de std::string_view, normalement passé par valeur). Vous vous demandez peut-être pourquoi nous ne passons pas simplement tout par référence. Dans cette section (lecture facultative), nous examinons le coût du passage par valeur par rapport au passage par référence, et nous affinons notre bonne pratique quant au moment où utiliser chacun.

Tout d'abord, nous devons considérer le coût de l'initialisation du paramètre de fonction. Avec le passage par valeur, l'initialisation signifie effectuer une copie. Le coût de la copie d'un objet est généralement proportionnel à deux facteurs :

  • La taille de l'objet. Les objets qui utilisent plus de mémoire prennent plus de temps à copier.
  • Les coûts de mise en place supplémentaires. Certains types classe effectuent une mise en place supplémentaire lors de leur instanciation (par exemple ouvrir un fichier ou une base de données, ou allouer une certaine quantité de mémoire dynamique pour contenir un objet de taille variable). Ces coûts de mise en place doivent être payés à chaque copie de l'objet.

En revanche, lier une référence à un objet est toujours rapide (à peu près aussi rapide que la copie d'un type fondamental).

Ensuite, nous devons considérer le coût d'utilisation du paramètre de fonction. Lors de la mise en place d'un appel de fonction, le compilateur peut optimiser en plaçant une référence ou une copie d'un argument passé par valeur (s'il est de petite taille) dans un registre du processeur (dont l'accès est rapide) plutôt que dans la RAM (dont l'accès est plus lent).

À chaque utilisation d'un paramètre par valeur, le programme en cours d'exécution peut accéder directement à l'emplacement de stockage (registre du processeur ou RAM) de l'argument copié. En revanche, lorsqu'un paramètre référence est utilisé, il existe généralement une étape supplémentaire. Le programme doit d'abord accéder directement à l'emplacement de stockage (registre du processeur ou RAM) alloué à la référence, afin de déterminer quel objet est référencé. Ce n'est qu'ensuite qu'il peut accéder à l'emplacement de stockage de l'objet référencé (en RAM).

Par conséquent, chaque utilisation d'un paramètre par valeur correspond à un seul accès au registre du processeur ou à la RAM, alors que chaque utilisation d'un paramètre référence correspond à un accès au registre du processeur ou à la RAM, plus un second accès à la RAM.

Troisièmement, le compilateur peut parfois optimiser le code qui utilise le passage par valeur plus efficacement que le code qui utilise le passage par référence. En particulier, les optimiseurs doivent être prudents dès qu'il existe une possibilité d'aliasing (lorsque deux pointeurs ou références ou plus peuvent accéder au même objet). Comme le passage par valeur produit une copie des valeurs des arguments, aucun aliasing ne peut se produire, ce qui permet aux optimiseurs d'être plus agressifs.

Nous pouvons maintenant répondre à la question de savoir pourquoi nous ne passons pas tout par référence :

  • Pour les objets peu coûteux à copier, le coût de la copie est similaire au coût de la liaison, mais l'accès aux objets est plus rapide et le compilateur est susceptible de mieux optimiser.
  • Pour les objets coûteux à copier, le coût de la copie domine les autres considérations de performance.

La dernière question est alors : comment définir « peu coûteux à copier » ? Il n'existe pas de réponse absolue, car cela varie selon le compilateur, le cas d'utilisation et l'architecture. Cependant, nous pouvons formuler une bonne règle empirique : un objet est peu coûteux à copier s'il occupe 2 « mots » de mémoire ou moins (où un « mot » est approximé par la taille d'une adresse mémoire) et s'il n'a aucun coût de mise en place.

Le programme suivant définit une macro de type fonction permettant de déterminer si un type (ou un objet) est peu coûteux à copier selon ce critère :

#include <iostream>

// Macro de type fonction qui vaut true si le type (ou l'objet) est inférieur ou égal à
// la taille de deux adresses mémoire
#define isSmall(T) (sizeof(T) <= 2 * sizeof(void*))

struct S
{
    double a;
    double b;
    double c;
};

int main()
{
    std::cout << std::boolalpha; // affiche true ou false plutôt que 1 ou 0
    std::cout << isSmall(int) << '\n'; // true

    double d {};
    std::cout << isSmall(d) << '\n'; // true
    std::cout << isSmall(S) << '\n'; // false

    return 0;
}

En passant…

Nous utilisons ici une macro de préprocesseur de type fonction afin de pouvoir fournir en paramètre soit un objet, soit un nom de type (car les fonctions C++ n'acceptent pas de types comme paramètres).

Cependant, il peut être difficile de savoir si un objet de type classe a ou non des coûts de mise en place. Il est préférable de supposer que la plupart des classes de la bibliothèque standard ont des coûts de mise en place, à moins que vous ne sachiez qu'elles n'en ont pas.

Astuce

Un objet de type T est peu coûteux à copier si sizeof(T) <= 2 * sizeof(void*) et s'il n'a aucun coût de mise en place supplémentaire.

Pour les paramètres de fonction, préférez std::string_view à const std::string& dans la plupart des cas

Une question qui revient souvent en C++ moderne : lorsque l'on écrit une fonction ayant un paramètre de type chaîne, le type du paramètre doit-il être const std::string& ou std::string_view ?

Dans la plupart des cas, std::string_view est le meilleur choix, car il peut traiter efficacement un plus grand nombre de types d'arguments. Un paramètre std::string_view permet également à l'appelant de passer une sous-chaîne sans avoir à la copier d'abord dans une chaîne qui lui est propre.

void doSomething(const std::string&);
void doSomething(std::string_view);   // à privilégier dans la plupart des cas

Il existe quelques cas où l'utilisation d'un paramètre const std::string& peut être plus appropriée :

  • Si vous utilisez C++14 ou une version antérieure, std::string_view n'est pas disponible.
  • Si votre fonction doit appeler une autre fonction qui prend en paramètre une chaîne de style C ou un std::string, alors const std::string& peut être un meilleur choix, car std::string_view n'est pas garanti d'être terminé par un caractère nul (ce qu'attendent les fonctions sur les chaînes de style C) et ne se convertit pas efficacement en std::string.

Bonne pratique

Privilégiez le passage des chaînes par std::string_view (par valeur) plutôt que par const std::string&, sauf si votre fonction appelle d'autres fonctions qui nécessitent des chaînes de style C ou des paramètres std::string.

Pourquoi les paramètres std::string_view sont plus efficaces que const std::string& (Avancé)

En C++, un argument de type chaîne sera généralement un std::string, un std::string_view, ou une chaîne de style C / un littéral de chaîne.

Pour rappel :

  • Si le type d'un argument ne correspond pas au type du paramètre correspondant, le compilateur tentera de convertir implicitement l'argument pour correspondre au type du paramètre.
  • La conversion d'une valeur crée un objet temporaire du type converti.
  • La création (ou la copie) d'un std::string_view est peu coûteuse, car std::string_view ne copie pas la chaîne qu'il désigne.
  • La création (ou la copie) d'un std::string peut être coûteuse, car chaque objet std::string effectue une copie de la chaîne.

Voici un tableau montrant ce qui se passe lorsque nous essayons de passer chaque type :

Type de l'argument Paramètre std::string_view Paramètre const std::string&
std::string Conversion peu coûteuse Liaison de référence peu coûteuse
std::string_view Copie peu coûteuse Conversion explicite coûteuse en std::string
Chaîne de style C / littéral Conversion peu coûteuse Conversion coûteuse

Avec un paramètre std::string_view passé par valeur :

  • Si nous passons un argument std::string, le compilateur convertit le std::string en std::string_view, ce qui est peu coûteux, donc c'est acceptable.
  • Si nous passons un argument std::string_view, le compilateur copie l'argument dans le paramètre, ce qui est peu coûteux, donc c'est acceptable.
  • Si nous passons une chaîne de style C ou un littéral de chaîne, le compilateur les convertit en std::string_view, ce qui est peu coûteux, donc c'est acceptable.

Comme vous pouvez le voir, std::string_view gère les trois cas à moindre coût.

Avec un paramètre de référence const std::string& :

  • Si nous passons un argument std::string, le paramètre se lie par référence à l'argument, ce qui est peu coûteux, donc c'est acceptable.
  • Si nous passons un argument std::string_view, le compilateur refuse la conversion implicite et produit une erreur de compilation. Nous pouvons utiliser static_cast pour effectuer une conversion explicite (vers std::string), mais cette conversion est coûteuse (car std::string copiera la chaîne désignée). Une fois la conversion effectuée, le paramètre se lie par référence au résultat, ce qui est peu coûteux. Mais nous avons effectué une copie coûteuse pour réaliser la conversion, ce qui n'est pas idéal.
  • Si nous passons une chaîne de style C ou un littéral de chaîne, le compilateur la convertit implicitement en std::string, ce qui est coûteux. Ce n'est donc pas non plus idéal.

Ainsi, un paramètre const std::string& ne gère efficacement que les arguments de type std::string.

Le même exemple, sous forme de code :

#include <iostream>
#include <string>
#include <string_view>

void printSV(std::string_view sv)
{
    std::cout << sv << '\n';
}

void printS(const std::string& s)
{
    std::cout << s << '\n';
}

int main()
{
    std::string s{ "Hello, world" };
    std::string_view sv { s };

    // Passage à un paramètre `std::string_view`
    printSV(s);              // ok : conversion peu coûteuse de std::string en std::string_view
    printSV(sv);             // ok : copie peu coûteuse de std::string_view
    printSV("Hello, world"); // ok : conversion peu coûteuse du littéral de chaîne de style C en std::string_view

    // Passage à un paramètre `const std::string&`
    printS(s);              // ok : liaison peu coûteuse à l'argument std::string
    printS(sv);             // erreur de compilation : impossible de convertir implicitement std::string_view en std::string
    printS(static_cast<std::string>(sv)); // mauvais : création coûteuse d'un std::string temporaire
    printS("Hello, world"); // mauvais : création coûteuse d'un std::string temporaire

    return 0;
}

De plus, nous devons considérer le coût d'accès au paramètre à l'intérieur de la fonction. Comme un paramètre std::string_view est un objet normal, la chaîne désignée peut être accédée directement. Accéder à un paramètre std::string& nécessite une étape supplémentaire pour atteindre l'objet référencé avant de pouvoir accéder à la chaîne.

Enfin, si nous voulons passer une sous-chaîne d'une chaîne existante (de n'importe quel type), il est relativement peu coûteux de créer une sous-chaîne std::string_view, qui peut ensuite être passée à peu de frais à un paramètre std::string_view. En comparaison, passer une sous-chaîne à un const std::string& est plus coûteux, car la sous-chaîne doit à un moment être copiée dans le std::string auquel le paramètre référence se lie.
