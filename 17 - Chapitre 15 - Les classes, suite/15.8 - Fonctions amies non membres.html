15.8 — Fonctions amies non membres

Pendant une grande partie de ce chapitre et du précédent, nous avons vanté les mérites des contrôles d'accès, qui permettent de contrôler qui peut accéder aux différents membres d'une classe. Les membres privés ne peuvent être accédés que par d'autres membres de la classe, et les membres publics peuvent être accédés par tout le monde. Dans la leçon 14.6 -- Fonctions d'accès, nous avons discuté des avantages de garder vos données privées et de créer une interface publique que les non-membres peuvent utiliser.

Cependant, il existe des situations où cet arrangement n'est ni suffisant ni idéal.

Prenons par exemple une classe de stockage dont le rôle est de gérer un ensemble de données. Supposons maintenant que vous vouliez également afficher ces données, mais que le code chargé de l'affichage propose de nombreuses options et soit donc complexe. Vous pourriez placer à la fois les fonctions de gestion du stockage et celles de gestion de l'affichage dans la même classe, mais cela alourdirait la classe et rendrait son interface complexe. Vous pourriez aussi les séparer : la classe de stockage gère le stockage, et une autre classe d'affichage gère toutes les capacités d'affichage. On obtient ainsi une séparation claire des responsabilités. Mais la classe d'affichage ne pourrait alors pas accéder aux membres privés de la classe de stockage, et ne serait peut-être pas en mesure de faire son travail.

Par ailleurs, il arrive que, syntaxiquement, on préfère utiliser une fonction non membre plutôt qu'une fonction membre (nous en verrons un exemple ci-dessous). C'est notamment le cas lors de la surcharge d'opérateurs, sujet que nous aborderons dans des leçons ultérieures. Mais les fonctions non membres ont le même problème : elles ne peuvent pas accéder aux membres privés de la classe.

Si les fonctions d'accès (ou d'autres fonctions membres publiques) existent déjà et suffisent pour la fonctionnalité que nous voulons implémenter, très bien : nous pouvons (et devons) simplement les utiliser. Mais dans certains cas, ces fonctions n'existent pas. Que faire alors ?

Une option consisterait à ajouter de nouvelles fonctions membres à la classe, afin de permettre aux autres classes ou aux fonctions non membres d'accomplir la tâche qu'elles ne pourraient sinon pas réaliser. Mais nous ne souhaitons peut-être pas exposer publiquement ces éléments : ils peuvent être très dépendants de l'implémentation, ou sujets à un mauvais usage.

Ce dont nous avons vraiment besoin, c'est d'un moyen de contourner le système de contrôle d'accès au cas par cas.

L'amitié, c'est magique

La réponse à ce problème est l'amitié.

Dans le corps d'une classe, une déclaration d'amitié (utilisant le mot-clé friend) permet d'indiquer au compilateur qu'une autre classe ou fonction est désormais une amie. En C++, un ami (friend) est une classe ou une fonction (membre ou non membre) à qui l'on a accordé un accès complet aux membres privés et protégés d'une autre classe. Ainsi, une classe peut accorder sélectivement à d'autres classes ou fonctions un accès complet à ses membres, sans rien changer par ailleurs.

Point clé

L'amitié est toujours accordée par la classe dont les membres seront accédés (et non par la classe ou la fonction qui souhaite y accéder). Grâce aux contrôles d'accès et à l'octroi d'amitié, une classe conserve toujours la maîtrise de qui peut accéder à ses membres.

Par exemple, si notre classe de stockage déclarait la classe d'affichage comme amie, alors la classe d'affichage pourrait accéder directement à tous les membres de la classe de stockage. Elle pourrait utiliser cet accès direct pour implémenter l'affichage des données de la classe de stockage, tout en restant structurellement séparée.

La déclaration d'amitié n'est pas soumise aux contrôles d'accès : peu importe donc l'endroit du corps de la classe où elle est placée.

Maintenant que nous savons ce qu'est un ami, examinons des exemples concrets où l'amitié est accordée à des fonctions non membres, à des fonctions membres et à d'autres classes. Nous traiterons des fonctions amies non membres dans cette leçon, puis nous étudierons les classes amies et les fonctions membres amies dans la leçon suivante 15.9 -- Classes amies et fonctions membres amies.

Fonctions amies non membres

Une fonction amie est une fonction (membre ou non membre) qui peut accéder aux membres privés et protégés d'une classe comme si elle était membre de cette classe. À tous autres égards, la fonction amie est une fonction ordinaire.

Examinons un exemple simple d'une classe qui déclare amie une fonction non membre :

#include <iostream>

class Accumulator
{
private:
    int m_value { 0 };

public:
    void add(int value) { m_value += value; }

    // Voici la déclaration d'amitié qui fait de la fonction non membre void print(const Accumulator& accumulator) une amie de Accumulator
    friend void print(const Accumulator& accumulator);
};

void print(const Accumulator& accumulator)
{
    // Comme print() est une amie de Accumulator
    // elle peut accéder aux membres privés de Accumulator
    std::cout << accumulator.m_value;
}

int main()
{
    Accumulator acc{};
    acc.add(5); // ajoute 5 à l'accumulateur

    print(acc); // appelle la fonction non membre print()

    return 0;
}

Dans cet exemple, nous avons déclaré une fonction non membre nommée print() qui prend un objet de la classe Accumulator. Comme print() n'est pas membre de la classe Accumulator, elle ne pourrait normalement pas accéder au membre privé m_value. Cependant, la classe Accumulator contient une déclaration d'amitié qui fait de print(const Accumulator& accumulator) une amie : cet accès devient donc autorisé.

Notez que, comme print() est une fonction non membre (et ne possède donc pas d'objet implicite), nous devons passer explicitement un objet Accumulator à print() pour qu'elle travaille dessus.

Définir une fonction amie non membre à l'intérieur d'une classe

Tout comme les fonctions membres peuvent être définies à l'intérieur d'une classe si on le souhaite, les fonctions amies non membres peuvent également l'être. L'exemple suivant définit la fonction amie non membre print() à l'intérieur de la classe Accumulator :

#include <iostream>

class Accumulator
{
private:
    int m_value { 0 };

public:
    void add(int value) { m_value += value; }

    // Les fonctions amies définies à l'intérieur d'une classe sont des fonctions non membres
    friend void print(const Accumulator& accumulator)
    {
        // Comme print() est une amie de Accumulator
        // elle peut accéder aux membres privés de Accumulator
        std::cout << accumulator.m_value;
    }
};

int main()
{
    Accumulator acc{};
    acc.add(5); // ajoute 5 à l'accumulateur

    print(acc); // appelle la fonction non membre print()

    return 0;
}

Bien que l'on puisse supposer que, puisque print() est définie à l'intérieur de Accumulator, elle en est membre, ce n'est pas le cas. Comme print() est définie comme amie, elle est traitée comme une fonction non membre (exactement comme si elle avait été définie à l'extérieur de Accumulator).

Préférer syntaxiquement une fonction amie non membre

En introduction de cette leçon, nous avons mentionné que l'on pouvait parfois préférer une fonction non membre à une fonction membre. Montrons un exemple de cela.

#include <iostream>

class Value
{
private:
    int m_value{};

public:
    explicit Value(int v): m_value { v }  { }

    bool isEqualToMember(const Value& v) const;
    friend bool isEqualToNonmember(const Value& v1, const Value& v2);
};

bool Value::isEqualToMember(const Value& v) const
{
    return m_value == v.m_value;
}

bool isEqualToNonmember(const Value& v1, const Value& v2)
{
    return v1.m_value == v2.m_value;
}

int main()
{
    Value v1 { 5 };
    Value v2 { 6 };

    std::cout << v1.isEqualToMember(v2) << '\n';
    std::cout << isEqualToNonmember(v1, v2) << '\n';

    return 0;
}

Dans cet exemple, nous avons défini deux fonctions similaires qui vérifient si deux objets Value sont égaux. isEqualToMember() est une fonction membre, et isEqualToNonmember() est une fonction non membre. Concentrons-nous sur la manière dont ces fonctions sont définies.

Dans isEqualToMember(), un objet est passé implicitement et l'autre explicitement. L'implémentation de la fonction reflète cette différence : il faut garder à l'esprit que m_value appartient à l'objet implicite, alors que v.m_value appartient au paramètre explicite.

Dans isEqualToNonmember(), les deux objets sont passés explicitement. Cela conduit à une implémentation plus parallèle, car le membre m_value est toujours préfixé explicitement par un paramètre explicite.

Vous pouvez tout de même préférer la syntaxe d'appel v1.isEqualToMember(v2) à isEqualToNonmember(v1, v2). Mais lorsque nous aborderons la surcharge d'opérateurs, ce sujet reviendra.

Amis multiples

Une fonction peut être amie de plusieurs classes à la fois. Par exemple, considérons l'exemple suivant :

#include <iostream>

class Humidity; // déclaration anticipée de Humidity

class Temperature
{
private:
    int m_temp { 0 };
public:
    explicit Temperature(int temp) : m_temp { temp } { }

    friend void printWeather(const Temperature& temperature, const Humidity& humidity); // déclaration anticipée nécessaire pour cette ligne
};

class Humidity
{
private:
    int m_humidity { 0 };
public:
    explicit Humidity(int humidity) : m_humidity { humidity } {  }

    friend void printWeather(const Temperature& temperature, const Humidity& humidity);
};

void printWeather(const Temperature& temperature, const Humidity& humidity)
{
    std::cout << "The temperature is " << temperature.m_temp <<
       " and the humidity is " << humidity.m_humidity << '\n';
}

int main()
{
    Humidity hum { 10 };
    Temperature temp { 12 };

    printWeather(temp, hum);

    return 0;
}

Trois points méritent d'être notés dans cet exemple. Premièrement, comme printWeather() utilise Humidity et Temperature de la même manière, il n'est pas vraiment logique qu'elle soit membre de l'une ou de l'autre. Une fonction non membre convient mieux. Deuxièmement, comme printWeather() est amie de Humidity et de Temperature, elle peut accéder aux données privées des objets de ces deux classes. Enfin, remarquez la ligne suivante en haut de l'exemple :

class Humidity;

Il s'agit d'une déclaration anticipée de class Humidity. Les déclarations anticipées de classes jouent le même rôle que les déclarations anticipées de fonctions : elles signalent au compilateur l'existence d'un identifiant qui sera défini plus tard. Cependant, contrairement aux fonctions, les classes n'ont ni type de retour ni paramètres, si bien que les déclarations anticipées de classes prennent toujours la forme simple class NomDeClasse (sauf dans le cas des modèles de classes).

Sans cette ligne, le compilateur nous signalerait qu'il ne sait pas ce qu'est un Humidity lors de l'analyse de la déclaration d'amitié à l'intérieur de Temperature.

L'amitié ne viole-t-elle pas le principe de masquage des données ?

Non. L'amitié est accordée par la classe qui réalise le masquage des données, dans l'attente que l'amie accède à ses membres privés. Considérez un ami comme une extension de la classe elle-même, avec les mêmes droits d'accès. Par conséquent, cet accès est attendu et ne constitue pas une violation.

Utilisée correctement, l'amitié peut rendre un programme plus facile à maintenir, en permettant de séparer des fonctionnalités lorsque cela a du sens du point de vue de la conception (au lieu de devoir les garder ensemble pour des raisons de contrôle d'accès). Ou lorsqu'il est plus pertinent d'utiliser une fonction non membre plutôt qu'une fonction membre.

Cependant, comme les amis ont un accès direct à l'implémentation d'une classe, les modifications de l'implémentation de la classe imposeront généralement des modifications aussi aux amis. Si une classe possède de nombreux amis (ou si ces amis ont eux-mêmes des amis), cela peut provoquer un effet de propagation.

Lorsque vous implémentez une fonction amie, privilégiez autant que possible l'interface publique plutôt qu'un accès direct aux membres. Cela protégera votre fonction amie contre de futures modifications de l'implémentation et réduira le nombre de codes à modifier et/ou à retester par la suite.

Bonne pratique

Une fonction amie doit privilégier l'utilisation de l'interface de la classe plutôt qu'un accès direct, chaque fois que cela est possible.

Préférer les fonctions non amies aux fonctions amies

Dans la leçon 14.8 -- Les avantages du masquage des données (encapsulation), nous avons indiqué qu'il fallait privilégier les fonctions non membres aux fonctions membres. Pour les mêmes raisons, il faut privilégier les fonctions non amies aux fonctions amies.

Par exemple, dans l'exemple suivant, si l'implémentation de Accumulator est modifiée (par exemple si nous renommons m_value), l'implémentation de print() devra elle aussi être modifiée :

#include <iostream>

class Accumulator
{
private:
    int m_value { 0 }; // si nous renommons ceci

public:
    void add(int value) { m_value += value; } // nous devons modifier ceci

    friend void print(const Accumulator& accumulator);
};

void print(const Accumulator& accumulator)
{
    std::cout << accumulator.m_value; // et nous devons modifier ceci
}

int main()
{
    Accumulator acc{};
    acc.add(5); // ajoute 5 à l'accumulateur

    print(acc); // appelle la fonction non membre print()

    return 0;
}

Une meilleure idée consiste à procéder ainsi :

#include <iostream>

class Accumulator
{
private:
    int m_value { 0 };

public:
    void add(int value) { m_value += value; }
    int value() const { return m_value; } // ajout de cette fonction d'accès raisonnable
};

void print(const Accumulator& accumulator) // n'est plus une amie de Accumulator
{
    std::cout << accumulator.value(); // utilise la fonction d'accès au lieu d'un accès direct
}

int main()
{
    Accumulator acc{};
    acc.add(5); // ajoute 5 à l'accumulateur

    print(acc); // appelle la fonction non membre print()

    return 0;
}

Dans cet exemple, print() utilise la fonction d'accès value() pour obtenir la valeur de m_value au lieu d'accéder directement à m_value. Désormais, si l'implémentation de Accumulator est modifiée, print() n'aura pas besoin d'être mise à jour.

Bonne pratique

Privilégiez l'implémentation d'une fonction comme non-amie chaque fois que cela est possible et raisonnable.

Soyez prudent lorsque vous ajoutez de nouveaux membres à l'interface publique d'une classe existante, car chaque fonction (même triviale) ajoute un certain niveau d'encombrement et de complexité. Dans le cas de Accumulator ci-dessus, il est tout à fait raisonnable de disposer d'une fonction d'accès pour obtenir la valeur accumulée courante. Dans des cas plus complexes, il peut être préférable d'utiliser l'amitié plutôt que d'ajouter de nombreuses fonctions d'accès à l'interface d'une classe.
