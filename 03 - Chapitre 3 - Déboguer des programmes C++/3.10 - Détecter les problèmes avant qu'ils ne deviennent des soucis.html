3.10 — Détecter les problèmes avant qu'ils ne deviennent des soucis

Lorsque vous commettez une erreur sémantique, cette erreur peut ou non être immédiatement visible à l'exécution de votre programme. Un problème peut rester caché dans votre code pendant longtemps, jusqu'à ce qu'un code nouvellement ajouté ou un changement de circonstances le transforme en dysfonctionnement du programme. Plus une erreur reste longtemps dans la base de code avant d'être trouvée, plus il est probable qu'elle soit difficile à localiser, et ce qui aurait pu être facile à corriger au départ se transforme en une chasse aux bogues qui consomme du temps et de l'énergie.

Que peut-on faire pour éviter cela ?

Ne pas commettre d'erreurs

La meilleure solution consiste évidemment à ne pas faire d'erreurs. Voici une liste de conseils qui peuvent vous aider à en éviter :

  • Suivez les bonnes pratiques.
  • Ne programmez pas lorsque vous êtes fatigué ou frustré. Faites une pause et revenez-y plus tard.
  • Connaissez les pièges courants du langage (tous ces comportements que nous vous déconseillons).
  • Ne laissez pas vos fonctions devenir trop longues.
  • Préférez la bibliothèque standard à votre propre code, lorsque c'est possible.
  • Commentez abondamment votre code.
  • Commencez par des solutions simples, puis ajoutez progressivement de la complexité.
  • Évitez les solutions astucieuses ou peu évidentes.
  • Optimisez pour la lisibilité et la maintenabilité, et non pour la performance.

Tout le monde sait que déboguer est deux fois plus difficile que d'écrire un programme. Alors, si vous êtes aussi astucieux que possible au moment de l'écrire, comment pourrez-vous le déboguer ?

—Brian Kernighan, « The Elements of Programming Style », 2e édition

Refactoriser votre code

À mesure que vous ajoutez de nouvelles fonctionnalités à vos programmes (« changements de comportement »), vous constaterez que certaines fonctions s'allongent. Plus une fonction est longue, plus elle devient complexe et difficile à comprendre.

Une façon de remédier à cela consiste à découper une longue fonction en plusieurs fonctions plus courtes. Ce processus, qui consiste à modifier la structure de votre code sans changer son comportement, s'appelle refactorisation (refactoring). Le but de la refactorisation est de réduire la complexité de votre programme en améliorant son organisation et sa modularité.

Alors, à partir de quelle longueur une fonction est-elle trop longue ? Une fonction qui occupe un écran entier en hauteur est généralement considérée comme trop longue : si vous devez faire défiler l'écran pour lire la fonction entière, sa compréhensibilité baisse nettement. Idéalement, une fonction devrait compter moins de dix lignes. Les fonctions de moins de cinq lignes sont encore préférables.

Gardez à l'esprit que l'objectif est de maximiser la compréhension et la maintenabilité, et non de minimiser la longueur des fonctions. Abandonner les bonnes pratiques ou utiliser des techniques obscures pour économiser une ou deux lignes ne rend pas service à votre code.

Point clé

Lorsque vous modifiez votre code, effectuez soit des changements de comportement, soit des changements de structure, puis testez de nouveau l'exactitude du programme. Effectuer les deux types de changements en même temps conduit souvent à davantage d'erreurs, et à des erreurs plus difficiles à trouver.

Introduction à la programmation défensive

Les erreurs ne viennent pas seulement de vous (par exemple une logique incorrecte) : elles peuvent aussi survenir lorsque les utilisateurs emploient l'application d'une façon que vous n'aviez pas anticipée. Par exemple, si vous demandez à l'utilisateur de saisir un entier et qu'il saisit une lettre, comment votre programme réagit-il ? À moins que vous n'ayez anticipé ce cas et ajouté une gestion d'erreur, probablement pas très bien.

La programmation défensive (defensive programming) consiste pour le programmeur à anticiper toutes les façons dont le logiciel pourrait être mal utilisé, que ce soit par les utilisateurs finaux ou par d'autres développeurs (y compris le programmeur lui-même) qui emploient le code. Ces mauvaises utilisations peuvent souvent être détectées, puis atténuées (par exemple en demandant à un utilisateur ayant saisi une mauvaise valeur de réessayer).

Nous explorerons les sujets liés à la gestion des erreurs dans de prochaines leçons.

Trouver rapidement les erreurs

Comme il est difficile de ne pas commettre d'erreurs dans les grands programmes, la meilleure solution suivante consiste à repérer rapidement celles que vous commettez.

La meilleure façon d'y parvenir est de programmer petit à petit, puis de tester votre code pour vous assurer qu'il fonctionne.

Cependant, il existe d'autres techniques que nous pouvons également utiliser.

Introduction aux tests de fonctions

Une façon courante de mettre au jour les problèmes d'un programme consiste à écrire des fonctions de test qui « exercent » le code que vous avez écrit. Voici une tentative rudimentaire, plutôt à des fins d'illustration :

#include <iostream>

int add(int x, int y)
{
    return x + y;
}

void testadd()
{
    std::cout << "This function should print: 2 0 0 -2\n";
    std::cout << add(1, 1) << ' ';
    std::cout << add(-1, 1) << ' ';
    std::cout << add(1, -1) << ' ';
    std::cout << add(-1, -1) << ' ';
}

int main()
{
    testadd();

    return 0;
}

La fonction testadd() teste la fonction add() en l'appelant avec différentes valeurs. Si toutes les valeurs correspondent à nos attentes, nous pouvons raisonnablement être confiants dans le bon fonctionnement de la fonction. Mieux encore, nous pouvons conserver cette fonction et l'exécuter chaque fois que nous modifions la fonction add, afin de nous assurer que nous ne l'avons pas cassée par inadvertance.

Il s'agit d'une forme rudimentaire de test unitaire (unit testing), une méthode de test logiciel qui consiste à vérifier, pour de petites unités de code source, si elles sont correctes.

Comme pour les bibliothèques de journalisation, il existe de nombreuses bibliothèques de test unitaire tierces que vous pouvez utiliser. Il est également possible d'en écrire une soi-même, mais il nous faudra davantage de fonctionnalités du langage pour traiter le sujet correctement. Nous reviendrons sur ce point dans une prochaine leçon.

Introduction aux contraintes

Les techniques fondées sur les contraintes consistent à ajouter du code supplémentaire (qui peut être retiré d'une version non destinée au débogage, si on le souhaite) pour vérifier qu'un ensemble d'hypothèses ou d'attentes n'est pas violé.

Par exemple, si nous écrivions une fonction calculant la factorielle d'un nombre, qui attend un argument non négatif, la fonction pourrait vérifier que l'appelant lui a bien transmis un nombre non négatif avant de poursuivre. Si l'appelant transmet un nombre négatif, la fonction pourrait signaler l'erreur immédiatement plutôt que de produire un résultat indéterminé, ce qui aide à détecter le problème dès son apparition.

Une méthode courante pour y parvenir consiste à utiliser assert et static_assert, que nous présentons dans la leçon 9.6 -- Assert et static_assert.

Recherche générale de problèmes

Les programmeurs ont tendance à commettre certains types d'erreurs courantes, et certaines de ces erreurs peuvent être détectées par des programmes entraînés à les repérer. Ces programmes, généralement appelés outils d'analyse statique (static analysis tools) et parfois informellement linters, analysent votre code source pour identifier des problèmes sémantiques précis (dans ce contexte, statique signifie que ces outils analysent le code source sans l'exécuter). Les problèmes relevés par les outils d'analyse statique peuvent ou non être la cause d'un problème particulier que vous rencontrez, mais ils peuvent aider à signaler les zones fragiles du code ou les points susceptibles de poser problème dans certaines circonstances.

Vous disposez déjà d'un outil d'analyse statique : votre compilateur ! En plus de vérifier que votre programme est syntaxiquement correct, la plupart des compilateurs C++ modernes effectuent une analyse statique légère pour détecter certains problèmes courants. Par exemple, de nombreux compilateurs vous avertiront si vous tentez d'utiliser une variable non initialisée. Si ce n'est pas déjà fait, configurer le niveau des avertissements et des erreurs de votre compilateur (voir la leçon 0.11 -- Configurer votre compilateur : niveaux d'avertissement et d'erreur) peut aider à les faire remonter.

De nombreux outils d'analyse statique existent, dont certains peuvent identifier plus de 300 types d'erreurs de programmation. Pour nos petits programmes à vocation pédagogique, l'utilisation d'un outil d'analyse statique est facultative, mais elle peut vous aider à repérer les endroits où votre code ne respecte pas les bonnes pratiques. Pour les grands programmes, l'utilisation d'un outil d'analyse statique est fortement recommandée, car il peut faire ressortir des dizaines, voire des centaines de problèmes potentiels.

Bonne pratique

Utilisez un outil d'analyse statique sur vos programmes pour repérer les endroits où votre code ne respecte pas les bonnes pratiques.

Pour les utilisateurs de Visual Studio

Visual Studio 2019 et les versions ultérieures intègrent un outil d'analyse statique. Vous pouvez y accéder via Générer > Exécuter l'analyse du code sur la solution (Alt+F11).
