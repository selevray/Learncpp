23.3 — Agrégation

Dans la leçon précédente 23.2 -- Composition, nous avons indiqué que la composition d'objets est le processus consistant à créer des objets complexes à partir d'objets plus simples. Nous avons aussi évoqué un type de composition d'objets, appelé composition (composition). Dans une relation de composition, l'objet entier est responsable de l'existence de ses parties.

Dans cette leçon, nous allons examiner l'autre sous-type de composition d'objets, appelé agrégation.

Agrégation

Pour qualifier une relation d'agrégation (aggregation), un objet entier et ses parties doivent respecter les conditions suivantes :

  • La partie (membre) fait partie de l'objet (classe)
  • La partie (membre) peut (si besoin) appartenir à plus d'un objet (classe) à la fois
  • L'existence de la partie (membre) n'est pas gérée par l'objet (classe)
  • La partie (membre) ne connaît pas l'existence de l'objet (classe)

Comme une composition, une agrégation reste une relation tout-partie, où les parties sont contenues dans le tout, et c'est une relation unidirectionnelle. Cependant, contrairement à une composition, les parties peuvent appartenir à plusieurs objets à la fois, et l'objet entier n'est pas responsable de l'existence et de la durée de vie des parties. Lorsqu'une agrégation est créée, elle n'est pas responsable de la création des parties. Lorsqu'elle est détruite, elle n'est pas responsable de la destruction des parties.

Prenons par exemple la relation entre une personne et son adresse domicile. Dans cet exemple, par simplicité, nous dirons que chaque personne a une adresse. Cependant, cette adresse peut appartenir à plusieurs personnes à la fois : par exemple, à vous et à votre colocataire ou à votre conjoint. En revanche, cette adresse n'est pas gérée par la personne : l'adresse existait probablement avant l'arrivée de la personne, et existera encore après son départ. De plus, une personne sait à quelle adresse elle habite, mais les adresses ne savent pas quelles personnes y vivent. Il s'agit donc d'une relation d'agrégation.

Considérons aussi une voiture et un moteur. Le moteur fait partie de la voiture. Et bien qu'il appartienne à la voiture, il peut aussi appartenir à d'autres choses, comme la personne qui possède la voiture. La voiture n'est pas responsable de la création ni de la destruction du moteur. Et si la voiture sait qu'elle a un moteur (elle doit le savoir pour aller quelque part), le moteur ne sait pas qu'il fait partie de la voiture.

Lorsqu'on modélise des objets physiques, le terme « détruit » peut poser problème. On pourrait objecter : « Si une météorite tombait du ciel et écrasait la voiture, les pièces de la voiture ne seraient-elles pas toutes détruites aussi ? » Oui, bien sûr. Mais c'est la faute de la météorite. L'essentiel est que la voiture n'est pas responsable de la destruction de ses parties (mais une force extérieure peut l'être).

On peut dire que l'agrégation modélise des relations « a-un » (un département a des enseignants, la voiture a un moteur).

Comme pour une composition, les parties d'une agrégation peuvent être uniques ou multiples.

Implémenter des agrégations

Comme les agrégations et les compositions sont toutes deux des relations tout-partie, elles s'implémentent presque de la même façon, et la différence est surtout sémantique. Dans une composition, on ajoute typiquement les parties comme membres ordinaires (ou sous forme de pointeurs lorsque la classe composite gère elle-même l'allocation et la désallocation).

Dans une agrégation, on ajoute aussi les parties comme membres. Cependant, ces membres sont généralement des références ou des pointeurs qui désignent des objets créés en dehors de la portée de la classe. Par conséquent, une agrégation prend habituellement en paramètres du constructeur les objets qu'elle va pointer, ou bien démarre vide et les sous-objets sont ajoutés plus tard via des fonctions d'accès ou des opérateurs.

Comme ces parties existent en dehors de la portée de la classe, lorsque la classe est détruite, le membre pointeur ou référence est détruit (mais pas supprimé). Les parties elles-mêmes continuent donc d'exister.

Examinons plus en détail l'exemple Teacher et Department. Dans cet exemple, nous faisons quelques simplifications : premièrement, le département ne contient qu'un seul enseignant. Deuxièmement, l'enseignant ignore dans quel département il se trouve.

#include <iostream>
#include <string>
#include <string_view>

class Teacher
{
private:
  std::string m_name{};

public:
  Teacher(std::string_view name)
      : m_name{ name }
  {
  }

  const std::string& getName() const { return m_name; }
};

class Department
{
private:
  const Teacher& m_teacher; // This dept holds only one teacher for simplicity, but it could hold many teachers

public:
  Department(const Teacher& teacher)
      : m_teacher{ teacher }
  {
  }
};

int main()
{
  // Create a teacher outside the scope of the Department
  Teacher bob{ "Bob" }; // create a teacher

  {
    // Create a department and use the constructor parameter to pass
    // the teacher to it.
    Department department{ bob };

  } // department goes out of scope here and is destroyed

  // bob still exists here, but the department doesn't

  std::cout << bob.getName() << " still exists!\n";

  return 0;
}

Ici, bob est créé indépendamment de department, puis passé au constructeur de department. Lorsque department est détruit, la référence m_teacher est détruite, mais l'enseignant lui-même ne l'est pas : il continue d'exister jusqu'à sa destruction indépendante plus tard dans main().

Choisir la relation adaptée à ce que vous modélisez

Bien qu'il puisse sembler un peu absurde, dans l'exemple ci-dessus, que les Teacher ne sachent pas pour quel Department ils travaillent, cela peut parfaitement convenir dans le contexte d'un programme donné. Lorsque vous déterminez quel type de relation implémenter, choisissez la relation la plus simple qui répond à vos besoins, et non celle qui semble la mieux correspondre à un contexte réel.

Par exemple, si vous écrivez un simulateur d'atelier de carrosserie, vous pourriez implémenter voiture et moteur comme une agrégation, afin que le moteur puisse être retiré et rangé sur une étagère pour plus tard. En revanche, si vous écrivez une simulation de course automobile, vous pourriez implémenter voiture et moteur comme une composition, puisque le moteur n'existera jamais en dehors de la voiture dans ce contexte.

Bonne pratique

Implémentez le type de relation le plus simple qui répond aux besoins de votre programme, et non ce qui semble correct dans la vie réelle.

Résumé de la composition et de l'agrégation

Compositions :

  • Utilisent typiquement des membres ordinaires- Peuvent utiliser des membres pointeurs si la classe gère elle-même l'allocation et la désallocation des objets- Sont responsables de la création et de la destruction des parties

Agrégations :

  • Utilisent typiquement des membres pointeurs ou références qui désignent des objets vivant en dehors de la portée de la classe agrégat- Ne sont pas responsables de la création ni de la destruction des parties

Il est à noter que les concepts de composition et d'agrégation peuvent être librement mélangés au sein d'une même classe. Il est tout à fait possible d'écrire une classe responsable de la création et de la destruction de certaines parties, mais pas d'autres. Par exemple, notre classe Department pourrait avoir un nom et un Teacher. Le nom serait probablement ajouté au Department par composition, et serait créé et détruit avec le Department. En revanche, le Teacher serait ajouté au département par agrégation, et créé et détruit indépendamment.

Bien que les agrégations puissent être extrêmement utiles, elles sont aussi potentiellement plus dangereuses, car elles ne gèrent pas la désallocation de leurs parties. Ces désallocations sont laissées à une entité externe. Si cette entité externe ne possède plus de pointeur ou de référence vers les parties abandonnées, ou si elle oublie simplement de faire le nettoyage (en supposant que la classe s'en chargera), alors de la mémoire sera perdue (fuite mémoire).

Pour cette raison, il faut privilégier les compositions aux agrégations.

Quelques avertissements et corrections

Pour diverses raisons historiques et contextuelles, contrairement à la composition, la définition de l'agrégation n'est pas précise : vous pourrez donc rencontrer, dans d'autres ouvrages de référence, une définition différente de la nôtre. Ce n'est pas grave, mais il faut en être conscient.

Une dernière remarque : dans la leçon 13.7 -- Introduction aux structures, aux membres et à la sélection de membre, nous avons défini les types de données agrégats (comme les struct et les class) comme des types de données regroupant plusieurs variables. Vous rencontrerez peut-être aussi le terme classe agrégat (aggregate class) au cours de votre apprentissage du C++ : il désigne une struct ou une classe sans constructeur fourni, sans destructeur ni surcharge d'affectation fournis, dont tous les membres sont publics, et qui n'utilise pas l'héritage. C'est essentiellement une struct de type POD (plain-old-data). Malgré la similitude des noms, agrégats et agrégation sont différents et ne doivent pas être confondus.

std::reference_wrapper

Dans l'exemple Department/Teacher ci-dessus, nous avons utilisé une référence dans Department pour stocker le Teacher. Cela fonctionne bien s'il n'y a qu'un seul Teacher, mais que faire si un Department a plusieurs Teachers ? Nous aimerions stocker ces Teachers dans une liste d'un certain type (par exemple un std::vector), mais les tableaux de taille fixe et les différentes listes de la bibliothèque standard ne peuvent pas contenir de références (car les éléments d'une liste doivent pouvoir être affectés, et une référence ne peut pas être réaffectée).

std::vector<const Teacher&> m_teachers{}; // Illegal

Au lieu de références, nous pourrions utiliser des pointeurs, mais cela ouvrirait la possibilité de stocker ou de passer des pointeurs nuls. Dans l'exemple Department/Teacher, nous ne voulons pas autoriser les pointeurs nuls. Pour résoudre ce problème, il existe std::reference_wrapper.

En substance, std::reference_wrapper est une classe qui se comporte comme une référence, mais qui autorise aussi l'affectation et la copie, et elle est donc compatible avec des listes comme std::vector.

La bonne nouvelle est qu'il n'est pas indispensable de comprendre son fonctionnement pour l'utiliser. Il vous suffit de connaître trois points :

  1. std::reference_wrapper se trouve dans l'en-tête <functional>.
  2. Lorsque vous créez votre objet encapsulé par std::reference_wrapper, cet objet ne peut pas être un objet anonyme (car les objets anonymes ont une portée d'expression, ce qui laisserait la référence pendante).
  3. Pour récupérer votre objet depuis std::reference_wrapper, vous utilisez la fonction membre get().

Voici un exemple utilisant std::reference_wrapper dans un std::vector :

#include <functional> // std::reference_wrapper
#include <iostream>
#include <vector>
#include <string>

int main()
{
  std::string tom{ "Tom" };
  std::string berta{ "Berta" };

  std::vector<std::reference_wrapper<std::string>> names{ tom, berta }; // these strings are stored by reference, not value

  std::string jim{ "Jim" };

  names.emplace_back(jim);

  for (auto name : names)
  {
    // Use the get() member function to get the referenced string.
    name.get() += " Beam";
  }

  std::cout << jim << '\n'; // prints Jim Beam

  return 0;
}

Pour créer un vecteur de références constantes, il faut ajouter const devant le std::string, comme ceci :

// Vector of const references to std::string
std::vector<std::reference_wrapper<const std::string>> names{ tom, berta };

Quiz

Question n° 1

Implémenteriez-vous plutôt les éléments suivants sous forme de composition ou d'agrégation ?
a) Une balle qui a une couleur
b) Un employeur qui emploie plusieurs personnes
c) Les départements d'une université
d) Votre âge
e) Un sac de billes

Solution

a) Composition : la couleur est une propriété intrinsèque de la balle.
b) Agrégation : un employeur ne commence pas avec des employés et, espérons-le, ne détruit pas tous ses employés lorsqu'il fait faillite.
c) Composition : les départements ne peuvent pas exister en l'absence d'université.
d) Composition : votre âge est une propriété intrinsèque de vous.
e) Agrégation : le sac et les billes qu'il contient ont des existences indépendantes.

Indice

Indice : stockez les enseignants dans un std::vector

std::vector<std::reference_wrapper<const Teacher>> m_teachers{};
Solution 
#include <functional> // std::reference_wrapper
#include <iostream>
#include <string>
#include <string_view>
#include <vector>

class Teacher
{
private:
  std::string m_name{};

public:
  Teacher(std::string_view name)
      : m_name{ name }
  {
  }

  const std::string& getName() const { return m_name; }
};

class Department
{
private:
  std::vector<std::reference_wrapper<const Teacher>> m_teachers{};

public:
  Department() = default;

  // Pass by regular reference. The user of the Department class shouldn't care
  // about how it's implemented.
  void add(const Teacher& teacher)
  {
    m_teachers.emplace_back(teacher);
  }

  friend std::ostream& operator<<(std::ostream& out, const Department& department)
  {
    out << "Department: ";

    for (const auto& teacher : department.m_teachers)
    {
      out << teacher.get().getName() << ' ';
    }

    out << '\n';

    return out;
  }
};

int main()
{
  // Create a teacher outside the scope of the Department
  Teacher t1{ "Bob" };
  Teacher t2{ "Frank" };
  Teacher t3{ "Beth" };

  {
    // Create a department and add some Teachers to it
    Department department{}; // create an empty Department

    department.add(t1);
    department.add(t2);
    department.add(t3);

    std::cout << department;

  } // department goes out of scope here and is destroyed

  std::cout << t1.getName() << " still exists!\n";
  std::cout << t2.getName() << " still exists!\n";
  std::cout << t3.getName() << " still exists!\n";

  return 0;
}
