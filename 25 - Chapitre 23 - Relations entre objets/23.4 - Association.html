23.4 — Association

Dans les deux leçons précédentes, nous avons étudié deux types de composition d'objets : la composition et l'agrégation. La composition d'objets sert à modéliser des relations où un objet complexe est construit à partir d'un ou de plusieurs objets plus simples (ses parties).

Dans cette leçon, nous allons examiner une relation plus faible entre deux objets par ailleurs indépendants, appelée association. Contrairement aux relations de composition d'objets, une association n'implique aucune relation tout/partie.

Association

Pour qu'une relation soit qualifiée d'association, un objet et un autre objet doivent satisfaire les conditions suivantes :

  • L'objet associé (membre) est par ailleurs indépendant de l'objet (classe)
  • L'objet associé (membre) peut appartenir à plus d'un objet (classe) à la fois
  • L'existence de l'objet associé (membre) n'est pas gérée par l'objet (classe)
  • L'objet associé (membre) peut connaître ou non l'existence de l'objet (classe)

Contrairement à la composition ou à l'agrégation, où la partie fait partie intégrante de l'objet englobant, dans une association l'objet associé est indépendant de l'objet. Comme dans une agrégation, l'objet associé peut appartenir simultanément à plusieurs objets et n'est pas géré par ceux-ci. Cependant, contrairement à l'agrégation, où la relation est toujours unidirectionnelle, dans une association la relation peut être unidirectionnelle ou bidirectionnelle (lorsque les deux objets se connaissent mutuellement).

La relation entre médecins et patients est un excellent exemple d'association. Le médecin entretient clairement une relation avec ses patients, mais conceptuellement il ne s'agit pas d'une relation tout/partie (composition d'objets). Un médecin peut recevoir de nombreux patients dans la journée, et un patient peut consulter plusieurs médecins (peut-être souhaite-t-il un second avis, ou consulte-t-il différents types de spécialistes). La durée de vie de chacun des deux objets n'est liée à celle de l'autre en aucune façon.

On peut dire que l'association modélise une relation « utilise-un » (uses-a). Le médecin « utilise » le patient (pour gagner sa vie). Le patient utilise le médecin (pour les besoins de santé qui sont les siens).

Implémentation des associations

Les associations étant un type de relation très général, elles peuvent être implémentées de nombreuses façons différentes. Cependant, le plus souvent, les associations sont implémentées à l'aide de pointeurs, l'objet pointant alors vers l'objet associé.

Dans cet exemple, nous allons implémenter une relation bidirectionnelle Médecin/Patient, car il est logique que les médecins connaissent leurs patients, et réciproquement.

#include <functional> // reference_wrapper
#include <iostream>
#include <string>
#include <string_view>
#include <vector>

// Comme Doctor et Patient ont une dépendance circulaire, nous allons déclarer Patient à l'avance
class Patient;

class Doctor
{
private:
    std::string m_name{};
    std::vector<std::reference_wrapper<const Patient>> m_patient{};

public:
    Doctor(std::string_view name) :
        m_name{ name }
    {
    }

    void addPatient(Patient& patient);

    // Nous implémenterons cette fonction après Patient, car nous avons besoin que Patient soit défini à ce moment-là
    friend std::ostream& operator<<(std::ostream& out, const Doctor& doctor);

    const std::string& getName() const { return m_name; }
};

class Patient
{
private:
    std::string m_name{};
    std::vector<std::reference_wrapper<const Doctor>> m_doctor{}; // pour pouvoir l'utiliser ici

    // Nous rendons addDoctor privée, car nous ne voulons pas qu'elle soit utilisée publiquement.
    // On doit utiliser Doctor::addPatient() à la place, qui est exposée publiquement
    void addDoctor(const Doctor& doctor)
    {
        m_doctor.push_back(doctor);
    }

public:
    Patient(std::string_view name)
        : m_name{ name }
    {
    }

    // Nous implémenterons cette fonction ci-dessous, en parallèle de operator<<(std::ostream&, const Doctor&)
    friend std::ostream& operator<<(std::ostream& out, const Patient& patient);

    const std::string& getName() const { return m_name; }

    // Nous déclarons Doctor::addPatient() comme amie afin qu'elle puisse accéder à la fonction privée Patient::addDoctor()
    friend void Doctor::addPatient(Patient& patient);
};

void Doctor::addPatient(Patient& patient)
{
    // Notre médecin ajoute ce patient
    m_patient.push_back(patient);

    // et le patient ajoute également ce médecin
    patient.addDoctor(*this);
}

std::ostream& operator<<(std::ostream& out, const Doctor& doctor)
{
    if (doctor.m_patient.empty())
    {
        out << doctor.m_name << " has no patients right now";
        return out;
    }

    out << doctor.m_name << " is seeing patients: ";
    for (const auto& patient : doctor.m_patient)
        out << patient.get().getName() << ' ';

    return out;
}

std::ostream& operator<<(std::ostream& out, const Patient& patient)
{
    if (patient.m_doctor.empty())
    {
        out << patient.getName() << " has no doctors right now";
        return out;
    }

    out << patient.m_name << " is seeing doctors: ";
    for (const auto& doctor : patient.m_doctor)
        out << doctor.get().getName() << ' ';

    return out;
}

int main()
{
    // Créer un Patient en dehors de la portée du Doctor
    Patient dave{ "Dave" };
    Patient frank{ "Frank" };
    Patient betsy{ "Betsy" };

    Doctor james{ "James" };
    Doctor scott{ "Scott" };

    james.addPatient(dave);

    scott.addPatient(dave);
    scott.addPatient(betsy);

    std::cout << james << '\n';
    std::cout << scott << '\n';
    std::cout << dave << '\n';
    std::cout << frank << '\n';
    std::cout << betsy << '\n';

    return 0;
}

Ce programme affiche :


James is seeing patients: Dave
Scott is seeing patients: Dave Betsy
Dave is seeing doctors: James Scott
Frank has no doctors right now
Betsy is seeing doctors: Scott

En règle générale, évitez les associations bidirectionnelles lorsqu'une association unidirectionnelle suffit, car elles ajoutent de la complexité et sont souvent plus difficiles à écrire sans commettre d'erreurs.

Association réflexive

Il arrive que des objets entretiennent une relation avec d'autres objets du même type. On parle alors d'association réflexive. Un bon exemple d'association réflexive est la relation entre un cours universitaire et ses prérequis (qui sont eux-mêmes des cours universitaires).

Considérons le cas simplifié où un Course ne peut avoir qu'un seul prérequis. Nous pouvons écrire quelque chose comme ceci :

#include <string>
#include <string_view>

class Course
{
private:
    std::string m_name{};
    const Course* m_prerequisite{};

public:
    Course(std::string_view name, const Course* prerequisite = nullptr):
        m_name{ name }, m_prerequisite{ prerequisite }
    {
    }

};

Cela peut conduire à une chaîne d'associations (un cours a un prérequis, qui a lui-même un prérequis, et ainsi de suite…).

Les associations peuvent être indirectes

Dans tous les cas précédents, nous avons utilisé des pointeurs ou des références pour relier directement les objets entre eux. Cependant, dans une association, cela n'est pas strictement nécessaire. Toute donnée permettant de relier deux objets convient. Dans l'exemple suivant, nous montrons comment une classe Driver peut avoir une association unidirectionnelle avec une Car sans inclure de membre pointeur ou référence vers une Car :

#include <iostream>
#include <string>
#include <string_view>

class Car
{
private:
    std::string m_name{};
    int m_id{};

public:
    Car(std::string_view name, int id)
        : m_name{ name }, m_id{ id }
    {
    }

    const std::string& getName() const { return m_name; }
    int getId() const { return m_id; }
};

// Notre CarLot est essentiellement un simple tableau statique de Car et une fonction de recherche permettant de les récupérer.
// Comme il est statique, nous n'avons pas besoin d'allouer un objet de type CarLot pour l'utiliser
namespace CarLot
{
    Car carLot[4] { { "Prius", 4 }, { "Corolla", 17 }, { "Accord", 84 }, { "Matrix", 62 } };

    Car* getCar(int id)
    {
        for (auto& car : carLot)
        {
            if (car.getId() == id)
            {
                return &car;
            }
        }

        return nullptr;
    }
};

class Driver
{
private:
    std::string m_name{};
    int m_carId{}; // nous sommes associés à la Car par son ID plutôt que par un pointeur

public:
    Driver(std::string_view name, int carId)
        : m_name{ name }, m_carId{ carId }
    {
    }

    const std::string& getName() const { return m_name; }
    int getCarId() const { return m_carId; }
};

int main()
{
    Driver d{ "Franz", 17 }; // Franz conduit la voiture d'ID 17

    Car* car{ CarLot::getCar(d.getCarId()) }; // Récupérer cette voiture auprès du parc automobile

    if (car)
        std::cout << d.getName() << " is driving a " << car->getName() << '\n';
    else
        std::cout << d.getName() << " couldn't find his car\n";

    return 0;
}

Dans l'exemple ci-dessus, nous disposons d'un CarLot qui contient nos voitures. Le Driver, qui a besoin d'une voiture, ne possède pas de pointeur vers sa Car : il possède en revanche l'ID de la voiture, que nous pouvons utiliser pour récupérer la Car depuis le CarLot lorsque nous en avons besoin.

Dans cet exemple particulier, procéder ainsi est un peu absurde, puisque récupérer la Car depuis le CarLot nécessite une recherche peu efficace (un pointeur reliant directement les deux objets serait bien plus rapide). Cependant, référencer des éléments par un identifiant unique plutôt que par un pointeur présente des avantages. Par exemple, vous pouvez référencer des objets qui ne sont pas actuellement en mémoire (ils se trouvent peut-être dans un fichier ou dans une base de données, et peuvent être chargés à la demande). De plus, un pointeur occupe 4 ou 8 octets : si la place est précieuse et que le nombre d'objets distincts est relativement faible, les référencer par un entier de 8 ou 16 bits peut économiser beaucoup de mémoire.

Résumé : composition, agrégation et association

Voici un tableau récapitulatif qui vous aidera à retenir la différence entre composition, agrégation et association :

Propriété Composition Agrégation Association
Type de relation Tout/partie Tout/partie Indépendants par ailleurs
Les membres peuvent appartenir à plusieurs classes Non Oui Oui
Existence des membres gérée par la classe Oui Non Non
Directionnalité Unidirectionnelle Unidirectionnelle Unidirectionnelle ou bidirectionnelle
Verbe de la relation Fait partie de A-un Utilise-un
