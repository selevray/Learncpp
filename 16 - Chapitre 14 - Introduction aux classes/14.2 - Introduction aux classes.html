14.2 — Introduction aux classes

Dans le chapitre précédent, nous avons étudié les structs (13.7 -- Introduction aux structs, membres et accès aux membres) et vu qu'ils sont très pratiques pour regrouper plusieurs variables membres dans un seul objet, que l'on peut initialiser et passer en un bloc. Autrement dit, les structs offrent un moyen commode de stocker et de déplacer des valeurs de données liées entre elles.

Considérez le struct suivant :

#include <iostream>

struct Date
{
    int day{};
    int month{};
    int year{};
};

void printDate(const Date& date)
{
    std::cout << date.day << '/' << date.month << '/' << date.year; // on suppose le format JJ/MM/AA
}

int main()
{
    Date date{ 4, 10, 21 }; // initialisation par agrégat
    printDate(date);        // on peut passer le struct entier à une fonction

    return 0;
}

Rappel

Dans ces tutoriels, tous nos structs sont des agrégats. Nous abordons les agrégats dans la leçon 13.8 -- Initialisation par agrégat d'un struct.

Aussi utiles que soient les structs, ils présentent un certain nombre de lacunes qui compliquent la construction de programmes grands et complexes (en particulier lorsqu'ils sont développés par plusieurs personnes).

Le problème des invariants de classe

La principale difficulté des structs est sans doute qu'ils ne fournissent aucun moyen efficace de documenter et de faire respecter les invariants de classe. Dans la leçon 9.6 -- assert et static_assert, nous avons défini un invariant comme « une condition qui doit être vraie pendant l'exécution d'un composant ».

Dans le contexte des types classe (qui comprennent les structs, les classes et les unions), un invariant de classe est une condition qui doit rester vraie pendant toute la durée de vie d'un objet pour que celui-ci reste dans un état valide. Un objet dont l'invariant de classe est violé est dit dans un état invalide, et l'utilisation ultérieure de cet objet peut entraîner un comportement inattendu ou indéfini.

Point clé

Utiliser un objet dont l'invariant de classe a été violé peut entraîner un comportement inattendu ou indéfini.

Considérons d'abord le struct suivant :

struct Pair
{
    int first {};
    int second {};
};

Les membres first et second peuvent être modifiés indépendamment l'un de l'autre et prendre n'importe quelle valeur, donc le struct Pair n'a pas d'invariant.

Considérons maintenant le struct suivant, presque identique :

struct Fraction
{
    int numerator { 0 };
    int denominator { 1 };
};

Les mathématiques nous apprennent qu'une fraction dont le dénominateur vaut 0 n'est pas définie (la valeur d'une fraction est son numérateur divisé par son dénominateur, et une division par 0 n'a pas de sens). Nous voulons donc garantir que le membre denominator d'un objet Fraction ne vaut jamais 0. Si c'est le cas, l'objet Fraction est dans un état invalide, et son utilisation ultérieure peut provoquer un comportement indéfini.

Par exemple :

#include <iostream>

struct Fraction
{
    int numerator { 0 };
    int denominator { 1 }; // invariant de classe : ne devrait jamais valoir 0
};

void printFractionValue(const Fraction& f)
{
     std::cout << f.numerator / f.denominator << '\n';
}

int main()
{
    Fraction f { 5, 0 };   // création d'une Fraction avec un dénominateur nul
    printFractionValue(f); // provoque une erreur de division par zéro

    return 0;
}

Dans cet exemple, nous utilisons un commentaire pour documenter l'invariant de Fraction. Nous fournissons aussi un initialiseur de membre par défaut pour que denominator vaille 1 si l'utilisateur ne fournit pas de valeur d'initialisation. Ainsi, notre objet Fraction reste valide si l'utilisateur décide de l'initialiser par valeur. C'est un début acceptable.

Mais rien ne nous empêche de violer explicitement cet invariant : lorsque nous créons Fraction f, nous utilisons l'initialisation par agrégat pour initialiser explicitement le dénominateur à 0. Cela ne provoque pas de problème immédiat, mais notre objet est désormais dans un état invalide, et toute utilisation ultérieure peut causer un comportement inattendu ou indéfini.

C'est exactement ce que l'on observe plus tard, lorsque nous appelons printFractionValue(f) : le programme se termine à cause d'une erreur de division par zéro.

En passant…

Une petite amélioration consisterait à écrire assert(f.denominator != 0); en début de corps de printFractionValue. Cela ajoute de la valeur documentaire au code et rend plus évidente la précondition violée. Mais, du point de vue du comportement, cela ne change pas grand-chose. Nous voulons vraiment détecter ces problèmes à la source (lorsque le membre reçoit une mauvaise valeur à l'initialisation ou à l'affectation), et non en aval (lorsque cette mauvaise valeur est utilisée).

Vu la relative simplicité de l'exemple Fraction, il n'est pas très difficile d'éviter de créer des objets Fraction invalides. En revanche, dans une base de code plus complexe, qui utilise beaucoup de structs, des structs avec de nombreux membres ou des membres aux relations complexes, il n'est pas toujours évident de savoir quelles combinaisons de valeurs peuvent violer un invariant de classe.

Un invariant de classe plus complexe

L'invariant de Fraction est simple : le membre denominator ne peut pas valoir 0. C'est facile à comprendre sur le plan conceptuel et assez simple à respecter.

Les invariants de classe deviennent plus délicats lorsque les membres d'un struct doivent avoir des valeurs corrélées.

#include <string>

struct Employee
{
    std::string name { };
    char firstInitial { }; // doit toujours contenir le premier caractère de `name` (ou `0`)
};

Dans ce struct (mal conçu), le caractère stocké dans le membre firstInitial doit toujours correspondre au premier caractère de name.

Lorsqu'un objet Employee est initialisé, c'est à l'utilisateur de s'assurer que l'invariant de classe est respecté. Et si name reçoit une nouvelle valeur, c'est encore à lui de veiller à mettre aussi firstInitial à jour. Cette corrélation peut ne pas être évidente pour le développeur qui utilise un objet Employee, et même si elle l'est, il peut oublier de la respecter.

Même si nous écrivons des fonctions qui aident à créer et mettre à jour les objets Employee (en veillant à ce que firstInitial soit toujours calculé à partir du premier caractère de name), nous comptons toujours sur l'utilisateur pour connaître ces fonctions et les utiliser.

En bref, compter sur l'utilisateur d'un objet pour qu'il respecte les invariants de classe risque fortement de produire du code problématique.

Point clé

Compter sur l'utilisateur d'un objet pour qu'il respecte les invariants de classe risque fortement de causer des problèmes.

Idéalement, nous aimerions rendre nos types classe infaillibles, de sorte qu'un objet ne puisse pas être placé dans un état invalide, ou signale immédiatement qu'il l'est (plutôt que de laisser un comportement indéfini surgir à un moment imprévisible dans le futur).

Les structs (en tant qu'agrégats) ne disposent tout simplement pas des mécanismes nécessaires pour résoudre ce problème de façon élégante.

Introduction aux classes

Lors du développement du C++, Bjarne Stroustrup voulait introduire des fonctionnalités permettant aux développeurs de créer des types définis par le programme, utilisables de manière plus intuitive. Il cherchait aussi des solutions élégantes à certains pièges fréquents et à certains problèmes de maintenance qui affectent les programmes grands et complexes (comme le problème de l'invariant de classe mentionné plus haut).

S'appuyant sur son expérience d'autres langages de programmation (en particulier Simula, le premier langage orienté objet), Bjarne était convaincu qu'il était possible de concevoir un type défini par le programme suffisamment général et puissant pour servir à presque tout. En hommage à Simula, il a appelé ce type une classe (class).

Tout comme les structs, une classe (class) est un type composé défini par le programme, qui peut avoir de nombreuses variables membres de types différents.

Point clé

D'un point de vue technique, les structs et les classes sont presque identiques : tout exemple implémenté avec un struct pourrait l'être avec une classe, et inversement. En pratique, toutefois, on n'utilise pas les structs et les classes de la même manière.

Nous traitons les différences techniques et pratiques entre structs et classes dans la leçon 14.5 -- Membres publics et privés et spécificateurs d'accès.

Contenu associé

Nous expliquons comment les classes résolvent le problème des invariants dans la leçon 14.8 -- Les avantages du masquage des données (encapsulation).

Définir une classe

Une classe étant un type de données défini par le programme, elle doit être définie avant d'être utilisée. Les classes se définissent de manière similaire aux structs, à ceci près que l'on utilise le mot-clé class au lieu de struct. Par exemple, voici la définition d'une classe employé simple :

class Employee
{
    int m_id {};
    int m_age {};
    double m_wage {};
};

Contenu associé

Nous expliquons dans la leçon à venir 14.5 -- Membres publics et privés et spécificateurs d'accès pourquoi les variables membres d'une classe sont souvent préfixées par « m_ ».

Pour montrer à quel point classes et structs peuvent se ressembler, le programme suivant est équivalent à celui présenté en début de leçon, mais Date est maintenant une classe au lieu d'un struct :

#include <iostream>

class Date       // on remplace struct par class
{
public:          // et on ajoute cette ligne, appelée spécificateur d'accès
    int m_day{}; // et on ajoute le préfixe « m_ » à chaque nom de membre
    int m_month{};
    int m_year{};
};

void printDate(const Date& date)
{
    std::cout << date.m_day << '/' << date.m_month << '/' << date.m_year;
}

int main()
{
    Date date{ 4, 10, 21 };
    printDate(date);

    return 0;
}

La majeure partie de la bibliothèque standard du C++ est constituée de classes

Vous utilisez déjà des objets de classe, peut-être sans le savoir. std::string et std::string_view sont tous deux définis comme des classes. En fait, la plupart des types de la bibliothèque standard qui ne sont pas des alias sont des classes !

Les classes sont vraiment le cœur du C++ : elles sont si fondamentales que le C++ s'appelait à l'origine « C with classes » (« C avec des classes ») ! Une fois que vous maîtriserez les classes, une grande partie de votre temps en C++ sera consacrée à les écrire, les tester et les utiliser.

Quiz

Question n° 1

Étant donné un ensemble de valeurs (âges, numéros de rue, etc.), nous pouvons vouloir connaître les valeurs minimale et maximale de cet ensemble. Comme les valeurs minimale et maximale sont liées, nous pouvons les regrouper dans un struct, comme ceci :

struct minMax
{
    int min; // contient la plus petite valeur rencontrée jusqu'ici
    int max; // contient la plus grande valeur rencontrée jusqu'ici
};

Toutefois, tel qu'il est écrit, ce struct possède un invariant de classe non précisé. Quel est cet invariant ?

Solution

L'invariant est min <= max. Si min devient un jour supérieur à max, tout code qui utilise ce struct risque de mal fonctionner.
