14.10 — Listes d'initialisation des membres du constructeur

Cette leçon poursuit notre introduction aux constructeurs commencée dans la leçon 14.9 — Introduction aux constructeurs.

Initialisation des membres via une liste d'initialisation de membres

Pour qu'un constructeur initialise des membres, on utilise une liste d'initialisation de membres (en anglais member initializer list, souvent appelée « liste d'initialisation de membres »). Ne la confondez pas avec la « liste d'initialisation » (initializer list) similaire, qui sert à initialiser des agrégats avec une liste de valeurs.

Les listes d'initialisation de membres se comprennent mieux à partir d'un exemple. Dans le programme suivant, le constructeur Foo(int, int) a été modifié pour utiliser une liste d'initialisation de membres afin d'initialiser m_x et m_y :

#include <iostream>

class Foo
{
private:
    int m_x {};
    int m_y {};

public:
    Foo(int x, int y)
        : m_x { x }, m_y { y } // voici notre liste d'initialisation de membres
    {
        std::cout << "Foo(" << x << ", " << y << ") constructed\n";
    }

    void print() const
    {
        std::cout << "Foo(" << m_x << ", " << m_y << ")\n";
    }
};

int main()
{
    Foo foo{ 6, 7 };
    foo.print();

    return 0;
}

La liste d'initialisation de membres est définie après les paramètres du constructeur. Elle commence par un deux-points (:), puis énumère chaque membre à initialiser, suivi de sa valeur d'initialisation, les couples étant séparés par des virgules. Il faut utiliser ici une forme d'initialisation directe (de préférence avec des accolades, mais les parenthèses fonctionnent aussi) : l'initialisation par copie (avec le signe égal) ne fonctionne pas dans ce contexte. Notez également que la liste d'initialisation de membres ne se termine pas par un point-virgule.

Ce programme produit la sortie suivante :


Foo(6, 7) constructed
Foo(6, 7)

Lorsque foo est instancié, les membres de la liste d'initialisation reçoivent les valeurs d'initialisation indiquées. Dans ce cas, la liste d'initialisation de membres initialise m_x avec la valeur de x (soit 6), et m_y avec la valeur de y (soit 7). Ensuite, le corps du constructeur s'exécute.

Lorsque la fonction membre print() est appelée, on constate que m_x vaut toujours 6 et m_y toujours 7.

Mise en forme de la liste d'initialisation de membres

C++ vous laisse une grande liberté pour mettre en forme vos listes d'initialisation de membres : le compilateur ne se soucie pas de l'emplacement des deux-points, des virgules ou des espaces.

Les styles suivants sont tous valides (et vous les rencontrerez probablement tous les trois en pratique) :

    Foo(int x, int y) : m_x { x }, m_y { y }
    {
    }

    Foo(int x, int y) :
        m_x { x },
        m_y { y }
    {
    }

    Foo(int x, int y)
        : m_x { x }
        , m_y { y }
    {
    }

Nous recommandons d'utiliser le troisième style :

  • Placez le deux-points sur la ligne qui suit le nom du constructeur, ce qui sépare clairement la liste d'initialisation de membres du prototype de la fonction.
  • Indentez la liste d'initialisation de membres, pour repérer plus facilement les noms des fonctions.

Si la liste d'initialisation de membres est courte ou triviale, toutes les initialisations peuvent tenir sur une seule ligne :

    Foo(int x, int y)
        : m_x { x }, m_y { y }
    {
    }

Sinon (ou si vous le préférez), chaque couple membre-initialisation peut occuper sa propre ligne (en commençant par une virgule pour conserver l'alignement) :

    Foo(int x, int y)
        : m_x { x }
        , m_y { y }
    {
    }

Ordre d'initialisation des membres

Le standard C++ impose que les membres figurant dans une liste d'initialisation de membres soient toujours initialisés dans l'ordre de leur définition dans la classe (et non dans l'ordre où ils apparaissent dans la liste).

Dans l'exemple ci-dessus, comme m_x est défini avant m_y dans la définition de la classe, m_x sera initialisé en premier (même s'il n'est pas listé en premier).

Comme on s'attend intuitivement à ce que les variables soient initialisées de gauche à droite, cela peut provoquer des erreurs subtiles. Considérez l'exemple suivant :

#include <algorithm> // pour std::max
#include <iostream>

class Foo
{
private:
    int m_x{};
    int m_y{};

public:
    Foo(int x, int y)
        : m_y { std::max(x, y) }, m_x { m_y } // problème sur cette ligne
    {
    }

    void print() const
    {
        std::cout << "Foo(" << m_x << ", " << m_y << ")\n";
    }
};

int main()
{
    Foo foo { 6, 7 };
    foo.print();

    return 0;
}

Dans cet exemple, notre intention est de calculer la plus grande des valeurs d'initialisation passées (via std::max(x, y)), puis d'utiliser cette valeur pour initialiser à la fois m_x et m_y. Pourtant, sur la machine de l'auteur, le résultat affiché est le suivant :


Foo(-858993460, 7)

Que s'est-il passé ? Bien que m_y soit listé en premier dans la liste d'initialisation de membres, comme m_x est défini en premier dans la classe, c'est lui qui est initialisé en premier. Or m_x est initialisé avec la valeur de m_y, qui n'a pas encore été initialisé. Enfin, m_y reçoit la plus grande des valeurs d'initialisation.

Pour éviter ce genre d'erreur, les membres de la liste d'initialisation de membres doivent être listés dans l'ordre où ils sont définis dans la classe. Certains compilateurs émettent un avertissement lorsque des membres sont initialisés dans le désordre.

Bonne pratique

Les variables membres figurant dans une liste d'initialisation de membres doivent être listées dans l'ordre de leur définition dans la classe.

Il est également judicieux d'éviter d'initialiser des membres à partir de la valeur d'autres membres (lorsque c'est possible). Ainsi, même si vous vous trompez dans l'ordre d'initialisation, cela n'a pas d'importance, car les valeurs d'initialisation ne dépendent alors d'aucun autre membre.

Liste d'initialisation de membres et initialisations par défaut des membres

Les membres peuvent être initialisés de plusieurs façons :

  • Si un membre figure dans la liste d'initialisation de membres, cette valeur d'initialisation est utilisée.
  • Sinon, si le membre possède une initialisation par défaut (default member initializer), cette valeur est utilisée.
  • Sinon, le membre est initialisé par défaut (default-initialized).

Cela signifie que si un membre possède à la fois une initialisation par défaut et figure dans la liste d'initialisation de membres du constructeur, c'est la valeur de la liste d'initialisation de membres qui prévaut.

Voici un exemple qui illustre ces trois méthodes d'initialisation :

#include <iostream>

class Foo
{
private:
    int m_x {};    // initialisation par défaut (sera ignorée)
    int m_y { 2 }; // initialisation par défaut (sera utilisée)
    int m_z;       // pas d'initialisation

public:
    Foo(int x)
        : m_x { x } // liste d'initialisation de membres
    {
        std::cout << "Foo constructed\n";
    }

    void print() const
    {
        std::cout << "Foo(" << m_x << ", " << m_y << ", " << m_z << ")\n";
    }
};

int main()
{
    Foo foo { 6 };
    foo.print();

    return 0;
}

Sur la machine de l'auteur, ce programme affiche :


Foo constructed
Foo(6, 2, -858993460)

Voici ce qui se passe. Lors de la construction de foo, seul m_x figure dans la liste d'initialisation de membres, donc m_x est d'abord initialisé à 6. m_y n'est pas dans la liste, mais il possède une initialisation par défaut, il est donc initialisé à 2. m_z n'est ni dans la liste, ni pourvu d'une initialisation par défaut : il est initialisé par défaut (ce qui, pour les types fondamentaux, signifie qu'il reste non initialisé). Par conséquent, lorsque nous affichons la valeur de m_z, nous obtenons un comportement indéfini.

Corps des fonctions constructeurs

Les corps des fonctions constructeurs sont le plus souvent laissés vides. En effet, nous utilisons principalement les constructeurs pour l'initialisation, qui se fait via la liste d'initialisation de membres. Si c'est tout ce dont nous avons besoin, le corps du constructeur n'a pas besoin de contenir d'instructions.

Cependant, comme les instructions du corps du constructeur s'exécutent après la liste d'initialisation de membres, nous pouvons y ajouter des instructions pour effectuer toute autre tâche de mise en place nécessaire. Dans les exemples précédents, nous affichons quelque chose sur la console pour montrer que le constructeur a été exécuté, mais nous pourrions aussi ouvrir un fichier ou une base de données, allouer de la mémoire, etc.

Les nouveaux programmeurs utilisent parfois le corps du constructeur pour affecter des valeurs aux membres :

#include <iostream>

class Foo
{
private:
    int m_x { 0 };
    int m_y { 1 };

public:
    Foo(int x, int y)
    {
        m_x = x; // incorrect : il s'agit d'une affectation, pas d'une initialisation
        m_y = y; // incorrect : il s'agit d'une affectation, pas d'une initialisation
    }

    void print() const
    {
        std::cout << "Foo(" << m_x << ", " << m_y << ")\n";
    }
};

int main()
{
    Foo foo { 6, 7 };
    foo.print();

    return 0;
}

Bien que dans ce cas simple le résultat soit celui attendu, cette méthode ne fonctionne pas lorsque certains membres doivent obligatoirement être initialisés, comme les membres données const ou les références.

Point clé

Une fois la liste d'initialisation de membres exécutée, l'objet est considéré comme initialisé. Une fois le corps de la fonction exécuté, l'objet est considéré comme construit.

Bonne pratique

Privilégiez la liste d'initialisation de membres pour initialiser vos membres, plutôt que d'affecter des valeurs dans le corps du constructeur.

Détecter et gérer les arguments invalides passés aux constructeurs

Considérons la classe Fraction suivante :

class Fraction
{
private:
    int m_numerator {};
    int m_denominator {};

public:
    Fraction(int numerator, int denominator):
        m_numerator { numerator }, m_denominator { denominator }
    {
    }
};

Une fraction correspond à un numérateur divisé par un dénominateur ; le dénominateur d'une fraction ne peut donc pas être nul (sinon nous obtenons une division par zéro, qui est mathématiquement indéfinie). Autrement dit, cette classe possède un invariant : m_denominator ne peut pas valoir 0.

Contenu associé

Nous avons abordé les invariants de classe dans la leçon 14.2 — Introduction aux classes.

Que faire lorsque l'utilisateur tente de créer une Fraction avec un dénominateur nul (par exemple Fraction f { 1, 0 };) ?

Dans une liste d'initialisation de membres, nos outils pour détecter et gérer les erreurs sont assez limités. Nous pouvons utiliser l'opérateur conditionnel pour détecter une erreur, mais ensuite, que faire ?

class Fraction
{
private:
    int m_numerator {};
    int m_denominator {};

public:
    Fraction(int numerator, int denominator):
        m_numerator { numerator }, m_denominator { denominator != 0.0 ? denominator : ??? } // que faire ici ?
    {
    }
};

Nous pourrions remplacer le dénominateur par une valeur valide, mais l'utilisateur obtiendrait alors une Fraction qui ne contient pas les valeurs qu'il a demandées, et nous n'aurions aucun moyen de l'informer que nous avons fait quelque chose d'inattendu. Ainsi, nous ne tentons généralement pas de valider quoi que ce soit dans la liste d'initialisation de membres : nous initialisons simplement les membres avec les valeurs reçues, puis nous essayons de gérer la situation.

Dans le corps du constructeur, nous pouvons utiliser des instructions, ce qui nous offre davantage de possibilités pour détecter et gérer les erreurs. C'est un bon endroit pour utiliser assert ou static_assert afin de vérifier que les arguments passés sont sémantiquement valides, mais cela ne gère pas réellement les erreurs à l'exécution dans une version de production.

Lorsqu'un constructeur ne peut pas construire un objet sémantiquement valide, on dit qu'il a échoué.

Lorsque les constructeurs échouent (prélude)

Dans la leçon 9.4 — Détecter et gérer les erreurs, nous avons introduit la gestion des erreurs et présenté quelques options pour les cas où une fonction ne peut pas poursuivre son exécution à cause d'une erreur. Comme les constructeurs sont des fonctions, ils sont soumis aux mêmes problèmes.

Dans cette leçon, nous proposions 4 stratégies pour traiter de telles erreurs :

  • Résoudre l'erreur au sein de la fonction.
  • Renvoyer l'erreur à l'appelant pour qu'il la traite.
  • Arrêter le programme.
  • Lever une exception.

Dans la plupart des cas, nous ne disposons pas d'assez d'informations pour résoudre entièrement ces problèmes dans le constructeur. Corriger le problème n'est donc généralement pas une option.

Pour les fonctions membres non spéciales et les fonctions qui ne sont pas membres, on peut renvoyer une erreur à l'appelant. Mais les constructeurs n'ont pas de valeur de retour, nous n'avons donc pas de bon moyen de faire cela. Dans certains cas, nous pouvons ajouter une fonction membre isValid() (ou une conversion implicite vers bool) qui indique si l'objet est actuellement dans un état valide. Par exemple, une fonction isValid() pour Fraction renverrait true lorsque m_denominator != 0.0. Mais cela signifie que l'appelant doit penser à appeler cette fonction à chaque création d'une nouvelle Fraction. De plus, disposer d'objets sémantiquement invalides et accessibles risque de provoquer des bogues. Cette solution vaut donc mieux que rien, mais elle n'est pas vraiment satisfaisante.

Dans certains types de programmes, nous pouvons simplement arrêter tout le programme et laisser l'utilisateur le relancer avec les bonnes entrées… mais dans la plupart des cas, ce n'est pas acceptable. Donc, probablement pas.

Il reste alors à lever une exception. Les exceptions interrompent entièrement le processus de construction, ce qui signifie que l'utilisateur n'accède jamais à un objet sémantiquement invalide. Dans la plupart des cas, lever une exception est donc la meilleure solution dans ces situations.

Point clé

Lever une exception est généralement la meilleure chose à faire lorsqu'un constructeur échoue (et ne peut pas se rétablir). Nous approfondirons ce point dans les leçons 27.5 — Exceptions, classes et héritage et 27.7 — Blocs try de fonction.

Note de l'auteur

Pour l'instant, nous supposerons généralement que la construction de notre objet de classe réussit et crée un objet sémantiquement valide.

Pour les lecteurs avancés

Si les exceptions ne sont pas possibles ou pas souhaitées (parce que vous avez décidé de ne pas les utiliser ou parce que vous ne les avez pas encore étudiées), il existe une autre option raisonnable. Au lieu de laisser l'utilisateur créer directement la classe, fournissez une fonction qui renvoie soit une instance de la classe, soit une valeur indiquant l'échec.

Dans l'exemple suivant, la fonction createFraction() renvoie un std::optional<Fraction> qui contient éventuellement une Fraction valide. Si c'est le cas, nous pouvons utiliser cette Fraction. Sinon, l'appelant peut le détecter et le traiter. Nous abordons std::optional dans la leçon 12.15 — std::optional et les fonctions amies dans la leçon 15.8 — Fonctions amies non membres.

#include <iostream>
#include <optional>

class Fraction
{
private:
    int m_numerator { 0 };
    int m_denominator { 1 };

    // le constructeur privé ne peut pas être appelé depuis l'extérieur
    Fraction(int numerator, int denominator):
        m_numerator { numerator }, m_denominator { denominator }
    {
    }

public:
    // Autorise cette fonction à accéder aux membres privés
    friend std::optional<Fraction> createFraction(int numerator, int denominator);
};

std::optional<Fraction> createFraction(int numerator, int denominator)
{
    if (denominator == 0)
        return {};

    return Fraction{numerator, denominator};
}

int main()
{
    auto f1 { createFraction(0, 1) };
    if (f1)
    {
        std::cout << "Fraction created\n";
    }

    auto f2 { createFraction(0, 0) };
    if (!f2)
    {
        std::cout << "Bad fraction\n";
    }
}

Quiz

Question n° 1

Écrivez une classe nommée Ball. Ball doit avoir deux variables membres privées : une pour contenir une couleur, et une pour contenir un rayon. Écrivez également une fonction qui affiche la couleur et le rayon de la balle.

Le programme d'exemple suivant doit compiler :

int main()
{
    Ball blue { "blue", 10.0 };
    print(blue);

    Ball red { "red", 12.0 };
    print(red);

    return 0;
}

et produire le résultat :


Ball(blue, 10)
Ball(red, 12)
Solution 
#include <iostream>
#include <string>
#include <string_view>

class Ball
{
private:
    std::string m_color { "none" };
    double m_radius { 0.0 };

public:
    Ball(std::string_view color, double radius)
        : m_color { color }
        , m_radius { radius }
    {
    }

    const std::string& getColor() const { return m_color; }
    double getRadius() const { return m_radius; }
};

void print(const Ball& ball)
{
    std::cout << "Ball(" << ball.getColor() << ", " << ball.getRadius() << ")\n";
}

int main()
{
    Ball blue { "blue", 10.0 };
    print(blue);

    Ball red { "red", 12.0 };
    print(red);

    return 0;
}

Solution

Question n° 3

Pourquoi avons-nous fait de m_color un std::string plutôt qu'un std::string_view ?

Solution

Dans cet exemple particulier, cela n'a pas d'importance (car nos arguments de couleur sont des littéraux de chaîne de style C, qui ne sortent pas de portée).

Mais conceptuellement, nous voulons que la classe Ball soit propriétaire de la couleur reçue. Si m_color était un std::string_view, passer un objet temporaire comme argument de couleur (par exemple une std::string renvoyée par une fonction) laisserait m_color pendouillant (dangling) une fois l'argument temporaire détruit.

Nous examinons ce cas plus en détail (et présentons un exemple) dans la leçon 13.11 — Divers sur les structures.
