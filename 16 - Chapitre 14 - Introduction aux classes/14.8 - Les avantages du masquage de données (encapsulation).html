14.8 — Les avantages du masquage de données (encapsulation)

Dans une leçon précédente (14.5 -- Membres publics et privés et spécificateurs d'accès), nous avons mentionné que les variables membres d'une classe sont généralement rendues privées. Les programmeurs qui découvrent les classes ont souvent du mal à comprendre pourquoi on fait cela. Après tout, rendre vos variables privées signifie qu'elles ne sont pas accessibles au public. Au mieux, cela demande plus de travail lors de l'écriture de vos classes. Au pire, cela peut sembler complètement inutile (surtout si nous fournissons un accès public aux données membres privées via des fonctions d'accès).

La réponse à cette question est si fondamentale que nous allons consacrer une leçon entière à ce sujet !

Commençons par une analogie.

Dans la vie moderne, nous avons accès à de nombreux appareils mécaniques ou électroniques. Vous allumez ou éteignez votre téléviseur avec une télécommande. Vous faites avancer votre voiture en appuyant sur la pédale d'accélérateur. Vous allumez la lumière en actionnant un interrupteur. Tous ces appareils ont un point commun : ils fournissent une interface utilisateur simple (un ensemble de boutons, une pédale, un interrupteur, etc.) qui vous permet d'effectuer les actions essentielles.

La façon dont ces appareils fonctionnent réellement vous est cachée. Lorsque vous appuyez sur un bouton de votre télécommande, vous n'avez pas besoin de savoir comment elle communique avec votre téléviseur. Lorsque vous appuyez sur la pédale d'accélérateur, vous n'avez pas besoin de savoir comment le moteur à combustion fait tourner les roues. Lorsque vous prenez une photo, vous n'avez pas besoin de savoir comment les capteurs recueillent la lumière et la transforment en image pixelisée.

Cette séparation entre interface et implémentation est extrêmement utile, car elle nous permet d'utiliser des objets sans avoir à comprendre leur fonctionnement : il suffit de savoir comment interagir avec eux. Cela réduit considérablement la complexité de l'utilisation de ces objets et augmente le nombre d'objets avec lesquels nous sommes capables d'interagir.

Implémentation et interfaces dans les types classes

Pour des raisons similaires, la séparation entre interface et implémentation est utile en programmation. Mais d'abord, définissons ce que nous entendons par interface et implémentation pour les types classes.

L'interface d'un type classe (appelée aussi interface de classe) définit la manière dont l'utilisateur du type classe interagira avec les objets de ce type. Comme seuls les membres publics sont accessibles depuis l'extérieur de la classe, les membres publics forment son interface. Pour cette raison, une interface composée de membres publics est parfois appelée interface publique.

Une interface est un contrat implicite entre l'auteur d'une classe et son utilisateur. Si une interface existante est modifiée, tout code qui l'utilise peut cesser de fonctionner. Il est donc important de s'assurer que les interfaces de nos types classes sont bien conçues et stables (qu'elles changent peu).

L'implémentation d'un type classe est constituée du code qui fait réellement se comporter la classe comme prévu. Cela comprend à la fois les variables membres qui stockent les données et le corps des fonctions membres qui contiennent la logique du programme et manipulent les variables membres.

Le masquage de données

En programmation, le masquage de données (appelé aussi masquage d'information ou abstraction de données) est une technique qui consiste à faire respecter la séparation entre interface et implémentation en cachant aux utilisateurs l'implémentation d'un type de données défini par le programme (en la rendant inaccessible).

Mettre en œuvre le masquage de données dans une classe C++ est simple. Premièrement, nous nous assurons que les membres de données de la classe sont privés (afin que l'utilisateur ne puisse pas y accéder directement). Les instructions à l'intérieur des corps des fonctions membres ne sont déjà pas directement accessibles aux utilisateurs, donc nous n'avons rien d'autre à faire à ce niveau. Ensuite, nous nous assurons que les fonctions membres sont publiques, afin que l'utilisateur puisse les appeler.

En suivant ces règles, nous obligeons l'utilisateur d'un type classe à manipuler les objets via l'interface publique, et nous l'empêchons d'accéder directement aux détails d'implémentation.

Les classes définies en C++ devraient utiliser le masquage de données. D'ailleurs, toutes les classes fournies par la bibliothèque standard le font. Les structs, en revanche, ne devraient pas utiliser le masquage de données, car avoir des membres non publics les empêche d'être considérés comme des agrégats.

Définir les classes de cette façon demande un peu de travail supplémentaire à l'auteur de la classe. Et exiger que les utilisateurs passent par l'interface publique peut sembler plus contraignant que de fournir un accès public direct aux variables membres. Pourtant, cela apporte un grand nombre d'avantages qui favorisent la réutilisabilité et la maintenabilité des classes. Nous consacrerons le reste de la leçon à ces avantages.

Nomenclature

En programmation, le terme encapsulation désigne généralement l'une de ces deux choses :

  • le fait d'enfermer un ou plusieurs éléments dans un conteneur d'une sorte ou d'une autre ;
  • le regroupement de données et de fonctions qui opèrent sur les instances de ces données.

En C++, un type classe qui possède des données et une interface publique permettant de créer et de manipuler des objets de cette classe est encapsulé. Comme l'encapsulation est un prérequis au masquage de données, et comme le masquage de données est une technique si importante, on inclut conventionnellement le masquage de données dans le terme encapsulation.

Dans cette série de tutoriels, nous supposerons que toutes les classes encapsulées mettent en œuvre le masquage de données.

Le masquage de données rend les classes plus faciles à utiliser et réduit la complexité

Pour utiliser une classe encapsulée, vous n'avez pas besoin de connaître son implémentation. Vous devez seulement comprendre son interface : quelles fonctions membres sont publiquement disponibles, quels arguments elles prennent et quelles valeurs elles renvoient.

Par exemple :

#include <iostream>
#include <string_view>

int main()
{
    std::string_view sv{ "Hello, world!" };
    std::cout << sv.length();

    return 0;
}

Dans ce court programme, les détails de l'implémentation de std::string_view ne nous sont pas exposés. Nous ne savons pas combien de membres de données possède un std::string_view, comment ils s'appellent ni de quels types ils sont. Nous ne savons pas comment la fonction membre length() renvoie la longueur de la chaîne observée.

Et le meilleur, c'est que nous n'avons pas à le savoir ! Le programme fonctionne tout simplement. Il nous suffit de savoir comment initialiser un objet de type std::string_view et ce que renvoie la fonction membre length().

Ne pas avoir à se soucier de ces détails réduit considérablement la complexité de vos programmes, ce qui à son tour réduit les erreurs. Plus que toute autre raison, c'est l'avantage clé de l'encapsulation.

Imaginez à quel point C++ serait plus compliqué si vous deviez comprendre comment std::string, std::vector ou std::cout sont implémentés pour pouvoir les utiliser !

Le masquage de données nous permet de maintenir des invariants

Dans la leçon d'introduction aux classes (14.2 -- Introduction aux classes), nous avons présenté le concept d'invariants de classe, c'est-à-dire des conditions qui doivent rester vraies pendant toute la durée de vie d'un objet pour que celui-ci reste dans un état valide.

Considérez le programme suivant :

#include <iostream>
#include <string>

struct Employee // les membres sont publics par défaut
{
    std::string name{ "John" };
    char firstInitial{ 'J' }; // doit correspondre à l'initiale de name

    void print() const
    {
        std::cout << "Employee " << name << " has first initial " << firstInitial << '\n';
    }
};

int main()
{
    Employee e{}; // vaut "John" et 'J' par défaut
    e.print();

    e.name = "Mark"; // on change le nom de l'employé en "Mark"
    e.print(); // affiche une mauvaise initiale

    return 0;
}

Ce programme affiche :


John has first initial J
Mark has first initial J

Notre struct Employee possède un invariant de classe : firstInitial doit toujours être égal au premier caractère de name. Si cela n'est plus vrai, la fonction print() ne fonctionnera pas correctement.

Comme le membre name est public, le code de main() peut affecter "Mark" à e.name, et le membre firstInitial n'est pas mis à jour. Notre invariant est rompu, et le second appel à print() ne fonctionne pas comme prévu.

Lorsque nous donnons aux utilisateurs un accès direct à l'implémentation d'une classe, ils deviennent responsables du maintien de tous les invariants, ce qu'ils peuvent ne pas faire (correctement, ou pas du tout). Faire peser cette charge sur l'utilisateur ajoute beaucoup de complexité.

Réécrivons ce programme en rendant nos membres de données privés et en exposant une fonction membre permettant de définir le nom d'un Employee :

#include <iostream>
#include <string>
#include <string_view>

class Employee // les membres sont privés par défaut
{
    std::string m_name{};
    char m_firstInitial{};

public:
    void setName(std::string_view name)
    {
        m_name = name;
        m_firstInitial = name.front(); // utilise std::string::front() pour obtenir la première lettre de `name`
    }

    void print() const
    {
        std::cout << "Employee " << m_name << " has first initial " << m_firstInitial << '\n';
    }
};

int main()
{
    Employee e{};
    e.setName("John");
    e.print();

    e.setName("Mark");
    e.print();

    return 0;
}

Ce programme fonctionne désormais comme prévu :


John has first initial J
Mark has first initial M

Du point de vue de l'utilisateur, le seul changement est qu'au lieu d'affecter directement une valeur à name, il appelle la fonction membre setName(), qui se charge de définir à la fois m_name et m_firstInitial. L'utilisateur est dispensé d'avoir à maintenir cet invariant !

Le masquage de données permet une meilleure détection (et gestion) des erreurs

Dans le programme ci-dessus, l'invariant selon lequel m_firstInitial doit correspondre au premier caractère de m_name existe parce que m_firstInitial existe indépendamment de m_name. Nous pouvons supprimer cet invariant particulier en remplaçant le membre de données m_firstInitial par une fonction membre qui renvoie l'initiale :

#include <iostream>
#include <string>

class Employee
{
    std::string m_name{ "John" };

public:
    void setName(std::string_view name)
    {
        m_name = name;
    }

    // utilise std::string::front() pour obtenir la première lettre de `m_name`
    char firstInitial() const { return m_name.front(); }

    void print() const
    {
        std::cout << "Employee " << m_name << " has first initial " << firstInitial() << '\n';
    }
};

int main()
{
    Employee e{}; // vaut "John" par défaut
    e.setName("Mark");
    e.print();

    return 0;
}

Toutefois, ce programme possède un autre invariant de classe. Prenez un moment pour essayer de le trouver. Nous attendrons ici en regardant sécher la peinture…

La réponse est que m_name ne doit pas être une chaîne vide (car chaque Employee doit avoir un nom). Si m_name reçoit une chaîne vide, rien de grave ne se produit immédiatement. Mais si firstInitial() est ensuite appelée, le membre front() de std::string essaiera d'obtenir la première lettre de la chaîne vide, ce qui conduit à un comportement indéfini.

Idéalement, nous voudrions empêcher m_name d'être jamais vide.

Si l'utilisateur avait un accès public au membre m_name, il pourrait simplement écrire m_name = "", et nous ne pourrions rien faire pour l'en empêcher.

En revanche, comme nous obligeons l'utilisateur à définir m_name via la fonction d'interface publique setName(), nous pouvons faire en sorte que setName() vérifie que l'utilisateur a transmis un nom valide. Si le nom n'est pas vide, nous pouvons l'affecter à m_name. Si le nom est une chaîne vide, nous pouvons réagir de plusieurs façons :

  • ignorer la demande de définir le nom à « » et revenir à l'appelant ;
  • arrêter le programme avec une assertion ;
  • lever une exception ;
  • faire la danse du pokey. Non, pas celle-là, attendez.

Le point essentiel est que nous pouvons détecter l'usage incorrect, puis le gérer comme nous le jugeons le plus approprié. Comment gérer au mieux ces cas est un sujet pour une autre fois.

Le masquage de données permet de modifier les détails d'implémentation sans casser les programmes existants

Considérez cet exemple simple :

#include <iostream>

struct Something
{
    int value1 {};
    int value2 {};
    int value3 {};
};

int main()
{
    Something something;
    something.value1 = 5;
    std::cout << something.value1 << '\n';
}

Bien que ce programme fonctionne parfaitement, que se passerait-il si nous décidions de modifier les détails d'implémentation de la classe, comme ceci ?

#include <iostream>

struct Something
{
    int value[3] {}; // utilise un tableau de 3 valeurs
};

int main()
{
    Something something;
    something.value1 = 5;
    std::cout << something.value1 << '\n';
}

Nous n'avons pas encore vu les tableaux, mais ne vous en faites pas. Le point ici est que ce programme ne compile plus, car le membre nommé value1 n'existe plus, et une instruction de main() utilise toujours cet identifiant.

Le masquage de données nous donne la capacité de modifier l'implémentation des classes sans casser les programmes qui les utilisent.

Voici la version encapsulée de la classe d'origine, qui utilise des fonctions pour accéder à m_value1 :

#include <iostream>

class Something
{
private:
    int m_value1 {};
    int m_value2 {};
    int m_value3 {};

public:
    void setValue1(int value) { m_value1 = value; }
    int getValue1() const { return m_value1; }
};

int main()
{
    Something something;
    something.setValue1(5);
    std::cout << something.getValue1() << '\n';
}

Modifions maintenant l'implémentation de la classe pour revenir à un tableau :

#include <iostream>

class Something
{
private:
    int m_value[3]; // note : nous avons modifié l'implémentation de cette classe !

public:
    // Nous devons mettre à jour les fonctions membres pour refléter la nouvelle implémentation
    void setValue1(int value) { m_value[0] = value; }
    int getValue1() const { return m_value[0]; }
};

int main()
{
    // Mais nos programmes qui utilisent la classe n'ont pas besoin d'être mis à jour !
    Something something;
    something.setValue1(5);
    std::cout << something.getValue1() << '\n';
}

Comme nous n'avons pas modifié l'interface publique de la classe, notre programme qui utilise cette interface n'a pas eu besoin de changer et fonctionne toujours de manière identique.

De manière analogue, si des lutins s'introduisaient chez vous de nuit et remplaçaient les composants internes de votre télécommande par une technologie différente (mais compatible), vous ne remarqueriez probablement rien !

Les classes dotées d'interfaces sont plus faciles à déboguer

Enfin, l'encapsulation peut vous aider à déboguer un programme lorsque quelque chose ne va pas. Souvent, lorsqu'un programme ne fonctionne pas correctement, c'est parce qu'une de nos variables membres a reçu une valeur incorrecte. Si tout le monde peut définir directement la variable membre, il peut être difficile de trouver le fragment de code qui a effectivement modifié la variable membre pour lui donner une mauvaise valeur. Il faudrait alors placer un point d'arrêt sur chaque instruction qui modifie la variable membre, et il peut y en avoir beaucoup.

En revanche, si un membre ne peut être modifié que par une seule fonction membre, vous pouvez simplement placer un point d'arrêt sur cette fonction et observer chaque appelant modifier la valeur. Cela permet de trouver beaucoup plus facilement le coupable.

Préférer les fonctions non membres aux fonctions membres

En C++, si une fonction peut raisonnablement être implémentée comme fonction non membre, préférez l'implémenter ainsi plutôt que comme fonction membre.

Cela présente de nombreux avantages :

  • Les fonctions non membres ne font pas partie de l'interface de votre classe. Ainsi, l'interface de votre classe est plus petite et plus simple, ce qui rend la classe plus facile à comprendre.
  • Les fonctions non membres imposent l'encapsulation, car elles doivent passer par l'interface publique de la classe. Il n'y a aucune tentation d'accéder à l'implémentation directement simplement parce que c'est pratique.
  • Les fonctions non membres n'ont pas à être prises en compte lorsque l'on modifie l'implémentation d'une classe (tant que l'interface ne change pas de façon incompatible).
  • Les fonctions non membres sont généralement plus faciles à déboguer.
  • Les fonctions non membres contenant des données et une logique propres à une application peuvent être séparées des parties réutilisables de la classe.

Si vous avez déjà une expérience d'un langage orienté objet moderne (comme Java ou C#), cette pratique peut vous surprendre. Ces langages reposent sur un autre modèle conceptuel, où la classe est au centre de tout et où tout se rapporte à elle. En conséquence, ces langages mettent les fonctions membres au premier plan (et en fait, Java et C# ne prennent même pas en charge les fonctions non membres).

Bonne pratique

Privilégiez l'implémentation des fonctions comme non membres lorsque c'est possible (en particulier les fonctions contenant une logique ou des données propres à une application).

Astuce

Voici un guide simplifié pour décider si une fonction doit être membre ou non membre :

  • Utilisez une fonction membre lorsque vous y êtes obligé. C++ exige que certains types de fonctions soient définis comme membres. Nous en verrons un exemple dans la prochaine leçon, lorsque nous parlerons des constructeurs. D'autres incluent les destructeurs, les fonctions virtuelles et certains opérateurs.
  • Privilégiez une fonction membre lorsque la fonction a besoin d'accéder à des données privées (ou protégées) qui ne doivent pas être exposées.
  • Privilégiez une fonction non membre dans les autres cas (en particulier pour les fonctions qui ne modifient pas l'état de l'objet).

Il existe des exceptions aux deux derniers points : nous en présenterons certaines lorsque nous aborderons les sujets qui leur sont associés.

Un cas courant mais délicat se produit lorsque privilégier une fonction non membre nécessite l'ajout de fonctions d'accès. Dans ce cas, vous devrez peser le pour et le contre.

  • Ajouter des fonctions d'accès signifie créer une ou deux nouvelles fonctions membres (un getter et éventuellement un setter), ce qui augmente la taille et la complexité de l'interface de la classe. Cela n'en vaut peut-être pas la peine, sauf si ces nouvelles fonctions d'accès peuvent être utilisées à plusieurs endroits.
  • N'ajoutez pas de fonctions d'accès à des données qui ne devraient pas être directement accessibles (par exemple parce qu'il s'agit d'un état interne) ou qui permettraient à l'utilisateur de violer un invariant de classe.

Contenu associé

L'article How Non-Member Functions Improve Encapsulation de Scott Meyers explore plus en détail l'idée de privilégier les fonctions non membres.

Illustrons cela avec trois exemples similaires, du moins bon au meilleur :

#include <iostream>
#include <string>

class Yogurt
{
    std::string m_flavor{ "vanilla" };

public:
    void setFlavor(std::string_view flavor)
    {
        m_flavor = flavor;
    }

    const std::string& getFlavor() const { return m_flavor; }

    // Le pire : la fonction membre print() accède directement à m_flavor alors qu'un getter existe
    void print() const
    {
        std::cout << "The yogurt has flavor " << m_flavor << '\n';
    }
};

int main()
{
    Yogurt y{};
    y.setFlavor("cherry");
    y.print();

    return 0;
}

La version ci-dessus est la pire. La fonction membre print() accède directement à m_flavor alors qu'un getter pour le parfum existe déjà. Si l'implémentation de la classe est un jour mise à jour, print() devra probablement aussi être modifiée. La chaîne affichée par print() est propre à l'application (une autre application utilisant cette classe pourrait vouloir afficher autre chose, ce qui nécessitera de cloner ou de modifier la classe).

#include <iostream>
#include <string>

class Yogurt
{
    std::string m_flavor{ "vanilla" };

public:
    void setFlavor(std::string_view flavor)
    {
        m_flavor = flavor;
    }

    const std::string& getFlavor() const { return m_flavor; }

    // Mieux : la fonction membre print() n'accède directement à aucun membre
    void print(std::string_view prefix) const
    {
        std::cout << prefix << ' ' << getFlavor() << '\n';
    }
};

int main()
{
    Yogurt y{};
    y.setFlavor("cherry");
    y.print("The yogurt has flavor");

    return 0;
}

La version ci-dessus est meilleure, mais pas encore parfaite. print() reste une fonction membre, mais elle n'accède plus directement à aucun membre de données. Si l'implémentation de la classe est mise à jour, print() devra être examinée pour déterminer si elle doit être modifiée (mais elle ne le sera pas). Le préfixe de print() est désormais paramétré, ce qui nous permet de déplacer le préfixe dans la fonction non membre main(). Mais la fonction impose toujours des contraintes sur la manière d'afficher les données (par exemple, elle affiche toujours préfixe, espace, parfum, saut de ligne). Si cela ne convient pas aux besoins d'une application donnée, il faudra ajouter une autre fonction.

#include <iostream>
#include <string>

class Yogurt
{
    std::string m_flavor{ "vanilla" };

public:
    void setFlavor(std::string_view flavor)
    {
        m_flavor = flavor;
    }

    const std::string& getFlavor() const { return m_flavor; }
};

// Le meilleur : la fonction non membre print() ne fait pas partie de l'interface de la classe
void print(const Yogurt& y)
{
        std::cout << "The yogurt has flavor " << y.getFlavor() << '\n';
}

int main()
{
    Yogurt y{};
    y.setFlavor("cherry");
    print(y);

    return 0;
}

La version ci-dessus est la meilleure. print() est maintenant une fonction non membre. Elle n'accède directement à aucun membre. Si l'implémentation de la classe change, print() n'aura pas du tout besoin d'être réexaminée. De plus, chaque application peut fournir sa propre fonction print() qui affiche exactement ce qu'elle souhaite.

L'ordre de déclaration des membres d'une classe

Lorsque nous écrivons du code en dehors d'une classe, nous sommes tenus de déclarer les variables et les fonctions avant de les utiliser. En revanche, à l'intérieur d'une classe, cette contrainte n'existe pas. Comme indiqué dans la leçon 14.3 -- Fonctions membres, nous pouvons ordonner nos membres comme bon nous semble.

Alors, comment les ordonner ?

Deux écoles de pensée s'opposent :

  • Placer les membres privés en premier, puis les fonctions membres publiques. Cela suit le style traditionnel « déclarer avant d'utiliser ». Quiconque lit le code de votre classe voit comment vous avez défini vos membres de données avant de les utiliser, ce qui peut faciliter la lecture et la compréhension des détails d'implémentation.
  • Placer les membres publics en premier, et mettre les membres privés en bas. Comme la personne qui utilise votre classe s'intéresse à l'interface publique, placer les membres publics en premier fait remonter en haut les informations dont elle a besoin, et place les détails d'implémentation (les moins importants) en dernier.

En C++ moderne, la seconde méthode (les membres publics en premier) est la plus couramment recommandée, en particulier pour le code destiné à être partagé avec d'autres développeurs.

Bonne pratique

Déclarez d'abord les membres publics, puis les membres protégés, et enfin les membres privés. Cela met en évidence l'interface publique et relègue les détails d'implémentation au second plan.

Note de l'auteur

La majorité des exemples de ce site utilisent l'ordre de déclaration inverse de celui recommandé. Cela tient en partie à l'histoire, mais nous trouvons aussi que cet ordre est plus intuitif lorsqu'on apprend les mécanismes du langage, où l'on se concentre sur les détails d'implémentation et sur la façon dont les choses fonctionnent.

Pour les lecteurs avancés

L'ordre suivant est recommandé par le guide de style C++ de Google :

  • Types et alias de types (typedef, using, enum, structs et classes imbriqués, ainsi que les types amis) ;
  • Constantes statiques ;
  • Fonctions de fabrique ;
  • Constructeurs et opérateurs d'affectation ;
  • Destructeur ;
  • Toutes les autres fonctions (fonctions membres statiques et non statiques, ainsi que fonctions amies) ;
  • Membres de données (statiques et non statiques).
