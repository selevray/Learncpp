14.6 — Fonctions d'accès

Dans la leçon précédente 14.5 -- Membres publics et privés et spécificateurs d'accès, nous avons étudié les niveaux d'accès public et privé. Pour rappel, les classes rendent généralement leurs membres données privés, et les membres privés ne peuvent pas être accédés directement depuis l'extérieur de la classe (partie publique).

Considérons la classe Date suivante :

#include <iostream>

class Date
{
private:
    int m_year{ 2020 };
    int m_month{ 10 };
    int m_day{ 14 };

public:
    void print() const
    {
        std::cout << m_year << '/' << m_month << '/' << m_day << '\n';
    }
};

int main()
{
    Date d{};  // crée un objet Date
    d.print(); // affiche la date

    return 0;
}

Bien que cette classe fournisse une fonction membre print() pour afficher la date complète, cela peut ne pas suffire à ce que l'utilisateur souhaite faire. Par exemple, que se passe-t-il si l'utilisateur d'un objet Date veut obtenir l'année ? Ou la modifier ? Il ne le pourrait pas, car m_year est privé (et ne peut donc pas être accédé directement depuis la partie publique).

Pour certaines classes, il peut être approprié (au vu de ce que fait la classe) de pouvoir lire ou modifier la valeur d'un membre donnée privé.

Fonctions d'accès

Une fonction d'accès (access function) est une fonction membre publique triviale dont le rôle est de lire ou de modifier la valeur d'un membre donnée privé.

Les fonctions d'accès existent sous deux formes : les accesseurs en lecture et les accesseurs en écriture. Les getters (également appelés parfois accessors) sont des fonctions membres publiques qui renvoient la valeur d'un membre donnée privé. Les setters (également appelés parfois mutators) sont des fonctions membres publiques qui modifient la valeur d'un membre donnée privé.

Terminologie

Le terme « mutator » est souvent utilisé comme synonyme de « setter ». Mais, plus largement, un mutator est toute fonction membre qui modifie (mute) l'état de l'objet. Selon cette définition, un setter est un type particulier de mutator. Il est toutefois possible d'avoir des fonctions qui ne sont pas des setters mais qui sont tout de même des mutators.

Les getters sont généralement déclarés const, afin de pouvoir être appelés aussi bien sur des objets const que non const. Les setters doivent être non const, afin de pouvoir modifier les membres données.

À titre d'illustration, mettons à jour notre classe Date pour lui donner un ensemble complet de getters et de setters :

#include <iostream>

class Date
{
private:
    int m_year { 2020 };
    int m_month { 10 };
    int m_day { 14 };

public:
    void print()
    {
        std::cout << m_year << '/' << m_month << '/' << m_day << '\n';
    }

    int getYear() const { return m_year; }        // getter pour l'année
    void setYear(int year) { m_year = year; }     // setter pour l'année

    int getMonth() const  { return m_month; }     // getter pour le mois
    void setMonth(int month) { m_month = month; } // setter pour le mois

    int getDay() const { return m_day; }          // getter pour le jour
    void setDay(int day) { m_day = day; }         // setter pour le jour
};

int main()
{
    Date d{};
    d.setYear(2021);
    std::cout << "The year is: " << d.getYear() << '\n';

    return 0;
}

Ce programme affiche :


The year is: 2021

Nommage des fonctions d'accès

Il n'existe pas de convention commune pour nommer les fonctions d'accès. Cependant, certaines conventions de nommage sont plus populaires que d'autres.

  • Préfixe « get » et « set » :
    int getDay() const { return m_day; }  // getter
    void setDay(int day) { m_day = day; } // setter

L'avantage des préfixes « get » et « set » est qu'ils indiquent clairement qu'il s'agit de fonctions d'accès (qui doivent être peu coûteuses à appeler).

  • Sans préfixe :
    int day() const { return m_day; }  // getter
    void day(int day) { m_day = day; } // setter

Ce style est plus concis et utilise le même nom pour le getter et le setter (la surcharge de fonctions permet de les distinguer). La bibliothèque standard C++ utilise cette convention.

L'inconvénient de la convention sans préfixe est qu'il n'est pas évident que cela modifie la valeur du membre day :

d.day(5); // cela ressemble-t-il à une modification du membre day avec la valeur 5 ?

Point clé

L'une des meilleures raisons de préfixer les membres données privés par « m_ » est d'éviter d'avoir un membre donnée et un getter portant le même nom (ce que C++ ne permet pas, contrairement à d'autres langages comme Java).

  • Préfixe « set » uniquement :
    int day() const { return m_day; }     // getter
    void setDay(int day) { m_day = day; } // setter

Le choix parmi ces styles relève de la préférence personnelle. Nous recommandons toutefois fortement d'utiliser le préfixe « set » pour les setters. Les getters peuvent utiliser le préfixe « get » ou aucun préfixe.

Astuce

Utilisez le préfixe « set » pour vos setters, afin de rendre plus évident qu'ils modifient l'état de l'objet.

Les getters doivent renvoyer par valeur ou par référence const lvalue

Les getters doivent offrir un accès en « lecture seule » aux données. Par conséquent, la bonne pratique est qu'ils renvoient soit par valeur (si la copie du membre est peu coûteuse), soit par référence lvalue constante (si la copie du membre est coûteuse).

Le renvoi de membres données par référence étant un sujet délicat, nous le traiterons plus en détail dans la leçon 14.7 -- Fonctions membres renvoyant des références vers des membres données.

Réserves sur les fonctions d'accès

Les cas dans lesquels il faut utiliser ou éviter les fonctions d'accès font l'objet de nombreux débats. Beaucoup de développeurs soutiennent que l'usage des fonctions d'accès va à l'encontre d'une bonne conception de classes (sujet qui pourrait à lui seul remplir un livre entier).

Pour l'instant, nous recommandons une approche pragmatique. Lorsque vous créez vos classes, tenez compte des points suivants :

  • Si votre classe n'a pas d'invariants et nécessite beaucoup de fonctions d'accès, envisagez plutôt d'utiliser une struct (dont les membres données sont publics) et de donner un accès direct aux membres.
  • Privilégiez l'implémentation de comportements ou d'actions plutôt que de fonctions d'accès. Par exemple, au lieu d'un setter setAlive(bool), implémentez les fonctions kill() et revive().
  • Ne fournissez des fonctions d'accès que lorsque la partie publique aurait raisonnablement besoin de lire ou de modifier la valeur d'un membre individuel.
