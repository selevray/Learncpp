14.17 — Agrégats constexpr et classes

Dans la leçon F.1 -- Fonctions constexpr, nous avons vu les fonctions constexpr, c'est-à-dire des fonctions qui peuvent être évaluées à la compilation ou à l'exécution. Par exemple :

#include <iostream>

constexpr int greater(int x, int y)
{
    return (x > y ? x : y);
}

int main()
{
    std::cout << greater(5, 6) << '\n'; // greater(5, 6) peut être évalué à la compilation ou à l'exécution

    constexpr int g { greater(5, 6) };  // greater(5, 6) doit être évalué à la compilation
    std::cout << g << '\n';             // affiche 6

    return 0;
}

Dans cet exemple, greater() est une fonction constexpr, et greater(5, 6) est une expression constante, qui peut être évaluée à la compilation ou à l'exécution. Comme std::cout << greater(5, 6) appelle greater(5, 6) dans un contexte non constexpr, le compilateur est libre de choisir d'évaluer greater(5, 6) à la compilation ou à l'exécution. Lorsque greater(5, 6) sert à initialiser la variable constexpr g, greater(5, 6) est appelée dans un contexte constexpr et doit être évaluée à la compilation.

Considérons maintenant l'exemple similaire suivant :

#include <iostream>

struct Pair
{
    int m_x {};
    int m_y {};

    int greater() const
    {
        return (m_x > m_y  ? m_x : m_y);
    }
};

int main()
{
    Pair p { 5, 6 };                  // les entrées sont des valeurs constexpr
    std::cout << p.greater() << '\n'; // p.greater() est évaluée à l'exécution

    constexpr int g { p.greater() };  // erreur de compilation : greater() n'est pas constexpr
    std::cout << g << '\n';

    return 0;
}

Dans cette version, nous avons un agrégat Pair de type struct, et greater() est désormais une fonction membre. Cependant, comme la fonction membre greater() n'est pas constexpr, p.greater() n'est pas une expression constante. Lorsque std::cout << p.greater() appelle p.greater() (dans un contexte non constexpr), p.greater() est évaluée à l'exécution. En revanche, lorsque nous essayons d'utiliser p.greater() pour initialiser la variable constexpr g, nous obtenons une erreur de compilation, car p.greater() ne peut pas être évaluée à la compilation.

Comme les entrées de p sont des valeurs constexpr (5 et 6), on pourrait penser que p.greater() devrait pouvoir être évaluée à la compilation. Mais comment faire ?

Fonctions membres constexpr

Tout comme les fonctions non membres, les fonctions membres peuvent être rendues constexpr à l'aide du mot-clé constexpr. Les fonctions membres constexpr peuvent être évaluées à la compilation ou à l'exécution.

#include <iostream>

struct Pair
{
    int m_x {};
    int m_y {};

    constexpr int greater() const // peut être évaluée à la compilation ou à l'exécution
    {
        return (m_x > m_y  ? m_x : m_y);
    }
};

int main()
{
    Pair p { 5, 6 };
    std::cout << p.greater() << '\n'; // correct : p.greater() est évaluée à l'exécution

    constexpr int g { p.greater() };  // erreur de compilation : p n'est pas constexpr
    std::cout << g << '\n';

    return 0;
}

Dans cet exemple, nous avons déclaré greater() comme fonction constexpr, de sorte que le compilateur peut l'évaluer à l'exécution ou à la compilation.

Lorsque nous appelons p.greater() dans l'expression d'exécution std::cout << p.greater(), elle est évaluée à l'exécution.

En revanche, lorsque p.greater() sert à initialiser la variable constexpr g, nous obtenons une erreur de compilation. Bien que greater() soit maintenant constexpr, p n'est toujours pas constexpr, donc p.greater() n'est pas une expression constante.

Agrégats constexpr

Si nous avons besoin que p soit constexpr, il suffit de le déclarer ainsi :

#include <iostream>

struct Pair // Pair est un agrégat
{
    int m_x {};
    int m_y {};

    constexpr int greater() const
    {
        return (m_x > m_y  ? m_x : m_y);
    }
};

int main()
{
    constexpr Pair p { 5, 6 };        // désormais constexpr
    std::cout << p.greater() << '\n'; // p.greater() est évaluée à l'exécution ou à la compilation

    constexpr int g { p.greater() };  // p.greater() doit être évaluée à la compilation
    std::cout << g << '\n';

    return 0;
}

Comme Pair est un agrégat, et que les agrégats supportent implicitement constexpr, le problème est réglé. Cela fonctionne ! Comme p est d'un type constexpr, et que greater() est une fonction membre constexpr, p.greater() est une expression constante et peut être utilisée là où seules des expressions constantes sont autorisées.

Contenu associé

Nous avons traité les agrégats dans la leçon 13.8 -- Initialisation d'agrégat de struct.

Objets de classe constexpr et constructeurs constexpr

Transformons maintenant notre Pair en non-agrégat :

#include <iostream>

class Pair // Pair n'est plus un agrégat
{
private:
    int m_x {};
    int m_y {};

public:
    Pair(int x, int y): m_x { x }, m_y { y } {}

    constexpr int greater() const
    {
        return (m_x > m_y  ? m_x : m_y);
    }
};

int main()
{
    constexpr Pair p { 5, 6 };       // erreur de compilation : p n'est pas un type littéral
    std::cout << p.greater() << '\n';

    constexpr int g { p.greater() };
    std::cout << g << '\n';

    return 0;
}

Cet exemple est presque identique au précédent, sauf que Pair n'est plus un agrégat (à cause de ses membres de données privés et de son constructeur).

Lorsque nous compilons ce programme, nous obtenons une erreur de compilation indiquant que Pair n'est pas un « type littéral ». Comment cela ?

En C++, un type littéral (literal type) est tout type pour lequel il est possible de créer un objet dans une expression constante. Autrement dit, un objet ne peut pas être constexpr à moins que son type ne soit un type littéral. Or notre Pair, qui n'est pas un agrégat, ne remplit pas cette condition.

Terminologie

Un littéral et un type littéral sont des notions distinctes (mais liées). Un littéral est une valeur constexpr insérée directement dans le code source. Un type littéral est un type pouvant servir de type à une valeur constexpr. Un littéral a toujours un type littéral. En revanche, une valeur ou un objet d'un type littéral n'est pas forcément un littéral.

La définition d'un type littéral est complexe ; un résumé se trouve sur cppreference. Il est cependant utile de noter que les types littéraux comprennent :

  • Les types scalaires (ceux qui contiennent une seule valeur, comme les types fondamentaux et les pointeurs)
  • Les types référence
  • La plupart des agrégats
  • Les classes dotées d'un constructeur constexpr

Nous comprenons maintenant pourquoi notre Pair n'est pas un type littéral. Lorsqu'un objet de classe est instancié, le compilateur appelle la fonction constructeur pour l'initialiser. Or le constructeur de notre classe Pair n'est pas constexpr, il ne peut donc pas être invoqué à la compilation. Par conséquent, les objets Pair ne peuvent pas être constexpr.

La solution est simple : il suffit de rendre le constructeur constexpr lui aussi :

#include <iostream>

class Pair
{
private:
    int m_x {};
    int m_y {};

public:
    constexpr Pair(int x, int y): m_x { x }, m_y { y } {} // désormais constexpr

    constexpr int greater() const
    {
        return (m_x > m_y  ? m_x : m_y);
    }
};

int main()
{
    constexpr Pair p { 5, 6 };
    std::cout << p.greater() << '\n';

    constexpr int g { p.greater() };
    std::cout << g << '\n';

    return 0;
}

Cela fonctionne comme prévu, tout comme la version agrégat de Pair.

Bonne pratique

Si vous voulez que votre classe puisse être évaluée à la compilation, rendez constexpr ses fonctions membres et son constructeur.

Les constructeurs implicitement définis sont constexpr lorsqu'ils peuvent l'être. Les constructeurs explicitement défaits par défaut (= default) doivent être explicitement déclarés constexpr.

Remarque

Le caractère constexpr fait partie de l'interface de la classe : le retirer plus tard casserait le code des appelants qui utilisent la fonction dans un contexte constant.

Les membres constexpr peuvent être nécessaires avec des objets non constexpr/non const

Dans l'exemple précédent, comme l'initialiseur de la variable constexpr g doit être une expression constante, il est clair que p.greater() doit être une expression constante, et donc que p, le constructeur de Pair et greater() doivent tous être constexpr.

En revanche, si nous remplaçons p.greater() par une fonction constexpr, les choses deviennent un peu moins évidentes :

#include <iostream>

class Pair
{
private:
    int m_x {};
    int m_y {};

public:
    constexpr Pair(int x, int y): m_x { x }, m_y { y } {}

    constexpr int greater() const
    {
        return (m_x > m_y  ? m_x : m_y);
    }
};

constexpr int init()
{
    Pair p { 5, 6 };    // nécessite que le constructeur soit constexpr lorsqu'il est évalué à la compilation
    return p.greater(); // nécessite que greater() soit constexpr lorsqu'elle est évaluée à la compilation
}

int main()
{
    constexpr int g { init() }; // init() évaluée dans un contexte de compilation
    std::cout << g << '\n';

    return 0;
}

Rappelez-vous qu'une fonction constexpr peut être évaluée à l'exécution ou à la compilation. Et lorsqu'une fonction constexpr est évaluée à la compilation, elle ne peut appeler que des fonctions capables d'être évaluées à la compilation. Dans le cas d'un type classe, cela signifie des fonctions membres constexpr.

Comme g est constexpr, init() doit être évaluée à la compilation. Dans la fonction init(), nous définissons p comme non constexpr/non const (parce que nous le pouvons, et non parce que nous le devrions). Même si p n'est pas déclaré constexpr, p doit tout de même être créé à la compilation, et nécessite donc un constructeur de Pair constexpr. De même, pour que p.greater() soit évaluée à la compilation, greater() doit être une fonction membre constexpr. Si le constructeur de Pair ou greater() n'était pas constexpr, le compilateur signalerait une erreur.

Point clé

Lorsqu'une fonction constexpr est évaluée dans un contexte de compilation, seules les fonctions constexpr peuvent être appelées.

Les fonctions membres constexpr peuvent être const ou non-const (C++14)

En C++11, les fonctions membres constexpr non statiques sont implicitement const (sauf les constructeurs).

En revanche, depuis C++14, les fonctions membres constexpr ne sont plus implicitement const. Cela signifie que si vous voulez qu'une fonction constexpr soit const, vous devez le indiquer explicitement.

Les fonctions membres constexpr non-const peuvent modifier les membres de données (Facultatif)

Une fonction membre constexpr non-const peut modifier les membres de données de la classe, à condition que l'objet implicite ne soit pas const. Cela reste vrai même lorsque la fonction est évaluée à la compilation.

Voici un exemple artificiel qui l'illustre :

#include <iostream>

class Pair
{
private:
    int m_x {};
    int m_y {};

public:
    constexpr Pair(int x, int y): m_x { x }, m_y { y } {}

    constexpr int greater() const // constexpr et const
    {
        return (m_x > m_y  ? m_x : m_y);
    }

    constexpr void reset() // constexpr mais non-const
    {
        m_x = m_y = 0; // une fonction membre non-const peut modifier les membres
    }

    constexpr const int& getX() const { return m_x; }
};

// Cette fonction est constexpr
constexpr Pair zero()
{
    Pair p { 1, 2 }; // p est non-const
    p.reset();       // appel autorisé d'une fonction membre non-const sur un objet non-const
    return p;
}

int main()
{
    Pair p1 { 3, 4 };
    p1.reset();                     // appel autorisé d'une fonction membre non-const sur un objet non-const
    std::cout << p1.getX() << '\n'; // affiche 0

    Pair p2 { zero() };             // zero() sera évaluée à l'exécution
    p2.reset();                     // appel autorisé d'une fonction membre non-const sur un objet non-const
    std::cout << p2.getX() << '\n'; // affiche 0

    constexpr Pair p3 { zero() };   // zero() sera évaluée à la compilation
//    p3.reset();                   // erreur de compilation : impossible d'appeler une fonction membre non-const sur un objet const
    std::cout << p3.getX() << '\n'; // affiche 0

    return 0;
}

En parcourant cet exemple, gardez à l'esprit que :

  • Une fonction membre non-const peut modifier les membres d'objets non-const.
  • Une fonction membre constexpr peut être appelée dans un contexte d'exécution ou dans un contexte de compilation.

Ces deux points sont indépendants.

Dans le cas de p1, p1 est non-const. Nous avons donc le droit d'appeler la fonction membre non-const p1.reset() pour modifier p1. Le fait que reset() soit constexpr n'a pas d'importance ici, car rien de ce que nous faisons n'exige une évaluation à la compilation.

Le cas de p2 est similaire. Ici, l'initialiseur de p2 est un appel de fonction à zero(). Bien que zero() soit une fonction constexpr, elle est appelée dans un contexte d'exécution et se comporte comme une fonction ordinaire. Dans zero(), nous instancions p non-const, appelons la fonction membre non-const p.reset() sur cet objet, puis retournons p. Le Pair retourné sert d'initialiseur à p2. Le fait que zero() et reset() soient constexpr n'a pas d'importance dans ce cas, car rien de ce que nous faisons n'exige une évaluation à la compilation.

Le cas de p3 est le plus intéressant. Comme p3 est constexpr, son initialiseur doit être une expression constante. L'appel à zero() doit donc être évalué à la compilation. Et comme nous évaluons dans un contexte de compilation, nous ne pouvons appeler que des fonctions constexpr. Dans zero(), p est non-const (ce qui est permis, même si nous évaluons à la compilation). Toutefois, comme nous sommes dans un contexte de compilation, le constructeur utilisé pour créer p doit être constexpr. De même que dans le cas de p2, nous avons le droit d'appeler la fonction membre non-const p.reset() sur l'objet non-const p. Mais comme nous sommes dans un contexte de compilation, la fonction membre reset() doit être constexpr. La fonction retourne ensuite p, qui sert à initialiser p3.

Note de l'auteur

Oui, nous avons utilisé un objet non-const pour initialiser un objet constexpr. Si cela vous paraît déroutant, c'est probablement parce que vous n'avez pas complètement distingué const de constexpr.

Rien n'impose qu'une variable constexpr soit initialisée avec une valeur const. Cela peut sembler le cas, car la plupart du temps nous initialisons les variables constexpr avec des littéraux (qui sont const) ou avec d'autres variables constexpr (qui sont implicitement const), et parce que les termes const et constexpr se ressemblent.

L'exigence porte en réalité sur le fait qu'une variable constexpr soit initialisée avec une expression constante. Pour les fonctions (et les opérateurs), constexpr n'implique pas const : les fonctions (et opérateurs) constexpr peuvent utiliser des objets non-const, voire en retourner.

Ce qui compte n'est pas le const, mais le fait que le compilateur puisse déterminer la valeur de l'objet à la compilation. Et, dans le cas des fonctions constexpr, cela est possible même lorsqu'elles retournent un objet non-const !

Fonctions constexpr retournant des références (ou pointeurs) const (Facultatif)

En général, on ne voit pas constexpr et const côte à côte, mais c'est le cas lorsqu'une fonction membre constexpr retourne une référence const (ou un pointeur vers const).

Dans notre classe Pair ci-dessus, getX() est une fonction membre constexpr qui retourne une référence const :

    constexpr const int& getX() const { return m_x; }

Que de const !

Le constexpr indique que la fonction membre peut être évaluée à la compilation. Le const int& est le type de retour de la fonction. Le const le plus à droite signifie que la fonction membre elle-même est const, ce qui permet de l'appeler sur des objets const.

En passant…

Une fonction membre retournant plutôt un pointeur const vers un objet const pourrait ressembler à ceci :

constexpr const int* const getXPtr() const { return &m_x; }

N'est-ce pas magnifique ? Non ? Très bien.
