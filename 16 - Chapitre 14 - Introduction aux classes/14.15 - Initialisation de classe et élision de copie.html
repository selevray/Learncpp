14.15 — Initialisation de classe et élision de copie

Dans la leçon 1.4 -- Affectation et initialisation des variables, nous avons présenté 6 types d'initialisation de base pour les objets de types fondamentaux :

int a;         // no initializer (default initialization)
int b = 5;     // initializer after equals sign (copy initialization)
int c( 6 );    // initializer in parentheses (direct initialization)

// List initialization methods (C++11)
int d { 7 };   // initializer in braces (direct list initialization)
int e = { 8 }; // initializer in braces after equals sign (copy list initialization)
int f {};      // initializer is empty braces (value initialization)

Tous ces types d'initialisation sont valides pour les objets de type classe :

#include <iostream>

class Foo
{
public:

    // Default constructor
    Foo()
    {
        std::cout << "Foo()\n";
    }

    // Normal constructor
    Foo(int x)
    {
        std::cout << "Foo(int) " << x << '\n';
    }

    // Copy constructor
    Foo(const Foo&)
    {
        std::cout << "Foo(const Foo&)\n";
    }
};

int main()
{
    // Calls Foo() default constructor
    Foo f1;           // default initialization
    Foo f2{};         // value initialization (preferred)

    // Calls foo(int) normal constructor
    Foo f3 = 3;       // copy initialization (non-explicit constructors only)
    Foo f4(4);        // direct initialization
    Foo f5{ 5 };      // direct list initialization (preferred)
    Foo f6 = { 6 };   // copy list initialization (non-explicit constructors only)

    // Calls foo(const Foo&) copy constructor
    Foo f7 = f3;      // copy initialization
    Foo f8(f3);       // direct initialization
    Foo f9{ f3 };     // direct list initialization (preferred)
    Foo f10 = { f3 }; // copy list initialization

    return 0;
}

En C++ moderne, l'initialisation par copie, l'initialisation directe et l'initialisation par liste font essentiellement la même chose : elles initialisent un objet.

Pour tous les types d'initialisation :

  • Lors de l'initialisation d'un type classe, l'ensemble des constructeurs de cette classe est examiné, et la résolution de surcharge sert à déterminer le constructeur qui correspond le mieux. Cela peut impliquer une conversion implicite des arguments.
  • Lors de l'initialisation d'un type non classe, les règles de conversion implicite servent à déterminer si une conversion implicite existe.

Point clé

Il y a trois différences principales entre les formes d'initialisation :

  • L'initialisation par liste interdit les conversions avec rétrécissement (narrowing).
  • L'initialisation par copie ne considère que les constructeurs et fonctions de conversion non explicit. Nous y reviendrons dans la leçon 14.16 -- Constructeurs de conversion et mot-clé explicit.
  • L'initialisation par liste donne la priorité aux constructeurs de liste correspondants par rapport aux autres constructeurs correspondants. Nous y reviendrons dans la leçon 16.2 -- Introduction à std::vector et aux constructeurs de liste.

Notez aussi que, dans certaines circonstances, certaines formes d'initialisation sont interdites (par exemple, dans la liste d'initialisation des membres d'un constructeur, on ne peut utiliser que les formes directes d'initialisation, pas l'initialisation par copie).

Copies inutiles

Considérons ce programme simple :

#include <iostream>

class Something
{
    int m_x{};

public:
    Something(int x)
        : m_x{ x }
    {
        std::cout << "Normal constructor\n";
    }

    Something(const Something& s)
        : m_x { s.m_x }
    {
        std::cout << "Copy constructor\n";
    }

    void print() const { std::cout << "Something(" << m_x << ")\n"; }
};

int main()
{
    Something s { Something { 5 } }; // focus on this line
    s.print();

    return 0;
}

Lors de l'initialisation de la variable s ci-dessus, nous construisons d'abord un Something temporaire, initialisé avec la valeur 5 (ce qui utilise le constructeur Something(int)). Ce temporaire sert ensuite à initialiser s. Comme le temporaire et s ont le même type (ce sont deux objets Something), le constructeur de copie Something(const Something&) serait normalement appelé ici pour copier les valeurs du temporaire dans s. Au final, s est initialisé avec la valeur 5.

Sans aucune optimisation, le programme ci-dessus afficherait :


Normal constructor
Copy constructor
Something(5)

Cependant, ce programme est inutilement inefficace, puisqu'il a fallu effectuer deux appels de constructeur : un à Something(int) et un à Something(const Something&). Notez que le résultat final est le même que si nous avions écrit ceci :

Something s { 5 }; // only invokes Something(int), no copy constructor

Cette version produit le même résultat, mais elle est plus efficace, car elle n'appelle que Something(int) (aucun constructeur de copie n'est nécessaire).

Élision de copie

Puisque le compilateur est libre de réécrire les instructions pour les optimiser, on peut se demander s'il peut supprimer la copie inutile et traiter Something s { Something{5} }; comme si nous avions écrit Something s { 5 } dès le départ.

La réponse est oui, et ce procédé s'appelle l'élision de copie (copy elision). L'élision de copie est une technique d'optimisation du compilateur qui lui permet de supprimer des copies d'objets inutiles. Autrement dit, dans les cas où le compilateur appellerait normalement un constructeur de copie, il est libre de réécrire le code pour éviter complètement cet appel. Lorsque le compilateur supprime par optimisation un appel au constructeur de copie, on dit que le constructeur a été élidé.

Contrairement aux autres types d'optimisation, l'élision de copie est exemptée de la règle « as-if ». C'est-à-dire que l'élision de copie peut supprimer le constructeur de copie même s'il a des effets de bord (comme afficher du texte dans la console) ! C'est pourquoi les constructeurs de copie ne devraient pas avoir d'effets de bord autres que la copie : si le compilateur élide l'appel au constructeur de copie, les effets de bord ne seront pas exécutés, et le comportement observable du programme changera !

Contenu connexe

Nous avons abordé la règle as-if dans la leçon 5.4 -- La règle as-if et l'optimisation à la compilation.

Nous pouvons le constater dans l'exemple ci-dessus. Si vous exécutez le programme avec un compilateur C++17, il produira le résultat suivant :


Normal constructor
Something(5)

Le compilateur a élidé le constructeur de copie pour éviter une copie inutile, et par conséquent l'instruction qui affiche « Copy constructor » ne s'exécute pas ! Le comportement observable de notre programme a changé à cause de l'élision de copie !

Élision de copie dans le passage par valeur et le retour par valeur

Le constructeur de copie est normalement appelé lorsqu'un argument du même type que le paramètre est passé par valeur, ou lorsqu'un retour par valeur est utilisé. Toutefois, dans certains cas, ces copies peuvent être élidées. Le programme suivant illustre certains de ces cas :

#include <iostream>

class Something
{
public:
    Something() = default;
    Something(const Something&)
    {
        std::cout << "Copy constructor called\n";
    }
};

Something rvo()
{
    return Something{}; // calls Something() and copy constructor
}

Something nrvo()
{
    Something s{}; // calls Something()
    return s;      // calls copy constructor
}

int main()
{
    std::cout << "Initializing s1\n";
    Something s1 { rvo() }; // calls copy constructor

    std::cout << "Initializing s2\n";
    Something s2 { nrvo() }; // calls copy constructor

        return 0;
}

En C++14 ou antérieur, avec l'élision de copie désactivée, le programme ci-dessus appellerait le constructeur de copie 4 fois :

  • Une fois quand rvo retourne Something à main.
  • Une fois quand la valeur de retour de rvo() sert à initialiser s1.
  • Une fois quand nrvo retourne s à main.
  • Une fois quand la valeur de retour de nrvo() sert à initialiser s2.

Cependant, grâce à l'élision de copie, il est probable que votre compilateur élide la plupart, voire la totalité, de ces appels au constructeur de copie. Visual Studio 2022 en élide 3 (il n'élide pas le cas où nrvo() retourne par valeur), et GCC les élide tous les 4.

Il n'est pas important de mémoriser quand le compilateur effectue ou non l'élision de copie. Sachez simplement que c'est une optimisation que votre compilateur réalisera s'il le peut. Si vous vous attendez à voir votre constructeur de copie appelé et que ce n'est pas le cas, l'élision de copie en est probablement la raison.

Élision de copie obligatoire en C++17 (C++17)

Avant C++17, l'élision de copie était strictement une optimisation facultative que les compilateurs pouvaient appliquer. En C++17, l'élision de copie est devenue obligatoire dans certains cas. Dans ces cas, l'élision de copie est effectuée automatiquement (même si vous demandez à votre compilateur de ne pas la réaliser).

En exécutant le même exemple que ci-dessus en C++17 ou plus récent, les appels au constructeur de copie qui auraient lieu lorsque rvo() retourne et lorsque s1 est initialisé avec cette valeur doivent obligatoirement être élidés. L'initialisation de s2 avec nrvo() n'est pas un cas d'élision obligatoire ; les 2 appels au constructeur de copie qui y ont lieu peuvent donc être élidés ou non selon votre compilateur et vos paramètres d'optimisation.

Dans les cas d'élision facultative, un constructeur de copie accessible doit être disponible (par exemple, non supprimé), même si l'appel effectif au constructeur de copie est élidé.

Dans les cas d'élision obligatoire, il n'est pas nécessaire qu'un constructeur de copie accessible soit disponible (autrement dit, l'élision obligatoire peut avoir lieu même si le constructeur de copie est supprimé).
