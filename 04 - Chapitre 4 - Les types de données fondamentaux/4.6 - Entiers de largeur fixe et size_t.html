4.6 — Entiers de largeur fixe et size_t

Dans les leçons précédentes sur les entiers, nous avons vu que C++ garantit seulement qu'une variable entière a une taille minimale, mais elle peut être plus grande selon le système cible.

Par exemple, un int a une taille minimale de 16 bits, mais il fait généralement 32 bits sur les architectures modernes.

Si vous supposez qu'un int fait 32 bits parce que c'est le cas le plus courant, votre programme risque de mal se comporter sur les architectures où int fait en réalité 16 bits (puisque vous stockerez probablement des valeurs nécessitant 32 bits dans une variable qui n'en a que 16, ce qui provoquera un dépassement de capacité ou un comportement indéfini).

Par exemple :

#include <iostream>

int main()
{
    int x { 32767 };        // x peut faire 16 ou 32 bits
    x = x + 1;              // 32768 provoque un dépassement si int fait 16 bits, sans problème si int fait 32 bits
    std::cout << x << '\n'; // qu'affiche ce programme ?

    return 0;
}

Sur une machine où int fait 32 bits, la valeur 32768 est comprise dans l'intervalle d'un int et peut donc être stockée dans x sans problème. Sur une telle machine, ce programme affiche 32768. En revanche, sur une machine où int fait 16 bits, la valeur 32768 ne tient pas dans un entier de 16 bits (dont l'intervalle va de -32 768 à 32 767). Sur une telle machine, x = x + 1 provoque un dépassement de capacité, la valeur -32768 est stockée dans x puis affichée.

À l'inverse, si vous supposez qu'un int ne fait que 16 bits pour que votre programme fonctionne sur toutes les architectures, l'intervalle des valeurs que vous pouvez stocker en toute sécurité dans un int est fortement réduit. Et sur les systèmes où int fait en réalité 32 bits, vous n'utilisez pas la moitié de la mémoire allouée à chaque int.

Point clé

Dans la plupart des cas, nous n'instancions qu'un petit nombre de variables int à la fois, et celles-ci sont généralement détruites à la fin de la fonction dans laquelle elles sont créées. Dans ces cas, gaspiller 2 octets de mémoire par variable n'est pas un problème (la plage limitée est un problème bien plus important). En revanche, lorsque notre programme alloue des millions de variables int, gaspiller 2 octets par variable peut avoir un impact significatif sur la consommation mémoire globale du programme.

Pourquoi la taille des types entiers n'est-elle pas fixe ?

La réponse courte remonte aux premiers temps du C, lorsque les ordinateurs étaient lents et que la performance était la préoccupation majeure. Le C a délibérément laissé ouverte la taille d'un entier afin que les implémenteurs de compilateurs puissent choisir une taille pour int offrant les meilleures performances sur l'architecture cible. Ainsi, les programmeurs pouvaient simplement utiliser int sans se soucier de savoir s'ils auraient pu employer un type plus performant.

Selon les standards actuels, l'absence d'intervalles constants pour les différents types entiers est problématique (surtout dans un langage conçu pour être portable).

Entiers de largeur fixe

Pour résoudre les problèmes évoqués ci-dessus, C++11 fournit un ensemble alternatif de types entiers dont la taille est garantie identique sur toutes les architectures. Comme la taille de ces entiers est fixe, on les appelle des entiers de largeur fixe (fixed-width integers).

Les entiers de largeur fixe sont définis (dans l'en-tête <cstdint>) de la façon suivante :

Nom Taille fixe Intervalle fixe Remarques
std::int8_t 1 octet, signé -128 à 127 Traité comme un signed char sur de nombreux systèmes. Voir la note ci-dessous.
std::uint8_t 1 octet, non signé 0 à 255 Traité comme un unsigned char sur de nombreux systèmes. Voir la note ci-dessous.
std::int16_t 2 octets, signé -32 768 à 32 767
std::uint16_t 2 octets, non signé 0 à 65 535
std::int32_t 4 octets, signé -2 147 483 648 à 2 147 483 647
std::uint32_t 4 octets, non signé 0 à 4 294 967 295
std::int64_t 8 octets, signé -9 223 372 036 854 775 808 à 9 223 372 036 854 775 807
std::uint64_t 8 octets, non signé 0 à 18 446 744 073 709 551 615

Voici un exemple :

#include <cstdint> // pour les entiers de largeur fixe
#include <iostream>

int main()
{
    std::int32_t x { 32767 }; // x est toujours un entier de 32 bits
    x = x + 1;                // donc 32768 tiendra toujours
    std::cout << x << '\n';

    return 0;
}

Bonne pratique

Utilisez un type entier de largeur fixe lorsque vous avez besoin d'un type entier dont l'intervalle est garanti.

Attention : std::int8_t et std::uint8_t se comportent généralement comme des char

En raison d'un oubli dans la spécification du C++, les compilateurs modernes traitent généralement std::int8_t et std::uint8_t (ainsi que les types rapides et les types « least » de largeur fixe, que nous présenterons dans un instant) comme signed char et unsigned char respectivement. Ainsi, sur la plupart des systèmes modernes, les types entiers de largeur fixe sur 8 bits se comportent comme des types char.

Pour un aperçu rapide :

#include <cstdint> // pour les entiers de largeur fixe
#include <iostream>

int main()
{
    std::int8_t x { 65 };   // initialise un type entier sur 8 bits avec la valeur 65
    std::cout << x << '\n'; // vous vous attendez sans doute à ce que cela affiche 65

    return 0;
}

Bien que vous vous attendiez probablement à ce que le programme ci-dessus affiche 65, ce n'est très probablement pas le cas.

Nous verrons ce que cet exemple affiche réellement (et comment s'assurer qu'il affiche toujours 65) dans la leçon 4.12 -- Introduction à la conversion de types et static_cast, après avoir étudié les char (et leur affichage) dans la leçon 4.11 -- Les char.

Attention

Les types entiers de largeur fixe sur 8 bits sont souvent traités comme des char plutôt que comme des valeurs entières (ce comportement peut varier selon le système). Les types entiers de 16 bits et plus ne sont pas concernés par ce problème.

Pour les lecteurs avancés

Les entiers de largeur fixe ne définissent en fait pas de nouveaux types : ce sont simplement des alias pour des types entiers existants de la taille souhaitée. Pour chaque type de largeur fixe, l'implémentation (le compilateur et la bibliothèque standard) détermine le type existant qui est aliasé. Par exemple, sur une plateforme où int fait 32 bits, std::int32_t sera un alias pour int. Sur un système où int fait 16 bits (et long 32 bits), std::int32_t sera plutôt un alias pour long.

Qu'en est-il des types de largeur fixe sur 8 bits ?

Dans la plupart des cas, std::int8_t est un alias pour signed char, car c'est le seul type entier signé de 8 bits disponible (bool et char ne sont pas considérés comme des types entiers signés). Dans ce cas, std::int8_t se comporte exactement comme un char sur cette plateforme.

Cependant, dans de rares cas, si une plateforme possède un type entier signé de 8 bits propre à l'implémentation, celle-ci peut décider de faire de std::int8_t un alias pour ce type. Dans ce cas, std::int8_t se comportera comme ce type, ce qui peut ressembler davantage à un int qu'à un char.

std::uint8_t se comporte de manière similaire.

Autres inconvénients des entiers de largeur fixe

Les entiers de largeur fixe présentent quelques inconvénients potentiels :

Premièrement, les entiers de largeur fixe ne sont pas garantis d'être définis sur toutes les architectures. Ils n'existent que sur les systèmes où il existe des types entiers fondamentaux correspondant à leurs largeurs et suivant une certaine représentation binaire. Votre programme ne compilera pas sur une architecture qui ne supporte pas un entier de largeur fixe utilisé par votre programme. Cependant, les architectures modernes ayant convergé vers des variables de 8, 16, 32 et 64 bits, ce problème est peu probable, sauf si votre programme doit être portable vers des architectures mainframe ou embarquées exotiques.

Deuxièmement, un entier de largeur fixe peut être plus lent qu'un type plus large sur certaines architectures. Par exemple, si vous avez besoin d'un entier garanti sur 32 bits, vous pourriez choisir std::int32_t, alors que votre processeur peut en réalité traiter les entiers de 64 bits plus rapidement. Toutefois, le fait qu'un processeur traite un type plus vite ne signifie pas que votre programme sera globalement plus rapide : les programmes modernes sont souvent limités par l'utilisation de la mémoire plutôt que par le processeur, et l'empreinte mémoire plus grande peut ralentir le programme davantage que le traitement plus rapide ne l'accélère. Il est difficile de le savoir sans mesurer.

Ce ne sont toutefois que des réserves mineures.

Types entiers rapides et « least » (Optionnel)

Pour atténuer les inconvénients ci-dessus, C++ définit aussi deux autres ensembles d'entiers dont l'existence est garantie.

Les types rapides (std::int_fast#_t et std::uint_fast#_t) fournissent le type entier signé/non signé le plus rapide dont la largeur est d'au moins # bits (où # = 8, 16, 32 ou 64). Par exemple, std::int_fast32_t vous donne le type entier signé le plus rapide d'au moins 32 bits. Par « le plus rapide », nous entendons le type entier que le processeur peut traiter le plus rapidement.

Les types « least » (std::int_least#_t et std::uint_least#_t) fournissent le type entier signé/non signé le plus petit dont la largeur est d'au moins # bits (où # = 8, 16, 32 ou 64). Par exemple, std::uint_least32_t vous donne le plus petit type entier non signé d'au moins 32 bits.

Voici un exemple tiré de Visual Studio de l'auteur (application console 32 bits) :

#include <cstdint> // pour les types rapides et least
#include <iostream>

int main()
{
    std::cout << "least 8:  " << sizeof(std::int_least8_t)  * 8 << " bits\n";
    std::cout << "least 16: " << sizeof(std::int_least16_t) * 8 << " bits\n";
    std::cout << "least 32: " << sizeof(std::int_least32_t) * 8 << " bits\n";
    std::cout << '\n';
    std::cout << "fast 8:  "  << sizeof(std::int_fast8_t)   * 8 << " bits\n";
    std::cout << "fast 16: "  << sizeof(std::int_fast16_t)  * 8 << " bits\n";
    std::cout << "fast 32: "  << sizeof(std::int_fast32_t)  * 8 << " bits\n";

    return 0;
}

Ce programme produit le résultat suivant :


least 8:  8 bits
least 16: 16 bits
least 32: 32 bits

fast 8:  8 bits
fast 16: 32 bits
fast 32: 32 bits

On constate que std::int_least16_t fait 16 bits, alors que std::int_fast16_t fait en réalité 32 bits. C'est parce que, sur la machine de l'auteur, les entiers de 32 bits sont plus rapides à traiter que ceux de 16 bits.

Dans un autre exemple, supposons que nous soyons sur une architecture qui ne dispose que de types entiers de 16 et 64 bits. std::int32_t n'existerait pas, alors que std::int_least32_t (et std::int_fast32_t) feraient 64 bits.

Cependant, ces entiers rapides et « least » ont leurs propres inconvénients. Premièrement, peu de programmeurs les utilisent réellement, et ce manque de familiarité peut entraîner des erreurs. Ensuite, les types rapides peuvent aussi gaspiller de la mémoire, car leur taille réelle peut être nettement supérieure à ce que leur nom laisse supposer.

Plus grave encore, la taille des entiers rapides et « least » étant définie par l'implémentation, votre programme peut présenter des comportements différents sur les architectures où ils correspondent à des tailles différentes. Par exemple :

#include <cstdint>
#include <iostream>

int main()
{
    std::uint_fast16_t sometype { 0 };
    sometype = sometype - 1; // dépassement volontaire pour provoquer le comportement de bouclage

    std::cout << sometype << '\n';

    return 0;
}

Ce code produit des résultats différents selon que std::uint_fast16_t fait 16, 32 ou 64 bits ! C'est précisément ce que nous cherchions à éviter en utilisant des entiers de largeur fixe !

Bonne pratique

Évitez les types entiers rapides et « least », car ils peuvent présenter des comportements différents sur les architectures où ils correspondent à des tailles différentes.

Bonnes pratiques concernant les types entiers

Compte tenu des avantages et inconvénients des types entiers fondamentaux, des types entiers de largeur fixe, des types entiers rapides/« least » et des difficultés liées au signé/non signé, il n'existe pas de consensus clair sur les bonnes pratiques en matière d'entiers.

Notre position est qu'il vaut mieux être correct que rapide, et échouer à la compilation plutôt qu'à l'exécution. Par conséquent, si vous avez besoin d'un type entier à l'intervalle garanti, nous recommandons d'éviter les types rapides/« least » au profit des types de largeur fixe. Si vous découvrez plus tard la nécessité de prendre en charge une plateforme exotique pour laquelle un type entier de largeur fixe précis ne compile pas, vous pourrez alors décider comment migrer votre programme (et le retester intégralement) à ce moment-là.

Bonne pratique

  • Préférez int lorsque la taille de l'entier n'a pas d'importance (par exemple, lorsque le nombre tiendra toujours dans l'intervalle d'un entier signé de 2 octets). Par exemple, si vous demandez à l'utilisateur son âge, ou si vous comptez de 1 à 10, il importe peu que int fasse 16 ou 32 bits (les nombres tiendront dans les deux cas). Cela couvre la grande majorité des cas que vous rencontrerez.
  • Préférez std::int#_t lorsque vous stockez une grandeur dont l'intervalle doit être garanti.
  • Préférez std::uint#_t lorsque vous manipulez des bits ou lorsqu'un comportement de bouclage bien défini est requis (par exemple pour la cryptographie ou la génération de nombres aléatoires).

Évitez autant que possible :

  • Les entiers short et long (préférez un type entier de largeur fixe).
  • Les types entiers rapides et « least » (préférez un type entier de largeur fixe).
  • Les types non signés pour stocker des grandeurs (préférez un type entier signé).
  • Les entiers de largeur fixe sur 8 bits (préférez un entier de largeur fixe sur 16 bits).
  • Les entiers de largeur fixe propres à un compilateur (par exemple, Visual Studio définit __int8, __int16, etc.).

Qu'est-ce que std::size_t ?

Considérez le code suivant :

#include <iostream>

int main()
{
    std::cout << sizeof(int) << '\n';

    return 0;
}

Sur la machine de l'auteur, ce programme affiche :


4

Assez simple, n'est-ce pas ? On peut en déduire que l'opérateur sizeof renvoie une valeur entière, mais de quel type entier s'agit-il ? Un int ? Un short ? La réponse est que sizeof renvoie une valeur de type std::size_t. std::size_t est un alias pour un type entier non signé défini par l'implémentation. Autrement dit, c'est le compilateur qui décide si std::size_t est un unsigned int, un unsigned long, un unsigned long long, etc.

Point clé

std::size_t est un alias pour un type entier non signé défini par l'implémentation. Il est utilisé dans la bibliothèque standard pour représenter la taille en octets ou la longueur des objets.

Pour les lecteurs avancés

std::size_t est en réalité un typedef. Nous étudions les typedefs dans la leçon 10.7 -- Typedefs et alias de types.

std::size_t est défini dans plusieurs en-têtes différents. Si vous avez besoin d'utiliser std::size_t, <cstddef> est le meilleur en-tête à inclure, car il contient le moins d'autres identifiants définis.

Par exemple :

#include <cstddef>  // pour std::size_t
#include <iostream>

int main()
{
    int x { 5 };
    std::size_t s { sizeof(x) }; // sizeof renvoie une valeur de type std::size_t, c'est donc le type de s
    std::cout << s << '\n';

    return 0;
}

Bonne pratique

Si vous utilisez explicitement std::size_t dans votre code, incluez l'un des en-têtes qui définissent std::size_t (nous recommandons <cstddef>).

L'utilisation de sizeof ne nécessite aucun en-tête (même si elle renvoie une valeur dont le type est std::size_t).

Tout comme la taille d'un entier peut varier selon le système, std::size_t varie également en taille. std::size_t est garanti non signé et d'au moins 16 bits, mais sur la plupart des systèmes il équivaut à la largeur d'adresse de l'application. Autrement dit, pour les applications 32 bits, std::size_t sera généralement un entier non signé de 32 bits, et pour une application 64 bits, un entier non signé de 64 bits.

L'opérateur sizeof renvoie une valeur de type std::size_t (Optionnel)

Note de l'auteur

Amusamment, nous pouvons utiliser l'opérateur sizeof (qui renvoie une valeur de type std::size_t) pour demander la taille de std::size_t lui-même :

#include <cstddef> // pour std::size_t
#include <iostream>

int main()
{
    std::cout << sizeof(std::size_t) << '\n';

    return 0;
}

Compilé en application console 32 bits (4 octets) sur le système de l'auteur, ce programme affiche :


4

std::size_t impose une limite supérieure à la taille d'un objet (Optionnel)

L'opérateur sizeof doit pouvoir renvoyer la taille en octets d'un objet sous forme de valeur de type std::size_t. Par conséquent, la taille en octets d'un objet ne peut pas dépasser la plus grande valeur que std::size_t peut contenir.

La norme C++20 ([basic.compound] 1.8.2) indique : « Construire un type tel que le nombre d'octets de sa représentation objet dépasse la valeur maximale représentable dans le type std::size_t (17.2) est mal formé. »

Si un objet plus grand pouvait être créé, sizeof ne pourrait pas renvoyer sa taille en octets, car elle sortirait de l'intervalle qu'un std::size_t peut contenir. Ainsi, créer un objet dont la taille en octets est supérieure à la plus grande valeur d'un std::size_t est invalide (et provoquera une erreur de compilation).

Par exemple, supposons que std::size_t fasse 4 octets sur notre système. Un entier non signé de 4 octets a pour intervalle 0 à 4 294 967 295. Par conséquent, un std::size_t de 4 octets peut contenir n'importe quelle valeur de 0 à 4 294 967 295. Tout objet dont la taille en octets se situe dans cet intervalle peut voir sa taille renvoyée dans une valeur de type std::size_t, ce qui est donc acceptable. En revanche, si un objet occupait plus de 4 294 967 295 octets, sizeof ne pourrait pas en donner la taille exacte, car la valeur sortirait de l'intervalle d'un std::size_t. Aucun objet de plus de 4 294 967 295 octets ne peut donc être créé sur ce système.

En passant…

La taille de std::size_t impose une limite mathématique stricte à la taille d'un objet. En pratique, l'objet le plus grand pouvant être créé peut être plus petit que cette limite (parfois nettement).

Certains compilateurs limitent la taille maximale d'un objet à la moitié de la valeur maximale de std::size_t (une explication se trouve ici).

D'autres facteurs peuvent aussi jouer, comme la quantité de mémoire contiguë disponible pour l'allocation sur votre ordinateur.

À l'époque où les applications 8 et 16 bits étaient la norme, cette limite imposait une contrainte importante sur la taille des objets. À l'ère des 32 et 64 bits, elle pose rarement problème, et vous n'avez généralement pas à vous en préoccuper.
