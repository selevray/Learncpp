21.4 — Surcharge des opérateurs d'entrée et de sortie

Pour les classes qui possèdent plusieurs variables membres, afficher chacune d'elles à l'écran devient vite fastidieux. Par exemple, considérez la classe suivante :

class Point
{
private:
    double m_x{};
    double m_y{};
    double m_z{};

public:
    Point(double x=0.0, double y=0.0, double z=0.0)
      : m_x{x}, m_y{y}, m_z{z}
    {
    }

    double getX() const { return m_x; }
    double getY() const { return m_y; }
    double getZ() const { return m_z; }
};

Si vous souhaitez afficher une instance de cette classe à l'écran, vous devriez faire quelque chose comme ceci :

Point point { 5.0, 6.0, 7.0 };

std::cout << "Point(" << point.getX() << ", " <<
    point.getY() << ", " <<
    point.getZ() << ')';

Il est évidemment préférable d'en faire une fonction réutilisable. Dans les exemples précédents, nous avons déjà créé des fonctions print() qui fonctionnent ainsi :

class Point
{
private:
    double m_x{};
    double m_y{};
    double m_z{};

public:
    Point(double x=0.0, double y=0.0, double z=0.0)
      : m_x{x}, m_y{y}, m_z{z}
    {
    }

    double getX() const { return m_x; }
    double getY() const { return m_y; }
    double getZ() const { return m_z; }

    void print() const
    {
        std::cout << "Point(" << m_x << ", " << m_y << ", " << m_z << ')';
    }
};

C'est bien mieux, mais cette approche présente encore quelques inconvénients. Comme print() renvoie void, elle ne peut pas être appelée au milieu d'une instruction d'affichage. Il faut donc écrire ceci :

int main()
{
    const Point point { 5.0, 6.0, 7.0 };

    std::cout << "My point is: ";
    point.print();
    std::cout << " in Cartesian space.\n";
}

Il serait bien plus simple d'écrire directement :

Point point{5.0, 6.0, 7.0};
cout << "My point is: " << point << " in Cartesian space.\n";

et d'obtenir le même résultat. Il ne serait plus nécessaire de découper l'affichage en plusieurs instructions, ni de se souvenir du nom de la fonction d'affichage.

Heureusement, en surchargeant operator<<, c'est possible !

Surcharge de operator<<

La surcharge de operator<< ressemble à celle de operator+ (ce sont tous deux des opérateurs binaires), à ceci près que les types des paramètres sont différents.

Considérez l'expression std::cout << point. Si l'opérateur est <<, quels sont les opérandes ? L'opérande de gauche est l'objet std::cout, et celui de droite est l'objet de votre classe Point. std::cout est en réalité un objet de type std::ostream. Notre fonction surchargée ressemblera donc à ceci :

// std::ostream est le type de l'objet std::cout
friend std::ostream& operator<< (std::ostream& out, const Point& point);

L'implémentation de operator<< pour notre classe Point est assez simple : comme C++ sait déjà afficher des double avec operator<<, et que nos membres sont tous des double, nous pouvons simplement utiliser operator<< pour afficher les membres de données de notre Point. Voici la classe Point précédente, complétée par l'opérateur operator<< surchargé.

#include <iostream>

class Point
{
private:
    double m_x{};
    double m_y{};
    double m_z{};

public:
    Point(double x=0.0, double y=0.0, double z=0.0)
      : m_x{x}, m_y{y}, m_z{z}
    {
    }

    friend std::ostream& operator<< (std::ostream& out, const Point& point);
};

std::ostream& operator<< (std::ostream& out, const Point& point)
{
    // Comme operator<< est une fonction amie de la classe Point, nous pouvons accéder directement à ses membres.
    out << "Point(" << point.m_x << ", " << point.m_y << ", " << point.m_z << ')'; // l'affichage réel se fait ici

    return out; // on renvoie std::ostream pour pouvoir enchaîner les appels à operator<<
}

int main()
{
    const Point point1 { 2.0, 3.0, 4.0 };

    std::cout << point1 << '\n';

    return 0;
}

C'est assez direct. Remarquez à quel point la ligne d'affichage ressemble à celle de la fonction print() écrite précédemment. La différence la plus notable est que std::cout est devenu le paramètre out (qui sera une référence à std::cout lors de l'appel de la fonction).

La partie la plus délicate concerne le type de retour. Avec les opérateurs arithmétiques, nous calculions et renvoyions un résultat unique par valeur (puisque nous créions et renvoyions un nouveau résultat). En revanche, si vous essayez de renvoyer un std::ostream par valeur, vous obtiendrez une erreur de compilation. Cela vient du fait que std::ostream interdit explicitement d'être copié.

Ici, nous renvoyons le paramètre de gauche par référence. Cela évite non seulement de copier le std::ostream, mais permet aussi d'« enchaîner » les commandes d'affichage, comme dans std::cout << point << '\n'.

Voyons ce qui se passerait si notre operator<< renvoyait void. Lorsque le compilateur évalue std::cout << point << '\n', en raison des règles de priorité et d'associativité, il évalue cette expression comme (std::cout << point) << '\n';. std::cout << point appellerait notre fonction operator<< qui renvoie void. L'expression partiellement évaluée devient alors void << '\n';, ce qui n'a aucun sens !

En renvoyant plutôt le paramètre out, (std::cout << point) renvoie std::cout. L'expression partiellement évaluée devient alors std::cout << '\n';, qui est à son tour évaluée !

Chaque fois que nous voulons que nos opérateurs binaires surchargés puissent être enchaînés de cette manière, l'opérande de gauche doit être renvoyé (par référence). Renvoyer par référence le paramètre de gauche est acceptable ici : comme ce paramètre a été passé par la fonction appelante, il doit encore exister quand la fonction appelée se termine. Nous n'avons donc pas à craindre de référencer un objet qui sortirait de portée et serait détruit à la fin de l'opérateur.

Pour le prouver, considérez l'exemple suivant, qui utilise la classe Point avec l'opérateur operator<< surchargé écrit ci-dessus :

#include <iostream>

class Point
{
private:
    double m_x{};
    double m_y{};
    double m_z{};

public:
    Point(double x=0.0, double y=0.0, double z=0.0)
      : m_x{x}, m_y{y}, m_z{z}
    {
    }

    friend std::ostream& operator<< (std::ostream& out, const Point& point);
};

std::ostream& operator<< (std::ostream& out, const Point& point)
{
    // Comme operator<< est une fonction amie de la classe Point, nous pouvons accéder directement à ses membres.
    out << "Point(" << point.m_x << ", " << point.m_y << ", " << point.m_z << ')';

    return out;
}

int main()
{
    Point point1 { 2.0, 3.5, 4.0 };
    Point point2 { 6.0, 7.5, 8.0 };

    std::cout << point1 << ' ' << point2 << '\n';

    return 0;
}

Ce programme produit le résultat suivant :


Point(2, 3.5, 4) Point(6, 7.5, 8)

Dans l'exemple ci-dessus, operator<< est une fonction amie parce qu'elle a besoin d'un accès direct aux membres de Point. En revanche, si les membres pouvaient être lus via des accesseurs (getters), operator<< pourrait être implémenté comme une fonction non amie.

Surcharge de operator>>

Il est également possible de surcharger l'opérateur d'entrée. Cela se fait de manière analogue à la surcharge de l'opérateur de sortie. L'élément clé à connaître est que std::cin est un objet de type std::istream. Voici notre classe Point avec un operator>> surchargé ajouté :

#include <iostream>

class Point
{
private:
    double m_x{};
    double m_y{};
    double m_z{};

public:
    Point(double x=0.0, double y=0.0, double z=0.0)
      : m_x{x}, m_y{y}, m_z{z}
    {
    }

    friend std::ostream& operator<< (std::ostream& out, const Point& point);
    friend std::istream& operator>> (std::istream& out, Point& point);
};

std::ostream& operator<< (std::ostream& out, const Point& point)
{
    // Comme operator<< est une fonction amie de la classe Point, nous pouvons accéder directement à ses membres.
    out << "Point(" << point.m_x << ", " << point.m_y << ", " << point.m_z << ')';

    return out;
}

// notez que point doit être non const afin que nous puissions modifier l'objet
std::istream& operator>> (std::istream& in, Point& point)
{
    // Cette version est sujette aux problèmes d'extraction partielle (voir ci-dessous)
    in >> point.m_x >> point.m_y >> point.m_z;

    return in;
}

int main()
{
    std::cout << "Enter a point: ";

    Point point{ 1.0, 2.0, 3.0 }; // données de test non nulles
    std::cin >> point;

    std::cout << "You entered: " << point << '\n';

    return 0;
}

En supposant que l'utilisateur saisisse 4.0 5.6 7.26, le programme produit le résultat suivant :


You entered: Point(4, 5.6, 7.26)

Voyons maintenant ce qui se passe lorsque l'utilisateur saisit 4.0b 5.6 7.26 (remarquez le b après le 4.0) :


You entered: Point(4, 0, 3)

Notre point est désormais un hybride étrange : une valeur provient de la saisie de l'utilisateur (4.0), une valeur a été initialisée à zéro (0.0), et une valeur n'a pas été modifiée par la fonction d'entrée (3.0). Ce n'est pas vraiment satisfaisant !

Prévenir l'extraction partielle

Lorsque nous extrayons une seule valeur, il n'existe que deux issues possibles : l'extraction échoue ou elle réussit. En revanche, lorsque nous extrayons plusieurs valeurs au cours d'une opération d'entrée, les choses se compliquent.

L'implémentation ci-dessus de operator>> peut conduire à une extraction partielle, et c'est exactement ce que l'on observe avec la saisie 4.0b 5.6 7.26. L'extraction vers m_x réussit à lire 4.0 dans la saisie de l'utilisateur, laissant b 5.6 7.26 dans le flux d'entrée. L'extraction vers m_y échoue à lire b, donc m_y reçoit par copie la valeur 0.0 et le flux d'entrée passe en mode échec. Comme nous n'avons pas effacé ce mode d'échec, l'extraction vers m_z s'interrompt immédiatement, et m_z conserve sa valeur d'avant la tentative (3.0).

Ce résultat n'est jamais souhaitable, et dans certains cas il peut même être dangereux. Imaginez que nous écrivions plutôt un operator>> pour un objet Fraction. Après avoir extrait avec succès le numérateur, une extraction échouée pour le dénominateur mettrait celui-ci à 0.0, ce qui pourrait ensuite provoquer une division par zéro et faire planter l'application.

Comment éviter cela ? Une solution consiste à rendre nos opérations transactionnelles. Une opération transactionnelle doit soit réussir complètement, soit échouer complètement : aucun succès ou échec partiel n'est autorisé. C'est ce que l'on appelle parfois le principe « tout ou rien ». Si un échec survient à n'importe quel moment de la transaction, les modifications déjà effectuées par l'opération doivent être annulées.

Point clé

Les transactions se produisent constamment dans la vie réelle. Prenons le cas où je souhaite transférer de l'argent d'un compte bancaire à un autre. Cela demande deux étapes : l'argent doit d'abord être débité d'un compte, puis crédité sur l'autre. Lors de l'exécution de cette opération, trois issues sont possibles :

  • L'étape de débit échoue (par exemple, fonds insuffisants). La transaction échoue, et aucun des deux soldes ne reflète le transfert.
  • L'étape de crédit échoue (par exemple, à cause d'un problème technique). Dans ce cas, le débit, qui a déjà réussi, doit être annulé. La transaction échoue, et aucun des deux soldes ne reflète le transfert.
  • Les deux étapes réussissent. La transaction est un succès, et les deux soldes reflètent le transfert.

Au final, il n'existe que deux issues possibles : soit le transfert échoue complètement et les soldes restent inchangés, soit il réussit et les deux soldes sont modifiés.

Réimplémentons notre operator>> surchargé pour Point comme une opération transactionnelle :

// notez que point doit être non const afin que nous puissions modifier l'objet
// notez que cette implémentation est une fonction non amie
std::istream& operator>> (std::istream& in, Point& point)
{
    double x{};
    double y{};
    double z{};

    if (in >> x >> y >> z)      // si toutes les extractions ont réussi
        point = Point{x, y, z}; // on remplace notre point existant

    return in;
}

Dans cette implémentation, nous n'écrasons pas directement les membres de données avec la saisie de l'utilisateur. Nous extrayons plutôt cette saisie dans des variables temporaires (x, y et z). Une fois toutes les tentatives d'extraction terminées, nous vérifions si elles ont toutes réussi. Si c'est le cas, nous mettons à jour tous les membres de Point en même temps. Sinon, nous n'en mettons à jour aucun.

Astuce

if (in >> x >> y >> z) est équivalent à in >> x >> y >> z; if (in). Rappelez-vous que chaque extraction renvoie in afin que plusieurs extractions puissent être enchaînées. La version en une seule instruction utilise le in renvoyé par la dernière extraction comme condition de l'instruction if, alors que la version en plusieurs instructions utilise explicitement in.

Astuce

Les opérations transactionnelles peuvent être implémentées selon plusieurs stratégies. Par exemple :

  • Modifier en cas de succès : on stocke le résultat de chaque sous-opération. Si toutes les sous-opérations réussissent, on remplace les données concernées par les résultats stockés. C'est la stratégie utilisée dans l'exemple Point ci-dessus.
  • Restaurer en cas d'échec : on copie toutes les données susceptibles d'être modifiées. Si une sous-opération échoue, les modifications apportées par les sous-opérations précédentes peuvent être annulées à l'aide de la copie.
  • Annuler (rollback) en cas d'échec : si une sous-opération échoue, chaque sous-opération précédente est annulée au moyen d'une sous-opération inverse. Cette stratégie est souvent utilisée dans les bases de données, où les données sont trop volumineuses pour être sauvegardées, et où le résultat des sous-opérations ne peut pas être stocké.

Bien que l'operator>> ci-dessus empêche les extractions partielles, il est incohérent avec le comportement de operator>> pour les types fondamentaux. Lorsqu'une extraction vers un objet de type fondamental échoue, l'objet n'est pas laissé inchangé : il reçoit par copie la valeur 0 (cela garantit que l'objet possède une valeur cohérente si la tentative d'extraction a lieu alors qu'il n'était pas initialisé). Pour rester cohérent, vous pouvez donc souhaiter qu'une extraction échouée réinitialise l'objet à son état par défaut (du moins lorsqu'un tel état existe).

Voici une version alternative de operator>> qui réinitialise Point à son état par défaut si une extraction échoue :

// notez que point doit être non const afin que nous puissions modifier l'objet
// notez que cette implémentation est une fonction non amie
std::istream& operator>> (std::istream& in, Point& point)
{
    double x{};
    double y{};
    double z{};

    in >> x >> y >> z;
    point = in ? Point{x, y, z} : Point{};

    return in;
}

Note de l'auteur

Une telle opération n'est plus à proprement parler transactionnelle (puisqu'un échec ne « ne fait rien »). Il ne semble pas exister de terme général pour désigner les opérations qui garantissent l'absence de résultats partiels. Peut-être « opération indivisible ».

Gérer les saisies sémantiquement invalides

L'extraction peut échouer de différentes manières.

Lorsque operator>> ne parvient tout simplement pas à extraire quoi que ce soit dans une variable, std::cin passe automatiquement en mode échec (ce que nous étudions dans la leçon 9.5 — std::cin et gestion des entrées invalides). L'appelant de cette fonction peut alors vérifier std::cin pour savoir si l'opération a échoué, et traiter ce cas comme il convient.

Mais qu'en est-il des cas où l'utilisateur saisit une valeur extractible mais sémantiquement invalide (par exemple, une Fraction dont le dénominateur vaut 0) ? Comme std::cin a bien extrait quelque chose, il ne passe pas automatiquement en mode échec. L'appelant ne se rendra alors probablement pas compte qu'une erreur s'est produite.

Pour y remédier, notre operator>> surchargé peut déterminer si l'une des valeurs extraites est sémantiquement invalide et, le cas échéant, placer manuellement le flux d'entrée en mode échec. Cela se fait en appelant std::cin.setstate(std::ios_base::failbit);.

Voici un exemple d'operator>> transactionnel surchargé pour Point qui fera passer le flux d'entrée en mode échec si l'utilisateur saisit une valeur négative extractible :

std::istream& operator>> (std::istream& in, Point& point)
{
    double x{};
    double y{};
    double z{};

    in >> x >> y >> z;
    if (x < 0.0 || y < 0.0 || z < 0.0)       // si une valeur saisie et extraite est négative
        in.setstate(std::ios_base::failbit); // on passe manuellement en mode échec
    point = in ? Point{x, y, z} : Point{};

    return in;
}

Conclusion

La surcharge de operator<< et de operator>> permet d'afficher facilement votre classe à l'écran et d'accepter la saisie de l'utilisateur depuis la console.

Question n° 1

int main()

    std::cin >> f1;

    Fraction f2{};
    std::cout << "Enter fraction 2: ";
    std::cin >> f2;

Et produire le résultat suivant :


Enter fraction 1: 2/3
Enter fraction 2: 3/8

Voici la classe Fraction :

#include <iostream>
#include <numeric> // pour std::gcd

class Fraction
{
private:
    int m_numerator{};
    int m_denominator{};

public:
    Fraction(int numerator=0, int denominator=1):
        m_numerator{numerator}, m_denominator{denominator}
    {
        // Nous plaçons reduce() dans le constructeur pour garantir que toute nouvelle fraction créée est réduite !
        // Les fractions écrasées devront être réduites à nouveau
        reduce();
    }

    void reduce()
    {
        int gcd{ std::gcd(m_numerator, m_denominator) };
        if (gcd)
        {
            m_numerator /= gcd;
            m_denominator /= gcd;
        }
    }

    friend Fraction operator*(const Fraction& f1, const Fraction& f2);
    friend Fraction operator*(const Fraction& f1, int value);
    friend Fraction operator*(int value, const Fraction& f1);

    void print() const
    {
        std::cout << m_numerator << '/' << m_denominator << '\n';
    }
};

}

Fraction operator*(const Fraction& f1, int value)
{
    return Fraction { f1.m_numerator * value, f1.m_denominator };
}

{
    return Fraction { f1.m_numerator * value, f1.m_denominator };

#include <limits>
#include <numeric> // pour std::gcd

class Fraction
{
private:
    int m_numerator{ 0 };
    int m_denominator{ 1 };

public:
    Fraction(int numerator=0, int denominator = 1) :
        m_numerator{ numerator }, m_denominator{ denominator }
    {
        // Nous plaçons reduce() dans le constructeur pour garantir que toute nouvelle fraction créée est réduite !
        // Les fractions écrasées devront être réduites à nouveau
        reduce();
    }

    void reduce()
    {
        int gcd{ std::gcd(m_numerator, m_denominator) };
        if (gcd)
        {
            m_numerator /= gcd;
            m_denominator /= gcd;
        }
    }

    friend Fraction operator*(const Fraction& f1, const Fraction& f2);
    friend Fraction operator*(const Fraction& f1, int value);
    friend Fraction operator*(int value, const Fraction& f1);

    friend std::ostream& operator<<(std::ostream& out, const Fraction& f1);

    void print() const
    {
        std::cout << m_numerator << '/' << m_denominator << '\n';
    }
};

Fraction operator*(const Fraction& f1, const Fraction& f2)
{
    return Fraction { f1.m_numerator * f2.m_numerator, f1.m_denominator * f2.m_denominator };
}

Fraction operator*(const Fraction& f1, int value)
{
    return Fraction { f1.m_numerator * value, f1.m_denominator };
}

Fraction operator*(int value, const Fraction& f1)
{
    return Fraction { f1.m_numerator * value, f1.m_denominator };
}

std::ostream& operator<<(std::ostream& out, const Fraction& f1)
{
    out << f1.m_numerator << '/' << f1.m_denominator;
    return out;
}

std::istream& operator>>(std::istream& in, Fraction& f1)
{
    int numerator {};
    char ignore {};
    int denominator {};

    in >> numerator >> ignore >> denominator;
    if (denominator == 0)                       // si notre dénominateur est sémantiquement invalide
        in.setstate(std::ios_base::failbit);    // on passe manuellement en mode échec

        f1 = Fraction {numerator, denominator}; // on met à jour notre objet avec les valeurs extraites

    return in;
}
