21.11 — Surcharge des transtypages (typecasts)

Dans la leçon 10.6 -- Conversion explicite de types (transtypage) et static_cast, vous avez appris que C++ permet de convertir un type de données en un autre. L'exemple suivant convertit un int en double :

int n{ 5 };
auto d{ static_cast<double>(n) }; // conversion de int en double

C++ sait déjà convertir entre les types de données fondamentaux. En revanche, par défaut, il ne sait pas convertir les classes que nous définissons nous-mêmes.

Dans la leçon 14.16 -- Constructeurs de conversion et le mot-clé explicit, nous avons montré comment utiliser un constructeur de conversion pour créer un objet d'un type classe à partir d'un objet d'un autre type. Mais cela ne fonctionne que si le type de destination est une classe que l'on peut modifier pour y ajouter ce constructeur. Que faire si ce n'est pas le cas ?

Examinons la classe suivante :

class Cents
{
private:
    int m_cents{};
public:
    Cents(int cents=0)
        : m_cents{ cents }
    {
    }

    int getCents() const { return m_cents; }
    void setCents(int cents) { m_cents = cents; }
};

Cette classe est assez simple : elle stocke un nombre de centimes sous forme d'entier et fournit des fonctions d'accès pour lire et modifier ce nombre. Elle fournit également un constructeur permettant de convertir un int en Cents.

Si nous pouvons convertir un int en Cents (grâce à un constructeur), nous pourrions aussi vouloir fournir un moyen de convertir un Cents en int. Dans certains cas, ce n'est pas souhaitable, mais ici cela a du sens.

Note de l'auteur

Un poème :

Convertir nos int en quelques Cents
Demandera un constructeur consentant
Bien sûr, convertir Cents en int a aussi du sens
Mais le compilateur crie à l'erreur et s'y oppose.

Pour autoriser ces conversions
Nous donnons notre accord au compilateur
Puis nous définissons comment, pour toutes les intentions,
Transformer ces types de contenus.

Quelle est donc la syntaxe qui contourne
La défense de typage statique du compilateur ?
Nous le détaillerons très bientôt, et ainsi
Vous ne resterez plus dans le suspense.

Une solution peu satisfaisante consiste à utiliser une fonction de conversion. Dans cet exemple, nous utilisons la fonction membre getCents() pour « convertir » notre variable Cents en int afin de l'afficher avec printInt() :

#include <iostream>

void printInt(int value)
{
    std::cout << value;
}

int main()
{
    Cents cents{ 7 };
    printInt(cents.getCents()); // affiche 7

    std::cout << '\n';

    return 0;
}

Bien que cette fonction produise le résultat souhaité, il ne s'agit pas vraiment d'une conversion : le compilateur ne comprend pas qu'il doit utiliser cette fonction pour les transtypages ou les conversions implicites. De plus, si nous effectuons beaucoup de conversions de Cents vers int, notre code sera encombré d'appels à getCents(), ce qui est peu élégant.

Que pouvons-nous faire d'autre ?

Surcharger un transtypage

C'est ici qu'intervient la surcharge des opérateurs de transtypage. Un tel transtypage peut être utilisé explicitement (via un cast) ou implicitement par le compilateur pour effectuer les conversions nécessaires.

Montrons comment surcharger un transtypage pour définir une conversion de Cents vers int :

class Cents
{
private:
    int m_cents{};
public:
    Cents(int cents=0)
        : m_cents{ cents }
    {
    }

    // Transtypage int surchargé
    operator int() const { return m_cents; }

    int getCents() const { return m_cents; }
    void setCents(int cents) { m_cents = cents; }
};

Pour cela, nous avons écrit un nouvel opérateur surchargé nommé operator int(). Notez qu'il y a un espace entre le mot operator et le type vers lequel nous transtypons.

Quelques points méritent d'être notés ici :

  • Les transtypages surchargés doivent être des membres non statiques, et doivent être const afin de pouvoir être utilisés avec des objets constants.
  • Les transtypages surchargés n'ont pas de paramètres explicites, car il n'existe aucun moyen de leur passer des arguments explicites. Ils ont tout de même un paramètre caché *this, qui pointe vers l'objet implicite (c'est-à-dire l'objet à convertir).
  • Les transtypages surchargés ne déclarent pas de type de retour. Le nom de la conversion (par exemple int) sert de type de retour, car c'est le seul type de retour autorisé. Cela évite une redondance dans la déclaration.

Dans notre exemple, nous pouvons maintenant appeler printInt() de cette façon :

#include <iostream>

int main()
{
    Cents cents{ 7 };
    printInt(cents); // affiche 7

    std::cout << '\n';

    return 0;
}

Le compilateur remarque d'abord que la fonction printInt() possède un paramètre de type int. Il constate ensuite que la variable cents n'est pas un int. Enfin, il vérifie si nous avons fourni un moyen de convertir un Cents en int. C'est le cas : il appelle donc notre fonction operator int(), qui renvoie un int, et ce int est passé à printInt().

De tels transtypages peuvent aussi être invoqués explicitement via static_cast :

std::cout << static_cast<int>(cents);

Vous pouvez fournir des transtypages surchargés pour tout type de données souhaité, y compris vos propres types définis par le programme !

Voici une nouvelle classe appelée Dollars qui fournit une conversion surchargée vers Cents :

class Dollars
{
private:
    int m_dollars{};
public:
    Dollars(int dollars=0)
        : m_dollars{ dollars }
    {
    }

     // Permet de convertir Dollars en Cents
     operator Cents() const { return Cents{ m_dollars * 100 }; }
};

Cela nous permet de convertir directement un objet Dollars en objet Cents ! Vous pouvez donc écrire quelque chose comme ceci :

#include <iostream>

class Cents
{
private:
    int m_cents{};
public:
    Cents(int cents=0)
        : m_cents{ cents }
    {
    }

    // Transtypage int surchargé
    operator int() const { return m_cents; }

    int getCents() const { return m_cents; }
    void setCents(int cents) { m_cents = cents; }
};

class Dollars
{
private:
    int m_dollars{};
public:
    Dollars(int dollars=0)
        : m_dollars{ dollars }
    {
    }

    // Permet de convertir Dollars en Cents
    operator Cents() const { return Cents { m_dollars * 100 }; }
};

void printCents(Cents cents)
{
    std::cout << cents; // cents sera implicitement converti en int ici
}

int main()
{
    Dollars dollars{ 9 };
    printCents(dollars); // dollars sera implicitement converti en Cents ici

    std::cout << '\n';

    return 0;
}

En conséquence, ce programme affiche la valeur :


900

ce qui est logique, puisque 9 dollars valent 900 centimes !

Bien que cela montre qu'une telle chose est possible, dans ce cas, ajouter à Dollars un constructeur de conversion (avec un paramètre de type Cents) est en réalité préférable. Nous expliquerons pourquoi plus bas.

Transtypages explicites

De même que nous pouvons rendre les constructeurs explicit pour qu'ils ne soient pas utilisés pour des conversions implicites, nous pouvons aussi rendre explicites nos transtypages surchargés, pour la même raison. Les transtypages explicites ne peuvent être invoqués que par un cast (par exemple static_cast) ou par une forme d'initialisation directe (avec parenthèses ou accolades). Ils ne sont pas pris en compte lors d'une initialisation par copie.

#include <iostream>

class Cents
{
private:
    int m_cents{};
public:
    Cents(int cents=0)
        : m_cents{ cents }
    {
    }

    explicit operator int() const { return m_cents; } // désormais marqué comme explicit

    int getCents() const { return m_cents; }
    void setCents(int cents) { m_cents = cents; }
};

class Dollars
{
private:
    int m_dollars{};
public:
    Dollars(int dollars=0)
        : m_dollars{ dollars }
    {
    }

    operator Cents() const { return Cents { m_dollars * 100 }; }
};

void printCents(Cents cents)
{
//  std::cout << cents;                   // ne fonctionne plus car cents ne se convertit plus implicitement en int
    std::cout << static_cast<int>(cents); // on peut utiliser à la place un transtypage explicite
}

int main()
{
    Dollars dollars{ 9 };
    printCents(dollars); // conversion implicite de Dollars en Cents acceptable car elle n'est pas marquée explicit

    std::cout << '\n';

    return 0;
}

Les transtypages doivent en général être marqués comme explicit. Des exceptions peuvent être faites lorsque la conversion produit à moindre coût un type défini par l'utilisateur similaire. Notre Dollars::operator Cents() n'a pas été marqué explicit, car il n'y a aucune raison d'empêcher qu'un objet Dollars soit utilisé partout où un Cents est attendu.

Bonne pratique

De même que les constructeurs de conversion à un seul paramètre doivent être marqués explicit, les transtypages doivent l'être, sauf lorsque le type vers lequel on convertit est essentiellement synonyme du type de destination.

Quand utiliser les constructeurs de conversion ou les transtypages surchargés

Les transtypages surchargés et les constructeurs de conversion remplissent des fonctions similaires :

  • Un constructeur de conversion est une fonction membre du type classe B qui définit comment créer un B à partir d'un A.
  • Un transtypage surchargé est une fonction membre du type classe A qui définit comment convertir un A en B.

Dans les deux cas, on part d'un A et on obtient un B. La principale différence entre les deux réside dans le fait que c'est A ou B qui « possède » la manière dont la conversion s'effectue.

Comme les deux approches nécessitent de définir une fonction membre, elles ne peuvent être utilisées que pour des types classe modifiables. Si A n'est pas un type classe modifiable, vous ne pouvez pas utiliser de transtypage surchargé. Si B n'est pas un type classe modifiable, vous ne pouvez pas utiliser de constructeur de conversion. Si aucun des deux n'est un type classe modifiable, vous devrez utiliser une fonction de conversion non membre à la place.

Lorsque A et B sont tous deux des types classe modifiables, nous pourrions utiliser l'une ou l'autre approche. Mais comme un seul des deux est nécessaire, laquelle faut-il privilégier ?

En général, un constructeur de conversion doit être préféré à un transtypage surchargé. À égalité par ailleurs, il est plus propre pour une classe de gérer elle-même sa construction, plutôt que de compter sur une autre classe pour la créer et l'initialiser.

Bonne pratique

Lorsque c'est possible, privilégiez les constructeurs de conversion et évitez les transtypages surchargés.

Il existe quelques cas où un transtypage surchargé est préférable :

  • Lorsqu'on fournit une conversion vers un type fondamental (puisque vous ne pouvez pas définir de constructeurs pour ces types). Le plus souvent, on s'en sert pour fournir une conversion vers bool, lorsqu'il est pertinent de pouvoir utiliser un objet dans une instruction conditionnelle.
  • Lorsque la conversion renvoie une référence ou une référence constante.
  • Lorsqu'on fournit une conversion vers un type auquel on ne peut pas ajouter de membres (par exemple une conversion vers std::vector, puisque vous ne pouvez pas non plus définir de constructeurs pour ce type).
  • Lorsque vous ne souhaitez pas que le type créé ait connaissance du type à partir duquel il est converti. Cela peut être utile pour éviter les dépendances circulaires.

Pour illustrer ce dernier point, std::string possède un constructeur permettant de créer une std::string à partir d'une std::string_view. Cela signifie que <string> doit inclure <string_view>. Si std::string_view avait un constructeur permettant de créer une std::string_view à partir d'une std::string, alors <string_view> devrait inclure <string>, ce qui créerait une dépendance circulaire entre les en-têtes.

À la place, std::string possède un transtypage surchargé qui gère la conversion de std::string vers std::string_view (ce qui ne pose pas de problème, puisqu'il inclut déjà <string_view>). std::string_view ne connaît pas du tout std::string et n'a donc pas besoin d'inclure <string>. Ainsi, la dépendance circulaire est évitée.

Lorsqu'un constructeur de conversion et un transtypage surchargé sont tous deux définis pour la même conversion, les deux sont pris en compte lors de la résolution de surcharge. Selon que le transtypage surchargé est constant ou non, que l'objet converti est constant ou non, et selon le type de cast ou d'initialisation utilisé (par copie ou directe), l'une ou l'autre fonction peut être choisie (ce qui peut conduire à privilégier un transtypage plutôt qu'un constructeur de conversion), ou le résultat peut être ambigu (provoquant une erreur de compilation). Pour cette raison, évitez de définir à la fois un transtypage surchargé et un constructeur de conversion capables d'assurer la même conversion.

Bonne pratique

Lorsque vous devez définir comment convertir un type A en un type B :

  • Si B est un type classe que vous pouvez modifier, privilégiez un constructeur de conversion de B créé à partir de A.
  • Sinon, si A est un type classe que vous pouvez modifier, utilisez un transtypage surchargé pour convertir A en B.
  • Sinon, utilisez une fonction non membre pour convertir A en B.
