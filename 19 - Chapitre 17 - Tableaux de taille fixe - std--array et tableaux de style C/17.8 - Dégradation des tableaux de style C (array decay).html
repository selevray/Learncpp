17.8 — Dégradation des tableaux de style C (array decay)

Le défi du passage de tableaux de style C

Les concepteurs du langage C avaient un problème. Considérez le programme simple suivant :

#include <iostream>

void print(int val)
{
    std::cout << val;
}

int main()
{
    int x { 5 };
    print(x);

    return 0;
}

Lorsque print(x) est appelée, la valeur de l'argument x (5) est copiée dans le paramètre val. Dans le corps de la fonction, la valeur de val (5) est affichée sur la console. Comme x est peu coûteux à copier, il n'y a aucun problème ici.

Considérez maintenant le programme similaire suivant, qui utilise un tableau d'entiers de style C de 1000 éléments au lieu d'un seul int :

#include <iostream>

void printElementZero(int arr[1000])
{
    std::cout << arr[0]; // affiche la valeur du premier élément
}

int main()
{
    int x[1000] { 5 };   // définit un tableau de 1000 éléments, x[0] est initialisé à 5
    printElementZero(x);

    return 0;
}

Ce programme se compile également et affiche la valeur attendue (5) sur la console.

Bien que le code de cet exemple soit similaire à celui de l'exemple précédent, son fonctionnement mécanique est un peu différent de ce que vous pourriez attendre (nous expliquerons cela ci-dessous). Cela vient de la solution que les concepteurs du C ont trouvée pour résoudre deux difficultés majeures.

Premièrement, copier un tableau de 1000 éléments à chaque appel de fonction est coûteux (et encore plus si les éléments sont d'un type coûteux à copier), donc nous voulons l'éviter. Mais comment ? Le C ne dispose pas de références, donc le passage par référence pour éviter de copier les arguments de fonction n'était pas une option.

Deuxièmement, nous voulons pouvoir écrire une seule fonction capable d'accepter des arguments tableaux de longueurs différentes. Idéalement, notre fonction printElementZero() de l'exemple ci-dessus devrait pouvoir être appelée avec des tableaux de n'importe quelle longueur (puisque l'élément 0 est garanti d'exister). Nous ne voulons pas avoir à écrire une fonction différente pour chaque longueur de tableau possible. Mais comment ? Le C n'a aucune syntaxe pour spécifier des tableaux de « longueur quelconque », ne prend pas en charge les modèles (templates), et les tableaux d'une longueur ne peuvent pas être convertis en tableaux d'une autre longueur (sans doute parce que cela impliquerait une copie coûteuse).

Les concepteurs du langage C ont trouvé une solution astucieuse (héritée par le C++ pour des raisons de compatibilité) qui résout ces deux problèmes :

#include <iostream>

void printElementZero(int arr[1000]) // ne fait pas de copie
{
    std::cout << arr[0]; // affiche la valeur du premier élément
}

int main()
{
    int x[7] { 5 };      // définit un tableau de 7 éléments
    printElementZero(x); // fonctionne d'une manière ou d'une autre !

    return 0;
}

D'une manière ou d'une autre, l'exemple ci-dessus passe un tableau de 7 éléments à une fonction attendant un tableau de 1000 éléments, sans qu'aucune copie ne soit effectuée. Dans cette leçon, nous allons explorer comment cela fonctionne.

Nous verrons aussi pourquoi la solution retenue par les concepteurs du C est dangereuse et peu adaptée à l'usage du C++ moderne.

Mais d'abord, nous devons aborder deux sous-sujets.

Conversions de tableau en pointeur (dégradation de tableau)

Dans la plupart des cas, lorsqu'un tableau de style C est utilisé dans une expression, il est implicitement converti en un pointeur vers le type des éléments, initialisé avec l'adresse du premier élément (d'indice 0). Familièrement, on appelle cela la dégradation de tableau (array decay), ou simplement dégradation (decay).

Vous pouvez le constater dans le programme suivant :

#include <iomanip> // pour std::boolalpha
#include <iostream>

int main()
{
    int arr[5]{ 9, 7, 5, 3, 1 }; // notre tableau contient des éléments de type int

    // D'abord, prouvons que arr se dégrade en pointeur int*

    auto ptr{ arr }; // l'évaluation dégrade arr, la déduction de type doit donner int*
    std::cout << std::boolalpha << (typeid(ptr) == typeid(int*)) << '\n'; // affiche true si le type de ptr est int*

    // Prouvons maintenant que le pointeur contient l'adresse du premier élément du tableau

    std::cout << std::boolalpha << (&arr[0] == ptr) << '\n';

    return 0;
}

Sur la machine de l'auteur, ce programme a affiché :


true
true

Il n'y a rien de spécial dans le pointeur auquel un tableau se dégrade. C'est un pointeur ordinaire qui contient l'adresse du premier élément.

De même, un tableau constant (par exemple const int arr[5]) se dégrade en pointeur vers const (const int*).

Conseil

En C++, il existe quelques cas courants où un tableau de style C ne se dégrade pas :

  1. Lorsqu'il est utilisé comme argument de sizeof() ou de typeid().
  2. Lorsque l'on prend l'adresse du tableau avec l'opérateur &.
  3. Lorsqu'il est passé comme membre d'un type classe.
  4. Lorsqu'il est passé par référence.

Comme les tableaux de style C se dégradent en pointeur dans la plupart des cas, il est courant de croire à tort que les tableaux sont des pointeurs. Ce n'est pas le cas. Un objet tableau est une séquence d'éléments, alors qu'un objet pointeur ne fait que contenir une adresse.

Les informations de type d'un tableau et d'un tableau dégradé sont différentes. Dans l'exemple ci-dessus, le tableau arr a le type int[5], alors que le tableau dégradé a le type int*. Notamment, le type tableau int[5] contient l'information de longueur, alors que le type pointeur int* issu de la dégradation ne la contient pas.

Point clé

Un pointeur issu de la dégradation d'un tableau ne sait pas quelle est la longueur du tableau vers lequel il pointe. Le terme « dégradation » désigne cette perte d'information de longueur dans le type.

Utiliser l'indexation d'un tableau de style C applique en fait operator[] au pointeur issu de la dégradation

Comme un tableau de style C se dégrade en pointeur lorsqu'il est évalué, l'indexation d'un tableau de style C opère en réalité sur le pointeur issu de la dégradation :

#include <iostream>

int main()
{
    const int arr[] { 9, 7, 5, 3, 1 };
    std::cout << arr[2]; // indexe le tableau dégradé pour obtenir l'élément 2, affiche 5

    return 0;
}

Nous pouvons aussi utiliser operator[] directement sur un pointeur. Si ce pointeur contient l'adresse du premier élément, le résultat sera identique :

#include <iostream>

int main()
{
    const int arr[] { 9, 7, 5, 3, 1 };

    const int* ptr{ arr };  // arr se dégrade en pointeur
    std::cout << ptr[2];    // indexe ptr pour obtenir l'élément 2, affiche 5

    return 0;
}

Nous verrons dans un instant où cela est pratique, et nous étudierons plus en détail le fonctionnement de ce mécanisme (ainsi que ce qui se passe lorsque le pointeur contient autre chose que l'adresse du premier élément) dans la prochaine leçon 17.9 -- Arithmétique des pointeurs et indexation.

La dégradation résout notre problème de passage de tableaux de style C

La dégradation de tableau résout les deux difficultés évoquées au début de la leçon.

Lors du passage d'un tableau de style C en argument, le tableau se dégrade en pointeur, et c'est ce pointeur contenant l'adresse du premier élément du tableau qui est transmis à la fonction. Ainsi, bien que l'on ait l'impression de passer le tableau de style C par valeur, on le passe en réalité par adresse ! C'est ainsi que l'on évite de copier l'argument tableau.

Point clé

Les tableaux de style C sont passés par adresse, même lorsqu'il semble qu'ils soient passés par valeur.

Considérez maintenant deux tableaux différents, de même type d'éléments mais de longueurs différentes (par exemple int[5] et int[7]). Ce sont des types distincts, incompatibles entre eux. Pourtant, ils se dégradent tous deux en le même type de pointeur (ici int*). Leurs versions dégradées sont interchangeables ! Supprimer l'information de longueur du type nous permet de passer des tableaux de longueurs différentes sans incompatibilité de type.

Point clé

Deux tableaux de style C de même type d'éléments mais de longueurs différentes se dégradent en le même type de pointeur.

Dans l'exemple suivant, nous illustrerons deux choses :

  • Nous pouvons passer des tableaux de longueurs différentes à une seule fonction (car ils se dégradent tous deux en le même type de pointeur).
  • Le paramètre de fonction qui reçoit le tableau peut être un pointeur (const) vers le type des éléments du tableau.
#include <iostream>

void printElementZero(const int* arr) // passage par adresse constante
{
    std::cout << arr[0];
}

int main()
{
    const int prime[] { 2, 3, 5, 7, 11 };
    const int squares[] { 1, 4, 9, 25, 36, 49, 64, 81 };

    printElementZero(prime);   // prime se dégrade en pointeur const int*
    printElementZero(squares); // squares se dégrade en pointeur const int*

    return 0;
}

Cet exemple fonctionne parfaitement et affiche :


2
1

Dans main(), lorsque nous appelons printElementZero(prime), le tableau prime se dégrade d'un tableau de type const int[5] en un pointeur de type const int* contenant l'adresse du premier élément de prime. De même, lorsque nous appelons printElementZero(squares), squares se dégrade d'un tableau de type const int[8] en un pointeur de type const int* contenant l'adresse du premier élément de squares. Ce sont ces pointeurs de type const int* qui sont effectivement passés à la fonction en argument.

Comme nous passons des pointeurs de type const int*, notre fonction printElementZero() doit avoir un paramètre du même type de pointeur (const int*).

Dans cette fonction, nous indexons le pointeur pour accéder à l'élément de tableau choisi.

Comme un tableau de style C est passé par adresse, la fonction a un accès direct au tableau transmis (et non à une copie) et peut en modifier les éléments. Pour cette raison, il est recommandé de rendre le paramètre constant si votre fonction n'a pas l'intention de modifier les éléments du tableau.

Syntaxe du paramètre de fonction pour un tableau de style C

Un problème lié à la déclaration du paramètre de fonction sous la forme int* arr est qu'il n'est pas évident que arr doit être un pointeur vers un tableau de valeurs plutôt qu'un pointeur vers un simple entier. C'est pourquoi, lors du passage d'un tableau de style C, il est préférable d'utiliser la forme de déclaration alternative int arr[] :

#include <iostream>

void printElementZero(const int arr[]) // traité de la même façon que const int*
{
    std::cout << arr[0];
}

int main()
{
    const int prime[] { 2, 3, 5, 7, 11 };
    const int squares[] { 1, 4, 9, 25, 36, 49, 64, 81 };

    printElementZero(prime);  // prime se dégrade en pointeur
    printElementZero(squares); // squares se dégrade en pointeur

    return 0;
}

Ce programme se comporte de manière identique au précédent, car le compilateur interprète le paramètre const int arr[] comme const int*. Cette écriture a toutefois l'avantage d'indiquer à l'appelant que arr est censé être un tableau de style C dégradé, et non un pointeur vers une valeur unique. Notez qu'aucune information de longueur n'est nécessaire entre les crochets (puisqu'elle n'est de toute façon pas utilisée). Si une longueur est fournie, elle sera ignorée.

Bonne pratique

Un paramètre de fonction attendant un tableau de style C doit utiliser la syntaxe de tableau (par exemple int arr[]) plutôt que la syntaxe de pointeur (par exemple int *arr).

L'inconvénient de cette syntaxe est qu'elle rend moins évident le fait que arr s'est dégradé (alors que c'est tout à fait clair avec la syntaxe de pointeur). Vous devrez donc être particulièrement vigilant à ne pas faire, avec un tableau dégradé, quoi que ce soit qui ne fonctionne pas comme prévu (nous en verrons quelques-uns dans un instant).

Les problèmes de la dégradation de tableau

Bien que la dégradation de tableau ait été une solution astucieuse pour passer à une fonction des tableaux de style C de longueurs différentes sans effectuer de copies coûteuses, la perte de l'information de longueur favorise plusieurs types d'erreurs.

Premièrement, sizeof() ne renvoie pas la même valeur pour un tableau et pour un tableau dégradé :

#include <iostream>

void printArraySize(int arr[])
{
    std::cout << sizeof(arr) << '\n'; // affiche 4 (en supposant des adresses sur 32 bits)
}

int main()
{
    int arr[]{ 3, 2, 1 };

    std::cout << sizeof(arr) << '\n'; // affiche 12 (en supposant des int de 4 octets)

    printArraySize(arr);

    return 0;
}

Cela signifie que l'utilisation de sizeof() sur un tableau de style C est potentiellement dangereuse : vous devez vous assurer de ne l'utiliser que lorsque vous avez accès à l'objet tableau réel, et non au tableau ou au pointeur dégradé.

Dans la leçon précédente (17.7 -- Introduction aux tableaux de style C), nous avons mentionné que sizeof(arr)/sizeof(*arr) était historiquement utilisé comme astuce pour obtenir la taille d'un tableau de style C. Cette astuce est dangereuse : si arr s'est dégradé, sizeof(arr) renvoie la taille d'un pointeur et non celle du tableau, ce qui produit une longueur erronée et risque de faire dysfonctionner le programme.

Heureusement, le remplaçant plus sûr introduit en C++17, std::size() (et std::ssize() en C++20), ne compile pas s'il reçoit une valeur de type pointeur :

#include <iostream>

int printArrayLength(int arr[])
{
    std::cout << std::size(arr) << '\n'; // erreur de compilation : std::size() ne fonctionne pas sur un pointeur
}

int main()
{
    int arr[]{ 3, 2, 1 };

    std::cout << std::size(arr) << '\n'; // affiche 3

    printArrayLength(arr);

    return 0;
}

Deuxièmement, et sans doute le point le plus important, la dégradation de tableau peut rendre le refactoring (le découpage de longues fonctions en fonctions plus courtes et plus modulaires) difficile. Du code qui fonctionne correctement avec un tableau non dégradé peut ne pas compiler (ou, pire, dysfonctionner silencieusement) lorsqu'il utilise un tableau dégradé.

Troisièmement, l'absence d'information de longueur pose plusieurs problèmes de programmation. Sans cette information, il est difficile de vérifier la cohérence de la longueur du tableau. Les utilisateurs peuvent facilement passer des tableaux plus courts que prévu (voire des pointeurs vers une seule valeur), ce qui provoquera un comportement indéfini lors de l'indexation avec un indice invalide.

#include <iostream>

void printElement2(int arr[])
{
    // Comment s'assurer que arr contient au moins trois éléments ?
    std::cout << arr[2] << '\n';
}

int main()
{
    int a[]{ 3, 2, 1 };
    printElement2(a);  // ok

    int b[]{ 7, 6 };
    printElement2(b);  // se compile mais produit un comportement indéfini

    int c{ 9 };
    printElement2(&c); // se compile mais produit un comportement indéfini

    return 0;
}

L'absence de longueur du tableau pose aussi problème lors du parcours du tableau : comment savoir quand on a atteint la fin ?

Il existe des solutions à ces problèmes, mais elles ajoutent à la fois de la complexité et de la fragilité au programme.

Contourner les problèmes de longueur des tableaux

Historiquement, les programmeurs ont contourné l'absence d'information de longueur par l'une de deux méthodes.

La première consiste à passer à la fois le tableau et sa longueur en tant qu'arguments distincts :

#include <cassert>
#include <iostream>

void printElement2(const int arr[], int length)
{
    assert(length > 2 && "printElement2: Array too short"); // impossible d'utiliser static_assert sur length

    std::cout << arr[2] << '\n';
}

int main()
{
    constexpr int a[]{ 3, 2, 1 };
    printElement2(a, static_cast<int>(std::size(a)));  // ok

    constexpr int b[]{ 7, 6 };
    printElement2(b, static_cast<int>(std::size(b)));  // déclenchera l'assert

    return 0;
}

Cette méthode présente toutefois plusieurs inconvénients :

  • L'appelant doit s'assurer que le tableau et sa longueur correspondent : si une mauvaise valeur de longueur est passée, la fonction dysfonctionnera quand même.
  • Des problèmes de conversion de signe peuvent survenir si vous utilisez std::size() ou une fonction renvoyant une longueur sous la forme std::size_t.
  • Les assertions d'exécution ne se déclenchent que lorsqu'elles sont atteintes à l'exécution. Si nos tests ne couvrent pas tous les appels de la fonction, il existe un risque de livrer au client un programme qui échouera sur une assertion lorsqu'il fera quelque chose que nous n'avons pas explicitement testé. En C++ moderne, nous voudrions utiliser static_assert pour valider à la compilation la longueur d'un tableau constexpr, mais il n'existe pas de moyen simple de le faire (puisque les paramètres de fonction ne peuvent pas être constexpr, même dans des fonctions constexpr ou consteval !).
  • Cette méthode ne fonctionne que si nous effectuons un appel de fonction explicite. Si l'appel est implicite (par exemple lorsque nous appelons un opérateur dont le tableau est l'opérande), il n'y a aucune possibilité de passer la longueur.

La seconde méthode consiste, lorsqu'il existe une valeur d'élément sans signification sémantique valide (par exemple une note d'examen de -1), à marquer la fin du tableau à l'aide d'un élément de cette valeur. La longueur du tableau peut alors être calculée en comptant les éléments situés entre le début du tableau et cet élément terminal. Le tableau peut aussi être parcouru en itérant depuis le début jusqu'à rencontrer l'élément terminal. L'avantage de cette méthode est qu'elle fonctionne même avec des appels de fonction implicites.

Point clé

Les chaînes de style C (qui sont des tableaux de style C) utilisent un caractère nul de fin (null-terminator) pour marquer la fin de la chaîne, afin de pouvoir les parcourir même lorsqu'elles se sont dégradées.

Mais cette méthode présente également plusieurs inconvénients :

  • Si l'élément terminal n'existe pas, le parcours dépassera la fin du tableau, provoquant un comportement indéfini.
  • Les fonctions qui parcourent le tableau doivent traiter spécialement l'élément terminal (par exemple, une fonction d'affichage de chaîne de style C doit savoir ne pas afficher le caractère terminal).
  • Il existe un décalage entre la longueur réelle du tableau et le nombre d'éléments sémantiquement valides. Si une mauvaise longueur est utilisée, l'élément terminal sémantiquement invalide risque d'être « traité ».
  • Cette approche ne fonctionne que s'il existe une valeur sémantiquement invalide, ce qui n'est souvent pas le cas.

Les tableaux de style C doivent être évités dans la plupart des cas

Du fait de la sémantique de passage non standard (le passage par adresse est utilisé au lieu du passage par valeur) et des risques liés à la perte d'information de longueur des tableaux dégradés, les tableaux de style C sont généralement tombés en désuétude. Nous recommandons de les éviter autant que possible.

Bonne pratique

Évitez les tableaux de style C dès que cela est possible.

  • Privilégiez std::string_view pour les chaînes en lecture seule (constantes symboliques de chaînes littérales et paramètres de type chaîne).
  • Privilégiez std::string pour les chaînes modifiables.
  • Privilégiez std::array pour les tableaux constexpr non globaux.
  • Privilégiez std::vector pour les tableaux non constexpr.

Il est acceptable d'utiliser des tableaux de style C pour des tableaux constexpr globaux. Nous en discuterons dans un instant.

En passant…

En C++, les tableaux peuvent être passés par référence, auquel cas l'argument tableau ne se dégrade pas lors du passage à la fonction (mais la référence au tableau se dégrade toujours lorsqu'elle est évaluée). Toutefois, il est facile d'oublier de l'appliquer systématiquement, et une seule référence oubliée entraînera la dégradation des arguments. De plus, les paramètres de référence à un tableau doivent avoir une longueur fixe, ce qui signifie que la fonction ne peut traiter que des tableaux d'une longueur particulière. Si nous voulons une fonction capable de traiter des tableaux de longueurs différentes, nous devons aussi recourir aux modèles de fonctions. Mais si vous faites tout cela pour « corriger » les tableaux de style C, autant utiliser directement std::array !

Alors, quand utilise-t-on encore les tableaux de style C en C++ moderne ?

En C++ moderne, les tableaux de style C sont typiquement utilisés dans deux cas :

  1. Pour stocker des données de programme globales constexpr (ou statiques locales constexpr). Comme ces tableaux sont accessibles directement depuis n'importe où dans le programme, nous n'avons pas besoin de les passer en argument, ce qui évite les problèmes liés à la dégradation. La syntaxe de définition des tableaux de style C peut être un peu moins lourde que celle de std::array. Plus important encore, l'indexation de tels tableaux ne pose pas de problèmes de conversion de signe comme c'est le cas avec les classes conteneurs de la bibliothèque standard.
  2. Comme paramètres de fonctions ou de classes qui souhaitent manipuler directement des arguments de chaînes de style C non constexpr (plutôt que d'exiger une conversion en std::string_view). Il y a deux raisons possibles à cela : premièrement, convertir une chaîne de style C non constexpr en std::string_view exige de parcourir la chaîne pour déterminer sa longueur. Si la fonction se situe dans une section de code critique pour les performances et que la longueur n'est pas nécessaire (par exemple parce que la fonction va de toute façon parcourir la chaîne), éviter la conversion peut être utile. Deuxièmement, si la fonction (ou la classe) appelle d'autres fonctions qui attendent des chaînes de style C, convertir en std::string_view juste pour reconvertir ensuite peut être sous-optimal (sauf si vous avez d'autres raisons de vouloir un std::string_view).

Quiz

Question n° 1

Qu'est-ce que la dégradation de tableau, et pourquoi pose-t-elle problème ?

Solution

Lorsqu'un tableau de style C est évalué, il est, dans la plupart des contextes, implicitement converti en pointeur vers le type des éléments du tableau.

Les tableaux dégradés perdent leur information de longueur, ce qui facilite l'introduction de bogues liés à la longueur dans le programme.

Question n° 2

Pourquoi les chaînes de style C (qui sont des tableaux de style C) utilisent-elles un caractère nul de fin ?

Solution

Lorsqu'un tableau de style C est passé à une fonction, il se dégrade et perd son information de longueur. Si la chaîne de style C n'avait pas de caractère nul de fin, la fonction ne pourrait pas déterminer la longueur de la chaîne.

Question n° 3

Question bonus : pourquoi les chaînes de style C utilisent-elles un caractère nul de fin, plutôt que d'exiger que la chaîne dégradée et une information de longueur explicite soient toutes deux passées à une fonction ?

Solution

Il existe sans doute de nombreuses réponses à cette question, en voici quelques-unes :

  • L'ergonomie serait déplorable, puisque nous aurions des paramètres supplémentaires et des nombres magiques partout (par exemple printString("Hello", 5)).
  • Il serait très facile que la chaîne et la longueur fournie ne correspondent pas. La longueur de la chaîne est essentiellement un invariant de la chaîne elle-même. Compter sur l'utilisateur pour maintenir cet invariant conduira inévitablement à des erreurs (par exemple printString("Hello", 6)).

Question bonus n° 2 : même si le C++ avait voulu imposer de passer une information de longueur explicite, pourquoi cela ne fonctionnerait-il pas ?

Indice

Indice : considérez le cas où nous affichons une chaîne à l'aide de std::cout.

Solution

Passer à la fois la chaîne de style C et une information de longueur explicite n'est possible que si la fonction est appelée explicitement. Si une fonction est appelée implicitement, il n'existe aucun moyen de transmettre l'information de longueur.

Considérez une instruction comme std::cout << cstr. L'opérateur binaire operator<< ne peut prendre que deux opérandes : std::cout et cstr. Il n'y a aucun moyen de passer un argument supplémentaire représentant la longueur. L'approche du caractère nul de fin n'a pas ce problème.
